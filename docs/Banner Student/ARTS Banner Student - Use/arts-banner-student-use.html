Overview

The ® Automated Results Transfer System () use bundle provides information on procedures for producing the ARTS model, which is a unified system of reporting results and qualifications to a Tertiary Admissions Centre (TAC).

Note: This 9x version corresponds to the ARTS 8.3 release version.

model

is a system used by all education institutions who are members of a TAC to harmonise requests for educational history for individual students.

enables you to obtain electronic academic record information about current and former students who have made the application for admission through an admissions centre, and who have authorised the admissions centre to obtain records directly on their behalf.

The process begins with an admissions centre requesting academic record information about a current or past student of an institution by creating a single Request File containing identifying information supplied by the applicant.

Using the request process, the TAC performs the following tasks:
  • Creates a single request file containing the identified information supplied by the applicant
  • Places the request file on a target directory on your institution system.
After the request file is placed on a target directory, your institution performs the following tasks:
  • Validates the request (renames and copies the request file) to a working directory
  • Retrieves the academic record information and constructs a result file
  • Copies the result file back to the target directory
The admissions centre then monitors your institution's target directory to verify results file pickup and acknowledgment file deletion.
Banner enables institutions to perform the following tasks:
  • Process requests
  • Produce comprehensive and compliant responses
  • Transmit the responses back to the requesting TAC.

Functions and features

Banner is made up of various steps and processes.

These are organised as follows:
  • Set up procedures and pages are used to define elements, values, and processes that are required to produce the extracts.
  • Upload the request file: Importing and processing file procedures are used to extract data from the request file.
  • Create the ARTS response file: Procedures and file transformation tools are used to match applicants in the Request File to students in , and to produce corresponding results records.

automation

The automation feature provide institutions with easy and better user experience by capturing Capturing both structured and unstructured data seamlessly.

The automation helps institutions to not only improve the process of with minimum manual intervention, but also to allow a provision to set sleep wake mode in the Schedular feature through the SOPARTS process.
Using the Schedular feature, institutions can do the following:
  • Set system login parameters as per the person login requirements.
  • Provide secure file processing with the help of Secure File transfer Protocol (SFPT), and hence, no need for file encryption and decryption.
  • View file statuses, files error details if any, and re-process the file request.
  • Delete the request and request acknowledgment file from internal directory.
  • Delete the result file after reading the result acknowledgment.

Common matching

Common Matching is a process that helps your institution create and manage basic person records.

This key component of provides the ability to match applicant details supplied in the Request File to an enrolled student in . The matching process in uses Common Matching to find students and to help you understand how the applicants in the Request File are matched to the students in .

Baseline Common Matching is capable of matching both persons (students) and non-persons (companies). For purposes of , only persons are matched. The following section explains the Common Matching process.

Basic person information provided in the Request File and used in Common Matching includes the following items:
  • Name (current or former) or ID
  • Biographical information (date of birth).

Using Common Matching

The Common Matching process checks existing identification records to establish whether an applicant's details match.

About this task

While Common Matching also provides a mechanism to add new records to the database and update existing ones, only uses Common Matching to join requests to existing students; ARTS information is not used to update or create person records.

The default matching level is called the Standard level, which includes 11 possible combinations of matching criteria to be used in linking an applicant to a student record. When using Standard Matching, your institution should undertake a step-wise search of its computerised student records, using progressively looser matching criteria, to locate possible matches, all of which are reported in the Results File. All of these records are examined by the admissions centre, the correct matches identified, and non-matching records rejected. For the other searches, more precise matching levels are used where certain pieces of information can be clearly defined and established for the applicant, such as the student ID.

The basis for the match is returned by your institution for each result file student match record.

Applicants to the admissions centre sometimes transpose their given names or use their second given name only. No part of the third name or any subsequent given name is used in the matching process.

The student identification code and name matches are based on strings of characters from which all punctuation marks and spaces have been purged. In the case of name matches, the given names supplied by the admissions centre must be matched against the first given name in the academic records.

Where only the previous family name is supplied in the Request File, without previous given names, the current given names are used with the previous family name.

Note: Common Matching does not attempt to locate putative matches based on other combinations of data values supplied in the request record such as current family name and either previous given name, or all combinations of multiple previous family names and previous given names.

The matching level value in the request file header record specifies the matching process to be used by the record retrieving program at the target institution. The matching level enables the requesting admissions centre to specify the exact search criteria when searching for matching records.

Standard Matching Process

The following standard matching process is used for a search of your institution student records system.

About this task

Step 1 Attempt a match using criterion 1; if one or more matches are found, construct the results record(s).
Step 2 Attempt a match using criterion 2; if one or more matches are found, construct the results record(s) then go to Step 6.
Step 3 Attempt a match using criterion 3; if one or more matches are found, construct the results record(s).
Step 4 Attempt a match using criterion 4; if one or more matches are found, construct the results record(s) then go to Step 6.
Step 4.1 (Optionally) attempt a match using criterion 4a; if one or more matches are found, construct the results record(s) then go to Step 6.
Step 5 Attempt a match using criterion 5; if one or more matches are found, construct the results record(s) then go to Step 6.
Step 6 Attempt a match using criterion 6; if one or more new matches are found (using the student number for comparison and ignoring those where student numbers match), construct the results record(s).
Step 7 Attempt a match using criterion 7; if one or more new matches are found (using the student number for comparison and ignore those where student numbers match), construct the results record(s).
Step 8 Attempt a match using criterion 8; if one or more new matches are found (using the student number for comparison - ignore those where student numbers match), construct the results record(s) for the others.
Step 9 Attempt a match using criterion 9; if one or more new matches are found (using the student number for comparison - ignore those where student numbers match), construct the results record(s) for the others.

If any matches have been found in Steps 1 through 9, then finish.

Step 10 Attempt a match using criterion 10; if one or more matches are found, construct the results record(s).
Step 11 Attempt a match using criterion 11; if one or more matches are found, construct the results record(s).
Step 12 Attempt a match using criterion 12; if one or more new matches are found (using the student number for comparison - ignore those where student numbers match), construct the results record(s).
Step13 Attempt a match using criterion 13; if one or more new matches are found (using the student number for comparison - ignore those where student numbers match), construct the results record(s).

If matches are found in Steps 10 through 13, then finish.

Step 14 Attempt a match using criterion 14; if one or more matches are found, construct the results record(s).
Step 15 Attempt a match using criterion 15; if one or more new matches are found (using the student number for comparison - ignore those where student numbers match), construct the results record(s).

Components of Common Matching

The Common Matching process is made up of multiple components.

The Common Matching Algorithm

The Common Matching algorithm implements the steps listed in the Standard Matching Process section in accordance with the matching level provided in the Request File for each applicant.

The algorithm is invoked automatically when the matching activities are run. The algorithm draws on rules and sources that are described in this section.

Rules used to find matches in Common Matching are organised by Matching Source.

Each Matching Source will have a different code. For , the required Matching Sources have been provided by default and need no configuration to run. Use the following pages to view the Matching Source and Rules created for .

File details

This section provides more information about the files generated and processed in the system.

Request File

The Request File contains details of an admission centre applicant who was, or might currently be, enrolled as a student at your institution to which the request is targeted, and who has authorised the admissions centre to obtain academic records.

In most cases, an institution student identification code is provided, along with other identifying information.

The Request File format comprises a header record (always present), followed by zero or more applicant previous name record(s).The two record types are identified by the value of the record type code field, the first field of the record.

Results withheld

Result withheld flag identifies whether the course attempt records subordinate to a student match record that is withheld by the institution. Institutions can block the student’s results for non-payment of fees and charges, or for some other logical reasons.

In such cases, the value of the Result Withheld flag of the corresponding student match record is ‘M’ or ‘O’, and the course attempt record count of the corresponding student match record be zeroes. The options available are
  • M: Results withheld for this student because of outstanding fees or charges
  • O: Results withheld for this student for reason(s) other than outstanding fees or charges
  • N: Results not withheld for this student
The value of the course attempt record count must be ‘00’ for Result file student match records where the Result withheld flag is ‘M’ or ‘O'.
To map the Result Withheld flag value:
  1. Check the mapping in the SKARMAP page where the Banner value = AR,RH etc should be selected to apply Result withheld flag as 'M' and Banner value = TR,GH etc should be selected to apply Result withheld flag as 'O').
  2. Go to the STVHLDD page and select Trans Hold or Grad Hold or Grade Hold flag set as ‘Y’ to achieve Result withheld flag value ‘M’ or 'O'.
  3. Go to the SOAHOLD page and select the hold type as specified in the SKARMAP page.
  4. Save your record to map the Result Withheld value.

Define system parameters

There are several elements where the selection of the correct data depends on specific codes.

About this task

For example, the snapshot uses two system parameters to determine whether a unit is a TAFE (VET) unit or a Higher Education unit, for subject weighting purposes. If you have defined 'VE' as the level code signifying VET units, you would use this as the value in the VET-UNIT parameter, and if you have defined 'HE' as the level code signifying Higher Education units, you would use this as the value in the HE-UNIT parameter.

It is possible to record more than one level code value for each parameter, as long as the same level code value is not used for both parameters.

To support the connectivity between baseline codes and elements, a predefined set of system parameters is delivered with validation, and you must configure these parameters for use. You can modify the delivered parameters to meet your needs, or you can create new ones.

Only users with appropriate permissions use the following procedure to define or modify system parameters.

Procedure

  1. Access the Report System Parameters (SKARSYS) page.
  2. Enter the academic year code in the Academic Year field, then go to the next block.
  3. Enter the parameter for which you want to enter valid values in the Parameter field.
  4. Enter the valid value(s) for the parameter in the Value field.
    You can enter multiple values for each parameter, separated by a comma, up to 2,000 characters.
  5. If desired, enter information in the Description and Notes fields.
  6. Save your changes.

Copy system parameters to another year

System parameters are associated with an academic year. You can copy one year's parameter definitions to another, then modify the new definition as desired.

About this task

When you copy system parameter rules from one year to another, all rules are copied. System parameter rules cannot be deleted if the system required indicator is selected, but the parameter value can be updated to null. System parameter rules can be deleted after being copied to the new academic year, if the system required indicator is not selected.

You can copy rules forwards or backwards in time. The the only restriction is that you cannot copy system parameter rules to an academic year that already has system parameter rules.

If you attempt to copy parameters to a year for which at least one parameter has already been defined, the system does not perform the copy and displays an error message.

Use the following procedure to copy system parameters to another year:

Procedure

  1. Access the Report System Parameters (SKARSYS) page.
  2. Select Copy Rules to New Year.
  3. Enter the code of the academic year to be copied in the From Year field of the Copy Rules window.
  4. Enter the code of the academic year to which the definitions are to be copied in the To Year field.
  5. Select the Process Rule Copy button.
  6. Modify the parameter definitions. For details, see the Define system parameters section.

Define source rules on GORCMSC

After setting up Matching Source codes, you must define the rules that will be used with each source code.

About this task

Note: For , source rules are already created by default.
Use the following procedure to define the source rules on GORCMSC:

Procedure

  1. Go to the Common Matching Source Code Rules (GORCMSC) page.
  2. Choose a Matching Source code.
  3. Select the Transpose Date Month / Day check box if you want Common Matching to look for a match on the full birth date.

    If one is not found, it will then look at just the month and the day, and then transpose the month and day. For example, if you enter 01/05 on GOAMTCH, you will receive matches on January 5th and May 1st.

    Note: You must include the Birth Date element in your rule to use this option.
  4. Select the Transpose First Name / Last Name check box.
    This option allows for the first and last names to be transposed.

    For example, Thomas Lee = Lee Thomas.

  5. Select the Allow Alias Wildcard Use check box.

    This option appends a% (percent wild card character) to incoming data to search for similar rows in alias tables. For example, if you enter Bet on GOAMTCH, Common Matching will find Beth = Elizabeth in the alias table and return potential matches with a first or middle name of Elizabeth.

  6. Select the Allow Length Override check box.

    This option uses the length of incoming data to search for matches on name fields, if the length of data on the rule is greater than the data input. For example, assume that you have a rule that specifies a length of five for First Name. With the Allow Length Override option, if you enter Sam in First Name field on GOAMTCH, then potential matches that begin with Sam, such as Samuel, Samantha, and Samson will be found as potential matches.

  7. Select the Prevent ID Creation on API Failure check box.

    If you want to use this option, you must provide complete information for Address, Telephone or E-mail to create the new ID. You can proceed with ID creation by removing partial information.

    Note: This option does not affect batch loads.
  8. Select the Create Hierarchy of Display Using Defaults button to populate the Address, Telephone, and E-mail fields in the Hierarchy of Display blocks (GORCMDH table) from the Data Entry/Update Defaults values (GORCMSC table).
  9. Specify the default address, telephone, or e-mail types.
  10. If you want the Matching Source code to be able to use Common Matching batch elements (those that do not have the Online indicator checked), then leave the Use for Online Common Matching check box blank.

    This allows batch elements of the Matching Source code to be used during batch processing only. If you do select the Use for Online Common Matching check box, then when you are building your rules in the next step, you will be limited to only using elements in your matching rule that the user can input on GOAMTCH. These are the elements that have the Online check box selected on GORCMDD.

  11. Specify whether the source code will be used to match against person, nonperson, or both data by choosing the appropriate values for the Match Type field.
  12. Specify any forms that the user can access from GOAMTCH to see the details for potential matches.

    You may enter up to six forms and assign a sequence number for each, which determines the order in which the forms will be displayed when the user selects the Details button on GOAMTCH.

  13. Save the source rule.

Create matching rules on GORCMRL

By default, all the appropriate rules are created for .

About this task

After defining your source rules, use the following procedure to create matching rules.

Procedure

  1. Access the Common Matching Rules (GORCMRL) page.
  2. Choose a Source code.
  3. Go to the next block.
  4. Enter a priority and description for your first matching rule.
  5. Save the matching rule.

    The algorithm processes each rule that has been defined for the Matching Source code separately and completely, based on the priority given in the Rule Priorities block.

    If the Rule Set 1 determines that the input record is either New or Matched, the overall status that is returned for the record is New or Matched. No additional rules will be processed.

    Note: For online processing, the potential matches that result from processing the rules may be viewed online from the Potential Matches tab on the Common Matching Entry (GOAMTCH) page. Potential matches are listed in order by rule set.
  6. If you are creating a matching rule based on a Banner table, go to the Matching Rules tab and choose the data element you want to match on.
    Do the following for each data element:
    1. Indicate the length of the item to be used for matching.

      For example, 1 will match the first character in the Length field.

      Whenever a length is specified for a Data Element on the Common Matching Rules (GORCMRL) page, the comparison will be made using the rule length of the fields.

      For example, using the last name, the comparison will be between the Data Element length of the last name on the incoming record to the Data Element length of the last name in . If the rule length is 5, then the first five characters of the incoming record’s last name are compared to the first five characters of the last name.

      A negative length may be entered for the ID and SSN/SIN/TIN fields to reverse the order, to last to first. For example, if -5 is entered for the length of the ID, the last five characters of the ID for the incoming record will be compared to the last 5 characters of the ID stored in .

      We recommend that you do not use a negative length for SSN/SIN/TIN because it could create performance issues.

      For example, assume you set Rule Set 1 as follows:

      Last Name length: 4

      First Name length: 3

      ID length: -4

      Patricia Longnecker, A00027280

      The first 4 characters of the last name would be used: LONG. The first three characters of the first name would be used: PAT The last four characters of the ID would be used: 7280.

      SPRIDEN_SEARCH_LAST_NAME always needs to be required. Although it is possible to set up a primary rule on GORCMRL with the Match on Null--Yes or No field for SPRIDEN_SEARCH_LAST_NAME set to Yes, this is not supported or recommended, because doing so may cause incorrect results on GOAMTCH.

      Because primary match logic uses last name/non-person name (SPRIDEN_SEARCH_LAST_NAME), a required data element for Common Matching, you must set the Match on Null--Yes or No field for SPRIDEN_SEARCH_LAST_NAMEto No.

      Note: Negative length on GORCMRL--Baseline Common Matching can only handle negative GORCMRL length for two fields, SPBPERS_SSN and SPRIDEN_ID. Negative lengths are not supported for any other baseline Common Matching fields. It is recommended that you do not use a negative length for SSN/SIN/TIN because it can create performance issues.
    2. In the Match on Null Data--Yes or No field, choose the Yes button to indicate that , or incoming data, or both can be NULL or identical to be considered a Match. Choose No to indicate that and incoming data must be NOT NULL and identical to be considered a match.
      Note: If your only rules are built using Name and SSN/SIN/TIN only and the match is not exact, the record will be marked as New. To cause the same record to suspend and potentials to be displayed, you need to include at least one more non-null and non-matched 'No' data element or one non-matched 'Yes' data element in your rule.
  7. If you are creating a matching rule that is not based within a table, then go to the Matching Procedures tab and add the specific database procedure(s) for matching components, and assign a priority to each one.
    Note: With this form, you can also assign site-specific procedures as rules for fields that do not reside in General. The SAKMTCH.P_MATCH_SORHSCH matching procedure has been delivered with this release. It allows the source code to use fields associated with high school data in the matching algorithm.
  8. Go to the Copy Rules To window and copy your rule to another existing rule set that does not have any rules yet.
  9. Save the rule.
