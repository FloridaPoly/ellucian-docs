Introduction

Banner® DEEWR supports producing reports required by the Australian Department of Education and Training (DET). It also includes self-service pages for capturing student requests for Commonwealth assistance.

Note: When this product was developed, the name of the agency was Department of Education, Employment and Workplace Relations (DEEWR), and the product was therefore named Banner DEEWR. Although the agency name has been changed to DET, at this time, the product name remains DEEWR.
Note: This 9x version corresponds to the Banner DEEWR 8.14 release version.

Functions and features

Banner DEEWR supports the capture and processing of the data required for the production of file submissions. The module draws information from Banner Student tables and pages, in addition to tables and pages added specifically for Banner DEEWR functionality.

The solution also includes Self-Service Web pages for capturing student requests for Commonwealth assistance. These Self-Service pages include electronic Commonwealth Assistance Form (eCAF) pages for Commonwealth assistance other than VET Student Loans.

Web pages are included to cover the following types of Commonwealth assistance:
  • Commonwealth support and HECS-HELP
  • FEE-HELP
  • OS-HELP
  • SA-HELP

For VET Student Loans, Banner DEEWR includes processes that interact with the Australian government eCAF system. Student enrolment records can be uploaded to the eCAF system using a .csv file and enrolment data and eCAF data can be retrieved using APIs. VET Student Loan eCAF data is then loaded into Banner using an MDUU process.

Australian Higher Education Providers and required VET institutions must comply with the Higher Education Support Act (HESA) 2003. As part of this compliance, the providers should be able to produce Commonwealth Assistance Notices (CANs) and distribute them to students.

The solution also provides templates of configurable processes for managing safety net processing.

Using Banner DEEWR includes various steps and processes. These are organised as follows:
  • Set up Banner DEEWR: Procedures and forms are used to define elements, values and processes that are required to produce the Banner DEEWR extract.
  • Collect and Record Data: Supplemental procedures and pages are used to enter and review any required data that might not have already been entered elsewhere in Banner.
  • Create the Return: Extract and Report Generation procedures and pages are used to create and view the data snapshot and extract. This step has three stages: snapshot process, extract process, and export process.
  • View Data: The Banner Mass Data Update Utility (MDUU) Universal Viewer is used to view the data produced by the snapshot and extract processes.

Although Banner DEEWR is delivered with defaulted configuration, many of the functions and processes can be tailored to your institution. For example, if your institution denotes the Admission Basis in a custom field instead of using the baseline Educational Level field, this can be remapped so the Banner DEEWR extract refers to the Custom field instead of Educational Level.

Note: Configuring Banner DEEWR requires knowledge of the underlying database tables and is usually carried out with the assistance of technical staff within your institution or Ellucian Professional Services.

Reporting data elements

The reporting requirements of Australian Higher Education and VET providers include data elements that have no logical equivalent in Banner. Additional fields are needed for programs, degrees, courses, campuses, students, and staff. Each of these data elements used to comply with the reporting requirements needs to meet specific validations.

The activities required to produce Banner DEEWR files are described in the Tasks section.

Business profiles

Standard business profile functionality requires that if one process uses business profile security, then all processes need to use business profile security. Therefore, the DEEWR_REPORTING business profile is defined for those authorised users who can run the Banner DEEWR reporting activities that do not contain tax file numbers.

These reporting activities include regular submissions, creation of locked data files from those submissions and revisions activities. The user names of the authorised users need to be attached to the DEEWR_REPORTING business profile, using GOAFBPR. All DEEWR Higher Education reporting processes have been attached to the DEEWR_REPORTING business profile on GKAPRRO, except for the ASC_TFN_REPORTS and ASC_TFN_LOCKED_DATA processes.

To provide complete security for tax file numbers, the TFN_PROFILE business profile is defined on the FGAC Business Profile Validation (GTVFBPR) page to ensure that only authorised users can run activities that include tax file numbers. The ASC_TFN_REPORTS, ASC_TFN_LOCKED_DATA, ASC_VFH_TFN_REPORTS, and ASC_VFH_TFN_LOCKED_DATA processes are attached to the TFN_PROFILE business profile on the Process Rules Roles (GKAPRRO) page. The user names of the authorised users need to be attached to the TFN_PROFILE business profile, using the FGAC Business Profile Assignments Form (GOAFBPR).

The SAFETY_NET_PROFILE business profile is defined for those authorised users who can run the Safety Net process - ASC_SAFETY_NET. The user names of the authorised users need to be attached to the SAFETY_NET_PROFILE business profile, using GOAFBPR. The Safety Net process - ASC_SAFETY_NET has been attached to the SAFETY_NET_PROFILE business profile on GKAPRRO.

The ASC_VFH_REPORTING business profile is defined for those authorised users who can run the VET Student Loan reporting activities. These reporting activities include regular VSL submissions, creation of locked data files from those submissions and revisions activities. The user names of the authorised users need to be attached to the ASC_VFH_REPORTING business profile, using GOAFBPR. The VET Student Loan reporting activities such as, ASC_VFH_REPORTING, ASC_VFH_REVISIONS and ASC_VFH_LOCKED_DATA are attached to the ASC_VFH_REPORTING business profile on GKAPRRO.

Reporting processes

The activities used for Banner DEEWR reporting are separated into several processes.

  • ASC_HEP_REPORTING contains activities for those higher education (HE) files that do not contain the tax file number data element.
  • ASC_TFN_REPORTS contains activities for those HE files that do contain the tax file number data element.
  • ASC_HEP_REVISIONS contains activities for HE Revisions files.
  • ASC_HEP_LOCKED_DATA contains activities for managing locked HE data files that do not contain the tax file number data element.
  • ASC_TFN_LOCKED_DATA contains activities for managing locked TFN HE data files.
  • ASC_VFH_PROCESSING contains activities for those VET Student Loan files that do not contain the tax file number data element.
  • ASC_VFH_TFN_REPORTS contains activities for those VET Student Loan files that do contain the tax file number data element.
  • ASC_VFH_LOCKED_DATA contains activities for managing locked VET Student Loan data files that do not contain the tax file number data element.
  • ASC_VFH_TFN_LOCKED_DATA contains activities for managing locked VET Student Loan files that do contain the tax file number data element.
  • ASC_VFH_REVISIONS contains activities for VET Student Loan Revisions files.

Multi-term processing allows users to run Banner DEEWR MDUU activities on a submission-by-submission basis, rather than having to run each activity for every term. Users need to only enter an academic year, DEEWR reporting period, and submission ID to have data from all relevant terms collected.

Multi-term processing is used by revisions file activities so that the activities refer to an original submission by submission ID rather than term.

Refer to Banner DEEWR Online Help for more information about forms and the support of multi-term processing feature.

Banner DEEWR is compatible with Study Path functionality. Study Path functionality was introduced in baseline Banner Student 8.3, with more features being added in Banner Student 8.4 and Banner Student 8.5, and more expected in future releases.

Banner DEEWR releases 8.3 and 8.3.1 were developed in Banner Student 8.4 and support features delivered in baseline releases 8.3 and 8.4. The Banner DEEWR 8.3 and 8.3.1 releases use Study Path features in Banner 8.4 (and the non-Accounts Receivable Study Path features of Banner 8.5).

Banner DEEWR releases from 8.4.1 to 8.6.3 were developed in Banner Student 8.5 but do not use the Accounts Receivable Study Path features of Banner 8.5 and Banner Accounts Receivable 8.2.

Banner DEEWR 8.7 was developed in Banner Student 8.6.5 with Accounts Receivable Study Path features of Banner 8.5 and Banner Accounts Receivable 8.2.

Commonwealth Assistance Notices (CANs)

The CAN feature allows you to gather data for use in your production of CANs and regenerate CANs for individual students or sub-groups of students.

This data source can be used by institutions to present official CANs to students, but Banner DEEWR does not offer any functionality to present a formatted official CAN; it only produces the data source from which it can be generated.

MDUU is used to gather CAN data.

Multi-term processing and use of Study Path functionality is used by the activities that gather data for use in producing CANs.

Note: All of the Process Rule Engine information is inserted into a new data table, which includes key fields such as PIDM, CRN, and Course Code. The formatted output has not been included in this release. Any formatted output would need to join the new data table with baseline tables to include descriptive data such as the student's current address, unit of study titles, course names, and program names.

eCAF processing

Banner DEEWR provides a solution for clients to record details of student requests for Commonwealth Assistance. Students can make requests either using a paper Commonwealth Assistance Form or through an eCAF.

The eCAF processing functionality includes Self-Service Web pages and data storage to support eCAFs and a form to allow administrative users to enter data that was submitted on a paper Commonwealth Assistance Form.

For VET Student Loans, Banner DEEWR includes processes that interact with the Australian government portal. Student enrolment records can be uploaded to the portal using a .csv file and enrolment data and eCAF data can be retrieved using APIs. VET Student Loan eCAF data is then loaded into Banner using an MDUU process.

Refer to the Self-Service chapter to learn more about Self-Service Web page details.

Banner DEEWR release also includes Tax File Number (TFN) encryption. Each TFN is stored as an encrypted string. The TFN is included in the Commonwealth Assisted Students (DU/VDU) File. Therefore, a function is included to the export activities for each of these files to decrypt the TFN at the point where the file needs to be correctly structured and formatted for submission to DET.

You can perform the following tasks:

  • Generate an appropriate .csv file to upload enrolments to the Australian government eCAF portal
  • Retrieve data from the Australian government eCAF portal using the GETENROLMENTS and GETECAFS APIs
  • Update or insert records on the Request for Commonwealth Assistance (SKAECAF) page by processing VET Student Loan data retrieved by the GETECAFS API.
  • Provide Self-Service Web pages for eligible students to submit a Commonwealth supported student and HECS-HELP eCAF.
  • Provide Self-Service Web pages for eligible students to submit a FEE-HELP eCAF.
  • Provide Self-Service Web pages for eligible students to submit an OS-HELP eCAF.
  • Provide Self-Service Web pages for eligible students to submit an SA-HELP eCAF.
  • Store eCAF data.
  • Provide a means for authorised administrative users to view eCAF data (except the TFN) and to enter data from paper Commonwealth Assistance forms.
  • Provide a means to encrypt tax file numbers.
  • Provide a means to decrypt tax file numbers so that correctly structured and formatted files can be submitted to DET.

Safety net processing

The safety net processing allows you to process records for students who have opted to pay fees up-front and who have not paid by the census date.

With this safety net process, you can perform the following tasks:
  • Distinguish between the students who have opted to take the safety net (and provided their tax file number) and those who have not taken the safety net option
  • Update the students' records according to their use of the safety net option (for example, change fee assessment rate or change students' enrolment status)
  • Process update actions in bulk (for example, applying a different fee assessment rate code or canceling enrolments)
  • Notify students by e-mail of the actions taken

To accomplish these functions, a new process code is created on the Business Rule Process Code Validation (GKVSQPR) page and a parameter code is attached to these process codes on the Business Rule Process Parameters (GKRSQPA) page.

Note: The process uses the Banner Mass Data Update Utility (MDUU) (process, rule sets, and rules features) to execute these functions.

Setting the due date for eligible charges

The skkrept.p_update_tbraccd_due_date procedure is an optional process that needs to be scheduled to run on a regular basis by your DBA or system administrator. It is meant to be called by an Oracle overnight Job Sub process.

It will update the Due Date for tuition charges for a CRN with the value of the census date for that CRN, taken from SKRAREG_CALC_CENSUS_DATE.The process uses the Current Enrolment View (SKVENRL) to select students and programs that are eligible for the process.

The view selects data from the SKRAREG table for each CRN and term for students in the SKVENRL view who are in programs that are eligible for a VET Student Loan.

It excludes CRNs that are in a term that is listed as a value for the EXCLUDED-TERM-CODE system parameter.

The process identifies programs that are eligible for a VET Student Loan in one of the following three ways:
  • The program is in the Locked VCO Data table (SKRLVCO) for the academic year
  • The program is not in the SKRLVCO table for the academic year but does have a degree code that is listed as a value for the VFH-DEGC-CODE system parameter
  • The program is not in the SKRLVCO table for the academic year and does not have a degree code that is listed as a value for the VFH-DEGC-CODE system parameter but is a program that is listed as a value for the VFH-CERT4-PROGRAM system parameter.

If your institution only wants to ever use programs that are in the SKRLVCO table for the academic year, you should leave the VFH-DEGC-CODE and VFH-CERT4-PROGRAM system parameters blank.

Where the CRN field is populated for an eligible transaction:
  • The process will then update the due date for eligible charge transactions for the student, term, study path and CRN.
  • Eligible charge transactions are those transactions with a detail code that meets the following criteria:
    • The detail code category is TUI and the DETAIL-CODE-LIST-PROVIDED system parameter is set to N

      OR

    • The DETAIL-CODE-LIST-PROVIDED system parameter is set to Y and the detail code matches a value listed for the DETAIL-CODE-LIST system parameter
  • The detail code does not match a value listed for the PAYMENT-PLAN-DETAIL-CODES system parameter
  • If the INCLUDE-IN-RATE-CODE system parameter is set to Y and the rate code on the student's curriculum matches a value listed for the INTERNATIONAL-RATE-CODE system parameter, then none of the student's records will be updated even if the detail codes meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to N, any record with an existing due date value will not be updated even if the detail code and the student meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to Y, any record with an existing due date value that is already the same as the corresponding census date will not be updated even if the detail code and the student meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to Y, any record with an existing due date value that is different to the corresponding census date will be updated if the detail code and the student meet the criteria for update.
Where the CRN field is NOT populated for an eligible transaction:
  • The process will then update the due date for eligible charge transactions for the student, term and study path.
  • If the DEFAULT-TBRACCD-DUE-DATE system parameter is blank then transactions where the CRN field is not populated will not be updated even if the detail code and the student meeting the criteria for update.
  • If the DEFAULT-TBRACCD-DUE-DATE system parameter is populated with a single value then eligible transactions will have the due date updated with that value.
  • Eligible charge transactions are those transactions with a detail code that meets the following criteria
    • The detail code category is TUI and the DETAIL-CODE-LIST-PROVIDED system parameter is set to N

      OR

    • The DETAIL-CODE-LIST-PROVIDED system parameter is set to Y and the detail code matches a value listed for the DETAIL-CODE-LIST system parameter.
  • The detail code does not match a value listed for the PAYMENT-PLAN-DETAIL-CODES system parameter
  • If the EXCLUDE-IN-RATE-CODE system parameter is set to Y and the rate code on the student's curriculum matches a value listed for the INTERNATIONAL-RATE-CODE system parameter, then none of the student's records will be updated even if the detail codes meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to N, any record with an existing due date value will not be updated even if the detail code and the student meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to Y, any record with an existing due date value that is already the same as the default date will not be updated even if the detail code and the student meet the criteria for update.
  • If the OVERRIDE-TBRACCD-DUE-DATE system parameter is set to Y, any record with an existing due date value that is different to the default date will be updated if the detail code and the student meet the criteria for update.

The skkrept.p_update_tbraccd_due_date procedure is optional and is delivered as DISABLED. If your institution wants to use this process, then this procedure needs to be enabled and scheduled by your DBA.

Refer to the instructions in the ASCGEN 8.6 Install Guide or the ASCGEN 8.6 Upgrade Guide under the "Step 8 Creating Oracle jobs for updating TBRACCD_DUE_DATE" section that will provide your Database Administrator with all the necessary information for scheduling the process.
