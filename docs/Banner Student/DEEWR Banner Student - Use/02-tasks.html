Setup tasks

This section provides setup tasks.

Define reporting data elements

To map Banner data to reporting data elements, you must create activities in the Banner Mass Data Update Utility (MDUU).

About this task

The activities required to produce each file are documented in separate specifications for each file. Before you can create these activities, you must define the elements and their valid values as described in the following procedure. Element codes have been delivered for reporting elements that do not have a logical baseline Banner location and are required for reporting.

Procedure

  1. Access the Report Element Validation (SKVRVAL) page.
  2. Define each element to be mapped.
  3. Save your changes.
  4. Access the Report Element Values (SKARVAL) page.
  5. Define the valid values for an element as follows.
    Note: You must define a separate record for each valid value for an element. For example, if an element has six valid values, you must define six records, one for each value.
    1. Create a new record.
    2. Enter the element name, as defined on SKVRVAL, in the Element Code field.
    3. Enter a valid value for the element in the Element Value field.
    4. Enter the text description associated with the value in the Description field.
    5. Select the Active check box.
    6. If the valid value is to be in use only for a limited time, enter the last date on which the value is to be used in the End Date field.
    7. Save your changes.
    8. Repeat 5 for each valid value.

Map external codes to Banner codes

You can map external codes, such as those used in the EN and LL files, to baseline codes for cases where a baseline code is too short or where using the Banner DEEWR values is not appropriate.

About this task

When the reporting process is run, the snapshot activities insert raw data from baseline fields, and then the extract activities run relevant data through this mapping table.

For example, the reporting element 348 (language spoken at home) uses four-character Australian Standard Classification of Languages (ASCL) codes. The Banner Native Language field is only three characters in length, but it is a logical place to capture the data. The Student Enrolment file snapshot activity therefore uses the Banner field to populate data element 348. The Student Enrolment file extract activity then transforms each Banner value to the matching ASCL value, as defined on the Report Elements Mapping (SKARMAP) page.

Procedure

  1. If you have not previously defined the data element to be mapped, define it as explained in the Define reporting data elements section.
  2. Enter the academic year code in the Academic Year field, then go to the next block.
  3. Enter the column name of the Banner baseline field to be mapped in the Banner Field field.
  4. Enter the Banner baseline value to be mapped in the Banner Value field.
  5. Enter the reporting element code to be mapped to the baseline field in the Element Code field.
  6. Enter the reporting element value to be mapped to the baseline value in the Element Value field.
  7. Save your changes.
  8. Repeat 3 through 7 for each mapping.

Copy external code mappings to another year

External code mappings are associated with an academic year.

About this task

You can copy one year's mappings to another, then modify the new mapping as desired. When you copy mapping rules from one year to another, all rules are copied, and you can delete any rules that no longer apply. You can copy rules forwards or backwards in time; the only restriction is that you cannot copy mapping rules to an academic year that already has mapping rules.

If you attempt to copy mappings to a year for which at least one mapping has already been defined, the system does not perform the copy and displays an error message.

Procedure

  1. Select the Copy Rules to New Year button.
  2. Enter the code of the academic year to be copied in the From Year field of the Copy Rules window.
  3. Enter the code of the academic year to which the definitions are to be copied in the To Year field.
  4. Select the Process Rule Copy button.
  5. If desired, modify the mappings as explained in the Map external codes to Banner codes section.

Copy system parameters to another year

System parameters are associated with an academic year.

About this task

You can copy one year's parameter definitions to another, then modify the new definition as desired. When you copy system parameter rules from one year to another, all rules are copied. System parameter rules cannot be deleted if the system required indicator is checked but the parameter value can be updated to null. System parameter rules can be deleted after being copied to the new academic year if the system required indicator is unchecked. You can copy rules forwards or backwards in time; the only restriction is that you cannot copy system parameter rules to an academic year that already has system parameter rules.

If you attempt to copy parameters to a year for which at least one parameter has already been defined, the system does not perform the copy and displays an error message.

Procedure

  1. Access the Report System Parameters (SKARSYS) page.
  2. Select the Copy Rules to New Year button.
  3. Enter the code of the academic year to be copied in the From Year field of the Copy Rules window.
  4. Enter the code of the academic year to which the definitions are to be copied in the To Year field.
  5. Select the Process Rule Copy button.
  6. If desired, modify the parameter definitions as explained in the Define system parameters section.

Data capture tasks

Build data for the Campus (CM) and Course of Study (CO) files

You can build data for capture by the snapshot activities (such as ASC_HEP_SNA_CM_FILE and ASC_HEP_SNA_CO_FILE) for each file when the Campus (CM) or Course of Study (CO) file is generated.

Procedure

  1. Ensure that all your programs are defined in the Program Definition (SMAPRLE) page.
  2. Define your institution's course file data records for each program and effective term ins the Course File Data (SKADRCO) page.
  3. Ensure that all your curriculum rules are defined in the Curriculum Rules (SOACURR) page.
  4. Define your institution's program offerings in the Program Offering (SKAPOFR) page.

Update data for the Campus Deletions (CD) file

You can update data for capture by the ASC_HEP_SNA_CD_FILE snapshot activity when the CD file is generated.

Procedure

  1. Make sure that the record that needs to be deleted has been included in a previous Campus (CM) file and exists in the Campus File Locked Data table (SKRDLCM).
  2. To update the corresponding program offering record(s) in the Program Offering (SKAPOFR) page, clear the Active indicator.

Build data for the VET Course of Study (VCO) files

You can build data for capture by the snapshot activity when the VET Course of Study (VCO) file is generated.

Procedure

  1. Make sure that all your programs are defined on the Program Definition (SMAPRLE) page.
  2. Define your institution's course file data records for each program and effective term on the Course File Data (SKADRCO) page.
  3. Ensure that the VFH Eligibility Indicator check box is selected for each program where continuing students are allowed to maintain their VET FEE-HELP loan.
  4. Ensure that the VET Student Loan indicator check box is selected for each program that is eligible for VET Student Loans.
  5. Make sure that all your curriculum rules are defined on the Curriculum Rules (SOACURR) page.
  6. Define your institution's program offerings on the Program Offering (SKAPOFR) page.

Create data for CANs

CANs are given to specific types of students.

  • HECS-HELP
  • FEE-HELP
  • OS-HELP
  • SA-HELP
  • VET Student Loan

The CAN Data table is created under the PRGNREP schema and is named as SKRDCAN. To avoid inconsistency in the table definition, all the columns are made "not null" and the NVL syntax provides default values for fields where the mapping might otherwise return a null value.

Activities that populate the table for the student types listed in this section default the following values into the following HELP type indicator:

Student Type Help Indicator Value
HECS-HELP H
FEE-HELP F
OS-HELP O
SA-HELP S
VET Student Loan V

If you run each activity separately and use the Purge before Populate option, the activity does not remove rows that exist due to one of the other activities.

Each activity includes a filter for its relevant HELP indicator, so you can run them all at one time and each record will have the correct HELP Type. Also, if you later run a single activity in Enabled with Purge mode, it does not remove any rows that have been inserted by the other activities.

Procedure

  1. Access the Additional Registration Data Inquiry (SKIAREG) page.

  3. Enter the CRN in the CRN field.
  4. Go to the next block.

View census information for a student

You can view census information for a student.

Procedure

  1. Access the Additional Registration Data Inquiry (SKIAREG) page.
  2. If you want to display only the records for a specific term, enter the term in the Term field.

    If you leave this field blank, the system displays records for all terms for the student.

  3. If you want to display only the records for a specific CRN, enter the CRN in the CRN field.

    If you leave this field blank, the system displays records for all CRNs for the student.

  4. Enter the student's ID in the ID field.
  5. Go to the next block.

    The system displays the relevant data for the specified student.

Prevent students from registering in CRNs for which the census date has passed

The BANINST1.JOB_SET_SSBSECT_SAPR Oracle job updates the value of the Special Approval code for any CRN for which the census date earlier than the current system date if that CRN is a traditional CRN (with a part of term) and if that CRN does not already have a Special Approval code.

About this task

If you want the system to perform this check, ask your DBA to enable this job and schedule it to be run at the same time each day.

Complete safety net processing

This section provides information and procedures about complete safety net processing.

Students with safety net

Students who have taken the safety net option must provide a tax file number (TFN). The status of students who do not make the required contribution payment is changed to a "deferred" payer, and the fees are re-assessed accordingly.

About this task

A series of rule set codes has been provided for each path of the process. For the students with the safety net option, the following process has been defined:

Procedure

  1. Select students (HAS_TFN_SELECT rule set) who have not paid and have the safety net option and gather this data
  2. Update (HAS_TFN_UPDATE rule set) the payment option (rate code) for these identified students
  3. Run the baseline Batch Fee Assessment process (SFRFASC)
  4. Send e-mails to students (HAS_TFN_EMAIL in MDUU rule set)
    Note: If you want to send an e-mail, then, the e-mail letter has to be built within Banner. A sample e-mail has been included in this release, which must be configured by your institution to enable you to send e-mails from within Banner. For any further assistance with sending e-mails from within Banner, you should contact your Account Manager, to arrange assistance from Professional Services.
Rule set codes for students with safety net

A series of rule set codes has been provided for the students who have taken the safety net option.

Student selection

The "Select" Rule Set code uses objects.

  • HAS_TFN_SELECT rule set to combine rules and actions.
  • HAS_TFN_COHORT rule code to select the correct student population.
  • TERM parameter code to allow users to easily use the same rule set for different terms.
    Note: You can set a default parameter value on the Business Process Rule Set (GKRPRST) page, or enter the parameter value when the process is launched.
  • AUTO_DELETE and AUTO_POPULATE action codes to remove old rows from the GKRPWRK table, then to populate GKRPWRK with records that fit the selection criteria, respectively.

The Business Process Rule Set (GKRPRST) page is used to define the process code and the rule set. The Business Rules Builder (GKRRSQL) page is used to build the SQL code of each rule. The Process Rule Column Definition (GKRPRCT) page is used to define the Banner table and columns to be updated by the rule.

The Process Launch (GKAPPLN) page runs the rule set. When you attach a parameter to a rule set, you can update the parameter values on GKAPPLN.

When you run the process code and the rule set that are defined in the Process Launch page, the AUTO_POPULATE action code updates the Process Rules Engine Working Table (GKRPWRK) with the selected data, using the column definitions from the Process Rules Engine Column Definition (GKRPRCT) page.

Student records update

The Update Rule Set code uses objects.

  • HAS_TFN_UPDATE rule set to combine rules and actions
  • CHANGE_RATE rule code to change each student's fee assessment rate code
  • TERM parameter code to allow users to easily use the same rule set for different terms
    Note: You can set a default parameter value on the Business Process Rule Set (GKRPRST) page, or enter it when the process is launched.
  • AUTO_POPULATE action code to update SGBSTDN_RATE_CODE

For the Update rule set, you define the process code, define the rule set in the Process Launch page, then run the process code in the Process Launch page with the defined parameter value. The AUTO_POPULATE action code updates the SGBSTDN_RATE_CODE.

E-mail to students

The Send an Email Rule Set code uses objects.

  • HAS_TFN_EMAIL rule set to combine rules and actions
  • HAS_TFN_EMAIL_10 rule code to gather the required data for the e-mail
  • HAS_TFN_EMAIL_11 rule code to arrange the data into the right format for the e-mail
  • HAS_TFN_EMAIL_12 rule code to physically send the e-mail and update the GURMAIL table
  • TERM parameter code to allow users to easily use the same rule set for different terms
  • LETTER parameter code to use the correct HTML letter
  • EMAIL_SUBJECT parameter code to allow users to easily change the subject of the e-mail over time
  • SENDER_ADDR parameter code to allow users to easily change the Sender Address of the e-mail over time
    Note: You can set the default parameter values on the Business Process Rule Set (GKRPRST) page, or enter them when the process is launched.
  • AUTO_POPULATE and SENDMAIL action codes to update GKRPWRK with the data needed to send and transmit the e-mail, respectively
Students without safety net

Students who do not take the safety net option must make a contribution payment or enrolment will be canceled.

A series of rule set codes has been provided for each path of the process. For the students without the safety net option, the following process has been defined:
  • Select students who have not paid and have not taken the safety net option (NO_TFN_SELECT in MDUU).
  • Update their records by inserting a user-defined attribute (NO_TFN_ATTRIBUTE rule set and ATTRIBUTE rule in MDUU).
  • Use Baseline Mass Registration Form (SFAMREG) to drop all CRNs for these students.
    Note: This ensures that the Registration Audit table (SFRSTCA) and enrolment scripts are updated appropriately.
  • Update the Enrolment Status (ESTS) code for these students.
    Note: This has to be done after the CRN drop, if ESTS prevents registration (NO_TFN_UPDATE rule set and CANCEL_ENROL rule in MDUU.
  • Run batch fee assessment (SFRFASC).
  • Send e-mails to students (NO_TFN_EMAIL in MDUU).

It is then possible to use this attribute to select the appropriate cohort of students in the Registration Mass Entry (SFAMREG) page, and delete their CRNs. This rule set code uses objects.

  • NO_TFN_ATTRIBUTE rule set to combine rules and actions
  • ATTRIBUTE rule code to process the update correctly
  • TERM parameter code to allow users to easily use the same rule set for different terms
  • ATTRIBUTE parameter code to allow institutions to define their own attribute code for this rule set
    Note: You can set default parameter values on the Business Process Rule Set (GKRPRST) page, or enter the parameter value when the process is launched.
  • AUTO_POPULATE action code to update the Student Attribute table (SGRSATT)
    Note: The educational institution uses the NO_TFN_ATTRIBUTE rule in the baseline Registration Mass Entry (SFAMREG) page to drop the students (listed after NO_TFN_ATTRIBUTE rule set is run), from all registrations, and ensure correct updating of all audits and section head counts.

MDUU Process Transactions table row deletion

After the safety net processing is completed for a term, the DELETE_GKRPWRK process allows you to delete rows from the MDUU Process Transactions Table (GKRPWRK) for a particular Process, Rule, and Action combination. This process is also useful when you are testing any changes you have made to the rules.

To execute this process, the following rule sets have been used:
  • DELETE_GKRPWRK rule set to combine rules and actions
  • DELETE_GKRPWRK rule code to remove rows from GKRPWRK
  • SQPR_CODE parameter code to allow users to select the Business Process Code for deletion of rows from the Process Rules Engine Working Table (GKRPWRK)
  • SQRU_CODE parameter code to allow users to select the Rule Code for deletion of rows from the Process Rules Engine Working Table (GKRPWRK)
  • SVBA_CODE parameter code to allow users to select the Action Code for deletion of rows from the Process Rules Engine Working Table (GKRPWRK)
    Note: You can set default parameter values on the Business Process Rule Set Form (GKRPRST), or enter the parameter value when the process is launched.
  • AUTO_DELETE action code to physically process the delete action

When you run this rule set in the Process Launch (GKAPPLN) page, you can nominate the process, rule, and action codes, so the rows will be removed from GKRPWRK.

Process file submissions

You can produce the files for submission to the Higher Education Provider Client Assistance Tool (HEPCAT).

You can control the execution of the process to run specific activities or tasks separately, or to run all tasks and activities together. However, it is advisable to run each task separately, evaluating the data each time. This results in better processing times and allows you to do any data cleaning before the final files are ready to be loaded into HEPCAT.

Refer to the Banner Mass Data Update Utility Use for more information about the pages.

ASC_HEP_REPORTING

You can produce Higher Education Student files.

Procedure

  3. Go to the next block.

  5. Access the Process Tree Execution (GKAPEXE) page.
  6. Enter ASC_HEP_REPORTING in the Process Code field.
  7. Go to the next block.
  8. Select the required stages on the Execution Tree Set-up tab.
  9. Go to the Execution tab.
  10. If necessary, enter values for the parameters.

Migrate historical reported data to locked tables

This procedure is designed in a way that institutions can use only one time.

About this task

When your institution first starts using the Banner DEEWR product, you will have records of all of your reported data from previous years. Much of this reported data is needed for possible future revisions processing, and if you intend to use the Banner DEEWR revisions functionality, you must migrate the historical reported data to the locked data tables.

The ASC_LOCKED_DATA_LOAD process loads historical reported data to the locked data tables. Historical data for each reporting file needs to be spooled to a delimited file, so that it can be registered in MDUU as an external table. Activities exist in ASC_LOCKED_DATA_LOAD to write the data from each external table to a corresponding staging table. These activities include error handling logic. Activities exist in ASC_LOCKED_DATA_LOAD to load records from each staging table to the corresponding locked data table. Only records without errors are loaded to the locked data table.

Note: When running the MDUU activities, it is recommended that you run each activity separately, by checking the data in "matched" tables before loading to locked data tables.

Use the following procedure to migrate the historical reported data to the locked tables.

  1. Access the Execution Tree Set-up (GKAPEXS) page.

Research task

This section discusses the research task to receive Commonwealth assistance.

Determine why a student is not eligible to receive Commonwealth assistance

Perform this task to determine the reason for a student's ineligibility to receive Commonwealth assistance.

About this task

Note: Only authorised administrative users can perform this task.

Procedure

  1. Review the system parameters and enter the values for the system parameters as needed.
  2. Check the student's citizenship status and compare it to the values for the system parameters that relate to citizenship.
  3. Check the residence code, both on the student's general learner record and on the study path for the program for which the student is trying to request Commonwealth assistance, and compare these to the values for the ECAF_RESD_ELIGIBLE system parameter.
  4. If the student is a permanent resident and is applying for FEE-HELP, verify that their program code is an eligible bridging program. If the program is an eligible bridging program, ensure that it is one of the values listed for the ECAF_BRIDGING_PROGRAM system parameter.
  5. If the program is eligible for a VET Student Loan, then it needs to be included in the locked VET Student Loan Course File Table (SKRLVCO) for the academic year of the term for which the student is requesting Commonwealth assistance.
  6. If the program is not eligible for a VET Student Loan, but should allow students to apply for Commonwealth support and HECS-HELP or for FEE-HELP or for OS-HELP, then it needs to be included in the locked Course File Table (SKRLDCO) for the academic year of the term for which the student is requesting Commonwealth assistance.
