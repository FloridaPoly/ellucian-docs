UCAS Data Transfer (SKPUHER) process

This process is used to upload data to and download data from XML-Link.

About this task

This process can be launched any time from job submission or directly from the command line (for example, in a Cron script). To run the process automatically, you must edit the SKPUHERD.SHL and SKPUHERU.SHL scripts (see “Edit the SKPUHER scripts”).

This process needs to be called twice in the following sequence: first with the Transfer Flag parameter set to U (upload) to send the transactions to UCAS, and then with the Transfer Flag parameter set to D (download) to receive the acknowledgements from UCAS. The XML-Link methods on the UCAS Data Processing (SKAUHPR) page for which the Auto check box is selected will be downloaded.

When launched, this process will do the following for a download:

Procedure

  1. Select all of the new data from UCAS. The UCAS data will be considered new when the UCAS timestamp is later than the Banner timestamp The data will be stored in interim tables.
  2. Check for duplicates
  3. Process the information from the interim tables into the Banner UCAS tables.

Results

When launched for an upload, this process will select all of the new data from the Banner UCAS module and send it to UCAS.

There is also the ability for an e-mail to be sent to confirm the success or failure of the process. The following parameters must be set up on the System Parameter Maintenance (GKAKSYS) page for this e-mail process to function:
  • ODBC RECIPIENT EMAIL ADDRESS
  • ODBC EMAIL SENDER
  • ODBC EMAIL SENDER NAME
  • ODBC EMAIL SERVER
  • ODBC FAILED EMAIL SUBJECT
  • ODBC SUCCESSFUL EMAIL SUBJECT
    Note: All of these parameters are used for XML-Link, although the parameter names have not been changed to reflect this.
    Parameter Name Required? Description Values
    Institution Code Yes The institution code. AAA format (for example, X01).  
    Transfer Flag Yes Indicates if a download or upload should be performed. U: Upload

    D: Download

UCAS Purge (SKPURGE) process

The purge routine permits the user to clear unwanted data from finalised admission cycles, such as old UCAS Marvin file data, previous application data, Banner copy view data, and so on.

Generally, this process will be run one time a year between one admission cycle closing and a new one beginning. It can also be used during the implementation phase for clearing test databases to provide a clear install for re-testing admission processes.

The purge process allows institutions to clear out old Marvin transaction and Banner copy view data from previous years. A process parameter allows you to delete copy view data with activity dates earlier than a specified value. You can delete applicant data in Banner UCAS for specific entry years or admissions systems. You can also delete old SWAS and NMAS applicant records,and records from the current admissions systems.

Warning: ODS users should be aware that deleting Banner UCAS applicant data through this process will result in that data being removed from the ODS reporting repository when it is next refreshed.

Data downloaded from XML-Link, which is initially stored in PRGNREP temporary tables, is deleted after it has been transferred into the Banner UCAS interim tables (‘copy view tables’) by the MDUU rules and so is not covered by SKPURGE.

Value Mapping Process Import (SOPSSDT) process

The SOPSSDT process allows you to import extensive seed data to the SKVSSDT table for the input Attribute and Entity. To run this process, ensure that you import the input seed data file in .xlsx first to the Jobsub directory.

The file should comprise of the Option 1, Option 2, Option 3, Title, and Short Title values respectively. See the attachment to refer to the information in detail.

Ensure that you also have the Entity and Attribute for the seed data that you want to import as per the definition in the SKAUFDS page. If you have not defined Attribute and Entity in the SKAUFDS page, you cannot import the seed data file.

The process parameters are:

Parameter Name Required? Description Values
Path of the file Yes Enter the path of the file name containing the seed data.  
Name of the file Yes Name of the .xlsx file comprising the seed data  
Entity Yes The entity used on SKVSSDT to store the mapping  
Attribute Yes The attribute used on SKVSSDT to store the mapping  
Run Mode Yes Enter A for Audit mode or U for Update mode  
Ellucian recommends you ensure the following as prerequisites.
  • Import the seed data file to the job directory and copy the file name and file path.
  • Define the Entity and Attribute in the SKAUFDS page.
  • Create the seed data in the .xlsx format only.
For the process to run, ensure the following.
  • Enter the path of the file, file name, SKVSSDT entity, and SKVSSDT attribute. The process parses the data from the .xlsx file and creates seed data records in the SKVSSDT table, that can be viewed on the SKASSDT page.
  • If a value for an entity and attribute already exists in SKVSSDT for the same, the process will not load the value.
  • The system creates the seed data records in the SKVSSDT table only when the process is run in the Update Mode (U).
  • The system inserts all the records in the .log file for you to view.
  • In the Audit Mode, the system validates the data and the .log file provides the snapshot of the results.

Awarding Body Linkage Data (SOPUABL) Process

The Awarding Body Linkage (ABL) data that is retrieved from the GET Reference endpoints;getReferenceAwardingBodies, getReferenceExamLevels, and getReferenceOfferSubjects) is acquired through XML-Link and then populated into the respective SKBUAWB, SKBUEXA, and SKBUSUB MDUU tables.

The downloaded data might contain descriptions of up to 250 characters. However, when transferring this data into Banner tables, it is necessary to condense the descriptions to 30 characters after removing special characters such as the ampersand (&). This abbreviation is crucial for compatibility with the Banner tables.

In the past, the abbreviation of descriptions was achieved using the Awarding Body Linkage (ABL) scripts. These scripts were provided separately from the release. After clients downloaded the GET Reference Endpoints, they manually executed these Awarding Body Linkage (ABL) scripts and then initiated the Load into Banner process from the SKAUHPR page.

The SOPUABL process streamlines the procedure by replacing the need for ABL scripts, eliminating manual steps. It involves populating the STVTSRC table with data from the SKBUAWB table after abbreviating the descriptions. However, unlike SKBUAWB, the data from SKBUSUB and SKBUEXA is not directly transferred to the target Banner tables.

Initially, all descriptions from these tables are added to the newly established Banner table (SOBUABL) designed specifically to manage both the original and abbreviated descriptions. Users can access and modify these descriptions through the new UCAS page SOAUABL. When adding descriptions into the SOBUABL tables, the abbreviated versions consist of the initial 30 characters from the descriptions column, with & replaced by +. This setup allows for easy management and viewing of both the complete and shortened descriptions.

Afterward, the abbreviated descriptions are updated back into the original MDUU tables. Specifically, columns SKBUSUB_SUBJTEXT_COPY and SKBUEXA_EXAMTEXT_COPY are populated with the abbreviated descriptions from the SOBUABL table. Then, data from SKBUEXA is transferred to tables SKVUSBJ, SKVSSDT, and STVTADM. Similarly, data from SKBUSUB is populated into tables STVTESC and SRBRITC. Whenever there's a modification in the descriptions during the download for existing data, that particular description is inserted into SOBUABL and subsequently updated in the Banner tables when this process runs.

Parameter Name Required? Description Values
Exam Year Yes Exam year processes Awarding Body Linkage data into STVTSRC.  
Sitting Code Yes You can provide multiple sitting codes. The process utilizes these codes to also handle data into STVTSRC.  

The process efficiently populates all new or updated descriptions related to Awarding Body Linkage (ABL), Exam Levels, and Offer Subjects into the Banner tables within a single run

Note: The parameters supplied for this process are solely utilized in handling the Awarding Body Linkage (ABL) data for STVTSRC and aren't involved in processing Exam Level or Offer Subject data.

WINC Institution Code Update (SOPUWIN) process

The SOPUWIN process supports the WINC data updates for the institution code.

Ellucian delivers the WINC scripts with Z89 as the default institution code. The SOPUWIN process reads institution code from the GKAKSYS page and updates the WINC scripts with the University's institution code.

The SOPUWIN process accepts the UCAS User ID as the parameter. This process asks for the UCAS User ID of client ( for example USER_Z89) and this will be used to update UserID values in GKAWSPV page which is used in UCAS processing.

Important: You must maintain the institution code as a first value in the GKAKSYS page for the Institute Code parameter. The SOPUWIN java process uses this institution code to update the WINC scripts. After the institutions run the SOPUWIN process, the changes cannot be undone.

Hence, the appropriate institution code with which the institutions download and upload the data from UCAS, must be the first value in the GKAKSYS page for the Institute Code parameter.

For example:
  • Parameter Name: INSTITUTION CODE
  • Parameter Value: Z70, Z89, Z95
After you run the SOPUWIN process, the WINC scripts gets updated with the Z70 institution code.

Run the SOPUWIN process

Steps to run the SOPUWIN process.

Before you begin

Users who run the SOPUWIN process, must have the following permissions. For example, if the user is UCAS_USER:
  • GRANT DROP ANY INDEX TO "BANINST1";
  • GRANT ALTER ANY INDEX TO "BANINST1";
  • GRANT CREATE ANY INDEX TO "BANINST1";

Procedure

  1. Access the Process Submission Control (GJAPCTL) page.
  2. In the Process Name field, enter SOPUWIN.
  3. Click Go.
  4. In the Printer Control section, enter DATABASE in the Printer field.
    The process requires no parameter values.
  5. Move your cursor to the Submission section and select the Submit option button.
  6. Click Save.
    The process generates the LOG and LIS files. You can view both the files in the Review Output (GJIREVO) page using the Related menu.
