Reports and Process for California Reporting

This Section discusses the reports and processes created or modified for California localizations.

For those that were created or substantially modified for California, complete descriptions are included. For those that were modified to a lesser extent, only the modifications are included here; for further information, refer to Banner Student Reports and Processes.

Standardized Attendance Accounting

To comply with the regulatory requirement introduced on March 25, 2024 by the Board of Governors, there is a new implementation within 320 reporting: Standardized Attendance Accounting calculation method.

Standardized Attendance Accounting impacts Parts II, III, V, and VI, so how the current calculation of contact hours and the FTES changes only when running the reports using the Standardized Attendance Accounting method.

The first difference is in the multipliers: instead of using the corresponding multiplier defined for each section, the multipliers are now set in Banner Applications Configurations (GUACONF page) under Application ID (CALGEN_320 - Banner California Student 320 Reporting).

Introduce in 2024, the Standard Attendance Accounting calculation method approach, is optional for 2025-2026, but it is mandatory for 2026-2027.

Under the Configurations tab, you can see the following configurations:

Configuration Name Comment Configuration Value
320_ST_LAB 320 Standard hours per unit of lab, used in the Standard Attendance Accounting method approach introduced in 2024 (optional 2025-2026, mandatory starting 2026-2027).

If your institution has a quarter system this value should be set to 36, otherwise should be set to 54.

 Delivered as 54 for semester system institutions; if the institution has quarter system, they need to set this to 36.
320_ST_LEC 320 Standard hours per unit of lab, used in the Standard Attendance Accounting method approach introduced in 2024 (optional 2025-2026, mandatory starting 2026-2027).

If your institution has a quarter system this value should be set to 36, otherwise should be set to 54.

 Delivered as 18 for semester system institutions, if the institution has quarter system, set this to 12.
320_ST_ACT 320 Standard hours per unit of lab, used in the Standard Attendance Accounting method approach introduced in 2024 (optional 2025-2026, mandatory starting 2026-2027).

If your institution has a quarter system this value should be set to 36, otherwise should be set to 54.

 Delivered as 36 for semester system institutions, if the institution has quarter system, set this to 24.
320_ST_ACT_TYP_CDE Use this configuration to set the GTVMTYP code value that will be used for ACTIVITY meeting type when creating a schedule in SSASECT. This is used only for the Standard Attendance Accounting method approach introduced in 2024 (mandatory for 2026)

Delivered as UPDATEME. Users need to configure with the GTVMTYP code they use for Activity.

NOTE: This configuration only allows setup for one code. Also this code should not have Lab checked on GTVMTYP.

You can obtain the contact hours from the Schedule SSASECT page, on the Meeting Times and Instructor tab. The hours are received from the field Session Credit Hours and the Meeting Type code that comes from the Meeting Type Validation GTVMTYP page.

If the Meeting Type code has Lab selected, then the hours of this are taken as Lab hours.

If the Meeting Type code has Lab unselected, then the hours of this are taken as Lecture hours.

If the Meeting Type code has Lab unselected, and in addition, this code is configured in Banner Applications Configurations - (GUACONF) page under the Application ID (CALGEN_320-Banner California Student 320 Reporting) in the Configuration Name (320_ST_ACT_TYP_CDE) value, this hours are taken as Activity hours.

This is how it works the calculation of contact hours:

Calculation of contact hours
Std CH(Student Contact Hours)= Lab Contact Hours + Lecture Contact Hours + Activity Contact Hours
Total CH(Total Contact Hours)= ((Lab Contact Hours * 320_ST_LAB )+(Lecture Contact Hours * 320_ST_LEC) + (Activity Contact Hours* 320_ST_ACT))
CH Resident(Contact Hours Resident)= Total CH * Enrollment Resident
CH Non-Resident(Contact Hours Non-Resident)= Total CH* Enrollment Non-Resident
Note:

The implementation of this calculation method is for Parts II, III, V and VI ONLY when SVRCALX is executed using Standardized Attendance Accounting and then SVRCALD/SVRCALS or other report is executed after (with exception of SVRCALP).

Enhanced academic calendar and computed drop code/fee refund modifications

Enhanced Academic Calendar dates and Computed Drop Code/Fee Refund functionality has been removed from the California localized application and incorporated into the core Banner Student Admin pages and Banner Student Self-Service Registration application.

CCFS-320 reporting modifications

The process was modified to evaluate the SSASECT reporting year and to use the following SOBPTRM date columns for the academic calendar date defaults.

  • SOBPTRM_ENRL_CUTOFF_DATE is the default for the Last Date to Enroll field (SSBSECT_ENRL_CUT_OFF_DATE)
  • SOBPTRM_REFUND_CUTOFF_DATE is the default for the Last Date for Refund field (SSBSECT_REFUND_CUTOFF_DATE)
  • SOBPTRM_ACAD_CUTOFF_DATE is the default for the Last Date to Record Academic History field (SSBSECT_ACAD_CUT_OFF_DATE)
  • SOBPTRM_DROP_CUTOFF_DATE is the default for the Last Date to Drop without a Penalty field (SSBSECT_DROP_CUT_OFF_DATE)
Warnings and error messages are delivered in the following conditions:
  • When a CRN has a meeting using override hours and has a value in the Hours per Week field that is not reasonable for the value in the Hours per Day field, the system displays a warning.
  • When a CRN has a weekly attendance method and is being copied to an intersession term, the system displays a warning, although the CRN is still copied. This applies to the following attendance methods:
    • Weekly
    • Independent Study combined with Weekly
    • Independent Study Lab.
  • When a CRN has daily attendance method and is being copied to an intersession term that crosses the academic year end, the default academic year code may not be valid for it. Instead the next-higher code may be the correct code. If that code does not exist, the CRN cannot be copied and the system displays an error message. This applies to the following attendance methods:
    • Daily
    • Independent Study combined with Daily
  • When a CRN has actual attendance method and is being copied to any term that crosses the academic year end, the default academic year code may not be valid for it. Instead the next-higher code may be the correct code. If that code does not exist, the CRN cannot be copied and the system displays an error message. This applies to the following attendance methods:
    • Actual
    • Independent Study combined with Actual

CCFS-320 Part IX Report C3SC (SVRCAL9)

This report was created to generate the multi-college district-wide CCFS-320 Part IX, AB 540 Headcount, Special Admit PE Credit FTES and Inmates in Correctional Facilities report.

This report uses the extract tables updated by SVRCALX, similar to SVRCALD, SVRCALS, and SVRCALU, but for a multi-college district. It gathers and reports data from multiple SVRCALX runs. For example, within the San Mateo County Community College District the college codes loaded into GTVDICD will be 371 (Canada College), 372 (College of San Mateo), and 373 (Skyline College). SVRCAL9 is run for the district code, which is 370 (San Mateo County Community College District) and which should not be loaded into GTVDICD. When you run SVRCAL9 for district ID 370, it treats this value as a wild card (like 37%) and reports all data that exists in the extract tables for 371, 372, and 373 for the same academic year and reporting period. (The SVRCALX time stamp is listed on the output so that you can tell if one of the colleges did not have updated data in the extract tables.)

Page one of the output is the AB 540 Headcount Report. The AB 540 Resident Code parameter, which allows multiple codes, is used to select the data for this head count. The count noted is of unique student records (unique PIDMs) in the extracted data that have one of the entered resident codes.

The second section of the output is the Special Admit Full-Time and Part-Time PE Credit FTES Report. This section does not use the AB 540 Resident Code parameter, and data related to that parameter is not listed on these pages.

This section uses the Concurrent Enrollment 5% Rule on SFAROVR to evaluate concurrent high school student enrollment for the 5% concurrent high school enrollment rule. If the last page notes that the percent is above 5%, you need to adjust student enrollments. See CCFS-320 Reporting for more information.

The third section of the output is the Inmates in Correctional Facilities FTES Report.

This section reports the number of FTES (credit, noncredit, and total) generated by incarcerated students.

Academic Year Yes Code of the academic year. This can be any valid value from STVACYR except 0000 and 9999. Academic Year Validation Page (STVACYR)
District ID Yes ID of the district. This is a wildcard value used to select all extracted data with the District/College ID codes (SVRCALP_DICD_CODE) that match the first two characters. For example, entering 370 will select data for SVRCALP_DICD_CODE the same way that 37% would in a page.

Changes regarding Standardized Attendance Accounting

SVRCAL9 has a new informative label regarding execution mode for informational purposes. While you execute SVRCAL9 using the Standardized Attendance Accounting calculation method, it shows the following label at the bottom of .lis file: Executed with Standardized Attendance Accounting, otherwise, it shows Executed without Standardized Attendance Accounting.

For this report is important that all the colleges within the same district execute using the same calculation method, otherwise they see the following message:

WARNING: The colleges within the district have different values for calculation method. To ensure data consistency, all colleges within the district must use same execution value in SVRCALX parameter 02 'Exec Standard Attendance Acct'.

Note: Even though SVRCAL9 has impact by Standardized Attendance Accounting calculations, the user should not rely on these amounts as they are not accurate at the moment when using this calculation method.

About the new Standardized Attendance Accounting calculation method

To comply with the regulatory requirement introduced on March 25, 2024 by the Board of Governors, there is a new implementation within 320 reporting: Standardized Attendance Accounting calculation method, which includes SVRCALD.

The new Standardized Attendance Accounting calculation method impacts on the calculation of the contact hours on Parts II, III, V and VI. For details on how contact hours are calculated for apportionment reporting, see Standardized Attendance Accounting, Hour and Date Calculations topic in the CALBSTU Use documentation and CCFS-320 Reporting on the Ellucian Documentation site.

When using SVRCALD with Standardized Attendance Accounting, a new summary section called Standardized Attendance Accounting Summary is displayed with the details of the Term Count, CRN Count, and CRNs with warnings, in addition of the Contact Hours divided by Resident and Non Resident of parts II, III, V and VI.

This summary section is only be visible when using Standardized Attendance Accounting calculation method, if user decides to execute reports without Standardized Attendance Accounting, this will not be visible and the format will keep as usual.

SVRCALD Output when executed with Standardized Attendance Accounting calculation method

The Standardized Multipliers (GUACONF) values used are displayed under Length Mult depending on the CRN configuration. For example, if the CRN has a schedule with a “Meeting Type” code type activity, the value for the activity multiplier configured in GUACONF is displayed.

Also the way Std CH and Total CH are calculated as previously stated and displayed accordingly.

When executing SVRCALD using student details, each student displays the calculated Total CH.

The Contact Hours for residents and non-residents for each section are calculated as Total CH * Enrollment and displayed accordingly.

The summary of each part is performed as usual, as it sums all of the CRNS that belong to a specific section, and this is displayed in the Summary of CRN Category Totals.

The only parts that remain untouched, meaning that Standardized Attendance Accounting was not implemented there and they continue working as usual disregarding execution mode used, are Part IV ACTUAL and Part VII ISNC.

Also, a new section Standardized Attendance Accounting Summary is included after the Summary of CRN Category Totals that includes the sum of the contact hours of the parts impacted by standardized (II, III, V and VI), divided by Resident and Non-Resident and also keeping with the same structure as the previous summary, the sum of the details for Term Count, CRN Count and CRNs with Warning.

Includes an informative label at the end of the output file that lets the user know if the Standardized Attendance Accounting method is used.

SVRCALD CSV generation

There is a new functionality, the generation of the reports in a CSV format.

First, the reports must exist in the Jobsub Output Definition page GJAJBMO and you should enable them. The reports need to have MME Type configured, it can be either PDF or Plain Text.

How to download the CSV file

After successfully executing the reports, you can see the CSV files generated in the Saved Output Review GJIREVO, but the option to download it is not available yet.

To download the CSV files:

  1. Navigate to Saved JobSub Reports GJAJLIS, enter with the Job (SVRCALD/SVRCALS), and click enter.
  2. You can filter using the Job Number.
  3. Select the file and click on the Download button, do this for all the files you want to download.

About the SVRCALD CSV generation

The CSV files are generated with each execution. The system will create a CSV file per each part with the following nomenclature:

Job name + section name + job number

The CSV files follow a selected parameter options, for example, this includes whether or not the job is executed using Student Details (the CSV includes details for students or not) or if this is executed using the Standardized Attendance Accounting calculation method (this impacts the way calculation for contact hours is executed just as explained in SVRCALD contact hours section) or other parameters selected.

SVRCALS Output when executed with Standardized Attendance Accounting calculation method

Contact Hours

When executing SVRCALS using Standardized Attendance Accounting, Parts II (WEEKLY), III(DAILY), V (INDEPENDENT STUDY WEEKLY) and VI (INDEPENDENT STUDY DAILY) have contact hours calculated with this method. The only parts that remain without changes (this means Standardized Attendance Accounting was not implemented there and they continue working as usual disregarding the execution mode used) are Part IV (ACTUAL) and Part VII (ISNC).

FTES calculation

When executing SVRCALS using Standardized Attendance Accounting, Parts II (WEEKLY), III (DAILY), V (INDEPENDENT STUDY WEEKLY), and VI (INDEPENDENT STUDY DAILY) have FTES calculated with this calculation method.

When executed for reporting period P1 or P2:

 
FTES= (Contact Hours/ 525)* STANDARDIZED PART ANNUALIZER

When executed for reporting period annual:

 
FTES= (Contact Hours/ 525)

Parts IV and VII remain with the same FTEs calculation disregarding the execution mode.

Part VIII FTES ANNUALIZERS (Excluding Summer Intersessions)

When executing SVRCALS using Standardized Attendance Accounting, the annualizer for Parts II (WEEKLY), III (DAILY), V (INDEPENDENT STUDY WEEKLY) and VI (INDEPENDENT STUDY DAILY) takes the value of Standard Annualizer configured in SVAAPIZ depending on the Reporting Period being executed; this value also is applied to FTES when executed for Part I or Part II.

When executing SVRCALS using Standardized Attendance Accounting, the annualizer for Parts IV and VII remains the same, disregarding the execution mode. As well, the value configured in SVAAPIZ for those sections is applied as usual to FTES.

When executing SVRCALS without Standardized Attendance Accounting, each section keeps the value of annualizer configured in SVAAPIZ and still applies as usual.

Also, the Standardized Attendance Accounting label is not shown.

Adjustment to FTES: Part I Faculty Contact Hours (Flex Calendar)

When executing SVRCALS using Standardized Attendance Accounting, there are still calculations of F-Factor, so, the districts still have an option to apply F-Factor to courses using positive attendance (credit and noncredit) and the alternative attendance accounting method for non-credit.

The parts using Standardized Attendance Accounting no need to apply factor, so this is not calculated for A.Credit Courses (2 Daily Census Procedure Courses) nor A.Credit Courses (4 Independent Study/Work Experience Course (b.Daily Census Procedures)).

Standardized Hours section

When executing SVRCALS using Standardized Attendance Accounting, there is a new section called “Standardized Hours”, this has the sum of contact hours for Parts II (WEEKLY), III (DAILY), V (INDEPENDENT STUDY WEEKLY) and VI (INDEPENDENT STUDY DAILY) split into dates.

There is a FTES calculation section where FTES from Part II (WEEKLY), III (DAILY), V (INDEPENDENT STUDY WEEKLY) and VI are also summarized. This section is only visible when SVRCALS is executed using Standardized Attendance Accounting, otherwise, this section will not display.

Informative label regarding the execution mode

SVRCALS has a new informative label regarding execution mode for informational purposes. When SVRCALS was executed using Standardized Attendance Accounting calculation method, it will display the following label at the bottom of .lis file: Executed with Standardized Attendance Accounting. Otherwise, it will display Executed without Standardized Attendance Accounting.

SVRCALS CSV generation

There is a new functionality, the generation of the reports in a CSV format.

First, the reports must exist in the Jobsub Output Definition page GJAJBMO and should be enabled. The reports need to have MME Type configured, it can be either PDF or Plain Text.

How to download the CSV file

After successfully executing the reports, you can see the CSV files generated in the Saved Output Review GJIREVO, but the option to download it is not available yet.

To download the csv files:

  1. Navigate to Saved JobSub Reports GJAJLIS, enter with the Job (SVRCALD/SVRCALS), and click enter.
  2. You can filter using the Job Number.
  3. Select the file and click on the Download button, do this for all the files you want to download.

About the SVRCALS CSV generation

The CSV files are generated with each execution. The system will create a CSV file per each part with the following nomenclature:

Job name + job number

The CSV files follow a selected parameter options, for example, this includes whether or not the job is executed using Student Details (the CSV includes details for students or not) or if this is executed using the Standardized Attendance Accounting calculation method (this impacts the way calculation for contact hours is executed just as explained in SVRCALD contact hours section) or other parameters selected.

CCFS-320 Supplemental Reports C3SC (SVRCALU)

This set of reports was created to support the CCFS-320 functionality. This group of reports details the supplemental reports.

  • Centers Supplemental
  • Leased Space Supplemental
  • Enhanced Funding Noncredit Supplemental
  • Basic Skills Supplemental
  • In-Service Supplemental
  • Apprenticeship Supplemental
    Note: The Apprenticeship Supplemental section is the only section that lists CRNs that are not included in the totals of the SVRCALS report. They are listed only in the SVRCALD apprenticeship-only version (that is the SVRCALD CCFS-320 or Apprenticeship Rpt parameter is set to A.

The output in each section is broken into non-credit/credit and resident/non-resident details, followed by the totals and the number of sections by subject, except for the "Centers" section, because for that section, in addition, the information is being displayed first by "Center", and then broken into non-credit/credit and resident/non-resident details.

This process creates the group of reports using the extract data in the following:
  • Report Definition Data Table (SVBCALP)
  • CRN Data Table (SVRCALN)
  • Student Registration Override Data Table (SVRCALO)
  • Student Registration Data Table (SVRCALR)
  • Student Data Table (SVRCALS)
  • Term Data Table (SVRCALT)

The Centers section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as being taught in a center (SVRCALN_BLDG_CENT_CODE is not null), which is determined from the following data when SVRCALX is run.

  • The extracted CRN is coded with the center code if it has at least one SSRMEET record with a building code that has the center code (if SVRCALN_BLDG_CENT_CODE = SLBBLDG_CENT_CODE and if at least one SSRMEET record has a (SSRMEET_BLDG_CODE = SLBBLDG_BLDG_CODE and SLBBLDG_CENT_CODE <> null)). If the CRN has two meetings with two different center codes, only the first code encountered is used for CCFS-320 reporting.
  • If all meetings have buildings with null center codes (SVRCALN_BLDG_CENT_CODE = null), the extracted CRN is not coded with a center code. Therefore, it is not included in this section of the supplemental report.

The Leased Space section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as being taught in a leased building (SVRCALN_BLDG_LEASED_IND = Y), which is determined from the following data when SVRCALX is run.

  • The extracted CRN has at least one SSRMEET record with a building code that is leased space (SVRCALN_BLDG_LEASED_IND = Y if at least one SSRMEET record has a (SSRMEET_BLDG_CODE = SLBBLDG_BLDG_CODE and SLBBLDG_LEASED_LEASED_IND = Y)).
  • If all meetings have buildings that are not leased (SLBBLDG_LEASED_LEASED_IND <> Y), the extracted CRN is not coded as in a leased space. Therefore, it is not included in this section of the supplemental report.

The Enhanced Funding Noncredit section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as enhanced funding noncredit (SVRCALN_ENHC_FUND_NOCR_IND = Y), which is determined when SVRCALX is run by setting SVRCALN_ENHC_FUND_NOCR_IND = SCBSUPP_ENHC_FUND_NOCR_IND.

The Basic Skills section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as basic skills (SVRCALN_BASIC_SKILL_CDE <> N), which is determined when SVRCALX is run by setting SVRCALN_BASIC_SKILL_CDE = SCBSUPP_BASIC_SKILL_CDE.

The In-Service section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as in-service (SVRCALN_IN_SERVICE_IND = Y), which is determined when SVRCALX is run by setting SVRCALN_IN_SERVICE_CODE = SCBSUPP_IN_SERVICE_IND.

The Apprenticeship section will include a CRN’s apportionment data if the CRN has no exceptions (SVRCALN_EXCEPTION_CDE is null) and if the CRN was coded as apprenticeship (SVRCALN_OCCS_CODE = A), which is determined when SVRCALX is run by setting SVRCALN_OCCS_CODE = SCBSUPP_OCCS_CODE.

PE Concurrent Enrollment Process C3SC (SVRCALP)

This process was created to support the CCFS-320 functionality. It lists enrollment information to help satisfy the sports 10% concurrent high school enrollment rule for apportionment.

This report is the only one in the CCFS-320 set that does not use the extract tables data from SVRCALX process. It uses live data from the Banner student module tables. This allows the report to be used and reviewed all year long as needed to monitor concurrent enrollment levels.

Note: SVRCALP only evaluates each CRN’s status for the 10% concurrent high school enrollment limit. SVRCAL9 is the district-wide report used for the sports 5% concurrent high school enrollment rule for apportionment.

All students are used on the report, but the concurrent high school student enrollment count causes the warning. A concurrent high school student is any student for whom the student type is Y (SGBSTDN_STYP_CODE = Y) because Y is the MIS SB15 valid value for “A special admit student currently enrolled in K-12.”

Note: The selection of the student data must use the standard Banner effective-term logic. Some students will have different data (concurrent student type) used in the report because the data changed between terms within the reporting year such as a student who changes from concurrent to not-concurrent within an academic year. The data for each term will be reported as concurrent or not-concurrent as appropriate for that term using effective term logic.

See CCFS-320 Reporting for more information.

320 Attendance Extract Process C3SC (SVRCALX)

This process was created to support the CCFS-320 Reporting functionality. This extract process selects all of the data used for the report for an academic year’s terms, CRNs and meetings, students, and registrations.

Important: To comply with the regulatory requirement introduced on March 25, 2024, by the Board of Governors on Standardized Attendance Accounting, a new parameter was added to the SVRCALX process to allow administrative users to define the calculation method used for process execution. This new parameter will enable the user to select Y if they want to use the new Standardized Attendance Accounting method or N if they want to use the previous calculation method. It will also control the calculations displayed for the reports executed later.

The data is saved in the following tables:

  • Report Definition Data Table (SVBCALP)
  • Term Data Table (SVRCALT)
  • CRN Data Table (SVRCALN)
  • Student Registration Data Table (SVRCALR)
  • Student Data Table (SVRCALS)
  • Student Registration Override Data Table (SVRCALO)

The CCFS-320 reports are created in separate processes from the table updates. All of the calculations are handled within the extract and saved with the data.

The output file SVRCALX.lis contains a record-count summary of the data extracted. If the value for the Include Exceptions Report parameter is Y, the output will also include the exception report, which lists CRNs that were excluded from reporting (contract CRNs or CRNs without reportable data) and CRNs with erroneous setups. This section also lists students that were excluded because they are in an included Positive Attendance CRN but have zero attendance hours or they are in an included Positive Attendance CRN with some attendance hours but no grade. This list should be reviewed for accuracy. These CRNs and students are saved to the extract table, but they are not included in the apportionment reports.

See CCFS-320 Reporting for more information.

Additional information about the CRNs in the exception report is provided in the following table. The first part of the message matches these messages, and the ending part of the message indicates what the problem is.

If the error message text begins with... It means...
Exception CRNs not reported... This is a CRN coded to suppress from apportionment or a valid CRN with no registration data (census students or actual hours) to report.
Exception CRNs not valid... This is a CRN with a setup that is not valid for reporting. Fix the related data to have the CRN included in apportionment reporting, then re-run the extract.
Exception CRNs errors... This is a CRN encountering a problem that should be reported to your administrative support contact.

The report has three reporting periods, but these are cumulative for the academic year. For reporting period 1, July 1 to December 31, data within that date is reported. For reporting period 2, January 1 to April 15, data within that date is reported along with the period 1 data. For annual reporting through July 1 through June 30, all data for the academic year is reported.

There are two extra Reporting Period parameters on the report: Resubmit-1 (R1) and Resubmit-2 (R2). These use all of the same logic as the Annual parameter; the only difference is that the extract data is saved with period R1 or R2; their data is not a replacement of the annual data in the extract table.

With each run, the process saves all selected data into the extract tables. If you re-run the process with the same academic year, district/college ID, and reporting period, the old data will be replaced. The CCFS-320 reports are created from this saved data. Other than SVRCALP, live Banner data is not used in the reports. SVRCALP uses live Banner data instead of the extract table data to allow for faster evaluation for the 10% concurrent high school enrollment rule early in the term without the burden of a complete CCFS-320 setup.

When selecting the summer intersession terms, the process considers how the Leading Summer check box on the Academic Year Validation Page (SVAACYR) is set, as follows.

  • If the Leading Summer check box is unchecked, the summer intersession is considered to be a trailing summer in the academic year (Fall-Spring-Summer) specified on the Term Control Page (STVTERM). The leading summer intersession is defined in STVTERM with the prior Academic Year value.
  • If the Leading Summer check box is checked, the summer intersession is a leading summer in the academic year (Summer-Fall-Spring) specified on STVTERM. The trailing summer intersession is defined in STVTERM with the next Academic Year value.

AB2248 Cal Grant Process (SVRCALG)

This process creates a custom response for the Acknowledgment action item, posts the action item and response to students enrolled in a particular term, and resets the Accept indicator on GOATPAD (GOBTPAC_USAGE_ACCEPT_IND) to 'N' for that same group of students.

The process inserts one record into the GCRAISR table to create a new response for the Acknowledgment action item, using the Action Item Response Text parameter so that institutions can determine the text of their responses.

Examples:
  • Acknowledged for Fall 2020
  • Acknowledged: Spring 2019
  • 202010

The examples should be distinct enough for you to build an audit trail of each term in which a student acknowledged the Cal Grants information by accepting the Terms of Usage page.

The process inserts one record into the GCRAACT table for each student enrolled in a particular term for the Acknowledgment action item, using the following three parameters:
  • Enrollment Term – ensures that the Acknowledgment action item is only posted for students who have an enrollment record (SFBETRM) for a particular term. You can only run this process for one term at a time.
  • Number of days to end Action Item – the GCRAACT table requires that an action item be posted with a display start date and display end date. The display start date will be set to the system date and the display end date will be set to system date plus the number of days entered for this parameter.

    Students cannot have the same action item posted for overlapping dates, so this date range should be kept quite small. It is possible to set the number of days to zero so that the display start date and display end date are the same date.

  • Action Item Response Text – allows the response inserted into GCRAISR to be assigned to the student’s action item record on GCRAACT.

Finally, the process sets the Accept indicator on GOATPAD (GOBTPAC_USAGE_ACCEPT_IND) to 'N' for any student with an enrollment record (SFBETRM) for the term entered for the ENROLLMENT_TERM parameter. This ensures that the next time those people attempt to log into self-service they will be presented with the Terms of Usage page.

Notes for the timing of running AB2248

This solution uses and reuses the same Action Item over time – Acknowledgment. This is because the only way to create new Action Items would be to install and set up CALBSTU General Self-Service 9.3 or later.

When action items are posted to students, records are inserted into GCRAACT. It is possible to post the same action item to the same student multiple times, but each set of display dates must not overlap. The delivered process will set the display start date to be the date that the process is run and the display end date to be a number of days after the date that the process is run.

If a student is enrolled in Term A and Term B and the process is run to post the action item for students enrolled in Term A and the display end date is set to system date + 1 day, then you should not run the process again for Term B until that display end date has passed.

If the process is run for Term B before the display end date has passed from running it for Term A, the student enrolled in both terms will not get the Acknowledgment action item posted for Term B but they will get their Accept indicator on GOATPAD reset to 'N'.
