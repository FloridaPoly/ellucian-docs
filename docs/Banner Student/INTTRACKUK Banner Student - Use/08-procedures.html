Tasks and step by step procedures to set up INTTRACKUK.

Define system parameters for INTTRACKUK

There are several reporting elements where the selection of the correct data depends on specific Banner codes or variables to be defined by the individual institution. (For example, Sponsor Licence Number).

About this task

To provide flexibility for the INTTRACKUK Reporting module, a set of configurable system parameters is delivered with the INTTRACKUK module. You can modify the delivered parameters to meet your needs, or you can create new ones to customize the system. You can also use these configurable system parameters to set the statuses of the CAS application. Only users with appropriate permissions can define or modify system parameters.

You can define the system parameters for the INTTRACKUK Reporting module.

Procedure

  1. Access the System Validation (GKVKSYS) page.
  2. Verify that the INTTUK system parameter code is present in the list of codes.
  3. Access the Report System Parameters (GKAKSYS) page.
  4. Enter INTTUK in the System Code field.
  5. Go to the next block.
  6. Select the parameter for which you want to enter or change the values in the Parameter field.
  7. Enter the valid value(s) for the parameter in the Value field.
    You can enter multiple values for each parameter, separated by a comma, up to 2,000 characters.
  8. If desired, enter information in the Description and Notes fields.
  9. Save your changes.

Steps to define the reporting parameters for Graduates CAS XML reporting using the SORGCAS process.

Procedure

  3. Go to the next block

    You can view the parameters only if you execute the seed data that is delivered along with this release.
  5. Enter the required values in the Configuration Value fields for the displayed parameters.

    To know more about the SORGCAS reporting parameters for Graduates CAS XML reporting, refer to the Graduates CAS XML Reporting parameters section in the Banner_INTTRACKUK_Data_Maps_8.3.8_9.3.28.1_October_2022.pdf file that is available as an attachment.

    To download this PDF file, click Attachment on this page.

Define or customize the Graduate Requirement types

Steps to define or customise the Graduate Requirement types.

About this task

The Type field in the SKAICAS page in the Graduate Requirement section denotes the proof collected from the students required to study in the UK. This field value is required to generate the XML output for the SORGCAS process, without selecting the Graduate Return Override check box for applications.

Seed data is available for the Graduate Requirement types. You can either use the seed data or add your own values, as required. The Description or Title field in the SKASSDT page determines the Graduate Requirement Type values that gets stored in the Type field in the SKAICAS page.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Perform a query for the following values:
    1. Entity field: INTTUK
    2. Attribute field: GRAD_REQUIREMENT_TYPE
  3. Modify an existing code or add a new code, as needed.
    Use the following steps to create a new value
  4. Select an available record and click Copy to insert a new row with the values copied.
  5. Update the Option 1 and Option 2 fields with the appropriate numerical values, for example, Text 8 and Code 8
  6. Enter the institution-defined values in the Description or Title field
  7. Save the record.

Define or customize user-defined CAS statuses

You can add to or change the delivered user-defined CAS status codes as required. For example, if you want to run the CAS Generation activity, you must create a user-defined status of MANCHK in SKASSDT first, after which you can view and use the code on SKAICAS.

You can define or change CAS statuses.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Perform a query for the following values:
    1. Entity field: INTTUK
    2. Attribute field: USER_DEFINED_CAS_STATUS
  3. Change existing codes or add new codes as needed.
  4. Save your changes.

Define or customize nation code mappings

You can add to or change the delivered mappings for nationality codes between GOAINTL, UCAS, HESA, and INTTRACKUK.

About this task

INTTRACKUK must use ISO 3166 Alpha 3 nation codes. Seed data delivered with INTTRACKUK includes all nations and nation codes specified under ISO 3166 Alpha-3. In addition, the following entry for the SKRUFDS table (which is maintained in the UCAS Field Description (SKAUFDS)) page defining the location of the standard mapping source and target is delivered:
Field Name INTTUK_NATION_MAP
Description UKBA nationality mapping
Mapping SKVSSDT
SKVSSDT Entity INTTUK
SKVSSDT Attribute UKBANATIONCODE
Lookup Field SKVSSDT_SDAT_CODE_OPT_1
Description Field SKVSSDT_SDAT_CODE_OPT_2
A function similar to HESA’s SKKHEXF.FN_VALUEMAP function is used that passes in the INTTUK_NATION_MAP field name and the UCAS nation code. This function performs the following tasks:
  • Checks SKRUFDS to determine how to derive the mapping value
  • Checks the list of values defined by INTTUK/UKBANATIONCODE for the UCAS nation code
  • Returns the Option 2 value mapped to the Option 1 UCAS nation code as the UKVI nation code
If you want to use different SKVSSDT nation codes or mappings from the ones delivered, you must define the different source location of the codes on SKAUFDS and then map those to the target codes on SKASSDT as described in the following procedure.

Procedure

  1. Access the UCAS Field Description (SKAUFDS) page.
  2. Define values for the following fields to add the nation code mappings:
    1. Field Name (must be INTTUK_NATION_MAP)
    2. Description (must be UKVI nationality mapping)
    3. Entity
    4. Attribute
    5. Lookup Field
    6. Description Field
  3. Save your changes.
  4. Access the Student System Data Maintenance (SKASSDT) page.
  5. Perform a query for the following values:
    1. Entity field: INTTUK
    2. Attribute field: UKBANATIONCODE
  6. Select the desired record.
  7. Enter the value that you want to use as UKVI nation code in the field specified in the Description Field in the SKAUFDS page.
  8. Repeat Step 6 and Step 7 for each record.
  9. Save your changes.
    For example, if an existing SKVSSDT nation list is defined for the SKBSPIN entity and SKBSPIN_NATN_CODE_LEGAL attribute, you could add an appropriate UKVI value to each entry in the Data 1 field. You would enter the following values for the INTTUK_NATION_MAP SKRUFDS entry:
    • SKVSSDT Entity: SKBSPIN
    • SKVSSDT Attribute: SKBSPIN_NATN_CODE_LEGAL
    • Lookup Field: SKVSSDT_SDAT_CODE_OPT_1
    • Description Field: SKVSSDT_DATA

Define or customize residence codes

You can modify or setup specific non-EU residence codes that indicate students who will require a CAS application.

About this task

The residence code of the student used in SGASTDN must exist in SKASSDT under the following information:
  • Entity: INTTUK
  • Attribute: NON_EU_RESD_CODE

The entity and the attribute information is used in defining all students having theresidence code against the student’s record as non-residents that is according to the UKVI regulation.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Perform a query for the following values:
    1. Entity field: INTTUK
    2. Attribute field: NON_EU_RESD_CODE
  3. Either create a record or copy an existing record, as appropriate.
  4. Enter the value to be used as the non-residence code from SGASTDN in the Option 1 field.
  5. Repeat Step 3 and Step 4 for each record.
  6. Save your changes.

Define SELT test score

The list of values for the SELT Test Date field in the English Qualification section of the SELT and Progression Details tab of SKAICAS looks up SELT test scores stored on the Test Score Information (SOATEST) page.

About this task

Test scores are sorted by test date in descending order. When you select a test date, the system populates the following fields in SKAICAS with the appropriate values from SOATEST.
  • SELT - Speaking
  • SELT - Listening
  • SELT - Reading
  • SELT - Writing
To make use of this feature, you must set up entries for the Reading, Writing, Speaking and Listening test types under the SELT_SCORE attribute on SKASSDT and map the test codes used on SOATEST to the corresponding test types.

You can map more than one test code to a test type. This allows you to account for cases where different test codes are used to record test results from different test providers (such as TOEFEL, IELTS, and so on).

Individual scores from different test dates cannot be selected because UKVI allows only scores from same test instance (date) to be used for a CAS application. If a selected set does not contain values for all four SELT score types, the system displays an error message asking the user to review and correct the data on SOATEST.

The following procedure explains how to create a SELT_SCORE attribute record.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Create a new record for the INTTUK entity and SELT_SCORE attribute.
  3. Copy Option 1 field (ELRD, ELWR, ELSP, ELLS) and Short Title field (Reading, Writing, Listening, and Speaking) as defined in the INTTUK standard entries.
  4. Use Option 2 and Option 3 fields to map your SELT related custom test codes (defined on STVTESC and used in SOATEST) to the corresponding SELT test type.
  5. Optional: If you need to map more than two test codes to one test type, you can create additional SKASSDT records for the same SELT test type.
  6. Save the record.
    There are a few SELT tests/certificates that are valid indefinitely, such as the following:
    • Cambridge IGCSE English as a First Language
    • Cambridge IGCSE English as a Second Language
    • Cambridge Certificate in Advanced English
    • Cambridge Certificate of Proficiency in English
    Hence, for each test code mapped in SKASSDT under the SELT_TEST_SCORE attribute, to define for how many years the specific test codes are valid. Data 1 can be used to enter the number of years the results for test code under Option 2 are valid. Data 2 can be used to define validity for the test code in the Option 3 field. The following rules apply for the validity of test scores:
    • Validity is entered in number of years, for example, if it is a value of '2', then this means that the test results are valid for two years.
    • If the validity of the test is indefinite, no value would be entered in the corresponding Data field.
    • When test scores are read from SOATEST into the SELT Test Date LOV in SKAICAS, test scores that have expired based on value defined in SKASSDT will not be displayed in the LOV and hence cannot be copied into SKAICAS SELT score fields through the LOV.
    • In addition, when a test date older than two years is manually entered in SKAICAS, on save a warning will be shown asking the user to confirm if test scores may be older than two years according to UKVI guidelines. Use OK to confirm and Cancel to correct the test date
    Note: The test code specific expiration validation will only work for test scores entered in SOATEST. For manual test score entry in SKAICAS, no test codes are entered, hence no test code specific validation can be carried out other than the basic two-year check.

    The following procedure explains how to define validity of SELT Test results.

  7. Access the Student System Data Maintenance (SKASSDT) page.
  8. Select the record under the INTTUK entity and SELT_SCORE attribute for which you want to define expiration.
  9. For the test code mapped in Option 2 enter the number of years the test results are valid in the Data 1 field, for example, 3 for three years. Where applicable, for the test code mapped in Option 3 field enter the number of years the test results are valid in the Data 2 field.
  10. Save the record.
Define user-defined text

You can define standard text to explain why an applicant who has previously studied in the UK plans to pursue another program of study that leads to the same or lower qualification as the previous one.

About this task

You set up predefined justification text records on the Student System Data Maintenance (SKASSDT) page under the USER_DEFINED_JUSTIF_TXT attribute. Institutions will see the predefined text records in the list of values for the progression Justification Text field and can select an appropriate record without having to retype or copy it each time. The following procedure explains how to create USER_DEFINED_JUSTIF_TXT attribute records.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Create a new record for the INTTUK entity for this attribute.
  3. Enter your custom text in the Option 1 and Short Title fields.
  4. Add your custom justification text in the Description field
    The LOV for the Progression Justification field in the SKAICAS page will only show the justification text as defined in the Description field.
  5. Save the record.
Define INTTUK attribute records

When customizing the SKASSDT entries for the SELT and progression attributes, (SELT_LEVEL, SELT_REASON, SELT_TEST_PROV, and PROG_LEVEL), Ellucian recommends that you do not delete the original records as provided by the INTTRACKUK installation, but add new records for corresponding attributes to create your custom data.

About this task

To obsolete or temporarily inactivate records on SKASSDT, Ellucian recommends that you remove the active flag for the record rather than deleting the SKASSDT record. In the current setup, the INTTRACKUK-specific entries are displayed on SKAICAS after the termination date defined on SKASSDT.

In addition, when an SKASSDT record is made inactive, the values already saved on SKAICAS are still displayed in the corresponding fields on the page. This is because, in most cases, the record has already been exported to XML and sent to UKVI, and the CAS record should reflect the values that were sent to UKVI. Values from inactive SKASSDT records are no longer shown in the LOVs in the SKAICAS page and cannot be selected.

The following procedure explains how to create INTTUK attribute records.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Create a new record for the INTTUK entity for this attribute.
  3. Enter your custom text in Option 1 field.
  4. Define the code to be used in the CAS Applicant Upload XML in the Short Title field.
    Codes must be all uppercase.
  5. Enter a description of the code in the Description field.
    This description displays the code in the corresponding field in the SKAICAS page. It allows you to provide more descriptive information about the code, but it is not used in the XML output that is sent to UKVI.

Customise Work Placement attributes

The Work Placement justification text field in SKAICAS allows you to enter an explanation as to why the work placement is more than 33% of the total length of the program.

About this task

UKVI, however, only allows for this threshold to be exceeded for a very limited number of reasons. Therefore, INTTRACKUK delivers a set of template justification text records as seed data.

With the USER_DEFINED_WP_JUSTIF_TXT attribute in the SKVSSDT table, you can enter a code as a short unique identifier for the justification record in the Short Title field in SKASSDT. The description field is used to enter the justification text to be sent to UKVI.

INTTRACKUK delivers three template justification records which cover the three valid reasons defined in the UKVI guidelines (valid March 2013) as to why work placement for Tier 4 General can exceed 33%. You can however, customize the template text or setup additional justification text records depending on the specific requirements of your institution. This flexible setup will also enable you to implement changes quickly when UKVI guidelines are changed.

The attribute delivers the following standard entries:
  • The course which includes a work placement of not more than 50 per cent of the total length of the course is at NQF/QCF 6 or SCQF 9 or above and is studied at a higher education institution.
  • The course which includes a work placement of not more than 50 per cent of the total length of the course is at NQF/QCF 6 or SCQF 9 and forms part of a study abroad programme.
  • There is a UK statutory requirement for the course to contain a specific period of work placement which exceeds the 33% threshold. The work placement is an integral and assessed part of the course.
The justification text records setup in SKASSDT are then displayed in the list of values for the Work Placement justification text in SKAICAS. The Code from the Short Title field in SKASSDT is shown in the LOV in addition to the justification text from the Description field in SKASSDT, but when selecting a text record, only the justification text itself will be pasted into the Justification field. The (template) text inserted into the Justification field can then be amended or edited in the field itself as required.

The following procedure explains how to create USER_DEFINED_WP_JUSTIF_TXT attribute records.

Procedure

  1. Access the Student System Data Maintenance (SKASSDT) page.
  2. Create a new record for the INTTUK entity for the USER_DEFINED_WP_JUSTIF_TXT attribute.
  3. Enter your custom text in the Option 1 and a unique code/identifier in the Short Title fields.
  4. Add your custom justification text in the Description field.
  5. Save the record.

Create CAS application records

To generate a CAS application for bulk upload in the SMS portal, you must create a CAS application record for an applicant or a student, admission term, and program.

Each CAS application is assigned a unique CAS application ID in the Confirmation of Acceptance for Studies (SKAICAS) page and in the CAS Details (SKRICAS) table. You can create the CAS applications manually using the SKAICAS page or automatically using a corresponding activity.

Manual creation method

You can create a CAS application manually.

Procedure

  1. Access the Confirmation of Acceptance for Studies (SKAICAS) page.
  2. Select the Banner ID for the applicant or the student.
    You can use the List of Values (LOV) search button to search query for a person by name, ID, and other criteria in SOAIDEN.
  3. Select Next Block.
  4. In the Term Code Admit field, enter the admission term or select a term code using the LOV.
  5. Select a program from the Program field.
    The LOV displays the programs for which an admission or learner record exists for the name selected and for the specified admission term.

    When an Admission record and a Learner record exist for a Student/Term and both show in the Program LOV in the SKAICAS page, and when you select the Admission record from the LOV, on saving, the Learner record gets selected, because it is assumed that the program associated with the Learner record will be the main program of study.

  6. Enter the relevant CAS application data on the Confirmation of Acceptance for Studies Data window.
    For example, you can enter a visa start date to override the official start date of the program or include the duration of a pre-sessional course for a degree program in the main application.
  7. Save the record to assign an unique CAS application ID to the record.

Automatic generation method

You can create a CAS application using automatic generation method.

About this task

The activity delivered with INTTRACKUK only creates new CAS application records in Confirmation of Acceptance for Studies (SKRICAS) table for applicants with a valid LEARNER record. The following selection criteria are applied for automatic generation method.
  • The residence code of the student in SGASTDN must exist in SKASSDT under the INTTUK entity and NON_EU_RESD_CODEattribute.
  • The student must have a status of AS (Active) in SGASTDN.
  • The program start date must be after the current date, but within the number of advance upload days as defined in the ADVANCEUPLDDAYS system parameter.
  • Another CAS application must not exist for the same student, term, or program (or curriculum priority).

Procedure to generate new CAS application records automatically.

Procedure

  1. Access the Process Tree Execution (GKAPEXE) page.
  2. Enter ESC_PBS_REPORTING in the Process Code field.
  3. Select Next Block.
  4. Select the ESC_CAS_GEN activity.
  5. Customize the execution tree to meet your local requirements.
    For example, you can change the status of tree nodes using the Change Status option. If desired, you can customize the activities and add these to the execution tree, or you can create your own execution tree. If you customize the activities, you need to create local copies of the baseline activities first.
  6. Go to the Execution window.
  7. Enter the values for the parameters as required.
  8. Change the value in the Execution Mode field to Update.
  9. Select either Run from Jobsub or Run Now, as desired, to execute the process.
  10. Review the results by selecting the View SQL log.
  11. Review records with User Defined Status MANCHK in SKAICAS.
  12. Enter additional data for the application, if required.
    You can remove CAS applications or use the Do Not Send CAS Applications check box on SKAICAS to prevent a specific record from being included in the Upload Snapshot.

Change CAS status to REFUSED

You can change the CAS application status to REFUSED.

Procedure

  1. Access the Confirmation of Acceptance for Studies (SKAICAS) page.
  2. Specify a record in the key block, then go to the next block.
  3. Go to the Refusal Information tab.
  4. Select the Date of Refusal.
    You can either enter the date in the day, month, and year format, use T for today, or select the date using the calendar icon.
  5. Enter the reason for refusal in the Reason for Refusal field.
  6. Enter the entry clearance post name in the Entry Clearance Post text field, if known.
  7. If an administrative review has been requested, select the Adm. Review Requested check box.
    You can enter any information on the administrative review in the text field next to the check box.
  8. If the administrative review was successful, select the Adm. Review Successful check box.
    The Set Status to Refused button becomes inactive. You cannot set the status to REFUSED when the administrative review was successful.
  9. In the Further Information field, enter any further information regarding the refusal, fee refunds, and other relevant data.
  10. If the administrative review has not been successful, click Set Status to Refused to change the status of the record to REFUSED.
    The CAS status can be set to REFUSED only if the current status of the record equals the value set for the FROM_STATUS_REFUSED parameter in the Report System Parameters (GKAKSYS) page.
  11. If required, create a new CAS application record for the student either using ESC_GEN_CAS, or using the Copy functionality or directly inserting a new record.

Revert CAS status of REFUSED

You can revert CAS status of REFUSED to the previous status.

Procedure

  1. Access the Confirmation of Acceptance for Studies (SKAICAS) page.
  2. Specify a record in the key block, then go to the next block.
  3. Go to the Refusal Information tab.
  4. Click Revert Status to: xxx.
    The XXX status will dynamically display the last valid status in the CAS history that the record was on before the record was set to REFUSED. This sets the status back to the last valid status that the record had before the status was set to REFUSED.
  5. 5. If appropriate, enter any new administrative review information.

Change CAS status to CLOSED

You can change the CAS application status to CLOSED.

Procedure

  1. Access the Confirmation of Acceptance for Studies (SKAICAS) page.
  2. Select the desired CAS record.
  3. Verify that the CAS History contains the status as specified for the FROM_STATUS_CLOSED parameter as the latest entry.
  4. Go to the Confirmation of Acceptance of Studies Data tab.
    The Close CAS button should be enabled.
  5. Click Close CAS to close the CAS application.
  6. If required, create a new CAS application record for the student either using ESC_GEN_CAS, or using the Copy functionality, or directly inserting a new record.

Search for CAS records

You can search for specific CAS records and select them in SKAICAS using the CAS query (SKIICAS) page.

About this task

The SKIICAS page is accessible from the key block of the SKAICAS page and allows you to enter a number of search criteria to find a specific record. This is especially useful in cases where UKVI sends or requests information on a CAS record but only provides the CAS Number as a reference.

Procedure to search for specific CAS records.

Procedure

  1. Access the Confirmation of Acceptance for Studies (SKAICAS) page.
  2. Click the Search icon on the right side of the key block.
  3. Enter your search criteria in any of the available fields, like CAS Number, Passport Number, and so on.
    Query is case insensitive. You can use wild-cards as required.
  4. Execute the query.
  5. Select a record from the list of query results.
  6. Double-click the ID column to go back to SKAICAS. The ID for the selected record will be displayed in the key block of the SKAICAS page.
  7. Select Next Block to view the CAS record details.
    Only the selected CAS record will display even if several CAS records exist for the same Student ID. You can make required changes to the CAS record and save changes. To view all records of the student, you need to go back to the key block and use next block again to refresh query.

    When SKIICAS is opened directly from main menu or using the Go to field, double-clicking into the ID field for a selected record will not open the SKAICAS page.

Process INTTRACKUK data

You can control the execution of each process to run specific activities or tasks separately, or to run all tasks and activities at once. However, we advise you to run each task separately, evaluating the data each time.

This results in better processing times and allows you to do any data cleaning before the final data is used in any reporting.

The export activities validate all the mandatory data elements that are available in thesnapshot table before the export into XML file occurs. If the data elements are missing, the export activity will fail and a .LOGfile will be written to the Oracle directory that has been specified as your output directory for the activity run. The .LOGfile will provide details on detected errors.

The ESC_PBS_REPORTING process is used to create snapshots and export data for the Applicant Upload, Update, No Shows, CAS Import, and E-mail Notification procedures.

If you have installed Attendance Tracking, the ESC_PBS_ATTR_REPORTING orESC_PBS_ATTR9_REPORTING processes can be used as required to produce Missed Contact reports.

Applicant upload reports

The select query for the activity identifies entries in the CAS Details (SKRICAS) table, where the CAS number has not yet been assigned (where SKRICAS_CAS_NUMBER is null) and the Do Not Send CAS Applications flag is unchecked (= No).

The upload snapshot activity will check whether an entry does not already exist in the Upload/Update Snapshot Table (SKRAULD) for the specified ID or the CAS application ID and has been stamped as exported.

If an entry already exists from a previous run that has not yet been exported, the existing record will be updated in the snapshot table.

Create upload snapshot

You can run the upload snapshot activity (ESC_PBS_AUPLD_SNA) and collect all data elements required for CAS application upload from different places in the Banner system, in addition to INTTRACKUK specific tables.

Procedure

  1. Access the Process Tree Execution (GKAPEXE) page.
  2. Enter ESC_PBS_REPORTING in the Process Code field.
  3. Select Next Block.
  4. Select the ESC_PBS_AUPLD_SNA activity.
  5. Customize the execution tree to meet your local requirements.
    For example, you can change the status of tree nodes using Change Status. If desired, you can customize the activities using the Execution Tree Setup (GKAPACT) page and add these to the execution tree, or you can create your own execution tree. If you customize the activities, you need to create local copies of the baseline activities first.

HESA Data Futures impact on upload snapshot

The INTTRACKUK snapshot process pulls the data from the HESA Data Futures table into the snapshot table, when the data exists in the HESA DF tables.

Otherwise, if the HESA Data Futures tables are null and you maintain the data as you do it currently, the data pull into the snapshot table works as is without any changes. This functionality impacts only the Nationality field.

Institutions can populate social economic identifier 'NATION' value in the GOAPSID page for the students. As a result, when the institutions execute the ESC_SNA_AUPDT snapshot activity, the activity fetches the Nationality value for the students from the GORPSID table (table for the GOAPSID page). This action populates the corresponding three-character country code in the SKRAULD snapshot table.

Note: The Nationality values that you use in the GOAPSID page are HESA Data Futures compliant and are two-character country codes.

HESA Data Futures Nationality values

Inherently, the ESC_SNA_AUPDT is designed to supply the three-character country codes to the SKRUALD table. As is, institutions use the country code in the Option 1 value for the UKBANATIONCODE attribute and INTTUK entity to enter the Nationality for their students. Therefore, the snapshot activity populates the Option 2 field values for the respective Option 1 value.

When institutions use the two-character codes in the NATION field for student's nationality, the snapshot activity returns the three-character nation codes in the SKRAULD table.

To map the HESA Data Futures codes to the as is country codes that are available for the UKBANATIONCODE attribute and INTTUK entity, Ellucian delivers update scripts to populate the HESA Data Futures country code in the Option 3 field for records with Attribute: UKBANATIONCODE and Entity: INTTUK.

Note: If your database has the appropriate three-character country code values for Option 2 field for the UKBANATIONCODE attribute, the update scripts will execute and populate the two-character country codes in the Option 3 field for the corresponding Option 2 value. If there are no records with appropriate country codes in Option 2, the update script finds no records to update. The update scripts will only update and not insert new records for the UKBANATIONCODE attribute INTTUK entity.

Therefore, after you run or execute the update scripts, mapping is available in the SKASSDT table, where you can view the Option 3 field values with two-character country codes for the UKBANATIONCODE attribute INTTUK entity.

The following are some of the real time use case scenarios at an institution and the respective outcomes.

Scenario 1:When institution maintains data both in the GOAPSID, GOAINTL, or other UCAS/HESA pages.

When an institution uses the GOAPSID page for its students to populate the Nationality in the respective HESA_COUNTRY report (based on the HESACOUNTRY value in the GKAKSYS page), the snapshot activity, on execution, picks the Nationality value from the GOAPSID page. Then, the corresponding three-character country code value in the Option 2 field for the UKBANATIONCODE attribute and INTTUK entity is matched and fetched to populate the SKRAULD snapshot table.

If the mapping for the Nationality value (two-character country code) that the GOAPSID page uses for a student does not exist in the SKASSDT page, and the Nationality values exists in other UCAS/HESA pages, the SKRAULD table populate with values corresponding to the Nationality values in the GOBINTL/SKBSPIN tables as is.

Scenario 2: When institution maintains the nationality values for its students in GORPSID only.

If institution has setup the Nationality for students in the GOAPSID page only, the snapshot activity populates the SKRAULD table with the three-character country code from the Option 2 field for the UKBANATIONCODE attribute and INTTUK entity. The Option 2 field corresponds to the Nationality value from the GOAPSID page (which will exist in Option 3 for the UKBANATIONCODE attribute and INTTUK entity)

When the mapping for the two character HESA Data Futures country code in the Option 3 field for any Option 2 value that does not exist, the Nationality values in the SKRAULD snapshot table is blank and subsequently the export process fails.

Scenario 3: When institution maintains the Nationality values for the GOAINTL page and other UCAS/HESA pages, and not in the GOAPSID page.

The snapshot process works as it is without any issues. The Option 2 field values mapped to the country codes for the UKBANATIONCODE attribute and INTTUK entity that populates in the SKRAULD table.

Graduate CAS report

CAS Numbers for eligible students who successfully completed their course of study should report to the Home Office. Unlike the other MDUU- based activities for Banner INTTRACKUK reports generation, the Graduates CAS report uses the SORGCAS process in job submissions to generate the Graduate CAS report.

Ensure that you have the following setup in place before you proceed with the SORGCAS process.
  • Enter the CAS_GRADUATE_LEVEL_CODE and CAS_STATUS reporting parameters in the GUACONF page to define which Level Codes and CAS Statuses are eligible for graduation confirmation.
  • Students should be graduates with the respective Outcome records on the SHADEGR page and a qualifying Outcome Status, provided the Awarded Indicator field is set to Awarded for the Outcome Status in the STVDEGS page.
  • Students degree records should have a valid degree code defined in the STVDEGC page.
  • You should enter the values in the Type and Date Obtained fields in the Graduates Requirements section of the SKAICAS page.
The SORGCAS process extracts the CAS Numbers for students that meets the criteria listed in this section and subsequently extracts the CAS Numbers for students with the degree levels and CAS statuses that you have defined for the relevant parameters in the GUACONF page, provided the Outcome records exists with the Awarded Indicators check box set to Awarded.

Alternately, institutions can override the applied SORGCAS validations by enabling the Graduate Return Override check box for CAS applications. By enabling this option, the SORGCAS process overlooks any of its inbuilt validations and prints the CAS Numbers in the XML output for all the applications with override option selected.

Note: After the CAS Number for an application is printed in the XML output for the SORGCAS process and the Graduate CAS History is populated for CAS application, (that is SKRICAS_GRAD_CAS_BATCH_TYPE, SKRICAS_GRAD_CAS_BATCH_DATE, and SKRICAS_GRAD_CAS_BATCH_NAME), you cannot update the status of the Graduate Return Override option.

Refer to the Student Graduation Data Update (SORGCAS) process available in the INTTRACKUK Reports and Processes content to know more about the process functionality.

View INTTRACKUK history data

You can view INTTRACKUK history through SKICTAF and GKAPUNV pages.

CAS Transactions Audit (SKICTAF) page

Many institutions create CAS applications in various steps using a combination of automated or scripted population of the Confirmation of Acceptance for Studies (SKAICAS) page fields and manual data entry. There are also cases where an application is created manually in SKAICAS and in the SMS without making use of Bulk Data Transfer.

Also, the different steps are often carried out by different users within the International or Registrar's Office. For example, the first user (which can be an overnight process) runs a script or MDUU activity to (mass) create CAS records, the second user reviews data and sets a user-defined status on the record, the next user enters additional data, then another user verifies data again and flags record as ready to go and so on.

With the introduction of the CAS audit form and table, all users authorized to access the audit form can now see and review changes made to the CAS records.

The audit form and table allow users to do the following.
  • An audit table logs the changes committed to the SKRICAS table for any CAS record in SKAICAS. In addition, some CAS data items that were not stored in the SKRICAS table, like the Program and Term Code Admit entered for a CAS record in SKAICAS, are logged in the new audit table as well.
  • The CAS Transactions Audit (SKICTAF) page displays all transactions logged in the SKRCTAF audit table and also allows users to view changes made to almost all fields available in the following tabs in SKAICAS:
    • Confirmation of Acceptance for Study
    • SELT and Progression Details
    • Work Placement Details
    • No Show Details
    • Missed Contact Details
    • Refusal Information
  • The transactions are divided into three types, namely, initial creation of a CAS record, data updates, (that is, insertion, update, and deletion of data) and record deletion.
  • Users can track the sequence of changes for any field by comparing data shown for previous sequence number with data for next sequence number.
  • Users can easily query the audit form for a specific record or a student/applicant by entering (a combination of) search criteria in the following key block fields of the audit form:
    • ID
    • CAS Number
    • Activity Date
    • USERID
  • Users can further refine the query made in the key block by entering additional search criteria in any of the fields in the main block.
It is important to note the following:
  • Queries in SKICTAF are case insensitive.
  • Last Updated date fields for Fees are excluded from the audit form as the activity date in the audit form already indicates when fields were updated.
  • The work placement address details are not logged in the audit form/table because the data is stored in the SPAIDEN page and displayed as read-only in SKAICAS.
  • As the Total Number From Latest Snapshot is only stored in the SKRMCON table, the audit table will not be updated immediately when SKRMCON is changed, As the usual work flow would be to run the activity, then go into SKAICAS form, report missed contacts to UKVI and update the relevant reporting fields in the Missed Contacts section in SKAICAS, only when next updates on SKAICAS are saved, a record will be created in the audit table and the latest values from SKRMCON inserted into the audit record. If values are retrieved from Attendance Tracking 8 and Attendance Tracking 9, counts are added up and only total counts are displayed in the audit form (same as in the corresponding SKAICAS field).
  • The SMS Upload and Update History fields have been excluded from the audit form/ table, as the tab is already displaying a log of transactions mostly stored in tables other than SKRICAS.
  • Records created previous to the introduction of the audit form/table will not show in the audit table/form. However, if these existing records are updated after installation of the 8.3 release, any updates will be logged going forward. The record with sequence number 1 would however show a transaction type of U (Update) and not I (Insert).

Universal Viewer (GKAPUNV) page

You can view the INTTRACKUK snapshot tables (SKRAULD, SKRNOSH and SKRMCON) created under the MDUU schema at any point in time to verify data using a SQL tool such as SQL*Plus or a reporting tool like Oracle Discovery. The MDUU includes a Universal Viewer to allow this data to be viewed.
