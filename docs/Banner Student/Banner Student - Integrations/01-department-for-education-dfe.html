Department for Education (DfE)

DfE Application Processing is the portal through which teacher training applicants can apply for a postgraduate teacher training course to teach in a state primary or secondary school, or in further education.

Note: This 9x version corresponds to the Banner Student 8.35 release version.
Using the DfE Application Processing Apply service, applicants apply for teacher training and set out the qualities, interests and ambition they could bring to the teaching profession. Providers of teacher training courses will use DfE Application Processing Apply to assess candidates’ eligibility and suitability for their training courses. They need information at the correct time and in the right format so that they can make well-informed decisions about which candidates to accept.
The Banner DfE Application Processing solution allow institutions to perform the following for all DfE Teacher Training applications.
  • Connect from Banner to Ethos Integration Pipelines using Ethos APIs. Ethos Integration Pipelines is a framework that allows institutions to integrate Ethos with non-ellucian partners.
  • Capture DfE Application Processing application information in Staging tables.
  • Load data to Electronic Admissions Tables for application processing.
  • Process Applications using the existing Electronic Admissions Processing logic supplied in Banner in concert with new additional Admissions functionality introduced to support DfE Application Processing. You can use the additional functionality for all application types, with appropriate configuration.
  • Check all incoming applications against existing records in the Banner database and push applicants to Banner Person and Admission tables using the existing Electronic Application Push processes (SAAEAPS and SARETMT).
  • Review applications and apply decisions for the applications using the SAADCRV page. For the admission records, you can also review the institution applied decisions from DfE Application Processing, that are updated in the SAADCRV page, using the Ethos Integration Pipeline.
  • Post application decisions from Banner to the Ethos Integration Pipeline and transact with the DfE Application Processing service.

About DfE Application Processing

de Ellucian DfE Application Processing solution supports the processing of teacher training applications submitted to institutions in England through the Apply for teacher training service of the UK Department for Education (DfE).

Terminology

This documentation uses the following terms:

Term Definition
DfE Apply The "Apply for teacher training" service of the UK Department for Education (DfE)
DfE Application Processing The Ellucian solution that supports the processing of teacher training applications submitted through DfE Apply

Processing overview

DfE Application Processing works with Ethos Integration, Banner, and the DfE API to process teacher training applications.

Prospective teachers can apply for teacher training through DfE Apply. The DfE provides an API where institutions can electronically retrieve applications for which the applicant has designated that institution. Institutions can use the same API to post decisions on those applications back to the DfE.

de Ellucian DfE Application Processing works with the DfE API and Banner to help you process teacher training applications. DfE Application Processing works as follows (see the diagram below):
  1. DfE Application Processing retrieves applications from the DfE using the DfE API, and then posts those applications through Ethos Integration to Banner.
  2. In Banner, you evaluate the applications and record decisions.
  3. Banner publishes the decisions to Ethos Integration.
  4. DfE Application Processing retrieves the decisions from Ethos Integration and then posts those decisions back to the DfE.

DfE Application Processing uses the Packages feature of Ethos Integration.

Configure DfE Application Processing in Banner

Institutions must configure DfE to process DfE Teacher Training applications through the Banner Student System.

The collection of the data and data extraction for admissions processing is performed in the Banner Student database. The processing is designed to accomplish the data collection of applications from DfE required by institutions to perform admission activities.

The following sections discusses the step by step configuration procedures that are involved in the DfE application processing.

Configure Electronic Application Processing

DfE uses Electronic Application Push processes to load applications to the Banner Student database.

The STVWSCF and STVWSCT setup pages are already delivered and institutions can view the values that gets displayed. Refer to the Banner Student Reference content to know more about the values that are already available in the pages for your setup.

Configure application type

Use the Application Type Code Validation (STVWAPP) page to define the type of application received.

About this task

Steps to create an application type for the DfE applications are as follows.

Procedure

  1. Access the Application Type Code Validation (STVWAPP) page.
  2. In the Code field, enter an application code for DfE application to create a new record.
  3. In the Description field, enter the description of the electronic admissions application type.
  4. In the Level field, enter the level code of the student that will be assigned to all Banner admissions applications created through the Web for this admissions application type.
  5. In the Student Type field, enter the student's type code.
  6. In the Admission Type field, enter the student's admission type code.
    If required, you can create an Admission Type in the STVADMT page for the DfE Teacher Training Application. You can define your own Admission Type code.
  7. Click Save.
    To know more about the STVWAPP page details and field descriptions, refer to Banner Student Reference content.

Configure application rules

The Electronic Admissions Application Rules (SAAERUL) page includes several rules that controls how the student admission application data is handled in Electronic Application Processing. Institutions must ensure if the rules defined in the SAAERUL page are accurate and additionally set up the DFEG group required for DfE applications processing.

About this task

To set up the DFEG group and default email types, use the following steps.

Procedure

  1. Access the Electronic Admissions Application Rules (SAAERUL) page.
  2. Enter DFEG in the Group field.
  3. Click Go to navigate to the next block.
  4. Enter the defined DfE STVWAPP code for DfE applications in DFEWAPPCODE rule label.
  5. In the DFEPHONEHOLDER rule label for DFEG group, enter INTL or PH to map the applicant's phone number to either the Phone Number (SPRTELE_PHONE_NUMBER) or the International Access field (SPRTELE_INTL_ACCESS) of the SPAIDEN page.

    If you want to record phone numbers with more than 12 characters, Ellucian recommends to set the mapping for DFEPHONEHOLDER to INTL.

    Institution staff responsible for applying decisions on DfE applications should have a valid email record in GOREMAL with the email type matching the default email type defined for USEREMAILTYPE rule group. The dfe-admission-decisions API checks for email records for staff users with email type matching the default email type (value for USEREMAILTYPE) to authenticate users.

    The dfe-admission-decisions API executes and communicates the decisions to DfE, only if the authentication is a success.

    Use the following procedure to set up the default email type.
  6. In the USEREMAILTYPE rule label for the DFEG group, enter a valid email type as defined in the GTVEMAL page.
    To create email records for staff users, use the default value (email type value entered for the USEREMAILTYPE rule label) as the Email Type in Email window of the SPAIDEN page (GOREMAL_EMAL_CODE).
    For the DFEG group, in the DFEADMNAPSTCODE rule label, enter a valid application status code that exists in the STVAPST page. You can use this application status to indicate that an application is deferred for a Term in Banner, and you can create a new application for a new term after the application is reinstated.

Term codes

To update the Withdrawn status on all applications and to create new applications after confirmed defer offer, institutions must create term code mappings with the course start dates.

Procedure

  1. Access the EDI Cross-Reference Rules (SOAXREF) page.
  2. In the key block, enter STVTERM in Cross Reference Label field.
  3. Navigate to the data block.
  4. Enter DFE as the Electronic Qualifier (SORXREF_EDI_QLFR).
  5. Enter the Course Start date in the YYYY-MM format.
    For example, if the start date for applications from staging (SAIEAST) is 01/09/2021, then the electronic value must be 2021-09. Ellucian mandates institutions to map the applied course start date and offer start date for all courses to the respective term codes.
    Ellucian mandates the mappings because, if you want to update the Withdrawn status for an application in the SAADCRV page and if there is an offer start date in staging, the dfe-application-submission-api searches for the respective term. If the offer start date is blank, the API searches for the term that is mapped to the applied course start date.
  6. Enter the STVTERM code in theBanner Value field.
  7. Save the record.

Set up Curricula Mapping for DfE courses

Steps used to map DfE course codes to Banner courses.

Before you begin

In the Curriculum Rules Control (SOACTRL) page, you must select the Perform Curriculum Checking (SOBCTRL_CURR_RULE_IND) option button to set as Yes. The dfe-application-submission-process API uses this setting to validate and update the curricula for admissions records, when there are changes to the offer course.

Procedure

  1. Access the Curriculum Mapping (SOACMAP) page.
  2. In the Key block, specify the academic year of the mapping rules.
    The Academic Year is not a mandatory field. You can directly navigate to the data block by leaving the Academic Year field value as blank.
  3. Go to the next block.
  4. From the Term LOV field, select a term value.
  5. From the Programme LOV field, select a program value.
    Ellucian recommends that the level for the DfE application type that you have already created in the STVWAPP page should match the level for curricula record in the SOACURR page.
  6. The Campus field displays the campus value automatically if the value is already setup for respective curricula record in the SOACURR page. Else, select a campus value from the Campus LOV field.
    Institutions should configure the campus value in the SOACMAP page as a Banner value (SORXREF_BANNER_VALUE) for the associated DfE campus value in the SOAXREF page for the Cross-Reference Label STVCAMP.
  7. From the Major LOV, select a major value.
  8. From the Admit Category LOV, select the value DFE.
  9. Enter the DfE course code in the Admit Curriculum field.
  10. Optional: Select the part of term.
  11. Optional: Ensure that the expiry date displayed on selecting the part of term is not past dated/expired. To select a future date, overwrite the selected date.
  12. Select a Source/Background Institution from the LOV.
    Institutions should configure the institution value in the SOACMAP page as a Banner value (SORXREF_BANNER_VALUE) for the associated provider or institution code in the SOAXREF page for the Cross-Reference Label STVSBGIC.
  13. Ensure to select the Active check box.
  14. Select a value (Full-Time/ Part-Time/ None) from the LOV that adheres to value sent from DfE for a course.
  15. Save the record.

Set up Banner Event Publisher

After you apply the Conditional Decision in Banner, the BEP event for decisions is triggered. The BEP event trigger is observed as a Change Notification in the Ethos Hub.

Configure the following BEP (Banner Event Publisher) event names for DfE-admission-decisions API:
  • EEDM.STU.DfeAdmissionDecisions.SARAPPD, where SARAPPD configuration is enabled by default for the decision pipeline to communicate the decision. If you disable the SARAPPD page configuration, the BEP event cannot publish the decisions.
  • EEDM.STU.DfeAdmissionDecisions.SARACMT, where SARACMT configuration is enabled by default for the decision pipeline to communicate the DfE notes. If you disable the SARACMT page configuration, the BEP event cannot publish the DfE notes.

Manage DfE Applications and Decisions

You can view and manage DfE applicants and applications in Banner.

Ellucian recommends that you must be cautious of the following while managing DfE applications for seamless processing.
  • If you reject or withdraw an offer, Banner cannot revert the application decision and status to an offer status. Banner considers the reject status (reject or withdraw offer decisions) as an end of state. However, we are working with DfE to understand and improve the status transitions.
  • With the current release install, the system can:
    • Update the withdraw decisions in Banner (applicants withdraw their applications), based on the Term Code crosswalk rules defined in the SOAXREF page for the STVTERM table.
    • The system verifies the term code mapped to an offer start date for applications. If the offer start date is NULL, the system verifies the term code mapped to the applied course start date.
  • For now, Banner does not support the DfE Notes and Interviews functionality. However, you can create notes and interviews for applications before applying a decision from the DfE interface. After you create an interview or notes to applications from DfE, you must download the updates to staging, run the SARSTML process.
  • You can defer applications provided the previous status of the applications in staging is pending_conditions or recruited. Else the defer functionality for Banner will not function as expected.
  • Before you download the confirm defer updates to staging (SAIEAST page), set up the user-defined STVAPST code to imply that the application is deferred or inactive in the SAAERUL page. The setup is for the DFEADMNAPSTCODE rule label in the DFEG rule group.
  • Before you download the DfE interview updates to staging (SAIEAST page), set up the user-defined comment types in STVCMTT page The setup is for the INTERVIEWDTCMNT, LOCATIONDTCMNT, and CANCELRSONCMNT rule labels in the DFEG rule group in SAAERUL page.
  • Before you download the DfE cancelled interview detail updates to staging (SAIEAST page), set up the user-defined Appointment Result Code in the STVRSLT page The setup is for the INTERVIEWCANCDE rule label in the DFEG rule group in SAAERUL page.
  • Before you download the DfE cancelled interview detail updates to staging (SAIEAST page), set up the user-defined Interviewer Code in the SPAIDEN page The setup is for the INTERVIEWERID rule label in the DFEG rule group in SAAERUL page.
  • To confirm defer offer on an application, ensure that the previous state for application in staging (SAIEAST page) is offer_deferred. You can confirm defer as conditions met or not met.
  • When your conditions are met for the confirm defer decision, status of the application at DfE is recruited. When your conditions are not met, the status of the application is pending_conditions. You can, then, bring the recruited or the pending_conditions status to staging.
  • When you run the DfEOutBound job, notes are sent to DfE. When you run the DfEInBound job, DfE creates the notes and are updated in the SAAADMS page.
  • While you create, update, and cancel the interviews from the Conditional Decisions window, ensure to note the following information.
    • Enter the decision as Interviewing, and provide the interview details in the INTERVIEW DETAILS section.
    • Run the DfEOutBound job to send the interview details to DfE.
    • Run the DfEInBound job to update the Interview ID from DfE in the SAADCRV page.
    • Provide the cancellation reason in Cancellation Reason field to cancel the Interviews from Banner.
    • You can view the scheduled interviews in DfE in the Interview Details section of the Conditional Decisions window.
    • You cannot create interviews that matches the date, time, and location and provider and additional details as per the application. At least any one of the information should differ.
    • You can update or cancel an interview only after the SAADCRV page displays the Interview ID.
  • Institutions can reject an application in the following ways:
    • When you select the decision as Reject, the Reject Reasons section is available in the Conditional Decisions window. You can enter the Reject Code and Reject Reason and save the record. Then, run the DfEOutBound job, to send the Reject decision is to DfE.
    • When you select the decision as Reject, and enter the rejection reason in the Reject/Withdraw Reason field of the Conditional Decisions section. Run the DfEOutBound job to send the Reject decision to DfE.
  • After downloading the confirm defer updates to staging, run the SARSTML process to create a new application.
  • The SARSTML process will not create the new application, when:
    • You do not create the term code mappings for the offer course start date in the SOAXREF page
    • Banner curricula mappings for term code does not exist in the SOACMAP page
  • The system does the following when:
    • The SARSTML process executes and creates a new application that is already in recruited or in pending conditions status in the EA tables
    • The electronic push process (SAAEAPS/SARETMT), executes and creates a new application in the SAAADMS page
  • For recruited applications, there are no further decisions that the system creates on the applications, apart from the withdraw status. If an applicant withdraws the application after the recruited status, the new application displays the updated withdrawn status.
  • However, for applications that are in the pending_conditions status after confirming deferral, as an additional step, you must apply the conditions met or not met decision from Banner or DfE. This step will update the status of the application to recruited at DfE. If an applicant withdraws the application after the pending_condition status, the new application displays the updated withdrawn status.

Execute the SARSTML process

After every data download to staging from DfE, institutions should run the SARSTML process to ensure that the data updates from DfE that are now existing in the staging table are loaded to the target tables. This ensures data integrity between DfE applications and records in Banner always.

Note: Institutions are expected to make decisions on applications only after creating admissions records. Hence, on running the SARSTML process after you create admissions records, the updated data from staging is loaded to the target baseline tables directly and not the Electronic Application (EA) tables.

If you do not create admission records, the SARSTML process continues to load or replace the applications data in the EA tables with the updated information from staging.

To load the demographic data such as ethnicity, disability and nationality codes to the GOAPSID page and the gender code to SPAIDEN page, institutions must execute the SARSTML process. Before you execute SARSTML, ensure that the pending_conditions or recruited status updates must be downloaded to Banner (right after applicant acceptance).

To create a new application in the EA tables after Confirmed Defer Offer decision, institutions must ensure to get the application status of pending_conditions or recruited, for confirmed applications downloaded to staging. With this, institutions can execute the SARSTML process for the applied recruitment cycle year (and not the current recruitment year) to create new applications in the EA tables for the latest term code. To create applications in the EA tables successfully, ensure that you map your applications offer course start date to term codes in the SOAXREF page.
