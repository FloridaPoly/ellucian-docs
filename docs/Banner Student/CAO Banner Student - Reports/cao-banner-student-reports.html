CAO Banner Student - Reports

Lists the processes and reports available in Banner CAO.

Net Acceptance File Import (SORNAIM) process

The SORNAIM process allows you to import the Net Acceptance files that the CAO sends. The file includes the Leaving Certificate Examination (LCE) points for each applicant for the student's specific courses. The information is available in .xlsx format.

Ellucian recommends that institutions to do the following before running the SORNAIM process.
  • Import the file into the job directory as a .xlsx extension file.
  • Ensure that applicant records are already available in the SZAIIOT page for respective programs.
To run the SORNAIM process, you must:
  • Import the Net Acceptance file to your job submission directory. Copy the file name and file path.
  • Enter the file path and file name and execute the SORNAIM process. You can run it either in the Update (U) or Audit (A) mode.
  • If you want to validate your records before inserting them, run the process in the Audit mode. You can see a snapshot of the process output, but will not insert the records to the LCE Points field for the SZAIIOT page.
  • The process loads the data into the LCE Points field for the SZAIIOT page, if you run the process in the Update mode, that matches the LCE Points to the ID, Program.
    Note: If the Program and ID in the Net Acceptance file does not match the data in the SZAIIOT page, the system will not import the LCE points and displays errors that is shown in the .log file.
  • You can view the LCE Points by each Program on the SZAIIOT page to verify the LCE Points for a particular applicant.
  • The .log file displays the successful records that the system creates.

CAO Interface: Join+Sort Files (SZPICAT) process

This process is used to join and sort the Identity (ID) and Application Selection (AS) files before running the SZPIIMG process. This process is seldom used because the SZPIIMG process merges and loads the ID and AS files in a single process.

The SZPIIMG process requires a single ID and single AS file. If there are multiple mini-ID files, they must be combined into a single ID file. If there are multiple AS files, they must be combined into a single AS file. Up to five individual AS files exist: Degree, Diploma/Cert, General Nursing, Psychiatric Nursing, and Mentally Handicapped Nursing.

It is important to note the following information about the SZPICAT process.
  • Use the GJAJFLU page to transfer ID, and AS files to the Jobsub server.
  • Files with extensions can only be transferred using the GJAJFLU page. For example: ID.txt, AS.txt.
  • While running the SZPICAT process, provide the Jobsub server path for 'Path Of ID or AS File1','Path Of ID or AS File2' and 'Path Of ID or AS File3' parameters. For example: /u02/banner.
  • While running the SZPICAT process, provide file names with extensions for 'Name Of ID or AS File1','Name Of ID or AS File2' and 'Name Of ID or AS File3' parameters. For example: ID.txt.

CAO Interface: Data Load (SZPIIFT) process

This process is used to load ID, AS, EF, MF, VA, and TX files into the system. The user selects the type of file to be loaded in the File Type process parameter.

It is important to note the following information about the SZPIIFT process.
  • Use the GJAJFLU page to transfer the file to the Jobsub server.
  • File with extension can only be transferred using the GJAJFLU page. For example: VA.txt.
  • While running the SZPIIFT process, provide the Jobsub server path for 'File Path' parameter. For example: /u02/banner.
  • While running the SZPIIFT process, provide file name with extension for 'File Name' parameter. For example: VA.txt.

AS files

Running the process with file type AS loads the Application Selection (AS) file. This process is seldom used because the SZPIIMG process merges and loads the ID and AS files in a single process.

EF files

Running the process with File Type EF loads the Exam (EF) file and populate the SORTEST table with the exam data.

The process can also be used to create an expected results record in the Person Comment page (SPACMNT) when loading an Exam file entry, for the current year, that does not contain any results.

Not all institutions will need to use this function, so the CAOLOADERTYP system variable is used to define the exam types for which the SZPIIFT process should create a record on the SPACMNT page when processing an exam file record with no results. (See Define the Load Expected Results Indicator)

The CAOEREXMYR system variable defines the current exam year for a specified exam type. When the SZPIIFT process loads an exam record that does not have any exam results, it will check the CAOEREXMYR system variable to see if the entry is for the current exam year. (see Define the Expected Results Year) If the exam type is also listed for the CAOLOADERTYP system variable, the process will generate a record in the SPACMNT page for the type defined by the CAOERCMTT system mapping (see Define the Comment Type Code.)

When the Exam file is eventually populated with the results, the SZPIIFT process will write the results to the SOATEST page as normal and will remove the comment from the SPACMNT page.

ID files

Running the process with file type ID loads an ID file into the system. This file type is seldom used because the SZPIIMG process merges and loads the ID and AS files in a single process.

MF files

Running the process with file type MF loads the merged ID and AS file into the system. These files were merged using the SZPICAT process.

This file type is seldom used because the SZPIIMG process merges and loads the ID and AS files in a single process.

VA files

Running the process with file type VA loads FETAC file and populates the vocational award data into the SORQQIA and SORQQIR tables.

TX files

Running the process with File Type TX loads the Text (TX) file. Details of the TX transaction loaded by this process are generally stored in the SPRCMNT table for the specified applicant.

However, TX transaction of type 66, which include the e-mail address and mobile phone number, are handled in a slightly different manner.

The load process reads the Code values on the GZVCAOI page for the CAOEMALCODE (e-mail) and CAOMOBLCODE (mobile phone) groups, and creates an appropriate record in the GOREMAL and SPRTELE tables, respectively. The e-mail value is located in position 12 to 61 and the mobile phone number is located in position 62 to 79. If the GZVCAOI CAOEMALCODE group is blank or not valid, an e-mail record will not be created. If the GZVCAOI CAOMOBLCODE group is blank or not valid, a mobile telephone record will not be created.

The processing of TX transactions of type 64 will generate an applicant's high school entry (SORHSCH) from the data contained in the transaction. Where more than one type 64 transaction is processed for the same applicant, the system will record the high school code associated with the earliest year that the student sat the Leaving Certificate exam.

Note: Ensure that only the latest file is used. Do not concatenate text files.

CAO Interface: Merge+Load File (SZPIIMG) process

This process is used to merge the ID and AS files into one file, and then load the file into the system.

This process also clears out and re-populates the Automatic Application Withdrawal Table (SZRWDAP) with all applications that were included in the ID/AS files (that is, applications to be excluded from automatic withdrawal processing).
Note: Institutions are expected to use the Merge + Load File Process (SZPIIMG) to load the ID and AS transactions, rather than run the appropriate processes for the separate ID and AS transactions. This is because the ID file does not contain any data that indicates the applicant has made a choice from your institution's courses.
It is important to note the following information about the SZPIIMG process.
  • Use the GJAJFLU page to transfer the ID and AS files to the Jobsub server.
  • Files with extensions can only be transferred using the GJAJFLU page. For example: ID.txt, AS.txt.
  • While running the SZPIIMG process, provide the Jobsub server path for 'Path Of ID File', 'Path Of AS File' and 'Path of master File' parameters. For example: /u02/banner.
  • While running the SZPIIMG process, provide file names with extensions for 'Name of ID File', 'Name of AS File' and 'Name of master File' parameters. For example: ID.txt.

CAO Interface: OF Data Load (SZPIIOF) process

The SZPIIOF process loads the Offer/Acceptance (OF) file. Only the latest file should be used, and do not concatenate text files.

The CAO processes applications and tries to match student preferences to available positions at the different institutions. Institutions are notified of offers and acceptances at each round by means of the Offer/Acceptance files.

If a new CAO application needs to be created as a result of loading an OF transaction, the residency code and cohort code will be populated with a value from existing CAO applications for the same term, or will default to a value of unknown. Offers and acceptances for the specific Year of Entry parameter are matched against application records having the same Year of Entry student attribute.

This process produces a report listing details of any superseding acceptance transactions that were loaded during processing. This occurs where a previous load has processed an applicant's acceptance for a course provided by the local institution, and the current load process identifies a later acceptance for a different course, regardless of whether the new acceptance is for another course provided internally (Local supersede) or for a course provided by another institution (Foreign supersede).

The report lists the original and new acceptance details along with any action that has been taken or is required on behalf of the user. The output of the report will be included in the .lis output file.

Note: Student records are created in Banner™ when offers and acceptances are received.
It is important to note the following information about the SZPIIOF process.
  • Use the GJAJFLU page to transfer the OF file to the Jobsub server.
  • Files with extensions can only be transferred using the GJAJFLU page. For example: OF.txt.
  • While running the SZPIIOF process, provide the Jobsub server path for 'File Path' parameter. For example: /u02/banner.
  • While running the SZPIIOF process, provide file name with extension for 'File Name' parameter. For example: OF.txt.

CAO Interface: RF Download (SZPIIRS) process

The SZPIIRS process writes flagged ratings and supplementary scores for applicants to their respective files, which are then sent to the CAO.

The CAO must be notified within the time allowed if an institution has created ratings or supplemental scores for an applicant. Only first year applicants scores are included in the file.

When the SZPIIRS process writes the last rating or score, the appropriate test scores are updated, so that the Released check box is selected and the release date is set to the current system date on the SZAIIOT page. This process formats the test score and rank values according to the maximum length specified in the Internal Code field on the GZVCAOI page for the CAOSCORELENGTH and CAORANKLENGTH groups, respectively.

It is important to note the following information about the SZPIIRS process.
  • Use the GJAJFLU page to transfer the file to the Jobsub server.
  • File with extension can only be transferred using the GJAJFLU page. For example: RS.txt.
  • While running the SZPIIRS process, provide the Jobsub server path for 'File Path' parameter. For example: /u02/banner.
  • While running the SZPIIRS process, provide file name with extension for 'File Name' parameter. For example: RS.txt.

CAO Interface: Load Schools (SZPIISF) process

The SZPIISF process loads the School (SF) file. The process compares each record in the CAO Schools File with the existing School records held in Banner in the STVSBGI and SOBSBGI tables, to identify new records that exist in the CAO Schools file but not in Banner.

The new records will be loaded into Banner, and the details will be written to the .lis file output.

The system can be configured to prevent automatic load of existing records with a matching School code when the School name or address or both in the CAO file are not identical to the name and address on the corresponding STVSBGI/SOBSBGI record. The details will be reported in the .lis file output to allow users to review the discrepancies, and manually apply any adjustments required to the records on Banner.

The CAOSFAUTOUPD system variable on the GZVCAOI page handles additional Schools file processing. This system variable indicates whether the CAO Interface: Load Schools Process (SZPIISF) should automatically update existing school entries with data from the schools file, or create a report that indicates that an entry exists but the schools file data is different.

Note: This process should only be run one time in a year.
It is important to note the following information about the SZPIISF process.
  • Use the GJAJFLU page to transfer the file to the Jobsub server.
  • File with extension can only be transferred using the GJAJFLU page. For example: SF.txt.
  • While running the SZPIISF process, provide the Jobsub server path for 'File Path' parameter. For example: /u02/banner.
  • While running the SZPIISF process, provide file name with extension for 'File Name' parameter. For example: SF.txt.

CAO Auto Withdrawal (SZPIIWA) process

The SZPIIWA process automatically sets the status to Withdrawn for CAO applications that are no longer included in files received from the CAO.

The SZPIIMG process must be run before running the SZPIIWA process to load the latest CAO files and identify active applications to be excluded from withdrawal processing.

When you enter the Year of Entry value and run the SZPIIWA process, the records are withdrawn only for the respective year of entry.

Note: The SZPIIWA process should only be run after loading the full CAO ID/AS files, and should not be run after loading the mini files.

Running the SZPIIMG process will clear out any existing data from the Automatic Application Withdrawal Table (SZRWDAP) and will re-populate it with excluded application entries.

The SZRWDAP process must first be run in Audit mode to produce a list of applications that will be included in the withdrawal processing. Finally, the process can be run in Processing mode to update the applications, setting the status to withdrawn.

Name Required? Description Values
Run Mode Yes Indicates in what mode to run the process. The process must be run in the A (Audit) mode before running in the P (Processing) mode.

Audit mode selects all of the CAO applications for the current CAO term that are not marked as excluded from withdrawal. The list of applications is saved to the SZRWDAP table with an action of I (Include in the withdrawal). A report of included applications is produced.

Processing mode creates a Withdrawn decision entry in the SARAPPD table, and sets the status to Withdrawn on all included applications. The report then lists details of included applications indicating whether withdrawal was completed successfully or an error was encountered.
