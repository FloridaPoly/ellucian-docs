HESA Common

The Banner Higher Education Statistics Agency (HESA) is a central body responsible for collecting and compiling statistical data on Higher Education establishments in the UK. The Banner HESA module is a reporting system that supports the collection of statistical data for transmission to HESA.

Banner HESA functional overview

The Banner® Higher Education Statistics Agency (HESA) is a central body responsible for collecting and compiling statistical data on Higher Education establishments in the UK. The Banner HESA module is a reporting system that supports the collection of statistical data for transmission to HESA.

Banner HESA supports the following HESA data collections:
  • Data Futures (DF)
  • Student Return
  • Initial Teacher Training (ITT) Return
  • Aggregate Offshore Return
  • Graduate Outcomes (GO)
  • Individualised Learner Record (ILR)
  • Destination of Leavers from Higher Education (DLHE)
  • Alternative Providers (AP) Student Return
Banner HESA does not support the following other collections:
  • Finance
  • Staff
  • Estates

HESA reporting requirements are complex and different institutions structure their data differently. The Banner HESA module therefore uses the Banner Mass Data Update Utility (MDUU) to provide maximum flexibility. A detailed set of MDUU rules are delivered for use with Banner HESA. You can use these as delivered or customise them to your institution's needs.

Banner HESA processing

This section provides an overview of the setting up and using Banner HESA.

With Banner HESA, you can do the following:
  • Define your HESA courses and modules
    Note: HESA courses are equivalent to Banner programs, and HESA modules are equivalent to Banner courses.
  • Collect HESA person, applicant, student, and graduate data
  • Process the HESA reports

When you first install Banner HESA, you must configure the system. Each year after that, as reporting requirements change, you must make changes to the configuration to ensure that your reports comply with the new requirements.

After you set up the module, your institution collects data from a variety of sources, including Banner, online enrolment, and HESA.

Your reports to HESA (other than DLHE) are generated using MDUU.

Details about the MDUU processes can be found in a spreadsheet, HESAnnnnnn_process.xls (where nnnnnn in the file name represents the release number), delivered with each Banner HESA release. The spreadsheet contains details about the following:
  • Delivered processes and activities
  • Source and target tables for each activity
  • Source definitions for each target column

The spreadsheet also includes SQL code that you can use to generate updated spreadsheets at any time to document the processes, source tables and column definitions used by the HESA processes. You can run the SQL as needed from any of your database instances to generate current information about delivered and local processes.

Submitting data

HESA data is submitted using the HESA Aardvark service. See the HESA website (http://www.hesa.ac.uk) or contact your HESA representative for more information.

Define HESA system parameters

A set of default system parameters and possible values are delivered with the system. You use these parameters and values to configure Banner HESA for your institution's needs.

Procedure

  1. Access the System Parameter Maintenance (GKAKSYS) page.
  2. Enter HESA in the System field, and then go to the next block.
  3. If necessary, perform a query to find the parameter you want to change.
  4. Define the parameter value.
  5. Save your changes.

Define HESA reporting periods

Using the HESA Term Code Dates (SKVHTRM) page, you can define your own HESA reporting periods with start and end dates that are different from a term defined in the Term Code Validation (STVTERM) page.

About this task

The SKVHTRM page is not currently used by delivered processing, but is provided in the HESA module to allow you to add data to the page and refer to it in locally customised rules.

Procedure

  1. Access the HESA Term Code Data (SKVHTRM) page.
  2. Enter the term code with which the reporting period is associated in the Term field.
  3. Enter the first date of the reporting period in the Start Date field.
  4. Enter the last date of the reporting period in the End Date field.
  5. Save your changes.
Define HESA cohorts

Define a HESA cohort, and associate information such as the type of the return and the Banner term code with the cohort.

Procedure

  1. Access the Cohort Code Validation (STVCHRT) page.
  2. Define a code for the cohort.
  3. Save your changes.
  4. Access the HESA Reporting Reference Data (SKAHRFD) page.
  5. Enter the cohort code in the Cohort field in the Key block, and then go to the next block.
  6. Define the cohort.
  7. Save your changes.

SORLCUR Trigger Processing

SORLCUR trigger processing creates and maintains the HESA instance records (SKBHINS, SKRHINS, and SKRHIHI tables) when an admissions decision creates the General Learner records.

The processing is controlled by the INSTANCE PROCESSING HESA system parameter, as follows:
  • If this is set to D, the default logic applies (a new combination of SORLCUR PIDM, admit term code, and priority are considered to be a new instance.

Seed rules for detecting previous instances

The seed rule sequences described in this section are delivered in GKRRSQL page.

The seed rule sequences include the following:
  • Process code: ESC_HSI
  • Rule code: ESC_HSI_SEED
The seed rules work both with and without study paths enabled. The first rule is used only if the learner curriculum row being inserted has study paths enabled (SORLCUR_KEY_SEQNO <> 99). It returns the sequence number of any previous row associated with the same PIDM and study path sequence number. If no row is found, a null value is returned.

The remaining rules fire only if the learner curriculum row being inserted is not study path-enabled (SORLCUR_KEY_SEQNO = 99). These rules detect a change in either priority or admit term code to signal that the new SORLCUR row should be considered a change to an instance rather than a new instance.

The rule returns one of the following.

  • Zero rows or a null value to indicate that the new SORLCUR Learner row represents a new instance. In this case a new SKBHINS / SKRHINS / SKRHIHI record will be created.
  • An existing SORLCUR_SEQNO. This is the 'old' curriculum record that is associated with an existing instance. This indicates that an instance already exists, and this existing instance will be updated so that it becomes associated with the new curriculum row.
    Warning: It is important to understand that, unless study-path is enabled, if two applications are accepted for the same person in the same term with the same curriculum priority, these seed rules consider the second application to be an update to the first. For example, if an applicant is admitted to a short course with curriculum priority 1 and then subsequently a HESA record is downloaded for the same term but a different program, a decision to admit this second application might not result in the creation of a second instance. Additional logic in the rules is needed to identify this, if necessary.

If your institution chooses to implement these rules or customised versions of them, you must test them to ensure that they meet your local processing requirements.

As with the original design of the HESA processing triggers, there will likely be some exceptional processing circumstances where the trigger logic does not correctly identify that a new SKBHINS is record is or is not needed. These exceptions must be handled by manual maintenance of the instance record.

Take note of the following.

  • The API used to evaluate these rules executes each active or date-effective rule in turn until it finds a rule that returns a row with a non-null value.
  • The result of the rule evaluation is the first column in the first such row.
  • The bind variables shown in the rules represent the value from the current row being inserted. The set of supported bind variables/parameters are shown in the Rule processing parameter and bind variable seed data section.
  • If you have study paths enabled, only rule 1 is effective, and the remaining rules are ignored. If you have study paths disabled, rule 1 is ignored and only rules 2 onwards are considered.
  • If you have study paths enabled, you must enable study paths for all programmes of study.
Rule 1: Existing Study Path

If a SORLCUR row associated with an instance is found for the same Study Path Sequence number, the new SORLCUR table row does not represent a new instance. Use the most recent of these records to update / insert the SKRHIHI table row.


SELECT   sorlcur_seqno
FROM sorlcur, skbhins, skrhihi
WHERE sorlcur_pidm = :pidm
AND sorlcur_lmod_code = 'LEARNER'
AND sorlcur_cact_code = 'ACTIVE'
AND sorlcur_seqno <> :seqno
AND (sorlcur_key_seqno = :key_seqno AND :key_seqno <> 99)
AND skrhihi_pidm = sorlcur_pidm
AND sorlcur_term_code = skrhihi_term_code
AND sorlcur_seqno = skrhihi_lcur_seqno
AND skbhins_pidm = sorlcur_pidm
AND skbhins_numhus = skrhihi_numhus
ORDER BY sorlcur_seqno DESC

AND skbhins_numhus = skrhihi_numhus
AND :KEY_SEQNO = 99
ORDER BY sorlcur_seqno DESC
Rule 4: Change of or correction to admit term

If a SORLCUR row associated with an instance is found for the same program and curriculum priority as the new SORLCUR row but with a different admit term code, the new SORLCUR row does not represent a new instance.

The seed data delivered as the following code sample uses the most recent of these records to update or insert the SKRHIHI row and to update the SKBHINS row.


SELECT   sorlcur_seqno
FROM sorlcur,skbhins,skrhihi
WHERE sorlcur_pidm = :pidm
AND sorlcur_lmod_code = 'LEARNER'
AND sorlcur_cact_code = 'ACTIVE'
AND sorlcur_seqno <> :seqno
AND (    sorlcur_program = :program
AND sorlcur_priority_no = :priority
AND sorlcur_term_code_admit <> :admit_term)
AND skrhihi_pidm = sorlcur_pidm
AND sorlcur_term_code = skrhihi_term_code
AND sorlcur_seqno = skrhihi_lcur_seqno
AND skbhins_pidm = sorlcur_pidm
AND skbhins_numhus = skrhihi_numhus
AND :KEY_SEQNO = 99
ORDER BY sorlcur_seqno DESC
Rule 5: Change of program

If a SORLCUR row associated with an instance is found for the same curriculum priority and term code as the new SORLCUR row but with a different program, the new SORLCUR row does not represent a new instance.

The seed data delivered as the following code sample uses the most recent of these records to update or insert the SKRHIHI row and to update the SKBHINS row.


SELECT   sorlcur_seqno
FROM sorlcur,skbhins,skrhihi
WHERE sorlcur_pidm = :pidm
AND sorlcur_lmod_code = 'LEARNER'
AND sorlcur_cact_code = 'ACTIVE'
AND sorlcur_seqno <> :seqno
AND (    sorlcur_program <> :program
AND sorlcur_priority_no = :priority
AND sorlcur_term_code_admit = :admit_term
)
AND skrhihi_pidm = sorlcur_pidm
AND sorlcur_term_code = skrhihi_term_code
AND sorlcur_seqno = skrhihi_lcur_seqno
AND skbhins_pidm = sorlcur_pidm
AND skbhins_numhus = skrhihi_numhus
AND :KEY_SEQNO = 99
ORDER BY sorlcur_seqno DESC

A feature of the delivered rules is that if a student is admitted into the same program twice with the same priority but in different terms, the rule above considers this a change of instance, not a new instance.

You might want to modify rule sequence 3 to assume that if the new row has an earlier admit term code than an existing row, then this is a correction to the admit term code. Otherwise (if new record has a later admit term code), this is a re-admission and a new instance is needed. In this case, the rule would be as follows.


SELECT   sorlcur_seqno
FROM sorlcur,skbhins,skrhihi
WHERE sorlcur_pidm = :pidm
AND sorlcur_lmod_code = 'LEARNER'
AND sorlcur_cact_code = 'ACTIVE'
AND sorlcur_seqno <> :seqno
AND (    sorlcur_program = :program
AND sorlcur_priority_no = :priority
AND sorlcur_term_code_admit > :admit_term)
AND skrhihi_pidm = sorlcur_pidm
AND sorlcur_term_code = skrhihi_term_code
AND sorlcur_seqno = skrhihi_lcur_seqno
AND skbhins_pidm = sorlcur_pidm
AND skbhins_numhus = skrhihi_numhus
AND :KEY_SEQNO = 99
ORDER BY sorlcur_seqno DESC

Known issue

Note: This issue affects only institutions that have not enabled study paths. The study path support delivered in Banner HESA 8.3 resolves this issue when study paths are enabled.

Institutions who make use of the logic to change the priority or admit term codes for records must be aware of a restriction that this introduces into Banner HESA Student-on-Module processing. The existing SKRHPOC table creates a relationship between Banner registration records (SFRSTCR) and curriculum data (SORLCUR). This is based on the assumption that both the priority and the admit term code for a HESA instance will not change. However the new rule-based logic for updating an instance breaks this assumption and will create 'orphan' rows in the SKRHPOC table.

This affects institutions that do the following:
  • Do not roll incomplete grades to academic history and therefore rely on module registrations to be snapshot and exported
  • Process curriculum and admit term changes after Student-on-Module processing has taken place
  • Rely on registration records and student on module processing for cohort building

The effect can be mitigated by refreshing the SKRHPOC table data periodically.

If you implement the rule-based logic to allow changes to be made to curriculum admit term and priority data, the following activities will not work as expected unless you refresh the SKRPHOC table data after any processing that would update SKBHINS_TERM_CODE or SKBHINS_PRIOIRTY columns:
  • ESC_HSRT_COHORT1
  • ESC_HSRT_SNA_NONMOD
  • ESC_HSRT_SNA_QUAL_AWARD
  • ESC_HSRT_SNA_STU_MOD
