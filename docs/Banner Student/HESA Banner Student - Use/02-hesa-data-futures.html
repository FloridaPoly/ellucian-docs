HESA Data Futures

The Data Futures functionality is built to support Banner HESA.

Note: This 9x version corresponds to the Banner HESA 8.23.1 release version.

The term 'course' is used to mean different things in Banner and in HESA. To distinguish terminology, in this use content, the term 'HESA course' refers to a 'Banner programme record. The term HESA module refers to a Banner course record.

The HESA Student record is a collection that begins from the year 1994/95. In the year 2022/23, the HESA student model significantly changed and is now known as HESA Data Futures. The data collected as part of the student record is used extensively by various stakeholders and is fundamental in the formulation of:
  • Funding
  • Publications (including UNISTATS)
  • League tables

The Data Futures programme brings the requirements of two existing data collections: student record and student alternative record (previously known as the Alternative provider student record) into a new student data collection specification. The new data specification has been a product of extensive work with Statutory Customers, HE Providers and sector bodies. The data specification needs to flex and adapt to the future requirements of a dynamic policy environment and therefore will require changes to be made. The collection specification of Data Futures has been structured in a way to ensure that these changes are not fundamental. An iterative schedule of releases will allow for modifications to be made, at regularly periods.

The Student record is collected in respect of all students registered at the reporting provider who follow courses that lead to the award of a qualification or provider credit. The emphasis of the coverage of the Student record is those who are (or were) actively following a course at some time during the applicable reference period.

To know about the physical data model, see the 56_Data_Model_f_22_6dfcdb3dc0.pdf file that is available as an attachment in the .zip compressed file.

Ellucian has converted the HESA DF model to provide a working student records system to enable the production of the new data model. This new functionality uses Data Connect to facilitate the extraction of data from tables to an XML format.

The following model for HESA data futures is available for institutions (downloaded 19th January 2023) This uses data connect and a suite of new data futures tables.

Configure and connect HESA Data Futures in Ethos Integration

Perform the setup that supports communication between Banner and Ethos Integration for the HESA Data Futures extraction.

HESA Data Futures Extraction process communicates with Banner through Ethos Integration. To support HESA Data Futures Extraction process, you need to connect Banner to Ethos Integration.

The Banner to Ethos Integration connect includes the following Banner API installation. The HESA Data Futures Extraction process requires Banner Ethos Student API 9.29, Banner Ethos Integration API 9.29 and Banner Business API Student HESA 9.3.29 releases.

For the procedures, see Connect Banner to Ethos Integration.

Create Banner application in Ethos Integration for HESA Data Futures

You must create Banner Student API, Banner Integration API, and Banner Business API application first, and then, a proxy setup for each API application.

For the procedures, see Set up Banner in Ethos Integration.

The Ethos application that you create for the Banner Student API, Banner Integration API, or Banner Business Process API must own the resources listed in this section. That will be the case if you create that Ethos application from the catalog, or use the Auto-Configure Resources feature in Ethos Integration to update the owned resources after installing the required Ethos API version, as described in the Update Banner's owned resources after an Ethos API upgrade.in the Ellucian Documentation site.

After you create the application and navigate to the Owned Resources window, you can see a list of all the application owned resources that are configured already.

However, for HESA Data Futures, as we need only specific list of APIs, use the DELETE ALL RESOURCES option to remove all the unrelated resources for Data Futures. To add only the API related resources, use the ADD RESOURCES option.

Note: Alternatively, you can also choose to retain the existing list of application owned resources that the system lists.

This section lists the API names that are available for each application. In the Owned Resources window, when you click ADD RESOURCES, the system allows you to either add the Ellucian Ethos resources or add a custom resource.

Note: If you do not see the API listed in the Ellucian Ethos Resource, you can add the API as a custom resource.

In the Owned Resources window, whenever there is an update to the list of APIs after an Ethos API upgrade, ensure that you delete all the existing resources and add the HESA Data Futures related API resources.

The hesa-df-extract-process is the Banner Student Ethos API that is used for Data Futures Extraction process

The following are the list of Banner Integration Ethos APIs used for Data Futures Extraction process:

  • hesa-courses
  • hesa-modules
  • hesa-sessionyears
  • hesa-qualifications
The following are the list of Banner Business APIs used for Data Futures Extraction process:
  • eu-hesa-venue-details
  • eu-system-parameter-maintenance

Create proxy application in Ethos Integration for HESA Data Futures

The application record contains basic information about HESA Data Futures Extraction process and how it interacts with Banner through Ethos Integration.

Before you begin

The Add Application wizard will prompt you for the user name and password for a user account that supports proxy API requests. Before running the wizard, create that user account using the procedure in Create Banner user for proxy API requests.

About this task

Note that multiple Ethos applications are needed to support HESA Data Futures Extraction process with Banner:
  • Ethos applications for the Banner Business API, Banner Student API, and Banner Integration API, which is part of setting up Banner in Ethos Integration.
  • An Ethos application for HESA Data Futures Extraction process, which you will create using the procedure mentioned in the following step-by-step procedure.

Procedure

  1. On the Ethos Integration header bar, click the gear button and select the Ethos environment where you want to perform this procedure.
  2. On the Ethos Integration header bar, click Applications.
  3. On the Applications page, click Add Application.
  4. In the Add Application dialog box, do the following:
    1. Select Manually.
    2. Select Configure REST API proxy.
    3. Click Continue.
  5. On the Application Details page of the wizard, enter the information described below and click Next.
    Field Entry
    Application name Enter a unique name for this application.

    Example name: HESA DF Business API proxy / HESA DF Integration API proxy/HESA DF Student API Proxy

    Ensure that the name uniquely identifies this application.

    When you need to select an application elsewhere in the Ethos Integration user interface, you will use the name to select the correct application.
    Description (Optional) Enter a description of this application.
  6. In the Add Source Applications page of the wizard, set up proxy API requests:
    1. Click Add Source Application to open the Add Source Application dialog box.
    2. In the Source Application field, select the Ethos application that you created for Banner.
      For Banner, you created three applications in Ethos Integration: one for the Banner Business API and one for the Banner Integration API, one for the Banner Student API and one for the Banner Integration API. Perform these steps twice, one time for each Banner application. You can enter the same credentials (for the same Banner user) in both cases.
    3. Enter the user name and password for the Banner user account that supports proxy API requests.
    4. In the Select a resource field, select any Ethos resource to which that user account has permissions in the ERP.
      You can select any resource for which you granted that user account permissions in the ERP. For example, persons. Ethos Integration uses that resource to validate the user credentials by confirming that the user account has access to at least one resource in the ERP. After the credentials are validated, the application will have access to all resources for which the user account has been granted permissions.
    5. Click Add.
    6. Click Next.
  7. Click View Application if you are ready to configure app-specific settings, or click Back to Applications if you want to just create the app now and configure settings later.

Create crosswalk to map Banner HESA Reference Period

The hesaReferencePeriod crosswalk maps the HESA Student Return Number and HESA Reference Period to student course session/session year start date and end date.

Procedure

  1. On the Ethos Integration header bar, click the gear button and select the Ethos environment where you want to perform this procedure.
  2. On the Ethos Integration header bar, click Packages.
  3. On the Packages page, click Crosswalks.
  4. Click Add to create a new crosswalk.
  5. In the Add new Crosswalk dialog box, enter hesaReferencePeriod and then click Create.
  6. Leave the Default Target Value field blank.
  7. Set up the offer mapping:
    Field Entry
    Mapping Name (Optional) Enter a descriptive name for this mapping.

    Example: HESA Reference Period
    Target Value Enter the start date and end date with comma concatenation. Example: 2021-10-02,2021-11-06
    Note: Ellucian recommends not to have a spaces between the dates as the empty space will generate an execution error when you run the process.
    Source Values Enter HESA Student Return Number concatenated with HESA Reference Period using the + sign. For example, C21056+01.
    Similarly, you can create multiple mappings for each HESA Student Return Number and HESA Reference Period concatenated with the + sign.
  8. Click Save.

Create crosswalk to map SLC installation

The slcInstalled crosswalk identifies whether the system has the Banner Student Loans Company (SLC) is installed in the system.

About this task

This mapping gets the Student Support Number(SSN) from the RKASSLC page. If the mapping value is Y, then system assumes that SLC is installed and fetches the SSN value from the RKASSLC page. If there is no mapping value available, the system, by default, fetches the SSN value from the GOAPSID page.

Even when it is Y, first checks the GOAPSID SSN value, if it is not null then the GOAPSID value is considered, if it is null then the RKASSLC value is considered. Also on entering Y, you should mention the SLC finaid year concatenated with comma ex: Y,2023. So that it fetches the SSN value from RKASSLC for that finaid year active record. Plus to provide an override in the GOAPSID if no SSN should be sent but one is valid in RKASSLC page if the client enters X in GOAPSID SSN (no tags) will be displayed in XML.

Procedure

  1. On the Ethos Integration header bar, click the gear button and select the Ethos environment where you want to perform this procedure.
  2. On the Ethos Integration header bar, click Packages.
  3. On the Packages page, click Crosswalks.
  4. Click Add to create a new crosswalk.
  5. In the Add new Crosswalk dialog box, enter slcInstalled and then click Create.
  6. Leave the Default Target Value field blank.

  7. Field Entry
    Mapping Name (Optional) Enter a descriptive name for this mapping.

    Example: slcInstalled
    Target Value Enter Y,SLCFinaidYear, (for example, Y, 2023), if SLC is installed. For any other value, the system considers that SLC is not available.

    If your SLCFinaidYear is blank in your system, there is no need to add a year. Enter Y. You can see that the system displays all the matching SSNs.
    Source Values Enter slcInstalled
  8. Click Save.
    If you do not enter Y, the SSN will be selected from the GOAPSID page for the HESA_COUNTRY report.

Create crosswalk for ofsRegister

The Module and the Module Instance entities are included in the Student record (056) HESA Data Futures Return, based on the ofsRegister value in Ethos Integration Crosswalk.

About this task

The Crosswalk is required for providers in England, and optional for others. If you do not create the crosswalk, the default value for ofsRegister is Not Approved.

Procedure

  1. On the Ethos Integration header bar, click the gear button and select the Ethos environment where you want to perform this procedure.
  2. On the Ethos Integration header bar, click Packages.
  3. On the Packages page, click Crosswalks.
  4. Click Add to create a new crosswalk.
  5. In the Add new Crosswalk dialog box, enter ofsRegister and then click Create.
  6. In Default Target Value and Target Value, enter the Registration Category value for the provider from the Office for Students (OfS) website.
    The mapping name is an optional entry.
    Valid Values Description
    Approved Providers in England that are registered with the Office for Students in the 'Approved' category are not required to return Module data but can do so optionally.
    Approved (fee cap) Providers in England that are registered with the Office for Students in the 'Approved (fee cap)' category must return Module data.
    Transition Year (fee cap) Provides in England that are registered with the Office for Students in the 'Transition Year (fee cap)' category must not return Module data and must return PARED and CARELEAVER data.
    Note: This value will be available after 31st of July, 2023.
    Not Approved Providers in England that are registered with the Office for Students in the 'Not Approved' category are not required to return Module data but can do so optionally.
    Approved No Module Even if the module instance and student module instance data are available, the system does not return tags for both module instance and student module instance in the XML.
  7. Click Save.

Set up the pipeline job to extract JSON data

Run HESADFExtraction job that downloads the raw student data futures data as a JSON file before coverage rules applied for the given job parameters.

About this task

You can set up the HESADFExtraction job to download new JSON file job to run on a schedule to periodically extract raw JSON file.
Note: For the procedures for managing pipeline jobs (such as running an existing job, modifying job parameters, and disabling/enabling a job), see Manage Ethos packages.

Procedure

  1. On the Ethos Integration header bar, click the gear button and select the Ethos environment where you want to perform this procedure.
  2. Perform the following steps to copy the API key for the Ethos application for HESA Data Futures Extraction process. You will paste that API key into the job settings later in this procedure. Copy one API key for Student API, and API key for Integration API and another one for the Banner Business API.
    1. On the Ethos Integration header bar, click Applications.
    2. On the Applications page, click the name of the Ethos application that you created for HESA Data Futures Extraction process.
    3. On the Application Overview page, click the API Keys tab.
    4. On the API Keys page, click Copy to copy the API key.
  3. On the Ethos Integration header bar, click Packages.
  4. On the Packages page, under Integration Packages, click HESA Data Futures Student.
  5. In the Pipelines section of the page, click HESADFExtraction.
  6. Click + New Job.
  7. On the New Job page, enter settings for the following job:
    Field Entry
    Job name Enter a descriptive name for this job. If you create multiple jobs for this pipeline, you can use this name to find this job on the Pipelines page.

    Example: Extract HESA Data Futures JSON data
    Ethos Business API Paste the API key that you copied earlier in this procedure for Banner Business API.
    Ethos Integration API Paste the API key that you copied earlier in this procedure for Integration API.
    Ethos Student API Paste the API key that you copied earlier in this procedure for Student API.
    HESA Student Return Number Enter the HESA Student Return Number. Example: C19052
    HESA Reference Period Enter the HESA Reference Period. Example: 01
    Cohort Codes Enter the cohort code(s).
    Term Codes Enter the term code(s).
  8. In the Job Run Details section of the page, specify when you want the job to run. See the following examples.
    You can run the job one time or set up a recurring schedule. For example, during testing you might choose to run a job one time. For ongoing processing of applications, you would likely set up a schedule.
    Example Job Schedule Steps
    Run the job immediately Click Run now.

    You can also run this job later from the Job Runs page for the job.
    Run the job daily at noon
    1. Click Schedule job.
    2. In the Repeats field, select Daily.
    3. In the Hours field, enter 12.
    4. In the Minutes field, enter 0.
    Run the job every 6 hours
    1. Click Schedule job.
    2. In the Repeats field, select Daily.
    3. In the Hours field, enter 6 and select Use as Interval.
    4. In the Minutes field, enter 0.
  9. If you set up a schedule for the job, and you want the schedule to end at a certain date and time, do the following:
    1. Enable the Setup Job Stop Date/Time? toggle switch.
    2. Select the desired stop date.
    3. Enter the desired stop time as HH:MM AM/PM. If you leave this field blank, the stop time defaults to 11:59 PM.
  10. In the Advanced Options section of the page, in the Maximum Concurrency setting, specify the number of concurrent threads for this job.
    Some pipeline jobs use multiple concurrent threads for processing. Increasing the number of concurrent threads can improve processing time, but too many simultaneous threads might overwhelm the target system for the job.
    You can accept the default of 10 threads unless you are seeing performance issues. If the pipeline job is taking a long time to run, try increasing the number of threads. If you are seeing performance issues in the target system, try decreasing the number of threads.
  11. Click Save.
    The Job Runs page for this job appears. You can view the status in the Status column. A status of Succeeded indicates that the job is finished. Click Refresh Content to update the status.

Populate Student Identifier (SOPHUDF) process

The SOPHUDF process (HESA Data Futures SIDs) allow institutions to populate the new HESA Data Futures student identifier (SID) details into the GORPSID table.

Note: Ellucian highly recommends that you copy any HUSIDs that you want to maintain in the GOAPSID page, before running the SOPHUDF process. Also, HESA Data Futures requires the SOBENGA Start Date to be present to ascertain the entry year.
The SOPHUDF process accepts the cohort code and term code as input parameters and fetches all the active Student IDs from the SGACHRT page for the cohort and term code. The process also updates the HUSID value in the GORPSID table for the active students only if the value does not exist already. The label on the table displays as HUSID, but the displayed HUSID contains your copied HUSIDs, in addition to the newly generated SIDs.
The structure of the SID is as follows:
  • First 2 digits: Year of entry into provider (last 2 digits of year)
  • Next 8 digits: Provider's UKPRN
  • Next 6 digits: Internal 6 digits is fetched from SPRIDEN_ID
  • Last digit: Check digit

Populate Engagement Details (SOPSPDF) process

The SOPSPDF process allows institutions to populate the engagement details (Student ID and Study Path) that is available in the SGACHRT page into the SOBENGA table. This process links data connect, crosswalks, cohorts and the HESA Data Futures tables.

When you create a new study path, the SOKDTFU trigger populates the Engagement number (NUMHUS) in the SOBENGA table for all HESA institutions. Ensure that you run the script into the GURLCIN table to indicate the HESA institution. Only after the generation of NUMHUS, you can access the SOAENRE page from the Key block.

For existing students:

When the student gets a new study path, the institution creates the HESA engagement record for the students to maintain the engagement details of students. The SOPSPDF process fetches all the existing Student IDs and the associated Study Path numbers that the SGACHRT page maintains and creates the engagement record if it doesn't exist.

The SOPSPDF accepts Cohort Code and Term Code as input parameters, and fetches all the Student IDs and the associated Study Path numbers that the SGACHRT page maintains. Institutions should populate the Study path details in the SGACHRT page before running the SOPSPDF process.

The process then validates the information by checking if the Study Path number is present in the SGRSTSP table for the student. If available, the process inserts the Student ID and Study Path number to the SOBENGA table.

The .log and .lis files provide the summary of the successfully processed records. The files also include any errors during the process generation.

Parameter Name Required? Description Values
Cohort Code Yes Enter the cohort code to fetch the selected population Cohort Code Validation (STVCHRT) page
Term Code Yes Enter the term code of the Cohort Term Code Validation (STVTERM) page
Note: Ethos HESA Data Futures processing checks the Cohort Active Indicator in the SGRCHRT table while selecting the records to include from the cohort table. However, in the SGACHRT page, the column name displays as Inactive check box, while the database field name is SGRCHRT_ACTIVE_IND (which represents as Active indicator). Be informed that when you select the Inactive indicator in the SGACHRT page, the system will not fetch the inactive records. The system considers the records with SGRCHRT_ACTIVE_IND as NULL as active records and includes the cohort record for processing.

Update Return to Regulator (SOURRDF) process

The SOURRDF process allow institutions to populate the Return to Regulator indicator in various HESA pages. The indicator controls the data that the system reports through HESA Data Futures.

Note: : Ellucian recommends to run this process before the HESA Data Future return. You can clear the Return to Regulator check box if you do not want the data to be reported.

The SOURRDF process accepts the multiple cohort code, multiple term code, Reference Start Date, and Reference End Date as input parameters and fetches all the active Student IDs from the SGACHRT page for the cohort and term code combination.

The system updates the Module, Course, Session, Venue, and Qualification Return to Regulator values based on the Course Session details that comes from the SOASTCS page. The SOASTCS page fetches data for a given student and engagement number where the Course ID is present and the data is within the reference period range.

Remove Duplicate SID From XML (SOPMSDF) process

The SOPMSDF process allows you to remove the duplicate SIDs and merges the OWNSTUs from given input. XML file for all records having duplicate SIDs. You can also sort the XML file as per the SID values.

This results in a single entry for that SID with multiple engagements in an output .XML file. To run this process, ensure that you import the input seed data file in .XML first to the input file path directory.

The process parameters are:

Parameter Name Required? Description Values
Path of the file Yes Enter the Oracle directory name that contains the file N/A
Input file name Yes Name of the .XML file N/A
Output file name Yes File which stores the output at the given Input file path. N/A
SID sorting (Y/N) No To store the Y or N values Y: Sort the XML as per the SID value

N: Do not sort the XML as per the SID value
Ellucian recommends you ensure the following as prerequisites.
  • Import the seed data file to the input file path directory and copy the input file name and file path.
  • Create the seed data in the .XML format only.
For the process to run, ensure the following.
  • Enter the Oracle directory name, input file name and output file name attribute. The process parses the data from the .XML file and after performing logic operations the output file will be generated which can be downloaded from the given input file path directory.
  • The system generates messages in the .LOG file for you to view.
  • Input file and output file should be .XML file type only.
  • Input file path directory should have write permissions to generate output file.

Record HESA course qualification details

Use the following step-by-step procedure to enter and record the information about a formally recognized academic award, such as a degree, diploma, or a certificate.

About this task

For every Qualification ID entered, you must add at least one qualification subject in this page. You can have zero or more entries in the AWARDING BODY ROLE block. Qualification IDs created in this page will be used in the Course Delivery block of the Course Delivery Details (SOAPCDE) page.

Procedure

  1. Access the Qualification Details (SOAQUAL) page.
