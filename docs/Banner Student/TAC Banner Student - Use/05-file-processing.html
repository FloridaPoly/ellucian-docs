SATAC file import definitions

This table provides details on the correct values to enter in the Import section of the Execution Tree Set-up (GKAPEXS) page for each SATAC file.

The file length described in the Fields field is one character longer than the length of the file received from SATAC. This is to accommodate carriage-return characters used in some text editors. If the text editor does not have additional carriage-return characters, the load will still work if you use the field values for each field.

Loading data to Electronic Admissions

For SATAC file processing, all of the Electronic Admissions activities are performed by a single activity, and the load to Electronic Admissions task can now be run in Audit mode.

Detailed messages are written to the Process Log (GKRRLOG) table and can be viewed in the Process Log (GKARLOG) page.

The following table describes the activity for loading files to Electronic Admissions.

Note: The target tables are the Banner Mass Data Update Utility (MDUU) tables and the activity uses the SKKSTAC function that has routines to appropriately populate the Electronic Admissions tables. The function also writes detailed processing messages to the GKRRLOG table.
Activity Type Activity Name Description
Load SATAC data to Electronic Admissions tables ASC_SATAC_EALOAD This activity uses the SKKSTAC function to retrieve data from the SATAC import tables, such as SKRSAPP and SKRSOFR and processes the data correctly into the appropriate baseline EA tables such as SABNSTU, SARHEAD, SARPERS, and SARETRY.

The activity uses the SATAC ID and admit term as populate keys, and also allows multiple preferences to be processed for each applicant.

The SKKSTAC package contains functions to correctly insert records into specific electronic admissions tables. The following table list the tables are used by SKKSTAC and what data is inserted into each table.

Table Action
SABNSTU If the applicant ID (SATAC ID) does not already exist, an AIDM is generated and linked to the applicant ID on SABNSTU. If the applicant ID matches an existing ID on SABNSTU, the system cannot generate a new AIDM so the existing linked AIDM is used and no updates are made to SABNSTU for that applicant.
SARHEAD A row is inserted into SARHEAD for each applicant preference for the applicant. This means that for each row the applicant has in SKRSOFR, if the course code has been matched to a Banner curriculum, there will be a row in SARHEAD. The SKRSOFR_ADMIT_TERM value is used to populate the SARHEAD_TERM_CODE_ENTRY column. Mapping rules exist on SKARMAP to map the SATAC applicant type to a valid web applicant (WAPP) code. These WAPP code is then used to populate the SARHEAD_WAPP_CODE value. The SATAC course code is populated into the SARHEAD_WEB_CASHIER_USER field to facilitate processing of multiple application preferences.
SARPERS A row is inserted into SARPERS for the applicant and for each person who has been related to the applicant in the SATAC APPL file and loaded to SKRSAPP. If the applicant has a next-of-kin person, an emergency contact person, or an employer contact, these are loaded into SARPERS with the specific relation SARPERS_RLTN_CDEcode. These SARPERS rows are repeated for each of the applicant's course preferences.
SARADDR A row is inserted into SARADDR for each of the applicant's addresses. These SARADDR rows are repeated for each of the applicant's course preferences.
SARPHON A row is inserted into SARPHON for each of the applicant's phone numbers and their respective e-mail address. These SARPHON rows are repeated for each of the applicant's course preferences.
SARHLTH A row is inserted into SARHLTH for the applicant's disability information. If the applicant indicates no disability, a row is inserted for no disability to facilitate later statutory reporting.

If an applicant has indicated one or more disabilities, a row is inserted into SARHLTH for each disability. These SARHLTH rows are repeated for each of the applicant's course preferences.
SAREMPL A row is inserted into SAREMPL for each record in the applicant's SATAC EMPL file (SKRSEMP table). These SAREMPL rows are repeated for each of the applicant's course preferences.
SARHSCH A row is inserted into SARHSCH for each high school record in the applicant's SATAC ACAD file (SKRSACA table). These SARHSCH rows are repeated for each of the applicant's course preferences.
SARHSUM Rows are inserted into SARHSUM for each high school record that was inserted into SARHSCH. These SARHSUM rows are repeated for each of the applicant's course preferences.
SARHSES Rows are inserted into SARHSES for each South Australian high school subject record in the applicant's SATAC SUBJ file (SKRSSUB table). These SARHSES rows are repeated for each of the applicant's course preferences.
SARHCRS Rows are inserted into SARHCRS for each South Australian high school subject record in the applicant's SATAC SUBJ file (SKRSSUB table). These SARHCRS rows are repeated for each of the applicant's course preferences.
SARPCOL A row is inserted into SARPCOL for each non-high school record in the applicant's SATAC ACAD file or SATAC OTHR file (SKRSACA table). The rows record the institution or location for each record. These SARPCOL rows are repeated for each of the applicant's course preferences.
SARPSES Rows are inserted into SARPSES for each record that was inserted into SARPCOL. These SARPSES rows are repeated for each of the applicant's course preferences.
SARPDEG Rows are inserted into SARPDEG for each record that was inserted into SARPCOL. The rows record the degree or award for each record. These SARPDEG rows are repeated for each of the applicant's course preferences.
SARDFOS Rows are inserted into SARDFOS for each record that was inserted into SARPDEG. The rows record the major, field of study, or field of education for each record. These SARDFOS rows are repeated for each of the applicant's course preferences.
SARETRY A row is inserted into SARETRY for each applicant preference for the applicant. This means that for each row the applicant has in SKRSOFR, if the course code has been matched to a Banner curriculum, there will be a row in SARETRY. The matched base curriculum rule number is populated in SARETRY.
SAREFOS A row is inserted into SAREFOS for each applicant preference for the applicant. This means that for each row the applicant has in SKRSOFR, if the course code has been matched to a Banner curriculum, there will be a row in SAREFOS. The matched major curriculum rule number is populated in SAREFOS.
SARPRFN Rows are inserted into SARPRFN for each applicant using data from various files. For example, any records in the SKRSFCT file will be inserted to SARPRFN, along with specific references from other files, such as basis of admission, course stream, allocatability status, and file ID. Where a reference record is not tied directly to a single preference, the SARPRFN rows are repeated for each of the applicant's course preferences.
SARRLST Rows are inserted into SARRLST for each applicant based on the applicant's SARHEAD_WAPP_CODE value. Processing rules exist in baseline for each WAPP code. These rules are built on the baseline Electronic Admissions Procedure/Routine Control Page (SAAECRL). The rows inserted into SARRLST are the correct procedures for the applicant's WAPP code. These SARRLST rows are repeated for each of the applicant's course preferences.
SARPERR Rows are inserted into SARPERR for each applicant based on the applicant's SARHEAD_WAPP_CODE value. Processing rules exist in baseline for each WAPP code. These rules are built on SAAECRL. The rows inserted into SARPERR are the correct routines for the applicant's WAPP code. These SARPERR rows are repeated for each of the applicant's course preferences.

For UAC file processing, all of the Electronic Admissions activities are performed by a single activity (ASC_UAC_EALOAD), and the load to Electronic Admissions task can be run in Audit mode.

Detailed messages are written to the Process Log (GKRRLOG) table and can be viewed in the Process Log (GKARLOG) page.

The following table describes the activity for loading files to Electronic Admissions.

Activity Type Activity Name Description
Load UAC data to Electronic Admissions tables ASC_UAC_EALOAD This activity uses several functions within the SKKUTAC package to load data to baseline Electronic Admissions tables. You can run this activity in audit mode which will not update the tables but will produce a detailed log about what can be loaded and what cannot be loaded and why it cannot be loaded. This log can be viewed on the MDUU page GKARLOG.

When the activity is run in update mode, the activity log is produced and the electronic admissions tables are updated where possible.

The activity uses the UAC ID and admit term as populate keys, and also allows multiple preferences to be processed for each applicant.

VTAC Data file

This topic describes the VTAC Data File details for loading the VTAC Offer (D1) file.

The D1 Offer and Master file from VTAC is a fixed length flat file that is now 5019 characters in length, before any line feed characters are taken into consideration.

This means that when the file is registered for the external table VTAC, each row is 5020 characters in length. This also means that the file is now too big to be handled by the GKAPEXS page and is too big for the external table VTAC to only have one column.

The table VTAC now has three columns, such as, VTAC_DATA (CHAR 2000), VTAC_DATA1 (CHAR 2000) and VTAC_DATA2 (CHAR 1020).

After the VTAC D1 file has been loaded to a directory that MDUU can access, users need to run the ASC_VTAC_REG_EXT_TABLE activity to register the file as an external table.

Users need to provide the filename, including the file extension, when they run the activity.

If the file extension, (for example,.txt) is not provided, then the external table will not be registered and an error message will be written to the TAC External Table Log (SKRTLOG) table.

Users can view records on SKRTLOG using the Universal Viewer (GKAPUNV) page.

The data in the external table is only temporary and will be purged when the user loads and registers a VTAC file for the next round. This means that a VTAC file for one round needs to be processed at least as far as VTAC staging tables before a VTAC file for the next round is registered.

Record Count Enrolments ASC_VTAC_RECON_COUNT This VTAC Enrolment Count by Course activity records the count of enrolments by course code. The count of enrolments of VTAC applicants by course code is calculated using the data that resides in the TAC Reconciliation Extract Table (SKRTACR).

The count of enrolments of direct applicants into VTAC courses by course code will be reported. The count of enrolment records will not be available in the SKRTACR table, so the activity uses learner program, major, and curriculum rule data in the Curriculum Table (SORLCUR) and Field of Study Table (SORLFOS) to link back to VTAC course codes in the SKRPOFR table.

For the count of direct applicant enrolments into VTAC courses, the correct VTAC course is determined by matching the base curriculum rule for the student on SORLCUR and the major field of study curriculum rule for the student and curriculum on SORLFOS with the base curriculum and major curriculum rule numbers on SKAPOFR where the academic year of the record on SKAPOFR is the current year. Then the programming logic identifies the SKAPOFR record where the Admissions Category is 'VTAC' and the term code of the SKAPOFR record matches the admit term code of the student's SORLCUR record.

If there is more than one VTAC course record on SKAPOFR for the matching term, base curriculum rule and major curriculum rule then the programming logic can only select a single record by matching the rate code for the student on SORLCUR with the rate code of the course record on SKAPOFR. Populating the rate code field on SKAPOFR has no impact on processing VTAC files but will allow you to match direct applicants to VTAC course codes more precisely.

If there is more than one VTAC course record on SKAPOFR for the matching term, base curriculum rule and major curriculum rule and the rate code is not populated on SKAPOFR, or if a direct applicant does not have a rate code on SORLCUR, then this person will be counted for each VTAC course record on SKAPOFR for the matching term, base curriculum rule and major curriculum rule, because there would be no way for the logic to match precisely to a single record.

The total count of enrolments by course code is pulled into a CLOB field, along with the course code so that this data can be used in the VTAC Enrolment return courses count file (D4.2).
