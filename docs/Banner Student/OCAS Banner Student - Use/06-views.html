Views

This section describes the OCAS views.

OCAS Applicant Alerts per Administrator (SVVOAAA) view

This view displays the fields that handle alerts of applicants attached to an administrator.

OCAS Applicant Academic Standing Status (SVVOAST) view

This view displays the applicant’s academic standing status.

OCAS Alternate Program Rules (SVVOALP) view

This view displays the relationships between the combination of OCAS programs, term, and campus, and the combination of the associated alternate programs, term, and campus.

This way, an applicant who does not match the requirements for a particular original program can be offered an alternate program. This view indicates whether each original program combination and alternate program combination is valid or not valid and whether it is active or not active in SVROPRC. In addition, this view displays the priority that specifies to the system which alternate program is offered first or after.

OCAS Banner Data (SVVOBID) view

This view is used to view the OCAS application number and its associated Banner ID (PIDM) plus other fields such as name, OCAS year, birth date, duplicate indicator and SIN. The base tables to build this view are SVRORAC, SVROCAC, SVROWAD, SVROBID, SPRIDEN, and SPBPERS.

OCAS Applicant Data (SVVOCAC) view

This view displays the fields used when defining OCAS Boolean variables. The table contains fields that belong to different tables making it easier to view the data.

OCAS Course Data (SVVOECD) view

This view displays the fields that handle extra course data.

OCAS Program Eligibility General Requirement Output (SVVOEGO) view

This view displays the fields that handle general requirements.

OCAS Program Eligibility Output Summary (SVVOELI) view

This view displays the fields for eligibility output.

OCAS Eligibility/Scoring Output Summary (SVVOESM) view

This view displays fields from the eligibility and scoring output at the summary level.

OCAS Eligibility/Scoring Output Detail (SVVOESO) view

This view displays the fields from the eligibility and scoring output at the detail level.

OCAS Eligibility/Scoring Rules Detailed Summary (SVVOESQ) view

This view displays the fields for eligibility/scoring rules.

OCAS Eligibility/Scoring Rules Summary (SVVOESR) view

This view displays information regarding the existing rules for eligibility and scoring per program, year, category, term and semester.

OCAS Test Data (SVVOETD) view

This view displays the fields that handle extra testing data.

Web Final Applicant Response User Definable Questions (SVVOFDQ) view

This view displays the final answers to user-definable questions that were originated in a web application.

SVVOFDQ also displays the application number and its associated Banner ID (if any) plus other fields such as applicant name, application form, year and other attributes that come from Web Final Applicant Response User Definable Questions (SVROFDQ) table and Web User Definable Question Maintenance (SVROQUE) table.

OCAS Letter Data (SVVOLTR) view

The SVVOLTR view contains data that can be posted in a letter or used to generate a report. If a valid applicant has no address or telephone number, a record is still generated in the letter view leaving those fields blank.

Records in the letter view only exist if the applicant exists as a valid applicant (that is, has a record in the SVROCAC table).

Personal Data

The following section contains the personal data of the applicant.

The view should retrieve only one record per OCAS application number per OCAS year. Only active applicants (SVROCAC_STATUS = A) with active programs (SVROCCC_STATUS = A) are returned.

Note: For cases when an offer letter must be sent, the term to use in GURMAIL will be the minimum term when offers were generated for the applicant’s different programs.

Address Data

The following section contains the address data of the applicant.

The applicant address that is retrieved is the one with the maximum sequence number for the OCAS address type (SVROCTL_OCAS_ADDR_ATYP_CODE) as long as the address is active (SPRADDR_STATUS_IND is null).

The applicant telephone number that is retrieved is the one with the maximum sequence number for the OCAS telephone code (SVROCTL_OCAS_TELE_CODE) as the telephone number is active (SPRTELE_STATUS_IND is null).

Missing Documentation

The following section contains the data related to the documentation that an applicant is missing.

For every document (hard copy) that OCAS indicated the applicant has missed, there will be a field in the SVVOLTR view that will indicate the document code and description.

These documents are from the SVROAAL table where the alert group was MDOC (missing document). These alerts can be viewed from the SVAOAAL page.

These missing documents can be part of a letter used to inform applicants that they are missing information. The description field should be included in the letter because the code may not be descriptive.

Program Information

The following section contains the data related to every applicant's program.

The view displays program information for three different regular choices. The program code, description, start date and semester are the values sent by OCAS (not Banner values). This avoids confusing the applicant, who applied using OCAS codes, not the Banner codes.

Example - SVVOLTR Program Information

Assume that an applicant must receive a letter stating that they has received an offer for program 2, is waitlisted for program 1, and is refused for program 3. The logic for calculating this would be as follows.

  • The applicant will have P1_QUEUE = W and will informed that the waitlist position for the program (P1_DESC) is the value for P1_WL_NUM.
  • The applicant will have P2_QUEUE = O, and will be informed that has been received as an offer for the program (P2_DESC) and must confirm acceptance or refusal by the due date (P2_DUE_DATE). If P2_CONDITIONAL_IND is Y, then the letter should mention that the offer is conditional.
  • The applicant will have P3_QUEUE = R, and will be informed that has been refused for the program (P3_DESC).

Therefore, the variables in the letter must look at the not null values in the P#_QUEUE field. The variables must check for every case of O/W/R to build a paragraph in the letter for each program with an offer, waitlist or refusal.

General Requirements Not Met

The following section contains the code and description of every general requirement that was not met for the applicant.

These general requirements are the ones that were entered as part of the rules in the SVAOESR form in the Eligibility General Requirements section.

Up to ten not met general requirements are listed in the view. However, the requirements where the Letter check box is checked on SVAOESR are the requirements that must be included in the letter that informs applicants that not all requirements have been met.

The description field should be included in the letter because the code may not be descriptive.

Example - SVVOLTR General Requirements Not Met

The logic is to check if P#_NOMET_OGRE_CODE_# is not null and P#_NOMET_OGRE_LTR_# is Y.

This means checking if there is a not met general requirement that must be part of a letter. If those conditions exist, then the code description (P#_NOMET_OGRE_DESC_#) can be included in the letter for every missing general requirement that needs be printed.

Institutional Testing Requirements Not Met

The following section contains the code and description of the test and sub-test for every institutional testing requirement that was not met for the applicant.

These institutional testing requirements are the ones that were entered as part of the rules in the SVAOESR page in the Institutional Testing Requirements section.

Up to ten not met institutional testing requirements are listed in the view. However, the requirements where the Letter check box is checked on SVAOESR are the requirements that must be included in the letter that informs applicants that not all requirements have been met.

The description field should be included in the letter because the code may not be descriptive.

Example - SVVOLTR Institutional Testing Requirements Not Met

The logic is to check if P#_NOMET_TEST_CODE_# is not null and P#_NOMET_TEST_LTR_# is Y, which means checking if there is a not met institutional testing requirement that must be part of a letter.

If those conditions exist, then the code description (P#_NOMET_TEST_DESC_#) can be included in the letter for every missing institutional testing requirement that needs be printed.

Eligibility Area (Formula) Not Met

The following section contains the code and description of every eligibility area that was not met for the applicant.

These eligibility areas are the ones that were entered as part of the rules in the SVAOESR page in the Eligibility Formula Definition section.

Up to ten not met eligibility areas are listed in the view. Any listed area means that the applicant did not meet the formula criteria to be considered for an offer,

The description field should be included in the letter because the code may not be descriptive.

Example - SVVOLTR Eligibility Area (Formula) Not Met

The logic is to check if P#_NOMET_OEAR_CODE_# is not null and P#_NOMET_OEAR_LTR_# is Y, which means checking if there is a not met eligibility area. If those conditions exist, then the code description (P#_NOMET_OEAR_DESC_#) can be included in the letter for every missing eligibility area that needs be printed.

Alternate Programs

The following section contains the three possible alternate programs.

When the alternate programs are only generated for programs where eligibility was met, then the view does not include any information about missing requirements because all of requirements will have been met.

Requirements Not Met for the Alternate Program

The following section contains the code and description of every requirement that was not met for the applicant’s alternate program.

Institution Data

The following section contains the data of the institution to which the applicant applied.
