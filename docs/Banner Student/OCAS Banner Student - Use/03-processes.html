Processes

This chapter describes the following processes.

OCAS Applicant Category Calculation (SVPOACC) process

This process is used to calculate the applicant category.

This process will not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) will still be processed.

The category is assigned to the applicant by CC record, which means by program and related parameters. The reason for this is that the category rules are defined by OCAS year and term, and the program is the one that has a term attached. So an applicant could fall in different categories depending on the category rules for the term where the programs start.

This process can be run from SVAOCAS (Calculate Category option) or GJAPCTL.

OCAS Admissions Acceptance (SVPOADM) process

This procedure inserts applicants into the Banner admissions tables (SARADAP, SARAPPD and SARAATT) and the General Student tables (SGBSTDN and SGRSATT) when the applicant has accepted the offer. An applicant is not processed in Banner Admissions if it is accepted after the OCAS soft/due date.

This process does not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) is still processed.

This process inserts or updates records in the Banner 7.0 baseline tables that handle concurrent curricula data. When data has been inserted and updated in the Banner Admissions (SARADAP/SARAPPD) tables or the Banner Student (SGBSTDN) table, the records are also inserted or updated in the SORLCUR and SORLFOS tables.

Same Term Offers

This process accepts a second CC-Y record for a different program in the same term for an applicant if the Same Term Offers check box was checked on the SVAOCTL page.

When a second CC-Y record arrives, the value in the Offer Accepted field for the offer that is associated with the incoming CC-Y is changed to Y (Yes) in the OCAS Offer (SVROOFR) table. When a CC-N for the original offer arrives along with the second CC-Y record, the value in the Offer Accepted field for the original offer is changed to N (No) in the SVROOFR table. If two active CC-Y records are accepted in the same term, then an error is generated.

By the end of processing all of an applicant’s transactions, if more than one active offer was accepted within a term in the SVROOFR table, then all of the transactions are rolled back for the applicant, and an error message is posted to the .log file.

Note: The SVROOFR table is only checked when at least one CC-Y transaction is being processed for an applicant.

This report can be run from SVAOQOP (Offer Accepted by Applicant (CC-Y) option), SVAOCAS (Calculate Admissions Acceptance option), GJAPCTL.

OCAS Alternate Program Calculation (SVPOALT) process

This process is used to calculate alternate programs for the applicant based on the values entered on the OCAS Alternate Programs (SVAOALP) page.

This process can be executed as many times as required. The process does not update existing data for choices with a sequence number of 6, which is the alternate choice.

This process does not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) is still processed.

The process does not evaluate courses that have no final and mid-term grades and that are completed before the current system date.

The process selects alternate programs based on the priority defined in the SVAOALP page, where 1 is the highest priority. If multiple programs have the same level of priority, then the program with the highest number of available offers is assigned. When all of the possible offers for a level of priority have been made, the process goes to the next level of priority.

When the Generate all possible alternates check box is cleared on the SVAOCTL, the process inserts an alternate program into the OCAS Program Choice Data (SVROCCC) table when there are less than three CC sequences with choice number 6 (SVROCCC_PROG_CHOICE_SEQ_NO = 6) for the same term where the alternate programs are offered for an applicant. When the Generate all possible alternates check box is checked on the SVAOCTL, the process inserts all of the possible alternate programs into the SVROCCC table.

When the Generate alternate when offer check box is unchecked on the SVAOCTL page, the process does not generate an alternate if the applicant already received an offer for another program in the same term where the alternate program was offered. When the Generate alternate when offer check box is checked on the SVAOCTL page, the process inserts new CC records into the SVROCCC table for the new alternate program even though the applicant already received an offer in the same term where the alternate program was offered.

If a student has received an offer, pursued the cross-referenced Banner program, or graduated from the cross-referenced Banner program, this process does not offer a possible alternate program (for example, if an applicant has pursued or graduated from pre-health, then pre-health would not be offered as an alternate for medicine). One of the following messages, as applicable, is displayed in the .lis file:
  • Eligibility not calculated. Applicant has already accepted an offer for the alternate program.
  • Eligibility not calculated. Applicant has already pursued the cross-referenced Banner program.
  • Eligibility not calculated. Applicant has already graduated from the cross-referenced Banner program.

The process will not process the selected alternate program if the alternate term does not have the OCAS year as the one to which the term of the corresponding original program is attached. A message reporting the error will be included in the process output.

Note: The SVPOALT process will be updated in a future release to process ineligible or waitlist applicants separately in conjunction with the recent enhancement to the SVAOALP page.

OCAS Data Processing (SVPOCAS) process

This process is used to load the OCAS transmission XML data file into the database, to edit the loaded data according to the OCAS field rules, and to set the records to an error free status.

The process supports the OCAS layout of the current application cycle (from the Fall term to the Summer term), and you must enter the year of the current application cycle in the OCAS Year parameter.

This process expects an XML file name according to the OCAS specifications, which is COLLYYYYMMDDNNNNNN, where COLL is the four letters that identify the college where OCAS data is being processed, YYYYMMDD is the date on which the file was generated, and NNNNNN represents the six-digit sequence number. The extension of the file always defaults to XML so that the file to be loaded must have an .XML as the extension to be loaded, otherwise the file will be rejected. The new file date must be greater than or equal to the file date of the last file loaded, and the new sequence number must be equal to one plus the sequence number of the last file loaded. If this is not the case, the system displays a message and does not continue with processing.

This process also assigns a primary administrator. Only administrators who have an admissions role (SVROADM_ADMIN_ROLE_IND = Y) can be assigned. This assignment is based on the applicant's program. The process sets the secondary administrator to null. In the case that an administrator cannot be assigned to the applicant program, the user running the process is set as the administrator.

This process will add the OCAS application number as an inactive alternate ID. This will insert a record into the SPRIDEN table using the OCAS application number with the SPRIDEN_CHANGE_ID field set to I (ID changed), and a record using the Banner ID with SPRIDEN_CHANGE_ID field set to null. This allows the OCAS application number to be used as an alternate ID search.

The process looks at the Alternate ID Indicator field (SVROCTL_ALT_ID_IND) to determine if an alternate ID using the OCAS application number will be created at the moment an insert/update on the SPRIDEN data is being performed. If the SVROCTL_ALT_ID_IND field has a value of Y (Yes), then an alternate ID will be created in the SPRIDEN table using the OCAS Application Number every time that a general person record is inserted or updated; otherwise, no ID will be created, just the normal insert/update of the record that is being performed.

For CC records, the program, start date, semester, and campus code combination must exist in SVROPRC.

Every record of the OCAS data file is stored in the corresponding table according the transaction code (SVRORBC, SVRORAC, SVRORCC, SVRORGC, SVRORSC, SVRORTC, SVRORIC, SVROREC and SVRORNC). Every record will have a status to register the condition of the data. The first time that a record is stored into the table, the status is set to null.

Note: Only valid OCAS administrators, who have an admissions role (SVROADM_ADMIN_ROLE_IND = Y), can execute the SVPOCAS project, which means that the user logged in when running the process must exist in the SVROADM table. The administrator must also exist as a valid user in the GOBEACC table.

This process will insert and update records in the Banner baseline tables that handle concurrent curricula data. When data has been inserted and updated in the Banner Admissions tables (SARADAP/SARAPPD) or the Banner Student (SGBSTDN) table, the records will also be inserted and updated in the SORLCUR and SORLFOS tables.

This process can be run from SVAORER (Launch OCAS Data Process option) or GJAPCTL.

OCAS File Name No Name of the OCAS file to be processed. When this parameter is null, the process edits all records that are associated with the value entered for the OCAS Year parameter and no file will be loaded. XML file name without file extension.
OCAS Applicant Number No OCAS applicant(s) to be processed. When an application number is entered and the OCAS File Name parameter is null, the process will edit the data attached to that application number. However, if an application number is entered and the OCAS File Name parameter is not null, then the process will ignore the application number and will load the data contained in the entered file. When run from the SVAORER page, the default value is from the Key block.

OCAS Applicant Transaction (SVPOCAT) process

This process is used to process the OCAS transactions. Alerts are displayed during the processing to track the applicant's application.

This process does not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). For CC records, the program, start date, semester, and campus code combination must exist and be active in SVROPRC.

The process inserts a record into the GURMAIL table when the SVROTLC table indicates that a letter must be generated for an OCAS AC or CC transaction (SVROTLC_LETR_CODE is not null and SVROTLC_POP_GURMAIL_IND = Y). A letter record is only be generated when the CC-Y was successfully created in Banner Admissions.

This process adds the OCAS application number as an inactive alternate ID. This inserts a record into the SPRIDEN table using the OCAS application number with the SPRIDEN_CHANGE_ID field set to I (ID changed), and a record using the Banner ID with SPRIDEN_CHANGE_ID field set to null. This allows the OCAS application number to be used as an alternate ID search.

The process looks at the Alternate ID Indicator field (SVROCTL_ALT_ID_IND) to determine if an alternate ID using the OCAS application number will be created at the moment an insert/update on the SPRIDEN data is being performed. If the SVROCTL_ALT_ID_IND field has a value of Y (Yes), then an alternate ID using the OCAS application number is created; otherwise, no ID is created, just the normal insert/update of the record that is being performed.

This process reports the person information that exist in the OCAS raw applicant data which is shorter than the baseline person information tables such as SPRIDEN, SPRADDR, and SPRTELE, and so on.

You can have the system create Admissions records in Banner baseline at an early stage (that is, as soon as the program is created, before CC-Y) or at a later stage (as has always been available in Banner OCAS). This choice is controlled by a new Early Admissions Indicator on the OCAS Control (SVAOCTL) page.

OCAS Expiry Dates Mass Update (SVPODMU) process

This process is used to perform a mass update of expiry dates related to program offers. The dates are as follows.

  • Offer Active Date (SVROCCC_OFFER_ACTIVE_DATE). The Offer Active Date applies to all queues not just the offer queue.
  • Soft Date/OCAS Due Date (SVROOFR_OCAS_DUE_DATE)
  • Hard Date (SVROOFR_HARD_DATE)
  • Populations that can be processed by the SVPODMU process are as follows:
  • All applicants that match the parameters when the OCAS application number is null.
  • All applicants entered in the OCAS Applicant Number parameter that match the other parameters.

This process can be run from SVAOQOP (OCAS Expiry Dates Mass Update option) or GJAPCTL.

Parameter value if not null.

 When run from the SVAOQOP page, the default value is the value entered by the user.

SVROPRS_HARD_INCREMENTAL will be zero when null.

 When run from the SVAOQOP page, the default value is the value entered by the user.

OCAS Eligibility Calculation (SVPOELI) process

This process is used to calculate the applicant eligibility according to the eligibility rules.

This process will not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) will still be processed.

Note: The process assumes that all of the eligibility rules are logically correct. To ensure this, all rules must have been entered through a form or replication process, otherwise the produced results will be wrong. To verify if the entered eligibility rules are valid, the SVPOESA process, which will audit the rules. This process will generate a report indicating which formulas are not valid. For the formulas that are not valid, the user has to return to the eligibility rules forms and correct them.

The process does not evaluate courses that have no final and mid-term grades and that are completed before the current system date.

The following describes the logic for generating a conditional offer (notice that final eligibility will appear as MET even though the temporary grades/scores were used for satisfying the requirements):
  • The General Requirement has not been met but the Final Only check box and Mandatory Requirement check box are checked in the Eligibility General Requirements Block on the SVAOESR page (SVROEGA_FINAL_ONLY_IND = Y and SVROEGA_MAND_IND = Y).
  • The course is not using only final grades for meeting the requirement. It is using at least one of any of the following instead: mid-terms, or estimated or substitutes grades.
  • The test is using the estimated scores to meet the requirements.
  • The Institutional Testing rule has not been met but the Final Only check box and Mandatory Requirement check box are checked in the Institutional Testing Requirements Block on the SVAOESR page (SVROITS_FINAL_ONLY_IND = Y and SVROITS_REQ_RULE_IND = Y)

The OCAS Offer Data Error File Loading (SVPOEOC) process used to load the error file generated by OCAS when processing offers.

The error file is sent back to the colleges by OCAS. The error file contains a report of the errors in the offer file that was transmitted by the college to OCAS. When the error file is downloaded, the user will be able to look at the errors using the OCAS Error Data for Offers Inquiry (SVIOEOC) page. The file is downloaded into the SVROEHO and SVROEDO tables.

Note: This process will only download the data from the file into the table. It will not fix any of the errors listed in the file. The user will have to look at the errors in the SVIOEOC page, and then decide how to correct the error.

The error file name must have the correct college attached to it. For example, if the error file is named ER_MOHA2005022400001, where MOHA are the college initials, then MOHA must be in the SVROCTL_COLLEGE_CDE field. The BC record is always loaded first. If the BC record already exists in the SVROEHO table, then a warning is displayed in the report, the file processing is stopped and no record is loaded. If an EC record already exists in the SVROEDO table, then a warning is displayed in the report and the remaining EC records are processed.

  • All Total fields (four) reported in the BC record totals

  • Total of EC records that were actually loaded by the SVPOEOC process.

OCAS Offer Data File Generation (SVPOOCF) process

This process is used to generate the Online Confirmation (OC) file.

The OC file is an offer file that contains OC records. The OC file will be sent back to OCAS from the colleges containing all the offer related data that occurred from the last time file was sent. The name of the flat file that is generated is as follows:

  • Audit mode: OF_AAAAYYYYMMDD#####_AUDIT.DAT.
  • Update mode: OF_AAAAYYYYMMDD#####.DAT, where:
    • AAAA = College
    • YYYY = Year of the system date when the OC file was generated
    • MM = Month of the system date when the OC file was generated
    • DD = Day of the system date when the OC file was generated
    • ##### = Sequence number of the OC file in the cycle (SVROCTL_LAST_OC_FILE_SEQNO)
      Note: The process must be run in Audit mode before being run in Update mode.

The OC file is only created if the Online Confirmation Indicator field (SVROCTL_ON_LINE_CONF_IND) has a value of Y on SVAOCTL.

Warning: When the OC file is being created, all other offer transactions must be stopped during that time. Any application that affects offer data (SVAOQOP, SVPORNK, SVPOCAT, SVAOCAS, etc.) should not be executed by any user until the SVPOOCF process has completely finished. Following this rule will keep the amount of records reported in the OC file consistent with the counter reported in the BC record. The best time for producing the OC file is at the end of the day, or when the user is sure that no offer activity will be registered in the system.

The SVROOFT table is locked when this process is run to avoid any offer transactions from being performed.

The applicant data that may be in the OC file can be viewed from the SVIOOFT form (SVROOFT table). Applicants where the OC File Indicator check box is unchecked on the SVIOOFT form (SVROOFT_OC_FILE_IND = null) are pending to be reported.

The criteria for excluding SVROOFT records from being processed are as follows.

  • Records with an OCAS Applicant Number with a year that is less that 06 (before 2006) will not be reported in the OC file, however they will still be marked as reported setting the SVROOFT_OC_FILE_IND field to Y.
  • Records that were not marked as OCAS Processed (SVROCAC_OCAS_PROC_IND = N) will not be reported in the OC file, however they will still be marked as reported setting the SVROOFT_OC_FILE_IND field to Y.
  • Records that have OCAS application numbers that are not numeric will not be reported in the OC file, however they will still be marked as reported setting the SVROOFT_OC_FILE_IND field to Y, and they will be printed in the final report under the EXCEPTION section of the SVPOOCF process.

Records with an OCAS Applicant Number with a year that is greater than or equal to 06 (2006 or after), are marked as OCAS Processed (SVROCAC_OCAS_PROC_IND = O), and have a numeric OCAS application number will be reported in the OC file. When the records are written in the OC file, they will be marked as reported setting the SVROOFT_OC_FILE_IND field to Y. These records will be written to the offer file.

In the case where no records meet the criteria, no file will be generated and no updates will be applied to any of the tables. The process will print a message in the report indicating that NO RECORDS FOUND TO BE PROCESSED.

A header (BC record) or main record will be always at the beginning of every file followed by the SVROOFT records (OC records).

OCAS Offer Letter Generation (SVPOOFR) process

This process is used to generate offer letter records for applicants that have offers assigned.

The process inserts one record into the GURMAIL table by term for all offers that exist for the applicant at the moment SVPOOFR was run, and for which a letter has not already been generated (SVROOFR_STATUS = A and SVROOFR_SENT_IND is null). The process will look for letter codes where SVROTLC_TRANS_CDE = OF (offer), or it will use the letter code entered as the parameter when running the process, this code will overlap the one defined on the SVROTLC table.

The records inserted into the GURMAIL by this process are controlled by the Generate Multiple Offer Letters check box on the Indicators tab of the OCAS Control (SVAOCTL) page, as follows.

  • If the Generate Multiple Offer Letters check box on SVAOCTL is selected, the process selects all of the program offers corresponding to the applicants entered by the parameters, and offer letters will be generated for all the programs irrespective of the program entered. See the Scenarios for generating multiple offer letters section for an example of how the process works.
  • If the Generate Multiple Offer Letters check box on SVAOCTL is cleared, the process selects only the program offers corresponding to entered by the parameters, and offer letters will be generated only for the programs entered, not for all programs for the applicant.

This process will not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) will be processed.

The term attached to the offer (in the SVROOFR table) will be used for inserting the letter record into the GURMAIL table. This will be done for every different term that the applicant has (with offers) and for which the SVPOOFR process was run.

Note: The SVPOOFR process will insert the letters into the GURMAIL table but does not send the letters to a printer.

OCAS Rank/Offer Calculation (SVPORNK) process

This process is used to calculate the ranking of an applicant based on the score, and to synchronize the queues at the end of ranking.

The ranking process ranks and marks selected applicants, which is used to place them on offer, wait or refusal lists. The process can be run in trial (Trial Run parameter set to Y) or real (Trial Run parameter set to N) mode. This process will not process any program that is inactive at the applicant program level (SVROCCC_STATUS <> A or is null). A program that is inactive at the general level (SVROPRC_ACTIVITY_IND = I) but active at the applicant program level (SVROCCC_STATUS = A) will still be processed. The process does not consider inactive offers.

This process generates a second offer in a term for an applicant if the Same Term Offers check box is checked on the SVAOCTL page. This feature applies to applicants who are ready to be assigned to the offer queue from the waitlist, refusal or no queue.

  • If the Same Term Offers check box is checked, then the following occurs:
    • An offer is generated for a new program even though an applicant has already accepted another program in the same term.
    • A new alert for the OFFR group with the following description is posted into SVROAAL table using the alert code 0023.
  • If the Same Term Offers check box is unchecked, then the following occurs:
    • Offers are not generated for programs being processed if the applicants have already accepted offers for another program in the same term.
    • The applicants is not considered for another offer in the same term.

However, multiple offers can be sent in the same term if the applicant has not accepted an offer for the corresponding term. Also, an applicant can accept more than one offer as long as they are not in the same term.

You can have the system create Admissions records in Banner baseline at an early stage (that is, as soon as the program is created, before CC-Y) or at a later stage (as has always been available in Banner OCAS). This choice is controlled by a new Early Admissions Indicator on the OCAS Control (SVAOCTL) page.

The SVPORNK can be used to revoke offers of applicants that did not meet the eligibility rules. When the process has been run with the Trial Run parameter set to N, then the process can be run with the Deactivate Offer when Non-Elig parameter set to Y. All of the offers that belong in that condition will be deactivated in the system (Note: the offer will be deactivated in Banner Admissions as well, as long as no registration activity exists).

The following describes the logic for generating a conditional offer (notice that final eligibility will appear as MET even though the temporary grades/scores were used for satisfying the requirements):
  • The General Requirement has not been met but the Final Only check box and Mandatory Requirement check box are checked in the Eligibility General Requirements section on the SVAOESR page (SVROEGA_FINAL_ONLY_IND = Y and SVROEGA_MAND_IND = Y).
  • The course is not using only final grades for meeting the requirement. It is using at least one of any of the following instead: mid-terms, or estimated or substitutes grades.
  • The test is using the estimated scores to meet the requirements.
  • The Institutional Testing rule has not been met but the Final Only check box and Mandatory Requirement check box are checked in the Institutional Testing Requirements section on the SVAOESR page (SVROITS_FINAL_ONLY_IND = Y and SVROITS_REQ_RULE_IND = Y)

The process indicates whether an applicant is eligible for the program and updates the existing offer to conditional if the program choice is Pending Finals (SVROCCC_ELIG_FINAL_IND = P). This occurs when the OCAS Eligibility Calculation (SVPOELI) process is run with Y specified for the Final Only parameter and there are pending grades to be received, which means that there is at least one course that can be used to calculate eligibility that has a completion date in the future.

An offer will be unconditional when all of the following conditions are met (when rules exist for the program in each section):
  • The General Requirements have been met when the Final Only check box is checked (SVROEGA_FINAL_ONLY_IND = Y).
  • The Institutional Testing Requirements have been met when the Final Only check box is checked (SVROITS_FINAL_ONLY_IND = Y).
  • The Eligibility Formula has been met using only the final grades and scores.

The process can be run as many times as required. The process synchronizes the queues for all applicants for whom eligibility changed, which means that applicants, who have offers or are on a waitlist, can be dropped from the corresponding queue when eligibility is changed to not met and the Deactivate Offer when Non-Elig parameter is set to Y.

The process creates a report that is ordered by the queue combination of program, term, semester and campus, and by applicant name. The report will indicate the queue to which the applicant was assigned, and the old queue to which the applicant was assigned before running the process.

This process can be run from SVAOCAS (Calculate Ranking for Current Program and Calculate Ranking for ALL Programs options), SVAOQTR (OCAS Rank Calculation option), or GJAPCTL.

Waitlist reordering

This process can also be used to reorder a waitlist and update students’ current scores, ranks, and rank dates in the Waitlist (SVROWLQ) table. The current score is updated with the value from SVROCCC.

Note: Current score, rank, and rank date are always updated together.
The following parameters are used to reorder applicants (both existing and incoming waitlisted) in the waitlist either by score or date:
  • Waitlist (WL) Reorder Option
  • Waitlist Reorder Sort Option
  • Print Waitlist Reorder Details.

Only groups of applicants (not individual applicants) can be reordered. That is, if specific applicant numbers are entered under the OCAS Applicant Number parameter, the process will not reorder the waitlist, as reordering is applicable only to the entire population of the program combination.

If no applicants exist on the waitlist at the time when the process executes, after the queue assignment processing, the new waitlisted applicants are either re-ordered or not, according to the option selected for the Waitlist (WL) Reorder Option parameter. If the option value is 2, 3, or 4, the applicants are re-ordered by the sort option (Score or Date).

If the Waitlist (WL) Reorder Option value is set to 2, 3, or 4 then the applicants with inactive programs in the Waitlist will be reassigned new rank numbers starting from the maximum rank number of all the applicants with active programs according to their current rank. Then all the waitlisted applicants including inactive ones current rank will be again Re-Numbered to have the ranks in sequential order. The entire WL will be Re-Numbered only when the process run in real mode because Waitlist (SVROWLQ) table will not be updated for a trial run.

The logic behind the Waitlist (WL) Reorder Option is independent of the Process Waitlist parameter. You can reorder the waitlist without adding applicants by setting the Waitlist (WL) Reorder Option parameter to 2 or 3. Alternatively, you can add applicants to the waitlist without reordering the waitlist by setting the Waitlist (WL) Reorder Option parameter to 1.

The process will transfer all of the tests from the SORTEST table that are associated with the PIDM of the application number(s) being processed according to the parameter values.

The only tests that will not be transferred are ones that have a date that is before the value entered for the Oldest date a test can be parameter.

The process will insert or update as many SVROETD records that are from the SVROTSC table when searching for the test code in the SVROTSC table using SORTEST values. That is, it is possible for one Banner test code to be associated with multiple OCAS test codes.

The process will insert the tests from the SORTEST table into the SVROETD table when no SVROETD records exist.

The process will update the tests from the SORTEST table in the SVREOETD table, when SVROETD records exist and the activity date of the SORTEST record is more recent (greater) than the date in the SVROETD record, and changes were made to the records.

  • SVROETD_SUBTEST_CDE: SVROTSC_SUBTEST_CDE where SVROTSC_TESC_CODE = SORTEST_TESC_CODE.
  • SVROETD_TEST_DATE: SORTEST_TEST_DATE
  • SVROETD_RAW_SCORE: SORTEST_TEST_SCORE
  • SVROETD_NORMALIZED_SCORE: See note below on how to calculate this field.

OCAS Transfer Transcription (SVPOTRN) process

This process is used to transfer multiple courses and tests from one OCAS applicant number to another number belonging to the same student. The source and target applicants, courses, and tests must be active for the data to be considered by the process.

The process finds all of the OCAS applicant numbers in the SVROCAC table that have the same PIDM as the target applicant number. Any existing courses or tests from previous years are transferred from all old applicant numbers to the current applicant number for the target year. When copying the data, the applicant number is the target applicant number for the current year, but the PIDM stays the same from the previous year. Only the final grades are transferred not the mid-term grades, and if the final grade is null, the record is not transferred. The existing records are not changed.

The Completion Date field on the SVAOTRN page indicates if the transcript information is current or from a previous application. A date in the past indicates that the transcript information was transferred from a previous application.

Courses

When transferring courses, the following rules are followed.

  • If a source course code is not present in the current records, the course is transferred.
  • If a source course code is present in the current records, when the records have the following:
    • Different completion dates, then the data is transferred
    • Same completion date and the same grade, then the data is not transferred
    • Same completion date and different grades but the same activity date, then the data is not transferred
    • Same completion date, different grades and different activity dates, then the data is only transferred if the source record has the most recent activity date
    • Same course and same completion date with multiple records in different years, then only the data with the most recent activity date is transferred. If more than one record has the same activity date, then only one record is transferred.
  • If a course is already present in the SVROECD table for the target record with the same course code, and same completion date, the course is not transferred regardless of the other rules.

The source tables to be used when copying course data are SVROCGC, SVROCIC and SVROECD; the target table is SVROECD.

Tests

The sources tables to be used when copying test data are SVROCTC and SVROETD; the target table is SVROETD.

When transferring tests, the following rules are followed.

  • If a source test code is not present in the current records, the test is transferred.
  • If a source test code is present in the current records, when the records have the following:
    • Same test code and different sub-test code, then the data is transferred
    • Same test code, same sub-test code and different test date, then the data is transferred
    • Same test code, same sub-test code and test same date are present in different years, then the record with the most recent activity date is transferred if not present in the target year
  • If a test is already present in the SVROETD table for the target record with the same test code, same sub-test code, and same completion date, the source test is not transferred regardless of the other rules.

Two Open Years

It is recommended the SVPOTRN process is only run for the current year. If the situation exists where two years are open for OCAS at the same time, run SVPOTRN for the oldest year, and wait at least one day before running the process for the most recent year.

When two years are open, a different normalization rule may exist in each year. The process will normalize the test scores using the rules from the SVAONCR, SVAOPCT, SVAOGEQ and SVAOSTN forms (based on the value in the Normalization Method field on the SVAOTSC form) for the most recent effective term that is valid for the target year.
