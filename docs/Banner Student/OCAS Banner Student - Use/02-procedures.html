Set up automatic PIN generation

If you want OCAS processing to generate PIN automatically on the GOBTPAC table in your daily operation for every new applicant that is received, you must authorize OCAS processes to do so.

Procedure

  1. Access the Crosswalk Validation (GTVSDAX) page.
  2. Perform a query for the CREATPIN internal group and the SVROCAC internal code.
  3. Change the value in the External Code field to Y.
  4. Save your change.

Define your program and campus combinations

To ensure that CC record processing runs correctly, you must create at least one corresponding record in the OCAS Program Campus Maintenance (SVAOPRC) page for each program and schedule created on the OCAS Program Schedule Maintenance (SVAOPRS) page.

About this task

SVAOPRS is where you define the valid program, term, start date, and semester combinations, and SVAOPRC is where you define the valid program, term, start date, semester, and campus code combinations.

Procedure

  1. Access the OCAS Program Schedule Maintenance (SVAOPRS) page.
  2. Create a record for each program, term, start date, and semester combination.
  3. Save your changes.
  4. Access the OCAS Program Campus Maintenance (SVAOPRC) page.
  5. For each record you created on SVAOPRS, create record that includes the campus code.
  6. Repeat 5 for each campus code associated with a program/term/start date/semester combination.
  7. Save your changes.

Define the parameters for detecting a duplicate person

When personal information is collected or loaded through the OCAS Web Application (OWA), OCAS Data (SVAOCAS) page, or OCAS Data Processing (SVPOCAS) process, the system uses the settings on the OCAS Duplicate Person Selection Parameters (SVAODSO) page to find perfect match or possible duplicate persons.

About this task

If you define single or multiple rules for finding a perfect match, the system first uses the parameters to detect if only one person already exists as a perfect match. If so, the system does one of the following.

  • If the information was obtained through SVAOCAS or SVPOCAS, it overrides the existing data with the collected information.
  • If the information was obtained through OWA, it treats the information as a possible duplicate.

If more than one person in the system is found according to the perfect match rules, the system treats those as possible duplicates.

If no perfect match is found, the system uses the rules that are defined for finding possible duplicates.

If one or more possible duplicates are found, the administrative staff is responsible to resolve these using the OCAS Duplicate Person (SVAODUP) page (as described in Process duplicate applicants) or using SVAOCAS if the application was manually entered through SVAOCAS.

If nether a perfect math or duplicate is found, the system pushes the personal information into baseline personal tables and assign a new Banner ID to the person.

Procedure

  1. Access the OCAS Duplicate Person Selection Parameters (SVAODSO) page.
  2. Create a new record.
  3. Select the check boxes for the desired combination of data types to match a possible duplicate person.

    At least one check box must be selected, and no two records can have the same combination of selected check boxes.

  4. Save your changes.

Ensure a record will be created when a CC-Y record is received

About this task

Warning: If this task is not completed, an SGBSTDN record is not generated when a CC-Y record is received.

Procedure

  1. Make a note of the decision code in the Banner Decision for CCY Code field on the SVAOCTL page.
  2. If you want a SGBSTDN record to be automatically generated when a CC-Y record is sent by the applicant, the Applicant Acceptance check box must be checked on the STVAPDC page for the decision code from step 1.

    This indicates that the applicant has accepted your institution’s offer of admission. Performing this step ensures that a SGBSTDN record is created every time a CC-Y record is received.

    If the Applicant Acceptance check box is unchecked, a SGBSTDN record will not be created. However if a SGBSTDN record already exists, the record will be updated.

Set up online confirmation

Online confirmation has been created by OCAS to allow Ontario college applicants to respond to their offers using the Web. You must indicate whether your institution will be using online confirmation from the OCAS Control (SVAOCTL) page.

About this task

If this task is not completed, online confirmation processing will not be performed correctly because of a lack of data. Completing this task enables the Offer Active Date to be calculated, which is a required field in the offer file that is sent to OCAS each time that offer activity is changed.

Procedure

  1. Access the OCAS Control (SVAOCTL) page.
  2. Go to the next block.
  3. Enter Y in the On-Line confirmation indicator field.
  4. Save the record.

Set up offer status mappings

When OCAS is installed, the values on the Offer Status VS Offer State (SVAOSVS) page must be set up. The SVAOSVS form maps the offer status to the offer states required in an offer file.

Procedure

  1. Access the Offer Status VS Offer State (SVAOSVS) page.
  2. Enter an offer status, which is used to indicate the status of an applicant in the offer queue at the college.
    Possible values are as follows:
    • A: Active
    • W: Not active because the applicant has withdrawn
    • X: Not active because the applicant is deceased
    • N: Not active because the applicant has a non-payment
    • D: Not active because the program was deleted (CC-D)
    • U: Not active because of a user reason (manually inactivated)
    • E: Not active because the eligibility changed to not met
    • S: Not active because the program is suspended
  3. Enter the offer state that corresponds with the offer status.
    The offer states are required by OCAS in the offer file. The same Offer State field value can be assigned multiple times to different offer status records. Possible values are as follows:
    • A: Active. Offer is active and available for the applicant to select within the rules established for the date fields (activation and expiry date)
    • R: Revoked. A valid offer that has been withdrawn by college and is not available for the applicant to select.
    • D: Deleted. Offer was deleted by college (that is, issued in error) and not available for the applicant to view or select.
    • S: Program Suspended. Offer was withdrawn by college due to the college program being cancelled. The program can be viewed but not selected from the OCAS web site.

Early stage and later stage admissions setup

You can choose to have the system create Admissions records in Banner baseline at an early stage (that is, as soon as the program is created, before CC-Y) or at a later stage (that is, as soon as the offer is accepted, after CC-Y).

About this task

If you are using early stage admissions, the system creates a record in the SARADAP table and the related admissions tables (such as SORLCUR, SORLFOS, and so on) for every program/term/campus combination for which the applicant has applied. This means that there will be different admissions applications, each with its own application sequence number, for every program combination that was inserted in SVROCCC. For example, if an applicant has three programs (CC-Is) regardless the term (even if they have the same or different term), then three records will exist, one for each program in SARADAP. When an applicant receives and accepts an offer for any program, the system updates the existing record or creates a new record in SARADAP and the related admissions tables, and creates records in SGBSTDN and SFBETRM, if applicable.

If you are not using early stage admissions, the system creates a record in the SARADAP table, SGBSTDN table, SFBETRM table, and so on, if applicable, only when the offer is accepted.

The following procedure explains how to set up admissions.

Procedure

  1. Access the OCAS Control (SVAOCTL) page.
  2. On the Personal Data tab, enter the desired Banner Student and Admissions type codes in the following fields:
    • Early Stage Banner Student Type Code
    • Early Stage Banner Adm Type Code
    • Later Stage Banner Student Type Code
    • Later Stage Banner Adm Type Code

      If the early stage admission type code is different from the later stage admission type code, two set of records (with different application numbers) will be created in SARADAP and the related admissions tables if you are using early stage admissions. The first set of records will be created when the program is first inserted in the SVROCCC table, and the second set of records will be created when an applicant accept an offer for the same program.

  3. Go to the Indicators tab.
  4. If you are using early stage admissions, perform the following steps.
    1. Select the Early Admissions Indicator check box.
    2. Enter the desired Banner decision codes to be used on early stage admission records in the fields in the Early Stage Decision Codes section.
  5. Enter the desired Banner decision codes to be used on later stage admission records in the fields in the Later Stage Decision Codes section.

    By default, the decision codes in the Early Stage Decision Codes section are the same as the ones in the Later Stage Decision Codes section, but you can change them.

  6. Save your changes.

Program eligibility rules setup

If you have already entered program eligibility rules, and want to copy the existing rules to another year, see “Copy existing rules to another year”.

A complex structure is used to evaluate program eligibility. The structure includes the following concepts:
  • Eligibility formula based on variable or constant values
  • AND and OR operators
  • Logic to support Boolean and "n-of" logic
  • Ability to define requirements in different grouping levels such as areas, groups and variables.
  • Ability to support eligibility formula such as the following:
    • For OSSD applicants: ENGA = 2 of (E1A or E11A or E19A)
    • For Mature applicants: ENGA = OTLE and NDCO and NDVO
  • Course level as requirement
  • Grades, including the following:
    • OSIS, OSS
    • Alphanumeric grades
    • Numeric grades
    • Weight (numeric value for scoring purposes)
    • Grades used for scoring
    • Grade to be used (middle term, final or highest)
    • Stanine
    • Percentile
    • Grade equivalent
    • Credits
  • Semester to apply
  • Specific courses as requirement
  • Tests: Specific tests and test scores
  • Ability to support equivalencies, recommended and senior courses
  • Non-test checklist or program requirements, including the following:
    • Compulsory/Optional rule indicator
    • Issued date
    • Expiry date
    • Program specific textual information
    • Previous diploma or degree (name, global average/score)
  • Differentiate applicants by category
  • Handle alternate programs
  • Country of origin determines if a TOFEL test is required. English speaking countries are identified.

Other points to consider

  • Out of province equivalencies are not done by OCAS. Documents are sent to the College, which then determines the equivalencies.
  • Collaborative programs courses must be U level.
  • Grade 9 and 10 courses may be used for apprenticeship programs.
  • Beginning with 2016, part-time programs are available at the OCAS website. Banner OCAS does not specify full-time or part-time for eligibility and scoring rules for a program combination. It is recommended that you define either categories or program schedules separately to identify different rules for eligibility and scoring processing.

Scoring rules setup

If you have already entered scoring rules, and want to copy the existing rules to another year, see “Copy existing rules to another year”.

A complex structure is used to calculate the score. The structure includes the following concepts:
  • Eligibility formulas based in variable or constant values
  • AND, OR, +, -, /, and * operators
  • Logic to support Boolean and "n-of" logic
  • Weighting factors
  • Ability to define requirements in different category levels
  • Ability to support formula such as ENGA = .125 X [(2 of (E1A or E11A or E19A)/2) or (.333OTLE + .333NDCO + .333NDVO)]
  • Course level as requirement
  • Grades, including the following:
    • OSIS, OSS
    • Alphanumeric grades
    • Numeric grades
    • Weight (numeric value for scoring purposes)
    • Grades used for scoring
    • Grade to be used (middle term, final or highest)
    • Stanine
    • Percentile
    • Grade equivalent
    • Credits
  • Semester to apply
  • Specific courses as requirement
  • Tests: Specific tests and test scores
  • Wildcard functionality
  • Equivalencies table
  • Recommended courses table
  • Senior courses table
  • Non-test checklist or program requirements, including the following:
    • Compulsory/Optional rule indicator
    • Issued date
    • Expiry date
    • Program specific textual information
    • Previous diploma or degree (name, global average/score)
  • Differentiate applicants
  • Handle alternate programs
  • Country of origin determines if a TOFEL test is required. English speaking countries are identified.

Other points to consider

  • Priorities are established according to the Residence status (Ontario, Canada, International)
  • Sponsors are recorded if needed for future billing activities
  • Out of province equivalencies are not done by OCAS. Documents are sent to the College, which then determines the equivalencies
  • Collaborative programs courses must be U level
  • Grade 9 and 10 courses may be used for apprenticeship programs
  • Repeat courses are handled (completed or in-progress)
  • Applicants applying to different terms can be handled.

Copy existing rules to another year

The SVPORPL process takes all of the OCAS settings from a prior OCAS year and generates the corresponding new data for the new year.

Procedure

  1. Enter the rule on the SVAOTRM page for the new year and associated terms.
  2. Enter the rules on the SVAOPRS page for the program/terms associated with the new year.
  3. Enter the rules on the SVAOPRC page for the program/term/campus associated with the new year.
  4. Enter the rules on the SVAOTRR page for setting the source and target term years to replicate.
  5. Run the SVPORPL process with 1 entered for the Replication Option parameter, and the source and target year set to the desired values.

    For example, if you want to replicate rules from 2011 to 2012, set the Source OCAS Year parameter to 2011 and the Target OCAS Year parameter to 2012.

  6. Review all of the rules for Boolean variables, categorization, and so on (that is, anything that does not include program) to ensure they have been replicated properly.
  7. Adjust any of the rule dates if necessary.

    For example, if you have Boolean variables that include dates using specific years, you will have to change those dates according to the new year.

  8. Run the SVPORPL process with 2 entered for the Replication Option parameter, and the source and target year set to the values that you want.

    3. Repeat for any remaining applicant records for which the CC Record Exists check box is unchecked.
    4. Rerun the SVPOALT process to generate the missing CC records with choice number 6.
  5. Run the OCAS Rank/Offer Calculation (SVPORNK) process using the parameters that will select the alternate programs for which an offer is going to be generated.

    The SVPORNK process calculates the offers for the population that is pending. If offers are still available, the SVPORNK process will assign offers to the applicants who have alternate programs.

  6. If you want to view an applicant’s alternate programs, access the OCAS Alternate Program Processing (SVAOALT) page.

Online confirmation

The "Set up online confirmation" setup task must be completed for online confirmation to work correctly. If this task is not completed, online confirmation processing will not be performed correctly because of a lack of data.

Completing this task enables the Offer Active Date to be calculated, which is a required field in the Online Confirmation (OC) file that is sent to OCAS each time that offer activity is changed. An OC file is an offer file that contains OC records.

Online Confirmation allows applicants to apply online through OCAS, and to view and select their offer details on the OCAS web pages.

When you process applicants using the OCAS Applicant Transaction (SVPOCAT) process, any applicants from 2006 and later will be eligible to use Online Confirmation. These applicants will have a value of O in the OCAS Processed Indicator field on the SVAOCAS page.

You need to create an OC file that lists all changes made to the offer data and is submitted to OCAS. OCAS then sends back an error file, which you use to correct the errors.

View offer information

The OCAS Offer Tracking Inquiry (SVIOOFT) page displays the information for each applicant’s offer and the history of records (OC records) that have been generated every time that a given event has affected an applicant's offer.

OC records are displayed in the SVIOOFT page when changes occur for the following fields:
  • SVROOFT_OFFER_ACTIVE_DATE (changed from the SVAOQOP page, and SVPODMU and SVPORNK processes)
  • SVROOFT_OFFER_EXP_HARD_DATE (changed from the SVAOQOP page, and SVPODMU and SVPORNK processes)
  • SVROOFT_OFFER_EXP_SOFT_DATE (changed from the SVAOQOP page, and SVPODMU and SVPORNK processes)
  • SVROOFT_OFFER_STATE (changed from the SVAOCAS and SVAOQOP pages, and SVPOCAT, SVPORNK, SVPODMU, and SVPOSIP processes)
  • SVROOFT_LATE_ADMIT (changed from the SVAOCAS page)

Each transaction record listed has been reported or will be reported using Online Confirmation (OC). The OC File Indicator field indicates if the record has already been reported in an offer file that was sent to OCAS. If the OC File Indicator field has a null value, then that record will be reported in the offer file.

Generate an Online Confirmation file

An Online Confirmation (OC) file is an offer file that contains OC records and lists all of the offer related data. The best time for producing the OC file is at the end of the day, or when no offer activity will be registered in the system.

About this task

Records with an OC File Indicator application number with a year that is greater than or equal to 06 (2006 or after), are marked as OC File Indicator Processed (SVROCAC_OCAS_PROC_IND = O), and have a numeric OCAS application number that will be reported in the OC file. When the records are written in the OC file, they will be marked as reported setting the OC File Indicator field (SVROOFT_OC_FILE_IND) to Y on the SVIOOFT form. These records will be written to the OC file.

Warning: When the OC file is being created, all other offer transactions must be stopped during that time. Any application that affects offer data (SVAOQOP, SVPORNK, SVPOCAT, SVAOCAS, etc.) should not be executed by any user until the SVPOOCF process has completely finished. Following this rule will keep the amount of records reported in the OC file consistent with the counter reported in the Batch Header (BC) record.

The SVROOFT table is locked when this process is run to avoid any offer transactions from being performed.

Procedure

  1. Access the Offer Data File Generation (SVPOOCF) process.
  2. Enter A (Audit) for the Run Mode parameter, and run the process.

    The process can be run in Audit mode as many times as necessary. The Audit mode flat file is named OF_AAAAYYYYMMDD#####_AUDIT.DAT.

    Note: The SVPOOCF process must be first run in Audit mode.
  3. When the Audit report is the way you want it, enter U (Update) for the Run Mode parameter, and run the process.

    The Update mode flat file is named OF_AAAAYYYYMMDD#####.DAT.

    After the records are written in the OC file, they will be marked as reported setting the SVROOFT_OC_FILE_IND field to Y.

  4. Submit the resulting .DAT file to OCAS.

These files are created using the OCAS Offer Data File Generation (SVPOOCF) page. The data file is submitted to OCAS by the user (the user is responsible for keeping track of which files were sent to OCAS).

View and manage error codes

Use the OCAS Error Code for Offer Data File Validation (SVVOEDO) page to define the error codes in the error file, which is returned to the institution from OCAS. The error file is processed using the OCAS Error Data File Loading (SVPOEOC) process.

About this task

If an error code does not exist in the SVVOEDO table during the load process, the SVPOEOC process will insert the new error code into the table, setting the description to UNDEFINED and the error type to null. In this case, a user can update the description and error type as necessary (the user must contact OCAS to request the description of the error).

Procedure

  1. Access the OCAS Error Code for Offer Data File Validation (SVVOEDO) page.
  2. If you want to modify an error code, perform the following steps.
    1. Find the code you want to modify.

      To search for new codes added by the SVPOEOC process, perform a Query on UNDEFINED in the Description field.

    2. Modify the required information.
      When changing the value in the Type field, only the following values can be entered:
      • F: Warning/error is related to the error file in general, or to the data contained in the Batch Heard (BC) record of the error file
      • R: Warning/error is related to the field format of an EC record in the error file
      • P: Warning/error for paper confirmations delivered to OCAS and processed by data entry clerks
      • Null: Error type is unknown.
  3. If you want to add a record, perform the following steps.
    1. Insert a record.
    2. Enter the error code in the Code field.
    3. Enter the error type in the Type field.
      Possible values are as follows:
      • F: Warning/error is related to the error file in general, or to the data contained in the Batch Heard (BC) record of the error file
      • R: Warning/error is related to the field format of an EC record in the error file
      • P: Warning/error for paper confirmations delivered to OCAS and processed by data entry clerks
      • Null: Error type is unknown.
    4. Enter a description in the Description field.
  4. Save the record.

View the header data in the error file

Use OCAS Error Data File Loading (SVPOEOC) process to process the error file.

The OCAS Error Header for Offer Inquiry (SVIOEHO) page displays the data for the Batch Header (BC) record that was in the error file. The error file is sent by OCAS to the colleges and contains the errors related to the submitted offer file. The SVIOEHO form displays the BC data in a format that is easier to interpret than viewing the data directly from the error file.

The user can view the number of Online Confirmation (OC) records that were sent in the offer file, the number of OC records that succeeded or failed when the offer file was processed, and the number of Error records (EC) returned in the error file.

View the error data in the error file

Use the OCAS Error Data for Offers Inquiry (SVIOEOC) page to display the Error (EC) records contained in the error file sent by OCAS. The institution is responsible for correcting the source of the error, and then submitting the offer file back OCAS.

The error file contains the error detail related to the offer file sent to OCAS. The error file is processed using the OCAS Error Data File Loading (SVPOEOC) process.

Update the dates for web viewing

Applicants can view offer data on the web on and after the offer active date but can select the offer data only on the days between (inclusive of) the soft and hard dates.

These OCAS dates can be updated from the OCAS Queue Operation (SVAOQOP) page or the OCAS Expiry Dates Mass Update (SVPODMU) process. The following dates can be updated.

Offer Active Date Date the offer became active. Earliest date when an applicant can see their offer (or any other queue) related data on the OCAS web pages.

If the date the user is logged in to the web page is equal to or later than the Offer Active Date, then the data will be displayed.
OCAS Soft/Due Date The Due Date and Soft Date have the same value however the values are handled in two different ways depending on the object that is referencing the value.

For the OCAS Due Date, this is the latest date when the applicant can send back the acceptance confirmation to the institution. The OCAS Due Date is used by the SVPOCAT and SVPOADM processes for calculating if an applicant's acceptance (CC-Y) will be accepted or rejected with or without an available room.

For the Soft Date, this is the expiry date that will be posted on the OCAS web site for the applicant to view. The applicant will be able to view and select this offer beyond this date up to the date in the SVROOFR_HARD_DATE field.
Hard Date Date the offer expires. When this date has passed, the applicant will be able to view this expired offer on the OCAS web site but will not be able to select it. The system will indicate that this offer has expired.
OCAS Queue Operation (SVAOQOP) page

The following options available on the SVAOQOP page allow the expiry dates to be changed.

  • OCAS Expiry Dates Mass Update
  • Change OCAS Soft/Due Date
  • Change OCAS Soft/Due Date for All Applicants
  • Change Offer Active Date
  • Change Offer Active Date for all Applicants
  • Change Hard Date
  • Change Hard Date for all Applicants.
