Release 9.3.42 and 8.39

The Banner Student 9.3.42 and 8.39 release includes quality improvements and technical currency updates.

Support for Banner 8 Self-Service has ended

As of January 1, 2026, Banner 8 Self-Service has moved out of Sustaining Support and has entered End of Support.

For detailed information on support statuses, please review our Support Assurance Policy.

Technical Currency Upgrades

As part of ongoing technical currency initiatives, Banner General Java batch programs have been upgraded to support the latest versions of key Spring frameworks. This enhancement ensures improved compatibility, performance, and alignment with modern development standards.

Banner General Java batch programs now support Spring Framework 7.x, Spring-boot 4.x and Spring-batch 6x libraries at runtime.

Modified Java Processes:

  • SARSTML
  • SOPSSDT

This enhancement addresses PE0008177 in the Ellucian Customer Center.

Enhanced Batch Job Submission Status Capture

The Banner Batch Job Submission framework has been enhanced to ensure consistent and accurate capture of job execution status across all Banner modules. This enhancement improves visibility into batch job lifecycle events by reliably recording queue, run, and completion timestamps, enabling better monitoring and troubleshooting of batch processes through the jobsub-statuses API.

The Banner Batch framework captures execution status for jobs in the GJBRSLT table and exposes this information through the jobsub-statuses API.

The enhancement resolves this conflict by implementing proper insert/update logic that handles both new and existing records gracefully, eliminating submission failures and ensuring accurate final status reporting.

Key features of this enhancement include:

  • Preservation of queue and run timestamps during record updates, maintaining complete job lifecycle history
  • Elimination of batch insert failures caused by framework-inserted status records
  • Improved accuracy of job status reporting through the jobsub-statuses API
  • Enhanced visibility and monitoring capabilities for batch job execution across Banner modules
  • Consistent behavior across both Oracle and PostgreSQL database environments

This enhancement addresses PE0007995 in the Ellucian Customer Center.

Extended Currency Support for Student Accounts Receivable

Banner Student extends the maximum supported values for fee, charge, refund, and balance amount fields in the Student Accounts Receivable module in Banner SaaS environments.

Banner Student delivers extended currency support for Student Accounts Receivable amount fields in Banner SaaS. Fee assessment amounts, charge amounts, payment amounts, refund amounts, and balance totals associated with the Student module now support values up to 99,999,999,999.99.

Institutions that process student fee transactions or have account balances that may exceed 999,999.99 benefit from this enhancement. No configuration change is required to enable extended currency support; the expanded field capacity is available automatically in Banner SaaS environments running Banner Student.

Note: This enhancement applies to Banner SaaS environments. Institutions using on-premises deployments should review their environment and database configuration before processing amounts in the extended range.

The Structured Progression Student Profile has been enhanced to display actual module scores alongside the F grade for failed modules. This enhancement provides programme leaders and exam board members with the detailed academic data needed to identify students eligible for compensation or condonement under institutional assessment regulations.

The enhancement improves the reliability and efficiency of progression processing and exam board preparation by ensuring all relevant academic data is available in a single view. The Student Profile page now includes a new Percentage column under the Courses and Grades section, which displays the actual numeric scores for failed modules. This does not alter grading or progression logic; it purely enhances data visibility in the user interface.

Enhance Structured Progression SHASPAR page and SHPPGAW process

Structured Progression has been enhanced to support progression rule logic based on student attributes, enabling differentiated progression and re-sit outcomes for multi-intake programmes. This enhancement addresses the needs of institutions delivering postgraduate programmes with multiple intake points throughout the academic year, such as October and January intakes.

A new field Attribute and new column shrpgrc_atts_code is added to the SHASPAR page, and a query is modified in the SHPPGAW process and related services to add attribute code logic while checking for stage and progression rules.

The enhancement introduces the ability to reference the Student Attribute Code (STVATTS_CODE) within SHASPAR (Student Assessment Parameters) rule conditions and SHPPGAW (Progression Award Rules) processing. This allows progression logic to distinguish automatically between different intakes or other cohort-defining attributes within the same programme structure, without requiring duplicate programme configurations or manual intervention.

This enhancement enables institutions to manage multi-intake postgraduate programmes accurately within a single progression framework, reducing manual workload while ensuring regulatory compliance and operational consistency across different student cohorts.

Automated Learner Curriculum End Date and Catalogue Term updates

Structured Progression has been enhanced to automatically update the Learner Curriculum End Date (SORLCUR_END_DATE) and increment the Catalogue Term based on student progression outcomes and academic standing decisions. This automation ensures accurate academic record maintenance and compliance with UK and Ireland reporting standards, particularly for HESA and ERM statutory reporting.

Two new columns SHRASAT_CAT_TERM_INCR_IND and SHRASAT_CURR_END_DATE_INCR_IND are added to the SHRASAT table. The SHAASAT page is modified to add new fields which are required to increment date and next roll term logic.

The progression‑awards‑results API has been enhanced to improve roll logic handling for award progression. These changes ensure accurate date adjustments and term rollovers based on adjustment rules. Additionally, the nextRollTerm value is advanced to the following year to ensure accurate progression handling.

When progression outcomes from an exam committee determine that a student must repeat a year, extend their study period, or experience other changes to their academic timeline, the system now automatically adjusts the curriculum end date to reflect the new academic timeline.

Key capabilities include:

  • Automatic update of SORLCUR_END_DATE when a progression outcome (such as Repeat Year, Proceed to Next Stage, or Withdrawn) is locked or approved within Structured Progression
  • Extension of end dates based on configurable rules mapped to the progression outcome (for example, "Repeat Year" extends the end date by one academic year)

SHRDEGV Multi-College/Multi-Campus Support

The Degree Verification Process (SHRDEGV) is enhanced to provide improved support for multi-college/multi-campus institutions. This enhancement introduces new optional parameters and improved data file header logic to better accommodate institutions with multiple OPEID codes.

Key enhancements include:

  • Added optional parameter for Population Selection (PopSel)
  • Added optional parameter for OPEID
  • Updated .dat file header logic to support OPEID in place of FICE/Branch code

The OPEID parameter can be provided as either 6 or 8 digits:

  • When the OPEID parameter is 8 digits, it replaces the existing FICE + branch code in the header, with the 8-digit OPEID populating starting at position 4 in the .dat file.
  • When the OPEID parameter is 6 digits, the 6-digit OPEID is used with "00" appended as the branch code, consistent with current behavior.
  • When the OPEID parameter is blank, the existing logic continues to use the 6-digit FICE from the SHACTRL page with "00" as the branch code.

The existing validation remains in place: if the FICE code is null in SHACTRL, the process will continue to throw an error.

Sleep Wake Listener Enhancements

Banner Student Sleep/Wake jobs now include Sleep Wake Listener enhancements that automatically monitor and restart critical batch processes. This enhancement eliminates manual intervention when processes terminate unexpectedly or during system upgrades, improving operational resilience and reducing downtime.

The Sleep Wake Listener continuously monitors configured batch jobs, detects abnormal termination, and automatically restarts jobs using the same parameters and user credentials from the last successful run. This automated recovery mechanism ensures seamless operation without requiring manual intervention.

Enhanced processes include:

  • SFRSCHD - Schedule Processing
  • SHRTRTC - Real-Time Conflict Checking
  • SHRPESE - Registration Event Streaming
  • SHRTCIM - Course Import Management
  • SHRPESI - Registration Event Service Integration
  • SCRCATE - Catalog Event Processing

Key features of the Sleep Wake Listener:

  • Automatic process monitoring at regular intervals
  • Restart capability using preserved parameters from the last run
  • Maintains the same user ID from the last run when restarting
  • Lock file mechanism to track active processes and their state
  • Parameter persistence in the GJRSWPR table to guarantee availability for recovery
  • Process tracking information maintained in the GJRSWPT table
  • Graceful shutdown capability during database upgrades
  • Automatic restart post-upgrade without requiring manual intervention

This enhancement significantly improves operational resilience, reduces downtime risk for critical registration and scheduling processes, and eliminates the manual work previously required to restart these processes after unexpected terminations or system upgrades.

Enhanced Course Program of Study Processing with Graded Course Preservation

The Course Program of Study (SFPCPOS) process has been enhanced to provide institutions with control over how graded and rolled courses are evaluated during financial aid eligibility processing. This enhancement resolves a critical issue where graded courses were being removed from SFASCRE evaluation results during SFPCPOS runs, potentially causing financial aid reductions or loss for students who had already completed courses.

Previously, when SFPCPOS ran with Parameter 11 set to N, graded courses were being completely removed from the SFASCRE (Student Curriculum) evaluation rather than being preserved with their original counts. This caused students to lose financial aid credits for courses they had completed, as the system was re-evaluating all courses instead of freezing graded course results.

This enhancement introduces a new parameter and audit source to give institutions precise control over course evaluation behavior:

Parameter 11 - Preserve Graded/Rolled Courses:

  • Y (Preserve Graded/Rolled Courses): Graded and rolled courses are not re-evaluated. The system carries forward results from the most recent prior SFPCPOS run for eligible courses. These courses are not sent to Degree Works or CAPP in the current run, protecting students from aid reductions after course completion.
  • N (Re-evaluate All Courses): All courses, including graded and rolled courses, are evaluated as usual through CAPP or Degree Works, maintaining legacy behavior.
  • Default Value: N (preserves existing institutional behavior unless customers opt in to the new functionality)

Preservation Logic (Parameter 11 = Y):

When Parameter 11 is set to Y, SFPCPOS preserves prior results for a course only when all of the following conditions are met:

  • The course is graded or rolled
  • The registration status voice type is R (Registered) or W (Web Registered)
  • A prior SFPCPOS run exists for that course

When these conditions are satisfied, SFPCPOS carries forward these fields from the prior run: Count In Program, Count for Aid, Audit Basis In Program, and In Program Repeat. If any condition is not met, the course is processed through normal evaluation through Degree Works or CAPP, regardless of the Parameter 11 setting.

Examples:

  • Parameter 11 = Y with a graded course and prior SFPCPOS result (preserved outcome)
  • Parameter 11 = Y with no prior SFPCPOS result (normal evaluation path)

New Audit Source - PAR (Parm 11=Y, Previous Audit Retained):

A new audit source value PAR has been introduced on SFASCRE to provide transparency when preservation logic is applied:

  • Display Text: Parm 11=Y, Previous Audit Retained
  • Database Value: PAR
  • When PAR appears: SFPCPOS was run with Parameter 11 = Y, and the preserve logic was applied for an eligible graded or rolled course with a prior SFPCPOS result
  • Meaning: The course was not re-evaluated in the current run; SFPCPOS retained the prior CPOS result under the Parameter 11 preservation rules
  • Distinct from: DW (Degree Works), CAPP (CAPP), MOV (manual override), and any SFACPSC "Override Rule" source

Processing Order and Precedence:

SFPCPOS follows this order of precedence when evaluating course rows:

  1. Preserve Override from SFASCRE (MOV)
  2. SFACPSC course override (Override tab/rules)
  3. Preserve Graded/Rolled carried-forward result (Parameter 11 = Y; audit source: PAR)
  4. Standard evaluation through Degree Works or CAPP (audit source: DW or CAPP)

Entry Point Behavior:

  • GJAPCTL (Job Submission): Users explicitly set Parameter 11 to Y or N on the parameter form
  • SFASCRE (Evaluate Courses in Program of Study): Parameter 11 is controlled through a Preserve Graded/Rolled Courses check box on the page. When selected,Parameter 11 = Y; when cleared, Parameter 11 = N.
  • ROAIMMP (Financial Aid): Current behavior is maintained with limitations on directly setting Parameter 11 (alignment with Financial Aid is tracked separately in PD0007538).

SFPCPOS Output Clarification:

To reduce support questions and improve clarity, the SFPCPOS output (.lis file) footer has been clarified:

  • Total Records Processed / Records Processed Successfully: Cumulative number of course records processed
  • Pages Completed Successfully (Page Size): Page Size is driven by Parameter 10 and represents the number of students per page/chunk, not the number of course records. The page count is informational (batching/check pointing) and does not cap or limit the total course records processed

For example, if output shows "Total Records Processed: 639" and "Pages Completed Successfully: 5 (Page Size: 25)", this means 639 course records were processed across 5 internal pages of up to 25 students each, not that only 125 records were processed.

This enhancement ensures accurate financial aid processing, prevents unintended aid reductions for students with completed courses, and provides institutions with flexible control over course evaluation behavior based on their specific business rules and student populations.
