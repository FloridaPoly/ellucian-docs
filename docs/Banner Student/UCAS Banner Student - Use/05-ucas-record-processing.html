UCAS Record Processing

This chapter explains the processing of the following records.

*N - Name details

Banner UCAS uses the applicant number as the unique identifier for an applicant although this value is no longer supplied by UCAS. The *N contains getUCASApplicantDetails and getGTTRApplicantDetails XML end points.

The function delivered with UCAS 8.0 version invokes when a record is downloaded from XML-Link without an applicant number, and it populates the applicant number columns on the Banner interim tables (SKBUSTA, SKBUSTN, SKBUSTC, and so on). The generated applicant number is then processed into the Banner UCAS tables (SKRUDAP, SKRSAIN, SKRUCCR, and so on) in the same way as an applicant number originating from UCAS.

For XML-Link, when the MDUU rules are run, Banner finds all new applicant records waiting to be processed into the interim tables that do not already exist on SKRSAIN or SKBUGAN. Then, it generates an applicant number for each of the new applicant records and stores them in SKBUGAN.

The SKAUHNC process, which loads raw UCAS data received through XML-Link into Banner baseline, calls the P_CREATE and P_UPDATE procedures within the GB_COMMON and GB_IDENTIFICATION APIs, which create PIDMs and SPRIDEN records.

The f_generate_id and f_generate_pidm functions in the gb_common package are called by the P_CREATE procedure in the gb_identification package. The P_CREATE procedure is called by all pages and processes that create new SPRIDEN records. The gb_identification package uses Oracle sequences to determine the next available number for the ID or PIDM instead of using the SOBSEQN table. The gos_id_seq.sql script creates the ID_SEQUENCE that generates unique identification numbers such as SPRIDEN_ID. The gos_pidm_seq.sql script creates the PIDM_SEQUENCE that generates unique internal identification numbers such as SPRIDEN_PIDM.

The P_CREATE and P_UPDATE procedures within the GB_ADDRESS, GB_TELEPHONE, GB_EMAIL, and GB_BIO APIs are also called to create SPRADDR, SPRTELE, GOREMAL and SPBPERS records.

Create SPRIDEN Increment PIDM Populate soundex from Banner function Populate SPBPERS_LEGAL_NAME with Forenames and Surname. If Forename is greater than 15 characters, then an attempt will be made to break the name between FIRST_NAME and MI.

Create SPBPERS PIDM LEGAL_NAME NAME_PREFIX

For UCAS applicants there is a system parameter POPULATE LEGAL NAME, which controls whether the SPBPERS_LEGAL_NAME column should be populated.

For XML-Link, you can download Unicode versions of applicant names. Both ASCII and Unicode versions of applicant name data are stored so that ASCII data is available to be passed to other systems downstream from Banner. Unicode names are stored as alternate names (SPRIDEN_CHANGE_IND = N). The value specified in the UNICODE NAME TYPE system parameter defines the name type to store with the Unicode data, and the value specified in the UNICODE LEGAL NAME system parameter defines whether the SPBPERS_LEGAL_NAME column is to be loaded in ASCII or Unicode format.

When SKAUHNC has completed loading records into Banner, all SKBUGAN records are deleted.

*A - Applicant address/telephone details

The *A data contains the getUCASApplicantDetails and getGTTRApplicantDetails) XML end points.

Actions

You can do the following actions

Create SPRADDR

Take the last not null address line. If it is line 4, then put the first 20 characters into SPRADDR_CITY.

If it is longer than 20, then also put an error for the *A record into SKRUREC_BANNER_ERRORS (Marvin) or SKBUHTS_ERROR (ODBC-Link). Then put all other not null lines into the SPRADDR_STREET_LINE# columns.

Put the Mail Sort Code into SPRADDR_GST_TAX_ID.

Place a full stop into the SPRADDR_CITY if it is still empty.

If the postcode is not null, put the system parameter value for UCAS STATE CODE DEFAULT into SPRADDR_STAT_CODE, and set SPRADDR_NATN_CODE to null. If the postcode is null, put the system parameter value for UCAS NATION CODE DEFAULT into SPRADDR_NATN_CODE and set SPRADDR_STAT_CODE to null. When an existing address is updated, the state code and nation code are always reprocessed according to these rules to ensure there are no API errors.

SPRADDR_ATYP_CODE will be set to the value specified for the UCAS ATYP CODE DEFAULT system parameter.

For XML-Link, you can download Unicode versions of applicant addresses. Both ASCII and Unicode versions of applicant address data are stored so that ASCII data is available to be passed to other systems downstream from Banner. The values specified for the UNICODE HOME ADDRESS TYPE and UNICODE UCAS ADDRESS TYPE system parameters define the address types to store with the Unicode data. They must be different from those used for the ASCII versions of both addresses, otherwise they will simply supersede the ASCII addresses.

In XML-Link, records are sent with hyphens in the address fields of getUCASApplicantsDetails and getGTTRApplicantsDetails when the applicant has not supplied address data. Banner UCAS ignores these records and they are not loaded to SPRADDR.

Create SPRTELE

SPRTELE_ATYP_CODE will be set to the UCAS ATYP CODE DEFAULT system parameter. SPRTELE_TELE_CODE will be set to the UCAS TELE CODE DEFAULT system parameter.

The following options are provided using system parameters:
  • Strip out non-numeric characters and place in SPRTELE_PHONE_AREA, SPRTELE_PHONE_NUMBER and SPRTELE_PHONE_EXT. Put the rest in SPRTELE_COMMENT.

    -OR-

  • Strip out non-numeric characters and place in SKRTELE_INTL_ACCESS. If length is still greater than 16 characters, then put number in SPRTELE_COMMENT and flag an error in SKRUREC_BANNER_ERRORS. Enter “.” in SPRTELE_INTL_ACCESS.

    - OR -

  • For all telephone numbers, store in SPRTELE_COMMENT and put enter "." in SPRTELE_INTL_ACCESS.

Place the MAILSORT code in SKRTELE_GST_TAX_ID.

In XML-Link, records are sent with hyphens in the telephone number fields of getUCASApplicantsDetails and getGTTRApplicantsDetails when the applicant has not supplied telephone number data. Banner UCAS ignores these records and they are not loaded to SPRTELE.

Create GOREMAL

GOREMAL_EMAL_CODE will be set to the UCAS EMAIL CODE DEFAULT system parameter.

GOREMAL_PREFERRED_IND will be set to the MAKE EMAIL ADRESS PREFERRED system parameter.

GOREMAL_DISP_WEB_IND will be set to the DISPLAY EMAIL ON WEB DEFAULT system parameter.

When a new e-mail address is processed for an applicant, the Preferred indicator will be set to null on any existing GOREMAL records (regardless of EMAL_CODE). This allows the new address to be set as the preferred address when the previous preferred e-mail address had a different EMAL_CODE.

When a new record is inserted with the same EMAL_CODE and address as an existing record, the existing record will be set to Inactive to avoid a unique-constraint violation.

In XML-Link, records are sent with hyphens in the e-mail address field of getUCASApplicantsDetails and getGTTRApplicantsDetails when the applicant has not supplied e-mail address data. Banner UCAS ignores these records and they are not loaded to GOREMAL.

*C and *G - Choice data

contains the getUCASApplicantChoices and getGTTRApplicantChoices XML end points.

Baseline application and curriculum records

Baseline application (SARADAP) records are created only for choices that belong to your institution and for which a decision is to be entered.

The SARADAP records are created by a call to the SAKMODS package (from within the SKAUHNC script), which calls the P_CREATE_APPLICANT procedure, which in turn calls the SB_ADMISSIONSAPPLICATION API, which creates SARADAP records (minus curriculum columns).

The SAKMODS package also calls the SB_CURRICULUM and SB_FIELDOFSTUDY APIs to populate the SORLCUR and SORLFOS curriculum tables, and the P_BACKLOAD_CURR back-load procedure, which populates the curriculum columns in the SARADAP table.

The SAKMODS package also creates checklist items and communication plans for applicants.

Note: The SAKMODS p_insert_commplans procedure populates the Communication Plan Collector (SORCCOL) table and not the SOBCPLN table. You must, therefore, run the Communication Plan Processing (SORCPLN) report to assign communication plans to UCAS applicants.

When the admissions SORLCUR record is created, curriculum error checking will be enforced according to the Admissions settings on the SOACURR Module tab (SORMCRL_ADM_IND) and on SOACTRL (SOBCTRL_ADM_ERRLVL_IND). Records that cannot be loaded due to a fatal curriculum error will be set to OH (On Hold) and the error message stored to SKBUSTC_ERROR_MSG or SKBUSTG_ERROR_MSG. Where a warning message is produced, the record will be loaded and the status set to PM (Processed with messages) and the warning message stored to SKBUSTC_ERROR_MSG or SKBUSTG_ERROR_MSG.

When a Choice record is loaded that creates a Learner (General Student) record, curriculum error checking will be enforced according to the Student settings on the SOACURR Module tab (SORMCRL_STU_IND) and SOACTRL (SOBCTRL_STU_ERRVL_IND). Records that cannot be loaded due to a fatal curriculum error will be set to OH (On Hold) and the error message stored to SKBUSTC_ERROR_MSG or SKBUSTG_ERROR_MSG. Where a warning message is produced the record will be loaded and the status set to PM (Processed with messages) and the warning message stored to SKBUSTC_ERROR_MSG or SKBUSTG_ERROR_MSG.

When a change of UCAS course is received from UCAS, the existing SORLCUR and SORLFOS are made inactive and new records are created for the new curriculum details.

The existing records are made inactive in the following way:
  • The SORLCUR_CACT_CODE field is set to INACTIVE.
  • The SORLFOS_CACT_CODE is set to INACTIVE and the SORLFOS_CSTS_CODE field is set to CHANGED.
  • The SARDSCL_STATUS_IND field is set to INACTIVE.
  • The SARCHKL, SOBCLPN, SKRUDAP, SARAPPD, and SARCHRT records are deleted.
When a change of UCAS year of entry is received from UCAS, resulting in a change of admissions term code, the existing SARADAP, SKRUDAP, SARAPPD, SARCHRT, SARDSCL, SORLCUR, and SORLFOS are made inactive and new records are created for the new curriculum details.

The existing records are made inactive in the following way:

  • The SORLCUR_CACT_CODE field is set to INACTIVE.
  • The SORLFOS_CACT_CODE is set to INACTIVE and the SORLFOS_CSTS_CODE field is set to CHANGED.
  • The SARADAP_APST_CODE field is set to W (Withdrawn).
    Note: W is not a system required code, so clients must ensure W (Withdrawn) is on the STVAPST page.

The APIs will create new SARADAP, SORLCUR and SOLRFOS records in the same way that the old records were created.

For more information about the APIs, see the Banner Student TRM.

Joint institution/UTT Schools Direct choices

If your institution operates joint admissions processing or is a UCAS Teacher Training (UTT, formerly GTTR) institution acting as an accrediting provider for one or more schools, choices for these secondary institutions are loaded into baseline Banner in the same way as those for your own primary institution.

The above holds good as long as the institution codes for these choices are listed in the INSTITUTE CODE system parameter in the GKAKSYS page.

For UTT choices, the accrediting provider code must also be listed in the INSTITUTE CODE system parameter for a SARADAP record to be created.

Processing a change of course

When a change of course is processed by loading a new Choice record, the system does the following.

  • Keeps the existing SARADAP record
  • Inactivates the old SORLCUR record by inserting a new row set to inactive
  • Inserts a new SORLCUR record set to active for the new program
  • Inactivates the old SORLFOS record by inserting a new row set to inactive
  • Inserts a new SORLFOS record set to active for the new major
  • Inserts a new communication plan collector record SOBCPLN
  • Leaves the existing communication plan record unchanged
  • Deletes the existing checklist items except where SARCHKL_RECEIVE_DATE is not null
  • Inserts new checklist items into SARCHKL
  • Leaves the existing SARAPPD records unchanged
  • Leaves the existing SARCHRT and SARDSCL records unchanged

Processing a change of term

The system does the following when a change of term is processed by loading a new Choice record.

  • Changes SARADAP_APST_CODE on the existing SARADAP record to the value in the INACTIVE SARADAP APST CODE system parameter, to indicate superseded/inactive.
  • Leaves the SORLCUR and SORLFOS records on the old SARADAP record unchanged (still active)
  • Leaves the checklist items, communication plans, and other ‘child’ records attached to the old SARADAP unchanged
  • Inserts a new SARADAP record (and associated decision, curriculum, checklist and communication plan records) for the new term

When a change of year and course are sent in the same transaction, the change of year is processed first so that the old SARADAP record shows the old course and the new SARADAP record shows the new course.

Processing a new Choice 7

UCAS use Choice number 7 for both Extra and Clearing.

A new choice 7 is defined as one with a different course to the previous choice 7, or one with the same course but a decision of REF (that is, the applicant applies for the same course through both Extra and Clearing). Users need to be able to enter a new decision for the new choice 7. When a new choice 7 is processed by loading a new Choice record, the system does the following:

  • Changes SARADAP_APST_CODE on the existing SARADAP record to the value in the INACTIVE SARADAP APST CODE system parameter, to indicate superseded/inactive
  • Leaves the SORLCUR and SORLFOS records on the old SARADAP record unchanged (still active)
  • Leaves the checklist items, communication plans, and other 'child' records attached to the old SARADAP unchanged
  • Inserts a new SARADAP record (and associated decision, curriculum, checklist and communication plan records) for the new choice
  • Changes SKRUCCR_SSDT_CODE_DECN and SKRUCCR_SSDT_CODE_CF_DECN on the existing SKRUCCR record to null
  • Sets the existing SKRUDEC record for Choice 7 to a status of SU (Superseded choice 7)

Processing residential category

There are rules defined in SKASSDT to control the loading of the *C - RESCAT (Residential Category) data. You can also create your own additional rules.

The *C - RESCAT rules are used to control the updating of the SKRSAIN_SSDT_CODE_RESCAT and the SARADAP_RESD_CODE columns. The rules are used in *K, *A, and *C record processing.

Options 1 and 3 can contain an actual value, a wildcard (%) matching any value (including null values) or the word NULL when a null-only match is required.

The value U used for options 1 and 3 for ‘Data’ item 2 will be the value from the RESD DEFAULT system parameter on GKAKSYS. You will need to change it if your default value is different.

*K records are loaded before *C records so these rules will be executed after the *K RESCAT rules. If no rules are found in SKASSDT, the value in the *C-RESCAT system parameter will be used to determine how records will be updated.

*P and *R - Results data

The *P and *R data contains getUCASApplicantsResults XML end points.

Results Refresh Control view/method

When a download is executed, Banner UCAS always downloads from getReferenceResultsRefreshControl. This indicates when UCAS are refreshing the data in the following.

  • getUCASResultsMatchStatus method
  • getUCASApplicantResults method
  • getUCASApplicantsUnits method

If the Results Refresh Control method indicates either that results data is being refreshed or that the refresh failed, Banner will not download data from the results methods. The Download Summary tab on SKAUHPR and the .lis file output by the SKPUHER process will display messages indicating the status of the results refresh and whether results data has been downloaded. If Results Refresh Control indicates that the results refresh is not running, Banner will continue as described in the following sections.

Downloading results data

Changes to result data are determined from the getUCASResultsMatchStatus timestamps and those on getUCASApplicantsResults are ignored. getUCASResultsMatchStatus is always downloaded before getUCASApplicantsResults, and if the getUCASResultsMatchStatus timestamp indicates that the result data has changed for an applicant, all existing UCAS SORTEST records are deleted and all result records then inserted.

Results data in XML-Link is normally downloaded on an applicant-by-applicant basis. However, this method of retrieving the data can be very time consuming when data is available for a very large number of applicants. As an alternative, it is recommended that you re-download all results data on days when there are many records to download. XML-Link processing will switch between the two methods automatically by identifying the number of applicants for which changed results data is available and switching to the full download method when the limit identified by this parameter is reached.

You must determine the switchover limit suitable for your institution because this is likely to vary based on the number of applicants applying. Analysis determined that results data for up to 10,000 applicants is available to download on ABL Sunday for smaller institutions. For larger institutions, the figure is up to 35,000 applicants. The limit must be entered in the value field for the XMLLINK RESULTS DOWNLOAD LIMIT system parameter. We do not advise setting this parameter to a value of less than 1000.

Timestamps

When UCAS do a mass update to results data on getUCASApplicantsResults, the timestamps for all affected applicants are set to the same date and time.

For some applicants, this might be earlier than the latest timestamp held on Banner. It is, therefore, advised that whenever UCAS announce a mass update to results data, you should reset the timestamp for getUCASResultsMatchStatus to a date and time earlier than the timestamp given by UCAS to the mass update. This will ensure that you download all the latest changes.

Reference Data

UCAS provide the codes for all the results data that is downloaded through getUCASApplicantsResults.

It is important that all the reference data is updated before you try to download results from getUCASApplicantsResults, as missing codes will result in applicant result records not being loaded.

All the scripts listed in this section are available on the Customer Download Centre in the SC-Europe-UCAS folder. Full instructions for executing the scripts are provided in the same location. The scripts are reviewed and updated if necessary each year before the ABL weekend.

The details for obtaining this data and loading it into the required Banner tables are in the following sections.

ABL subject codes

To obtain the latest ABL/EBL subject ID codes from UCAS, download the data from getReferenceABLSubjects.

These are stored in the interim SKBUEBL table and are used to map subject IDs on getUCASApplicantsResults to subject codes held in getReferenceOfferSubject. getReferenceABLSubjects also provides the exam level, sitting, year, and awarding body for each subject ID. This data is used when processing getUCASApplicantsResults records into Banner.

Subject codes

To obtain the latest subject codes from UCAS, download the data from getReferenceOfferSubject. These are initially stored in the interim SKBUSUB table, and you use the following scripts to transfer the data to the STVTESC and SKBUSBJ tables.

  • stvtesc1.sql , which inserts new codes into STVTESC
  • stvtesc2.sql , which updates descriptions for existing codes in STVTESC
  • skvusbj1.sql , which inserts new codes into SKVUSBJ
  • skvusbj2.sql , which updates descriptions for existing codes in SKVUSBJ

The codes are used in SORTEST_TESC_CODE.

Examination levels

To obtain the latest examination level codes from UCAS, download the data from getReferenceExamLevel. These are stored in the interim SKBUEXA table, and you use the following scripts to transfer the data to the SKVSSDT and STVTADM tables.

  • stvtadm1.sql , which inserts new codes into STVTADM
  • stvtadm2.sql , which updates descriptions for existing codes in STVTADM
  • stvtadm_map1.sql , which inserts new codes into SKVSSDT
  • stvtadm_map2.sql , which updates descriptions for existing codes in SKVSSDT

The codes are used in SORTEST_TADM_CODE.

Awarding bodies

To obtain the latest awarding body codes from UCAS, download the data from getReferenceAwardingBody. These are stored in the interim SKBUAWB table, and you use the following scripts to transfer the data to the STVTSRC table.

  • skbuawb1.sql , which updates descriptions in SKBUAWB (replace the ampersand symbol with a plus symbol and remove quotes)
  • stvtsrc1.sql , which inserts new codes into STVTSRC
  • stvtsrc2.sql , which updates descriptions for existing codes in STVTSRC

The codes are used in SORTEST_TSRC_CODE.

getUCASApplicantUnitResults Data

Unit result data is subject to the Results Refresh Control view/method as described in “Results Refresh Control view/method”.

Unit result data is processed from the SKBUUGD interim table into SKRUAUG. SubjectID is joined to cvEBLSubject/getReferenceABLSubjects to identify the subject code that is stored to SKRUAUG_TESC_SCORE. Unit results are provided only when by UCAS. SKAUHNC therefore only inserts to SKRUAUG and there is no processing in SKAUHNC for updating records in SKRUAUG.

The identification of the correct HESA instance (SKBHINS) records to update with *J data, is accomplished as follows:
  1. Match SKRSAIN_APPLICANT_NO to SKBHINS_APPLICANT_NO

    This match uses the UCAS applicant number to find the right SKBHINS record; the applicant number is inserted into SKBHINS when it is created by the SKKHINS trigger.

  2. Match SARADAP_APPLNO to SORLCUR_APPL_SEQNO

    This match starts with the UCAS choice that is UFA, joins first to SKRUDAP and then to SARADAP, identifies the application number on SARADAP, and finally finds this on SORLCUR, which leads it to the related SKBHINS record.

  • If a match is found using the applicant number, the second method of matching is not used.
  • If no match is found or if multiple matches are found using the applicant number, the second method is then used.
  • If that method finds no SKBHINS or multiple SKBHINS records, the *J record is put on hold (OH) and the following error message is displayed: Found zero or multiple NUMHUS for same UCAS Application Number.

Processing of data from SKBUSTJ into Banner UCAS and baseline tables is subject to the above system parameters on the System Parameter Maintenance (GKAKSYS) page.

Each system parameter can have a value of UPDATE, UPDATE IF NULL, or IGNORE, as follows.
  • If the system parameter is set to UPDATE, any existing data in the HESA AND UCAS column is always updated by the data in SKBUSTJ.
  • If the system parameter is set to UPDATE IF NULL, the destination column is populated with the data from SKBUSTJ only if it was null.
  • If the system parameter is set to IGNORE, the existing data is not updated by the data in SKBUSTJ.

The system parameters that affect storage to both SKRSAIN and SKBHINS (for example, *J DOMICILE) behave as follows:

Each system parameter can have a value of UPDATE, UPDATE IF NULL, or IGNORE. If the system parameter is set to UPDATE, the system checks the value of the *J UPDATES RULE parameter.

  • If this is set to SKBHINS, the system updates only the SKBHINS columns with the *J data.
  • If this is set to SKRSAIN, the system updates only the SKRSAIN columns with the *J data.
  • If this is set to BOTH, the system updates both SKBHINS and SKRSAIN columns.
If the system parameter is set to UPDATE IF NULL, the system checks the value of the *J UPDATES RULE parameter.
  • If this is set to SKBHINS, the system checks whether SKBHINS data exists and updates the SKBHINS column only if no data already exists. It does not update SKRSAIN.
  • If this is set to SKRSAIN, the system checks whether SKRSAIN data exists and updates the SKRSAIN column only if no data already exists. It does not update SKBHINS.
  • If this is set to BOTH, the system checks whether SKBHINS data exists and updates the SKBHINS column only if no data already exists. It also checks whether SKRSAIN data exists and updates the SKRSAIN column only if no data exists.
If the system parameter is set to IGNORE, the existing data will not be updated by the data in SKBUSTJ.

UCAS Schools data

UCAS produces a Schools ‘file’ three or four times a year, and when they do, the timestamps of all records on getReferenceSchools are modified even though there might not have been changes to many individual records.

This means that all of the records would be downloaded and reprocessed into Banner causing any local changes to be lost.

To prevent local data from being overwritten by incoming UCAS data, the SCHOOLS DATA LOADING system parameter allows you to specify whether your institution updates all records or inserts only new records.

Updates only change the values in the coded fields (Country Code, Establishment Group, Status, School Type, and Merged with), and names and addresses are stored in Banner in initial-capital format to prevent the need for manual reentry.
