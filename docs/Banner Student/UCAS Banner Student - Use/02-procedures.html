Implementation

This section provides the following UCAS implementation procedures.

Define UCAS system parameter values

A set of default system parameters and possible values are delivered with the system. These parameters and values are used to configure the UCAS system. Use the System Parameter Maintenance (GKAKSYS) page to customise this data. Appropriate permissions are required to modify this page.

If your institution operates joint admissions processing, you must enter the institution codes for both institutions you process in the INSTITUTE CODE system parameter. You must enter the values in a comma separated list with the primary institution first.

If you are a UCAS Teacher Training (UTT, formerly GTTR) institution acting as an Accrediting Provider (AP) for one or more Schools Direct institutions, you must enter the institution codes for all these schools in the INSTITUTE CODE system parameter.

The following table provides an overview of the types of parameters you can define. Refer to the System Parameter Maintenance (GKAKSYS) page section for complete details about these parameters. All these parameters have a system code of UCAS.

Group Code  
*H Use parameters in this group to define your institution’s rules for the processing of *H data into Banner. Your institution values for these parameters must be defined before you can process *H data into Banner.

For XML-Link, the data items covered by these parameters are downloaded using the getUCASApplicantsDetails method.
*J Use parameters in this group to define your institution’s rules for the processing of *J data into Banner. Your institution values for these parameters must be defined before you can process *J data into Banner.

For XML-Link the data items covered by these parameters are downloaded using the getUCASHESAData and getGTTRHESAData methods.
*K Use parameters in this group to define your institution’s rules for the processing of *K data into Banner. Your institution values for these parameters must be defined before you can process *K data into Banner.

For XML-Link, the data items covered by these parameters are downloaded using the getUCASApplicantsBackground, getGTTRApplicantsBackground, getUCASApplicantsDetails, and getGTTRApplicantsDetails methods.
APPROVAL Use parameters in this group to define your institution’s rules for approving decisions before they are sent to UCAS. Your institution values for these parameters must be defined before you can enter any applicant decisions into Banner.
AUTOMATCH Use parameters in this group to define your institution’s rules for auto-matching applicants to existing Banner person data. Your institution values for these parameters must be defined before you can process any UCAS data into Banner.

DEFAULT Use parameters in this group to define default values to be stored in Banner where values have not been provided by UCAS. Your institution values for these parameters must be defined before you can process any UCAS data into Banner.

ONLINE Use parameters in this group to define your institution’s display rules for the Application Review Centre in Self-Service. Your institution values for these parameters must be defined before users can view data in the Application Review Centre.
RULES Use parameters in this group to define a variety of rules to control the processing of UCAS data. Your institution values for these parameters must be defined before you can process any UCAS data into Banner.
UNICODE Use parameters in this group to define your institution’s rules for processing Unicode data into Banner.
XMLLINK Use parameters in this group to define the Banner Web Service Interface Client (WINC) and Banner Mass Data Update Utility (MDUU) processes used to transfer data through XML-Link.

Map UCAS fields for Banner use

This procedure describes how to map a baseline Banner column to a corresponding UCAS module column or field description used by the UCAS download and upload processes.

About this task

If desired, you can store different codes in the baseline Banner columns to those provided by UCAS. The mapping process allows you to define the correspondence between UCAS codes and internal codes. In addition, the mapping facility can be used to store the descriptions for codes supplied by UCAS. A set of default mappings is delivered with Banner UCAS.

Procedure

  1. Access the UCAS Field Descriptions (SKAUFDS) page.
  2. In the Field Name field, enter the Banner column name.
  3. Take one of the follow actions, as appropriate.
    • If the column is to be mapped to an SKVSSDT entity, select the SKVSSDT option button in the Mapping option button group and define the relevant values in the fields to the right of the Mappingoption button group.
    • If the column is to be mapped to a table, select the Table option button in the Mappingoption button group and define the relevant values in the fields to the right of the Mapping option button group.
    • If the column is to be mapped to a field description used by the UCAS file import/export processes, select the None option button in the Mapping option button group and enter the field description in the Description field.
  4. Save the record.

Define rules for processing *J and *K/*C RESCAT data

You can choose whether to load data based on specific criteria when loading *J data or the RESCAT field on *K or *C.

*J data is downloaded using the getUCASHESAData and getGTTRHESAData XML-Link methods.

*K data is downloaded using the getGTTRApplicantsDetails and getUCASApplicantsDetails XML-Link methods.

*C data is downloaded using the getUCASApplicantCHoices XML-Link method.

Rules for loading *J data and the *K or *C RESCAT field can be created in the Value Mapping and List-of-Value Definition (SKASSDT) page. The entity code for each rule is ODBCLINK, and the attribute names are the same as the system parameter names relating to the specific columns, for example, *J - NATIONALITY. Make sure that option 1 contains the value already held in Banner and that option 3 contains the incoming value from UCAS. You can use % as a wildcard or enter the value NULL as appropriate in options 1 and 3. Set option 2 to Y or N, as applicable, to indicate whether the particular incoming value should update the existing value or not. If no rules are specified for a *J column or the data does not match any rules, the data will be loaded according to the system parameters for the *J column.

See UCAS Record Processing for details of sample rules delivered with Banner UCAS.

Banner UCAS support for inconsistent HESA requirements

Several inconsistencies exist between HESA and UCAS requirements. The following table describes these inconsistencies and the manner in which Banner UCAS accommodates HESA reporting.

Inconsistency Resolution
Gender identification
On the UCAS Admissions Guide 2015, the question is defined as, "State if their gender identity is different to the sex they were assumed to be at birth." HESA defines the Gender Identification data item as, "Students should, according to their own self-assessment, indicate if their gender identity is the SAME as the gender originally assigned to them at birth." The UCAS application has another question that asks, "Do you identify as transgender?"

Some institutions do not consider this to be the same information as what is required by HESA. This has been escalated to HESA, who have confirmed that they have similar concerns. For these institutions, the Apply field value does not appear in the StarJ transaction because it does not correspond to the question in their record, nor do they validate the GENDERID field using the StarJ data.

Banner updates the Gender Identity field on the Supplemental General Person Information (SKASPIN) page and this is used in the HESA return.

 The UCAS Gender Identity field is included on the Admissions Processing tab of the Supplemental Applicant Information (SKASAIN) page. If desired, you can mask this field from being displayed on the page.

Use the GENIDEN parameter on the System Parameter Maintenance (GKAKSYS) page to specify which page field (SKASAIN, SKASPIN, both, or neither) is to be updated by Banner UCAS.

If you choose to use SKASAIN instead of SKASPIN, you can run the optional optional_mig_genderid_080802.sql script included with the 8.8.2 release to move Gender Identity data from SKASPIN to SKASAIN for 2015 applicants only.
Religion or belief
For institutions in Scotland or Northern Ireland, code 03 - Christian, is not valid for the HESA Student RELBLF field. Instead, institutions in Scotland must use codes 04,05 or 09 and clients in Northern Ireland must use codes 04 through 09 for different denominations of Christianity and will receive a validation error when using a 03 code for this field.

UCAS only have code 03 for Christianity in the ReligionBelief reference method. Therefore, institutions in Scotland and Northern Ireland need to obtain this data from a source other than UCAS so that the level of detail required by HESA can be stored.

Banner stores the religion code from UCAS in SPAPERS, but this field is also used in the HESA Student return.

 The UCAS Religion field is included on the Admissions Processing tab of SKASAIN. If desired, you can mask this field from being displayed on the page.

Use the RELGBEL parameter on GKAKSYS to specify which page’s field (SKASAIN, SPAPERS, both, or neither) is to be updated by Banner UCAS.

If you choose to use SKASAIN instead of SPAPERS, you can run the optional optional_mig_religion_080802.sql script included with the 8.8.2 release to move Religion data from SKASPIN to SPAPERS for 2015 applicants only.
Sexual orientation
Some institutions consider that the sexual orientation data from UCAS is not reliable and want to keep it separate from the data used in the HESA Student return.

Banner stores the sexual orientation code from UCAS in SKASPIN, but this field is also used in the HESA Student return.

 The UCAS Sexual Orientation field is included on the Admissions Processing tab of SKASAIN. If desired, you can mask this field from being displayed on the page.

Use the SEXORINT parameter on GKAKSYS to specify which page’s field (SKASAIN, SKASPIN, both, or neither) is to be updated by Banner UCAS.

If you choose to use SKASAIN instead of SKASPIN, you can run the optional optional_mig_sexort_080802.sql script included with this release to move Sexual Orientation data from SKASPIN to SKASAIN for 2015 applicants only.

Set up the XML-Link connection

The procedures in this section must be performed to use XML-Link to transfer data to and from Banner UCAS.

To support XML-Link, the Banner UCAS module uses Banner Web Service Interface Client (WINC) and the XML Import Engine (XIGN 8.1).

XIGN is used with WINC to fetch data from XML-link, which presents data from a Web-Service Description Language (WSDL) document. WINC is a Web Service client that can connect to a Web Service that presents itself using a WSDL document. It invokes operations exposed by such a Web Service and downloads the data in SOAP format. It then extracts the body portion of it, and parses and creates a DOM object. This DOM object is then passed to XIGN to process and save into a series of temporary tables.

Refer to these products' Use content and Reference content for complete information about them.

The seed data delivered with WINC provides the records used to define the Web Service and its operations for both production and test XML-Link connections. When the seed data scripts are run, you input the three-digit UCAS institution code (for example, Z89) with which you want to connect to XML-Link. If you operate joint admissions processing, you must run the scripts a second time for each institution code. The resulting seed data will then contain the institution code as part of the code for each element in SC_XL_ANN_XYZ format for the XML-Link production system or SC_XLT2_ANN_XYZ for the XML-Link test system, where ANN represents your institution code and XYZ represents the identifier for that element.

Note: You do NOT need to import the WSDL files for XML-Link manually on the GKAWSDE page, as the seed data does this for you. However, you need to enter the location for the Oracle Wallet which contains the digital certificate for XML-Link, as discussed in the following section.

The rest of this section provides the following step-by-step procedures for setting up your XLM-Link connection.

Set up the Access Control List (ACL)

You must set up the ACL for each UCAS XML-Link URL to which you want to connect (that is, test and production). If the ACL is not defined, you are likely to see the following error message.

Error while invoking SOAP request: ORA-24247: network access denied by access control list (ACL).

This is a technical task for a DBA/system administrator. Support for this task including a script to create the ACL can be obtained by contacting the Ellucian Support Center.

Timestamps on a number of records from UCAS have proved to be unreliable, as the timestamp actually represents the time of the record change, but not when this change is published on XML link.

About this task

This can cause records to be missed from downloads, as there is sometimes a lag between the timestamp time and the time that the specific record appears on XML link. This feature allows clients to change the download logic so that the next web service call can select records earlier than the last web service call based on the number of seconds set in this parameter. The next web service call would then download records affected by the timestamp lag.

Download behaviour

If a single applicant is downloaded, the WINC processing functionality will download the current data from all applicant-specific methods regardless of the timestamp and whether the same records have already been downloaded (it will provide a snapshot of all current data held on the UCAS database for a specific applicant).

Download timestamps are not updated when the details of a single applicant are downloaded. As a result, any new downloaded records will be downloaded a second time whenever a full download for a specific method is performed.

When downloading data from XML-link, the following occur.

  • The system checks the database timestamps of all the rows in the XML-Link methods that are set to Executable.
  • All of the rows in the XML-Link methods that are set to Executable and have a database timestamp that is later than the timestamp in Banner are downloaded to Banner PRGNREP staging tables.
  • MDUU rules are run to transfer the data from the PRGNREP staging tables to the Banner interim tables.

    When the MDUU rules are run, Banner finds all new applicant records waiting to be processed into the interim tables that do not already exist in SKRSAIN or SKBUGAN. Then it generates an applicant number for each of the new applicant records and stores them in SKBUGAN. A sequence is used while generating Direct, UCAS, and UTT applicant numbers. Banner appends the prefix, suffix or both defined in the APPNO PREFIX and APPNO SUFFIX system parameters to the generated applicant number for UCAS and UTT applicants.

    The number generated by Banner is nine characters. This ensures that the sequence is padded with zeros up to nine characters.

    For example, if G is the designated prefix, the following applicant numbers would be the first ones generated:
    • G00000001
    • G00000002

      If X is the designated suffix, the following applicant numbers would be the first ones generated:

    • 00000001X
    • 00000002X

      If A is the designated prefix and Z is the designated suffix, the following applicant numbers would be the first ones generated:

    • A0000001Z
    • A0000002Z
  • The data in the PRGNREP staging tables is deleted.

    When data is received from the XML-link methods, new records will be inserted and existing records will be updated in the Banner interim tables.

New records are inserted into SKBUSTN and SKBUSTA only if there are changes to name or address data.

The following methods provide the data to go into SKBUSTK for UCAS applicants:
  • getUCASApplicantsDetails (SKBXUAD)
  • getUCASApplicantsStatus (SKBXUST)
  • getUCASApplicantsBackground (SKBXUAB)
  • getUCASApplicantAnswers (SKBXUAN)

A new SKBUSTK record is inserted when a new record is downloaded from getUCASApplicantDetails, but when new records are downloaded from any of the other methods they update only the latest SKBUSTK record. If a new SKBUSTK record is created and there are no new Status, Background, or Answers records, any data that should come from those records will be taken from the previous SKBUSTK record. It is recommended that you always download all these methods and not just the primary Details method.

Similarly, the following methods provide the data to go into SKBUSTG:
  • getGTTRApplicantChoices (SKBXGCH)
  • getGTTRApplicantDetails (SKBXGAD)

A new SKBUSTG record is inserted when a new record is downloaded from getGTTRApplicantChoices, but when new records are downloaded from getGTTRApplicantDetails they update only the latest SKBUSTG record. If a new SKBUSTG record is created and there is no new Details record, any data that should come from there will be taken from the previous SKBUSTG record. It is recommended that you always download both these methods and not just the primary Choices method.

  • getUCASApplicantEducation
  • getUCASApplicantQualifications
  • getUCASApplicantsEmployment
  • getGTTRApplicantEducation
  • getGTTRApplicantQualifications
  • getGTTRApplicantsOtherLanguages
  • getReferenceSchoolContacts methods

    The getReferenceResultsRefreshControl method is always downloaded regardless of the timestamp value, even when not selected, because it contains flags indicating whether the results methods (getUCASResultsMatchStatus, getUCASApplicantsResults, and getUCASUnitResults) are being refreshed. The flags tell Banner whether to try to download from these methods.

When ABL results (*PQR) data is downloaded from the getUCASApplicantsResults method, Banner will always first download the getUCASResultsMatchStatus method to identify which applicants have new or changed results records. The system uses the XMLLINK RESULTS DOWNLOAD LIMIT system parameter to determine whether to download individual results on an applicant by applicant basis or as a mass download of all results, according to the number of applicants for whom changed result data is available.

The default is to download results individually, but when results for a large number of applicants (typically several thousand) are available, it is necessary to download all results because it is quicker to do that than to selectively download only changed ones.

Upload Banner rows into UCAS using XML-Link

The XML-Link Upload tab on the UCAS Data Processing (SKAUHPR) page is used to define the upload settings, and to access and view the upload data.

About this task

Transactions (decisions and enquiries) entered on the UCAS Decision (SKAUDEC) and the UCAS Multiple Transaction Maintenance (SKAUMLT) forms are stored in the Tranin Copy View (SKBUTIN) tab; before being uploaded to UCAS using the XML-Link Set methods. Transactions are stored in the SKBUTIN table with the appropriate institution code, and records with a status of NS (Not Sent) are uploaded to XML-Link for the correct institution.

When a record is selected for upload, the SKBUTIN processing status (SKBUTIN_PROC_STATUS) is changed from NS (Not Sent) to IP (In Progress). When the record has been acknowledged by UCAS (that is, when the UCASResponse method is downloaded), the processing status is set to RE (Received) whether or not an error was returned. In addition, the transaction status (SKRUDEC_TRANS_STATUS) is changed to PE (Pending).

If a record fails to upload to UCAS, the SKBUTIN processing status remains as IP. The reason for the failure is logged by WINC and can be viewed on GKAWLOG.

When the upload is performed, any SKBUTIN records with a processing status of IP are reset to NS. If the Set method for the transaction type was selected, the system attempts to upload the record again. If the Set method for the transaction type was not selected, the system will attempt to upload the record the next time the Set method is selected.

If the record failed to upload because there were characters in the Marvin offer text that cannot be processed through an XML message, this must be corrected in the table. Special characters include Unicode characters (such as " & < > £ and €) and accented characters. You can do one of the following:
  • Correct the offer text in SKBUTIN_FREEFORMAT to remove any accents or special characters, reset PROC_STATUS IP to NS, and send again.
  • Set the processing status of the SKBUTIN record to IG, delete the SKRUDEC record, set SKRUCCR_OUTSTANDINGDECN_IND to null for the choice, and then reenter the decision including the corrected offer text through SKAUMLT or SKAUDEC.

Errors returned are stored in SKBUTIN_ERRORCODE and SKBUTIN_ERROR_MSG. UCASResponse method is returned by XML-Link immediately on receipt of a transaction by a Set method. The UCASResponse results are displayed in the Upload Summary tab.

Procedure

  1. Access the UCAS Data Processing (SKAUHPR) page.
  2. Enter the institution code if you want to process data for the entire institution, or enter the applicant number if you want to process data for an individual applicant, then go to the next block.
  3. Go to the XML-Link Upload tab.
  4. Upload the methods either automatically or manually, as follows.
    1. If you want to upload methods automatically, perform the following steps.
      • Select the Auto check box for each method that you want to upload.

        This can also be set on GKAWSPR.

      • Save your changes.
      • Run SKPUHER either from the Job Submission (GJAPCTL) page or through a cron job set up to run automatically on a periodic basis.
    2. If you want to upload methods manually, perform the following steps.
      • Select the Run Now check box for each method that you want to upload.

        This can also be set on GKAWSPR.

      • Save your changes.
      • Select Upload XML-Link Data from the Options menu.
      • When the XML-Link Upload Launch Parameters window is displayed, click Run Now.
      • Accept the default ‘Log and Continue’ Web Service Process Exception Mode unless advised otherwise by Ellucian.

        This ensures that any errors encountered during the download are logged and all successful downloads are committed to the database.

        Warning: The 'Log and continue with SOAP message' web service process exception mode should be used only as a last resort and under guidance from Ellucian when problems occur with a particular download. It should never be used in day-to-day processing and should be avoided if downloading large numbers of records.
        The data is uploaded.
  5. When the upload is finished, click Cancel/Exit to exit the XML-Link Upload Launch Parameters window.
  6. After the upload, review the Upload Summary tab as described in Review upload details.
  7. If you want to delete the upload summary details, select Delete XML-Link Upload Summary Details from the Options menu.

  3. If applicable, enter the necessary information in the Transactions block.
  4. If applicable, enter the necessary information in the Change Details block.

    If any records fail to store, an error message is displayed, the record is rolled back to its previous state, and the commit process moves on to the next record. This can occur, for example, if there is a fatal curriculum error and it ensures that other records are still stored.

    If your institution is a UCAS Teacher Training (UTT) institution, you might receive applicant choices for schools for which you are the accrediting provider. These choices contain the institution code of the school, but you can enter decisions for them.

    When you save the decision on SKAUMLT, the system saves the decision against the primary institution (the HEI/Accrediting provider) so that it can be returned to UCAS with all the decisions for your own institution choices, without the need for separate XML-Link accounts for each school.

    Banner enforces UCAS business rules so that you can choose only the transaction types and decisions that are valid for a particular applicant choice, based on the previous decision and the reply if applicable. Banner also validates the Marvin codes used in offers according to UCAS business process rules.

    Abbreviations for use in Marvin offer strings are stored in the SKVUABR table and can be viewed on the UCAS Abbreviations (SKAUABR) page. Grade codes are stored in SKVSSDT (the Value Mapping and List-of-Value Definition (SKASSDT) page), entity GRDECODE, attribute UCAS GRADE CODES. Process duplicate clearing applicants

The UCAS Duplicate Maintenance (SKAUHDP) page is used after running the deduplication process on data received from UCAS.

About this task

This procedure allows you to select and process clearing applicants who have outstanding potential duplicates. If a match is selected on SKAUHDP, the process that loads the UCAS data into Banner merges the existing applicant details and the new UCAS details into a single applicant number.

During Clearing, it is recommended that you set the DEDUP MATCH APPLICANT system parameter to Y. The setting defines whether the deduplication process will automatically flag an applicant as a duplicate when the personal ID entered in SKAUCLR matches an existing personal ID in Banner. This guards against the possibility that the applicant has provided the wrong personal ID. Although very unlikely, if this were to happen, the UCAS records received will have name, address, and personal details that differ from the original clearing applicant. If this is not “trapped” as a potential duplicate using this parameter, the personal details of your original clearing applicant will be replaced by those of the new applicant.

The DEDUP MATCH APPLICANT parameter should be set to N when not in the clearing period.

Procedure

  1. Access the UCAS Duplicate Maintenance (SKAUHDP) page.
  2. Select an applicant in the Applicant field.

    If an existing Clearing choice record is found for a potential match, the Clearing button is active. You can click the button to open a canvas where you can compare the incoming data with the data already in Banner.

  3. If there is an ID in the Banner Student Production Data block that matches the selected applicant, select the Match check box.
  4. Repeat this process for the remaining applicants listed on the Received Data From UCAS block.
  5. Save the record, which will process the applicants, and merge applicant details if necessary.
