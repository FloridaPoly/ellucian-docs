UPDATE IF NULL

IGNOR		 Indicates what can be updated when a *J record is processed. If UPDATE, then the current value is always updated with the *J value. If UPDATE IF NULL, then the current value is only updated if it is a null value. If IGNORE, then the current value is never updated.

If the UCAS details are stored on both the SKRSAIN and SKBHINS tables, the relevant parameter refers to both tables.

The system parameters that affect storage to both SKRSAIN and SKBHINS (for example, *J - DOMICILE) behave as follows.

Each system parameter can have a value of UPDATE, UPDATE IF NULL, or IGNORE.

  • If the system parameter is set to UPDATE, the system checks the value of the *J UPDATES RULE parameter. If this is set to SKBHINS, the system updates only the SKBHINS columns with the *J data. If this is set to SKRSAIN, the system updates only the SKRSAIN columns with the *J data. If this is set to BOTH, the system updates both SKBHINS and SKRSAIN columns.
  • If the system parameter is set to UPDATE IF NULL, the system checks the value of the *J UPDATES RULE parameter. If this is set to SKBHINS, the system checks whether SKBHINS data exists and updates the SKBHINS column only if no data already exists. It does not update SKRSAIN. If this is set to SKRSAIN, the system checks whether SKRSAIN data exists and updates the SKRSAIN column only if no data already exists. It does not update SKBHINS. If this is set to BOTH, the system checks whether SKBHINS data exists and updates the SKBHINS column only if no data already exists. It also checks whether SKRSAIN data exists and updates the SKRSAIN column only if no data exists.
  • If the system parameter is set to IGNORE, the existing data will not be updated by the data in SKBUSTJ.

DEDUP MATCH APPLICANT Y/N Specifies whether the deduplication process will automatically flag an applicant as a duplicate when the personal ID entered by the user in SKAUCLR matches an existing personal ID in Banner.

Valid values are Y (Yes) and N (No).

You should consider setting this parameter to Y if your institution creates applicant details in the SKAUCLR page using the personal ID and name provided by the applicant during the clearing period. This guards against the possibility that the applicant has provided the wrong personal ID. Although very unlikely, if this were to happen, the XML-Link records received following a clearing decision will have name, address, and personal details that differ from the original clearing applicant. If this is not ‘trapped’ as a potential duplicate using this parameter, the personal details of your original clearing applicant will be replaced by those of the new applicant.

This parameter should be set to N when not in the clearing period.

This parameter can hold multiple institution codes in cases where your institution is processing decisions for joint admissions entities. Separate usernames and passwords for XML-Link are required for each institution defined in the parameter. All institution codes should be delimited by commas with the primary institution being first in the list.

The UCAS course structure defined within the Banner UCAS module will not support multiple occurrences of the same UCAS course code across different admissions entities. This does not allow any differentiation between course codes across multiple admissions entities. If any client has a need to support the same course code across different admissions entities, each leading to a different Banner program, this can be supported by use of multiple SKRUTOP records for the same course but different campus codes. This functionality already exists in the Banner UCAS module.
