USI Processing

The SKKAUSI package in AVETMISS Reporting contain all functions and procedures used in USI processing. This section provides details on how the USI processes work, referring to functions and procedures in the SKKAUSI package.

Related concepts
  • Unique Student Identifier

Create USI

The CreateUSI web service may be invoked in real time when a record is saved in the Additional ID Verification (GKAADIV) page with no value for the Additional Identification field and an ID Type of 'USI'.

The web service will only be invoked if the value of the USI-REAL-TIME system parameter is set to either B or F in the Report System Parameters (SKARSYS) page.

A new trigger has been added to the GKRADIV table called GT_GKRADIV_BIU_ROW and that trigger invokes the p_createusi_realtime procedure provided the following conditions are satisfied:
  • GKRADIV_CONSENT = 'Y'
  • GKRADIV_ADID_CODE = 'USI'
  • GKRADIV_VERIFIED_DATE IS NULL
  • GKRADIV_SOURCE != 'WEB SERVICE' (This condition is written to avoid the trigger from firing CreateUSI when a record is updated into GKRADIV through BulkUploadRetrieve or BulkVerify responses.)
Also, if any request is already existing in SKRRQST with the status as PENDING then that request status is updated to EXPIRED through the procedure p_set_status_expired_failed so that a fresh web service request can be sent and then the following conditions are checked before invoking the CreateUSI Web service.
  • There is currently no record in the Request Collector table (SKRRQST) for this PIDM, for a USI request where the status is either PENDING or RECEIVED
  • Either GKRADIV_DOC_VERIFICATION_IND = 'N' or GKRADIV_DOC_VERIFICATION_IND = 'Y' and there is an appropriate active and primary record in GKRVDOC for the person

When a record gets inserted to GKRADIV through the GKAADIV page then Data Origin will be stored in the GKRADIV table as 'Banner' and when a record gets inserted through self-service then Data Origin will be stored into GKRADIV table as 'SELF-SERVICE'.

Hence CreateUSI will be invoked if the value for the 'USI-REAL-TIME' system parameter is either B (Both page and Self-Service) or it will be invoked if the value is F (only page) and the Data Origin is 'Banner'.

SKKAUSI.P_SKTCUSI_INSERT

When a record is created through the GKAADIV page, if :NEW.gkradiv_additional_id IS NULL then a procedure is called which will insert that GKRADIV record into a temporary table SKTCUSI through the procedure skkausi.p_sktcusi_insert.

This is required because the MDUU activity ASC_CREATE_USI will fetch values for Contact Method and Document Verification Indicator from SKTCUSI table. Because the web service invocation is happening on the 'before insert' trigger, the values will not yet be in the GKRADIV table and hence these details are stored in the temporary table SKTCUSI so that the MDUU activity can pick it up from there.

After this step, the procedure skkausi.p_createusi_realtime is called.

SKKAUSI.P_CREATEUSI_REALTIME

skkausi.p_createusi_realtime(:NEW.gkradiv_pidm,lv_additional_id_out);

It has two parameters. The first parameter is the PIDM which is passed into this procedure from the trigger and the second parameter is the USI (Additional_ID) which is an out parameter. If the result of a real time CreateUSI web service is SUCCESS or MATCH FOUND then lv_additional_id_out will contain the USI created for that student and this will be stored in the GKRADIV table.

This procedure is created as a pragma autonomous transaction because we have commit/rollback written inside this procedure and as per Oracle's restriction the code inside the trigger or the code which is called inside the trigger GT_GKRADIV_BIU_ROW cannot have a commit/rollback. To overcome this restriction we have created this procedure as a pragma autonomous transaction. This same reasoning holds good for other procedures that are created as pragma autonomous transactions and written inside the SKKAUSI package.

The first step in this procedure is to get the value of skbsusi_create_usi_url. This field is present in the USI tab of the External Systems Interaction Control page (SKASYSC). If the URL is not present then an exception is raised and a record is inserted into the Request Exceptions table (SKREXPT) with the message "CreateUSI URL details are not available on USI tab of SKASYSC page." This record can be viewed on the Request Exceptions page (SKAEXPT).

If the URL is present, then the procedure SKKAUSI.p_createusi_internal is called.

SKKAUSI.P_CREATEUSI_INTERNAL

SKKAUSI.p_createusi_internal( p_pidm_in , p_request_id_out, p_gkrrlog_seqno_out);

It has one IN parameter (PIDM) and two OUT parameters Request ID and gkrrlog_seqno.

The first parameter is the PIDM which is passed into this procedure from the skkausi.p_createusi_realtime procedure.

The second parameter is the Request ID that is generated using the value of the skbsusi_request_prefix concatenated with the organisation code concatenated with a sequence number.

The request prefix is present in the USI tab of SKASYSC.

The organisation code is the value from the Training Organisation ID field on the Organisation Details page (SKATORG) for the Banner ID of the organisation that is present in the USI tab of SKASYSC.

The sequence number is an Oracle sequence.

The third parameter is the sequence number from the MDUU log table (GKRRLOG) for the CreateUSI MDUU process.

The process code is present in the USI tab of SKASYSC.

This skkausi.p_createusi_internal procedure inserts a record into the SKRTRNS table, and the SKRRQST table and executes the CreateUSI MDUU process to populate the SKSCUSI table.

Control is then passed back to the skkausi.p_createusi_realtime procedure.

SKKAUSI.P_CREATEUSI_REALTIME

The skkausi.p_createusi_realtime procedure builds the CreateUSI request XML using the data in the SKSCUSI table and sends the request to the USI system.

When the CreateUSI response is received back from the USI system, the procedure SKKAUSI.p_process_createusi_response is called.

SKKAUSI.P_PROCESS_CREATEUSI_RESPONSE

If the CreateUSI response does not include any 'ErrorMessage' node, then the XIGN process ASC_USI_CREATE_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXCUSI table.

The procedure SKKAUSI.p_create_usi_response is called.

If the CreateUSI response includes an 'ErrorMessage' node, then the XIGN process ASC_USI_CREATE_FAULT_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXCUSI table.

The procedure SKKAUSI.p_create_usi_response_fault is called.

SKKAUSI.P_CREATE_USI_RESPONSE

If the result of the CreateUSI request is either Success or MatchFound.

The generated USI is used to update the Additional ID Verification table (GKRADIV), the Status is updated to 'SUCCESS' and the Verification Date is populated.

A record is inserted into the Additional Identification table (GORADID).

The corresponding request records in SKSCUSI, SKRRSQT and SKRTRNS are updated with the status of SUCCESS

A record is inserted into the SKRSTRN table for the PIDM.

If the value of the GKRVDOC-PURGE system parameter is 'A', then all records for the person are purged from the Identity Document Details table (GKRVDOC).

If the value of the GKRVDOC-PURGE system parameter is 'P', then the primary record for the person is purged from the Identity Document Details table (GKRVDOC).

If the result of the CreateUSI request is Failure:

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE'.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSCUSI, SKRRSQT and SKRTRNS are updated with the status of COMPLETE

SKKAUSI.P_CREATE_USI_RESPONSE_FAULT

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE'.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSCUSI, SKRRSQT and SKRTRNS are updated with the status of SOAPFAULT.

If there is any problem in executing SKKAUSI.p_create_usi_response_fault, the SKKAUSI.p_set_status_expired_failed procedure is called.

SKKAUSI.P_SET_STATUS_EXPIRED_FAILED

This procedure sets the status of pending requests to EXPIRED in the SKSCUSI, SKRRQST and SKRTRNS tables.

A record is inserted into the Request Exceptions table (SKREXPT).

Bulk Upload

This section discusses the bulk upload processing activities.

SKKAUSI.P_BULKUPLOAD_SCHEDULER

SKKAUSI.P_BULKUPLOAD_SCHEDULER is the procedure that gets invoked through an Oracle job that is scheduled every day.

First, the procedure gets the count of rows in GKRADIV that need to have a USI requested

These will be records in GKRADIV that match the following conditions:

GKRADIV_ADID_CODE = 'USI'

GKRADIV_ADDTIONAL_ID is null

GKRADIV_CONSENT_IND = 'Y'

GKRADIV_VERIFIED_DATE is null

There is currently no record in the Request Collector table (SKRRQST) for this PIDM, for a USI request where the status is either PENDING or RECEIVED

Either GKRADIV_DOC_VERIFICATION_IND = 'N' or GKRADIV_DOC_VERIFICATION_IND = 'Y' and there is an appropriate record in GKRVDOC for the person

The purpose of the count is so that the process can determine how many BulkUpload requests need to be sent.

The process gets the URL for BulkUpload requests and the Maximum Number of Records in a BulkUpload Request data from SKBSUSI.

Next skkausi.p_BulkUpload gets the Training Organisation ID for the non-person ID on the USI tab of SKASYSC. The cursor finds the SKBTORG_TRAIN_ORG_ID from the Organisation Details table (SKBTORG) where the SKBTORG_PIDM matches the SKBSUSI_PIDM, and uses the record from SKBTORG that is the latest record (maximum effective term) where the Training Organisation Indicator (SKBTORG_TRAIN_ORG_IND) = 'Y'.

This Training Organisation ID is used for the OrgCode element in the BulkUpload request.

If any of the required data from SKBSUSI is missing, then the request cannot be created

A row is inserted into SKRTRNS with the Request ID of BULKUPLOADDATAnnn (where nnn is a sequence) and with a SKRTRNS_STATUS_MESSAGE of 'BulkUpload data is not available on USI tab of SKASYSC page.'

If no Training Organisation ID is found, then the request cannot actually be created.

A row is inserted into SKRTRNS with the Request ID of ORGCODEnnn (where nnn is a sequence) and with a SKRTRNS_STATUS_MESSAGE of 'Organisation Code details are not maintained on SKASYSC/SKATORG page.'

Next the skkausi.p_BulkUpload is called.

SKKAUSI.P_BULKUPLOAD

SKKAUSI.p_BulkUpload (p_gkrrlog_seqno_out);

It has one OUT parameter - gkrrlog_seqno.

This parameter is the sequence number from the MDUU log table (GKRRLOG) for the BulkUpload MDUU process.

The process code is present in the USI tab of SKASYSC.

A request ID is generated for each set of records, up to the maximum number of records in a bulk upload request, until all of the PIDMs are covered by a request

A row for the request ID is inserted into SKRTRNS

PIDMs are allocated to the request ID, up to the maximum for bulk upload requests and rows are inserted into SKRRQST for each PIDM for the request ID.

The process loops through these SKRTRNS and SKRRQST steps until each PIDM has been allocated to a request.

The procedure also executes the BulkUpload MDUU process to populate the SKSBUSI table.

If the MDUU activity encounters an error, then the details are written to the GKRRLOG table, the status of the relevant request records in SKRTRNS and SKRRQST are set to 'EXPIRED' and a record is inserted into the Request Exceptions table (SKREXPT) for each PIDM in the request, with the following message 'Error during execution of BulkUpload: %01%' - where %01% will be the error message that was also written to GKRRLOG.

If the MDUU activity was able to successfully populate the SKSBUSI target table, control is then passed back to the skkausi.p_bulkupload_scheduler procedure.

SKKAUSI.P_BULKUPLOAD_SCHEDULER

The skkausi.p_bulkupload_scheduler procedure builds the BulkUpload request XML using the data in the SKSBUSI table and sends the request to the USI system.

If the XML cannot be created, then a record is inserted into the Request Exceptions table (SKREXPT) for each PIDM in the request, with the following message 'No data is available for processing in MDUU table.'

When the BulkUpload response is received back from the USI system, the procedure SKKAUSI.p_process_bulkupload_response is called.

SKKAUSI.P_PROCESS_BULKUPLOAD_RESPONSE

If the BulkUpload response does not include any 'ErrorMessage' node, then the XIGN process ASC_USI_BULK_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXBUSI table.

The procedure SKKAUSI.p_bulk_upload_response is called.

If the BulkUpload response includes an 'ErrorMessage' node, then the XIGN process ASC_USI_BULK_FAULT_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXBUSI table.

The procedure SKKAUSI.p_bulk_upload_response_fault is called.

SKKAUSI.P_BULK_UPLOAD_RESPONSE

The corresponding request records in SKSBUSI, SKRRSQT and SKRTRNS are updated with the status of RECEIVED and the Receipt ID in each of these tables is populated.

SKKAUSI.P_BULK_UPLOAD_RESPONSE_FAULT

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSBUSI, SKRRSQT and SKRTRNS are updated with the status of SOAPFAULT.

If there is any problem in executing SKKAUSI.p_bulk_upload_response_fault, the SKKAUSI.p_set_status_expired_failed procedure is called.

SKKAUSI.P_SET_STATUS_EXPIRED_FAILED

This procedure sets the status of pending requests to EXPIRED in the SKSBUSI, SKRRQST and SKRTRNS tables.

A record is inserted into the Request Exceptions table (SKREXPT).

Bulk Upload Response Retrieve

SKKAUSI.P_BULKUPDRET_SCHEDULER is the procedure that gets invoked through an Oracle job that is scheduled every day.

It fetches skbsusi_bulk_retrieve_hours and skbsusi_bulk_retrieve_url, which are stored in the USI tab of the SKASYSC page. If any of them is null then it inserts a record into SKRTRNS(The Transactions Data Table) with the message 'BULK UPLOAD RETRIEVE data is not available on USI tab of SKASYSC page'.

At the time that the BulkUploadRetrieve request job is scheduled to run, one of the first steps it does is to check all the BulkUploadRequests that are due to get their results retrieved.

For each of those BulkUpload request IDs, the process checks the timestamp of the bulk upload request.

It adds the Number of Hours Before Sending Bulk Upload Retrieve to the bulk upload request timestamp for each request.

Then, if the system date and time is greater than this calculation of "Number of Hours Before Sending Bulk Upload Retrieve plus bulk upload request timestamp", the corresponding BulkUploadRetrieve request will be sent.

If the results are not ready, then the USI Registry system will send a "Not ready yet" BulkUploadRetrieve response and another BulkUploadRetrieve request will be sent at the next time that the BulkUploadRetrieve job is scheduled.

Banner will keep sending BulkUploadRetrieve requests in this way until a terminating BulkUploadRetrieve response is received.

That terminating BulkUploadRetrieve response might be success or it might be failure - but it will be a definite response (as opposed to "Not ready yet").

When the bulk upload retrieve response is received back from the USI system, the procedure SKKAUSI.p_process_bulkupdret_response is called.

SKKAUSI.P_PROCESS_BULKUPDRET_RESPONSE

If the bulk upload retrieve response does not include any 'ErrorMessage' node, then the XIGN process ASC_USI_BULKRETRIEVE_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXRUSI table.

The procedure SKKAUSI.p_bulkupload_retrieve_response is called.

If the bulk upload retrieve response includes an 'ErrorMessage' node, then the XIGN process ASC_USI_BLKRETRIEVE_FAULT_RESP will be executed.

The response XML is parsed and data is populated into the SKXRUSI table.

The procedure SKKAUSI.p_bulk_retrieve_res_fault is called.

SKKAUSI.P_BULKUPLOAD_RETRIEVE_RESPONSE

If the result of the bulk upload retrieve response USI request is either Success or MatchFound.

The generated USI is used to update the Additional ID Verification table (GKRADIV), the Status is updated to 'SUCCESS' and the Verification Date is populated.

A record is inserted into the Additional Identification table (GORADID).

The corresponding request records in SKSBUSI, SKRRSQT and SKRTRNS are updated with the status of SUCCESS

A record is inserted into the SKRSTRN table for the PIDM.

If the value of the GKRVDOC-PURGE system parameter is 'A', then all records for the person are purged from the Identity Document Details table (GKRVDOC).

If the value of the GKRVDOC-PURGE system parameter is 'P', then the primary record for the person is purged from the Identity Document Details table (GKRVDOC).

If the result of the CreateUSI request is Failure:

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE'.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSBUSI, SKRRSQT and SKRTRNS are updated with the status of COMPLETE

SKKAUSI. P_BULK_RETRIEVE_RES_FAULT

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE'.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSBUSI, SKRRSQT and SKRTRNS are updated with the status of SOAPFAULT.

If there is any problem in executing SKKAUSI.p_bulk_retrieve_res_fault, the procedure SKKAUSI. p_bulkupload_ret_status is called.

SKKAUSI. P_BULKUPLOAD_RET_STATUS

This procedure sets the status of pending requests to EXPIRED in the SKSBUSI, SKRRQST and SKRTRNS tables.

A record is inserted into the Request Exceptions table (SKREXPT).

Verify USI

The VerifyUSI web service may be invoked in real time when a record is saved in the Additional ID Verification (GKAADIV) page with a value entered for the Additional Identification field and with an ID Type of 'USI'.

The web service will only be invoked if the value of the USI-REAL-TIME system parameter is set to either B or F in the Report System Parameters (SKARSYS) page.

A new trigger has been added to the GKRADIV table called GT_GKRADIV_BIU_ROW and that trigger invokes the procedure p_verifyusi_realtime provided the following conditions are satisfied:
  • GKRADIV_CONSENT = 'Y'
  • GKRADIV_ADID_CODE = 'USI'
  • GKRADIV_VERIFIED_DATE IS NULL
  • GKRADIV_SOURCE != 'WEB SERVICE' (This condition is written to avoid the trigger from firing VerifyUSI when a record is updated into GKRADIV through BulkUploadRetrieve or BulkVerify responses.)
Also if any request is already existing in SKRRQST with the status as PENDING then that request status is updated to EXPIRED through the procedure p_set_status_expired_failed so that a fresh web service request can be sent and then the following conditions are checked before invoking the VerifyUSI web service.
  • There is currently no record in the Request Collector table (SKRRQST) for this PIDM, for a USI request where the status is either PENDING or RECEIVED
  • When a record gets inserted to GKRADIV through the GKAADIV page then Data Origin will be stored in the GKRADIV table as 'Banner' and when a record gets inserted through self-service then Data Origin will be stored into GKRADIV table as 'SELF-SERVICE'.

Hence VerifyUSI will be invoked if the value for the 'USI-REAL-TIME' system parameter is either B (Both page and Self-Service) or it will be invoked if the value is F (only page) and the Data Origin is 'Banner' or it will be invoked if the value is S (only Self-Service) and the Data Origin is 'SELF-SERVICE'.

SKKAUSI.P_SKTVUSI_INSERT

When a record is created through GKAADIV page, if :NEW.gkradiv_additional_id IS NOT NULL then a procedure is called which will insert that GKRADIV record into a temporary table SKTVUSI through the procedure skkausi.p_sktvusi_insert.

This is required because the MDUU activity ASC_VERIFY_USI will fetch values for the USI field from the SKTVUSI table. Because the web service invocation is happening on the 'before insert' trigger the values will not yet be in the GKRADIV table and hence this detail is stored in the temporary table SKTVUSI so that the MDUU activity can pick it up from there.

After this step the procedure skkausi.p_verifyusi_realtime is called.

SKKAUSI.P_VERIFYUSI_REALTIME

skkausi.p_verifyusi_realtime(:NEW.gkradiv_pidm,lv_status_code_out,lv_request_id_out);

It has three parameters. The first parameter is the PIDM which is passed into this procedure from the trigger and the second parameter is the USI STATUS which is an out parameter and it contains values like VALID or INVALID or DEACTIVATED or it can be null. If it is null then it means there was some issue while invoking a web service request.

The first step in this procedure is to get the value of skbsusi_verify_usi_url. This field is present in the USI tab of the External Systems Interaction Control (SKASYSC) page. If the URL is not present then an exception is raised and a record is inserted into the Request Exceptions table (SKREXPT) with the message VerifyUSI URL details are not available on USI tab of SKASYSC page. This record can be viewed on the Request Exceptions (SKAEXPT) page.

If the URL is present then the procedure SKKAUSI.p_verifyusi_internal is called.

SKKAUSI.P_VERIFYUSI_INTERNAL

SKKAUSI.p_verifyusi_internal( p_pidm_in , p_request_id_out, p_gkrrlog_seqno_out);

It has one IN parameter (PIDM) and two OUT parameters Request ID and gkrrlog_seqno.

The first parameter is the PIDM which is passed into this procedure from the skkausi.p_verifyusi_realtime procedure.

The second parameter is the Request ID that is generated using the value of the skbsusi_request_prefix concatenated with the organisation code concatenated with a sequence number.

The request prefix is present in the USI tab of SKASYSC.

The organisation code is the value from the Training Organisation ID field on the Organisation Details (SKATORG) page for the Banner ID of the organisation that is present in the USI tab of SKASYSC.

The sequence number is an Oracle sequence.

The third parameter is the sequence number from the MDUU log table (GKRRLOG) for the VerifyUSI MDUU process.

The process code is present in the USI tab of SKASYSC.

This skkausi.p_verifyusi_internal procedure inserts a record into the SKRTRNS table, and the SKRRQST table and executes the VerifyUSI MDUU process to populate the SKSVUSI table. Also it sets the parameter 'USI_REQID' which can be used to refer to the request ID in Banner Self-Service.

Control is then passed back to the skkausi.p_verifyusi_realtime procedure.

SKKAUSI.P_VERIFYUSI_REALTIME

The skkausi.p_verifyusi_realtime procedure builds the VerifyUSI request XML using the data in the SKSVUSI table and sends the request to the USI system.

When the VerifyUSI response is received back from the USI system, the procedure SKKAUSI.p_process_verifyusi_response is called.

SKKAUSI.P_PROCESS_VERIFYUSI_RESPONSE

If the VerifyUSI response does not include any 'ErrorMessage' node, then the XIGN process ASC_USI_VERIFY_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXVUSI table.

The procedure SKKAUSI.p_verify_usi_response is called.

If the VerifyUSI response includes an 'ErrorMessage' node, then the XIGN process ASC_USI_VERIFY_FAULT_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXVUSI table.

The procedure SKKAUSI.p_verify_usi_res_fault is called.

SKKAUSI.P_VERIFY_USI_RESPONSE

If the USI_STATUS of the VerifyUSI request is VALID and either the first name and last name status = MATCH or Single name status = MATCH and the date of birth status = MATCH then it means the USI is successfully verified and the following inserts and updates are done.

The verified USI is used to update the Additional ID Verification table (GKRADIV), the Status is updated to 'SUCCESS' and the Verification Date is populated.

A record is inserted into the Additional Identification table (GORADID).

The corresponding request records in SKSVUSI, SKRRSQT and SKRTRNS are updated with the status of SUCCESS.

The corresponding record is deleted from the temporary table SKTVUSI as it is no longer needed.

A record is inserted into the SKRSTRN table for the PIDM.

If the value of the GKRVDOC-PURGE system parameter is 'A', then all records for the person are purged from the Identity Document Details table (GKRVDOC).

If the value of the GKRVDOC-PURGE system parameter is 'P', then the primary record for the person is purged from the Identity Document Details table (GKRVDOC).

If the USI_STATUS of the VerifyUSI request is either INVALID OR DEACTIVATED or if the USI_STATUS is VALID but the first name status or the last name status or the Single name status or the date of birth status is NOMATCH then it means the transaction is complete but the USI is not successfully verified and the following inserts and updates are done:

The Status on the Additional ID Verification table (GKRADIV) is updated to with the USI_STATUS that is received as response and the verified date is updated to NULL as the USI is not successfully verified yet.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSCUSI, SKRRSQT and SKRTRNS are updated with the status of COMPLETE

SKKAUSI.P_VERIFY_USI_RESPONSE_FAULT

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE'.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error.

The corresponding request records in SKSVUSI, SKRRSQT and SKRTRNS are updated with the status of SOAPFAULT.

If there is any problem in executing SKKAUSI.p_verify_usi_response_fault, the SKKAUSI.p_set_status_expired_failed procedure is called.

SKKAUSI.P_SET_STATUS_EXPIRED_FAILED

This procedure sets the status of pending requests to EXPIRED in the SKSVUSI, SKRRQST and SKRTRNS tables.

A record is inserted into the Request Exceptions table (SKREXPT).

DELETE_VERIFIED_USI_PROCESS

This process allow authorised users to delete a verified USI record for a person, so that they can then enter a more recent USI value for that person.

The DELETE_VERIFIED_USI MDUU activity uses a function to remove the record from the GKRADIV table and from the GORADID table, and to populate a SKRUSIL log table. After the verified record is removed, the user can then go to the GKAADIV page and enter the correct USI for the person.

Bulk Verify

SKKAUSI.p_bulkverify_scheduler is the procedure that gets invoked through an oracle job that is scheduled every day. This procedure,first calls the skkausi.p_bulk_data_cleanup procedure.

SKKAUSI.P_BULK_DATA_CLEANUP

The skkausi.p_bulk_data_cleanup procedure checks whether there are any bulk verify requests that are in a PENDING state.

Ideally there should be no bulk verify request that should be in PENDING state because the response from the USI system is synchronous for bulk verify requests. Hence if there are any pending bulk verify requests then they need to be updated with the status as EXPIRED before sending a fresh bulk verify request and that's what p_bulk_data_cleanup procedure does.

SKKAUSI.P_BULKVERIFY_SCHEDULER

The GKRADIV cursor fetches all the student records from GKRADIV table for whom GKRADIV_ADDITIONAL_ID is not null and GKRADIV_VERIFIED_DATE is null and GKRADIV_CONSENT = 'Y' and GKRADIV_ADID_CODE = 'USI'

If no records exist in GKRADIV satisfying the above conditions then it means for all the students USI is verified and hence a record is inserted into SKRTRNS with the message "No data is available for processing in GKAADIV page."

If the Bulk Verify URL is not specified in USI tab of SKASYSC page then it will insert a record into SKRTRNS with the message "BulkVerify URL details are not available on USI tab of SKASYSC page."

Before sending the Bulk Verify request xml to the USI server it internally processes the MDUU process specified for the field Bulk Verify USI Process on the USI tab of SKASYSC page.

If the MDUU activity corresponding to the Bulk Verify USI Process fails for any reason and records are not inserted into the USI BulkVerify Request Snapshot Table (SKSBVUS) then a record is inserted into Request Exceptions page with the actual error message generated by MDUU on why the activity failed to execute.

After this step the procedure skkausi.p_bulkverify is called.

SKKAUSI.P_BULKVERIFY

SKKAUSI.p_bulkverify(lv_gkradiv_pidm_exists, lv_gkrrlog_seqno_out);

It has one IN parameter (PIDM) and one OUT parameter (gkrrlog_seqno).

The first parameter is the PIDM which is passed into this procedure from skkausi.p_bulkverify_scheduler.

The second parameter is the sequence number from the MDUU log table (GKRRLOG) for the BulkVerify USI MDUU process.

The process code is present in the USI tab of SKASYSC.

This skkausi.p_bulkverify procedure inserts a record into the SKRTRNS table, and PIDMs are allocated to the request ID, up to the maximum for bulk verify requests and rows are inserted into SKRRQST for each PIDM for the request ID.

The procedure also executes the Bulk VerifyUSI MDUU process to populate the SKSBVUS table.

Control is then passed back to the skkausi.p_bulkverify_scheduler procedure.

SKKAUSI.P_BULKVERIFY_SCHEDULER

The skkausi.p_bulkverify_scheduler procedure builds the BulkVerify request XML using the data in the SKSBVUS table and sends the request to the USI system.

When the BulkVerify response is received back from the USI system, the procedure SKKAUSI.p_process_bulkverify_response is called.

SKKAUSI.P_BULKVERIFY_REPONSE

If the BulkVerify response does not include any 'ErrorMessage' node, then the XIGN process ASC_USI_BULK_VERIFY_RESPONSE will be executed.

The response XML is parsed and data is populated into the SKXBVUS table.

The procedure SKKAUSI.p_bulk_verify_usi_response is called.

If the BulkVerify response includes an 'ErrorMessage' node, then the XIGN process ASC_USI_BULK_VERIFY_FAULT_RESP will be executed.

The response XML is parsed and data is populated into the SKXBVUS table.

The procedure SKKAUSI.p_bulkverify_usi_res_fault is called.

SKKAUSI.P_BULK_VERIFY_USI_REPONSE

The corresponding request in SKRTRNS is updated with a status of COMPLETE.

If the USI_STATUS of a record in the BulkVerify request is VALID and either the first name and last name status = MATCH or Single name status = MATCH and the date of birth status = MATCH then it means the USI is successfully verified and the following inserts and updates are done:

The verified USI is used to update the Additional ID Verification table (GKRADIV), the Status is updated to 'SUCCESS' and the Verification Date is populated for the PIDM.

A record is inserted into the Additional Identification table (GORADID) for the PIDM.

The corresponding request and PIDM records in SKSBVUS and SKRRSQT are updated with the status of SUCCESS.

The corresponding record is deleted from the temporary table SKTBVUS as it is no longer needed.

A record is inserted into the SKRSTRN table for the PIDM.

If the value of the GKRVDOC-PURGE system parameter is 'A', then all records for the person are purged from the Identity Document Details table (GKRVDOC).

If the value of the GKRVDOC-PURGE system parameter is 'P', then the primary record for the person is purged from the Identity Document Details table (GKRVDOC).

If the USI_STATUS of a record in the BulkVerify request is either INVALID OR DEACTIVATED or if the USI_STATUS is VALID but the first name status or the last name status or the Single name status or the date of birth status is NOMATCH then it means the transaction is complete but the USI is not successfully verified and the following inserts and updates are done:

The Status on the Additional ID Verification table (GKRADIV) is updated to with the USI_STATUS that is received as response and the verified date is updated to NULL as the USI is not successfully verified yet for the PIDM.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error for the PIDM.

The corresponding request and PIDM records in SKSBVUS and SKRRSQT are updated with the status of COMPLETE.

SKKAUSI.P_BULKVERIFY_USI_RES_FAULT

The corresponding request record on SKRTRNS is updated with a status of SOAPFAULT.

The Status on the Additional ID Verification table (GKRADIV) is updated to 'FAILURE' for each PIDM in the request.

A record is inserted into the Request Exceptions table (SKREXPT) with the details of the error for each PIDM in the request.

The corresponding request and PIDM records in SKSBVUS and SKRRSQT are updated with the status of SOAPFAULT.

If there is any problem in executing SKKAUSI.p_bulkverify_usi_res_fault, the SKKAUSI.p_set_status_expired_failed procedure is called.

SKKAUSI.P_SET_STATUS_EXPIRED_FAILED

This procedure sets the status of pending requests to EXPIRED in the SKSBVUS, SKRRQST and SKRTRNS tables.

A record is inserted into the Request Exceptions table (SKREXPT) for each PIDM.
