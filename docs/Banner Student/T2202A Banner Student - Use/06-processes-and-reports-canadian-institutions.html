Processes and Reports (Canadian Institutions)

This chapter discusses the following processes and reports.

T2202A Calculation Q.M.-TTC (SVPTAXC) process

The SVPTAXC process calculates qualifying months and eligible Tuition Tax Credits (TTC) for all selected students in the tax year.

This process now uses the setting for the new QSN_REQR internal code of the T2202A internal group on the Crosswalk Validation (GTVSDAX) form to determine whether the SVBREL8 records are to be processed, as follows:
  • If the value for the External Code field is Y and the permanent code that is retrieved from a customized table or the SPRCMNT table for students is NULL or xxxx00000000, the process does not create or update records in the SVBREL8 table.
  • If the value for the External Code field is not Y, the system creates or updates records in SVBREL8, no matter what permanent code is returned from a customized table or the SPRCMNT table.

Qualifying months and eligible tuition fees are independent of each other. Even if a student or CRN is excluded, the process checks to see if any eligible fees were paid for any particular term.

This data is stored in the SVBTAXC table and is viewed on the SVATAXC page. For each record that exists in the SVBTAXC table, there will be one record in the SVBTAXT table. The number of terms in the SVBTAXT table is the number of terms in a tax processing year for a particular student.

The report does the following:
  • Validates that fees from the previous tax year (SVBTAXT and SVBTXRP) only belong to non-United States institutions (no R or C in the RESI_CDE field).
  • Prevents the processing of students with the Exception Lock indicator set to Y on the SVBTAXT record for that tax year.
  • Uses the terms that exist in the SFBETRM and TBRACCD tables, and in the SVBTAXT table for the current maximum SVBTAXC sequence number.
  • Displays a warning when a valid birth date does not exist but will continue the calculation for that student.
  • Uses the default dates to calculate the TTC when a term is using CRN rules and the rules match but were not used for the calculation (example, when dates that are not valid do not cross the tax year).
  • Creates a new record showing zero months and zero TTC when using the SVPTAXC process to recalculate a student who already has a record in the SVBTAXC table and when there are no months or TTC in the new calculation results.
  • Verifies that changes exist before inserting a new sequence number when recalculating the T2202 data when the record has been printed. A new sequence number is not inserted when the data remains the same.
  • Captures and stores charitable donation amounts in the SVBTAXT table.
  • Calculates ancillary amounts referencing detail codes that are associated with the current year on SVAANCI and populate the results in the SVBTAXT table.

    If the current tax year is 2014, and if a split term involved in a calculation started in 2013, the ancillary amount is prorated using the weighted term percentage (WTP). If the current tax year is 2015 or later, and if a split term involved in a calculation started in 2014 or later, the ancillary amount is the remaining ancillary amount from previous years.

  • Stores all the details of the calculations in two tables and displays the information on the SVATAXC page. If a student calculation rule was used or no rules were used, the details are stored in the SVBTAXS table. If a CRN calculation rule was used, the details are stored in the SVBTAXR table.
  • Saves errors, notifications and warnings to the SVRTMSG table when the process is run in Update mode. The messages can be viewed from the SVITMSG page.
  • Calculates the receipt number if the charitable donation amount for a student is greater than zero. It also carries the receipt number (if one exists) from the last record forward to the amended record of the T2202A Taxation Qualifying Months (SVBTAXC) table. It does not recalculate the receipt number if one already exists in the current record.
  • Validates the student SIN before the SIN is populated in the SVBTAXC_SIN field.
  • Handles T2202 amendments and cancellation to allow amended and cancelled T2202 records to be created based on the XML Submit Indicator.
  • Handles the situation of "No valid address" of a student in T2202 record when the student does not have an active address.
  • Stops inserting data in SVBTAXC when the status is original and there is no amount or session data available for the student so that there is no junk data in SVBTAXC.
You can run the report from the SVATAXC or GJAPCTL pages. See SVPTAXC process for a list of messages generated during the SVPTAXC process.

CRN processing

The CRN dates are used to calculate qualifying months, and to prorate the TTC even when the CRN is outside or totally within the tax year and the weighted term percentage (WTP) is zero.

This allows you to identify terms that are partially in the tax year even though the term’s start and end dates are not within that tax year.

This process calculates and stores WTP and Hours per Week Equivalent (HWE) data using the CRN or Meeting Time start and end dates instead of the term start and end dates.

The SVPTAXC process compares the tax year end date to the maximum end dates for the Term and the CRNs, Meeting Times, or Student Rules. If the tax year end date is less than (ends before) the other dates, the WTP is used to allocate the fees to the term. Basically, the process looks to see how much of the time is within the tax year to calculate the WTP. On the other hand, if the tax year end date is greater than the maximum CRN, Meeting Times, Student Rules and Term, then the Remaining Balance indicator is marked with a Y and gives all of the fees minus any fees that were used in the prior year.

Full-time months calculation

The SVPTAXC process allow students who study as a Canadian institutions for a full-time qualifying month calculation.

For students who study at a Canadian institution, if the duration of the program is more than three consecutive weeks with at least 10 hours per week, then the month in which the courses start or finish can be qualified as a full-time month even though the courses did not take three weeks in those months. This applies to a program with associated courses/terms that spans one or two tax years.

When the full-time qualifying month calculation is completed for a tax year, if January or December does not qualify as a full-time month yet, the process determines whether a program with associated courses/terms spans two tax years. If the courses/terms span two tax years, the process determines whether the student can get a full-time month in January or December for the tax year looking back for the courses/terms started in the previous years or looking forward for the courses/terms ended in the next years.

Part-time months calculation

The SVPTAXC process gives part-time months to a student if the CRN has twelve hours in a month.

The criteria is that the student does not have to attend the course for a minimum of twelve hours in the month from which they are withdrawing (assuming that the student passes the three consecutive week rule) but the course must have at least twelve hours in the month. Therefore, the calculation date and the reporting date can be different. Although the student's registration date for an early exit status may show the date the student actually withdrew from the CRN, the SVBTAXR_END_DATE column will reflect the date the process used to calculate the HWE.

Depending on the circumstances, a specific calculation might be needed to calculate the part-time months.

Specific calculation

A specific calculation will only be used when all of the following occur:
  • The Specific Calc when MT for PT m parameter is set to Y.
  • The student met the CRN calculation rules in the SVAHWER page.
  • The student is in one of situations that are described in Table 1.
  • At least one of the Days of the Week check boxes was selected on the Meeting Time block on the SSASECT page for a CRN in a term that the student has registered.

The Specific Calc when MT for PT m parameter is used to determine if a specific calculation should be used when meeting times are used to calculate if a month is part-time. The process determines the exact weekdays and weekend days that have meeting hours in the SSRMEET table for students who have a combination of registration status rules, CRN calculation rules, and meeting time records (SSRMEET) .The logic for the part-time calculation decides how many hours will be given to the month in which the weeks belong. The original Hours per Week Equivalent (HWE) will be multiplied by a factor, which is the number of days when a student is scheduled to attend a class in a week divided by the total number of days marked in the student meeting record (SSRMEET). If at least one day is not marked in the student meeting records, the process will not use the specific calculation. In other words, the process will use the whole week instead.

The Weekend Management Indicator parameter will not be used if the specific calculation is used.

Tuition tax credit calculation

When the tuition tax credit is calculated, the WTP (Weighted Term Percentage) is obtained for each student for each term.

This is applied to the eligible TBRACCD records. The calculation adds all the T2202 eligible paid charges or eligible charges only (a detail code with a tax type that has the T2202A Eligible Indicator checked on TSADETC), depending on the rules set on the SVATAXL page. The calculation then subtracts all payments (with tax type that has the T2202A Eligible Indicator checked on TSADETC), and multiplies the result by the WTP. This amount is stored in the SVBTAXC table with the appropriate term. The process checks each rule in order until a match is found.

The calculation also builds a matrix of HWEs (Hours per Week Equivalents) for all CRNs taken by a student and adds them up. The following is an example of how to calculate the qualifying months based on HWEs.

Example

A particular institution has three divisions: Credit, Continuing Education, and a Music Academy. Each division has their unique term code for each term. Students may take course(s) from any of (or all of) the divisions in the same period of time.

Calculate qualifying months based on the HWE for each course that the student takes in the month. For part-time enrollment, a course must satisfy the three consecutive weeks and three hours per week rules to be included in the calculation. HWEs for courses offered in different terms and different course levels could be calculated in a slightly different way.

For the courses offered by the Credit division: (the exception being courses with a schedule code of K - these courses are not considered in the HWE calculation)

(TERMS - 200101 Winter, 200102 Spring, 200104 Fall)

HWE = (SSBSECT_CREDIT_HRS * SVBTAXC_CRED_FCTR) in Winter/Fall term.HWE = (SSBSECT_CREDIT_HRS * SVBTAXC_CRED_FCTR) * 1.5 in Spring term.

The start date and end date for each course is the SSRMEET_START_DATE and SSRMEET_END_DATE if available, or else the SSBSECT_PTRM_START_DATE and SSBSECT_PTRM_END_DATE of the CRN. HWEs are assigned to each week for the period from the start date to the end date. If the student withdraws from a course, then the HWE is assigned to each week for the period from the start date to the withdrawal date.

For the courses offered by the Continuing Education division:

(TERMS - 200111 Winter, 200112 Spring, 200113 Summer, 200114 Fall)

HWE = (SSBSECT_CONT_HR * SVBTAXC_CONT_FCTR)

The start date and end date of the course is the SSRMEET_START_DATE and SSRMEET_END_DATE if available, or else the SSBSECT_PTRM_START_DATE and SSBSECT_PTRM_END_DATE. HWEs are assigned to each week for the period from the start date of the course to the end date of the course.

For the courses offered by the Music Academy division:

(TERMS - 200121 Winter, 200122 Spring, 200123 Summer, 200124 Fall)

HWE = (SSRMEET_HRS_WEEK * SVBTAXC_MEET_FCTR)

The start date and end date for the course is the earliest start date and the latest end date of the SSRMEET record(s) for the course. HWEs are assigned to each week for the period from the start date of the course to the end date of the course.

The HWEs are summed for the student for each week. If the HWE for the student for the week is >= X(e.g., X=9) (defined by institution), then the student qualifies as full-time for the month. If the HWE for the student for the week is X< 9, and X>= 3, then the student qualifies as part-time for the month.

Early-exit cases

When student rules are used, the process will stop calculating qualifying months using that rule, and the default dates from the SVAHWER page will be used for the TTC.

When CRN rules are used, the process will stop calculating qualifying months for that CRN and continue with the next one. If no CRNs have valid dates for that term, then the default dates from the STVTERM page will be used for the TTC.

This process gives part-time months to a student if the CRN has twelve hours in a month. The criteria is that the student does not have to attend the course for a minimum of twelve hours in the month from which they are withdrawing (assuming that the student passes the three consecutive week rule) but the course must have at least twelve hours in the month. Therefore, the calculation date and the reporting date can be different. Although the student’s registration date for an early exit status may show the date the student actually withdrew from the CRN, the SVBTAXR_END_DATE will reflect the date the process used to calculate the HWE.

For student and CRN rules, an N for No Rule Used will be inserted into the SVBTAXS table when the default dates are used.

When the calculated end date occurs before the calculated start date, the warning message: W - Stud EARLY EXIT End Date Less than Start Date will be printed in the .LIS file when the following occurs:
  • A student matches the student calculation rules for a term.
  • The student enrollment status code (SFBETRM_ESTS_CODE) is marked as early exit in the SVAESTS page for the tax year.
When the calculated end date occurs before the calculated start date, the warning message: W - CRN EARLY EXIT End Date Less than Start Date will be printed in the .LIS file when the following occurs:
  • A student matches the CRN calculation rules for a term
  • The course registration status code (SFRSTCR_RSTS_CODE) associated with the CRN is marked as early exit in the SVARSTS page for the tax year.
For any other scenarios, when the calculated end date occurs before the calculated start date, the error message E - Start-date must be LE end-date in the term/crn will be printed in the .LIS file.

Open entry/open exit courses

When calculating qualifying months using open entry/open exit courses, the HWE is distributed evenly over the number of weeks for the course.

Credits for open entry/open exit courses are set up as the number of overall hours for the course, not per week as for regular courses therefore before calculating the HWE, the hours are converted to a hours per week equivalent.

Formula: HWE = [UNIT_VALUE * ATOF(HWCC_UNIT_FCTR)] / [weeks between SFRSTCR_ADD_DATE and SFRSTCR_RSTS_DATE ]

In the following samples, the CR for the courses is 32 regardless of whether the student's course is 2 weeks or 33 ½ weeks:

Sample:
  • Total hours = SFRSTCR_CRED_HR * SVBHWCC_UNIT_FACTOR = 32 * 3 = 96 hours
  • Days between SFRSTCR_ADD_DATE and SFRSTCR_RSTS_DATE = 235 days
  • Weeks between SFRSTCR_ADD_DATE and SFRSTCR_RSTS_DATE = 235 / 7 = 33.57 weeks
  • HWE = (32 * 3) / 33.57 = 2.859

    Sample:

  • Total hours = SFRSTCR_CRED_HR * SVBHWCC_UNIT_FACTOR = 32 * 3 = 96 hours
  • Days between SFRSTCR_ADD_DATE and SFRSTCR_RSTS_DATE = 14 days
  • Weeks between SFRSTCR_ADD_DATE and SFRSTCR_RSTS_DATE = 14 / 7 = 2 weeks
  • HWE = (32 * 3) / 2 = 14.5
    Note: The course in this example would not qualify on its own because it does not meet the three consecutive week rule.
    A student who gets even a partial decimal as a result of this calculation would have to work at least one day into the following week. For example:
  • June 1 - 6 would result in 6 days/7 = .8571or 1 week
  • June 1 - 7 would result in 7 days/7 = 1.0 or 1 week
  • June 1 - 8 would result in 8 days/7 = 1.1429 or 2 weeks

Meeting times

The report calculates and stores HWE data for individual meeting times as if they were separate CRNs. The CRN data will be stored in the SVBTAXR table.

The student rule data will be stored in the SVBTAXS table along with detail data when no rule is available in the SVPTAXC process. This enhancement also splits the calculation detail records into two separate tables, and displays a unique block on the SVATAXC page.

Meeting times with varying start and end dates, and multiple entries are allowed. When processing meeting records, assume the following:
  • A CRN can have multiple meeting records associated with it.
  • Each meeting record is processed as a sub-CRN using the start and end dates of the session, and the hours per week field as the HWE for that session.
  • Meeting sessions may be serial or overlapping. For overlapping sessions, the sum of the individual hours per week for each sub-CRN will be used to calculate the HWE.
  • For the case when a CRN has one session, which all students attend, plus one or more sessions that are offered at the same time on the same day but students attend only one of those sessions, then it is recommended that one of those sessions have the hours per week set to the proper value and the other sessions have the hours per week set to zero. If this is not done, then the HWE for this CRN will be overstated.
The following examples show the calculation of the HWE for a CRN with multiple meeting sessions:
  • Multiple meeting times with the same start and end dates for a CRN and Hrs/Wk in each time.

    The course meets Monday and Tuesday from 8:00 to 9:00 (Seq 1 = 2 Hrs) and on Wednesday from 10:00 to 12:00 (Seq 2 = 2 Hrs) from September 4 to December 22. Total Hrs/Wk = (2+2) = 4 for each week.

  • Multiple meeting times with varying start and end dates for a CRN and Hrs/Wk in each time.

    The course meets Monday and Tuesday from 8:00 to 9:00 (Seq 1 = 2 Hrs) from September 4 to October 31 and on Wednesday from 10:00 to 12:00 (Seq 2 = 2 Hrs) from November 1 to December 22. Total Hrs/Wk = 2 for each week.

  • Multiple meeting times with the same start and end dates for a CRN and Hrs/Wk not in each time.

    The course meets Monday and Tuesday from 8:00 to 9:00 (Seq 1 = 2 Hrs), and on Wednesday from 10:00 to 12:00 (Seq 2 = 2 Hrs) or on Thursday from 1:00 to 3:00 (Seq 3 = 0 Hrs) from September 4 to December 22. Total Hrs/Wk = (2+2+0) = 4 for each week.

  • Multiple meeting times with varying start and end dates for a CRN and Hrs/Wk not in each time.

    The course meets Monday and Tuesday from 8:00 to 9:00 (Seq 1 = 2 Hrs) from September 4 to October 31, and on Wednesday from 10:00 to 12:00 (Seq 2 = 2 Hrs) or on Thursday from 1:00 to 3:00 (Seq 3 = 0 Hrs) from November 1 to December 22. Total Hrs/Wk = 2 for each week.

  • Multiple meeting times with the same start and end dates for a CRN and multiple sessions offered on the same days at the same time and Hrs/Wk not in each time.

    The course meets Monday and Tuesday from 8:00 to 9:00 (Seq 1 = 2 Hrs) and on Wednesday from 10:00 to 12:00 (Seq 2 = 2 Hrs) in one room, or on Wednesday from 10:00 to 12:00 (Seq 3 = 0 Hrs) in another room from September 4 to December 22. Total Hrs/Wk = (2+2+0) = 4 for each week.

Open Learning Registration

The SVPTAXC process captures registration data for CRNs created with the Open Learning Registration (OLR).

For every CRN that a student has, the process determines if the CRN is using OLR by looking at the SFRSTCR_PTRM_CODE field for the CRN. If the SFRSTCR_PTRM_CODE field is not null (Current Registration Methods), then the CRN is processed as usual. If the SFRSTCR_PTRM_CODE field is null (OLR), then the CRN is processed using the dates on the SFRAREG table, or the registration status date on the SFRSTCR table if the student is withdrawn this course. Meanwhile, this process retrieves the GTVSDAX external code specified for the OLR_SEG internal code for the T2202A internal group and the value of the OLR Division check box on the CRN Calculation Rules tab of SVAHWER. The combination of the external code and the division indicator is used in calculating hours per week (HWE) and the duration for an OLR course depending on specific scenarios as follows.

If there are no extensions (that is, the value for the SFRAREG_EXTENSION_NUMBER field is 0), then the process determines if the registration status code of the CRN (SFRSTCR_RSTS_CODE) is Withdraw.

  • If the registration status code of the CRN is Withdraw (value of the STVRSTS_WITHDRAW_IND field is Y), then
    • Start date of the CRN is the start date (SFRAREG_START_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0
    • End date of the CRN is last day of the month of the value in the SFRSTCR_RSTS_DATE field
    • HWE is the unit value of the matched CRN calculation rule divided by the total number of weeks between the calculated start date and end date if the OLR Division check box is selected, or HWE is the unit value of the matched CRN calculation rule if the OLR Division check box is cleared
  • If the registration status code of the CRN is not Withdraw (value of the STVRSTS_WITHDRAW_IND field is null), then
    • Start date of the CRN is the start date (SFRAREG_START_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0
    • End date of the CRN is the completion date (SFRAREG_COMPLETION_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0
    • HWE is the unit value of the matched CRN calculation rule divided by the total number of weeks between the calculated start date and end date if the OLR Division check box is selected, or HWE is the unit value of the matched CRN calculation rule if the OLR Division check box is cleared.

If there are extensions (that is, the value for the SFRAREG_EXTENSION_NUMBER field is greater than or equal to 1), then the process determines if the registration status code of the CRN (SFRSTCR_RSTS_CODE) is Withdraw.

  • If the registration status code of the CRN is Withdraw (value of the STVRSTS_WITHDRAW_IND field is Y), then
    • Start date of the CRN is the start date (SFRAREG_START_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0
    • End date of the CRN is calculated as follows:

      Last day of the month of the value in the SFRSTCR_RSTS_DATE field if the value of the external code is 1

      -- OR --

      The completion date (SFRAREG_COMPLETION_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0 if the value of the external code is 2 and if the withdrawn date is greater than the completion date of the segment zero

      -- OR --

      Last day of the month of the value in the SFRSTCR_RSTS_DATE field if the value of the external code is 2 and if the withdrawn date is not greater than the completion date of the segment zero.

    • HWE is the unit value of the matched CRN calculation rule divided by the total number of weeks between the calculated start date and end date excluding any dropped or withdrawn extensions if the OLR Division check box is selected, or HWE is the unit value of the matched CRN calculation rule if the OLR Division check box is cleared
  • If the registration status code of the CRN is not Withdraw (value of the STVRSTS_WITHDRAW_IND field is null), then
    • Start date of the CRN is the start date (SFRAREG_START_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0
    • End date of the CRN is calculated as follows:

      The completion date (SFRAREG_COMPLETION_DATE) of the record with the maximum value in the SFRAREG_EXTENSION_NUMBER field that does not have a registration status of withdraw; this means that the dates of any extension that has been dropped or withdrawn are excluded from the dates. This is when the value of the external code is 1.

      -- OR --

      The completion date (SFRAREG_COMPLETION_DATE) of the record where the value for the SFRAREG_EXTENSION_NUMBER field is 0. This is when the value of the external code is 2.

    • HWE is the unit value of the matched CRN calculation rule divided by the total number of weeks between the calculated start date and end date excluding any dropped or withdrawn extensions if the OLR Division check box is selected, or HWE is the unit value of the matched CRN calculation rule if the OLR Division check box is cleared

Eligible application fees paid through Banner Self-Service

This process captures T2202 eligible application fees paid through Banner Self-Service. Individuals can make credit card payment through Self-Service. If the individual does not have a Banner PIDM when the payment is made, the transactions are stored in the TBBMISC or TBRMISD table.

The SVPTAXC process checks every student to see if any eligible application fees were paid through Self-Service. If yes, the amount is added to the T2202 tax credit total amount. This amount is calculated regardless of the method of calculation (payments or charges). The Process Appl Fees Paid BSS parameter indicates if these amounts will be calculated. Some users have the application amounts forced into the TBRACCD table and will not want to count it twice.

Only amounts attached to valid T2202A tax type codes will be processed (that is, the value for the TTVTAXT_TAXT_IND column should be Y for the tax type code that is being processed).

Only amounts attached to valid T2202A terms for the tax year will be processed, which means that the term must exist on the SVRFRYR table.

It is not necessary that the term in which students paid the application fees is the same term in which the students enroll; however, it is required that the terms must be in the same tax year.

Program/degree/campus codes selection

The program/degree and campus codes calculation or selection is based on SGBSTDN records and SFBETRM and TBRACCD tables.

For each term in SFBETRM and TBRACCD, the process uses the record from SGBSTDN with the matching term; if there is no matching term, the process uses the SGBSTDN record for the term with the most recent start date prior the start date of the term processed (in SFBETRM and TBRACCD).

The process checks if there is registration information for the student in the SFRSTCR table for the SGBSTDN terms when more than one term share the same start date. If only one term has registration information, then the one will be selected. If multiple terms or no terms have registration information, then the selection will be based on the Mode Same Start Date Term field on SVATAXL.

If there is more than one term in SGBSTDN with the same start date, the Mode Same Start Date Term field on SVATAXL is used to determine which term is to be used when two or more term codes share the same start date in the Student Table (SGBSTDN): the maximum term code (1) or the term based on the student’s registration and the priority of the term (2).

For each term in SFBETRM and TBRACCD, the campus specified in the SGBSTDN record returned by the process is used to populate the Tuition Tax Credit Eligible Fees block of the SVATAXC page.

When the last term is processed from SFBETRM and TBRACCD, the program/degree from the corresponding SGBSTDN record will be populated in SVBTAXC record for the student.

After all the terms that are involved in qualifying months and fees calculation for a student have been processed, if no program or degree has been selected or returned, the process checks SGBSTDN one last time to determine whether there is any record with the earliest start date of the effective terms less than or equal to the last day of the tax year. If such a record exists, the program or degree code in this record is populated in SVBTAXC; otherwise, the process reports an error indicating there is no program or degree so that no T2202 record will be generated.

Error reported when there is no program/degree

The process uses the value entered for the Print Message when no Prog/Deg parameter to determine which error is to be printed when there is no program/degree.

If the value is 1 (Generic Message), the system prints the message: There is NO PROGRAM or DEGREE.

If the value is 2 (Specific Message), one of the following occurs, as applicable.

  • If the student has no program/degree, the system prints the message: There is no record in SGBSTDN for this person.
  • If the student does not have at least one program starting before the end of tax year, the system prints the message: No programs start before the end of tax year.

    This message is reported when the SGBSTDN table for the student does not have a program or degree that started before the end of the tax year, even if the student has registered for a course in a section that starts before the end of the tax year, as shown in the following example:

    Student enrolled to the Program (P1) in Term (T1) for 2009 T1 begins January 1, 2009
    Student is registered to Course (CRN 01) in Section (S1), which starts in 2008 CRN 01 begins December 6, 2008

    The student does not qualify for tax year 2008, because the only program or degree for which the student is registered starts in the effective term, T1, in 2009, even though part of the term, section S1, starts in 2008. The Banner Baseline program and degree are associated on a term basis, not on a part-of-term level.

  • If the student still has no program and degree codes returned, the system prints the generic message: There is NO PROGRAM or DEGREE.

    For example, this message will be displayed for a student having a program or a degree but not a valid enrollment status in SFAREGS, because the status is missing from SVAESTS for the processed year.

If the record has not been printed in an XML file, the current record sequence number is more than 1 and the calculated Relevé 8 amount is changed to zero, then the record is updated in the SVBREL8 table.

If the record has been printed in the XML file, then a new record is always created.

Amended slip

The SVPTAXC process does not generate an amended Relevé 8 record is when the name of the student is changed in the Student ID Table (SPRIDEN).

An amended record is created only in the following scenarios:
  • Changes to the part-time or full-time qualifying months that caused the Relevé 8 Box A amount (SVBREL8_AMOUNT) to change
  • Changes to the tuition amount that caused the Relevé 8 Box B (SVBREL8_BOXB_AMOUNT) amount to change
  • Changes to the charitable amount that caused the Relevé 8 Box C (SVBREL8_BOXC_AMOUNT) amount to change
That is, an amended record is only created if the value in Box A, B or C was changed.

If the record has not been printed in an XML file, the current record sequence number is 1, and the calculated Relevé 8 amount is changed to zero, then the following message is included in the .LIS file: Record deleted from SVBREL8, and the record is deleted from SVBREL8 table.

If the record has not been printed in an XML file, the current record sequence number is more than 1 and the calculated Relevé 8 amount is changed to zero, then the record is updated in the SVBREL8 table.

If the record has been printed in the XML file, then a new record is always created.

Time status

When running the process, you can indicate whether the system is to use the latest time status as specified on the SFBETRM table or the historical effective time status.

This status indicated can be as specified on the SFRTHST table to calculate the qualifying months for which a student would be eligible in a tax year.

If you specify 1 for the Time Status Mode parameter, the process uses the time status from SFBETRM to determine if it, along with another factors such as program, campus, and so on., matches a student calculation rule or exclusion rule and then calculates the hours per week for the entire period of the term defined in the matched calculation rule. This is similar to Scenario 5: Student rules.

If you specify 2 for the Time Status Mode parameter, the process first determines whether the student has multiple time status records on SFRTHST for the specified term. If so, the process uses the historical effective time status method; otherwise, the process uses the latest time status method as if you had specified 1 for the Time Status Mode parameter.

The rest of this section provides detailed explanation and examples of the historical effective time status method.

The SVPTAXC process treats every time status of a student as a sub-term that needs to be calculated separately. The process checks all time status records for which effective dates are before the end date of the term (as defined on STVTERM), along with another factors such as program, campus, and so on, to determine whether a student exclusion or calculation rule (based on settings on SVAHWER) is matched, using the following sequence.

  1. If a student exclusion rule is matched, the time status record is not considered as a contribution of hours per week in its sub-term for the qualifying month calculations.
    Note: If a user configures the same rule as both a student calculation rule (inclusion) and a student exclusion rule, which is not recommended, then if a time status record matches the student exclusion rule, the process will not take the time status record for the calculations (qualifying months) it keeps track of what was excluded originally.
  2. If a student exclusion rule is not matched, the process determines whether the time status record matches a calculation rule, and if so, the time status record is considered as a contribution of hours of per week in its sub-term for the qualifying month calculations.
  3. If none of the time status records in a term are detected as excluded or included, the process will go through CRN rules in the same term.
  4. If at least one of the time status records in a term is detected as excluded or included, the process will not go through CRN rules in the same term.

When using SFRTHST, take note of the following considerations and restrictions.

  • All of your institution’s time status rules must be defined on SVAHWER.
  • Any time status value that is not included on SVAHWER will not be considered when matching rules for students.
  • The values in the From Date and To Date fields for the student calculation rules defined on SVAHWER are ignored. Instead, the start and end dates of the term (defined on STVTERM) are used to determine which months are included in the term for which a rule is being evaluated.
  • If the time status effective date (SFRTHST_TMST_DATE) is later than the last day of the tax year or the end date of the term, the time status record is not considered, and the calculation does not evaluate it.
  • The Full/Part-time Students field on SVAHWER is used to determine whether a time status value is to be treated as part time (P) or full time (F).
  • The coverage of months is based on the months in which the term’s start date and end date fall.

Refer to Example using calculation (inclusion) rules and Example using exclusion rules for more information.

The time status effective dates are used to divide the entire term into multiple sub-terms and then to calculate the start date and end date of all the sub-terms. The start date of first sub-term and the end date of last sub-term are recalculated as follows:
  • The start date for the first effective time status sub-term that meets a calculation rule is extended or reduced to the first day of the month that the start-of-term date falls in. If there are multiple time status records for which effective dates are before the start-of-term date, the one that is closest to the start-of-term date is used as the first effective time status sub-term, and the others are not considered in the calculations.
  • The end date of the last effective time status sub-term that meets a calculation rule is extended to the last day of the month in which the end-of-term date falls.
Refer to Examples calculating time status sub-terms for more information.

The calculated start and end dates of each time status sub-term are populated into the Start Date field (SVBTAXS_START_DATE) and End Date field (SVBTAXS_END_DATE) in the Student Rule Calculation Detail block of the T2202A Taxation (SVATAXC). The values in the From Date field (SVBTAXT_FROM_DATE) and To Date field (SVBTAXT_TO_DATE) on the Tuition Tax Credit Eligible Fees block of SVATAXC are the earliest start date and latest end date of all the calculated time status sub-terms in a term. However, if none of the time statuses in a term match a student calculation rule, and if one or more time statuses match student exclusion rules in the same term, the values in the From Date and To Date fields will be the start date and end date of the term.

The process populates the Student Calculation Rule Number field (SVBTAXS_HWSC_RULE_NUM) or the Student Exclusion Rule Number field (SVBTAXS_HWSE_RULE_NUM) of the Student Rule Calculation Detail block of SVATAXC with the inclusion or exclusion rule number from SVAHWER that was detected when a time status record was matched to a student calculation or exclusion rule in a term. This applies for both time status modes: “Use latest time status in SFBETRM” and “Use effective time status in SFRTHST.”

The Hours per Week Equivalent field (SVBTAXS_HWE) on the Student Rule Calculation Detail block of SVATAXC for each time status sub-term is populated with the value in the Full-time Hours per Week or Part-time Hours per Week field (as appropriate) of the Education/Tuition Amount Limits (SVATAXL) page. This depends on the value (F or P) in the Full/Part-time Students field of the calculation rule to which a time status record matched.

Calculation of Relevé 8 (SVPREL8) process

This process calculates the Relevé 8 amounts for individuals (multiple IDs allowed) or groups of individuals based on population selection.

This process now uses the setting for the new QSN_REQR internal code of the T2202A internal group on the Crosswalk Validation (GTVSDAX) form to determine whether the SVBREL8 records are to be processed, as follows:
  • If the value for the External Code field is Y and the permanent code that is retrieved from a customized table or the SPRCMNT table for students is NULL or xxxx00000000, the process does not create or update records in the SVBREL8 table.
  • If the value for the External Code field is not Y, the system creates or updates records in SVBREL8, no matter what permanent code is returned from a customized table or the SPRCMNT table.

This process uses the data stored in the SVBTAXC, SVBTAXL, and SVBRL8S tables to determine which students, sessions (maximum of 2) and amounts qualify for the Relevé 8 (based on limits set in the SVBTAXL table).

After recalculating the Relevé 8 data when the record has been printed on the page or generated and validated in XML, the process verifies that changes exist before inserting a new sequence number. A new sequence number is not inserted when the data remains the same.

The process counts one session each time a student has an F in every month of a defined session to a maximum of two sessions in a tax year.

For tax years before 2013, to qualify for a Relevé 8, a student must be full-time for an entire session. The amount that determines a full-time status is based on the number of sessions that the student started and completed in the tax year. The process shows the changes made to a record when a student no longer qualifies for a Relevé 8 session. This is only for full-time cases. If a student changed from full-time months to part-time months, the process recalculates the Relevé 8 data or creates a cancelled record if an original has been generated and validated.

For tax year 2013, a student is not required to be full-time for an entire session, as long as the tuition fees in Box B1 or B2 are greater than zero. The Box B1 amount is the total amount of tuition fees paid to your institution provided they are attributable to a study session the student started before March 28, 2013, and these fees can be claimed at a rate of 20%. The Box B2 amount is the total amount of tuition fees paid to your institution provided they are attributable to a study session the student started after March 27, 2013, and these fees can be claimed at a rate of 8%.

For tax year 2014 and later, a student is not required to be full time for an entire session, as long as the tuition fees in Box B are greater than zero.

This process validates the student SIN before the SIN is populated in the SVBTAXC_SIN field.

The process also handles the situation of "No valid address" of a student in T2202 record when the student does not have an active address.

The process reports the total claimable amount on the Reporting Periods window of SVATAXC as the value for Box B on the SVBREL8 record for a student.

The Relevé 8 amount is not calculated according to tuition fees, and cannot be claimed by the student. The amount is claimed on the Quebec Provincial Income Tax Return by the person who claims the student as a a dependent.

The page is commonly referred to as the RL-8 slip, and must be enclosed with the Quebec Provincial Income Tax Return. The Relevé 8 is valid only if it is issued by an educational institution.

If Relevé 8 slips (original or amended) for 2007 have been printed for all students in a population, the system prints duplicate Relevé 8 slips for the students and does not query and update the SVRRLSQ table for the purpose of calculating the sequential number.

If the Relevé 8 slips (original or amended) for 2007 have not been printed for one or more students in a population, the job retrieves the SVRRLSQ table to get the first available range of numbers for 2007, and the returned rows in the table are locked. Any other user who tries to use the Relevé 8 web page or SVAREL8 page to print Relevé 8 slips for 2007 cannot perform the printing task if the SVRRLSQ table is needed to calculate the sequential number, and the system displays the message: ORA-00054: resource busy and acquire with NOWAIT specified. Please contact the system administrator.

When the job is finished, the locked rows in SVRRLSQ table are unlocked, and any users who tried to use the Relevé 8 web page or SVAREL8 page to print Relevé 8 slips can then perform the printing task.

Note: The Quebec government provided each higher education software vendor with a range of eight-digit serial numbers for 2007. The relevant information has been delivered as seed data in the SVRRLSQ table.

If the Relevé 8 slip (original or amended) has never been printed before, the system obtains the eight-digit value from the Next Available Number field (SVRRLSQ_NEXT_NUM) on the Relevé 8 Government Assigned Numbers Control (SVIRLSQ) page calculates a check digit using a formula provided by the Quebec government. (See IN-412-V(2007-08)[1].pdf posted on the Quebec Revenue web site for more information.) The system uses these two values to form the nine-digit sequential number and displays it on the Printable Relevé 8 page. This nine-digit number is also stored in the Government Sequential Number field (SVBREL8_RLSQ_SEQ_NO) on the SVAREL8 page. The Next Available Number field of SVIRLSQ is then updated with a new number by adding 1 to the former eight-digit number.

The process commits all transactions at the end of successful printing, or rolls back the transactions if printing was unsuccessful. This is because the SVRRLSQ table must be locked by the SVRREL8 process until all Relevé 8 slips (original or amended) for 2007 have been successfully printed for all students in a population. This is a matter of managing data concurrency and consistency with the SVRRLSQ table. Previously, the process committed every 100 records for a large population.

This concept applies to the Relevé 8 web page and SVAREL8 page (a call to SVRREL8) when printing individual RL8-slip that has never been printed for year 2007.

Logic flow for calculating the sequential number

Discusses the logic flow to calculate the sequential number.

  1. The job gets all the information for all students in the population and process the information one by one as previously.
  2. The system determines whether a student currently being processed has had a slip printed for the record with the maximum record sequence number from the SVBREL8 table for the tax year.
    • If so, the job proceeds, if applicable, to print a duplicate slip without referring to the SVRRLSQ table, then repeats the action for next student.
    • If not, the system retrieves the SVRRLSQ table to get the first available range of numbers for the first time.
      • If there is an available range of numbers, the job proceeds to step 3 listed in this job procedure.
      • If nothing is returned, the process commits all pending transactions to the database and then terminates and enters the following message in a LOG file: Maximum number in the range of Relevé-8 Slip sequential numbers has been reached. Please contact your software vendor to get a new range.
        Note: If SVRRLSQ has been queried, the table is not re-queried unless all sequence numbers assigned by the Quebec government in the current available range have run out for the tax year.
  3. The job performs the following:
    • Obtains the eight-digit value in the SVRRLSQ_NEXT_NUM column of SVRRLSQ table to calculate a check digit and generates a nine-digit formed number composed of the eight digits and the check digit.
    • Writes the formed number into the new Current Sequential Number column in the flat file that will be mail merged into the new templates for the tax year. If an Relevé 8 slip is specified as Amended, the process obtains the value previously calculated and stored in the SVBREL8_RLSQ_SEQ_NO column of the SVBREL8 table and writes the value into the new Nº du relevé 8 original column in the flat file.
    • Stores the nine-digit formed number in the SVBREL8_RLSQ_SEQ_NO column of the SVBREL8 table.
    • Updates the SVRRLSQ_NEXT_NUM column of the SVRRLSQ table with next new available number by adding 1 to the current available number.

After all the tasks have been finished, the job returns to step 1 of this job procedure to continue printing for the next student in the population.

If all sequence numbers in the current available range have run out during printing, the job will try to get next available range of numbers for the tax year.

If nothing is returned, the process commit all pending transactions to database and then terminates and enters the following message in a LOG file: Maximum number in the range of Relevé-8 Slip sequential numbers has been reached. Please contact your software vendor to get a new range.

If there is a next available range of numbers for the tax year, the job proceeds to finish the tasks specified in 3.

Relevé 8 XML Transmission Report (SVRRELX)

This report is used to generate XML files that contain students' Relevé 8 data and add the XML sequence number and XML file name to the data records in the SVBREL8 table.

This report now uses the setting for the new QSN_REQR internal code of the T2202A internal group on the Crosswalk Validation (GTVSDAX) form to determine whether the SVBREL8 records are to be printed in XML files, as follows:
  • If the value for the External Code field is Y and the permanent code that is retrieved from SVBREL8 table for students is NULL or xxxx00000000, the process does not print SVBREL8 records in XML files.
  • If the value for the External Code field is not Y, the system prints the SVBREL8 records in XML files, if applicable, no matter what permanent code is returned from the SVBREL8 table.
Only the records not already printed in an XML file, meaning without an XML file name associated in SVBREL8 table are included in the generated XML file.

The schema of the XML file is related to the year in which the Relevé 8 data is being filed. The XML file is generated with a corresponding schema version depending on the tax year. The XML schema information is delivered as seed data for the Relevé 8 Authorization and Certification Number Control Table (SVRAUTH), which you can view on SVIRLSQ.

Before start printing student records in the XML transmission file(s), the process validates the following:
  • The transmitter number exists on the Relevé 8 XML Transmission Information Control (SVAXLTM) page for the given tax year
  • The record for the tax year exists on the Relevé 8 Institution XML Sequence Number Control (SVARXSQ) page, and the next available XML number has not reached the maximum
  • The Institution Name 1 and Address Line 1 exist on SVAXLTM or the Installation Control (GUAINST) page.
  • The institution postal code is valid
The system also checks for required address information. First, it checks the value in the Nation field on one of the following pages, as appropriate:
  • For tax years before 2013, T2202A Taxation (SVATAXC) page
  • For tax year 2013 and later, Relevé 8 Taxation Form (SVAREL8) page
If the value is one of the valid nation codes defined on the Crosswalk Validation (GTVSDAX) page, the system continues processing, as further checking is required only for Canadian and US addresses.
That is, for the XML transmission file to be generated for a student, the student’s record must contain valid values for the following fields:
  • Address Line 1 (cannot be NO VALID ADDRESS, which is treated as null)
  • City
  • State or Province
  • ZIP or Postal code
If the value is not one of the valid nation codes defined on GTVSDAX, the system then checks for valid values in the following fields:
  • Address Line 1 (cannot be NO VALID ADDRESS, which is treated as null)
  • City
  • State or Province
If all of these fields are null, the system reports an error and does not generate XML for the student. The student's address must be corrected as follows before the data can be successfully transmitted.
  • For tax years before 2013, the data must be corrected on SVATAXC page.
  • For tax year 2013 and later, the data must be corrected on the General Person (SPAIDEN) page and the Calculation of Relevé 8 Process (SVPREL8) must be re-run.

If the Address Line 1 field is not null, the system generates a XML transmission file for the student, even though the city and state (or province) are null. In this case, the value xxx is used for the associated elements in the XML transmission file.

Specific error messages will be reported in the .LOG file if at least one of the above criteria is not met, and the process will be terminated immediately.

The student address reported in the XML file is the one from the SVBTAXC table for years before 2013, or from SVBREL8 for 2013 and later, populated by running SVPTAXC process or SVPREL8 process, and depending on the Address Type Hierarchy parameter. For more information on address-related errors reported in the LIS file, refer to the data in SVBTAXC or SVBREL8.

For tax year 2013 and later, this report determines whether an address has changed, and if so, does the following when the record has not been transmitted:
  • Generates an XML record with the latest address information in the XML file
  • Updates the address related columns in the Relevé 8 Taxation (SVBREL8) table

The institution needs to send the XML file to the Revenu Québec. If Revenu Québec rejects or the XML file is not valid, then a new file must be sent.

Note: Ellucian recommends that you run the SVPTAXC and SVPREL8 processes before the SVRRELX report to make sure that the reported data is the most recent.
The XML file name has a format of AAPPPPPPSSS.xml , where the values are as follows:
  • AA: Last two digits of the tax year. The number must be greater than 07.
  • PPPPPP: Six digits that are after the NP in the transmitter number. The value must be the same as the value in the Transmitter Number field on the Relevé 8 SML Transmission Information Control (SVAXLTM) page.
  • SSS: Sequence number between 001 and 999. The number is a one up number, and is not dependant on the content of the file. If the sequence number reaches 999, the number will begin from 001.
Different XML files are generated by the process and you may have to send to Revenu Québec a summary RL-8 (RL-8.S-V (2010-10)), contact Revenu Québec if you have questions.

If you have to send the summary with your XML file, all the needed information is present in the .LIS file.

When the process runs out of XML sequence numbers an error is reported and the process is aborted.

Data that is not valid will not be printed in the XML file as the file is validated against the XML schema.

    Retransmit File No Name of the XML file (in AAPPPPPPSSS.xml format) to be retransmitted. If a value is specified for this parameter, the process ignores any values entered for other parameters other than the Tax Year parameter.

    The new file will have the same name as the file that was originally transmitted, and it will contain the same students as in the original file. If the validation processes in SVRRELX detects any record as not valid, the new file will be deleted and no file will be generated until the problems are corrected.
