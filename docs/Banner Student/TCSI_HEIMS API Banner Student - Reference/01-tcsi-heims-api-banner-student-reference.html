Course File Data (SKADRCO) page

Use this page to enter or display program-specific data elements that cannot be mapped to existing Banner fields.

The relationships between course and course of study are as follows.

  • One course of study can be attached to many courses.
  • Each course may only have one course of study.

The relationships between program and course are as follows.

  • One course can be attached to many programs.
  • Each program may only have one course.
When a course is assigned to two programs, the following values must also be the same for those two programs:
  • Course of study
  • Course type
  • Program EFTSL
  • Combined course of study indicator
When a course of study is assigned to two courses (and therefore a number of programs), the following values must also be the same for those two courses (and the associated programs):
  • Course type
  • Program EFTSL
  • Combined course of study indicator

Check for Original File Submission section

The SKADREV page checks the DEEWR Student Load-Liability File Locked Data Table (SKRDLLL), or the VFH Student Load-Liability Locked File Data Table (SKRLVLL) to determine whether the student’s record was included in the original submission to DEEWR.

If the student was not included in that original submission, then Revisions cannot be processed for that student and the record must be included in the next available DEEWR submission. This check does not affect the registrations displayed in the Revised Registrations section, and it simply establishes whether the student has been reported in an LL or VLL file for the period selected. The year, reporting period, and submission in the key lock refer to the values set up on the Reporting Calendar (SKAREPT) page.

If the Higher Education option is selected in the Key block, the check for original file submission will be performed on the DEEWR Student Load-Liability File Locked Data Table (SKRDLLL).

If the VET FEE-HELP option is selected in the Key block, the check for original file submission will be performed on the VFH Student Load-Liability File Locked Data Table (SKRLVLL).

If the OS-HELP Revision option is selected in the Key block, there will be a check for original submission.

If the SA-HELP Revision option is selected in the Key block, there will be a check for original submission.

This section records the information that the student’s record was not originally reported and allows the user to indicate the next submission in which the student’s record will be reported.

Field Description
Student not reported in original submission Check box used to indicate whether the student was reported in the original submission for the year, reporting and submission specified in the Key block.
Next Submission Next submission details for the selected ID. Valid values are:
  • Academic Year = Code of the academic year.
  • Reporting Period = Reporting period for the selected academic year.
  • Submission = Submission code for the selected academic year and reporting period.

Reporting periods and submissions must be set up on SKAREPT.

Revision Summary section

Use this section to enter or display record revision details for the ID and registration term specified in the Key block.

If the All Registrations check box is checked, and the data is for a term that is later than or equal to the term code set for the BANNER-FROM-REG-TERM system parameter, then all records whose SFRSTCR term code matches the terms listed on SKAREPT for the year, reporting period, and submission specified in the Key block are displayed. If the optional term field is entered in the Key block, then this section displays all registrations which match the year, report period, submission and term. If the All Registrations check box is checked, and the data is for a term that is earlier the term code set for the BANNER-FROM-REG-TERM system parameter, then all records whose SHRTCKN term code matches the terms listed on SKAREPT for the year, reporting period, and submission specified in the Key block are displayed. If the optional term field is entered in the Key block, then this section displays all records which match the year, report period, submission and term. This section also displays any records that are saved to the Revisions Tracking Table (SKRDREV). Where a record is saved to SKRDREV already, the saved record is shown in preference to the record with the same CRN from SFRSTCR.

If the All Registrations check box is cleared, no registrations from SFRSTCR or SHRTCKN are displayed. Instead, records from SKRDREV (if any) are displayed, and users may select individual records from SFRSTCR/SHRTCKN using the search feature accessed through the drop-down arrow under the CRN label.

There will not be any attempts made to distinguish registrations in VET FEE-HELP programs from registrations in Higher Education programs beyond the study path features described in the following section.

Update Locked Data window

The Update Locked Data window displays the updateable fields for those data elements that would normally be updated by correcting the student's registration.

In the case of data that was migrated to Banner, there will be no Banner registration record, so this Update Locked Data tab provides a mechanism for correcting this EFTSL and Liability data.

This tab will only be enabled when the data that needs to be revised is from a term that is earlier than the term set for the BANNER-REG-FROM-TERM system parameter.

When the All Registrations check box is checked, the fields are populated with data from the relevant SKRDLLL or SKRLVLL locked data table. When the All Registrations check box is not checked, these fields are not populated.

In both cases, the fields are able to be updated so that corrected data can be reported to DEEWR.

TCSI Notifications (SOATNOT) page

The SOATNOT page allows you to view notifications received from TCSI.

You can view the following in the SOATNOT page.
  • Data from the SOTINOT table, that is populated when you run the GET notifications, using the SOPHEIM process.
  • All notifications for an organisation or notifications for the organisations that you received from a particular date.
  • Records in a grid view or in a single record view.
Mostly, if a notification requires corrective action, you can return to the SOATNOT page, and check the Processed indicator after that corrective action is successfully processed.

In the case of CHESSN Allocations, the SOPHIMP process updates the Processed indicator when the CHESSN is successfully retrieved and loaded into the SKRCHSN table.
