Curriculum Mapping

Data migration from Staging tables to Electronic Admissions Application tables (SARSTML) process

The SARSTML process allows you to push data from the Ethos Staging Tables to the Electronic Admission Tables for admissions processing. You can also load changed biographic and demographic information for existing admission records to the target Banner tables to maintain the latest updates for candidates.

To proceed with the SARSTML process, ensure the following:
  • To run the SARSTML process, you must first create the curriculum mapping rules in the Curriculum Mapping (SOACMAP) page for the academic year to map the incoming DfE applications curricula to Banner curricula.
  • You must assign each rule to a term within that academic year.
  • Any terms that you use in the SOACMAP page should be set up in the SOATERM page before you associate the term with a curriculum mapping rule.
  • As per the program and majors that you assign in the SOACMAP page, the curricula rules and the associated major rules should exist in the SOACURR page.
  • The Provider Code and the Campus fields must have a valid value in the SOAXREF page, for the STVSBGI and STVCAMP labels, respectively.
The Ethos Staging Tables comprises data coming from Ethos APIs and resides in the following distinct tables:
  • Ethos Admissions Staging (SAREAAS) table
  • Ethos References Staging (SAREARS) table
  • Ethos Work Experience Staging (SAREAES) table
  • Ethos Qualifications Staging (SAREAQS) table
The SARSTML process pushes the application data from the staging tables to the Electronic Admissions tables, for candidates without any admissions records that exist. The SARSTML process uses the following validations.
  • Validates if there are any entry curriculum for application is established in SOACMAP.
  • Validates if the Name field exists in application.
  • Validates if the City field exists in application; if not, passes the dot (.) value.
  • Validates if the application is already loaded to the target admissions tables in Banner by the SARETMT or SAAEAPS processes.
The SARSTML process uses the following parameters.
Parameter Name Required Description Values
Run Mode (A=Audit, U=Update) Yes Enter A for Audit mode or U for Update mode  
Application ID No Enter the Application ID of applicant  
Academic Year Yes Enter the year to which applications should be pushed to EA tables STVACYR
Note: Execute the process in Update Mode (U) for applications that you want to push to EA tables.

You can leave the Applicant ID as blank. In such cases, all applications pertaining to specified academic year (not already pushed) are loaded to the EA tables.

How the SARSTML process functions

When you run SARSTML, the process functions in the following ways.
  • The process loads the maximum sequence application number for all applications to the EA tables. After the process loads an application to the EA tables, the SAREAAS_PROCESS_IND is set to Y.
  • For applications already available in the EA tables without admissions records, there can be a new sequence for the application available in staging. The SARSTML process replaces the existing data from EA with the latest application information from staging.
  • For applications with the existing admission records, any changed biographic or demographic data (changes to name, telephone number, email address, and other candidate information) for DfE candidates is directly loaded to the target tables in Banner from staging.
    Note: The dfe-applications-submission-api handles the changes to the curricula. The SARSTML process does not update the admissions curricula for applications.
  • After a download of the defer status and updates for applications, the SARSTML process loads the defer attributes for the applications to the SAAQUAN page.
  • After institutions reinstate DfE applications, by applying the confirmed deferred offer decision to the current recruitment year, Ellucian recommends that you download the application updates from DfE to staging. On running the SARSTML process after the application updates download for the applied course year, the SARSTML process creates new applications in the EA tables. The new application from the SARSTML process is available for the term code that is mapped to the application's offer course start date and offer curricula. You can now verify the new applications that the SARSTML process creates in the SAAETBL page.
    Note: To create the offer start date to term code mappings, use the SOAXREF page for the STVTERM identifier and create mappings. Refer to the Term Codes section under setup Crosswalk Rules for more

    Ensure that you set up all the DfE courses correctly for all term codes, that you require to create admissions applications.

    If institutions do not download the updates after an confirm deferred offer, the SARSTML process will not create the new application.

  • The SARSTML process loads the phone numbers from Staging to the SARPHON table in the required EA format to avoid truncation of digits in the Common Matching Entry (GOAMTCH) page.
  • The SARSTML process derives the Banner Campus Code from the concatenated campus codes that are set up in the SOAXREF page. The process creates applications in EA for the appropriate Banner curricula as defined in the SOACMAP page.

Telephone/email rules

The following are the rules that the SARSTML process follows to update the target tables with the changed telephone/email information.
  • DFEINACTIVETELE: The DFEINACTIVETELE rule for DFEG rule group determines if the previous telephone numbers for applicants in the SPRTELE table is to be updated as Inactive, when a telephone number update comes for the candidates from DfE. Institutions can set it up as Y or N.
    Note: If set to Y, the previous telephone number records in the SPRTELE table for candidates are updated to inactive and not primary, while the latest telephone number is inserted as active and primary.

    Previous SPRTELE record gets updated with SPRTELE_STATUS_IND ='I' and SPRTELE_PRIMARY_IND = 'null'. The new telephone record in SPRTELE is inserted with the latest telephone number where SPRTELE_STATUS_IND = null and the SPRTELE_PRIMARY_IND = 'Y'.

    If set to N, the old telephone number records in SPRTELE is not updated to inactive, it is just updated as not primary, while the latest telephone number is inserted as active and primary.

    Previous SPRTELE record gets updated with SPRTELE_PRIMARY_IND = 'null', while SPRTELE_STATUS_IND = ‘null’ and the new record in SPRTELE is inserted with latest phone where SPRTELE_STATUS_IND = null and update SPRTELE_PRIMARY_IND = 'Y'.

  • DFEINACTIVEMAIL: The DFEINACTIVEMAIL rule for DFEG rule group determines if the previous email records for candidates in the GOREMAL table is to be updated as Inactive, when an email address update comes for candidates from DfE. Institutions can set it up as Y or N.
    Note: If set to Y, then the previous email records in GOREMAL for candidates are updated to inactive and not preferred, while the latest email is inserted as active and preferred.

    Previous record is updated with GOREMAL_STATUS_IND =’I' and GOREMAL_PREFERRED_IND = ‘N’ and the new email record in GOREMAL is inserted with GOREMAL_STATUS_IND =’A’ and GOREMAL_PREFERRED_IND = ‘Y’.

    If set to N, then the old email in GOREMAL is not updated to inactive, it is just updated as not preferred, while the latest email is inserted as active and preferred.

    Previous record is updated with GOREMAL_PREFERRED_IND = ‘N’, while GOREMAL_STATUS_IND remains active (A). The new email record in GOREMAL is inserted with GOREMAL_STATUS_IND =’A’ and GOREMAL_PREFERRED_IND = ‘Y’.

SARSTML process output

For the admissions processing, the SARSTML output for applications is loaded to the EA tables. The application information is inherent in the Electronic Admissions Processing, and a Web ID and AIDM gets generated per applicant. For candidates with existing admission records, any changed biographic and demographic data, candidate application information is loaded to the target Banner tables directly.

Executing the SARSTML process, generates the sarstml.log and sarstml.lis files as output files. The sarstml.log file records the outcome of the SARSTML job run.

For admissions processing, if the applications are pushed to EA tables successfully on executing the SARSTML process, the sarstml.log records the AIDM generated for applicants. The SAREAAS_PROCESS_IND column is updated to ‘Y’ denoting application is loaded to EA successfully.

If applications are not pushed to EA tables due to validation errors, the errors encountered gets displayed in the sarstml.log file. The SAREAAS_PROCESS_IND column is updated to ‘N’ denoting that the application is not pushed.

Institutions can manually correct the push errors encountered for applications in the sarstml.log and execute the SARSTML process again.

Note: If you encounter ORA errors (Oracle errors) for an application (for example, where incoming data type/field length is not matching the EA data type/field length), the SARSTML process aborts the subsequent applications processing. The sarstml.log file contains the ORA errors.
The SARSTML process calls the existing baseline packages to update the candidate information. Institutions can view the changed information on the SPAIDEN page. The following are the package details:
  • gb_identification: Name changes to the SPRIDEN table
  • gb_bio: – DOB change to the SPBPERS table
  • gb_address: Address changes to the SPRADDR table
  • gb_email: Email changes to the GOREMAL table
  • gb_telephone: Telephone changes to the SPRTELE table
    Note: Updates to the SARQUAN table gets loaded directly and are displayed in the SAAQUAN page. The SARSTML process also loads the Nationality, Ethnicity, and Disability Data to the GORPISD table to facilitate HESA reporting.
  • The SARSTML process creates new applications for the mapped term code and curricula. These new applications are for the applications that are deferred previously, and are now confirmed in the next recruitment cycle year.
  • The SARSTML process will not create applications and validation errors that appears in the sarstml.log file, if the term code mapping does not exist in the SOAXREF page for STVTERM identifier and curricula mappings that do not exist in SOACMAP.

The SAREAAS_PROCESS_IND process indicator field denotes the following:

Name Description
SAREAAS_PROCESS_IND = ‘N’ Indicates that applications are not pushed to EA tables
SAREAAS_PROCESS_IND = ‘Y’ Indicates that applications are pushed to the EA tables
SAREAAS_PROCESS_IND = ‘O’ Indicates applications status as Offer
SAREAAS_PROCESS_IND = ‘R’ Indicates applications status as Recruited
SAREAAS_PROCESS_IND = ‘J’ Indicates applications status as Rejected
SAREAAS_PROCESS_IND = ‘P’ Indicates applications status as Pending Conditions
SAREAAS_PROCESS_IND = ‘W’ Process indicator to indicate applications status as Withdrawn.
SAREAAS_PROCESS_IND = ‘F’ Process indicator to indicate applications status as Deferred.

Curriculum Map Rules Roll (SOPCROL) process

The SOPCROL process allows you to roll curriculum mapping rules from one academic year to another.

Note: To run the SOPCROL process, you must have first created the curriculum mapping rules in the Curriculum Mapping (SOACMAP) page for the academic year that you want to copy from. Each rule must be assigned to a term within that academic year.

Any terms used in the SOACMAP page should be set up in the SOATERM page before you associate the term with a curriculum mapping rule. Any curriculum rule should have a program code before you associate the curriculum with a curriculum mapping rule.

When curriculum mapping rules are rolled from one academic year to another, it is expected that terms are created in the 'To Year' that follow the same pattern as terms that are used for rules in the 'From Year'. For example, if rules exist in the year 2020 for the 202010 term and to be rolled to the year 2021, the process attempts to roll the rules to the 202110 term.

If the term calculated for the 'To Year' does not exist in the STVTERM page, the corresponding rule(s) will not be rolled to the 'To Year' and the system displays an error message in the report output.

If the term calculated for the 'To Year' does exist in the STVTERM page, but has not been set up in the SOATERM page, the corresponding rule(s) will only be rolled to the 'To Year', if the value of the 'Roll if no valid term (Y/N)' parameter is Y.

The report output displays messages to indicate that the new term is not in the SOATERM page and whether the rule is copied. If the associated curriculum is OFF for both Recruiting and Admissions, the corresponding rule(s) will only be rolled to the 'To Year' if the value of the 'Roll invalid curriculum (Y/N)' parameter is 'Y'. The report output displays messages to indicate that the curriculum is OFF for those modules and whether the rule has been copied.

If the rule has a part of term and if that same part of term code is not created for the term calculated for the 'To Year', then corresponding rule(s) will not be rolled to the 'To Year' and the system displays an error message in the report output. If the rule in the 'From Year' is not active, then it will not be rolled to the 'To Year' and the system displays an error message in the report output.

If the rule in the 'From Year' is already created in the 'To Year', the rule will not be rolled to the 'To Year' and the system displays an information message in the report output. The process is repeatable. Hence, if the process runs in Update mode with some rules being rolled successfully, you can re-run the process to roll more rules after any necessary corrections.

The output displays information for every rule, whether it has been successfully rolled, rolled with warning, already exists in the 'To Year', or has an error that prevents it from being rolled.

The process has the following parameters.

Parameter Name Required Description Values
From Year Yes Enter the year from which curriculum mapping rules are to be rolled. Academic Year Validation (STVACYR) page
To Year Yes Enter the year to which curriculum mapping rules are to be rolled. Academic Year Validation (STVACYR) page
Run Mode (A=Audit, U=Update) Yes Enter A for Audit mode or U for Update mode  
Roll invalid curriculum (Y/N) Yes Should a rule be rolled if the curriculum is no longer valid in Recruiting and Admissions?  
Roll if no valid term (Y/N) Yes Should a rule be rolled if the term in the To Year is not valid in the SOATERM page?
