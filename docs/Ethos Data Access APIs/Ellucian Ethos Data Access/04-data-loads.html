Data loads

The data load process

Ellucian Ethos Data Access gathers data from authoritative sources, and stores the data to the cloud data storage, whether they are deployed on premises or in the cloud.

The Current Data tab lists the configured resources for a selected authoritative source application and the current number of records in Ellucian Ethos Data Access for each resource. Use this tab to start the data load of resources from the authoritative source to Ellucian Ethos Data Access and also to monitor the live count of resource records as the change notifications come in.

The Data Loads tab provides more information about completed loads and the Change Notifications tab provides more information about updates to data that was loaded. These tabs also include any error messages related to loads and updates respectively.

Data model extensibility

Ellucian Ethos Data Access enables data model extensibility. Data model extensibility allows Ethos Integration to support the variable and dynamic nature of application integration, without modifying enterprise level systems.

Data model extensibility can be accomplished in the following ways:

  • By creating new institutional data models.
  • By extending existing Ellucian Ethos Data Models.
Example - Use case

Ellucian Ethos Data Access enables an institution or a partner to extend Ellucian Ethos Data Models and access the extended data models through GraphQL.

The following scenario depicts a use case where it would be appropriate and beneficial to extend an Ellucian Ethos Data Model.

For this scenario, consider the Ellucian Ethos Data Model resource Buildings. The Buildings resource in the higher education domain is defined as physical structures with rooms located in specified physical locations. For this scenario, we will focus only on a small subset of the published schema. The following is an example of the Buildings resource schema in JSON format.

"id": {
            "title": "ID",
            "description": "A global identifier of a building for use in all external references to the building.",
            "type": "string",
            "format": "guid",
            "pattern": "^[a-f0-9]{8}(?:-[a-f0-9]{4}){3}-[a-f0-9]{12}$"
        },
        "code": {
            "title": "Code",
            "description": "A code that identifies the building.",
            "type": "string"
        },
        "title": {
            "title": "Title",
            "description": "The full name of the building.",
            "type": "string",
            "minLength": 1
        }

At your institution, this schema will generally represent buildings found on your campus. However, assume we have a requirement that a downstream system needs the building capacity exposed within the resource. In our authoritative source system, Building capacity information is available, but this property is not supported by default in the Buildings Data Model. In such case, we can extend the Buildings data model with an additional property.

After extending the Buildings data model in Data Access to include the building capacity, the extended Buildings data model schema would appear as follows:

"maxCapacity": {
            "title": "Max Capacity",
            "description": "testing",
            "userEdited": true,
            "type": "number",
            "minimum": 10,
            "maximum": 500,
            "formatNumberType": "none",
            "isFormat": true,
            "elementIndex": 0
        },
        "id": {
            "title": "ID",
            "description": "A global identifier of a building for use in all external references to the building.",
            "type": "string",
            "format": "guid",
            "pattern": "^[a-f0-9]{8}(?:-[a-f0-9]{4}){3}-[a-f0-9]{12}$"
        },
        "code": {
            "title": "Code",
            "description": "A code that identifies the building.",
            "type": "string"
        },
        "title": {
            "title": "Title",
            "description": "The full name of the building.",
            "type": "string",
            "minLength": 1
        }

This simple example demonstrates how to extend an Data Model schema with numeric data. However, Ellucian Ethos Data Access supports more complex data types and use cases.

Add properties to a data model

You can add properties to the existing properties of an Ellucian Ethos Data Model or institutional data model.

About this task

When you have an existing Ellucian Ethos Data Model you can add properties to it (extend it). This is primarily used so that GraphQL users can extend their queries.

You can extend one data model at a time.

Procedure

  1. Log in to Ellucian Ethos Data Access.
  2. On the Current Data pane, select a data model from the list to access a desired data model.
    If you are unable to find the specific data model in the data models list, click Filter to locate it. See Filter for a data model.
  3. Click Extend .
    The data model page for the resource displays.
    Note: The latest version is selected for the Ellucian Ethos Data Model by default. However, when you add or edit a property to a data model version that is not the latest version, you will see the last selected version on the data model page after you save the changes.
  4. Select another version of the data model, if required.
    Version is not applicable for an institutional data model.
  5. In the data model window, click the plus icon to add a property.
  6. On the Add Property page, enter the details as follows:
    Label Description
    Title*
    Enter a unique title.
    • The data model title is case insensitive.

      Example: Consider ABC and abc are same, and not allowed to repeat it.

    • Special character and number are not allowed.
    • Spaces can be used.

    Example value: ABC XYZ
    Name This field auto fills content as you type the title in the Title field. The first word of the title will convert to lowercase and subsequent words will be converted to camel case and spaces between words will be removed. You are prohibited to edit the Name field.

    Example value: abcXyz
    Description Enter the description for the property. This is an optional field.
    Nullable property If you want to make the property value optional, select the check box.
    Type Set the property type. Options include string, number, or object.
    Add another property If you want to add another property, select the check box.

    * indicates a required field.

  7. Set the property Type. The property Type supports string, number, and object types.
    • string: Default property type.

      Select one of the values from String Type drop-down list.

      • none: Default string type. The Minimum Length and Maximum Length are optional.
        Note: If Minimum Length is specified, Maximum Length value must be greater than or equal to Minimum Length.
      • Select date if the string type is date.
      • Select utcDateTime if the string type is utcDateTime.
    • number: Enter the value in Minimum and Maximum field as needed.
      Note: If Minimum value is specified, Maximum value must be greater than or equal to Minimum.
    • object: Choose Object as data type, if you intend to hold child properties within a parent property. Child properties can be heterogeneous; that is, any combination of data types can be used.
  8. Click Add.
    The Added property successfully message briefly displays. If you selected the check box to Add another property, a new Add Property page displays.
  9. Repeat the process on the Add Property page for each property that you want to add.
    The newly added property displays at the bottom of the properties list. See Rearrange the properties for a data model for details on how to reorder the sequence of a property.
  10. Optional: Add child properties to an Object type property.
    1. Click the More options icon next to the object property and select Add.
    2. Add a Title for the child property.
    3. In the Type field, enter string, number or object child properties.
    4. Click Add.
    5. Optional: If you want to add another child property to that object, select the Add another property check box.
      A new Add Property page displays.
    6. Repeat the process on the Add Property page for each property that you want to add.
      The newly added child property or (properties) displays under the Object property.
    You can add a maximum of four levels of nested objects.
  11. Required: Click Optimize on the resource after extending it if you have already loaded it.

Delete properties for a data model

  • You can not delete the ID and Title properties of institutional data model with a lock icon.

Procedure

  1. Log in to Ellucian Ethos Data Access.
  2. On the Current Data page, select a data model from the list to access a desired data model.

  1. Log in to Ellucian Ethos Data Access.
  2. Click Filter .
  3. Filter the list by resource name, number of current records in Data Access, or load status.
    Filter Description
    Resource Enter a resource name.
    Current Records Enter the number of current records and specify one of the following:
    • exactly
    • between
    • less than
    • greater than
    Status

    Select the load status you want to filter:

    • All

    • Load in progress

  5. Optional: Click Clear Filters to disable the filter option.

Assign and reassign child properties to an object

You can assign or reassign child properties of an Ellucian Ethos Data Model or institutional data model to an object.

About this task

You can move the child properties of an Ellucian Ethos Data Model or institutional data model to assign it under some object or reassign and bring it back to the root (main schema) level.

Procedure

  1. Log in to Ellucian Ethos Data Access.
  2. On the Current Data pane, select a data model from the list to access a desired data model.
    If you are unable to find the specific data model in the data models list, click Filter to locate it.
  3. Click Extend .
    The data model page for the resource displays. The latest version is selected for Data Model by default.
  4. Select another version of the data model, if required.
  5. To assign or reasssign child properties to an object, click the More options icon next to the property that you want to move and click Move To.

Populate the cloud storage with the initial data load

The initial data load populates the cloud storage.

Before you begin

If you have made change to a data model extension, be sure the change is published before you load it in Data Access. For details, refer to Data model extensibility and Reload the cloud storage.

Procedure

  1. From the Ellucian Customer Center, click Tools.
  2. In the Ethos menu, click the Data Access link for your region.
  3. Select the desired environment and tenant (if applicable).
  4. On the Current Data tab, select your authoritative source from the drop-down field at the top of the page.

    The page displays the list of resources as defined in the authoritative source in Ellucian Ethos Integration.

    Notice that the Record Count for all resources is 0. This indicates that no records for these resources have been loaded to the cloud storage.

  5. Select the check box next to the resources you want to load into the cloud storage.
    You only need to load data from the resources your data consumer applications will be accessing.
    1. Optional: For a paginated load only (where Data Access makes Ethos API calls to load data from). If you are loading a resource that requires a load filter, such as ledger-activities, select the filter value in the Load Filter column.
      For example, find the ledger-activities resource and select Fiscal Year: 2018.
      Data Access requires you to use load filters for resources with an extremely large number of data records. These load filters restrict the number of incoming data records and allow the data load to complete in a timely manner. If you do not select a value, Data Access loads the records for the first value of the drop-down list.
      This does not work for a file bulk load. There is a separate process to provide load filters for file bulk loads. See Filter bulk load.
  6. Click Load to load the data for these resources.
    Monitor the load progress (%) indicator. Load time can vary for each resource, depending on the number of records being loaded.
    To see the details of the loading data, go to the Data Loads tab, then click Refresh to refresh the data display.
  7. Optional: If this is a Shared Technology Platform (STP) tenant, some resources might be listed under more than one application owner. You might want to load the data from each application owner of the resource. Do note that shared resources, identified with an asterisk on their name, can be loaded only from the application that has been configured as the Designated Owner of Shared Data.

    To see an example of a Shared Technology Platform (STP) data load for a shared application, refer to Example Shared Technology Platform data load for a shared application.

  8. Optional: If necessary, you can Cancel a data load.
    You can cancel the data load only while the Cancel button appears. When the finalizing status appears, Data Access is completing the necessary actions to make the records available to applications.
  9. Repeat these steps any time new resources are defined for your authoritative source.
    Note: Data Access turns on change notifications for a resource after its initial load.

What to do next

After you have successfully loaded your data:

If you are configuring Data Access for GraphQL, refer to GraphQL requests or Make GraphQL requests to Data Access.

Example Shared Technology Platform data load for a shared application

In a Shared Technology Platform configuration, multiple authoritative sources can share or own the same resource.

For example, the Campus Card System needs access to building information that is in the housing-assignments data model, so that it can control access to campus housing. The North Campus and the Main Campus are authoritative for the housing-assignments data model, and this information resides in a single Banner application. On the other hand, all of the information from the students data model, also in Banner, is shared between the two campuses.



For the Campus Card System to be able to request the data it needs from Data Access, the resources need to be bulk loaded into Data Access. For the housing-assignments resource, because it has two independent authoritative sources, each needs to be bulk loaded separately, following the steps as indicated on Populate the cloud storage with the initial data load. These steps should be performed twice: a first time, selecting the North Campus authoritative source; and the second time, selecting the Main Campus authoritative source.

Because housing-assignments from North Campus is handled separately from Main Campus, you will see a different count of records loaded into Data Access for the resource, depending on which authoritative source owns it. In a similar fashion, change notification updates coming into the resource will be received from both sources, independently from each other.

For the students data, North Campus and Main Campus have access to the full list of students in the institution, so the information is considered shared. For these cases, a third authoritative source, Shared, is defined in Ethos Integration as the shared data owner for the students resource. In Data Access, students are identified as a shared resource (its name is followed by an asterisk). As a result, it only needs to be loaded one time when selecting the Shared application as defined in Ethos Integration and following the steps as indicated on Populate the cloud storage with the initial data load.

For additional information, refer to Create the applications in Ethos Integration for Banner (MEP), Support for multiple ownership of resources, and Set up an application to subscribe to changes published by Banner (MEP).

Reload the cloud storage

After the initial data load, you might need to reload the cloud storage in certain conditions.

About this task

Ellucian recommends reloading the cloud storage after changes to:
  • A resource's privacy settings
  • The authoritative source version
  • The authoritative source application
When Data Access detects changes in privacy settings, the authoritative source application, or the authoritative source version, it displays an outdated status tag next to the affected resource on the Current Data tab. To see the reason for the suggested data reload, point to the outdated status tag for that resource.
Warning: Ellucian recommends you do not rely on the outdated status tag as the only indication to reload resource data. You should reload the resource data as appropriate for your institution.

Procedure

  1. Select the Data Access environment where you want to perform this procedure.
    1. In Data Access, click the settings icon.
    2. Select the Environment where you want to perform this procedure.
      If you have access to multiple tenants, select both the tenant and environment.
  2. Click the Current Data tab.
  3. Select your authoritative source from the drop-down field at the top of the page.
  4. Select the resources to reload.
    Use the filter icon to narrow the list of resources. You can filter the list by resource name, number of current records in Data Access, or load status.
    1. Optional: If you are reloading a resource which requires you to filter the incoming records, select the filter value in the Load Filter column.
      • Selecting a Load Filter value that you previously loaded will replace the data for that filter.
      • Selecting a Load Filter value that you have not previously loaded will add new data to the cloud storage. Previously loaded data for a different Load Filter value will not be overwritten.
      To determine which filtered data was previously loaded for that resource, click the Current Records (Data Access) value for that resource on the Current Data tab. Alternately, go to the Data Loads tab and click the Records Loaded value for the specified resource.
  5. Click Reload to reload the selected resources.
    Monitor the load progress (%) indicator. Load time can vary for each resource, depending on the number of records being loaded.
    To see the details of the loading data, go to the Data Loads tab. Click Refresh to refresh the data display.
  6. Optional: If this is a Shared Technology Platform (STP) tenant, some resources might be listed under more than one application owner. You might want to reload the data from each application owner of the resource. Please note that shared resources, identified with an asterisk on their name, can be loaded only from the application that has been configured as its Designated Owner of Shared Data.

    To see an example of a Shared Technology Platform data load for a shared application, refer to Example Shared Technology Platform data load for a shared application.

  7. Optional: If necessary, you can Cancel a data load.
    You can cancel the data load only while the Cancel button appears. When the finalizing status appears, Data Access is completing the necessary actions to make the records available to applications.

Manual Optimization

After data is loaded, in some cases, administrators need to request the manual optimization of a resource.

About this task

Optimization allows indexes to be created so GraphQL data requests by data consumers can perform better. Additionally, metadata is created from array properties so these can also be available for querying.

After resources are bulk loaded, optimization is automatically performed on them, to prepare them for GraphQL requests by data consumers. Refer to GraphQL requests.

Use the procedure below to manually optimize resources in these situations:
  • There were errors reported in the initial optimization attempt.
  • You loaded data in the test environment before December 18, 2019. Data before that date was not automatically optimized.
  • You loaded data in the production environment before January 15, 2020. Data before that date was not automatically optimized.

Procedure

  1. From the Ellucian Customer Center, click Tools.
  2. In the Ethos menu, click the Data Access link for your region.
  3. Select the desired environment and tenant (if applicable).
  4. On the Current Data tab, select your authoritative source from the drop-down field at the top of the page.
  5. Select the check box next to the resources you want to optimize.
    Note: Only loaded resources can be optimized. If the resource has not been loaded, or has been flagged as outdated and needs to be reloaded, then follow the load or reload steps. This will automatically perform the optimization at the end of the process.
  6. Click Optimize for the selected resources.
    The optimizing tag displays while the optimization process is taking place. Optimizing time can vary per resources, depending on the number of records.
    The Optimize button displays as disabled if one or more of the selected resources cannot be optimized, for example, if it is not loaded or if it is flagged as outdated.
    You cannot cancel this process after it has started.
  7. Repeat these steps for additional sources and resources.

S3 file bulk load status property

When you initiate a S3 file bulk load, the Current Data tab displays the status of S3 Bulkload initiated as a badge in the last column, until all files are written to S3.

Clicking the Refresh status button makes an API request to the source system to check the status of the S3 file bulk load. This polls the source system for the status of the load for five minutes, in five second intervals. When the five minutes are complete, the Refresh status button is available again. Status and progress information display as steps.

When the bulk load is in the inProgress phase, the status column shows the progress of the steps as they complete. The inProgress status means that the source system is going through the process of extracting, transforming, and loading data and writing one or more files to a predefined S3 bucket.

The extracting, transforming, and loading process that happens at the source can take anywhere from seconds to days, depending on the number of records being loaded. After files are written to S3, data is loaded into Data Access. Data Access takes over to ingest files and persist data into the database. A Cancel badge becomes available at this time.

Note: If a source system does not support this standard yet, Data Access is backwards-compatible to the old style API response.

When Data Access encounters the old style API response after you click the Refresh status button, the status displays as Preparing during the process of extracting, transforming, and loading data and writing one or more files to a predefined S3 bucket.

The new display of loading progress phases applies only to Banner customers using API version 9.22 or higher.

Data Loads tab

The Data Loads tab displays details for recent data loads to the cloud data storage. Sort the table on any column by clicking on the column header, or use the filter to narrow the data loads list.

Column Description
Date Timestamp of the start of the data load for this resource.
Source authoritative source of the resource.

In STP cases, each load of an authoritative source displays separately from the others. For example, loads for housing-assignments from AppNorth and AppSouth need to be performed separately, and therefore the events will be listed separately in this tab.
Resource Resource name.
Version Ellucian Ethos Data Model version.
Operation Identifies whether the record was created from an initial load, reload, or optimization.
Records Per Page Number of records per page for this resource.
Duration Duration for the data load or reload. Hover over the duration for start and end times.
Records (source) Number of records for this resource on the authoritative source.
Records Loaded Number of records successfully loaded to Data Access.

For resources with load filters, hover over the underlined value to identify which filtered value was included in this data load or reload.

To see all loaded values for this resource, locate the resource on the Current Data tab and click the Current Records (Data Access) value.

If the Records Loaded count differs from the Records (source), refer to the Potential causes of record count differences section below.
Errors Number of errors during the data load, reload, or optimization.

Potential causes of record count differences

If the Records (source) count and Records Loaded count differ, consider these causes.

  • Was the data at the authoritative source updated in any way while the load was in progress? If so, then you should expect a difference in these record counts.

    For example, a data load lasted 15 minutes. If there were any updates, deletes, or creates that could have been submitted at the authoritative source during those 15 minutes, some of these changes may have been sent to Data Access during the ingestion process, but after the initial record count.

    The full set of updates will be processed when the bulk load process completes and the queued change notifications are processed as usual.

  • Did Data Access report errors during a resource load? If so, the number of records affected by these errors can be compared against the difference between the counts reported for Records (source) and Records Loaded.

    Depending on the nature of the error, it might mean records are missing from the cloud data storage.

For concerns about potentially missing data records, contact Action Line to further investigate.
Review data load error messages

If the data load contains errors, Data Access provides additional information to help you troubleshoot the cause of the error.

Procedure

  1. Select the Data Access environment where you want to perform this procedure.
    1. In Data Access, click the settings icon.
    2. Select the Environment where you want to perform this procedure.
      If you have access to multiple tenants, select both the tenant and environment.
  2. On the Data Loads tab, click the arrow or error count to expand the section to display the error messages.
  3. Click More to view additional details provided by the source of the error, either Ellucian Ethos Integration or the authoritative source.
    The error details include Offset and Limit. These help you to locate the error at the authoritative source.
    • Offset indicates which page contains the error.
    • Limit is the page size.

    For example, a data load ingested 10,000 records and the error message states Offset: 50 Limit: 10. This means that the error record is somewhere between record 51 and 60.

  4. Click to download all ingestion error messages on the displayed page to a text file.

Data load troubleshooting

If you encounter issues during data loads, such as slow processing, you may be able to resolve them using Ellucian-recommended procedures.

See also Troubleshooting Data Access bulk load errors.

Cancel a data load

You may want to cancel an in-progress data load or reload. This might happen when you discover authoritative source data inconsistencies at the time of load, so you should cancel the data load and reload.

About this task

When you cancel a resource's reload or initial data load, that resource's data reverts to its previous state.
  • If you cancel a data reload, the records return to the previous set of data before the reload began.
  • If you cancel an initial data load for a resource, Data Access removes all records for that resource.
You can only cancel a data load or reload while the Cancel button appears. When the finalizing status appears, Data Access is completing the necessary actions to make the records available to applications.

Procedure

  1. Select the Data Access environment where you want to perform this procedure.
    1. In Data Access, click the settings icon.
    2. Select the Environment where you want to perform this procedure.
      If you have access to multiple tenants, select both the tenant and environment.
  2. Go to the Current Data tab.
  3. Scroll to find the resource you want to stop the data loading process for.
  4. Click Cancel for the specified resource.
    This only cancels the data load for the specified resource. Other resources continue to load data.

Results

  • If you canceled a resource's initial data load, the resource has 0 records.
  • If you canceled a resource's data reload, the data returns to the previous set of data before the reload began.
  • If you canceled a resource's data reload that has multiple authoritative sources, as in the case of STP, this resets the status of the resource data for the corresponding authoritative source, without affecting the state of the data coming from other authoritative administrator sources.

    For example, housing-assignments is owned by AppNorth and AppSouth. It has already been loaded in AppNorth, with 123 records, and it is loading for the first time in AppSouth. If the load from AppSouth gets canceled, AppSouth returns back to 0 records, but the count from AppNorth is left with its 123 records intact.

Related tasks
  • Populate the cloud storage with the initial data load
  • Reload the cloud storage

Throttle data loads

If you experience slow data loads or failures due to authoritative source timeouts, you may need to throttle the data loads by adjusting how many records are fetched from your authoritative source.

About this task

If Data Access is retrieving more records than your authoritative source can handle, adjusting the page settings can improve data load performance.
  • Page Size determines how many records are retrieved per page of data. Page Size is defined for each resource.
  • Max Concurrent Pages determines how many pages are retrieved in parallel from authoritative source at the same time. Max Concurrent Pages are defined for each resource and at the global level for all resources.
Note: The page settings use recommended values from the authoritative sources and Data Access as defaults. Do not specify custom values unless it is required.

Procedure

  1. Select the Data Access environment where you want to perform this procedure.
    1. In Data Access, click the settings icon.
    2. Select the Environment where you want to perform this procedure.
      If you have access to multiple tenants, select both the tenant and environment.
  2. Go to the Current Data tab.
  3. Select the resource for which you want to adjust the page settings.
  4. For the specified resource, click in the table row of the resource.
  5. Reduce the Page Size value as needed.
  6. Reduce the Max Concurrent Pages setting for the resource as needed.

When you reload the resource, you should see an improvement in performance.

  1. You may still need to adjust the maximum number of pages that Data Access can process for all resources.
    1. Click Settings at the top of the Ellucian Ethos Data Access page.
    2. Reduce the Max Concurrent Pages to reduce the number of pages that can be processed at the same time.
      Note: The total number of pages being loaded across all resources cannot exceed the global Max Concurrent Pages setting.
      A data load for 4 resources is triggered. Each resource has a Max Concurrent Pages setting of 5, so the load would retrieve 20 pages. However, the global Max Concurrent Pages is set to 15. Therefore, only 15 pages can load at one time. The remaining 5 pages will be queued.

API Not Eligible for Bulk Load 
value too long for type character varying(50)

OR

RecordID 100 must be a valid GUID.

OR

The method is not supported by the resource.
 Data Access only supports SPEC APIs and EEDM APIs — not BPAPIs or ERP APIs. A resource must meet all three of the following criteria to be loadable in Data Access.
  1. Must support a GET ALL operation.

    The resource must return data without specifying a GUID in the request. If it does not, Data Access will report: The method is not supported by the resource.

    The GET ALL operation is different from the GET BY ID operation:

    -- GET BY ID (uses a GUID to return one specific record):
GET https://integrate.elluciancloud.com/api/persons/de56342b-24f0-4f5e-b01e-000ca8c0d3ed

-- GET ALL (returns data without specifying a GUID):
GET https://integrate.elluciancloud.com/api/persons

    Example of a resource that does not support GET ALL:

    GET https://integrate.elluciancloud.com/api/account-funds-available-transactions
-- Response: "The method is not supported by the resource."

    This resource only exposes a POST method, confirmed in its /api/resources metadata:

    "name": "account-funds-available-transactions",
"representations": [
  {
    "X-Media-Type": "application/vnd.hedtech.integration.v11+json",
    "methods": [ "post" ]
  }
]
  2. Must support paging / paginated responses (limit and offset)

    The resource must accept limit and offset parameters on a GET ALL request.

    • limit=1 & offset=0 — returns the first record on the first page
    • limit=2 & offset=0 — returns the first two records on the first page
    • limit=2 & offset=1 — returns the third and fourth records on the second page

    Test the resource in Bruno to confirm paging works:

    GET https://integrate.elluciancloud.com/api/persons?offset=700&limit=100
  3. Must expose a 128-bit GUID as its root identifier

    Each record in the response payload must have a valid 128-bit GUID as the value of the id field. If it does not, bulk load will fail.

    Real-world example of a failing resource:

    Resource Name : registration-terms-allowed
Activity time : 9/8/2025 2:56:28 PM CDT
Offset        : N/A
Limit         : 1
Error         : terms-2b25-2ffa must be a valid GUID

    This resource has an LDM.GUID record in Colleague, but it is not a valid 128-bit GUID and cannot be loaded in Data Access.

    What is a GUID? A GUID (Globally Unique Identifier) is a 128-bit number virtually guaranteed to be unique across all time and space, used to uniquely identify entities such as software components, database records, or files. It must be the value of the id property in each node of the response output.

    Example — valid GUID identifier in a persons response:

    GET https://integrate.elluciancloud.com/api/persons/1805ffaf-8a2b-48c7-8f6e-fcd07026ac73

{
  "names": [
    {
      "type": {
        "category": "legal",
        "detail": { "id": "be4d8700-d84d-4dc7-b5e3-1733aab46854" }
      },
      "fullName": "LAST NAME",
      "lastNamePrefix": "LAST",
      "lastName": "LAST NAME",
      "preference": "preferred"
    }
  ],
  "credentials": [
    { "type": "colleaguePersonId", "value": "0000000" }
  ],
  "id": "1805ffaf-8a2b-48c7-8f6e-fcd07026ac73"
}

    How to verify resource capabilities:

    Call the /api/resources endpoint and inspect the metadata for your resource. It must show getAllPatterns with method: get and name: paging. Example from persons v12.6.0:

    GET https://integrate.elluciancloud.com/api/resources

-- persons v12.6.0 — confirms GET ALL + paging are supported:
"getAllPatterns": [
  {
    "name": "paging",
    "method": "get",
    "X-Media-Type": "application/vnd.hedtech.integration.v12.6.0+json"
  }
]

    A resource must satisfy all three requirements — GET ALL, paging, and a valid GUID id to be loaded in Data Access.

    Note: To identify the API type (SPEC, EEDM, BPAPI, ERP), check the API Catalog, the type is listed directly below the API name.
