Structured Registration

This chapter details the setup and processing for Structured Registration.

Overview of Structured Registration

In Banner Student Registration, the term Structured Registration refers to a registration model where students are guided through the class selection based on their academic program requirements.

To use this processing effectively, the academic program definition should be constructed so that the requirements occur in chronological order. In addition, there should be a clear delineation between requirements for each student classification or academic stage. For example, the academic program should have a distinct set of coursework from which the student must choose to progress from Freshman to Sophomore or from Year 1 to Year 2.

For each stage defined in an academic program, there are three categories into which coursework can be divided:
  • Mandatory courses are specific courses the student must take to progress from one stage to the next.
  • Optional courses are courses that relate closely to the student's major, and the student might be asked to choose a number of courses from a specific list.
  • Elective courses are broadly defined selections using course ranges, attributes, departments, and so on.

Settings on the Term Control Page (SOATERM) provide processing controls that define when mandatory, optional, or elective coursework is available for students to select in Self-Service. Students may only add and drop classes that are part of Structured Registration if the type (mandatory, optional, or elective) is active.

SOATERM also contains Error Severity controls that allow unsatisfied requirements to be considered as a fatal error, a warning, or no error. When error checking is set to Fatal, the student will not be able to save any of the registration selections until all requirements are met. When error checking is set to Warning or None, the student may continue with registration even when all requirements have not been met.

You also have configuration options on SOATERM that allow you to decide whether courses that a student has already completed or has in progress should update the met/not met indicator for the requirements in their current term of study.

Rules on the Crosswalk Validation Page (GTVSDAX) serve as processing controls for CAPP areas using class codes, student attributes, priorities, or naming conventions.

CAPP overview

Structured Registration uses CAPP rules and programs to facilitate registration.

With CAPP, Banner Registration Self-Service displays courses that specifically relate to the student's primary academic program or the student's selected study path. Students must register for the courses presented to them. They cannot directly enter CRNs or search for classes that do not meet the CAPP criteria.

Note: If you do not use CAPP, you can define and use an external API that will request data from a third party degree audit system and create a list of prescribed courses that Banner will process. Refer to Use external API to set up processing with third party applications.

For CAPP program definitions in Structured Registration, Banner uses guidelines to determine which requirements you have designated as mandatory, optional, or elective. These guidelines ensure that CAPP data includes the program definitions, along with the associated areas, groups, and the rules for those areas or groups.

Banner selects curriculum records as follows:
  • CAPP matches the student's current and active primary curriculum record to select the program requirements.
  • If your institution uses study paths, Banner uses the program associated with the student's study path.
  • Banner uses the catalog term for the curriculum record to match the effective term of the CAPP program requirement data. If the curriculum record does not have a catalog term, Banner uses the registration term to find the effective term of the CAPP program requirement data.

Structured Registration pulls data from CAPP one time for each registration term. It does not recalculate the data after the student initially logs in and selects a term.

Warning: You must change data in CAPP before students log in and begin registration. If you make any changes to CAPP area or group requirements after a student initially selects the Structured Registration tab, you will need to delete the pidm, term, and program data from the SFBSTRH and SFRSTRD tables. This ensures that Banner Registration Self-Service displays the new requirements.

Depending on the Configuration Option settings on the Term Control (SOATERM) page, Registration Self-Service may or may not consider in-progress registrations and coursework already taken by the student in the compilation of Structured Registration data. Banner uses the SFKRGST/SFKRGST1 package to collect data from CAPP. It builds records for Structured Registration that provide students with the courses they need for registration.

Unlike Projected Registration, it is not necessary to run compliance to use Structured Registration. Compliance concerns classes that students have already completed. Based on their stage or classification, students must work with the displayed requirements to select class sections and complete registration. When a student logs in to registration, the registration process compiles the Structured Registration data based on their primary, active program, or study path program. When the student submits the selected classes in the summary for registration, Structured Registration processing verifies that the student has fulfilled all the program requirements for the registration period.

See the Banner Student CAPP content for more information about setting up and using CAPP.

Comparison of projected and structured

Projected Registration and Structured Registration are similar in that they provide students with lists of classes from which to choose, but different in the way those lists are generated. Here is a quick summary of the differences.

Projected Registration works as follows:
  • The focus is on what is complete, based on what has already occurred in the past.
  • No validation of how coursework will satisfy specific program requirements is performed.
  • Courses are presented to the student in a practical order based on prior coursework and the organization of requirements in CAPP.
  • The course presentation is flexible, as to how much is shown to the student at one time.
  • A course that is identified as mandatory is one that is required for the degree but is not required for the current registration period.
  • Students can select courses from the projected list based on what they perceive as best for them.
Structured Registration works as follows:
  • The focus is on the student's current stage or classification and what coursework is required based on the student's academic program.
  • Coursework is based on the categories (mandatory, optional, and elective) that make up the requirements for the current registration period.
  • The focus is on subject matter for courses that are closely related to the student’s area of study.
  • Each year of coursework is regimented, strictly organized, and controlled.
  • A mandatory course is a one that must be taken in the current registration period.
  • Students are guided through each registration period.
  • Students are directed as to what courses they must take, and they cannot deviate from the structured requirements.
  • Validation of selected coursework against specific program requirements is performed.

Processing Structured Registration

This section contains information about setting up and using Structured Registration.

In summary:
  • Set up Structured Registration controls on the Term Control Page (SOATERM).
  • Define GTVSDAX rules as processing controls.
  • Access the Structured tab in Banner to use Structured Registration.
The following tables are used specifically with Banner Student Structured Registration:
  • Structured Registration Header Table (SFBSTRH)
  • Structured Registration Rule Detail Table (SFRSTRD)
  • Structured Registration Term Control Table (SOBSTRG)
The following Banner views are used specifically with Structured Registration:
  • SFVRGCP0 - used to select areas for a student’s curriculum based on GTVSDAX rules that identify how areas are coded.
  • SFVRGCP1 - used to select student data and match the data to program requirements.
  • SFVRGCP2 - used to select the GTVSDAX rule for identification of CAPP requirements. The internal group REGPROJSTRUCT is selected for the internal codes REGSTRUCT and CLASS.
  • SOVCLTP - used to select the primary, current and active, concurrent curriculum record for a term. The term must be included to use this view, where SOVCLTR_STVTERM_CODE = 'XXXXXX'.
  • SOVCLTR0 - used to select the concurrent curriculum record for a term. The term must be included to use this view, where SOVCLTR_STVTERM_CODE = 'XXXXXX'.

CAPP data detail and display

When CAPP is in use, CAPP program requirements for areas, groups, rules, and courses are considered for Structured Registration.

The data is extracted and presented to the student in Self-Service for selection. Checks occur to make sure registration can continue based on the student’s choices. Settings on SOATERM for mandatory, elective, and optional coursework direct how these categories are identified in the CAPP program definition. Rules on GTVSDAX are used to match a CAPP area to a student by associating a class code to a priority, or by associating the CAPP area name to a class code using a naming convention. (See the " GTVSDAX Rules" section for more information.)

In Self-Service, students are guided through the detailed course requirements, where they are allowed to select classes from a specific list. When courses are selected and added, they are displayed in the registration summary, where they can be submitted for registration. Any registration errors are displayed in the Notification Center.

CAPP allows text to be attached to the rule header. This text can be used to provide additional information to the student about the requirement. In addition, a URL can be inserted into the rule text which will allow the student to navigate to a website or document for additional clarification about the specific requirement or the academic program. CAPP also allows for text entries to be associated with a type. SOATERM is used to associate a specific CAPP text type with the informational text that is available to the student in Structured Registration. A separate text type is used to identify the URL to which the student can navigate.

The CAPP detail used in Structured Registration comes from the Program Requirements Page (SMAPROG), the Area Requirements Page (SMAAREA), and the Group Requirements Page (SMAGROP). The configuration below describes the basic organization of data within CAPP. This organization is tiered and allows Structured Registration to determine the stage or classification at which the student is positioned. It also presents a significant opportunity for students to pick from lists of courses. Each tier supports course ranges, credit hour ranges, and condition ranges. Conditions can be explicit and implicit (sets and subsets).

Program, area, and group data

This section discusses how data from CAPP is used in Structured Registration.

A program in CAPP

A program makes the association between the student's curriculum and CAPP.

An area in CAPP

Areas are the building blocks of a student's academic program requirements.

There are two types of areas, group areas and course areas. As their names imply, group areas are areas made up of groups, and course areas are made up of course requirements. Groups are basically mini-areas which are made up of course requirements. For Structured Registration, each area represents what a student must complete for a stage or classification within a registration period.

An area can be either a group area or a course area. Also, areas can contain requirements from all three categories: mandatory, optional, and elective. The determination of which category requirements belong to is controlled by your entries on SOATERM.

Note: You can define areas as dynamic. For more information on dynamic areas, see the Banner Student CAPP content. When dynamic areas are used, the association between stage or classification must be contained within the area name.

Course area

Course areas are made up of the following:
  • area course/attributes attachments
  • area course/attributes attachment rules

Group area

Group areas are made up of the following:

  • area group attachments
  • area group attachment rules
    Note: Set and subset designations can be used for attachments to both group areas and course areas and allow for the construction and processing of course lists. For more information on sets and subsets, see the Banner Student CAPP content.

Other attributes

Characteristics from CAPP course records may also be used, to make requirements more specific.

Other characteristics can include:
  • course attributes
  • campus
  • college
  • department

Requirement types

Data extracted from CAPP falls into three categories of requirements (mandatory, optional, and elective) based on the area attachments.
  • Type 1 (mandatory) is identified by the Mandatory Rule Key entered on SOATERM or any course attachment defined without using a rule.
  • Type 2 (optional) is identified by the Optional Rule Key entered on SOATERM. Generally, courses identified as optional closely relate to a student's major or program.
  • Type 3 (elective) is identified by the Elective Rule Key entered on SOATERM. Generally, these requirements are very broad and allow the student considerable freedom in selection.
    Note: The above descriptions are simply general guidelines. There is no hard and fast rule that differentiates one type from another. For the best results, use the same requirement types across Areas and Groups. This is especially important when Groups are attached to Areas with Set/Subset values that create an OR condition between them.

Structured Registration takes into consideration only those CAPP entries that exist in the Area Course/Attribute Attachment section and the Group Course/Attribute Attachment section of SMAAREA and SMAGROP, respectively.

SMAPROG general requirements

Use the Program Requirements (SMAPROG) page to establish the general requirements for the program. When a student accesses Structured Registration in Self-Service, the student's primary program or selected study path is used to determine which program requirements are used.

The term in the SMAPROG General Requirements section, relates to the effective term of these program requirements. The catalog term from the student’s program record (or the registration term if the catalog term is Null) is used to determine the correct version of the program requirements to process.

Note: The program requirements must be active.

When programs are captive, all required areas should be attached to the program when the process determines which areas to use for a specific term or stage. When programs are not captive, areas will be checked to see if they are dynamic. All dynamic areas are evaluated to see if the student meets the defined criteria. For more information about captive and dynamic areas, see the Banner Student CAPP content.

SMAPROG program area attachments

Program Area Attachments are also defined on SMAPROG. When a student accesses Structured Registration in Self-Service, the student's primary program or selected study path is used to determine which program requirements are used.

The term in the record relates to the effective term of these program requirements. The catalog term from the student's program record (or the registration term if the catalog term is Null) is used to determine the correct version of the program requirements to be processed.

The Structured Registration Banner Self-Service process determines which areas pertain to the student’s current registration period by using values from the GTVSDAX REGPROJSTRUCT internal group. See the "GTVSDAX rules" section for more information.

  • When the GTVSDAX REGSTRUCT rule is A, all areas attached to the program will be processed.
  • When the GTVSDAX REGSTRUCT rule is N, processing evaluates the area name and identifies the areas to be used, based on the student's class. This setting must be used when dynamic areas are in use.
  • When the GTVSDAX REGSTRUCT rule is P, processing evaluates the area priority which is associated with the area when it is attached to the CAPP program on SMAPROG. The order in which areas should be processed can also be mapped to a class (year in school).
  • When the GTVSDAX REGSTRUCT rule is T, the area requirements will be used when the following conditions are met.
    • The Structured Registration Attribute field on the Area Library (SMAALIB) page has an attribute assigned to the area.
    • The student has that Attribute code assigned to them on the Additional Student Information (SGASADD) page.
SMAAREA data

Here is a summary of the area data used in Structured Registration processing.

  • An area is associated with a program by defining the program as either captive or non-captive.
    • Programs that are defined as captive must have their associated areas explicitly attached. This is done by listing the areas in the Program Areas Attachment information of SMAPROG.
    • Non-captive programs can have either their associated areas explicitly attached or their areas dynamically selected by the program, based on matching the characteristics attached to the area with the characteristics that belong to the student.

      For more information on the difference between captive and non-captive programs, see the Banner Student CAPP content.

  • The area header contains the area, term, catalog term, student level, and course level. This data is accessed from the area identified from the program area attachments and indicates whether the course or group path should be used in Structured Registration.
  • The area course/attribute attachment data used in processing includes: set, subset, rule, subject, course numbers low and high, course attributes, required credits and courses, maximum credits and courses, campus, college, and department.
  • The area course/attribute attachment rule data used in processing includes: required number of conditions, required credits per condition, required courses per condition, maximum credits per condition, maximum courses per condition, total required credits, total required courses, total maximum credits, and total maximum courses.
  • The area group attachment is used to associate a group with an area.
Area requirement types

Structured Registration provides the ability to define up to three types of requirements within a program area.

The types are mandatory, optional and elective. Each type is differentiated by creating the detail requirements under rules defined at the area level. Each type is assigned an arbitrary name which is used as a standard for all areas. The association of the rule name used for each type is then set up on SOATERM. For the type designated as mandatory, besides having the detail requirements stored under a rule, the detail requirements can also be attached directly to the area.

Generally, mandatory courses are those which are required based on the student’s program and year in the school.

Courses can be designated as mandatory on SMAAREA without including them in an area rule. Mandatory courses are requirements attached directly to an area or attached to an area using the Mandatory Rule Key defined on SOATERM.

Optional and elective courses can be selected from lists presented to the student. These lists of courses can contain specific courses, course ranges, or courses with specified attributes. Optional and elective courses are defined in CAPP using area level rule attachments.

Set up Structured Registration

Set up Structured Registration in administrative Banner.

Procedure

  1. Access the Term Control Page (SOATERM).
  2. Select the Registration tab and go to the Registration Model section.
  3. Select the Structured indicator.
  4. Select the Structured Registration tab.
  5. Verify the settings for Structured Registration controls.
    1. Define the error severity.
      • Fatal - Students must complete all registration requirements before saving selected classes.
      • Warning - Students will be warned if all registration requirements have not been met, but they will be allowed to save what has been selected.
      • None - Students will not be stopped or warned if requirements have not been met.
    2. Under the Configuration Options section, indicate if you would like courses taken in other terms to be considered when requirements are displayed for the current term in Structured Registration.
      • Check Academic History - Use this indicator to select if you want the system to query academic history and update the display of program requirements that have already been met. To be applied toward meeting a requirement, classes in academic history must be assigned a passing grade. Passing grades are those which have the Count in Passed check box selected on the Grade Code Maintenance (SHAGRDE) page.
      • Check In Progress Courses - Use this check box to indicate that you want the system to update the status of students' requirements based on their currently enrolled classes when they are registering. This includes classes in other terms and those in which the student was enrolled through the Student Course Registration page (SFAREGS) for the current term. Only classes with a Registered status type will be applied toward meeting requirements. Classes with Dropped, Withdrawn, and Waitlisted statuses will not be applied toward meeting requirements. Grades assigned to in-progress courses will not be considered.
      • Evaluate Non-Rolled Grades on In Progress Courses - When you have selected the Check In Progress Courses check box, use this check box to indicate if you want the system to evaluate grades assigned to in-progress courses that have not yet been rolled to academic history. When this check box is selected, only those in-progress courses with passing grades will be applied toward meeting requirements. Passing grades are those which have the Count in Passed check box selected on the Grade Code Maintenance (SHAGRDE) page.
    3. Define whether registration is active for mandatory requirements.

      Select the Mandatory Active check box.

      If mandatory requirements are defined under the area rules, enter the name of the mandatory rule key to be retrieved from CAPP or the third party software.

      The rule key is the name by which the mandatory classes are defined. If left blank, registration expects mandatory classes to be defined at the top-most level of the CAPP area.

    4. Define whether registration is active for optional requirements.

      Select the Optional Active check box.

      Enter the name of the optional rule key to be retrieved from CAPP or the third party software. The rule key is the name by which the optional classes are defined. The rule key is required when you select the Optional Active check box.

    5. Define whether registration is active for elective courses.

      Select the Elective Active check box.

      Enter the name of the elective rule key to be retrieved from CAPP or the third party software. The rule key is the name by which the elective classes are defined. The rule key is required when you select the Elective Active check box.

    6. Enter the information for the external API when CAPP is not in use. (See step 7.)
    7. Define the print type and links type for information text.
      • When additional text instructions have been appended to a CAPP rule and should be displayed to the student, enter the print type to be used in the Structured Print Type field.
      • When the rule text contains a URL that is to be displayed to the student, enter the print type to be used in the Links Print Type field.
  6. Access GTVSDAX and set up the rules for REGSTRUCT and CLASS.
    See the " GTVSDAX Rules" section for more information.
  7. Set up the external API if CAPP is not in use.
    See the "Use external API" section for more information.
  8. Access the Program Requirements Page (SMAPROG).
    Verify that the registration model is set to Structured for the program and term range.

GTVSDAX rules

Rules on GTVSDAX with the internal group of REGPROJSTRUCT are used for Structured Registration processing.

REGSTRUCT rule

Use the REGSTRUCT rule to determine whether to use the name convention for the area (N), the area priority (P), the student attribute (T), or all (A).The default is P.

Area selection for display in a given term is based on the student's class or year in school when this rule is set to N or P.

CLASS rule

Use the CLASS rule to map your institution’s class codes to the area(s) to be processed for each stage of a student’s academic program (such as first year, second year, and so on).

Multiple CLASS rules should be created, each having a sequence field that corresponds to the order in which a student progresses through the institution’s class codes and one of the institution's class codes entered in the external code field.

  • When the REGSTRUCT rule is set to N, the last two characters of the name of each area attached to the students’ program should match the class code students would have when they are expected to complete that set of requirements.
  • When the REGSTRUCT rule is set to P, the priority assigned to an area when it is attached to the program on SMAPROG is matched to the sequence number of the student's class code entered for the CLASS rule

During processing, the system looks for an area associated with the student's program on SMAPROG that has a priority value equal to the GTVSDAX sequence number of the CLASS record with an external code equal to the student's class code.

Rule summary

Sample seed data rules are provided for your reference.

Note: The external code for the class code can be any valid class code. It does not have to be numeric. Also, the sequence number does not necessarily correspond to the class year, such as sequence 1 does not have to correspond to first year class. Sequence number 1 maps to the area with priority of 1 on SMAPROG. Sequence number 2 maps to the area with priority 2 on SMAPROG, and so on. Therefore, a class code of SR could be mapped to sequence number 1 if you choose to do so.

When the external code is equal to the student's class value, the area on SMAPROG with a priority of 1 is used for the Structured Registration requirements.

Example of area priority and selection of CAPP areas

When the CLASS rule has an external code of FR with a sequence number of 1, the requirements for the SMAPROG area with a priority of 1 will be displayed for a student with the class code of FR. When the external code is 03 with a sequence number of 1, the requirements for the SMAPROG area with a priority of 1 will be displayed for a student with a class code of 03.

Student Attributes and selection of CAPP areas

When you want to use student attributes to select CAPP areas for a student's program, the GTVSDAX rule must exist.

External Code Internal Code Internal Code Group
T REGSTRUCT REGPROJSTRUCT

When using Student Attributes to select CAPP areas, the class rules are not considered. When the student has been assigned an attribute on SGASADD, and it is effective for the registration term, the requirements will be displayed for any area that 1) is attached to the student’s program and 2) has been assigned the same attribute on SMAALIB.

Example of student attributes and selection of CAPP areas

A student has been assigned the attribute Y1S1 (Year 1, Semester 1) on SGASADD effective term 201610. On SMAALIB, area AAS_ACCS1 (AAS Accounting Sem 1) has been defined with Y1S1 in the Structured Registration Attribute field, and on SMAPROG the area has been attached to the student's program. When the student logs into Self-Service Registration and selects term 201610, the requirements associated with that area are displayed in Structured Registration.

All area requirements

When you want to use requirements for all areas associated with the student's program, the following GTVSDAX rules must exist.

External Code Internal Code Internal Code Group
A REGSTRUCT REGPROJSTRUCT

In this case, all requirements from all areas associated with the student's program are displayed to the student, regardless of the area name, the priority of the area on SMAPROG, the student's class, and the student's attributes. However, the ability to register for specific requirement types is determined by the SOATERM settings for mandatory requirements, optional requirements, and electives.

All area requirements example

Here is an example where the GTVSDAX REGSTRUCT rule is set to A, and the student's CAPP program definition contains three areas.

Program Area Rules Requirement Type
GEN-ED 2 rules attached MANDATORY, ELECTIVE
MAJOR 2 rules attached MANDATORY, OPTIONAL
ENGL-ELEC 1 rule attached ELECTIVE

When the SOATERM settings for Structured Registration are set with Mandatory Active selected and Optional Active selected, the student would be able to register for the mandatory requirements from GEN-ED and MAJOR along with the optional requirements from MAJOR. The student would not be able to register for the electives from GEN-ED and ENGL-ELEC.

When the SOATERM settings for Structured Registration are set with Elective Active selected, the student would be able to register for the elective requirements from GEN-ED and ENGL-ELEC. The student would not be able to register for the mandatory or optional requirements from GEN-ED and MAJOR.

Search Again

A Search Again button is provided to manage the number of sections presented to the user.

CAPP supports single course numbers, course number ranges, attributes, and various characteristics, any of which can result in large numbers of sections being listed. Structured Registration uses the Basic Search page layout in Self-Service when the Search Again button is selected. Processing does not support the expansion to the Advanced Search page. The displays for Basic Search and the Search Again share the same SOAWSCR configuration entries.

When the Basic Search page is configured, all the fields the student can use must be included on a single page. It is recommended that only the low and high course number fields are displayed and not the Course Number field. When either the Course Number Low value or the Course Number High value from CAPP exists, all Course Number fields on the Search Again page will be protected from update.

When both the Course Number Low and the Course Number High values are populated in CAPP, the Course Number field on the Search Again page is Null. The Course Number Low from CAPP populates the low Course Number Range field, and the Course Number High from CAPP populates the high Course Number Range field.

Structured Overview display

When using Structured Registration in Self-Service, an outline is presented in the left panel of the page to show a high level overview of the program.

This view displays a hierarchy of requirements that can be reviewed using the links. This view provides a visual display of requirements that have been met (green check mark), and still need to be met (empty circle), grouped into their mandatory, optional, or elective categories.

Use third party service

The third party service needs to send all processed data in the proper hierarchy for rules and rules under rules. If "AND", "OR" conditions exist for requirements, the third party service should group them accordingly.

The following sections describe the minimum requirements that your third party service provider must meet.

URL

Your third party service should be exposed as a RESTful Service on the URL accessible by the Banner 9.31.0 application.

Authentication

External API access requires Base64 encoding of the username and password. The third party service is expected to authenticate all incoming requests with the Base64 encoded username and password. The response is returned when the data is successfully validated, based on the credentials entered in SOAREST.

Request criteria

The Banner 9.31.0 application will provide following criteria for the RESTful request.

Response Field Field Attribute Description
bannerId String (9 char) Student's ID, required.
term String (6 char) Student's term, required.
Response

A JSON type of response is expected from the third party service. The Banner 9.31.0 application will request "application/json" as the acceptToken in the request.

The response should contain hierarchical information about Structured Registration data. The response contains one or more headers, and each header can contain hierarchical subRules.
