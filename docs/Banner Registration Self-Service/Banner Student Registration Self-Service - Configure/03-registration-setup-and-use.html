Registration setup and use

Configure search criteria and results

You can define and configure the class search criteria and results used on the Self-Service Registration pages.

Search criteria elements can be configured by term. You can select the display of and display order of the elements. You can also define the search criteria displayed based on the persona of the user (such as a student, a faculty member, an administrator, and so on). Element labels can be customized.

The Field Configuration Page (SOAWSCR) is used to define Self-Service page and field text configurations for your institution. This page takes the place of the Schedule Search Controls (search by schedule type, campus, level, course attribute, instructor, sessions, instructional method, duration) on the Term Control Page (SOATERM). SOAWSCR can be found on the Overall Configuration Menu (*SRCHCONF), accessed from the Registration Menu (*Registration).

Note: The search controls are still used on SOATERM. The SOBTERM table has not been modified. The values in the columns on SOBTERM are ignored when the SOAWSCR page rules are defined.

Refer to the Banner Student Online Help for section and field details for the pages used with configuration.

When configuration changes are made on SOAWSCR, you must exit from the Self-Service application and log back in to see the changes take effect.

Overall Page and Field Configuration Page (SOAWSCR)

Here is a more detailed look at SOAWSCR. This page is used to maintain the registration page and field configuration definitions for your institution.

Page elements are delivered as seed data. You can specify a persona, a page, and an effective term related to the fields that are available for configuration on a Self-Service Registration page. You can also define if an item is displayed, the display order of the fields on the page, and customized display text for the field labels. The customized label text is used instead of the delivered text. At least one item must be displayed for each Self-Service Registration page.

You cannot create or delete records on this page, but you can modify seed data records. All records are system required, but you can edit information for the Display Number, the Displayed indicator, the Custom Display Text field, and the Required indicator. When the Displayed indicator is cleared, the Display Number is blank.

Note: If you enable the Required indicator for the College field on the Class Search Basic (#10) and/or the Course Search Basic (#310) pages, an asterisk (*) displays on the page, and the requirement to enter information in the College field is enforced. If you enable the Required indicator for any other field(s), an asterisk (*) does not display on the page, and users are not required to enter information for the field(s).
Note: You can use the Data Extract option to save your data to an Excel spreadsheet.

To use this page you need to set up page configuration codes on the Overall Configurable Page Validation Page (STVWSPG) and page field configuration codes on the Overall Configurable Page Field Validation Page (STVWSFD). The pages can be found on the Validation page Sub Menu [STVTRCN - STVXLBL] (*STDVALD3G). Seed data is delivered for these pages.

  • The Overall Configurable Page Validation Page (STVWSPG) is used to define Self-Service Registration pages, sections of pages, and page panels that allow the use of configurable fields.
  • The Overall Configurable Page Field Validation Page (STVWSFD) is used to define the fields that can be configured on the Self-Service Registration pages.

Configuration rules can be copied from an existing term to a term that does not have any rules. Persona configuration information can be copied from one rule to a new persona rule. However, copying configuration rules from one persona to another will not yield the desired results if the Self-Service Registration application does not support that functionality.

For example, copying Registration Admin Summary from the REGISTRAR persona to the FACULTYINSTRUCTOR persona will not provide faculty members with the additional functionality that only registrars can access within the application.

Note: If you enable the Required indicator on the Class Search Basic page, the requirement to enter information will be enforced only for the College field. If you enable the Required indicator for any other fields, an asterisk (*) can display for those fields, but the requirement to enter information in those fields will not be enforced.
Note: The following pages only look at term 000000:
  • Registration History Lookup Schedule (code 300)
  • Registration History Active Registrations (code 305)
  • Registration Student Schedule by Centric Period (code 307)
  • Registration Landing page (code 1000).
To configure the display of these pages for different personas, update the pages for those personas for effective term 000000.

Fields that are configurable, such as those used for search criteria and displayed in the page grids, are defined on STVWSPG. The code values are named in the same manner as program variables to be easily understood within the program.

Code values are system-required, and the user will never see the values unless they work in the actual program. Other validation tables also use “English-like” codes that are not used for displayed text descriptions. On SOAWSCR, you can customize the field label text associated with the field code values, rearrange the field display order by sequence number, and hide fields you do not want to display by unchecking the Displayed indicator.

The default field labels are delivered in the message.properties files and the supported language versions of these files. The service that displays the field labels looks for a custom value defined in the Custom Display Text field (SORWSCR_DISPLAY_TEXT) for the field to be displayed. If a custom value is found, it is used for the field label. If a custom value is not found, the value from the message.properties file is used.

The sb_pagefieldconfig API is used with SOAWSCR to maintain Self-Service registration page and field display configuration definitions.

Review seed data

You can use SQL to view seed data in the tables listed in this section. These tables contain large amounts of seed data.

Registration Configuration Table (SORWSCR)

Seed data is delivered for this table for all pages, fields, and personas. Data is also provided for class searches and course searches. This data is used with the SOAWSCR page.

For a full list of the required data, run the sscosorwscri.sql create script. You can find this script in the upgrade build folder.

Next, run the following SQL script to return all system required values.


select sorwscr_wspg_code,stvwspg_desc,
 sorwscr_pers_code, stvpers_desc, sorwscr_wsfd_code,
 sorwscr_display_ind, sorwscr_required_ind 
from stvpers, stvwspg, sorwscr 
where sorwscr_system_req_ind = 'Y' 
and stvpers_code = sorwscr_pers_code
and stvwspg_code = sorwscr_wspg_code
order by sorwscr_wspg_code, sorwscr_pers_code, sorwscr_wsfd_code;

Seed data is delivered for this table for use with the SOAWSCR page. To review the system required values, use the following code.


select * from stvwspg where stvwspg_system_req_ind = 'Y' order by stvwspg_code;
Note: The Registration Landing page code of 1000 only looks at term 000000.

Set up registration models

You can use simultaneous registration model settings for basic registration, Structured Registration, and Projected Registration. Registration model settings can be turned on or off by term. You can associate a CAPP program definition with a specific registration model by term.

The registration model configuration you want to use for processing is set up on the Term Control Page (SOATERM) and Program Requirements page (SMAPROG). The settings on SOATERM and SMAPROG determine what registration tabs will display to the student in Self-Service for the term and program.

Term

The Registration Model section in the Term Information options on SOATERM contains registration model indicators for Basic, Structured, and Projected. The Basic indicator is checked as the default setting for the term.

The registration model indicators allow you to define which models are allowed for a term. At least one selection is required or an error is displayed. Multiple models can be selected for a term. The settings can also be copied from one term to another.

Program

The Registration Model Code option group on SMAPROG is used to select the registration model to be used with the program in the Key block.

The values are Basic, Structured, and Projected. The default is Basic. Only one option can be selected, but you can set up different options by from and to term ranges for the program.

Examples

A program can have a different registration model for use in different terms.

Program BA-MATH
  • Term 201510 - Basic registration
  • Term 201520 - Projected Registration
  • Term 201530 - Structured Registration
Different programs can use different registration model settings within the same term.Term 201530
  • Program BA-MATH - Structured
  • Program BA-History - Basic

Self-Service

When a student logs in to Self-Service, selects Register for Classes, and then selects a term, the page and tabs displayed are based on the settings on SOATERM and SMAPROG. The student can proceed through the registration path that is presented.

  • When the student's program is set up for basic registration for the term, the Class Search and Registration page is displayed with the Find Classes, Enter CRNs, and Schedule and Options tabs.
  • When the student's program is set up for Projected Registration for the term, the Class Search and Registration page is displayed with the Find Classes, Enter CRNs, Projections, and Schedule and Options tabs. (The Plans tab is also displayed when registration planning is in use.)
  • When the student's program is set up for Structured Registration for the term, the Class Search and Registration page is displayed with the Structured and Schedule and Options tabs.

Set up add and drop controls

Indicators in the Self-Service Options section of the Term Control (SOATERM) page take the place of Crosswalk Validation (GTVSDAX) page rules previously used to process conditional add and drop, drop last class, auto drops, and administrative drops.

If these indicators are not used, the GTVSDAX page rules are used instead. For example, if the value for Allow Student to Drop their Last Class is null, and the WEBDROPLST rule is set to Y or N, that value becomes the default.

Allow Student to Select Conditional Add Drop CONDADDDRP
Allow Student to Drop their Last Class WEBDROPLST

Below are the details for these SOATERM page indicators.

Fields Descriptions
Allow Student to Select Conditional Add Drop Check box indicates whether students can use conditional adding and dropping during registration in Self-Service.

Used when an error occurs after the student submits registration selections. The entire registration process is canceled, even if other classes submitted for registration do not have any errors. When this indicator is not checked, classes without errors can still be processed for registration.

The process saves values of Y (box is checked) and N (box is not checked) to the database.
Allow Student to Drop their Last Class Check box used indicates whether students can drop their last class during registration in Banner Self-Service.

The process saves values of Y (box is checked) and N (box is not checked) to the database.
Auto Drop Connected Course Drop Errors Radio group indicates how automatic drops should be processed during registration in Banner Self-Service.

When the student submits the registration selections, and then tries to drop one class from a pair of classes with a link, corequisite, or prerequisite, an error occurs, but other registration selections can still be processed.

Choices include:
  • Drop Connected Course - Both classes are automatically dropped. Saved to the database as Y.
  • Do Not Drop, Display Error - The student receives an error, but there is no automatic action taken by the system. Saved to the database as N.
  • Confirm to Drop - The student receives a message asking if the other class in the pair can be automatically dropped. Saved to the database as C.
  • Allow Connected Drops - Students are no longer allowed to drop connected courses. If the student attempts to drop a connected course, they receives an error, and the record is saved to the database as I.
Administration Drop Connected Course Errors Radio group indicates how administrative drops should be processed during registration in Self-Service.

When the student first comes into registration after selecting a term, if the student has registration errors that are from a connected class, the class is automatically dropped. The student has no control over this drop event.

Choices include:
  • Drop - The class is automatically dropped. Errors are reported in the SFTRGAM table. Saved to the database as Y.
  • Do Not Drop, Report in Administrative Error Table - An error is reported, but there is no automatic action taken by the system. Errors are reported in the SFTRGAM table. Saved to the database as N.
  • Do Not Report and Do Not Drop - No error is reported, and no automatic action is taken by the system. Saved to the database as I.

Calculated Drop

Calculated Drop functionality is based on dates from which a specific drop or withdraw code will be derived or selected and presented to a Registrar, Student, or Faculty-Advisor for a registered, traditional section in a term that has Calculated Drop active.

The drop codes may have different refund rules associated with them based on the date the registered section is eligible to be dropped or withdrawn. A presented Calculated Drop code will be the only option available to a Student or Faculty-Advisor to select on a particular date to drop or withdraw from a traditional class. A Registrar is made aware of the option to select a Calculated Drop code but may always choose any registration status code.

The Calculated Drop functionality may also recalculate a drop or withdraw code from a traditional section with a drop or withdraw status. The recalculation of a drop from a drop is only available to the administrator on SFAREGS or to the Registrar persona in Self-Service. The Registrar has the option to select a Calculated Drop code but may always choose any registration status code.

Students, Faculty or Advisor personas will never have an option to select a recalculated drop or withdraw code from a traditional section in drop or withdraw status.

Term Control (SOATERM)

Use the Calculated Drop indicator in the Registration section of SOATERM to enable Calculated Drop functionality.

If you select the Calculated Drop indicator, then all traditional sections in that term will be evaluated against the Calculated Drop rules. You do not need to turn on Calculated Drop when you set up rules for the process.OLR Sections and the Registration Mass Entry page (SFAMREG) are excluded from Calculated Drop functionality.

Part of Term Schedule Calendar Default Dates

Part of Term Schedule Calendar Default Dates are in the Base Part of Term section on the Part of Term And Web Registration Controls tab.

Part of Term Schedule CalendarDefault Dates are applied against a Part of Term and are optional. When Part of Term Schedule Calendar Default Dates exist for Last Date to Enroll, Last Date for Refund, Last Date to Record Academic History, or Last Date to Drop Without Penalty, these dates default from the part of term assigned when the section is created on SSASECT and will display on SSAACCL. When the Copy From Term/Copy To Term feature is used on SOATERM, any Part ofTerm Schedule Calendar Default Dates in the Copy From term are not copied to the Copy To term.

Schedule Academic Calendar Rules (SSAACRL)

Use the options and associated rules on the Schedule Academic Calendar Rules (SSAACRL) to set up the refund date associated with each term.

Schedule Calendar (SSAACCL)

Schedule Calendar (SSAACCL) page is described in the sub topics.

Calculated Section Start Date

The Calculated Section Start Date on SSAACCL is calculated and displayed from the section on SSASECT and represents the first day the class meets.

When a section is created on SSASECT with one or more meeting records, all meeting records are evaluated to find the first day the class meets. The Calculated Section Start Date is also evaluated against SSAEXCL. If excluded dates match the Calculated Section Start Date, the next non-excluded day the class meets will equal the Calculated Section Start Date.

When a section is created with no meeting record, the Calculated Section Start Date will equal the Part of Term Start Date applied to the Section on SSASECT. If the Part of Term Start Date falls on a Saturday or Sunday, the Calculated Section Start Date will be the following Monday. Excluded Dates from SSAEXCL are also evaluated against the Calculated Section Start Date when it is based on the Part of Term Start Date.

In order to accommodate the Refund Date added to the Schedule Academic Calendar rules page SSAACRL, Last Date for Refund field has been added to the Schedule Calendar SSAACCL when an Academic Calendar Type rule is applied to a CRN.

Last Date for Refund functions in the same manner as the other non-required updatable date fields on this page. Census One Date is required on SSAACCL and reflects the Census One Date on the section when it is created on SSASECT. Census Two Date is optional but also reflects the Census Two Date from the section on SSASECT.

On SSAACCL, the Census One Date, Census Two Date, Last Date to Enroll, LastDate for Refund, Last Date to Record Academic History and Last Date to DropWithout a Penalty may be updated manually at any time. There is no validation other than verification of a valid date.

On SSAACCL, the Census One Date, Census Two Date, Last Date to Enroll, LastDate for Refund, Last Date to Record Academic History and Last Date to Drop Without a Penalty may also be updated by the entry of an Academic Calendar Type from the Schedule Academic Calendar rule on SSAACRL. If the Schedule AcademicCalendar rule from SSAACRL has a NULL Census One Date or Census Two Date,Census One Date defaults from the section on SSASECT because it is a required field and Census Two Date will default from the section on SSASECT if it exists. Even after an Academic Calendar Type rule is applied and saved, all of these date fields may be updated manually at any time. There is no validation other than verification of a valid date.

After an enrollment exists for the section, an Academic Calendar Type cannot be added to the section. However, the Census One Date, Census Two Date, Last Date to Enroll, Last Date for Refund, Last Date to Record Academic History and Last Date to DropWithout a Penalty date fields may be manually updated. Again, there is no validation of the dates other than verification of a valid date.

Part of Term Schedule Calendar Default Dates from SOATERM

When a traditional section is created on SSASECT, Last Date to Enroll, Last Date for Refund, Last Date to Record Academic History and Last Date to Drop Without Penalty will also be updated by the Part of Term Schedule Default Dates from SOATERM.

When new, traditional CRNs are created on SSASECT and a Part of Term Schedule Calendar Default Dates rule exists on SOATERM for the Part of Term assigned to the CRN, those dates default for the section and are visible on SSAACCL.

Changing Part of Term after Academic Calendar Rules Applied

After a section is created and has been assigned an Academic Calendar Type in Part of Term One and then on SSASECT the section is changed to Part of Term Two, the CRN SSAACCL dates will update as if creating a new CRN.

The Academic Calendar Type will have been removed from the section because it had been applied in Part of Term One. The section dates on SSAACCL will reflect the Part of Term Two Census One Date and Census Two Date if it exists.The Last Date to Enroll, Last Date for Refund, Last Date to Record Academic History and Last Date to Drop Without aPenalty will match the corresponding Part of Term Schedule Calendar Default Dates if they exist.

SCHEDULE - SSASECT

Create CRN will use the SOATERM Part of Term Schedule Calendar Default Dates if they exist.

Copy CRN will use the same Academic Calendar Type rule assigned in the Copy From Term only when the Academic Calendar Type rule has been defined in the Copy To Term.

Course Registration Drop Status Rules (SFADROP)

Use the Course Registration Drop Status Rules (SFADROP) page to control the display of the Drop or Withdraw code that calculates based on the dates applied to the section on SSAACCL.

Course Registration Drop Status Rules are defined at the term level. Note that SSAACCL against which rules on SFADROP are evaluated is defined at the CRN level. Course Registration Drop Status Rules defined on SFADROP take effect when Calculated Drop is turned ON for the term on SOATERM.

Note: All Status Codes entered on SFADROP must be defined in STVRSTS with a Status Type of Dropped or Withdrawn. In the case of the required Status * in the Course Registration Status for Drop Calculation section, the Dropped or Withdrawn STVRSTS code selected for this field must not exist in SFARSTS in any part of term for the SFADROP Term Code rule.

In the case of the codes assigned to a Registrar, Student or Faculty or Advisor in the Schedule Calendar Registration Drop or Withdraw Status section, the Dropped or Withdrawn STVRSTS code selected for these fields must exist in SFARSTS for any part of term for the SFADROP Term Code rule.

Course Registration Status for Drop Calculation

The selection of a Status for Course Registration Drop Status for Drop Calculation validates against STVRSTS and must be defined as a Dropped or Withdrawn Status Type.

The Status code selected in this position must NOT be defined for the SFADROP key block term or any part of term on SFARSTS. The Status code in the Course Registration Drop Status for Drop Calculation is the Status code that triggers the calculation of a drop code by the administrator on SFAREGS. If this Status Code is defined as a status for the Term/Part of Term on SFARSTS, the Status will function as defined on SFARSTS and not function as a trigger to calculate the drop.

Note: Ellucian suggests that an STVRSTS Dropped or Withdrawn code be designated for the Status * defined in the Course Registration Status for Drop Calculation section on SFADROP for use in any/all terms set up for Calculated Drop. This way, the same Dropped or Withdrawn code would be available for use by administrators on SFAREGS in any Calculated Drop term set up on SFADROP. Accordingly, this Dropped or Withdrawn status used for the Course Registration Status for Drop Calculation on SFADROP should never be defined for any term or part of term on SFARSTS.

Should an institution decide that an SFADROP Status* be designated only for use by the Registrar to trigger Calculated Drop on SFAREGS, a suggestion might be to update the STVRSTS Dropped or Withdrawn Status code Description to identify the function such as Calculated Drop Trigger Status. Accordingly, the STVRSTS Action Description that will display to the Registrar in Self-Service would be updated with an appropriate description such as Drop Code Calculated.

The administrator responsible for the setup of Calculated Drop processing and assigning this code on SFADROP would typically be responsible with communicating this Status for Course Registration Drop Status for Drop Calculation to any administrators who would use this Status* to trigger the calculated drop on SFAREGS.

Schedule Calendar Registration Drop or Withdraw Status

The Schedule Calendar Date column refers to the dates applied to the Section on SSAACCL: Calculated Section Start, Refund, Census One, Record Academic History and Drop Without Penalty.

Priority refers to the order in which the rules are checked. Date Qualifier refers to the comparison that will be made against the date on the Section on SSAACCL. The remainder of the fields represent the Drop or Withdraw code that presents to the Registrar persona in SFAREGS and in Self-Service or to the Student or Faculty and Advisor personas in Self-Service when a rule is met.

The Drop or Withdraw code assigned to each persona must be defined on SFARSTS for the term and exist in at least one Part of Term. Any valid Drop or Withdraw code defined on SFARSTS may be assigned to any persona.

Each rule is optional, but if any field on a row is updated, all fields for the rule need to be updated to save the record. Rules that are left NULL will be skipped. Rules will be checked in priority order.

If an SFADROP rule is met, the drop or withdraw code calculated for the section will be the only option available to choose from the action drop down in Self-Service by the Student or Faculty or Advisor Persona. Note that the STVRSTS Drop or Withdraw code must be have the Web Indicator selected to display to the Student or Faculty or Advisor in Self-Service.

If no SFADROP rule is met for the section the Student cannot drop or withdraw from the section, and a Faculty or Advisor cannot drop or withdraw the student from the section.

In the case of a Registrar persona in SFAREGS or Self-Service, when an SFADROP rule is met the Registrar will always have the option to choose the calculated drop/withdraw code or any valid code from SFARSTS List of Values on SFAREGS or from the Action Drop down in Self-Service.

If no SFADROP rule is met for the section, the Registrar will always have the option to choose any valid SFARSTS code on SFAREGS from the List of Values or in Self-Service from the Action Drop down.

Registrar Persona - SFAREGS

The Student Course Registration page (SFAREGS) presents a drop registration status code when a rule is met on SFADROP.

When Calculated Drop is on for the term for any registered traditional section, the administrator may initiate the Calculated Drop process by entering the Course Registration Status for Drop Calculation defined on SFADROP.

When the administrator enters this status code on the registered, dropped or withdrawn traditional section, the Calculated Drop process is executed to display the drop or withdraw code defined for the Registrar on the SFADROP rule that was met. If no rule is met for the selection, the administrator will see an error message, and is able to choose any valid SFARSTS code.

The Calculated Drop process evaluates the date on SFAREGS against the SSAACCL dates applied to the section and drop code rules from SFADROP to determine which drop or withdraw code applies to the Registrar persona.

It is the responsibility of the administrator who sets up SFADROP to communicate the Status* for calculating the drop code on SFAREGS to administrators who will need to use it.

Registrar Persona - Self-Service

Self-Service for the Registrar persona presents a Calculated Drop registration status code in the Action drop-down when a rule is met on SFADROP.

When Calculated Drop is on for the term and the Registrar meets a rule on SFADROP, the Registrar will see the Calculated Drop code when they select the Action drop-down for any registered, dropped or withdrawn traditional section in the Registration Summary. This is how the Registrar initiates the Calculated Drop process in Self-Service, instead of entering the Course Registration Status for Drop Calculation defined on SFADROP.

The Registrar may select the Calculated Drop code or any other valid Registration Status Code presented in the Action Drop down and submit. The Registrar is notified if a Drop Code did not calculate, and can select any other valid registration Status Code from the Action drop-down.

Note: While the Registrar does not enter the Course Registration Status for Drop Calculation from SFADROP in Self-Service to initiate the calculated drop process, the Action drop-down in Self-Service may present the STVRSTS Action Description of the Course Registration Status for Drop Calculation as part of the User Interface. In Self-Service, the description of the Status* defined on SFADROP optionally displays from the STVRSTS Action Description and can be updated appropriately by your institution.
Student Persona - Self-Service

You can set up links in Self-Service that allow students to access online bookstores and review required course materials when selecting classes for registration.

About this task

The Higher Education Opportunity Act (HEOA) might require that at least one bookstore link be configured at your institution as a hyperlink to an online book site. Sites can include your institution's internal campus bookstore and external online book sellers.

The bookstore links are configured in the Banner Applications Configurations (GUACONF) page and are available at the section level for a course. You can also set up the Bookstore Links option to access a secondary custom page at your institution that displays the bookstore links.

A student can do the following to access the bookstore links.

Procedure

  1. Click on the course title and access the Class Details window.
  2. Select the Bookstore Links option.
  3. View the institution's bookstore links and select one to access a bookstore.

Results

The options in the Class Details window are configured on the Overall Page and Field Configuration Page (SOAWSCR). The fields displayed on SOAWSCR can be used as valid substitution parameters in the bookstore URL links.

You can link to bookstore sites in several ways:
  • Link to a website with no parameters.
  • Link to a website using hard-coded parameters.
  • Link to a website with dynamic parameters defined on SOAWSCR for section search results.
  • Link to a website specific to the campus code associated with the class section .The campus code value is taken from the Campus Code Validation (STVCAMP) page.

Using Personas

Personas are used within Registration Self-Service processing to determine display configuration and page access. Detail available on the Self-Service pages is determined based on the display configurations set up by persona.

A person can have a single persona or multiple personas. Personas can be used for students, advisors, faculty members, and administrators, such as registrars. Anonymous users can also have a persona. Personas are extensions of and are mapped to Banner Web Tailor roles and include more specific data than Web Tailor. For example, the FACULTY role in Web Tailor has been separated into distinct persona types for FACULTY, ADVISOR, and both FACULTY AND ADVISOR.

The REGISTRAR role is manually assigned in Web Tailor. The persona using this role must have a login to Self-Service. Registrars can access pages that are similar to the pages accessed by students and faculty members, but these pages contain additional functionality. This persona can select any term and student for processing.

The Overall Page and Field Configuration Page (SOAWSCR) is used to configure page information display, display order, and field labels on Registration Self-Service pages. Personas-based page access is also configured on SOAWSCR. The configuration is based on the persona, page, and term combination in the Key block. You can copy data from one term to another and from one persona to another on this page.

Use the Persona Validation Page (STVPERS) to create and maintain codes for personas used with Banner Registration Self-Service. Personas control what pages can be accessed in Self-Service by a user and what tasks can be performed. Values can be system required.

Use the Persona Rules Page (SOAPERS) to set up rules used with persona entities. Each rule is associated with a Web Tailor role and the appropriate persona type, such as administrative, faculty, student, or proxy. Persona rules control what pages can be accessed in Self-Service by a user and what tasks can be performed. SOAPERS can be found on the Overall Configuration Menu (*SRCHCONF), accessed from the Registration Menu (*Registration).

Persona flow

Here is a sample of how a user would access and move through Self-Service when personas are in use.

Procedure

  1. The user accesses the Registration Self-Service application and sees the Registration Landing page.
  2. The user selects a link that requires a log in, and the user logs in to the application.
  3. When multiple personas exist, the user sees the Persona Selection page and is prompted to select a persona from a list. The selection determines the paths that are available.

    A user with a single persona, such as a student, does not see this list, as the role is defaulted.

  4. The user opens a specific page from a link on the Registration Landing page, and the selected persona is validated and defaulted to the page.

  5. The Select a Term page is displayed, and the terms available are dependent on the user's persona.
  6. The persona in use is displayed at the top of the page, to the left of the user name.
  7. The pages carry that persona forward until the user changes to a different persona.
  8. The persona can be changed on the Registration Landing page by clicking on the displayed persona and selecting a different persona from the list on the Persona Selection page.
  9. The user can continue with registration processing using the newly selected persona.

Add Authorization processing

Registration Add Authorization processing provides faculty, advisors, and administrators with the ability to allow students to register in classes that have already begun to meet or have reached capacity.

Banner executes Registration Add Authorization processing when a student registers for a class that has an STVRSTS Registration Code with a Status Type of Registered and the Count In Enrollment flag is selected.

If a faculty, advisor, or administrator wants to allow a student or students to register for a class that has already started meeting or is closed due to capacity, they can provide the students with an authorization code. The code enables students to override capacity or section started registration errors and register for the class. This eliminates the overhead involved with students needing to request special permission for registration between offices. Administrators can enter authorization codes on SFAREGS and in Self-Service Registration. Students, faculty, and advisors can enter authorization codes in Self-Service Registration.

Administrators can generate authorization codes on the Registration Add Authorization Codes (SFAAUTC) page for a specific term and CRN, or they can create multiple codes through the Authorization Code Generator (SFPAUTG) batch process. They can distribute the codes to faculty, advisors, and administrators based upon the policies of your institution. Faculty, advisors, and administrators provide the authorization codes to students who use the codes to register when prompted at the time of registration.

Errors specifically associated with the Add Authorization process that prompt for an authorization code include:

  • If a class has reached capacity, an instructor can allow a student to register beyond capacity. The instructor provides an authorization code to the student to register, as long as the Census One date has not been reached on the section and no waitlist is available.
  • After the class has begun (Add Authorization Start Date on SSASECT) an instructor can allow students to register on or after that date. The instructor provides an authorization code to these students to register as long as the Census One date has not been reached on the section. When Add Authorization processing is active, waitlisting for classes that have already started is not an option.
  • After a section has met its Census One date, students will not be prompted for authorization codes to register for that section. Registration for classes by the student, faculty or advisor on or after the Census One date is not allowed.

After a section has reached its Add Authorization Start Date, the option to waitlist for the section is no longer available regardless of whether waitlist seats are available.

Add Authorization Processing is an optional setting by term and is turned on and off on SOATERM.

Note: The authorization codes that allow a student to register beyond capacity or after a class has started do not guarantee the student will get into the class. After a valid authorization code is entered, all registration error checking continues to occur. Error checking for things like prerequisites, approvals, or holds could still prevent the student from getting into the section.

Administrators can pre-assign authorization codes to students on SFAAUTC by term and CRN. This allows the student to register for a section and override the request of an authorization code. Administrators maintain authorization codes on SFAAUTC. They can use a batch process, Authorization Code Removal (SFPAUTR), to delete unused authorization codes.

Add authorization codes give an instructor flexibility to allow students to register for a class in special circumstances:

Administrators have the option to:
  • pre-assign an authorization code to a student on SFAAUTC
  • provide a valid authorization code when prompted on SFAREGS or in Self-Service Registration
  • override the request for an authorization code on SFAREGS or as the registrar persona in Self-Service to register the student for a class that meets add authorization error checking rules.

In the case of a Census One error, the administrator can override the Census One error on SFAREGS or in Self-Service – registrar persona.

Unless pre-assigned an authorization code by an administrator on SFAAUTC, students will need a valid authorization code to register for a section that meets add authorization error checking rules. Otherwise, they cannot register for the section.

Unless pre-assigned an authorization code by an administrator on SFAAUTC, Faculty and Advisors will need a valid authorization code to register a student for a section that meets add authorization error checking rules. Otherwise, they cannot register the student for the section.

SFAROVR processing

You must have a rule on SFAROVR that you can use to setup Add Authorization processing on SOATERM.

The rule you create on SFAROVR for Add Authorization processing must have the Capacity option selected. Other checklist options are allowed, but Capacity triggers the display of the Add Authorization window when an authorization code is required.

Typically, an administrator would apply an SFAROVR rule to a student on SFASRPO for a term/CRN before registration in order for a student to bypass associated fatal errors and register for the section. For Add Authorization processing, the SFAROVR rule is not applied in advance. Instead, when the Add Authorization window is displayed with a request for an authorization code and the authorization code is validated, the SFAROVR rule on SOATERM is added to SFASRPO at that time.

If your institution is using Add Authorization processing, Ellucian recommends you create an STVROVR/SFAROVR rule specifically for Add Authorization processing with only Capacity selected.

Note: If a SFASRPO Permit-Override code defined with a capacity override is pre-assigned for a term/student ID/CRN, the permit will allow the student into the section without an authorization code if there is a capacity error. Pre-assigned SFASRPO permit-override codes with a capacity override take precedence over Add Authorization processing.

When Add Authorization processing is enabled on SOATERM and SSASECT, the add authorization codes are active for the section. Add Authorization processing occurs in both SFAREGS for Administration and in Self-Service for registrar, student, faculty, and advisor personas. In Self-Service, the only difference from student, faculty, or advisor functionality is that the registrar persona has the option to override add authorization errors. SFAREGS and Self-Service are both on or both off when SOATERM Add Authorization Processing is Active for Term is on.

Setup SOATERM

To enable Add Authorization processing, you must perform these steps on SOATERM.

Before you begin

Create a Permit-Override code on SFAROVR before you enable Add Authorization processing on SOATERM.

On SOATERM, the Permit-Override code validates against SFAROVR. SFASRPO will be updated for the term/CRN when a student uses a valid authorization code to register for a section. It is highly recommended that the Permit-Override Code entered for Add Authorization processing on SOATERM be used only by the Add Authorization process. If the SFASRPO Permit-Override Code defined for Add Authorization processing is pre-assigned, or any SFASRPO record with a capacity override exists for the student/CRN before registration, the permit will allow the student into the section without an authorization code if there is a capacity error.

Note: When a valid authorization code is associated with a term/CRN with a First Assigned Date on SFAAUTC, SFASRPO will be updated. However, if additional fatal errors are encountered that prevent the student from successfully registering for the class, the SFASRPO record is deleted and the SFAAUTC assignment is retained. If the fatal errors are resolved and the student attempts to re-register for the section, the student will get into the class without the request for an authorization code as long as the authcode days reusable after assignment is valid.

Procedure

  1. On the Registration Error Checking tab in the Options section, set the Capacity field to Fatal.
  2. On the Web Processing Controls tab in the Add Authorizations section, select the Active for Term indicator to turn on Add Authorization processing for the selected term.
  3. Set the Disable Before Start Date indicator depending upon when you want Add Authorization processing to begin.
    Action Description
    Select the Disable Before Start Date on SOATERM. If you want Add Authorization processing to wait until the Add Authorization Section Start Date on SSASECT has been met to start Add Authorization processing, take this action.
    Deselect the Disable Before Start Date on SOATERM. If you want Add Authorization processing to begin in advance of the Add Authorization Section Start Date, take this action.
    If you choose to begin Add Authorization processing before the Add Authorization Section Start Date, the process will first check the Census One date and then Capacity to determine if an Authorization Code is required. If the section has reached capacity and the section has a waitlist maximum equal to zero, the system will display a message that an authorization code is required and the section is closed. After the Add Authorization Section Start Date is reached, the process will check the Census One date, Capacity, and the Add Authorization Section Start Date in that order to determine if an authorization code is required.

    All capacity errors will not necessarily display the Authorization Code Required message. Before the SSASECT Authorization Code Start Date and when SOATERM Add Authorizations are active for the term and Disable Before Start Date is off, the system displays baseline capacity and waitlist messages if the section has a waitlist maximum greater than zero and no authorization required messages will display. Waitlist processing stops after the section meets the Add Authorization Start Date and Authorization Code Required messages will display accordingly.

  4. Enter a value for Days Required Relative to Start Date.
    Valid values are -999 to 999. A value of 0 is valid. This is the number of days (plus or minus) added or subtracted from the Add Authorization Start Date for the section on SSASECT. SFASRPO override

When an authorization code is validated to register for a section, Banner creates a Student Registration Permit-Override (SFASRPO) record for the Term/Student/CRN. This is the Registration Permit-Overrides Control (SFAROVR) rule that is established on Term Control (SOATERM) associated with Add Authorizations.

The traditional use of SFASRPO is to establish a rule before the student registers for a section. If an SFASRPO record exists for a Term/Student/CRN with a capacity override, then the SFASRPO rule will allow the student to register for the section. An SFASRPO rule assigned to the TERM/Student/CRN takes precedence over the requirement of an authorization code.

EXAMPLE 1: SFASRPO has a rule preassigned for the Term/Student/CRN with a capacity override. The section has already started and would require an authorization code. When the student attempts to register for the CRN, no authorization code will be requested because the SFASRPO record exists with a capacity override.

EXAMPLE 2: SFASRPO does not have a rule preassigned for the Term/Student/CRN with a Capacity Override. The student registers for a section and uses a valid authorization code. Banner updates SFAAUTC with the Student ID against the authorization code used. Banner updates SFASRPO with the SFAROVR rule from SOATERM that has a Capacity Override. The student drops the class. Banner deletes the associated SFASRPO record and retains the student authorization code assignment on SFAAUTC. When the student attempts to re-register for the CRN, the student can successfully register without an authorization code as long as the days reusable after assignment is valid. If the Census One date has passed, the student cannot register for the class.

EXAMPLE 3: SFASRPO does not have a rule preassigned for the Term/Student/CRN with a Capacity Override. The student registers for a section and uses a valid authorization code. Bannerupdates SFAAUTC with the Student ID against the authorization code used. Banner updates SFASRPO with the SFAROVR rule from SOATERM that has a Capacity Override. On SFAAUTC, an administrator removes the ID from the authorization code. If the student attempts to re-register for the CRN after having dropped, no authorization code will be requested, because the SFASRPO record exists with a capacity override.

Add Authorization and Waitlist Processing

Add Authorization processing and Waitlist processing can be set up and used on a section. However, Add Authorization processing and Waitlist processing function independently.

Waitlist checking is executed before the section Add Authorization Start Date. The SSASECT Add Authorization Start Date establishes the end of Waitlist processing and the beginning of Add Authorization processing. Please note that the transition from Waitlist processing to Add Authorization processing is not applicable unless the section has waitlist maximum greater than zero.

When a section has a waitlist maximum greater than zero, the Add Authorization process does not begin until the Add Authorization Start Date is met, regardless of the Disable Before Start Date setting on SOATERM.

Waitlist processing is enabled when the waitlist maximum is greater than zero, the Disable Before Start Date is off, and the section has no capacity before the Add Authorization Start Date.

Waitlist processing stops after the section meets the Add Authorization Start Date and authorization code required messages will be displayed.

Waitlist processing is ignored when the waitlist maximum is equal to zero.

Non-Automated Waitlist

Baseline Waitlist functionality is executed until 12:00:00 AM on the section Add Authorization Start Date. Regardless of the SOATERM Disable Before Start Date setting, add authorization required messages will not be displayed during this time when a section has a waitlist maximum greater than zero.

At 12:00:00 AM on the Add Authorization Start Date, Add Authorization processing begins and waitlist functionality is disabled. Add authorization code required messages will be displayed.

After the section meets the Add Authorization Start Date, in Self-Service students, faculty, and advisor personas cannot place the student on the waitlist for that section. On SFAREGS, an attempt to use a waitlist status code will present an error that can be overridden. In Self-Service for any persona, the option to Waitlist will not present in the drop-down if the section meets the Add Authorization Start Date. The Registrar persona in Self-Service can override the start date error.

Automated Waitlist

Automated Waitlist functionality is executed until 12:00:00 AM of the section Add Authorization Start Date.

Regardless of the SOATERM Disable Before Start Date setting (ON or OFF), the Add Authorization Code required messages will not be displayed until the section Add Authorization Start Date when a section has a waitlist maximum greater than zero.

The number of hours established on the SSAWLSC or SOAWLTC Waitlist Notification Deadline are deducted from the Add Authorization Start Date. The result of this calculation represents the date and time Waitlist messaging stops for the section. This no-notice period is established to provide a period of time to transition from Waitlist messaging to Add Authorization processing. Waitlist notifications are no longer sent for the section during this time, but students who previously received a waitlist notification for the section are allowed to register from unexpired waitlist notices until the section Add Authorization Start Date.

The no-notice period is the time between SSASECT’s Waitlist Notification Ending Date and the Add Authorization Start Date.

The Waitlist Notification Ending Date displays the Add Authorization Start Date minus the Waitlist Notification Deadline on the Waitlist Automation Section Control (SSAWLSC). If the SSAWLSC Waitlist Notification Deadline does not exist, it uses the SOAWLTC Automated Waitlist Term Control Waitlist Notification Deadline.

Before the no-notice period on the section, automated waitlist processing is enabled.

During the no-notice period on the section, only unexpired notices can be used to register for the section. No new waitlist notices are sent. Students can be placed on the waitlist, but they will not be notified to register. Add Authorization processing is disabled.

After the no-notice period on the section, Waitlist processing stops. Add Authorization processing begins.

Registration Add Authorization Processing: Self-Service Authorization Code Entry Window

Add Authorization processing in Self-Service is supported in the Basic Registration model that includes registration from a class search, registration by direct CRN entry, registration for all linked classes and registration from a plan. It is not supported in the Projected, Structured or Block registration models.

Add Authorization is not supported through the Search by Date Range option at this time. If a student searches by date range and selects a section to add to the summary pane, the registration error notification will appear upon submit. The student may return to Add CRN and enter the CRN, or search again by term, and the add authorization window will be available.

Because Plan Ahead is working with future registrations, add authorization processing is not applicable.

Self-Service Add Authorization Code processing mirrors the processing and setup required for Registration using Add Authorization Codes for SFAREGS. There is no option to turn Add Authorization processing on for SFAREGS and off for Self-Service or vice-versa.

In Self-Service, the Search feature has been enhanced to present classes that require an authorization code and a Self-Service Authorization Code Window has been introduced. Similar to SFAREGS, the design of the Self-Service Add Authorization Code window is based on the design of the Self-Service OLR Window.

Similar to SFAREGS, the authorization code messages that are displayed in the Self-Service Add Authorization Code window and request authorization codes include:

  • Authorization required: Closed Section
  • Authorization required: Reserve Closed
  • Authorization required: CRN started

Self-Service Add Authorization and search for classes

Upon searching for classes in Self-Service, traditional sections that require entry of an authorization code will display a key icon and associated text in the Search Results Status column.

OLR sections will never display a key icon but can require an authorization code at the time the start date is calculated upon registration for the section.

If the traditional or OLR section has reached the Census One date, there is no search status that an authorization code is required. When the student, faculty, or advisor chooses to add the section to the Registration Summary, upon submit an error is displayed in the Notification Center that the census date prohibits registration. Students cannot register for the section. The registrar persona is also displayed with census date prohibits registration, but can choose to override the error.

Upon the selection of View Linked sections, the Search Status column will also indicate when an authorization code is required to register for linked sections.

Display of the key icon is dependent on the SOATERM Add Authorizations Disable Before Start Date setting for the traditional section. The key will not display for OLR sections, but the OLR section can still require an authorization code.

EXAMPLE: SOATERM Disable Before Start Date is off, the Add Authorization process checks capacity before the section start date.

Traditional: 0 Capacity, 0 Maximum Waitlist, Future Start Date, Census One in Future: Key displays because section closed requires authorization code.

OLR: 0 Capacity, Census One is not checked, Waitlist is not checked: Key will not display but section closed will require an authorization code.

EXAMPLE: Disable Before Start Date is on, the Add Authorization process checks capacity when the section start date is today or in the past.

Traditional: 0 Capacity, 0 Maximum Waitlist, Future Start Date, Census One in Future: Key does not display because section start date is in the future. A baseline capacity error will be displayed.

Traditional: 0 Capacity, 0 Maximum Waitlist, Start Date today or past, Census One in Future: Key displays because Capacity is 0 the Section Start Date is in the past. Section Closed requires an authorization code.

OLR: 0 Capacity, Census One is not checked, Waitlist is not checked: Key does not display. Section started depends on the entry of the Start Date in the OLR window equal to the current date. When the Current Start Date is entered, Section Closed requires an authorization code.

Self-Service Authorization Code Window

Add authorization processing in Registration Self-Service to use an Authorization Code Entry window.

Note: Add Authorization processing is the same in Self-Service as SFAREGS except that the user interaction and design of the window is slightly different.

Traditional sections

Upon ADD of a single traditional section that requires an authorization code a window displays to Enter Your Authorization Code. Section information displays in addition to an Authorization Code Message, a Status and option to enter the authorization code.

The student, faculty, or advisor personas can choose to Cancel or Confirm. Cancel will abandon the request to add the section. Confirm will validate the authorization code entered. Entry of an authorization code that is not valid or authorization code assigned to a different student will display errors. Entry of a valid authorization code will place the section in the Registration Summary. The authorization code is assigned to the Student ID on SFAAUTC and the Permit-Override assigned on SFASRPO.

When multiple traditional sections that require authorization codes are added to the Registration Summary for instance using Enter CRNs, the same window displays to Enter Your Authorization Codes for all sections. Functionality is the same except that there is the option to remove an individual CRN from the window using the minus icon.

The registrar persona can choose to Add to Summary, Cancel or Confirm. Cancel will abandon the request to Add the section. Upon Confirm, entry of an authorization code that is not valid or authorization code assigned to a different student will display errors. Entry of a valid Authorization Code and Confirm will place the section in the Registration Summary and the authorization code has been assigned to the Student ID on SFAAUTC and the Permit-Override assigned on SFASRPO. Add to Summary will place all CRNs that are listed in the Enter Your Authorization Code window in the Registration Summary. The Registrar may choose to Override the request for an authorization code in the Registration Summary. Upon Override, the student is not assigned an authorization code on SFAAUTC and the Permit-Override is not assigned on SFASRPO.

After sections reside in the Registration Summary, upon SUBMIT all registration error checking takes place with the exception of capacity which was checked as part of the Add Authorization processing.

Upon SUBMIT in the Registration Summary and display of the Census One error in the Notification Center, the Registrar can override the Census One error. Student, faculty, or advisor personas do not have the option to override.

Self-Service OLR Window and Add Authorizations

OLR sections function with Add Authorization processing. However, the calculation of a Section Add Authorization Start Date on SSASECT and wait listing are not applicable to OLR sections.

Keep in mind that the OLR Start Date updated in the OLR Window considers the SOATERM Days Required Relative to Start Date. When the result of the calculation is in the future a request for an authorization code will not display as a result of Section Started. If there is no capacity in the section, a request for an authorization code could display.

In Self-Service upon entry of a single OLR section, the OLR Window will display. When the start date is calculated = current date or the section has reached capacity, the window immediately responds to include an Authorization Code Message and prompt for entry of the authorization code. Cancel abandons the request for the section and the OLR window will close. A valid authorization code is required to Confirm and place the section in the Registration Summary.

The Start Date can be changed to the future to avoid requirement of an authorization code and the request for entry of the Authorization Code will be removed as long as there is capacity.

When multiple OLR sections are added to the Registration Summary for instance using Enter CRNs, the OLR window displays the sections. All processing is the same as a single except that there is the option to remove an individual OLR CRN from the window using the ‘minus’ icon. Cancel abandons the request for all of the sections in the window.

When a mixture of traditional and OLR CRNs are added to the Registration Summary for instance using Enter CRNs, separate windows for OLR date entry and traditional sections that require an authorization code will display and require resolution accordingly.

The registrar persona also has the option to choose Add to Summary in the OLR Confirm Your Dates window. This option is available to the Registrar to Override requests for an authorization code. Add to Summary will place the OLR CRNs that are listed in the Confirm Your Dates window in the Registration Summary. The student is not assigned an authorization code on SFAAUTC and the Permit-Override is not assigned on SFASRPO.

Regardless of the type of section or window displayed, entry of an authorization code that is not valid or authorization code assigned to a different student will display errors. Entry of a valid authorization code and Confirm will place the section in the Registration Summary. Validated authorization codes are assigned to the Student ID on SFAAUTC and the Permit-Override assigned on SFASRPO.

Note: After a traditional or OLR section is added to the Self-Service Registration Summary, the option to enter an Authorization Code will not be available.

EXAMPLE: A student successfully registers without an Authorization Code. Registrar drops the student from the section in Self-Service or SFAREGS and the drop code is retained. The student sees the dropped section in Self-Service and has the option to re-register for the section. Over time capacity has been reached or the section has started so an Authorization Code is now required. When the student attempts to re-register and SUBMIT, a message displays in the Notification Center that an Authorization Code is required. However the window to allow entry of an Authorization Code will not display. The student will need to work with administration to drop/delete the section and then Search/Add in Self-Service to re-initiate the Add Authorization Code window. In this same scenario, the Registrar will receive the same messages in the Notification Center, but the Registrar can drop/delete and re-register the student to trigger the Add Authorization Window or choose to Override the request for the Authorization Code. In this same scenario, SFAREGS does display the Add Authorization window.

Batch Waitlist Notification (SFRBWLP) processing notes

The Batch Waitlist Notification (SFRBWLP) process will stop sending waitlist notices if seats become available between the section waitlist notification ending date and the add authorization start date.

This prevents conflicts between seats available to students on a waitlist and students assigned authorization codes. The time between the SSASECT waitlist notification ending date and the add authorization start date allows students who were previously notified to move from the waitlist to registered in the class. This can occur if the waitlist notification has not expired.

During this time, the system will not send waitlist messages to students if a seat becomes available. You can place students on a waitlist, but they will not be notified if a seat becomes available for the section. After the section meets the add authorization start date, you cannot place students on the waitlist for the section.

Map the zero textbook cost attribute codes used by your institution to the GORICCR entries that have been provided as seed data with Process Code = DISPLAY.ZEROTEXTBOOKCOST.ATTR,
