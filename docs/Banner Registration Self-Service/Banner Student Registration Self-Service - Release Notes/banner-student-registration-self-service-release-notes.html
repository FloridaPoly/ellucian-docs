Grails 7.1.0 Framework Upgrade

This release upgrades the underlying application framework from Grails 6.2.3 to Grails 7.1.0. This major framework upgrade modernizes the technology stack to Jakarta EE 10, Spring Boot 3.5.14, Groovy 4.0.31, and Tomcat 10.1.x. There are no changes to application functionality or user-facing behavior. Existing configurations remain compatible and no database changes are required. JDK 17 continues to be the minimum supported version. Customers who have developed extensions or customizations must update their code to replace javax.* imports with jakarta.* equivalents, update CAS client imports from org.jasig.cas.client.* to org.apereo.cas.client.*, and align with the updated framework versions.

Refer to the Install Guide for the updated technology stack requirements and Grails 7.1.0 Migration Guide in Banner Self Service Developer Documentation.zip in Banner Self-Service - Get Started for detailed code change instructions.

This enhancement addresses PE0008352 in the Ellucian Customer Center.

Term-Based Registration Holds Implementation

Ellucian now delivers complete implementation of term-based registration holds for Banner Student. This enhancement provides institutions with comprehensive tools to manage term-specific registration restrictions, ensuring regulatory compliance and enhanced academic policy enforcement across all Banner modules and integration points.

Term-based holds enable institutions to prevent student registration for specific academic terms until required actions or obligations are satisfied.

New Hold Information page (SGASTHD)

The Hold Information (SGASTHD) page includes a new Hold by Term section that provides comprehensive management of term-specific registration holds. This enhancement enables administrators to:

  • Create and manage term-based registration holds with individual active indicators.
  • Associate specific hold types with academic term codes for targeted enforcement.
  • Control hold activation status independently for each term-hold combination.
  • View complete hold history including both active and inactive term-based holds.
  • Maintain separation between traditional date-range holds and term-specific holds.

The Hold by Term section restricts hold validation to registration hold types only, ensuring proper enforcement during registration processes. Each hold entry specifies a single term code (no term ranges) and includes an active indicator that determines whether the hold enforces registration restrictions.

Note: Only holds with Active Indicator = Y prevent registration. Holds with Active Indicator = N remain for historical tracking without affecting student registration capabilities.

SPRTHLD database table

The SPRTHLD database table provides the data foundation for term-based registration holds. This table stores term-specific hold assignments and includes:

  • Student identification: Links holds to student PIDM for individual student tracking.
  • Term code: Specifies the academic term for which the hold applies.
  • Hold type code: References registration hold types defined in STVHLDD.
  • Active indicator: Controls whether the hold enforces registration restrictions (Y = active enforcement, N = historical record).
  • Release indicator: Controls whether only the system user who entered the term hold may release it (when set to Y).
  • Audit fields: Captures creation and modification timestamps with user attribution.

The SPRTHLD table is implemented for both Oracle and PostgreSQL database environments, ensuring consistent functionality across all Banner Student deployment configurations. Database schema changes are applied automatically during the upgrade process.

Registration hold enforcement

Banner Student now validates term-based holds during registration operations when hold error checking is enabled. This enforcement applies across multiple registration channels and administrative processes, including:

  • Self-Service Banner (Registration): Term-based holds are evaluated when students attempt to register through Self-Service, preventing unauthorized registration for restricted terms.
  • Administrative registration pages: Hold validation enforces restrictions on SFAREGS (Registration), SFAMREG (Multiple Student Registration), and SORMEBP (Extended Registration) pages.
  • Registration APIs: person-holds - Enhancement of this API will be addressed with PE0007779 in a future release.
  • Batch registration processes: Term-based holds are validated during automated registration workflows.

Hold enforcement behavior follows these rules:

  • Holds only prevent registration when the hold term matches the term for which the student is attempting to register.
  • Only active holds (Active Indicator = Y) enforce restrictions.
  • Hold severity configuration (Fatal or Warning) defined in the SOATERM page, SOBTERM table is honored for term-based holds.
  • Students receive clear error messages indicating which hold prevents registration and why.

Institution-wide hold display

To ensure consistency and visibility, term-based holds are now displayed appropriately throughout Banner Student. This modification ensures that:

  • Administrative users can view term-based holds on student records across all Banner modules.
  • Hold displays clearly distinguish between traditional date-range holds and term-specific holds.
  • Active and inactive holds are appropriately indicated to prevent confusion.
  • Integration with existing hold viewing functionality maintains familiar user experience.
  • Inquiry pages and reports include term-based hold information where applicable.

The display enhancements ensure administrators have complete visibility into student hold status for effective student support and registration troubleshooting.

Regulatory compliance and use cases

Term-based registration holds support multiple regulatory and institutional requirements:

  • Requires acknowledgement of representation fee for each term before registration, to meet regulatory requirements.
  • Prerequisite acknowledgment: Institutions can require students to complete mandatory orientations, advisement, or other prerequisites before registering for specific terms.
  • Financial obligations: Holds can enforce term-specific payment plans or financial clearance requirements.
  • Academic probation: Students on academic probation can be required to complete intervention programs before registering for subsequent terms.
  • Athletic eligibility: Term-specific holds can enforce NCAA or conference eligibility verification requirements.

Implementation and configuration

To implement term-based registration holds at your institution:

  1. Define registration hold types in the Hold Type Validation (STVHLDD) page. Only registration hold types can be used for term-based holds.
  2. Configure hold severity settings (Fatal or Warning) in the Term Status Information (SOATERM) page for each applicable term.
  3. Create term-based holds in the Hold Information (SGASTHD) page Hold by Term section, specifying the term code and setting the active indicator appropriately.
  4. Test hold enforcement across registration channels including Self-Service and administrative pages.
  5. Communicate hold policies and resolution procedures to students and support staff.

New Term-Based Holds (SPRTHLD) table

Ellucian is delivering this enhancement to establish the foundational data framework required to support the future delivery of term-based registration holds. This foundation will enable institutions, in a future release, to apply registration restrictions at the academic term level.

As part of this initial foundational support, a new Banner Student table, SPRTHLD, is introduced. This table stores term-based registration holds that are effective for a specific academic term. The table provides a centralized and consistent way to manage term-based hold data and serves as foundational support for future term-based hold functionality.

Tip: Although the SPRTHLD table structure might support additional types of term-based holds in the future, this release supports only student registration term-based holds.

Full functional support for term-based registration holds will not be available until PE0006095 is delivered, which will fully enable this capability. For details, see PE0006095.

Display Course Alias Regulatory Compliance (AB1111) support

To comply with the Common Course Numbering System (AB1111) regulatory compliance in California, Banner Registration Self-Service displays a Course Alias field based on the system configuration.

Students can view the Course or Course Alias values based on the settings that are configured by Administrators in Banner Registration Self-Service.

Display Course Alias:

  • If the Course Alias is enabled (Display Course Alias) on the Course Alias Usage Rules (SCACARL) page for a term or college, and if there is a value in the Course Alias field for a Course, the Course Alias field will display as the Course Number throughout all of Registration Self-Service for that course.
  • If the Course Alias is enabled (Display Course Alias) on the SCACARL page for a term or college, and there is no value in the Course Alias field for a Course, the Course Number will display as normal throughout Registration Self-Service for that course.
  • If the Course Alias is disabled (Display Course ID) on the SCACARL page for a term or college, regardless of whether there is a value in the Course Alias field for any course, the Course Number will display as normal throughout Registration Self-Service.

Search by Course Alias:

  • The search parameter is compared against both the Course Number and Course Alias fields irrespective of the SCACARL configuration.
  • If the Course Alias is enabled (Display Course Alias) on the SCACARL page, and there is a value in the Course Alias field for a course, whether you search for the Course Number or Course Alias, the applicable course will be returned displaying the Course Alias.
  • If the Course Alias is disabled (Display Course ID) on the SCACARL page, and there is a value in the Course Alias field for a course, whether you search for the Course Number or Course Alias, the applicable course will be returned displaying the normal Course Number, and not the Course Alias.

Migration of Web Tailor configuration to Banner Applications Configurations (GUACONF) page

The configuration to display the Terms of Usage page available in Web Tailor Customize Web Rules is moved to the GUACONF page as DISPLAY_USAGE_INDICATOR under GLOBAL app ID. This key is delivered as seed data with the value picked from your current value of the Display Usage indicator.

For more information, see Terms of Usage in the Banner Self-Service Use content.

The configuration to set the PIN expiration days available in Web Tailor Customize Web Rules is moved to the GUACONF page as DEFAULT_PIN_EXP_DAYS under GLOBAL app ID. This key is delivered as seed data with the value picked from your current value of PIN expiration days.

For more information, see Third Party Information section in the Banner General - Page Reference.

Redis caching

You can configure Redis caching for Banner Self-Service applications. Redis can handle large amounts of real-time data, using its in-memory data storage capabilities to help support highly responsive database constructs. Caching with Redis allows for fewer database accesses, which helps to reduce the amount of traffic and instances required.

For more information, see Redis cache configuration in the Banner Registration Self-Service Install content.

Additional Fee Assessment API

A micro-service outside of Banner will be used, and the waiver solution requires a hook to be added to the RegistrationBatchFeeAssessmentCollectorService.groovy file. This hook checks if a valid Waiver connection is established in the External API Connection Information (SOAREST) page, and if a connection exists, a POST API request is sent to the waiver micro-service with the required information. The code on SOAREST is called "COF" for the College Opportunity Fund, but can be utilized for any applicable scenario where a hook is required to send an API request from Fee Assessment to trigger the micro-service.

Insert a script in the STVREST to add a new COF value.

COF College Opportunity Fund Y

An institution must create valid rows in the following Banner Admin pages:

  • Banner Applications Configurations (GUACONF) page for the tenantId under the global application, and determine the configuration.
  • External API Connection Information (SOAREST) page to set a timeout.
