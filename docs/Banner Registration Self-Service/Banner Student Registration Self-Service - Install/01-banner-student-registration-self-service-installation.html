Banner Student Registration Self-Service - installation

You can streamline the Registration Self-Service installation by using Ellucian Solution Manager (ESM) to complete most of the installation tasks. You do need to manually customize the WAR file, set up the application-specific configurations, and configure the application server.

This content includes information about installing Banner Student Registration Self-Service.

Review Banner product release dependency information in Ellucian Solution Manager or the Banner Interdependency Matrix attached to Article KB000500135 - Banner Interdependency and Compatibility Matrix in the Ellucian Customer Center.

Single sign-on (SSO) support

Ellucian recommends that you first establish the single sign-on environment before implementing Registration Self-Service.

Central Authentication Service (CAS) and Security Assertion Markup Language (SAML) 2.0 are the Single Sign-On (SSO) protocols supported by Registration Self-Service. Both are certified to run with Ellucian Ethos Identity. You can download Ellucian Ethos Identity from the Ellucian Customer Center.

For more information about how to establish a single sign-on environment, refer to the Ethos information available for download from the Documentation Libraries in the Ellucian Customer Center.

Warning: If you do not enable Single Sign-On (SSO), a user must authenticate before accessing each Banner 9.x application. If a user logs out of an application, the user is logged out of that current application, but is still logged in to all other applications that are currently open.

Configure shared settings

The shared_configuration home directory contains a cross-application configuration file called banner_configuration.groovy. You can change settings in this file. As part of improving the Banner security model, it is mandatory to externalize the cross-application configuration file banner_configuration.groovy by setting the system property -DBANNER_APP_CONFIG.

Shared configurations can also exist in database table (GUROCFG) under application ID GLOBAL. The configurations in database will always take precedence over the configurations in the file. Banner Common Database Upgrade 9.43 will have uploaded some shared configuration by default to the database (GUROCFG table). You can edit these configurations using the GUACONF page.

Shared configurations in the groovy file

These configurations are in the banner_configuration.groovy file.

JNDI datasource

You can optionally change the datasource name in the configuration file to point to the JNDI datasource that is configured in your application server.

For example, jndiName = "jdbc/bannerSsbDataSource" is the default configuration. You can change this to match the JNDI datasource name in your environment. If you change the jndiName, you must regenerate the WAR file, even if you are using an external configuration.

Location of images

The banner.picturesPath setting in the GUROCFG table specifies the location of student and faculty photographs.

In the banner.picturesPath = System.getProperty(‘base.dir’) + ‘/test/images’, banner.picturesPath setting is the application base directory appended with /test/images.

The base.dir is a system property that can be set through JAVA_OPTS.

The value of banner.picturesPath must be a fully qualified path to the directory that contains the image files. For example, banner.picturesPath = '/home/banner/test/images'.

Session timeouts

When you determine the timeout settings for CAS and Banner 9.x applications, consider the time limits imposed for each.

For example, if the Banner 9.x timeout setting is less than the CAS timeout setting, SSO authentication might still be valid even though the user is exited from the Banner 9.x application. As long as the CAS authentication remains valid, the user can re-enter the Banner 9.x application without re-authenticating.

The following timeouts are used in the self-service application.

banner.transactionTimeout

The banner.transactionTimeout setting is used to prevent excessive delays due to long database transactions. The setting is configured in the banner_configuration.groovy file. To use this timeout, set the banner.transactionTimeout setting to 300 seconds.

Ensure that either the configuration file is deployed with the application, or the application is using the configuration file where it is currently located.

If a database transaction takes longer than banner.transactionTimeout seconds, the transaction is aborted and any change is rolled back.

Note: In some cases, the web user interface might ignore the database timeout/error notification and not remove the loading spinner. If this occurs, refresh the page to continue using the application.
AJAX timeout

The AJAX timeout terminates HTTP requests that exceed the specified time limit. The self-service application sets the timeout value based on the banner.transactionTimeout setting plus an increment to allow for communication and processing of the request.

You do not need to override the AJAX timeout, but the timeout value can be overridden in JavaScript by calling $.ajaxSetup( { timeout: timeoutValue } );

Note: The timeoutValue must be in milliseconds.
Note: Although the web user interface continues after an AJAX timeout, the server might continue processing the request until it completes or reaches a database transactionTimeout.

Page Audit

Page Audit is a Banner Platform feature that enables page audit across Banner Self-Service applications.

Table Name: GURASSA

Information Description
Audit Time Application server time.
SSB Login ID The user id used to login to SSB. SPRIDEN ID is stored for Self-service users/SSO users. Email address is stored for Guest users.
Application ID Application ID for the page the user is accessing.
Page URL Page the user is accessing.

Example: /StudentRegistrationSsb/ssb/registration
IP Address IP address of user
Activity Date The date that information in this record was entered or last updated.
User ID The user ID of the person who inserted or last updated this record.
PIDM Self-service users get the respective PIDM. Guest users are not handled for this information yet.

Enable Page Audit

The following table shows a few example values and results:

App ID GUACONF    
  Key Value Result
Global EnablePageAudit N or null No pages audited.
    % All pages across all the self-service applications are audited.
    Registration Those URLs of applications that contain the word registration are audited. This is not case sensitive search.
    Hr Those URLs of applications that contain the word hr are audited.
Note: If you have configured the same configuration in the above table at the application level, then audit is enabled only for the configured application and not across all Banner Self-Service applications.
Login Audit

Login Audit is a Banner Platform feature that enables Login and Logout audit across Banner Self-Service applications.

Table Name: GURASSL

Information Comment
Audit Time Application server time.
SSB Login ID The user id used to log in to SSB. SPRIDEN ID is stored for self-service users/SSO users. Email address is stored for Guest users.
Application ID Application ID for the page the user is accessing.
IP Address IP address of the user.
User Agent User agent from the client browser.
Activity Date The date that information in this record was entered or last updated.
User ID The user ID of the person who inserted or last updated this record.
PIDM Self-service users get the respective PIDM. Guest users are not handled for this information yet.
Logon Comment

A comment recorded at logon/logout time

Login Successful for successful login

Logout Successful for successful logout
Note: For a better understanding of the Login Audit, see the following notes:
  1. Only successful login/logouts are audited in the new table GURASSL; the error cases will continue to be audited in GURALOG table.
  2. Single Sign On login/logout is also audited, tested with CAS and SAML.
  3. Login ID is Spriden ID for Single Sign On.
  4. User agent is the complete string from the browser that is used.
  5. Guest users are audited for Login/Logouts with the email address.

Configure application-specific settings

Banner 9 applications read configuration at startup from a shared configuration file (banner_configuration.groovy), from an application configuration file (StudentRegistrationSsb_configuration.groovy) and from the database table (GUROCFG).

The application configuration file setting can override the shared configuration file settings and the configurations in database can override any configurations set in the files.

Application configurations in the groovy file

The application configuration for Banner Registration Self-Service is set in StudentRegistrationSsb_configuration.groovy file.

Config job and application page role job

The job configurations configJob and applicationPageRoleJob have been added to the StudentRegistrationSsb_configuration.groovy file. configJob is an improved job and applicationPageRoleJob is a new job.

The purpose of these job parameters is to set the configurations for a job to run periodically to pick up the new values set on the database configurations or application page role and become active in the Self-Service applications.

The following old configJob configuration is deprecated, so Ellucian recommends to remove it from your configuration file.

configJob {
    interval = 86400000
    actualCount = -1
}
If the old configurations exist, the system ignores them and uses the new jobs instead. The application that is still on the older configuration or not configured for newer jobs falls back to the default:
  • 30 minutes run for configJob
  • daily mid-night at 00:00 run for applicationPageRoleJob

You can configure the configJob and applicationPageRoleJob jobs using Spring Scheduler cron expressions. See Config job and application page role job configurations in the Banner Self-Service Common Features Use content for information on customizing the cron expression for the jobs configJob and applicationPageRoleJob.

Note: The application configurations loaded in the database take precedence over the configurations in the configuration file. If you have removed the configurations from the database table, or have not configured the configJob, the application continues to use the configurations in the configuration file, not the ones in the database.
System properties configured in the groovy file

The following properties in the StudentRegistrationSsb_configuration.groovy file are internal to the application and are required for carrying out its own lifecycle activities. Leave these properties undisturbed.


grails.plugin.xframeoptions.urlPattern = '/login/auth' 
grails.plugin.xframeoptions.deny = true 
bnrStuRegSelfServShort="Registration Self-Service" 
banner.applicationName="StudentRegistrationSsb"
Institutional home page redirection support

The institutional home page redirection support configuration allows Registration Self-Service to provide an institutional home page to which users can navigate back to if they have access issues specific to insufficient privileges when accessing the Registration Self-Service application.

/*********************************************************************
* Home Page link when error happens during authentication. *
*********************************************************************/
grails.plugin.springsecurity.homePageUrl='http://URL:PORT/'
Proxied Oracle users

When connecting to self-service applications, the ssbOracleUsersProxied setting specifies whether the Oracle account is used for the database connections. The ssbOracleUsersProxied setting also controls whether Value Based Security (VBS) is enabled in the self-service application.

The following values can be used for the ssbOracleUsersProxied setting:
  • False - The Oracle account is not used for the connection and VBS is not enabled in the self-service application. If the Oracle account is locked, the user can still log in to the self-service application.
  • True - The Oracle account is used for the connection and VBS is enabled in the self-service application. If the Oracle account is locked, the user cannot log in to the self-service application.
Configure Banner Registration Self-Service for Single Sign-On

You can configure Banner Registration Self-Service to run in a single sign-on (SSO) environment using either Central Authentication Service (CAS) or Security Assertion Markup Language (SAML) SSO protocols. Ellucian certifies against and supports Ellucian Ethos Identity.

You can find more information about single sign-on in the documentation in the Ellucian Customer Center.

Redirect pages in a MEP environment

If your environment is enabled for Multi-Entity Processing (MEP), two settings (grails.plugin.springsecurity.logout) must be configured in the StudentRegistrationSsb_configuration.groovy configuration file for your environment. You do not need to configure these settings if your environment is not enabled for MEP.

If a user tries to access a self-service URL that does not include a valid MEP code, an error prompt is displayed on the Error page of the application and the user can use the Logout or Return Home button.

The following configuration settings determine where each button redirects the user:

  • grails.plugin.springsecurity.logout.afterLogoutUrl - This setting contains the URL of the institution-specific page where the user is redirected if the Logout button is clicked.
    For example, a portal page has the following settings:
    • https://cas-server/logout?url=http://myportal/ main_page.html (CAS environment)
    • http://myportal/main_page.html (non-CAS environment)
  • grails.plugin.springsecurity.logout.mepErrorLogoutUrl - This setting contains the URL of the institution-specific page where the user is redirected if the Return Home button is clicked.

Each URL can be any page that does not require a MEP-enabled database connection or any page outside the self-service application.

enableNLS configuration

The enableNLS configuration allows you to enable or disable the NLS DB package calls on every database connection.

Setting the enableNLS configuration to true enables the National Language Support in the Oracle database to the user specific language, that is, the error messages from Oracle database will display in the user specific language.

Setting the configuration to false disables the National Language Support for the error messages from Oracle database and improves the performance of the application. There are no expected impacts on the error messages in the application logs.

This key is delivered with a default value of true and is present in the application configuration file, StudentRegistrationSsb_configuration.groovy.

Registration Self-Service application extensibility

This feature gives a user defined in SPRIDEN whose Oracle user account has the WTAILORADMIN role the ability to show and hide fields on the user interface.

Note: You must assign the WTAILORADMIN role to any Oracle user who will work with Extensibility.

System properties configured in the database

These are the application-specific system properties in the database.

Update Student Term Data tab

The Update Student Term Data tab is optionally displayed on the Prepare for Registration page. This tab allows a student to update major, educational goal, and employment expectation information for any term in which the student has not already registered or changed this information.

The updateStudentTermData setting in the Banner Applications Configurations (GUACONF) page determines whether the tab is displayed. The default value is N (do not display the tab). If you want to give students access to the Update Student Term Data page, you must change the value of the setting to Y as follows:

updateStudentTermData = 'Y'

Note: Other settings in this configuration file are used to configure the link that appears on the Term Select page when in the registration path. These settings are temporary and are removed from the StudentRegistrationSsb_configuration.example when the Term Select page is fully functional.
Bookstore links

The Higher Education Opportunity Act (HEOA) requires your institution to configure at least one hyperlink to an online bookstore.

You can link to a bookstore web site in several ways:

  • With no parameters
  • With hard-coded parameters
  • With dynamic parameters
  • For a specific campus code

Bookstore links are configured in the GUACONF page. Links configured in this file are available at the section level for a course. Use the following parameters to set up a bookstore link:

Parameter Required/Optional Instructions
URL Required Enter a valid URL for the link to the bookstore.

For example: http://www.borders.com
Label Required Enter the messages.properties code to be displayed as the hyperlink label.

Add the code and the label text to the messages.properties file, using the bookstore.links.borders sample as a guide.
Campus Optional Enter specific links based on the campus code.

For example, if you have multiple campuses and you want to use a different Follett bookstore number for each campus, include a URL configuration for each campus and include the campus code in the URL parameters.
Page Required, if the Params parameter is used Enter the Overall Page and Field Configuration (SOAWSCR) page number, if the URL is specific to the search results (For example, 30 equals Section).
Params Optional Three options are available for identifying the parameters to be entered in the URL:
  • Select a value from SOAWSCR for substitution. (INSTRUCTOR and MEETINGTIME are not valid values.)
  • Identify the element directly from the section object code, if it is not on SOAWSCR.
  • Supply NAME in the parameter list, to pass student name to the bookstore link. The format of the name is specified in the default.name.format of General Person plugin messages.properties file. If using variables, use {0}, {1}, and so on, as placeholders for the parameters, appearing in the same order as in the params array.
Emailing and printing a schedule

You can set up links to email a schedule to a student or print a schedule.

If enabled, these links appear on the following pages:

  • Schedule and Options
  • Look Up a Schedule
  • Schedule by Centric Period (email only)

    Links are configured in the GUROCFG table.

The mail host setting must be your SMTP server. The your.smtp.address setting is your institution’s email address, such as mail.school.edu, or a valid IP address to the mail server. The from setting is the email address that is displayed in the From field of emails that are sent to students. This email address must also be a valid email address within your DNS/email server, preferably an email account that is not actively monitored. For example: 

grails {
mail {
host = "mailhost.sct.com" 
} 
} 
grails.mail.default.from="firstname.lastname@university.com" 
allowPrint = true
defaultWebSessionTimeout

The defaultWebSessionTimeout property is used to terminate user sessions that are left idle or abandoned without logging out. This setting is used to set the overall session inactivity time. The defaultWebSessionTimeout setting can be configured in the banner_configuration.groovy file.

Note: If defaultWebSessionTimeout is not specified, a default value of 1500 seconds is used.
Password reset

You can specify whether users have the ability to reset their passwords by updating the ssbPassword.reset.enabled setting.

If the value of the setting is true, users can reset their passwords. If the value of the setting is false, a disabled error message is displayed.

Configure application-specific settings using the GUACONF page

The Banner General Admin application provides a user interface to modify the configuration values on the Banner Applications Configurations (GUACONF) page.

About this task

Logback logging

Logging configurations are available in logback.xml file. In a PRODUCTION environment, this file resides in the Banner application's classpath. You can externalize the logback configuration as specified in the Externalize logback configuration topic.

These are the default settings for Banner logging:
  • The default Root logger level is configured to ERROR.
  • Logging is turned to DEBUG for specific packages and is commented.
  • Use JMX to change logger levels for Root or specific packages/artifacts.
  • JMX MBean must be unique for each application that is deployed into the JVM. This configuration should be updated for each instance of each application to ensure uniqueness.
    jmxConfigurator("${loggingAppName}-logback")
  • Users can specify a different logging directory using the following system property:
    -Dbanner.logging.dir=<full directory path> (THIS MUST BE AN ABSOLUTE PATH WITH WRITE PERMISSION)

    For example:

    -Dbanner.logging.dir=/home/tomcat/target/logs
  • Users can enable hibernate loggers by configuring the following system property:
    -Dorg.jboss.logging.provider=slf4j

    For example:

    setEnv.sh(linux)/setEnv.bat(Windows)
  • If a different logging directory is not configured, then the log files will be generated in the build folder as provided default by Grails.
Logging level

The root logging level is pre-configured to the ERROR level. Multiple class or package level configurations, by default, are set to a status of DEBUG and is commented.

You can set a different logging level for any package or class. However, configuration changes for logging take effect when the application is restarted.

For example,

<root level="DEBUG">
        <appender-ref ref="APP_LOG"/>
    </root>

Uncomment the packages or classes in the logback as required.

For example, //logger("net.hedtech.banner.security.​​​​​​SelfServiceBannerAuthenticationProvider", DEBUG).

If the package is not defined, then define in the above format.

Note: Changing the logging level to DEBUG produces very large log files.

Alternatively, you can use JMX to modify logging levels for any specified package or class, or even at the root level. When using JMX, the logging level changes only affect the running application. When you restart the application, changes that you made using JMX are lost.

Date format keys

The default.date.format and js.datepicker.dateFormat are date format keys that use different specifications to represent the date. The default.date.format is associated with the ICU format, which is dd/MM/yyyy. The js.datepicker.dateFormat is associated with the Java Script or Keith Wood format, which is dd/mm/yyyy.

For dates to be displayed properly, the two formats must match. For example, for 1 June, 2012, the calendar parses 01/06/2012 using js.datepicker.dateFormat, and when the dates are saved, the date value on the server side is parsed by groovy using default.date.format to display 01/06/2012 in the application.

default.date.format

This key determines the date format for display and data entry in the user interface. It must match the ICU specification and can be changed based on locale. For more information about the ICU specification, see https://unicode-org.github.io/icu/userguide/.

For the default.date.format for June 1, 2014, use one of the following variables for the year:

Year format Interpretation Comment
yy 14 Two digit year
yyyy 2014 Four digit year

For the default.date.format for June 1, 2014, use one of the following variables for the month:

Month format Interpretation Comment
M 6 Single digit month (no leading zero)
MM 06 Double digit month
MMM Jun Short month name
MMMM June Long month name

For the default.date.format for June 1, 2014, use one of the following variables for the day:

Day format Interpretation Comment
d 1 Single digit day in a month (no leading zero)
dd 01 Double digit day in a month

js.datepicker.dateFormat

This key determines the date format for the interactive date selection control. It must match the jQuery Keith Wood datepicker format specification. For more information on the Keith Wood datepicker format, see http://keith-wood.name/datepick.html.

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the year:

Year format Interpretation Comment
yy 14 Two digit year
yyyy 2014 Four digit year

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the month:

Month format Interpretation Comment
m 6 Single digit month (no leading zero)
mm 06 Double digit month
M Jun Short month name
MM June Long month name

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the day:

Day format Interpretation Comment
d 1 Single digit day in a month (no leading zero)
dd 01 Double digit day in a month

Configure email recipient

You must configure email recipient to enable support for users in a time zone that does not observe daylight savings time.

This configuration is required when the tomcat server is configured on a daylight savings time (DST) zone and application users are in non-DST time zone.

Add the following option to the catalina.sh file and restart the Tomcat server.

Add -Duser.timezone=<NON-DST TIME ZONE> at the end of existing CATALINA_OPTS.

For example: -Duser.timezone=America/Bogota

Configure Java management extension

This is an optional step that enables you to monitor or debug the application.

About this task

Java Management Extensions (JMX) is a Java technology that supplies tools for managing and monitoring applications, system objects, devices, and service oriented networks. Enabling JMX connections allows you to remotely monitor and debug the application server.

Procedure

  1. Add the following options to the catalina.sh file and restart the Tomcat server. 
    set CATALINA_OPTS=-Dcom.sun.management.jmxremote
-Dcom.sun.management.jmxremote.port=8999
-Dcom.sun.management.jmxremote.ssl=false
-Dcom.sun.management.jmxremote.authenticate=false
-Djava.rmi.server.hostname=your.hostname.com
  2. Change the java.rmi.server.hostname value to the hostname or IP address of the machine where Tomcat is installed.
    For example:
    -Djava.rmi.server.hostname=prod.appserver1.com
or
-Djava.rmi.server.hostname=149.24.3.178
  3. JMX does not define a default port number to use. If necessary, change com.sun.management.jmxremote.port to use port 8999.
    Ellucian recommends that you connect remotely to the Tomcat server using JMX.
    Warning: Ensure that the jmxremote.authenticate parameter is not set to False in a production environment. If it is set to False, it does not require connections to be authenticated and will create a security threat. For more information, see the Apache Tomcat documentation for Enabling JMX Remote.

Configure language preferences

As an admin user, you can configure the Language Setting option to be enabled (or disabled) for end users to allow them to choose a preferred language for their login sessions.

Set an institution level locale

You can set a locale at the institution level in addition to setting a preferred language for your user login.

Procedure

  1. Login to the Banner Admin application.
  2. Access the Banner Applications Configurations (GUACONF) page.
  3. In the Application ID field, enter GLOBAL, and click Go.
  4. Go to the Configurations tab.
  5. Under Configuration Name, on the Locale attribute row, in the Configuration Value column field, enter a locale value.
    The institution level locale takes effect.

Configure the Language Setting option

Use the following steps to disable (or enable) the Language Setting option for end users.

About this task

When you start the self-service application, an internal process inserts an entry for the 'Locale' configuration in the self-service configuration table (if the record does not exist). The default value for the User Preference Indicator setting is Yes and the Configuration Value is empty.

Perform these steps to disable the preferred language setting:

Procedure

  1. Login to the Banner Admin application.
  2. Access the Banner Applications Configurations (GUACONF) page.
  3. In the Application ID field, enter GLOBAL, and click Go.
  4. Go to the Configurations tab.
  5. Under Configuration Name, on the Locale attribute row, clear the User Preference Indicator check box.
    This disables the Language Setting option ignoring the user preference setting, and lets the browser locale take effect.
    Note: You can set the User Preference Indicator to Yes to enable the Language Setting option.
