Set up the Experience mobile app

The Experience App provides Experience content in a mobile app, available for both Android and iOS. The Experience App is available with Experience Premium.

Overview

The Experience App displays the same content as the Experience web application, providing a consistent experience for users who use both the web application and the mobile app. While the responsive design of the web application provides a good user experience in a mobile browser, the mobile application provides an improved experience by taking advantage of native mobile features, including:
  • Navigation and user interface conventions that users expect in a mobile app. Examples include:
    • Bottom navigation containing icons for home, search, calendar, notifications, and main menu.
    • Opening of external links as an overlay that provides intuitive navigation back to the app.
    • Push notifications sent for notifications posted to Experience.
  • Mobile communication features: Selecting a phone number launches the phone app, selecting an email address launches the email app, and selecting an address launches the map app.

The mobile application appears in the Apple App Store and Google Play Store as your institution's app, with customizable branding (app name, icon, descriptive text, and preview images).

Simplified setup

You do not need to be an app developer to create your mobile application with the Experience App. When you initiate the build of the mobile app from the Experience Setup application, Experience automatically builds the app and uploads it to Google and Apple. (You will need to create developer accounts in the Apple App Store and Google Play Store, and enter information about your app, to support creating your institution's iOS and Android versions of the Experience App).

No configuration or content setup is required specifically for the Experience App:
  • The Experience App uses the identity provider and Ethos configuration that you have already performed for the Experience web application to authenticate users and to retrieve information through Ethos.
  • The Experience App displays the same content as the Experience web application.

Documentation for setup in Google and Apple

This documentation for setting up the Experience App contains procedures for setting up the Experience App in the Google Play Store, Apple App Store, and Firebase, and provides links to Google and Apple documentation. The Google and Apple user interfaces and documentation might change without Ellucian's knowledge. If the Google or Apple user interface does not match the steps in this documentation, consult Google or Apple documentation for the comparable procedures.

Replacing an existing mobile app

The Experience App build process supports replacing an existing mobile app with the Experience App.

The Experience App setup procedures describe the appropriate entries if you are replacing an existing app. When you publish the Experience App to the Google Play Store and Apple App Store, the new app will have the same name as your existing app, and will automatically replace the existing app on users' devices. Users will not need to remove the existing app and then add the new app from the Google Play Store or Apple App Store.

Required Android artifacts

Replacing an existing app requires that you have the information listed below for your existing Android app.
  • Path to the keystore file
  • Keystore password
  • Key alias name
  • Key alias password

An administrator at your institution who set up the existing app would likely know those values.

If you do not have this information, you cannot use the Experience App build process to automatically replace the existing app. You will need to create an Experience App with a different name than your existing app, and your users will need to delete the existing app from their devices and add the new app from the Google Play Store or Apple App Store.

App name considerations

If you create a test version of your app from the Test instance of Experience, be sure to give it a name that is different than the name of the existing app that you are replacing. For details, see Suggested development approach.

Suggested development approach

To simplify the build process and avoid potential name conflicts, consider these recommendations for build environment and application name.

Build environment

When you access Experience Setup to build your app, you select an Experience instance (Test or Production). Ellucian recommends that you build your app only from the Production instance. Because both Google and Apple allow you to test your app with a small group of testers before making it publicly available, there is no need to build test versions of the app from the Test instance of Experience.

Application name and identifiers

If you choose to create a test version of the app from the Test instance of Experience, be sure to use different application names, bundle identifiers (Apple), and Application IDs (Google) in Test and Production. For example, include the word "test" in the name of the app created from Experience Test.

This approach avoids a potential conflict when publishing an app to the Google Play Store or Apple App Store. After publishing an app, you cannot use the Experience App build process in Experience Setup to create and publish a new app with the same name. That is, you cannot publish an app from Experience Test and later publish an app with the same name from Experience Production.

If you build your app only from the Production instance of Experience, as recommended in Build environment above, this is not an issue.

Supported devices

Users can access the Experience App on Apple and Android devices.

Supported versions:
  • Apple devices running iOS 17 or later.
  • Android devices running Android 12 or later.

Prepare for the Experience App

Configure Ellucian Experience and set up content

The Experience App uses the same configuration (such as identity provider setup and Ethos setup), and displays the same content, as the browser-based Experience web application. Before building your mobile application, perform the procedures in this documentation for configuring Ellucian Experience and setting up cards and other content.

Create image files for your app

You will need the following image files when you set up your app:
  • An icon that appears with your app in the Apple App Store and Google Play Store. The icon should be visible against the white splash screen in the mobile app. You need two versions of the icon:
    • A PNG image file, 1024 x 1024 pixels, and less than 1 MB. You will upload this version in Experience Setup and Apple.
      For guidance in creating your icon, see App icons in the Apple Developer documentation. In particular, consider these guidelines to avoid having Apple reject your submission:
      • Use a non-transparent image for the icon background layer.
      • Use graphical images rather than photos or screenshots.
      • Use a square image without rounded corners.
    • A PNG image file, 512 x 512 pixels, and less than 1 MB. You will upload this version in Google.
  • A feature graphic used to help promote your app in different places on Google Play. This must be a PNG or JPEG image file, 1024 x 500 pixels, and less than 1 MB

Create a Google developer account

Although you do not need to do any app development to create the Experience App, you do need to create a developer account in the Google Play Store to support creating your institution's Android version of the app.

Sign in to the Google Play Console with a Google account, and then create a Google Play Developer account. For the procedures, see the "Register for a Google Play Developer account" section of How to use Play Console.

Both the Google account and the Google Play Developer account should be associated with your institution rather than an individual.

Create a Google service account and API key

Ellucian Experience will use the service account and API key to securely access Google when uploading your mobile app.

About this task

You can use the same service account and API key for all Experience App development.

Procedure

  1. Access the New Project page in the Google Cloud Console, using your Google developer account.
  2. Enter a project name and then click Create.
    You can skip the Location section.
  3. Enable the Google Play Android Developer API for the new project:
    1. Access the Google Play Android Developer API page.
    2. Select the project you created.
    3. Click Enable.
  4. Access the Service Accounts page.
  5. Select the project you created.
  6. At the top of the page, click +Create Service Account.
  7. On the Create service account page, enter the service account settings:
    1. In the Service account details section, enter a service account name.
      This name appears in the list of service accounts on the main Service accounts page.

      Example name: Experience App access

    2. Click Create and Continue.
      Google creates a service account and an associated email address.
    3. In the Grant this service account access to project section, click the Select a role drop-down and enter service account user in the Filter box, and then scroll down and select Service Account User from the list.
    4. Click Continue.
      You can skip the Grant users access to this service account section. The Experience App does not use that option.
    5. Click Done.
  8. Back on the Service accounts page, locate the email address for the new service account that you just created. In that row, expand the Actions menu and then click Manage keys.
  9. On the Keys page, click Add Key > Create new key.
  10. In the Create private key dialog, select JSON and then click Create.
    The JSON key is automatically created and downloaded to the downloads folder on your computer.
  11. Back on the Service accounts page, copy the email address for the new service account.
  12. Access the Google Play Console using your Google developer account.
  13. In the menu, click Users and Permissions.
  14. On the Users and Permissions page, click the Action menu next to the Manage users drop-down, and select Invite new users.
  15. On the Invite user page, do the following:
    1. In the User details section, in the Email address field, paste the email address for the service account that you copied in Step 11.
    2. In the Permissions section, click the Account permissions tab.
    3. In the Account permissions section, click Admin (all permissions).
    4. Click Invite user.
    5. In the Send invitation? dialog, click Send invitation.
      No further action is required (that is, you do not have to accept the invite elsewhere).

Define the settings for your Android app in the Google Play Console.

    The entry must use only alphanumeric characters.

    Make a note of this app name. You will need to enter it again in Experience Setup.

    Note: You enter the app name in three places: the Google Play Console, Apple App Store Connect, and Experience Setup. The app name must match in all three places.
    Package name Enter a Package Name for the app.

    You can check availability to confirm if the entered package name is available. Ellucian recommends that you use a reverse domain style entry.

    Example: edu.mycollege.mobileapp

    Make a note of this package name. You will need to enter it again in Experience Setup.

    Note: You enter the package name in two places—the Google Play Console and Experience Setup > Mobile Application > Connect Google Play Store > Application ID. The package name must match in both places.
    Default language Select the default language for your app.
    App or game Select App.
    Free or paid Select Free.
  4. Complete the Declarations section and then click Create app.
  5. On the Dashboard page, in the Set up your app section of the page, expand View tasks.
  6. In the Let Us Know About the Content of Your App section, enter information about the app content. After completing each category, click Save and then return to the dashboard to continue with the next category.
    Category of information Entries

    App access

    2. Click Add instructions.
    3. In the dialog:
      1. Enter a username and password. When you submit your app for approval, Google will use these credentials to review your app.
      2. Select No other information is required to access my app.

    Content rating
    1. Click Start questionnaire.
    2. On the Category page:
      1. Enter an email address that Google can use to contact you about the content ratings. This should be an institutional email address (such as mobileinfo@mycollege.edu) rather than an individual email address.
      2. Select the All other app types category.
      3. Select the Terms and conditions check box.
      4. Click Next and then complete the questionnaire.
    Target audience Select the age groups that include the expected users of your app.
    News apps Select No.
    Data safety This section contains a questionnaire with a large number of questions about how the app collects and shares user data.     1. Click Select an app category and provide contact details.
    2. On the Store settings page, in the App category section, click Edit.
    3. On the App category page, enter the information below and then click Save.
      Setting Entries
      App or game Select App.
      Category Select Education.
    4. Optional: Back on the Store settings page, still in the App category section, click Manage tags and then enter tags to help users find your app in the Google Play Store.

    6. On the Store Listing contact details page, enter an email address that will appear in the Google Play Store with your app. This should be an institutional email address (such as mobileinfo@mycollege.edu) rather than an individual email address.

    Full description

(New app) Build the Android app

The build process creates the Android app and uploads it to the Google Play Store.

About this task

If this is the first build of this Android app, the build will likely fail due to a limitation in the automated upload process, as indicated by a build status of Failed. After performing this procedure, you will need to continue with Manually roll out the Android app (first-time build).

Procedure

  1. In the Ellucian Customer Center, click Tools and then select Experience Setup to access the Production instance of Experience Setup.
    See Build environment for the basis for using the Production instance rather than the Test instance of Experience.
  2. Click the Mobile Application tab.
  3. Enter the application name and ID:
    Setting Entry
    Application Name Enter the app name that you defined when you set up this app in the Google Play Console.
    Note: You enter the app name in three places: the Google Play Console, Apple App Store Connect, and Experience Setup. The app name must match in all three places.
    Connect Google Play Store > Application ID Enter a unique identifier for the app. For considerations, see Application name and identifiers.

    You are defining this application ID here. It does not need to match anything you entered in Google. Ellucian recommends that you use a reverse domain style entry.

    Example: edu.mycollege.mobileapp
  4. Enter the remaining build settings:
    Setting Entry
    Connect Google Play Store > Upload JSON file Click CHOOSE FILE and then upload the API key file you created and downloaded using the procedure in Create a Google service account and API key.
    Google Client ID If you are using the Google Productivity Cards (Gmail and Google Drive cards), enter the client ID. You can copy that value from the Experience card:
    1. In Experience Card Management, edit either of the Google Productivity Cards.
    2. In the Configuration section of the card setup page, copy the value in the Google OAuth Client ID Android field.
    3. Paste that value here in the Google Client ID field.
    Application Icon Click CHOOSE FILE and then upload the 1024 x 1024 version of the icon you created for your app as described in Prepare for the Experience App.
  5. Click Start New Build > For Google Play Store.
    Note: Only one Google build can be in progress at a time. If a build is currently in progress, the Start New Build command will not be available.
  6. In the Start New Build dialog, do the following:
    1. Enter comments (optional) to help you identify later what you changed in this build.
    2. Click Submit.
  7. On the Build Status page, review the status of the build.
    Build Status Description
    Queued Experience is preparing the build.
    In-Progress Build is in progress. Periodically refresh the page to update the status. The Google build typically takes five to ten minutes.
    Ready The build succeeded, and the app has been uploaded to Google. (The app is not yet available to testers or other users in the Google Play Store; you will perform steps later to make the app available to those users.)
    Failed The build failed. Click Details for information about the problem.
    Note: See Manually roll out the Android app (first-time build) for information about the expected failure of a first-time build and the steps to work around that issue.
Manually roll out the Android app (first-time build)

For the first build of the Android app, you will need to manually upload the app file to Google and set up a closed test track.

About this task

For the first build of a new Android app, the AAB file is automatically uploaded to the Google Play Console Internal Testing track.

Due to a limitation in the Google APIs, newly created apps remain in a Draft state until a release is manually rolled out from the Play Console. While Experience Setup can successfully upload the first build, it cannot complete the final Save and publish (rollout) step for new apps. The following instructions guide you through finalizing the first build by reviewing the draft release and initiating the rollout to internal testing in the Google Play Console.

Procedure

  1. Access the Google Play Console using your Google developer account.
  2. On the Google Play Console home page, locate your app and click View app.
  3. In the menu, select Test and release > Testing > Internal testing.
  4. On the Internal testing page, open the Releases tab.
    You will see a release already created by Experience Setup with the uploaded AAB file in Draft status.
  5. Click Edit release.
  6. Review the release details.
  7. Click Next.
  8. Click Start rollout to internal testing (or Save and publish, depending on UI).
  9. Confirm the action in the dialog.

Results

Future builds created through Experience Setup will be automatically deployed to your Internal Testing track. The Play Store UI can be used to promote these builds to Closed Testing or Open Testing if desired.

Set up app key signing

For the replacement of an existing app with the Experience App, you must set up app key signing in the Google Play Console.

About this task

An existing app that you are replacing with the Experience App probably uses an APK file, which requires that you set up app key signing. If your existing app uses an AAB file (the same file type used by the Experience App), you do not need to set up app key signing. To determine whether you need to set up app key signing, perform the initial steps in this procedure and look for the information message described in Step 4.
If you do need to set up app key signing, you will need the following information for your existing Android app:
  • Path to the keystore file
  • Keystore password
  • Key alias name
  • Key alias password

Procedure

  1. Access the Google Play Console using your Google developer account.
  2. On the Google Play Console home page, locate your app and click View app in that row.
  3. In the menu, select Test and release > Testing > Internal testing.
  4. On the Internal testing page, on the Releases tab, click Create new release.
    On the Create internal testing release page, in the App integrity section of the page, you will likely see the message "Releases not signed by Google Play." This indicates that you need to set up app key signing using the steps in the rest of this procedure.

    If you do not see that message, you can skip this procedure.

  5. Click Use Play app signing.
  6. On the App signing page, in the Let Google Play manage your app signing key section, select Use existing app signing key from Java KeyStore.
  7. Click Download encryption public key.
  8. Click Download PEPK tool.
  9. Click the copy icon to copy the command, and paste it into a command prompt window.
  10. On the computer where you downloaded the PEPK tool, create a folder that will contain the private key that will be created when you run the command.
  11. In the command prompt window, modify the command:
    Replace this: ...with this:
    pepk.jar Full path to the pepk.jar file that you downloaded in Step 8.
    foo.keystore Full path to the keystore file for your app.
    foo Your key alias name
    encrypted_private_key_path Full path to the private key that will be created when you run the command.

    This path should end in the folder you created in Step 10 followed by a name for the private key file. For example, if you created a folder called exp_app_private_key, and you want the file to be called private_key.pem, this path would end in exp_app_private_key\private_key.pem
    /path/to/encryption_public_key.pem Full path to the encryption public key file that you downloaded in Step 7.
  12. In the command prompt window, run the command.
    Tips for successfully running this command:
    • Make sure you have OpenJDK version 21 or later installed on your computer.
    • If you are on a Windows computer, and the command fails, you might need to enter the full path of the java executable.
  13. When prompted, enter the keystore password and the key alias password.
    The command creates the private key file in the folder that you specified.

Experience content requirements to support the iOS app

To support the iOS version of the Experience App, all content linked from Experience must reside on a server that complies with Apple's App Transport Security requirements described in TLS Security.

For example, this linked content might include images and documents that reside on your institution's servers or servers outside of your institution. Update the app version number

The app version number in Apple must match the build version number to prevent spurious warnings to users.

About this task

When you submit an app for review, you enter information including a version number. The default version number has a value like 1.0. For the Experience App, you need to replace that with the build version number, which has a format like 1490.100.xxx.
Note: If these build numbers do not match, users might get spurious notifications that a new app version is available and they need to update their app, when in fact they have the latest version.

Procedure

  1. Access App Store Connect using your Apple developer account.
  2. On the App Store Connect home page, click Apps.
  3. On the Apps page, click your app.
  4. Scroll down to the Build section of the page.
  5. Add the Test Flight build that you want to submit for review.
    If you previously added a build, and want to use a different build, remove the existing build and add a new one. For details, see Choose the build before you submit to review.
  6. Back on the page for your app, copy the version number in the VERSION column of the Build table.
  7. Scroll up and enter that version number in the Version field.
    The default version number has a value like 1.0. Replace that with the Experience build version number, which has a format like 1490.100.xxx.
  8. Click Save.

Publish the iOS app

Publishing the app makes it available to end users. Follow the instructions in the Overview of publishing an app section of the App Store Connect Help, including the steps for submitting your app for review.

Follow this guidance to avoid a rejection of your app by Apple, based on customer experience:
  • Thoroughly test your app before submitting it, as described in Test the iOS app.
  • Your submittal will include the credentials for a user account that Apple will use when testing the app. That user must have usage tracking enabled in Experience. Sign in to Experience as that user, go to the Profile page, and enable the SHARE USAGE DATA setting.
