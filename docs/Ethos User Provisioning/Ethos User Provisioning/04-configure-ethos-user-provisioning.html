Configure Ethos User Provisioning

The configuration procedures institutions need to complete before their administrators can provision users with Ethos User Provisioning (EUP).

EUP configuration requires administrators to complete a series of tasks using a number of different applications and user interfaces. At a high level, these tasks can be broken down according to the application or interface that administrators use to complete each task:
  1. Integrate EUP and Banner or Colleague—This release of EUP supports integration with Banner or Colleague, and administrators set up and configure the integration of Banner or Colleague and EUP in Ellucian Ethos Integration. They may also have to complete additional configuration tasks in each ERP to support the integration. The required configuration steps here require significant experience of working in Banner or Colleague and how to integrate these ERPs with Ethos Integration.
  2. Configure the identity provider—Administrators define and maintain this configuration in the EUP Administrative UI, a dedicated user interface developed by Ellucian for EUP. The configuration of an identity provider in this interface requires a working knowledge of identity management systems in general and of the provider in particular.
  3. Configure the Experience cards for EUP—Administrators use Ellucian Experience to enable and configure the Experience card or cards required for EUP, so that other users can access and work with these cards on their Experience dashboards. This requires a detailed understanding of what Experience is, its key features, and the workflows it supports.

So, the required configuration tasks in each application or interface require a different skillset and no single administrator will have the skillset required to complete all of these tasks. Ellucian recommends that you complete these tasks in the order indicated above. You cannot configure the identity provider unless you have successfully integrated EUP and Banner or Colleague in Ethos Integration. Similarly, the Experience card for EUP will not provide any useful functionality if you have not successfully configured the identity provider.

  • Asia-Pacific (Sydney)

Do note that EUP uses the same Ethos tenant across regions. So, institutions who may have sites or campuses in different regions, the United States and Canada, for example, do not have to have dedicated Ethos tenants in each region, and can use a single tenant.

Integrate EUP and the ERP

To provision user identity data from an Ellucian ERP (Banner, Colleague) to an identity provider with EUP, you must integrate these systems with Ethos Integration.

Ellucian Ethos Integration acts as a data conduit between applications, allowing them to participate in a messaging enterprise that individual institutions can configure as required. It supports the exchange of data through publish/subscribe, proxy API requests, and GraphQL. See Ethos Integration overview for an introduction to Ellucian Ethos Integration and to access the extensive documentation resources that Ellucian provides for this technology.

Following standard conventions, Ethos Integration refers to a system that owns or manages data, and is considered to be the primary or most reliable source for this data, as an authoritative source. EUP currently supports two authoritative sources of the user identity data it requires to provision users in an Identity Provider (IdP)—the Ellucian ERPs Banner and Colleague.

As authoritative sources of the data, the ERPs must publish change notifications through Ethos Integration for any changes to this data, which EUP consumes and processes to provision new users, update existing users, or delete users in the IdP. These change notification records must be in a specific JSON format that adheres to the user-identity-profile API data model (the exact version depends on the ERP). To support this process and to ensure the successful provisioning of users to the IdP, administrators must integrate EUP with the ERP through Ethos Integration.

Data rule mapping in GTVSDAX

Banner allows users to have an unlimited number of email addresses, physical addresses, and phone numbers.

Map every email address, physical address, and telephone number element in the user-identity-profiles structure to a Banner contact type. To accomplish this mapping, use the Crosswalk Validation (GTVSDAX) page. The capture and apply processes use these GTVSDAX rules to retrieve data from Banner and populate the associated elements in the user-identity-profiles model.

Note: You can skip further configuration if you have already configured these rules.

  • Internal Code: IDM

  • Sequence: 1 (Add a code sequence that fetches the address type at index 1 from the list of address types)

Extend the user-identity-profiles API

You can add any extension attribute that is not a part of the user-identity-profiles model following established procedures to extend Ethos APIs for both Banner and Colleague.

If an institution requires additional attributes for any Banner or Colleague Ethos API, it can:
  • Extend an Ethos API delivered by Ellucian.
  • Create a custom API.

For EUP, Ellucian recommends that institutions extend the user-identity-profiles API instead of creating a custom API. It provides detailed documentation resources that describe how to extend Ethos APIs for Banner and Colleague. The documentation provided here complements these resources with additional information on extending the user-identity-profiles API.

Banner

Banner Ethos API Extensibility is a set of tools, practices, and patterns that enable an institution or Ellucian partner to extend and add new attributes to any Banner Ethos API, including user-identity-profiles. See Banner Ethos API Extensibility and related topics for more information.

At a high-level, the process to extend a Banner Ethos API, including the user-identity-profiles API, using Banner Ethos API Extensibility consists of the following steps:
  • Define requirements to understand what kind of extension you require and where it is sourced from in Banner.
  • Configure Banner to define a mapping for the new extension.
  • Create the required Banner Event Publisher (BEP) events.
  • Map the BEP events to the API.
  • Configure the API to manage and enable the extension.

Deprovisioning

Support for automated deprovisioning processes is a core requirement of any user life cycle management system, including EUP, which supports different mechanisms and options for deprovisioning users, which depend on the identity provider.

Deprovisioning in EUP is based on a deprovisioning trigger, a condition or event that causes the deprovisioning of a user from an identity provider. In EUP, you can define and enable a deprovisioning trigger based on role matching in an incoming change notification, or matching the value of a specific attribute in this notification.

  • With the role matching trigger, deprovisioning occurs when a user does not have any of the roles you have configured for an identity provider target in EUP.
  • With the attribute matching trigger, deprovisioning occurs if an attribute value matches the value you have defined for a role in EUP, but only if the user does not have any active roles.

You can configure these triggers at the target, or global, level and at the role level in the EUP Administrative UI. The exact details depend on the identity provider. You cannot configure or enable deprovisioning for SCIM identity providers in this release of EUP.

Note: EUP does not update any attribute values when deprovisioning users, by design. This applies to both deprovisioning by No Configured Provisioning Roles and to role-based deprovisioning by attribute value triggers. Attribute updates are prevented by design when a user is being deprovisioned.

Use cases

EUP can deprovision the same user multiple times, but only under the following conditions:

  • When it deprovisions a user that is already deprovisioned from role-based to global deprovisioning . For example, if the user is already deprovisioned (role-based), it can deprovision again by removing the one valid role.
  • When it deprovisions a user to another role with matching attribute values, and deprovisioning only occurs based on the Move User OU and No Disable account settings in the EUP Administrative UI.

Deprovisioning does not occur in the following cases:

  • When EUP has already deprovsioned the user, by disabling the user account, and it attempts to deprovision the same user again, role-based to role-based, or global to global or global to role-based. This only works for role-based to global deprovisioning, as noted.
  • When EUP attempts to deprovision a user again with the same role and matching attribute value.

AgentAD and AgentLDAP

For AgentAD and AgentLDAP, you can configure the role matching deprovisioning trigger at the target level, only, on the Global Configuration tab in the EUP Administrative UI. You can do this as part of the overall configuration of the targets for these providers. See Configure an AgentAD target and Configure an AgentLDAP target for details.

You configure the attribute matching trigger for AgentAD and AgentLDAP at the role level, only, on the Role Provisioning Rules tab in the UI. See Configure attribute matching deprovisioning (AgentLDAP, AgentAD) for more information.

These providers can only use one of the deprovisioning triggers in EUP, and cannot use both triggers. If you do in fact configure both triggers, the attribute matching trigger takes precedence over the matching roles trigger, and deprovisioning only occurs when the system executes this trigger.

The attribute matching trigger only deprovisions a user if that user does not have an active role in the incoming change notification. If a user has at least one active role, then deprovisioning does not occur, regardless of the triggers you have defined in EUP and the values in the notification.

In EUP, a user does not have an active role if:
  • The user does not have any institutional roles in the change notification.
  • The user has a role, but the attribute and value defined for this role, in its attribute matching trigger, matches that in the change notification. So, for example, if the user had a role of Student, and you had defined a trigger for this role using the attribute studentStatus with a value of inactive, then the user is not considered to have an active role, and is deprovisioned, if the change notification also contains the studentStatus attribute with a value of inactive (assuming the user has no other roles).
  • The user has two or more roles, but the attribute and value defined for each role, in the attribute matching triggers for these roles, matches that in the change notification. So, for example, if the user had a role of Student and Faculty, and you had defined triggers for these roles using the attributes studentStatus and facultyStatus, both with a value of inactive, then the user is not considered to have an active role, and is deprovisioned, if the change notification also contains the studentStatus and facultyStatus attributes with the values inactive (assuming the user has no other roles).

    This logic also applies if a user does not have all of the roles for which you have configured an attribute matching trigger. So, in this example, if a user only had the Faculty role, the system would deprovision that user when processing the same change notification.

    It also applies if the user does not have any institutional roles in the change notification, but the notification contains the attributes and values defined for the attribute matching triggers, in EUP.

User Account Control value requirements

For Active Directory, EUP does not support reprovisioning of users from a disabled state when the user account control value is any value other than 514. If you attempt to reprovision a user with a different user account control value, the system automatically throws an error:

User xxxx cannot be reprovisioned as the user was not disabled by EUP. Please update the User Account Control value for the user xxxx to 514 in the IDP and try to reprovision it again

EUP also does not allow update of users when the user account control value is set to anything other than 512. Customers must update their users with a user account control value of either 512 when updating users or 514 when reprovisioning users.

Reprovisioning

In a user life cycle management system, reprovisioning refers to the process of recreating user accounts that the system had previously disabled, deprovisioned, or moved to an inactive Organizational Unit (OU). EUP currently supports reprovisioning for Okta, Microsoft Entra ID, AgentAD, and AgentLDAP.

In EUP, reprovisioning is based on active roles, which it reassigns to a user during the reprovisioning process. If it attempts to update a user who does not have at least one assigned active role, then this update attempt fails.

To support reprovisioning, EUP prevents any updates to user attributes during the deprovisioning process or after it, when a user is already disabled. In this case, the system generates an error message to the effect that it cannot update the attributes as the user is already deprovisioned.

Organizational Unit movement during reprovisioning

When reprovisioning users, EUP moves the users back to an available Organizational Unit (OU), as determined by the configuration settings in the EUP Administrative UI.

The default behavior of EUP, to move the user back from an inactive OU, operates as follows:
  • When a user is in an inactive OU and reprovisioning is triggered, with the highest priority role configured in the UI so that the Move user switch is set to on, then EUP moves the user to the OU defined for the highest priority role using the Organizational Unit field associated with the Move user switch.

    Administrators can access the Move user switch and the Organizational Unit field in the Move Existing Users section on the Role Provisioning Rules tab in the UI.

  • When a user is in an inactive OU and reprovisioning is triggered, with the highest priority role configured in the UI so that the Move user switch is set to off, then EUP moves the user to the OU defined for the highest priority role in the Organizational Unit field on the Create User tab in the UI.
  • When a user is in an inactive OU and reprovisioning is triggered, with the highest priority role configured in the UI so that the Do not move user to any Organizational Unit switch is set to on, then EUP moves the user to the OU defined for the highest priority role in the Organizational Unit field on the Create User tab in the UI.

    Administrators can access the Do not move user to any Organizational Unit switch in the Move Existing Users section on the Role Provisioning Rules tab in the UI.

  • When a user is not in an inactive OU (and only disabled), then EUP moves the user in the same way as described in the scenarios above, if it needs to move that user.

Before you begin

About this task

You can access the field mappings for a role on the Field Mappings tab, which the system displays on the Role Provisioning Rules tab in the UI when you select the role. The mapping is defined between a target field, in the identity provider target, the identity provider you selected when creating the target, and a source field, in EUP.

Each target has a specific set of target fields that it must have a mapping for to successfully provision user accounts, that is these required fields define the minimum set of values a user account must have in that target. Ellucian defines a set of baseline mappings for these required target fields, which as expected, depend on the platform type the target. The UI displays these mappings on the Field Mappings tab for every role you create when configuring a target. You cannot delete the baseline mappings but can edit these mappings if required by updating the target field of the mapping. To meet additional custom requirements, you can augment the baseline mappings with one or more custom mappings for any role, and you can delete these custom mappings if required.

The procedure for managing role-level field mappings is the same for all identity provider targets, and is described below. It does not depend on the platform type of the target.

When you have defined the required field mappings, you can select the searchable attribute for the role from the list on the Field Mappings tab. This takes precedence over the default searchable attribute you defined on the Global Configuration tab for the target, but only for this role.

    • The Actions column contains icons that enable you to manage the mapping. The system displays the edit icon in this column for the baseline mappings, but the edit and delete icons for custom mappings.

  7. Define the target and source fields for the new mapping in the corresponding fields.
    The source field is the property in the provisioning request payload that you want to map to the target field in the identity provider target. The structure of the provisioning request, and the properties in the request, are determined by the schema of the user-identity profiles API. You can view the schema in the API catalog, which you can access through the Ellucian Documentation site.

    The Ellucian ERPs Banner and Colleague use different versions of the API, each with a different schema. So, the integrated ERP determines what source fields you can add here. You must enter the name of the source field exactly as defined in the schema.

    The target field is the corresponding or matching field in the identity provider target. Again, you must enter the name of this field as defined in the target. The system does not validate the values that you enter for the source and target fields, but it does display a warning at the top of the Field Mappings tab stating that you must ensure that a mapping exists for every required field in the identity provider target to avoid provisioning failures, and to ensure that all target attributes are available in the target.

    So, to take a very simple example, if your integrated ERP is Banner, you could define the source field as say mobilePhone and the target attribute as cellularPhone. You could also define the same mapping in Colleague, as the corresponding schema also includes the same mobilePhone property.
  8. Click Add in the Actions column to add the custom mapping.

    The system adds the new mapping to the list of mappings. You can add additional custom mappings, if required.

    Tip: EUP considers the baseline and custom mappings you have defined for every role when provisioning users, and not only the highest priority role. However, if you define a mapping for the same source attribute, but to different target attributes, for two or more roles, than EUP provisions the user using the mapping defined for the highest priority role, only.
  9. Edit a baseline or a custom mapping by clicking the edit icon in the Actions column for the mapping.

    You can edit the source and target fields for baseline and custom mappings and when you click the icon to edit a mapping, the system activates the source and target fields. It also replaces the icons in the Actions column with the Cancel and Update buttons.

    You must ensure that you map the mandatory target attributes for every baseline mapping to the correct source attribute, so as to avoid provisioning failures. The system displays a warning message to this effect at the top of the Field Mappings tab, as mentioned. Similarly, if you edit a target attribute, you must ensure that the updated attribute is available in the corresponding IdP.

  10. Update the source or target fields and click Update in the Actions column.

    The system updates the mapping, but only if you have defined mappings for all mandatory, target attributes.

    If you have not defined a mapping for a mandatory target attribute, or attributes, the system displays the following error message at the top of the Field Mapping tab: The target attribute(s) ‘target_attribute_list’ are mandatory and must be mapped to a source attribute, where target_attribute_list is a comma-delimited list of the mandatory, target attributes. You must resolve this error before you can update the mapping, by ensuring that mappings exist on the tab for each target attribute listed in the error message.

    Tip: If a change notification from an ERP is missing the one or more of the mandatory target attributes for an IdP, EUP displays the following error, for both the bulk and real-time provisioning workflows in the Provisioning Metrics UI: Unable to Provision User because user payload is missing Mandatory IDP Attribute - [Missing Attributes List], where Missing Attributes List is the list of missing attributes. Administrators can define one or more groups for a role on the Group Membership tab in the EUP Administrative UI. When a user is assigned a role, they are also assigned to the specified list of groups defined for that role.

Install

You can install the EUP agent in Windows using the latest version of an installation file that Ellucian provides on Ellucian Downloads. After extracting this file, you must complete some configuration steps to ensure the agent can run in your environment.

Procedure

  1. Download the installation file (a .zip file) for the latest version of EUP from Ellucian Downloads, which you can access through the Ellucian Customer Center.
    1. Log in to the Ellucian Customer Center.
    2. Click Resources in the header bar, then, under Downloads, click All Downloads.

    3. Select Downloads in the header bar and select the Search Downloads option.
    4. Enter Ellucian-Ethos-User-Provisioning in the search field, accept the option to show results for packages, but select the option to sort the results by date, and click Search.
    5. Open the latest package from the list, the package for the latest version of EUP.
    6. Download the eup-agent-version.zip installation file from this package, where version refers to the version number.
      The package also contains a readme file that you can also download, but this is not necessary.
  2. Extract the installation file you downloaded in the previous step, eup-agent-version.zip, into the EUP directory.
    Tip: Ensure that the name of the directory or folder into which you extract the installation file for the EUP agent does not contain a space or any other special characters. Also, do not include the version number in this name, as this can cause confusion during future upgrades of the agent.
  3. Check if you have installed the required version of NodeJS, or not.
    • If NodeJS is already installed in your system, proceed to the next step.
    • If you do not have a NodeJS installed in your system, download and install the Node Long Term Support (LTS) version from https://nodejs.org/en/download.
      Note: Ensure that you download the .msi installer for NodeJS on Windows.
  4. Open the configuration file EUP/eup-agent/eup-agent-config.json in a text editor of your choice and add the required directory service details and tenant ID configurations to this file.

    You can define one or more identity provider targets in EUP for the identity providers it supports, including AgentAD and AgentLDAP, where a target corresponds to a specific deployment of that provider. Each target has a label, defined in the EUP Administrative UI, that uniquely identifies the target in your Ethos environment. See Create an identity provider target for details.

    The properties in the eup-agent-config.json configuration file can be classified as common properties, which apply to all AgentAD and AgentLDAP targets in your environment, and target-specific properties, which apply to a specific target. You only have to define a single value for the common properties in the configuration file, but values of the target-specific properties for each AgentAD or AgentLDAP target. You define the target-specific properties in the IDPLabel array, and each item in this array corresponds to a specific target. You must define values for the common properties and for every AgentAD and AgentLDAP target if you want EUP to provision users to these targets.

    Property Description
    Common Properties
    webSocketUrl The URL of the production web socket connection to pull the payload details.

    This URL depends on the AWS region in which you have deployed EUP, and you must specify the correct URL for your region. The default value is the URL for the United States, and you only have to update this URL if you have deployed EUP in another region.
    metricsUrl The URL for accessing production metrics to send provisioning status.

    This URL depends on the AWS region in which you have deployed EUP, and you must specify the correct URL for your region. The default value is the URL for the United States, and you only have to update this URL if you have deployed EUP in another region.
    tenantId The ID of the Ethos tenant for your institution. You can copy this ID from different user interfaces, including the EUP Administrative UI.
    ethosIntegrationURL The Ethos Integration URL.

    This is the URL to which EUP will post messages for Ethos Integration to consume and it depends on the AWS region in which you have deployed EUP. You must specify the correct URL, or domain, for your region. See Ethos Integration domains for details. The default value is the URL for the United States, and you only have to update this URL if you have deployed EUP in another region.
    LOG_RETENTION_PERIOD The retention period for agent log entries, in days. It deletes entries after the retention period elapses.
    poolsize The size of the pool to allow asynchronous requests in the EUP agent.
    connectionTimeout To accommodate the server inaccessible error for a short while, the ConnectionTimeout parameter is introduced where the server polling happens until connection is made or connection times out with the value set in eup-agent-Config.json file.

    The default ConnectionTimeout value is set to 10000.
    oauth_Url The URL to the EUP OAuth server. The value of this property depends on the AWS region in which you have deployed EUP.
    • Set this value to https://oauth.prod.50639.elluciancloud.com/token for deployments in the Middle East (UAE) region.
    • Set this value to https://oauth.prod.10005.elluciancloud.com/token for deployments in all other regions.
    Target-Specific Properties
    IDPLabel The name of the array that defines the properties for each target in your Ethos environment. Each item in this array contains values for all of the target-specific properties described below.
    name The label of the AgentAD or AgentLDAP identity provider target.

    The value you enter here must exactly match the label you have defined in the EUP Administrative UI. As such, Ellucian recommends that you copy and paste this label from the UI. It displays the label in the corresponding column of the identity provider target list, which you can access by clicking the Identity Provider Configuration link in the header bar. It also displays the label when you open a target from this list, in the Identity Provider Label field on the Global Configuration tab and with the IDP Label subtitle on the Role Provisioning Rules tab.
    directoryServerUrl The server URL of AD or LDAP.
    directoryUser The complete user name with DN to access the server.
    directoryPassword The password to access the server.

    The system will encrypt the password you enter here when you restart the EUP agent. It will not display the encrypted values should you open the file in a text editor after restarting, but instead obfuscates or masks these values as a row of asterisks, following the usual convention.
    objectClass The Object class that the user creation must belong to in AD or LDAP.
    userAccountControl The system provisions the user using this value in AD. For example, 512.

    For deprovisioning, the system sets the user with this value plus two. For example, 514 (if the value is set to 512). For reprovisioning, it sets the user back to the original value again, 512 in this example.
  5. Add an item to the IDPLabel array in the EUP/eup-agent/eup-agent-config.json file for every AgentAD or AgentLDAP identity provider target in your Ethos environment.
    Use this template to add these items to the array, replacing the sample values here with the actual values in your environment. To add the first item, copy and paste this template to the IDPLabel array and replace the values.         {

        }

  6. Add the OAuth token details to the OAuth configuration file, EUP/eup-agent/oauth-config.json. 
    {
"clientId":""**********"",
"clientSecret":""**********""
}

    You generate the clientId and clientSecret values in the EUP Administrative UI, on the General Settings tab. See Generate OAuth credentials for more information.

    The system encrypts the values you enter in this file when you restart the EUP agent. It does not display the encrypted values should you open the file after restarting, but instead obfuscates or masks these values, again as a row of asterisks.

  7. Set the logging level value to DEBUG, INFO, ERROR, or WARNINGS in the logging-config.js file so that you can view the corresponding log entries.
  8. Run the npm install node-windows command in the EUP/eup-agent directory to download all the application dependencies.
    This generates the node_modules folder.
  9. Use these commands to create the eupagent.service file for Windows.
    1. Run the command node window-agent-service.js install.
      This creates the EUP agent service in the Windows Services application.
    2. Start the EUP agent service using the command node window-agent-service.js start.
      You can stop the EUP agent service at any time using the command node window-agent-service.js stop.
      Tip: You can also start and stop the services from the Services console in Windows, which you can open using the services.msc command. In this console, search for the EUP agent service and start or stop this service using the standard options the console provides for all Windows services.

      You must stop and restart the service if you update the EUP agent configuration in the eup-agent-config.json and oauth-config.json files. This will encrypt and mask specific values in these files, as noted above.

    • It stores the OAuth client ID and client secret in the Windows credential store and cleans up the oauth-config.json file with the credential ID and client secret. If it is already stored, read it from the Windows credential store.
    • You can find the logs in the EUP/eup-agent/logs/eup-agent.logs file.
  10. Optional: To uninstall EUP agent as a service for Windows, on a command prompt as an administrator, run the command node window-agent-service.js uninstall.
    EUP agent service is removed from the Windows Services application.
Upgrade

Ellucian provides an upgrade script with every major release of EUP that enables administrators to quickly upgrade their EUP agent installation from the preceding versions of the agent to the latest version.

Before you begin

  • Backup your existing installation, but skip the node_modules folder.
  • Ensure that you have downloaded and extracted the compressed file (.zip) for the latest version of the EUP agent. You can use the upgrade script for the latest version of the agent to upgrade from a preceding or prior version of the EUP agent to the latest version, but only if you have already installed version 1.17.0 of the agent, or later. If you have installed an earlier version of the EUP agent, you must install version 1.17.0 first. See Install. After this installation is complete, you can use the upgrade script for the latest version to upgrade the EUP agent to this version.
  • Ellucian recommend that if you have installed a previous version of the EUP agent, you use the upgrade script for the latest version of the agent to upgrade to this version, instead of a fresh installation of the latest version.
  • If running, stop the EUP agent service using the command node window-agent-service.js stop. You can also stop the service from the Services console in Windows, by searching for the EUP agent service in this console.
  • Copy the location path of your current EUP Agent.

Procedure

  1. Download the latest EUP agent .zip file from Ellucian Downloads and extract its contents into a folder at your preferred location on the server.
  2. Open the Windows Command Prompt and navigate to the folder where you extracted the latest EUP agent files.
  3. Run the upgrade script upgrade.bat from the installation directory by entering the name of this script on the command line.
    You can also run the upgrade script by double-clicking the upgrade.bat batch file in Windows Explorer.

    The script displays an informational message as a reminder to check that your current installation conforms to the required prerequisites, as described above. However, it does not verify that your installation complies with these prerequisites. The script then prompts you to enter the location where you extracted the latest version of the agent.

  4. Enter the location, the path to the current installation of the EUP agent.
    The script starts the upgrade process, which checks what version of the agent you have currently installed.
    • If you have installed a version of the agent before version 1.17.0, the script displays a message to the effect that you must install version 1.17.0 first, before you can run the upgrade script, and stops the upgrade process.
    • If you have installed version 1.17.0 or later of the agent, the script upgrades this version to the latest version of the agent.

    When the upgrade process is complete, the script exits with the message Successfully Upgraded eup-agent to the latest version. Please start the eup-agent service.

    If the upgrade added one or more new attributes in the configuration file for the EUP agent, eup-agent-config.json, the script also displays an informational message to this effect, which lists the new attributes and their default values. This message then advises you to update these default values to the correct values for your installation.

  5. If the script displayed the message about new attributes and the default values, update the default values as required in the eup-agent-config.json configuration file.
    See Step 4 in the Install topic for the up-to-date list of the attributes in this file with a description of each value.

Results

When the script has completed the upgrade, and after you have updated the default values of any new attributes, you can start the agent using the command node window-agent-service.js start.

Upgrade

Ellucian provides an upgrade script with every major release of EUP that enables administrators to quickly upgrade their EUP agent installation from the preceding versions of the agent to the latest version.

Before you begin

  • Backup your existing installation, but skip the node_modules folder.
  • Ensure that you have downloaded and extracted the compressed file (.zip) for the latest version of the EUP agent. You can use the upgrade script for the latest version of the agent to upgrade from a preceding or prior version of the EUP agent to the latest version, but only if you have already installed version 1.17.0 of the agent, or later. If you have installed an earlier version of the EUP agent, you must install version 1.17.0 first. See Install. After this installation is complete, you can use the upgrade script for the latest version to upgrade the EUP agent to this version.
  • Ellucian recommend that if you have installed a previous version of the EUP agent, you use the upgrade script for the latest version of the agent to upgrade to this version, instead of a fresh installation of the latest version.
  • Ensure you have installed jq, a JSON processor open-source tool, on the Linux server where you have installed the agent. If not, install this tool on the server.
  • If running, stop the EUP agent service using the command sudo systemctl stop eupagent.service.

Procedure

  1. From the Linux command line, run the upgrade script upgrade.sh.

    The script displays an informational message as a reminder to check that your current installation conforms to the required prerequisites, as described above. However, it does not verify that your installation complies with these prerequisites. The script then prompts you to enter the location where you extracted the latest version of the agent.

  2. Enter the location, the path to the current installation of the EUP agent.
    The script starts the upgrade process, which checks what version of the agent you have currently installed.
    • If you have installed a version of the agent before version 1.17.0, the script displays a message to the effect that you must install version 1.17.0 first, before you can run the upgrade script, and stops the upgrade process.
    • If you have installed version 1.17.0 or later of the agent, the script upgrades this version to the latest version of the agent.

    When the upgrade process is complete, the script exits with the message Successfully Upgraded eup-agent to the latest version. Please start the eup-agent service.

    If the upgrade added one or more new attributes in the configuration file for the EUP agent, eup-agent-config.json, the script also displays an informational message to this effect, which lists the new attributes and their default values. This message then advises you to update these default values to the correct values for your installation.

  3. If the script displayed the message about new attributes and the default values, update the default values as required in the eup-agent-config.json configuration file.
    See Step 4 in the Install topic for the up-to-date list of the attributes in this file with a description of each value.

Results

When the script has completed the upgrade, and after you have updated the default values of any new attributes, you can start the agent using the command sudo systemctl start eupagent.service.

Configure and enable the Experience card

You must configure and enable the Provisioning Metrics card provided by Ellucian so that administrators can access and use this card. Users with the required roles and permissions can configure and enable all Experience cards, including the Provisioning Metrics card, using the card setup wizard.

Before you begin

The user performing this procedure must have been granted the Card Management administrative permission in Ellucian Experience Setup, as described in Grant Experience dashboard permissions.

About this task

An administrator in Ellucian Experience is a user that has the required administrative role or roles in the system. Institutions will define these roles in Ellucian Experience and assign the roles to users as necessary. Ellucian Experience also defines a set of administrative permissions, and institutions will typically grant these permissions to the administrative role or roles (they can also grant permissions to individual administrators).

Experience administrators with the Card Management administrative permission can configure all Experience cards, including the Provisioning Metrics card, using the card setup wizard that they can access from their Experience home page.

For more information about how to access and use the wizard, see Set up an Experience card. This task complements this resource, in that it focuses on the specific configuration options that you can set for the Provisioning Metrics card in the wizard.

Procedure

  1. Open the card setup wizard for the Provisioning Metrics card that you want to configure and enable.
    For more information about instructions on how to open this wizard for a specific Experience card, see Set up an Experience card.

    You can find the Provisioning Metrics card, and open the wizard for it, by searching for the card type or card title.

    Note: Each Experience card has a card title and a card type. Ellucian set a default card title and set the card type. Institutions can update the title as required but cannot update the type. So, the card type acts as identifier for the card and Ellucian documentation resources always refer to Provisioning Metrics card using the card type.
  2. Enter basic settings for the card in the wizard.
    For more information about a detailed description of the settings, see Set up an Experience card.
  3. When prompted, set the roles for the Provisioning Metrics card.

    The users or roles that you select here determine who has access to the card in Experience and your institution defines the available roles and users in Experience Setup.

    Ellucian recommends that you should only allow administrators, or similar roles, access to the Provisioning Metrics card and as such you should only select these roles or users here. Do not select any student roles or users, or the option to select all users.

  4. Enable the card in the wizard.
    You can enable, or disable, any Experience card using the card setup wizard, see Set up an Experience card. You can also enable or disable Experience card from the page where you open the wizard, see Edit a card. This link also provides useful advice on the implications of disabling and re-enabling existing cards.

Results

When you have configured and enabled Provisioning Metrics card, administrators can begin to use this card on their Ellucian Experience home pages.

Grant access to Banner security objects (Banner)

EUP requires the user-identity-profile data model to be populated at the time that the tenant's Ethos Integration hub is published; otherwise, provisioning will not succeed.

Cause

To observe any errors in Ethos User Provisioning Datadog logs, filter for (Provisioning service:(provisioning-event-consumer or provisioning-admin-ui). The logs show that notification of change has been received, but processing has failed. For the beta client's tenant, disable Ethos User Provisioning to manually inspect the incoming change notifications.

The next step includes calling the tenant's Integration API proxy directly with the credentials configured in Ethos Integration. A GET call is made to /IntegrationApi/api/user-identity-profiles, which returns an access denied error message.

EUP cannot process Banner IDs that contain an at symbol (Banner)

EUP cannot provision a user from Banner if the Banner ID for that user contains an at symbol (@) or ampersand.

Remedy

EUP administrator.

To resolve this issue, you can configure a Banner extension mapping by setting up a rule and attaching it to a process using the GORRSQL administrative page. See Define an extension mapping in Banner for the detailed procedure. When following this procedure, note that:
  • You can use the name HEDM_EXTENSIONS for the process rule code that you create on the GTVSQPR page.
  • You should use a specific name for the process rule code that you create on the GTVSQRU page, for example REMOVE_AT_SYMBOL.
  • You will have to define the SQL query that removes the at symbol from the Banner ID.
