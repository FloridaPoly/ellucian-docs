Ethos Integration APIs

Use the Ethos Integration APIs

Configure your applications to authenticate with Ellucian Ethos Integration, and to provide and receive data through Ellucian Ethos Integration by making a proxy API call, publishing a change notification, or retrieving a change notification.

Whitelist the Ethos Integration IP addresses

The Proxy API service, which runs in AWS, needs to call APIs of authoritative systems at your institution. Because of this, your firewall rules must allow for inbound requests from the Ethos Integration IP addresses.

Whitelist the appropriate IP addresses for your region/domain. See IPs to Whitelist.

Authenticate applications with Ellucian Ethos Integration

Applications using Ellucian Ethos Integration must invoke the Ellucian Ethos Integration authentication endpoint with their API Key to receive an access token in JWT format.

The access token is used by the application to access all other services (for example, proxy, publish, and subscribe). When an access token expires, the application should request a new one with its API key.

Invoke the Authentication service to get an access token

Applications that interact with Ellucian Ethos Integration services – Publisher, Message Queue, Proxy, Error Reporting – require a valid access token.

About this task

The Ellucian Ethos Integration Authentication service returns an access token after successful validation of an API key sent to it in an initial request. The API key for an application is generated by Ellucian Ethos Integration when the application record is created in the Ellucian Ethos Integration administration interface.

Procedure

  1. In the Ellucian Ethos Integration administration interface, create an application record for the application that needs to connect to Ellucian Ethos Integration.
  2. Copy the generated API key.
  3. Use the generated API key to get an access token so that the application can interact with Ellucian Ethos Integration services. You can use the examples provided to assist you with this step.
  4. Use the access token in subsequent requests to interact with Ellucian Ethos Integration services.
cURL example - Get an access token

This is an example of invoking the token service with your application to get an access token.

curl -X POST 
-H "Authorization: Bearer {API KEY}" 
-H "Cache-Control: no-cache" 'integrate.elluciancloud.com/auth'
Note: If you are in a region other than the U.S., substitute your region-specific domain in place of integrate.elluciancloud.com in the examples. See Ethos Integration domains.
API client example - Get an access token

This is an example of using an API client to get access to a JSON Web Token (JWT), whose purpose is to authenticate subsequent requests to Ellucian Ethos Integration. You can create a change notification message that is stored to the Message Queue Service.

Procedure

  1. Set the Change Method request: Post.
  2. Enter the JWT token service endpoint URL: https://integrate.elluciancloud.com/auth
    Note: If you are in a region other than the U.S., substitute your region-specific domain in place of integrate.elluciancloud.com in the examples. See Ethos Integration domains.
  3. In the Header section, in the Authorization field, enter Bearer (token from the Config UI - API Key field).
  4. Click Send.

Results

API client Response JWT Token: Copy the generated JWT token to a text editor. The token will be long and start with "ey...." If you are using Notepad, make sure the word wrap feature is disabled.

Make requests to the REST APIs

The Ellucian Ethos Integration Proxy API service facilitates request/reply messaging between non-authoritative client applications and authoritative systems. The Proxy API service decouples applications, allowing non-authoritative systems to make requests of resources without having to know which application is authoritative for the resource.

About this task

Use of the Proxy API service is dependent on proper configuration of Ellucian Ethos Integration through your tenant’s administration interface.

Procedure

  1. Create an application, add the Base URI for the application, and define the resources that the application owns.
    Ellucian Ethos Integration uses this information to route requests to the application for resources for which it is authoritative.
  2. Create an application, and add credentials for the application that owns the resources.
    Ellucian Ethos Integration uses these credentials when accessing the endpoints exposed by the authoritative application.
  3. Make a GET, PUT, POST, or DELETE request of a resource exposed by the authoritative application using the Proxy API.

Results

Ellucian Ethos Integration routes the request to the application that is authoritative for the resource using the stored credentials. The authoritative system identifies the credentials, services the request, and replies to Ellucian Ethos Integration, which forwards the reply to the requesting application.

Query by POST (QAPI)

If it is supported by the application that owns a resource, you can use query by POST (QAPI) to make complex queries.

Example use cases for QAPI include:
  • Query filter information needs to be secure and encrypted.
  • Filter information is too large for the HTTP GET query string.

The following are required to support a QAPI call:

  • The system administrator must enter the Base QAPI URI in the Owned Resources section of the Ethos Integration application that owns the resource. Configure the Base QAPI URI as part of the initial setup of owned resources.
  • Each query by POST statement must include qapi. For example:
    POST https://integrate.elluciancloud.com/qapi/persons HTTP/1.1

Make GraphQL requests to Data Access

An application can make GraphQL requests using the Ethos Integration Proxy API.

GraphQL requests use a POST request to the graphql endpoint of the Ethos Integration Proxy API, which routes the request to Data Access and returns the response from Data Access to the requesting application. For guidance in creating GraphQL requests:
  • To create GraphQL requests using a GraphQL IDE application, see the GraphQL Playground example.
  • To create GraphQL requests within the code for your requesting application, see Proxy API.
  • For examples, see Sample GraphQL queries.
GraphQL Playground example - Create a GraphQL request

You can design and test your GraphQL requests using a GraphQL IDE application such as GraphQL Playground, which is used in this example.

Before you begin

Before testing your queries using GraphQL Playground, you will need to set up the required resources that you will include in your query:
  • In Ethos Integration, create an Ethos application. Add to that application the GraphQL resources that you will include in your query.
  • In Data Access, load the resources that you will include in your query.
    Note: You must load at least one resource to support the initial introspective query that returns the schema and API documentation information from Data Access.

Procedure

  1. In GraphQL Playground, create a workspace. For the URL Endpoint, specify https://integrate.elluciancloud.com/graphql.
    Note: If you are in a region other than the U.S., substitute your region-specific domain in place of integrate.elluciancloud.com in the examples. See Ethos Integration domains.
  2. Perform the following steps to perform an introspection query that retrieves the Ellucian Ethos Data Model schema and API documentation for the resources stored in Data Access.
    You will be able to use this information when you build your query.
    1. Obtain an access token. For example, use an API client to get the token using the procedure in API client example - Get an access token.
      When you get the token, use the Ethos API key from the Ethos application that you created to support this procedure.
    2. In the footer, click HTTP HEADERS and then enter the following: 
      {
"Authorization": "Bearer {access_token}",
"accept-encoding": "gzip"
}
      Replace {access_token} with the token that you obtained earlier.

      The gzip entry zips the schema information returned from Data Access, so that the entire schema is returned. Without zipping, the schema might exceed the size limit for the response.

    3. On the right side of GraphQL, click the SCHEMA tab to view the schema, or click the DOCS tab to view the API documentation.
  3. In the editor pane on the left, enter your GraphQL query.
    For examples, see Sample GraphQL queries.

    As you enter the query, the autocomplete feature in GraphQL Playground provides suggestions based on the API documentation for the selected resource.

  4. Click the Play button to execute the query.
  5. View the response in the right pane.
    Note that the response conforms to the data permissions granted to the Ethos application whose API key was used to generate the token. These permissions are based on the GraphQL resources that you added to that Ethos application and any individual attributes within those resources that you filtered. If you requested a resource or attribute that the application does not have permission to access, the response will indicate that.

Selecting fields

You can request any field from a given EEDM schema. The field names are the same as they are in EEDM, and appear in the same nested structure. When you encounter a property which is a link in EEDM, keep nesting and you can select fields from the linked entity.

{
  sections16 {
    edges {
      node {
        id
        titles {
          value
        }
      }
    }
  }
}

Filtering

You can specify one or more fields to filter by. When you specify the filter value, you specify a field to filter on, an operator to use, and a value. Available operators are listed in the table below.

Operator Field type Value type Description
EQ ID, String, Int, Float, Date (same) Matches exactly
EQI String (same) Matches exactly (case insensitive)
NEQ ID, String, Int, Float, Date (same) Does not match exactly
NEQI String (same) Does not match exactly (case insensitive)
IN ID, String, Int, Float, Date (same) Matches one of the specified values
NIN ID, String, Int, Float, Date (same) Matches none of the specified values
STARTS_WITH String String Starts with the specified value exactly (case insensitive)
CONTAINS String String Contains the specified value exactly (case insensitive)
ENDS_WITH String String Ends with the specified value exactly (case insensitive)
NULL String, Int, Float, Date, Object, List Boolean If true, matches when the specified field is absent from the document
AFTER Date Date Matches if the date is after the specified date
BEFORE Date Date Matches if the date is before the specified date
BETWEEN Date Date, Date Matches if the date is between the specified dates
LAST_DAYS Date Int Matches if the date is within the last X days

Basic filtering example:

{
  subjects6(filter: { metadata: { createdBy: { EQ: "bob" } }, { abbreviation: { EQ: "MATH" } } } ){
    edges {
      node {
        id
        title
      }
    }
  }
}

You can filter by properties of related entities:

{
  courses16(filter: { subject6: { title: { EQ: "Computer Science" } } } ){
    edges {
      node {
        id
        title
        subject6 {
          title
        }
      }
    }
  }
}

You can specify null testing. Note that the name of the resource in this case is camel case, without the dash: academicLevels rather than academic-levels.

{
  academicLevels6(filter: { description: {NULL: false} } ){
    totalCount
    edges {
      node {
        id
        code
        description
        title
      }
    }
  }
}

Multiple filters are AND'd together implicitly by default. However, you can OR them together instead:

{
  academicLevels6(
    filter: {
      OR: [
        { code: { EQ: "UG" } }
        { title: { EQ: "Undergraduate" } }
      ]
    }
  ) {
    edges {
      node {
        id
      }
    }
  }
}

Because GraphQL uses a different object type (GraphQLInputObjectType) for input arguments, a separate set of types must be generated for filtering. Each type is prefixed with an F and the leaf nodes are filter input objects, such as IDFilter or StringFilter, which provide the structure to specify filter operators and filter values as input arguments. You will see this separate set of types when browsing the Docs generated by the introspective call.

Sorting

You can specify one or more fields to sort by:

{
  academicLevels6(sort: { code: DESC }) {
    edges {
      node {
        id
        code
      }
    }
  }
}

If you specify more than one field to sort by, use an array so that precedence is set:

{
  academicLevels6(sort: [{ code: DESC }, { description: ASC }]) {
    edges {
      node {
        id
        code
      }
    }
  }
}}

Because GraphQL uses a different object type (GraphQLInputObjectType) for input arguments, a separate set of types must be generated for sorting, with an enumeration for ascending or descending. The schema is generated in the same way and has the same nested structure matching EEDM, but each type is prefixed with an S. You will see this separate set of types when browsing the Docs generated by the introspective call.

Total count

Total count information can be retrieved from the query. For the best query performance times, use this only for cases where totalCount is required for your scenario, as it is a slightly more expensive query to run.

{
  academicLevels6(sort: [{ code: DESC }, { description: ASC }]) {
    totalCount
    edges {
      node {
        id
        code
      }
    }
  }
}

Pagination

Pagination applies to the primary entity being queried. To limit the number of records returned, specify the limit argument. To begin paginating from a certain point in the result set, specify the offset argument. You must specify a sort argument to use either of these. You can obtain a total count of the records that match any specified filter by requesting the totalCount property which is a peer of edges.

{
  subjects6(offset: 10, limit: 10, sort: { abbreviation: ASC }) {
    edges {
      node {
        id
        abbreviation
      }
    }
    totalCount
  }
}

Multi-resource queries

These samples show options for detailed queries for multiple resources. These query persons, comments, and personHolds in a single query.

There are two variations to this query:
  • Direct GraphQL query
  • Query using GraphQL variables

The way the data models are designed, it is not possible to gather data for doing single resource queries, because persons cannot query into comments and personHolds, so if you want comments to query into persons, you will not obtain personHolds data.

However, you can do a multi-resource query on comments and personHolds and filter based off the person ID for each resource in the same query. Person is included as an example. You can remove persons12 from it and simply query the person12 data from either comments or personHolds, or both, if needed.

  ) {
    edges {
      node {
        id
        credentials{
          type
          value
        }
      }
    }

Retrieve messages

Applications that are configured as subscribers to resources must request the messages that Ellucian Ethos Integration stores for them.

Types of messages include:

Change notifications
These are resource based messages that give the current state of a resource at the time a change occurred. This is what you get when you subscribe to changes for a specific resource that an authoritative app owns.
A change notification does not contain information about what specifically changed in the source system (before and after values). It tells you what happened to the resource (operation) and what data the resource contains (content) at the time of the change.
Business events
These are event-based messages that show specifically what changed in a source system as a result of some event, such as somebody’s address changed. A business-event is not tied to a resource that is exposed through an API.
The content of a business-event does not have a full representation of any data model. It is more based around the event that occurred in the source system. The content contains details about what exactly was changed.

Both types of messages will live in the same queue. If an application is subscribed to both types, then the responses to retrieve messages will contain both types in the order that they were published. Each message will contain a messageType property to indicate if it is a change-notification or business-event.

The following HTTP methods are supported:
  • Use a HEAD request to obtain a count of available messages. The response to the HEAD request provides that count in the x-remaining header value.
  • Use a GET request to retrieve messages. The response to the GET request provides:
    • The messages, in the body of the response.
    • A count of available messages remaining after this response, in the x-remaining header value.

The GET request can include two optional parameters, described in the table below. For more information about these parameters, see Message Queue API.

Parameter Description
limit This parameter defines the maximum number of messages to retrieve. If the limit parameter is specified (maximum of 1000), the Message Queue API will send up to that number of messages, if available. If the limit parameter is not specified, the Message Queue API will send up to the default limit of 20 messages, if available.

The total size of the response is limited to 10 MB. If the size limit is reached, the number of messages will be less than the specified number limit.
lastProcessedID If the lastProcessedID parameter is not included in a GET request, the response will begin with the next unretrieved message. If the lastProcessedID parameter is included, the response will begin with the next message with an id greater than the specified lastProcessedID.

You can use the lastProcessedID parameter to retrieve messages that have already been retrieved. For example, you might do this if some messages were successfully retrieved from Ethos Integration but were not processed properly in the subscribing application.

Manage Ethos Integration API keys

You can add or remove API keys for an application.

Applications integrating with Ethos Integration are identified by their unique API keys, which serve as credentials. Ethos Integration supports provisioning two types of API keys to an application:

  • Unrestricted API Key - Accepts requests from any integrated applications with the appropriate credentials set up in Ethos Integration.
  • Restricted API Key - Specify an IP address or range of IP addresses. Applications making requests using a restricted API key must make requests from the IP addresses within the specified range. If the request originates from an IP address outside the specified range, the request is denied and an error response is returned.

Best practices for securely using API keys

Applications integrating with Ethos Integration are identified by their unique API keys, which serve as credentials. It is important to keep your API keys secure.

To ensure your API keys are secure, follow the best practices below:
  • Do not embed API keys directly in code. API keys that are embedded in code can be exposed if you share the code. Instead of embedding your API keys in your applications, store them in environment variables or in protected files outside of your application source tree.
  • Do not store API keys in files inside your application source tree. If you store API keys in files, keep the files outside your application source tree to help ensure your keys do not end up in your source code control system. This is particularly important if you use a public source code management system, such as GitHub.
  • Restrict your API keys to be used by only the IP addresses that need them. By restricting the IP addresses that can use each key, you can better ensure security. Refer to Modify API key restrictions.
  • Restrict your API keys to be usable only for certain APIs. Integrated applications only to the APIs they need for integration functionality and no more. Or, if you are a Banner customer, refer to Set up proxy API requests (multiple owners).
  • Delete unneeded API keys. To minimize your exposure, delete any API keys that you no longer need.
  • Change your API keys periodically. Refer to Change the API key.

Proxy API

This service synchronously proxies RESTful API requests to the authoritative source registered for a resource and all GraphQL calls to Ellucian Ethos Data Access.

Before communicating with the Proxy Service, a client application must get a JWT token from the Ethos Integration authentication service. The application sends this token with each request to the Proxy. The Proxy extracts the contents of that token to get information about the application sending the request.

The Proxy Service exposes a REST API for CRUD on Ellucian Ethos Data Model resources. It also exposes an end point for GraphQL requests.

Client applications can make requests against the Proxy API.

For all REST API calls:

  1. The Proxy API will identify the resource the request is being made on.
  2. The Proxy API will identify the environment id of the client application from the JSON Web token (jwt).
  3. The Proxy API will look up in the Config API (or its cache) which application is authoritative for that resource. If there is none defined, an appropriate error message is returned to the client application.
  4. The Proxy API will look up the credentials for the client application used for this authoritative source and, along with the request, pass the credentials for validation by the authoritative source API.
  5. The Proxy API will route the response from the authoritative source back to the client application.
For GraphQL calls:
  1. The Proxy API will route the request from the client application to Data Access.
  2. The Proxy API will route the response from Data Access back to the client application.
REST API Specification Value
Method: GET, POST, PUT, DELETE, PATCH
Route: https://integrate.elluciancloud.com/api/{resource}
Headers: Authorization - "Bearer <access token>"

Other headers may be included as required by the destination API. The Proxy will forward.

Response

  • Headers: Content-Type=application/json
  • Payload: A JSON response from the authoritative system.
GraphQL Specification Value
Method: POST
Route: https://integrate.elluciancloud.com/graphql
Headers: Authorization - "Bearer <access token>"

The Proxy Service caches all application configurations. The cache expiration is set to 5 minutes. If you want to bypass caching and pick up the changes immediately, you can send this header in the request: hedtech-ethos-integration-cache-control

The value of the header can be anything, but it cannot be empty, null, or undefined.

Response

  • Headers: Content-Type=application/gzip
  • Payload: A JSON response from Data Access.

Ethos API Integration standards

Follow these standards as you develop your custom applications for Ethos Integration.

Ethos Integration governing principles

Ellucian Ethos Integration operates under a defined set of governing principles.

Ellucian Ethos Integration governing principles establish the responsibilities of applications that connect to Ellucian Ethos Integration, and the format and manner in which data is shared.

Adhere to REST principles and semantics

Ellucian Ethos Integration is based on Representation State Transfer (REST), an architectural style for networked applications.

REST relies on a stateless, cacheable, client-server communications protocol. In virtually all cases, this protocol is HTTP.

RESTful applications use HTTP requests to create data, read data, update data, and delete data from exposed services using standard HTTP operations; POST, GET, PUT, and DELETE, respectively.

REST is a lightweight alternative to mechanisms like Remote Procedure Calls (RPC) and Web Services such as SOAP and WSDL.

Quantify data as entities or resources

Ellucian Ethos Integration requires that data exchanged between integrated systems be quantified as a resource or entity. This principle follows the REST architecture.

While Ellucian Ethos Integration can support any JSON-based data definition, Ellucian has standardized on the Ellucian Ethos Data Model for specifying the data that is exchanged between its systems.

Use JSON schema to define data structures

Ethos Integration API resources are defined using JavaScript Object Notation (JSON) schema.

JSON schema is a JSON-based format for defining the structure of JSON data. JSON schema provides a contract for which JSON data is required and valid for a given entity. As a result, the data structure is standardized and can be enforced regardless of the underlying implementation in individual applications.

JSON Schema is the standard protocol that Ellucian Ethos Integration has adopted for all Ethos Integration API schema artifacts. For more information, see json-schema.org.

Employ the concept of an authoritative source

An authoritative source is the master source for a unit of quantifiable data in the enterprise.

This source is usually implemented as an application or database, and is synonymous with the database term system of record. After data is represented as a resource, the authoritative source for that data within the messaging enterprise must be identified. Products such as Banner, Colleague, and Elevate are expected to be authoritative within an enterprise for most, if not all, data in their respective data stores.

The concept of an authoritative source for a resource establishes a defined set of responsibilities within the messaging enterprise for authoritative sources and non-authoritative sources.

  • An application must notify the enterprise of any changes to data for which it is authoritative.
  • An application must expose services (APIs) for the resources for which it is authoritative.
  • An application that is not authoritative for a resource must request changes to the enterprise data. Requests may be fulfilled or rejected by the authoritative application.

Ellucian Ethos Integration enforces adherence to these principles by integrated applications through its administration interface.



Use standard messaging integration patterns

Ellucian Ethos Integration enforces data synchronization through standard message exchange patterns.

The publish and subscribe message exchange pattern is used when authoritative systems make changes to data. The authoritative system publishes data change notifications to Ellucian Ethos Integration using the Ellucian Ethos Integration's Publisher API. Authoritative systems have no knowledge of the non-authoritative systems that subscribe to these messages.

The request and reply message exchange pattern is used when a system needs to change or interact with data for which it is not authoritative from an enterprise perspective. Request messages are sent by non-authoritative applications to the Ellucian Ethos Integration's Proxy API for fulfillment by the authoritative application for the resource. Reply messages are produced by an authoritative source in response to a request message, and are returned to the non-authoritative application that sent the request by way of the Ellucian Ethos Integration's Proxy API.

Scope

This document describes the API interaction and contract between a client (calling system) and the server (source system). It does not discuss the payload or any specific data models themselves, only the communication channel. It will discuss areas of basic operations, behaviors, and special topics related to the APIs.

HTTP-based APIs are the primary focus of these standards. This includes any API that may be REST or RPC architectural styles, as discussed below. This document will not distinguish between the two styles but call out the commonalities of the two. The services delivered through Ethos depend on HTTP based operations. The individual products (authoritative sources) and APIs could be implemented in either or both architectural styles.

JSON is the primary data format referred to in these standards. HTTP-based APIs do not mandate that the JSON format be used, but it is the most popular format of today and the format will reference examples and policies around these standards.

Architectural style

Ellucian Ethos Integration enabled APIs are based on HTTP. This is currently the primary protocol by which Ethos Integration bundles its set of services on.

Two of the most popular HTTP API styles today are REST and Remote Procedure Call (RPC). Both styles are supported in these standards.

Representation State Transfer (REST) is an architectural style for networked applications. REST relies on a stateless, cacheable, client-server communications protocol. In virtually all cases, this protocol is HTTP.

RESTful applications use HTTP requests to create data, read data, update data, and delete data from exposed services using standard HTTP operations; POST, GET, PUT, and DELETE, respectively.

For a tutorial on REST, please refer to the following REST API Tutorial.

HTTP-based Remote Procedure Call (RPC) is another pattern for using HTTP to execute services between client and server.

The major differences between these two different patterns are around design and how the API is used or called. Please refer to the systems API documentation for details on how the APIs are to be used.

In general, the addressability of the APIs will be different in addition to the internal behaviors. For example, a REST URL for retrieving a persons resource would look like: GET /persons/5674f28b-b216-4055-b236-81a922d93b4c. In the REST API the caller would simply expect the persons resource to be returned in the response payload.

For a HTTP/RPC formatted URL it would look like: GET /readPersons?personId=1234.

In the context of these standards, the request and response payload are referred to as the "resource", and most commonly is in JSON format.

For more detailed information on how HTTP is implemented, please refer to RFC7231.

Role of authoritative source

Authoritative source systems are the backbone of information consumed in the Ethos ecosystem.

Description

Authoritative systems are the gold source custodian for certain pieces of the higher education domain.

These systems expose data in the form of resources and reserve the right to allow (or limit) access to viewing and performing any operation on the resources they expose, such as read and various write operations.

They perform a key integration function by enabling Subscriber systems to perform additional business processes on otherwise silo'd data. They do this by exposing HTTP-based APIs so that Subscriber systems can retrieve and perform operations on resources that are described by data model schemas.

Expectations

Authoritative systems are the sole custodian of all data associated with the data models they have the authority over.

Authoritative systems MUST expose data through HTTP-based APIs, adhering to standards herewith, enabling access to read and operations on data the systems expose. They also must support the About and Resources endpoints described in the API endpoint document. Both of these required APIs provide the Ethos environment details information about what the Authoritative system supports.

Instances of Ellucian Ethos Data Model resources MUST be identified by a value that adheres to the Ellucian GUID standard, which supports UUID V4 random GUID generation and MUST be a globally unique value regardless of the resource or owner of the resource.

Change Notification messages MUST be published through the Ethos Integration system to ensure subscribers of data in Authoritative systems are kept current.

All data models MUST be supported as defined by their published schema.

Architecture and design

The technology architecture and design of the Authoritative Source system is driven by the owners of that system. There are no standards for the technology stack or the approach taken. The two main new requirements for the system are to expose HTTP-based APIs and being able to call the Ethos Integration APIs to publish data change information.

If making HTTP/JSON-based calls is new to the systems technology stack, the Authoritative Source must now be able to:
  • Expose HTTP-based endpoints for APIs to Ethos Integration, through any private firewalls
  • Make HTTPS standard calls across the Internet
  • Read and write JSON, mapping to the applications domain model and technology
  • If exposing data using an Ellucian Ethos Data Model, identify them with the Ethos-defined GUID format. If a GUID does not exist, it MUST be added to the data store.
  • Capture and store any configuration settings required to support its resources
  • Detect and publish changes in the data comprising Ethos resources
  • Support the Ethos Extensibility and Data Privacy requirements

Some general guidelines on the two broad requirements include:

Expose resources through HTTP APIs

The Authoritative Source MUST expose access to resources using HTTP/JSON APIs, adhering to the Ethos API standards published here.

  • Use known and well proven libraries and components
  • Use a well-established HTTP library that enables REST and standard HTTP server features, to enable API calls to:
    • Expose HTTPS addressed URLs (SSL)
    • Be able to read a request body and write to a response body
    • Read and set custom and standard HTTP response
    • Support HTTP query string parameters for any defined filters
    • Support Ethos standard operations described in the Operations standards, such as paging.
    • Expose Ethos standard API endpoints as defined in these standards, specifically the About and the Resources API.
  • Implement the data model as defined in the schema
    • On Read operations, the data will be read using the Authoritative Source system's technology stack and the data MUST be transformed into a resource representation that adheres to the data model schema.
    • On Write operations, the system MUST read JSON from incoming requests then transforming the data into the systems technology stack and then passed to the native business logic for processing

Directive Description
Required Implement the About API endpoint to communicate version information.
Required Implement the Resources API endpoint to communicate what resources and versions the system is authoritative for.

Publish change notifications

The Authoritative Source is also responsible for publishing change data to Subscribers, adhering to the Change Notification specification and publishing APIs.

Use a well-established HTTP library enabling your application to make standard HTTP calls, to publish Change Notifications to Ethos Integration that specifically supports:
  • HTTPS addressed URLs (SSL)
  • Be able to write to a request body and read from a response body
  • Set custom and standard HTTP request headers which is required to call an API
  • Read custom and standard HTTP response headers
  • If Internet access is provided through an Internet Proxy Service, be sure that the HTTP library supports the required settings

Using the best tools on the technology stack, be able to detect change on source data and published required Change Notifications, as close to the transaction completion as possible.

A typical flow of logic:

  • Native change data capture features are enabled to detect when source data is changed from any potential input source
  • Logic is applied to determine if the data change is contained in the data model the source is used for

    If the data change is not an Ethos concern it can be ignored

  • If the change data impacts the Ethos resource, then the process flow MUST now retrieve a new Ethos "current" resource representation
  • Using the data from the change data capture and the current Ethos resource representation, build a Ethos Change Notification
  • Publish the Change Notification to Ethos Integration adhering to the published API documentation

When publishing Change Notifications the LATEST version or representation of the resource SHOULD be published. This means, if version 1, version 2 and version 3 of a resource (meaning 3 major changes) are supported, then version 3 is what is expected to be published.

The Authoritative Source MUST also remain backwards compatible such that version changes do not disrupt the flow of Change Notification messages used by systems that are not supporting this latest version. This is an extremely rare case, but for example, if version 1.0 of a resource contains a property that is removed in version 2.0. The Authoritative Source SHOULD still publish a Change Notification message if the property triggered a change in the source system. Even though the Subscriber would receive a version 2.0 representation in the Change Notification (and thus not see the property), they are instructed to do a new GET of the resource for the version they support.

The resource in the Change Notification MUST also adhere to any Data Privacy and Extensibility rules. Because the Change Notification is published to many subscribers from a Data Privacy perspective, the resource MUST apply all the Data Privacy rules and present the most restrictive view of the resource.

Upgrades, configurations, changes and health

Authoritative Source systems maintain a product roadmap which includes regular updates with new features and capabilities. Often times, these new features include new support for new APIs. Consideration SHOULD be given by the Authoritative Source around three areas when offering new Data Model support on product release upgrades.

The first area of focus is on resource identifiers or GUIDs. Where the Authoritative Source does not have existing GUIDs for data now comprising a new Ellucian Ethos Data Model, it MUST create a location to store AND to generate new GUIDs on instance data. This SHOULD be done before enabling the API.

The process for generating GUIDs SHOULD take place out of band from the actual upgrade process due to performance requirements and limiting outage time. Some instance data may be needing to generate GUIDs on potentially large volumes (e.g. millions) of resources. Therefore, care SHOULD be given that the GUID generation process is a process that can be effectively managed outside the installation process. Lastly, some environments may clone production copies of data into test or development environments. Consideration SHOULD be given to these processes because a GUID by definition MUST be globally unique.

The second area of focus is on configuration. Some EEDM-based resources will require administrative users to configure settings on the Source systems before the API will be available. This could include such things as default values, mappings, or process settings.

Data models that are not Ellucian Ethos Data Models may not have GUIDs and could be exposing resources with alternative system identifiers or filters.

Finally, due to the first two areas mentioned, Change Notification publishing SHOULD BE turned off on the resource by default. Only when the API is healthy SHOULD the Change Notification publishing layer be activated. Health is currently defined by ensuring GUIDs have been generated and any required configuration settings set.

Subscriber considerations

It is REQUIRED that all Authoritative Source systems follow the guidelines above and implement APIs following the published Ethos API Standards. Subscribing systems expect consistent behavior across all Authoritative Systems.

Most subscribing systems will need to provision an initial data set (or seed data) upon the initial on-boarding of the integration. This will typically be facilitated by the bulk paging APIs provided by the Authoritative Source. See the Operation Standards on "getting a list of resources". After the initial data set is loaded, Subscribers can then listen for Change Notifications and enable their own business process logic.

The Authoritative Source system needs to consider how large volumes of resources are consumed and if Subscriber systems are making local copies of resources. Today, there are some cases in large Authoritative Sources with large volume resources (such as a system managing the persons resource) where simple configuration changes can impact change on a large number of resources.

For example, by changing the email-type enum mapping on persons an administrator effectively is "updating" all of the persons in their system with a simple click of a button. Refer to the Authoritative Source documentation to find out if large process or changes such as this generate Change Notifications. If the Source does not it will need to notify Subscribers that bulk read may need to be performed again.

Data Model considerations

The Authoritative Source MUST implement the entire schema definition for the data model, as it is written. The Data Model contract MUST be adhered to.

Optional properties in the schema does NOT mean those properties are optional for the Authoritative Source to implement. They are only optional for the Subscriber when sending new or update requests.

If a property is not required in the schema, but it is required in the Authoritative Source, then a default value MUST be configurable to use.

Enums defined in the schema typically will require a configuration mapping, to map from the data model value to the Authoritative Source value. Review the API documentation to ensure all configuration requirements can be met.

All published filters must be supported. Filters are defined in the schema.

All supported resource versions in the API MUST be communicated through the standard resources endpoint. This MUST also include alternative resource representations. See the Endpoints standards for details.

Role of the data model

Data models are used as API contracts that describe an instance of a resource. An instance of a resource is an instance of data. For example, a persons resource is the occurrence of a single person in the system.

Therefore, Data Models describe the structure of resources in Ethos. Authoritative Source APIs expose the behavior around the resource. The APIs enable reading and writing operations on resource instances that adhere to their Data Model definition. Subscribing Systems can call Authoritative Source APIs to consume and request actions to be taken with these resources.

The Ellucian Ethos Data Model (EEDM) is a specific category of data models supported by Ellucian, our partners, and our institutions. The EEDM is a representation of meaningful real-world concepts in the higher education software domain. It provides a common vocabulary that supports the entire range of integration needs between applications that comprise a higher education institution.

The EEDM is a global, semantic network model of entities and their relationships. For semantic networks, the goal is to gather information together into easily-recognizable entities and concepts, and then connect them together. Model designers identify all of the entities in the domain along with their properties and describe them in separate models. In EEDM, these models are implemented in JavaScript Object Notation (JSON) schema files.

Ellucian is applying the discipline of using data models to refer to the contract of an API, no matter the architectural style of the API (REST or RPC).

Models instantiated as resources

As mentioned, the data model establishes a contract between systems sharing information. A data model describes the structure of the data in an Authoritative Source. This includes the layout and the data types used.

When a Subscriber requests to read data from an Authoritative Source, a GET request is created and given to Ethos Integration which routes the request to the Authoritative Source. The Authoritative Source reads the data using its business logic and transforms the product-specific data into an Ethos Resource which adheres to the Data Model schema.

Resources are what systems use and create. Data Models (or schemas) describe the layout and data types of the resource.

Process data model

A process-oriented Ellucian Ethos Data Model provides a defined structure (schema) to be used for PUT/POST/DELETE operations that enable integrating systems to accomplish a common activity more easily with an authoritative system. The actions that a process API takes can involve one or more Ethos APIs.

The following are attributes of a process data model.
  • It has a fixed schema that includes required and optional properties.
  • There is no GUID property in the schema because it does not represent a distinct "thing" or resource. As a result, GET and change notifications are not supported.
  • The response to a process API request can be one or more existing resources. Change notifications for those existing resources provide additional details.
  • It supports synchronous processes. When an asynchronous process needs to be supported, which is what person-matching-requests is, then GUIDs must be generated to represent the request. GET is supported against that resource, and it therefore results in the ERP essentially building a new structure (table or file) to represent that resource, making it a new Ethos "thing".
  • Its name ends with the word "process" and is not pluralized because it does not represent a set of resources.
  • Its schema can contain properties that are not applicable to a particular authoritative system.

Alternative resource representations

Each resource is defined by its schema and the schema is used to communicate a contract between the Authoritative Source and the Subscriber. This one-to-one relationship between a resource and its schema is more accurately described as a saying a resource has one DEFAULT schema.

There are cases when a resource also supports an additional or alternative representation in addition to the default.

The business case(s) for an alternative resource representation include:
  • Providing a minimal or a larger representation of the resource, such as sections and sections-maximum.
  • Providing a more accurate and simplified contract for PUT/POSTs where the default schema may have numerous read-only properties.
  • Providing schemas that are used in QAPIs request bodies that may incorporate query properties that do not exist in default schema.

If an alternative representation is requested or used in request, that EEDM version and model name must be included in the appropriate request header. See the Operations Standards for more details. This includes both the accept and content-type headers.

An example of the larger representation need is the sections resource. Sections has a default resource representation but it also supports and additional alternative representation called sections-maximum. See the Authoritative Source documentation for more details.

The following directives apply to all alternative resource representations:

Directive Description
Required The alternative representation is NOT its own API endpoint or resource name. It uses the API and resource name of the default representation.
Required The resource ID (or GUID) property in the alternative representation is the SAME identifier used in the default.
Required The properties (or data) in the alternative representation MUST be existing in a DEFAULT schema. This could be the schema of another resource.
Required Change Notifications are NOT published using the alternative representation ONLY the default representation.

Semantic versioning

All schemas are semantically versioned and are identified by the version property contained in the schema. As Ellucian continues to implement semantic versioning, this version property is going to be transitioned to all schemas. Please refer to the EEDM documentation for clarity on the exact version of the schema you are referencing.

Semantic Versioning uses a familiar version numbering scheme that implies meaning:

Given a MAJOR.MINOR.PATCH format such as (2.1.0)

  • MAJOR version is incremented when new incompatible changes have been made
  • MINOR version is used when functionality is added in a backwards-compatible manner
  • PATCH version is used when backwards-compatible small and minor fixes are made that are not structurally significant

Role of the subscriber

Authoritative source considerations

API (Ethos Integration proxy calls)

Refer to the Ethos Integration APIs documentation for detailed information regarding the interaction with the Authoritative Source through Ethos Integration.

There are several key points that are valuable to clarify when designing the programmatic flow for a Subscriber.

First, it is vital to understand how the authentication process works between the Subscriber and Ethos Integration. Please review the Token API documentation for how to call Ethos Integration to get a authentication token to use to call an Ethos API.

As a Subscriber, the timeout period of the temporary token generated is very important. The Subscriber application needs to implement a pattern and flow to first get the token and then when the token times out, retrieve another token before calling the API again.

The timeouts of the token are added security layer but requires the Subscriber to build and plan for that feedback loop.

After the Subscriber has a valid token and calls a resource API following the API Standards, there are several other patterns to consider.

Subscribers must tell the Authoritative Source what kind, or what version, of representation they want returned. This is done by putting in Ethos-formatted version numbers into the Accept Header. Refer to the Operations standards for more details.

There could be conditions when the API call creates an error message. Do not assume every API call will be a success. Plan for exception and error handling when the Subscriber makes the call. Missing configuration items and unexpected user data are a couple of types of errors the Subscriber may encounter.

All APIs perform differently. The small volume resources, the APIs could return results in seconds. Other more complicated and larger ones could be close to the timeout period. Therefore, when Subscribers are making resource API calls plan for the performance variation.

In summary consider the following when interacting with Ethos Integration:
  • Authentication token timeout feedback loops
  • Versions
  • Errors
  • API performance

Change notifications

The flow of change processing logic should be fairly common across all subscribers. The following list breaks down key areas to consider when designing and implementing a processing layer in a Subscriber.

  • Read the next batch of Change Notifications
  • For each notification:
    • Determine if the resource or instance of the resource is important to the Subscriber, if it is not then it can be ignored.
    • Check the version property and validate the version is one that the Subscriber supports:
      • If not, the Subscriber can do a GET request back through Ethos Integration asking for a version it can read.
      • If it is a version supported then the Subscriber can transform the JSON resource into an object for its use.
    • If Data Privacy was enabled (see explanation below), a GET request MAY be done to attempt to get a full representation of the resource
    • If a more current representation is desired a GET request could be done to the API. The Change Notification contains the most recent view at the time the Change Notification was built.
    • Evaluate the operation reflected in the notification and preform the required business logic:
      • If "deleted" perform any cached or stored data clean up
      • If "replaced" and data is stored in the Subscriber it will need to be updated
      • If "created" and the Subscriber is interested, then a copy or partial copy of the data could be stored or trigger a business process
  • Get the next batch (loop)

All Change Notifications include a version property when a resource is in the actual Change Notification. This should be used, in the above process, by the Subscriber to determine if it is supported and can be read.

Data Privacy is a also a key area to remember when developing support for processing Change Notifications. Refer to the Change Notification Standards page for details, but the key thing to remember is the representation of the resource in the Change Notification MAY NOT always be a full representation. If the Authoritative Source has any Data Privacy rules (see below) defined, all of the rules are applied to the Change Notification building process to ensure that the least privileged view of the resource is published.

In the event privacy rules have been applied, the Content Type property in the Change Notification will be set to "partial". This presents a feedback loop for the Subscriber. This does not mean the Subscriber application does not have access to the full resource. Remember, if ANY privacy rules for ANY API Subscriber are defined, they all get applied. A common process flow is that "if the contentType value is equal to partial, the Subscriber can try to make a call back to the API with a GET request to see if a full representation can be retrieved". The response may be the full resource, OR it may be a partial representation that only you as the Subscriber can see.

Deleted Change Notifications MAY NOT have a resource representation in it. Most Authoritative Sources delegate the Change Notification process to occur outside of the business transaction, therefore the data is unavailable.

The Content Type, of the Change Notification message, may also be empty if the Subscriber is NOT allowed to view the instance data.

Because Change Notifications SHOULD contain the latest resource representation version, the Authoritative Source MUST also remain backwards compatible such that EEDM changes do not disrupt the flow of Change Notification messages used by systems that are not supporting this latest version. This is an extremely rare case, but for example, if version 1.0 of a resource contains a property that is removed in version 2.0. The Authoritative Source SHOULD still publish a Change Notification message if the property triggered a change in the source system. The Subscriber would receive a version 2.0 in the Change Notification (and thus not see the property), but following the pattern above the system can do a GET on version 1.0 to see the changed property.

Deprecations

Data models AND Authoritative Source APIs can in some cases be deprecated based on the Authoritative Source business planning. It is important to have awareness of this possibility and it is critical to stay informed by reading release notes and any latest news that may declare a deprecation has occurred. It is the Authoritative Source responsibility to declare deprecations and to give ample time for Subscribing systems to react before removing them.

Privacy

Authoritative Sources have the granular control over what data is returned from its systems. There are a variety of use cases, not only including protecting Personally Identifiable Information (PII), that the Authoritative Source may restrict the data the Subscriber has access to.

Ethos Authoritative Sources enable the administrator to remove resource properties depending on the API user making the request.

When properties are removed a special response header is included in the response. This is the trigger for the Subscriber to know that the resource in the response is not the full resource representation. Review the X-Content-Restricted header in the Operations standards as well the Content Type details in the Change Notifications specification.

Data Model considerations

Schema validation

Some Subscriber systems may choose to use the actual JSON schema to validate a given instance of a resource. There are numerous open-source tools that can be used to take a resource in JSON and validate it against the schema. This is NOT required to do for Subscribers. One of the key responsibilities of the Authoritative Source is to provide resource representations that adhere to their published Data Model schemas.

Code generation

The Data Model MUST be referenced when developing Subscriber interfaces to Ethos resources. The Data Model defines the structure of a resource in Ethos. Depending on the programming language of choice the Data Models could be used to help improve developer productivity by using various open source code generation tools. These tools could aide in the generation of language specific and typed objects. For example, taking a JSON schema and building a JAVA POJO object. These are not required and in some cases with large schemas may not be the most efficient way, but it could be considered.

Extensions

Data models can be extended by specific instances of an Authoritative Source. The most common use case is a business process in a particular source system uses data or properties that are localized and not available in a Data Model. Therefore, the Authoritative Source system may choose to implement Ethos Extensibility. This feature and the Data Access product enables custom properties to be added to specific instances of a Ellucian Ethos Data Model.

These extensions are defined in additional JSON schema documents that are maintained through an Extension lifecycle process by the Data Access product.

Semantic versioning

Because Data Models are semantically versioned, the Subscriber should understand what the MAJOR MINOR PATCH concepts mean because it is important to consider that when designing interfaces. From a Subscriber perspective, you need to balance the resistance to change the Subscriber system with the need to take advantage of new resources and the times when resource versions are deprecated.

All schemas are semantically versioned and are identified by the version property contained in the schema. As Ellucian continues to implement semantic versioning, this version property is going to be transitioned to all schemas. Please refer to the EEDM documentation for clarity on the exact version of the schema you are reading.

Beginning in Q2 2019, Ellucian APIs (along with the data models) will continue to implement semantic versioning behavior. See the API Behavior section for details. As a subscribing system, the Subscriber needs to be fully understand what versions of the resource are returned and how this changes with API and data model upgrades. Depending on how the Subscriber consumes and then stores the API result, it could be imperative that the Subscriber keep the stored copy of the resource up do date by processing all of the resources Change Notifications.

API naming

The proper naming of an API is essential for its successful use and adoption. Having a bad name leads to confusion and often misuse.

Often naming an API is easy and obvious to the API developer, but there are cases when deciding what to name an API could be more complex.

Anatomy of a good API name

Naming APIs is often difficult. Please invest the time in creating a good name because a bad name makes the adoption of your API difficult. For example, the user may find it hard to even locate your API and then when they find it, they may be confused by what it does. More often than not, users derive their understanding of behavior and meaning of the API through its name.

Several attributes of a good name include:

Attribute Description
Simple

A name should minimize confusion and be self-describing. For example, the name books. Combined with the operation and the name it can provide the user a simple understanding of what the API does. A HTTP POST of books could be viewed as an API that creates books.

Also consider how the name will be searched for and included in search results with other APIs. User fewer words, and do not try to be overly descriptive. For example, sections is a good name. sectionInfos, sectionDetails, or sectionData are less so.
Expressive Clearly conveys the resource the data represents. Avoid having users have to translate the words you use in the name to something. For example, source-contexts is difficult to understand what the data is.
Predictable Easy to learn and predict how it could be used.
Contextual Ensure the name is in the context you intent and consider how users coming from other domains may interpret the name. For example, book means something in terms of a library or store, yet means something else entirely in travel management system. Consider the enterprise use of your name and consider how it fits with other APIs within the service you are providing.

PATCH

According to RFC5789, "The PATCH method requests that a set of changes described in the request entity be applied to the resource identified by the Request-URI. The set of changes is represented in a format called a patch document identified by a media type."

It is optional for the API to implement the PATCH method.

Rationale for supporting

PATCH is similar to the PUT operation in that they both enable an update of resource properties. Ellucian standards further indicate that optional properties can be ignored in PUT requests, which is quite similar to a PATCH.

However, there are several areas where PATCH may provide a more graceful experience for the API consumer:
  • When the resource may have many required properties in the schema, but the API caller is needing to only update a few properties. Using PATCH saves the caller from making a GET request first to get all the current required properties to fulfill the request. Even though Ellucian API standards support ignoring missing optional properties, the PATCH is a more precise syntax.
  • When the resource contains an array, or other complex objects, and the operation is simply to add or remove an item, a PATCH may be supported with a single request. This is related to the existing standards that arrays are a full replacement, in PUT requests.

Key Considerations from the RFC

If the Request-URI does not point to an existing resource, the server may create a new resource, depending on the patch document type (whether it can logically modify a null resource) and user authorization rules.

In a PUT request, the enclosed entity is considered to be a modified version of the resource stored on the origin server, and the client is requesting that the stored version be replaced. With PATCH, however, the enclosed entity contains a set of instructions describing how a resource currently residing on the origin server should be modified to produce a new version.

Please refer to the RFC5789 for a more detailed description of PATCH and its detailed operations.

Alignment with other Standards

For an API to implement PATCH it needs to coexist gracefully and consistently with other operations. The following directives and statements expand upon how other API Standards are used in conjunction with the PATCH operations.

Rationale for supporting

This approach is a public standards based approach for operation discovery on an API. For APIs that are directly called by Internet Browsers the OPTIONS operation is used as part of origin policy validation to prevent unintended calls to other websites.

The request body is typically empty but the public standard does call this out for potential future use.

Usage with CORS

The CORS (cross-origin resource sharing) protocol enables internet browser-based applications to make API calls to many sources, but with intention, protecting the user from unintended calls to websites they may not be aware of.

This pre-flight request is a call to the OPTIONS operation to the API server, and the response informs the browser what operations are allowed.

To best support CORS the pre-flight request process, the request SHOULD NOT require authentication.

If the request is authenticated then the server could use the user as part of the calculation for the operations returned.

Optional and required model properties

JSON Schema-based data model property values are either required or optional, by which they are either essential to the very definition of the entity, or not. Because required properties are essential, they must contain some value, they cannot ever be empty; and, after set, they can only ever be updated to a new value, never unset to be empty.

By contrast, any optional Data Model property may be empty; and, if after set to a value, it may be subsequently set to a new value, or unset to indicate that it has no value.

Directive API Behaviors
Required All required properties MUST be returned in the data model GET operation. This assumes the API user has permissions to see the property.
Required If an optional property in the resource is empty in the source system, the API MUST not return the property as part of the result.
Required The API must enforce the schema defined in the data model on all operations.

As of 1H-2024, Change Notifications on Ellucian Ethos Data Models do not support ETags.

Setting and unsetting values

As part of the Ellucian validate-in-depth strategy, Data Model values are validated against multiple layers of validation rules.

The first layer is that the value must pass the syntactical definition of the property, as specified in the JSON Schema. If the JSON Schema definition states that the property is a string, for example, then the value being set must also be a string. If that string must match one of an enumerated list of possible values, then it must also be one of those values; and so on.

To unset an optional property, the caller MUST pass an "empty" form of the property's primary JavaScript data type. The following list applies to the API request the calling system will be making to the API:

  • For strings, an empty string: ""
  • For objects, an empty object: {}
  • For arrays, an empty array: []
  • For numbers, a null value: null

Numbers use the JavaScript null value to indicate an unset, not zero, because zero is a value. Booleans are not listed here, because they are not supported in the data model.

If an optional JSON property includes any syntactical constraints, then the API MUST provide an explicit, alternate JSON schema that will validate the unset, empty form of that property. For example, if we say that an optional property must match "ABC" when set, then the API must also provide an alternate definition that matches the empty string "" when unset.

APIs only need this when there are constraints on the property. If the optional property were defined to just be a string, then it will already validate both an empty and non-empty string. In fact, if the API provided an alternate unset schema in this case, validation would always fail.

Below are the constraints which will trigger the need for an alternate unset schema, by primary JavaScript data type:

  • Strings: any property with an enum, pattern, or minLength attribute
  • Objects: any property that contains any other child property that is constrained, or has a minProperties attribute
  • Arrays: any property with a minItems attribute
  • Numbers: always require an unset schema

APIs MUST never assume that an omission means that the property is to be unset. An unset is always an explicit declaration, just like a set. It means, "this property is defined as explicitly having no value."

Exceptions to partial updates on PUT

Due to the behavior of arrays with json merge partial updates are not supported on Ellucian Ethos Data Model properties that are arrays. If an array item is not included in a PUT request it will be deleted from the authoritative source system. This means to delete a selected array item on a PUT request, do not include it in the list and do not include the corresponding Unsetting value from the above list. The array values provided in the PUT request body MUST override the existing array values from the authoritative source.

APIs SHOULD support sorting. Refer to the product API documentation for implementation support and additional details on sorting.

HTTP request query parameters

Like filtering and pagination control, sorting is accomplished using a query parameter whose value is a URL encoded JSON string.

An example 'sort' query parameter is shown below (before being URL encoded):

?sort=[{"title": "asc"}]  // sort 'title' property in ascending order

The following is the same example, which has been URL encoded:

Note the 'sort' is a JSON Array, albeit the above example only including one element. The sort query parameter is used to identify one or more properties (in order) and whether sorting should be 'asc' (ascending) or 'desc' (descending). sort=[{"title":"asc"},{"age":"desc"}] // sort on title, then age (descending)

and URL encoded:

sort%3D%5B%7B%22title%22%3A%22asc%22%7D%2C%7B%22age%22%3A%22desc%22%7D%5D

Reasons for partial content responses

There are two main reasons why an API may not return a full representation of data in a API response. Please refer to the authoritative source documentation to better understand the impact of these features.

The first feature is referred to as “Data Privacy” in these standards. Data Privacy rules call for a source system to remove properties from the API response, if the API user is not authorized to view them. If a Privacy rule has been applied, the Response header X-Content-Restricted will be added to the response and the value will be “partial”. This tells the calling system that a property has been removed.

There could be user interface features that the API must honor in the form of “Restricted Fields”. These features mask a field value from the user interface until the user explicit clicks a button to “Show me” the fields. At this point the masking rules are removed and the user can see the data. This is different from an authorization rule because the user interface user is authorized to view the data, it is just being masked. The API SHOULD honor these same rules and could be another reason why partial content is removed. In the case of restricted fields, the API caller may include a specific request header that tells the API not to mask or remove the fields.

ETags

Entity Tags (ETags) support conditional requests in which the API server may or may not perform the requested action based on an additional variable the API client provides.

The API server that leverages an ETag enables more efficient caching and also provides the API client optimistic locking protection for updates.

If an ETag is supported, when a GET request is made to a single resource, an ETag response header is included in the response.

Then, in a future GET, PUT, or PATCH request the API client includes the ETag header. Including the ETag with the operation request enables the API server to check to see if the a new ETag has been created (meaning the resource has changed) and can then adjust its response to the request.

The ETag value generated by the API can either be a strong formatted string, preferably a MD5 Hash of the requested resource contents or a weaker value of a integer or even a concatenated string.

The ETag value and corresponding request header are both OPTIONAL for Ellucian APIs to implement and at the discretion of the API application to determine if they are required.

Directive Description
Required If the API server can support ETags, the value of the ETag SHOULD be a MD5 Hash for strong unique resource support, or a weaker value could be supported.
Required If on subsequent data change operations, if an ETag value submitted is not valid, the API server must return HTTP status code of 409 or 412, depending on the strength of the tag.
Required If GET request is made with an ETag request header and the resource has not changed, the API Server MUST return a HTTP status code of 304, with no content.
API versioning

Versioning an API and applying a consistent versioning practice ensures that APIs do not intentionally break API consumers.

Versioning becomes a part of the contract between the consumer and server, which allows for a reliable API yet also is flexible enough to enable continuous improvements.

Managing changes through versions

As discussed on this page, APIs cannot break but should gracefully evolve. Through the use of proper version management processes and solutions, the API can change.

The following information is useful to understand what is considered a safe evolution of an API through a safe (non-breaking) and an unsafe (breaking) change. It should be noted that the list below refers to any API implementing a resource in the JSON data format.

Non-breaking changes:
  • Adding a new optional property
  • Adding a new enum value
  • Required property changing to an optional property
  • Adding a new filter or query parameter
Breaking changes:
  • Adding a new required property
  • Renaming a property
  • Removing a property
  • Removing an enum value
  • Changing an optional property to required
  • Moving a property location
  • Converting property data types, including regex formats
  • Changing an object into an array or an array into an object
  • Resource name change
  • Removing a resource
  • Property value link change
  • Changing filter implementation behavior
  • Changing the underlying business logic in a significant manner which impacts the business process or interpretation of the data

Versioning by header

Ellucian Ethos-friendly APIs have standards on supporting versioning through the use of a header. There are other styles of versioning management, such as through the URL path, but to be consistent throughout Ethos, the versioning negotiation is done through request headers.

Please refer to the Accept headers and Content type header section of API behaviors for more details. Also, pay close attention to the API operations section which documents the expectations of the API consumer and API during various HTTP operations.

Semantic versioning

Ellucian Ethos-enabled API adhere to the semantic versioning standard published at http://semver.org.

Beginning in the 2nd Quarter of 2019, Ellucian has made improvements to versioning behavior in the APIs to more easily support semantic versioning.

Calling systems should use whole number (MAJOR) version numbers in accept headers. This will simplify the code and reduce change on calling systems.

For example, use application/vnd.hedtech.integration.v1+json to access the semantically versioned 1.0.0 resource.

A calling system can then withstand API upgrades and will only need to adjust code when they are ready to accept new properties or when the calling system would like to take advantage of a new MAJOR version.

The following principles are now applied to the API behavior based on the accept header values.

  • When a MAJOR version is requested, return the latest MAJOR.MINOR.PATCH version implemented that is compatible
  • When a MAJOR.MINOR version is requested, return the latest MAJOR.MINOR.PATCH that is compatible
  • When a MAJOR.MINOR.PATCH version is requested, return the latest MAJOR.MINOR.PATCH that is compatible

Please refer to the API source documentation for specific support examples.

By definition, MINOR and PATCH updates to resources are only additions of attributes. Therefore, the existing calling system code can still unmarshall the resource representation in its expected version.

Semantic versioning and API lifecycles

Ellucian Ethos-enabled APIs use semantic versioning to communicate to calling systems what versions of the API are currently supported.

This includes any pre release or “before general availability” versions of an API. The semantic versioning standard fully supports the initial development, alpha, beta, and through a 1.0.0 initial general release of an API.

Ellucian Ethos-enabled APIs also follow the initial development standard by using the semantic versioning header to reflect a pre-release version.

For example, if an API is in a beta program, the response header, which always tells the full semantic version truth, would return:

X-Media-Type: application/vnd.hedtech.integration.v1.0.0-beta+json

X-Media-Type: application/vnd.hedtech.integration.v1.0.0+json

As a reminder, to reduce breaking calling systems, callers SHOULD request representations of data using only the MAJOR version whole number.

  • APIs must enable early adopters to continue to use standard or common usage patterns.
  • They must also allow for graceful adoption of the API as it is released.
  • Focus efforts on API producers to manage the lifecycle versus requiring API consumers to change.
  • Take special care to NOT unexpectedly introduce pre-release data into the ecosystem when a API consumer did not request it.

Query string filters

Ethos API requests made with filters MUST URL Encode the query string. The criteria object used for filtering Ethos API calls contains unsafe reserved characters per RFC3986 Section 2.2.

Ad-hoc queries must use the query syntax described herein. Using this syntax, queries are defined as a JSON document. Queries are submitted by passing the query document as a JSON-formatted string using a query parameter called "criteria". For example:

https://integrate.elluciancloud.com/api/courses?criteria={"title" : "my course title"}

In the above example, the query document is shown as plain text for the sake of clarity. However, in reality this string should be URL encoded. For example:

https%3A%2F%2Fintegrate.elluciancloud.com%2Fapi%2Fcourses%3Fcriteria%3D%7B%22title%22%3A%20%22My%20Course%20Title%22%7D

Application servers, which host API based applications, are starting to enforce this RFC. Therefore, making sure the query string is encoding is REQUIRED. This includes not only API client applications, but also REST desktop tools. Various tools are used by developers and analysts to call REST APIs for testing and ad hoc querying. Some of these desktop applications automatically encode the URL for the user and some do not. The end user of the REST client needs to ensure it is properly configured to encode the URL.

The following sections provide an overview of the query syntax. Please note the examples below are not URL encoded for readability.

Equality

The simplest query is a test for equality. Let's assume we are searching for a course resource that has a title property:

https://integrate.elluciancloud.com/api/courses?criteria={"title" : "MATH101"}

The above example says give me all the courses where the course title equals MATH101. You can create an AND query by specifying more than one property in the query document. The following example says return all instances where description equals Beginning mathematics and number equals 101.

https://integrate.elluciancloud.com/api/courses?criteria={"description" : "Beginning mathematics", "number" : "101"}

Please refer to the product documentation for additional support information on a equality could be interpreted by data type. For example, an API may implement a "greater than or equal to" definition if the type is a date.

Querying embedded documents

Given the following document:

{"id" : "6b0339df-6fce-484d-8073-2b39c7989598", "item" : {"name" : "item1", "code" : "001"}}

To exactly match the entire embedded document, your query document would look like the following:

{"item" : {"name" : "item1", "code" : "001"}}

Named query support

A named query is a pre-defined query that must be described within the API documentation. Named queries may be used to perform very complex queries without requiring the API user to construct a complicated ad-hoc query.

A named query is specified as a query parameter and may require arguments which must be expressed using JSON (where the arguments are provided as name-value pairs akin to the ad-hoc query syntax used for filtering by 'equality', as described above).

?highestPerformingStudents={"grade":"A","honors":"true"}

Invalid query parameters

Properties passed in as part of the criteria query parameter defined below must be valid (defined in the documentation for the API)

Given this document example:

{"description" : "Beginning mathematics", "number" : "101", "title" : "MATH101"}

The supported properties to query on are description, number and title.

This is a valid example of the criteria:

criteria={"description" : "Beginning mathematics", "number" : "101", "title" : "MATH101" }

This is a valid example using one of the criteria properties:

criteria={"number" : "101"}

This is a not valid example, instructor is not a property in this example allowed to be queried on.

criteria={"number" : "101", "instructor" : "101bf628-8750-4885-b0b9-0366e85e37a5" }

If the filter is not valid, the API MUST return an error.

Query specification

Documentation pertaining to each data model must specify the filtering requirements that must be supported by any authoritative source for that model. This model-specific documentation must specify which model properties may be included within an ad-hoc query, and specify the named queries (and arguments) that must be supported.

That is, while the implementation of a query may vary greatly by technology, the semantics and interface of that query must be consistent regardless of what solution is configured as the authoritative source for that model.

Note it is necessary to limit the properties that may be included within an ad-hoc query to ensure acceptable performance (e.g., indexing may be necessary within a data store).

The Ellucian Ethos Data Model working group must be used to coordinate the specification and agreement of specific filtering requirements for each Ellucian Ethos Data Model.

Basic operators

The following basic operators are supported.

Operator Definition
$gt Greater than
$gte Greater than or equal
$lt Less than
$lte Less than or equal
$ne Not equal

Below is an example of how to use the above operators. This example says give me all the instances where count is greater than 10.

OR queries

An OR query can be performed using the $or operator. The example below will return all instances where property1 equals true or property equals false.

{"$or" : [{"property1" : true}, {"property2" : false}]}

The $or operator can also be used in conjunction with the other operators. For example:

{"$or" : [{"qty" : {"$gt : 10}}, {"qty" : {"$lt" : 20}}]}

JSON schema

JSON Schema is a standard format for APIs to describe the data contract between the API consumer and server.

APIs that support the use of JSON in the request, response and at times in the URL, use JSON schema to define the data elements in the API in a manner that can be annotated and validated.

JSON schema, as defined by http://json-schema.org/, is the standard means to describe the type and structure of data. The Ellucian Ethos Data Model was the first set of APIs Ellucian supported using the JSON Schema format, but today, any Ellucian Ethos API uses JSON schema to represent the data model for the API.

The following section describes various data modeling concepts and JSON schema practices for APIs.

Modeling concepts

Viewing

Data models are expressed in JSON format using JSON schema syntax. On large models viewing the information can be a challenge. Be sure to refer to the EEDM documentation to view a human readable representation of the schema and sample data. In addition, using any publicly available JSON viewer is helpful.

Required properties

Some of the properties displayed in the model are declared to be Required. In these cases, the schema is communicating that those fields are at a minimum needed to handle a request to create or update a resource. There could be other properties that are required in the Authoritative Source (but not declared in the Data Model) and these MUST be handled by the use of default values if not provided by a Subscriber. Authoritative Sources SHOULD allow administrators to configure default values which can be used.

Boolean properties

Booleans should be cautiously used and instead defer to using meaningful enumerations. This allows for flexibility in the data over time. If the data "grows" you can expand the enumerations list with less impact than if you change from a Boolean to an enumerated property. For example, at one point in time the property "married" used to be a simple yes or no answer. In today's world of complex CRMs, you could have many enumerated values to answer that question. If a Boolean makes the most sense, make sure the property clearly identifies what a TRUE value would represent and what FALSE would represent. Strive to use affirmative names for clarity.

A good example name for the marriage example would be "isMarried". Some bad examples would include: "married" and "isNotMarried".

OneOf

There are several uses of a OneOf relationship in the Data Model. This is an advanced declaration in the schema and is meant to communicate that there could be different property types depending on the use case or other data. The formal definition of oneOf is "To validate against oneOf, the given data must be valid against exactly one of the given subschemas."

Enums to configuration

Enums MUST be used with caution. Enum values require Authoritative Source configuration. This requires administrators to map the Ethos value in the enum to the Source systems code or value.

Links

Some schemas refer or link to other schemas. This is done by using the link property. To reduce complexity the best scenario for linking to other resources is to simply use and refer to the other resources identifier. Subscribers can simply retrieve the dependent resource by ID. This is preferred over copying certain properties from one instance to another.

Extensions

There could be cases where an Authoritative Source and a Subscriber decide that the Data Model used can be improved to support a localized data set. As an example, there could be properties the Authoritative Source uses that are currently not a part of the Ethos Data Model.

This is the primary use case to leverage the capabilities of Ethos Data Model extensions. The ability to add additional properties to a Data Model and configure an Authoritative Source to honor and retrieve these additional properties, enables Subscribers to have access to otherwise unexposed data.

Schemas can be extended (or added to) using Ellucian Ethos Data Access for GraphQL integrations. See Data model extensibility for more information.

Batches

APIs composed in a domain-driven and transactional manner typically support one resource at a time when creating or updating data. In some use cases, such as loading or updating large numbers of resources, this pattern can lead to less-than-desired outcomes.

A batch interface can be supported to address these challenges and can lead to more performant and manageable outcomes.

Click the attachment icon in the navigation area at the side of this page on this page and download the batches and batchesopenapiexample JSON files.

Batch APIs have the following advantages:
  • Fewer API requests reduce API chatter. 1000 calls can be 1.
  • Overhead logic, such as a security check, is reduced.
  • Fostering asynchronous patterns decreases overall time to completion.

The following details describe how APIs can implement a batch interface and how API clients can use it.

Requests

Requests using a batch interface support an array of resources in the request body and other API-required metadata.

Here is an example of a request using the batch resource interface:

{
  "batch": {
    "id": "00000000-0000-0000-0000-000000000000",
    "resource": {
      "name": "widgets",
      "version": "application/vnd.hedtech.integration.v1+json"
    },
    "items": [
      {
        "id": "00000000-0000-0000-0000-000000000000",
        "code": "AB",
        "title": "The first new resource.",
        "description": "The first new resource description."
      },
      {
        "id": "00000000-0000-0000-0000-000000000000",
        "code": "CD",
        "title": "The second new resource.",
        "description": "The second new resource description."
      }
    ]
  }
}

Description

The following table gives a brief description of the batch interface. See the batches.json schema attachment for more details. This schema is extensible by supporting additional properties in the JSON schema so that source systems can augment the batches data with any system specific meta data that may be required.

Property Description
batch.id The identifier for the batch.
resource.name The name of the resource contained in the items collection.
resource.version The semantic version of the resources in the items collection.
items Array of resources to be created or updated.
items.id

If the item id is a nil GUID ("00000000-0000-0000-0000-000000000000"), or not present then the API assumes this resource is to be created.

If the item id is a value, then it is used in the context of an update.

Types of processing

Synchronous and Asynchronous

The schema presented in this standard is designed to support APIs that process the batch request in both a synchronous and asynchronous manner.

Because batch requests attempt to process a large number of resources at once, the API SHOULD process the request asynchronously. This provides a safe and well-defined pattern for making the requests, processing the requests, polling for process state, and finally reviewing results.

If the API cannot process in asynchronous manner, this same interface still SHOULD be used for consistency and future improvement.

Transactions

Batch APIs consider each operation on a single item in the items collection to be an atomic transaction.

This means that when the batch has 10 items in the items collection and one transaction fails, then nine items are created or updated, and one is returned in error.

The API response will contain the same ordered number of items representing the successful items and failures.

API Invocation

The preferred method for supporting a batch request is to support a nested resource named batches.

For example, if you have a resource named widgets:

Request: POST https://integrate.elluciancloud.com/api/widgets/batches/ HTTP/1.1
Request
    Body (Content-Type :application/vnd.hedtech.integration.v1.0.0+json)

The use of a nested resource enables the API to reuse the security permissions defined at the base resource level for that batch. Because the batch response contains a representation of the resource, the same permissions are inherited.

When the API is asynchronous, this also enables the resource address of the batch to be in the same permissions model again.

HTTP POST Preferred Operation

As discussed in these standards, a POST operation intends to instruct the API server to create a new resource based on the provided request body.

The batch is the resource for batch APIs.

Each item in the items collection is treated as an upsert, or a replacement. If the resource already exists, then the API treats the transaction as an update. If the resource does not exist, a new resource is created.

This API server can determine the type of operation by using the resource identifier.

If the resource identifier is a nil GUID or missing, the API treats it as a create resource request. If the resource identifier is valid and exists, the API treats the request as a update of an existing resource.

Responses

The response of a batch request provides the API client with detailed information about the success of the overall operation and each individual resource.

The representation of the batch is used to optimize the creation or modification of resources, and therefore has a different strategy as to returning resources. The single resource operations, such as PUT and POST, can return a full representation of the resource. The batch typically would not.

On new resource creation, only the resource identifier, key, or the minimal set of properties to support GET are returned. On a update of an existing resource, the same rule applies.

Initial Response when asynchronous processing is supported:

{
  "batch": {
    "id": "af10dbeb-ff2a-4df5-aa44-4281b24f1611",
    "status": "inProgress"
  }
}

Polling or an immediate synchronous response:

{
  "batch": {
    "id": "af10dbeb-ff2a-4df5-aa44-4281b24f1611",
    "resource": {
      "name": "widgets",
      "version": "application/vnd.hedtech.integration.v1.0.0+json"
    },
    "status": "completed",
    "totalErrorsCount": 1,
    "items": [
      {
        "id": "90b9080-b8ab-49e4-aca3-eadea0d10e25"
      },
      {
        "errors": [
          {
            "id": "ee99dcf8-9dc8-4382-92cb-8ef1471a5c1c",
            "message": "The resource could not be updated due to a duplicate code."
          }
        ]
      }
    ]
  }
}

Property Description
batch.id The identifier for the batch, if available.
resource.name The name of the resource contained in the items collection.
resource.version The semantic version of the resources created or updated by the server.
status The process or job status. This can vary depending on the source system. See the source system documentation for possible values.

Array of resources to be created or updated.

If the item is a success, the item instance is created or updated.

If the item fails, then the object is a errors collection.

Code When used

404 If the batch URL is called but not supported.
413 When the batch request contains more items in the items collection than the API can support.

Error handling

As mentioned above, the API response will contain a list of either item IDs or other properties as a JSON object, or if there was an error, an error message JSON object that follows the Ellucian error messages standard.

The response includes the inbound request items array and response items array. Therefore, it will be the same size and is expected to be in the same order.

This is the method by which the caller can know which items failed. Callers can iterate through the response list "for each item" and, if the item is an error, use the array index value to reference the corresponding request array index to determine which request items failed.

It is important that the API client application calling a batches API save off the request it builds, because it will be expected to be used in conjunction with the response.
