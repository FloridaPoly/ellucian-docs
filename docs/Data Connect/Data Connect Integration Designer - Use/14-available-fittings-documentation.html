Ethos Consume Change Notifications fitting

Use this fitting to consume change notifications (CNs) from Ethos Integration. After processing a change notification (CN), use the Confirm CN fitting to mark it as processed.

These two fittings are used together in the following order:
  1. Consume CN
  2. Fitting segments to perform necessary processing
  3. Confirm CN

Pay attention to the following when using this fitting:

  • This fitting will request Ethos to return CNs using the last processed ID previously recorded by the Confirm fitting. If no last processed ID has been recorded, this fitting will use a last processed ID of "0".
  • By default, multiple CNs are consumed in a batch. Configure the batch size using the limit configuration below.
  • It is the responsibility of the processing segments to preserve the CN number so that it can be used in the Confirm fitting. If the CN number is not preserved (due to error, or intentional skip logic), then the last processed ID persisted by the Confirm fitting will not be updated.
  • If the behavior of your processing logic is such that a certain last processed ID does not reach the Confirm fitting (due to error or otherwise), the last processed ID is not incremented. If a subsequent CN is successfully processed, confirmation of that CN will implicitly confirm the prior CNs because CNs are ordered.
  • CNs will be pushed down the pipeline one at a time. Because of the streaming nature of an integration pipeline, the first CN that was pushed down the pipeline may still be making its way through the later processing steps when the second CN begins making its way through the first set of processing steps. Order of processing is maintained, but there is no transactional guarantee that the first CN will be completely processed before the second CN begins to be processed.

Expected input

Optional message payload that is a JavaScript object.

Reference configuration

Configuration Description
Resources Required. Array of Ethos resources: A list of resources is available in the API Catalog.
Limit Optional. Maximum number of messages to consume. Note: Ethos Integration defaults to 20 if not set, and has a top limit of 1000.
Target Optional. Dot-notation target within payload to put Ethos response. When not set it replaces the whole message payload.
Ignore Errors Optional. Flag that when set to true, it disables error reporting to Ethos when an error is caught. Use this in conjunction with errorPath to implement custom error handling further in the pipeline.
Error Path Optional. Dot-notation error path. Setting this will push original message forward with error details. Error path can specify a location in header or payload. When no location is specified it defaults to payload, in other words: "error" is the same as "payload.error"
Api Key Optional. Name of a pipeline parameter which will contain the the API key to be used by this fitting. When not specified ethosApiKey will be used.

Example

The following is an example of how to use Ethos Consume Change Notification.

  1. In order for this fitting to work, an Ethos Api Key should be created as a parameter. Click over the dropdown menu aside the pipeline name, select Edit Pipeline Settings, and add a new pipeline parameter named ethosApiKey. This parameter should be required, sensitive and of type string. The name is reserved so it will always pick that parameter unless a different option is selected as the APIi key in the configuration.
  2. Enter the following configuration:
  • Resources -> Name: instructional-methods
  • Resources -> Enter Supported Versions: 6 (Click the + button after entering this parameter)

Running the test will get all the change notification messages up to the limit set, if there was no limit set then it will return up to 20, to a maximum of 1000.

Output

This fitting will push a new message for each change notification received in the response.

Example

The following is an example of how to use Ethos Proxy Get:

  1. In order for this fitting to work, an Ethos API Key should be created as a parameter. Click over the dropdown menu aside the pipeline name, select Edit Pipeline Settings, and add a new pipeline parameter named ethosApiKey. The name is reserved so it will always pick that parameter unless a different option is selected as the API key in the fitting configuration.
  2. Enter the following fitting configuration:
    • Fitting Name: Ethos Proxy Get
    • Resource: persons (in lowercase)
    • Accept Versions: 12

  3. For this example, an optional string pipeline parameter named personGuid will be defined. This parameter is going to be used by the fitting as the ID of the person.

A new message with the same header as the input and with a payload that is the response. If the response is JSON, it will be parsed into a JavaScript object.

If neither the idFromPayload nor the idFromContext properties are specified the resource is queried without ID as a get all. The same happens if the personGuid value is not provided.

When specifying the idFromPayload or idFromContext configuration properties but provided with a JSONPath syntax that is not valid, the Ethos resource isn't reached, the original input message passes along to the next fitting and an error gets reported.

Example

The following is an example of how to use Ethos proxy Get with filter:

  1. In order for this fitting to work, an Ethos API Key should be created as a parameter. Click over the dropdown menu aside the pipeline name, select Edit Pipeline Settings, and add a new pipeline parameter named ethosApiKey. The name is reserved so it will always pick that parameter unless a different option is selected as the API key in the fitting configuration.
  2. Enter the following fitting configuration:
  • Resource: persons
  • Filter: ?criteria={"names":[{"firstName":"james"}]}
  • Accept Versions: 12 (Click the + button after entering this parameter)
  1. Run the test. This retrieves all the persons that match with the given filter criteria.

Output

A new message with the same header as the input and with a payload containing the response. This fitting supports paging. This fitting will determine if paging is needed based on the x-total-count response header, the page size (if specified), and the response body length.

With Paging

If paging is needed, and the payload target path is specified, then the paged response(s) will be concatenated into an array and the array will be inserted into the message payload at the location specified by the payloadTargetPath property in the fitting configuration. The message will then be pushed through this fitting. It should be understood that the payloadTargetPath property is not intended to be used with a high volume of data from many paged responses to prevent running out of memory.

If the payloadTargetPath is not specified, then each paged response will be pushed through this fitting as a separate message.

The page size can also be specified in the fitting configuration. Each paging request will use a limit criteria equal to the page size. If the page size is not specified, the default page size for the given resource as determined by the Ethos resource API is used.

Without Paging

If paging is not needed and the payloadTargetPath configuration property is specified, the response will be inserted into the message payload at the location specified by the payloadTargetPath, and the message will be pushed through this fitting.

If paging is not needed and the payloadTargetPath is not specified, then the response will replace the message payload, and the message will be pushed through this fitting.

Query by Post

To use an Ethos QAPI endpoint, set queryByPost to true and also specify contentVersion. The payload of the message coming into this fitting becomes the body of the outgoing QAPI call. Paging is supported on the QAPI response.

File List (AWS S3 List Objects) fitting

Use this fitting to retrieve a list of file names stored in S3.

Expected input

No input is required but message payload should preferably be of type object. Message is only required if the filePrefix has message dependent interpolation references.

Reference configuration

Configuration Description
File Prefix Required. Case-sensitive, retrieves only the files with the given prefix.
Target Optional. Payload target. Supports dot-notation structure.
Bucket Optional. The name of a parameter (context entry) containing an S3 bucket name.
Access Key Id Required if using the bucket option. The name of a parameter (context entry) containing an AWS Access Key ID.
Secret Access Key Required if using the bucket option. The name of a parameter (context entry) containing an AWS Secret Key.

Key Interpolation

The config.filePrefix allows for interpolation tags that take into account values in context and processed message (including header and payload).

Some examples of filePrefix values:

  • Roster - Simple hardcoded value (no interpolation).
  • {{context.filePrefix}} - Interpolated value from context
  • {{message.header.filePrefix}} - Interpolated value from message.header
  • {{message.payload.filePrefix}} - Interpolated value from message.payload
  • subfolder/{{context.filePrefix}} - Combination of hardcoded folder with interpolated filename from context
  • {{context.foldername}}/{{message.payload.filePrefix}} - Combination of two interpolated values from both context and message.payload.

The final filePrefix value will always be prefixed by the tenant ID found in pipeline context.

Example

The following is an example of how to use File List

File prefix is the only required parameter. For this example, the File Prefix used will be person.

Expected output

This fitting will retrieve the list of files that matches with the provided text or empty if nothing found.

When config.target is not configured, the result will be set as the outgoing message payload.

When config.target is configured, the process will embed the result in the target's location. If the incoming message is not an instance of message or its payload and not of type object, the original value will be stored in the outgoing message payload's _originalValue property, while the result is placed in the target's location.

Error Handling

Errors while accessing an Object's HEAD metadata will not cause pipeline interruptions. In these cases, the incoming message as-is will be passed through and the error will be reported.

To specify a bucket of your choosing, use the bucket configuration property and include AWS credentials in the related properties.

  • {{context.foldername}}/{{message.payload.filename}} - Combination of two interpolated values from both context and message.payload

HTTP Request fitting

Use this fitting to perform an HTTP operation.

Expected input

A message payload that is a string or JavaScript object.

Reference configuration

Configuration Description
Method Optional. HTTP method (GET|POST|PUT|DELETE, etc .). Defaults to GET.
Uri Required. Path to the requested resource. for example, http://domain/path.
Target Optional. Dot-notation target within payload to put response body
Result Headers Optional. Dot-notation target within message to put response headers. When not set headers will be dropped silently. Valid examples: theHeaders, payload.theHeaders, header.theHeaders, message.payload.theHeaders, message.header.theHeaders. Note that if the response is an array, the headers will be saved into message.header.propName even if payload was specified as the place to save them. Repeated headers will be stored in an array value.
Cache Optional. Flag to enable or disable response caching (only for GET requests), defaults to false.
Stream Optional. Flag to enable or disable response streaming (only for GET requests). When streaming is enabled cache and target will not be supported and result headers are ignored.
Authorization Optional. Authorization specification. The authorization section allows someone to setup user name and password for basic authorization header setup. This will override any explicit authorization header specification at the headers section.
Headers Optional. Hash of key or value pairs to be sent as headers.

The authorization section allows someone to setup username and password for basic authorization header setup. This will override any explicit authorization header specification at the headers section.

Ellucian recommends that interpolation is utilized in both username and password. We use mustache.js to interpolate values. Avoid hard coding sensitive access information in a pipeline's configuration.

The following is an example of how to use HTTP request fitting to make OAuth calls with client-id and secret-key.

  1. Enter the following parameters:

    a.

    • Name: clientId
    • Label Type: Single string value
    • Label: Client ID
    • Required: Yes
    • Sensitive: Yes
    • Type: String
    • Min Length: 1

    b.

    • Name: clientSecret
    • Required: Yes
    • Sensitive: Yes
    • Type: String
    • Min Length: 1

    c.

    • Name: authUrl
    • Label Type: Single string value
    • Label: Authentication URL
    • Required: Yes
    • Type: String

    d.

    • Name: resource
    • Label Type: Single string value
    • Label: Resource
    • Required: Yes
    • Type: String
    • Min Length: 1
  2. Enter the following fitting configuration:
    • Fitting Name: getAuthToken
    • Method: POST
    • Uri: {{{context.authUrl}}}
    • Authorization Username: {{{context.clientId}}}
    • Authorization Password: {{{context.clientSecret}}}
    • Body Type: from-urlencoded
    • Body Content: JSON
    {
  "grant_type": "client_credentials",
  "resource": "{{{context.resource}}}"
}

  3. Run the test to get the Authorization token from the access_token in the payload of the result. Use the following information in the required fields:
    • Client ID: enterYourClientID
    • Client Secret: enterYourClientSecret
    • Authentication URL: https://test/token

Output

Non-Streamed Requests

By default HTTP Fitting Request response body is read as a whole (in one step) and sent down the pipeline in a message envelope using the same header as the incoming message. If the response is JSON, it will be parsed into a JavaScript object.

Streamed Requests

When streaming is enabled by using the stream parameter, the fitting splits the request response body and sends each chunk as it is received down the pipeline as string until all content is read. This is useful for big downloads.

Note:

Result headers are not populated when using the streaming options.

Transformation Functions

There are several transformation categories each of which contain one or more functions that can be used to change a mapped field's format or content.

  • string
    • toUpper : Converts all the alphabetic characters in a string to uppercase.
    • toLower : Converts all the alphabetic characters in a string to lowercase.
    • trim : Removes the leading and trailing white space and line terminator characters from a string.
    • truncate : Truncates a string if it exceeds a specified maximum length. Accepts one numeric parameter.
    • trimTruncate : Removes the leading and trailing white spaces and truncates a string if it exceeds the specified maximum length. Accepts one numeric parameter.
    • append : Appends one or more values to the input and returns the result.
    • prepend : Prepends one or more values to the input and returns the result.
    • substr : Gets a substring beginning at the specified location and having the specified length.
    • replace : Replaces text within input using a regular expression or search string.
    • split : Split a string into substrings using the specified separator and return them as an array.
    • toNumber : Converts a string value into a number.
  • number

    toFixed : Returns a string representing a number in fixed-point notation. Accepts one numeric parameter.

  • date

    format : Converts a date from an input format to the output format. Accepts two parameters, an input and an output date format strings. Based on momentjs format tokens.

  • array
    • unique : Returns a duplicate free version of list. Only works for primitive data types like strings and numbers, and is case sensitive. Aliases: removeDuplicates
    • without : Return an array version without provided values.
    • join : Adds all the elements of an array separated by the specified separator string. Accepts an optional delimiter parameter. If omitted, comma (,) is used to join array values.
    • find : Returns the value of the first element in the array where criteria or pathExpression predicate is true. For example,. preferred as criteria, and $.preference as pathExpression.
  • object
    • get : Returns the value of the first element matching pathExpression.
    • query : Returns an array of elements that satisfy the provided JSONPath expression, or an empty array if none were matched.
  • util
    • crosswalk : Translates the values in a single string or array based on crosswalk. Accepts one string parameter to specify which crosswalk configuration or function to use.
    • coalesce : Returns specified alternate value when input is undefined or null.
    • log : Outputs input content to console.log and passes-through its value. Used primarily for debugging purposes.
Example using the util.crosswalk function

Crosswalks are a way to customize the translation of one value to another. This is especially useful when data need to match a very specific set of enumerated values. When using util.crosswalk, you can reference tenant wide crosswalks or segment defined ones. The name of the crosswalk needs to be set as the first function parameter. If the crosswalk is not found the function will not be executed and ignored.

There are some built-in crosswalk functions that can be used out of the box with util.crosswalk:

Accumulators

Accumulators are defined within the detail.accumulators configuration property. They are defined buckets to analyze incoming data and can be configured as custom properties to accumulate values to be used in the footer row.

Note: They are not available for header row use.*

Accumulator naming is flexible, it can based on reporting logic needs or some meaningful label. Each accumulator definition consists of a cumulative function name and the parameters it needs. For example:

  • Name: averageGrade
  • Cumulative Function: Average
  • Parameters: column1

Assuming there is an accumulator of name averageGrade defined, to include it as part of the Footer row you would configure it as:

  • Type: Literal
  • Value: {{accumulators.averageGrade}}

If the averageGrade calculation renders a number with a long decimal section, like 66.66666667. By using the number.toFixed Transformation Function you can standardize the way the value is presented across different scenarios.

  • Category: number
  • Function: toFixed
  • Enter Parameters: 2 (Click + button after entering the parameter)

This way you can transform any averageGrade value into a rounded 2 decimal position number. The example value of 66.66666667 would be transformed to 66.67.

Lastly, if you need to add an offset of 10 to that average. You would need to change the column type to eval and convert the value into a mathematical operation where accumulators.averageGrade gets added 10. Like this: {{accumulators.averageGrade}} + 10

In this case your value of 66.66666667 would be integrated into the mathematical expression and evaluated to 76.66666667, then transformed to 76.67.

Cumulative Functions

There are currently four implemented cumulative functions:

  • add: Adds the specified parameter value to the accumulator.
  • min: Keeps the accumulator updated with the smaller of a series of values.
  • max: Keeps the accumulator updated with the greater of a series of values.
  • avg: Keeps the accumulator updated with the cumulative average of a series of values.

All cumulative functions expect numeric inputs, however, a specific column name (as string) can be defined to make it the basis of value series to be analyzed.

Consider the following accumulators setup:

  • Accumulator01:
    • Name: counter
    • Cumulative Function: Addition
    • Parameters: 1
  • Accumulator02:
    • Name: col1Sum
    • Cumulative Function: Addition
    • Parameters: column1
  • Accumulator03:
    • Name: col1Average
    • Cumulative Function: Average
    • Parameters: column1

There are three defined accumulators: counter, col1Sum, and col1Average.

Their naming is totally flexible, but after they are set, their case-sensitive name must be used when using their reference tag on the footer row:

  • {{accumulators.counter}}
  • {{accumulators.col1Sum}}
  • {{accumulators.col1Average}}

// Payload 1
{ "column1": 100 }
// Payload 2
{ "column1": 50 }
// Payload 3
{ "column1": 50 }

  • counter : 3

  • col2Average : 66.6666667

Header and footer rows

Not to be confused with detail column headers, header and footer rows are optional content rows that can aid in the final report presentation or format. A header row is the very first row to be displayed, while the footer row is the last one.

For example, a header row can contain the report title while the footer row can contain totals.

REPORT TITLE
column1,column2,column3
foo1,bar1,100
foo2,bar2,100
foo3,bar3,50
TIS THE LAST ROW

Header and footer configuration properties are lists that accept string (literal) values or configuration object for more advanced definitions. Both types can be found in a single list at the same time.

Each header and footer column is interpreted and then rendered. The logic follows this strict order:

  1. Reference Tag are replaced.
  2. JavaScript expressions are evaluated.
  3. Final value is rendered.

    More on Reference tags below.

To get a report just like the previous example, the fitting configuration must look like the following:

  • Header01:
    • Type: Literal
    • Value: REPORT TITLE
  • Column01:

    Path: column1

  • Column02:

    Path: column2

  • Column03:

    Path: column3

  • Footer01:
    • Type: Literal
    • Value: TIS THE LAST ROW

Even though the detail.columnHeaders is set to true, it has nothing to do with the report header and footer configurations.

  • transform: Optional list of transformation functions.

Reference Tags

Reference tags are mustache type placeholders that are replaced at runtime.

It is the first step to be executed in the column interpretation logic. Any value coming out of the reference tag will be available for JavaScript expression evaluations and transformations, if they apply.

Reference tag data comes from two different sources: context and accumulators. When a tag is specified but cannot be mapped to a context or accumulator field, then it is replaced with empty string.

// With a mask of '<hidden>'
'test' is masked with '<hidden>'

Transform function

Values may be obtained from the pipeline context using context.get('key'). New values can also be added to the context from within a transform function by using the context.set function, which accepts a key and a value as parameters.

function transform (message, context) {

  return message;
}

Transformation functions

There are several transformation categories each of which contain one or more functions that can be used to change a mapped field's format or content.

string

  • toUpper: Converts all the alphabetic characters in a string to uppercase.
  • toLower: Converts all the alphabetic characters in a string to lowercase.
  • trim: Removes the leading and trailing white space and line terminator characters from a string.
  • truncate: Truncates a string if it exceeds a specified maximum length. Accepts one numeric parameter.
  • trimTruncate: Removes the leading and trailing white spaces and truncates a string if it exceeds the specified maximum length. Accepts one numeric parameter.
  • append: Appends one or more values to the input and returns the result.
  • prepend: Prepends one or more values to the input and returns the result.
  • substr: Gets a substring beginning at the specified location and having the specified length.
  • replace: Replaces text within input using a regular expression or search string.
  • split: Split a string into substrings using the specified separator and return them as an array.
  • toNumber: Converts a string value into a number.

number

toFixed: Returns a string representing a number in fixed-point notation. Accepts one numeric parameter.

date

format: Converts a date from an input format to the output format. Accepts 2 parameters, an input and an output date format strings. Based on moment.js format tokens.

array

  • unique: Returns a duplicate free version of list. Only works for primitive data types like strings and numbers, and is case sensitive. Aliases: removeDuplicates
  • without: Return an array version without provided values.
  • join: Adds all the elements of an array separated by the specified separator string. Accepts an optional delimiter parameter. If omitted, comma (,) is used to join array values.
  • find: Returns the value of the first element in the array where criteria or pathExpression predicate is true. For example, preferred as criteria and $.preference as pathExpression.

object

  • get: Returns the value of the first element matching pathExpression.
  • query: Returns an array of elements that satisfy the provided JSONPath expression, or an empty array if none were matched.

util

  • crosswalk: Translates the values in a single string or array based on crosswalk. Accepts one string parameter to specify which crosswalk configuration or function to use.
  • coalesce: Returns specified alternate value when input is undefined or null.
  • log: Outputs input content to console.log and passes-through its value. Used primarily for debugging purposes.

Crosswalks are a way to customize the translation of one value to another. This is especially useful when data need to match a very specific set of enumerated values. When using util.crosswalk, you can reference tenant wide crosswalks or segment defined ones. The name of the crosswalk needs to be set as the first function parameter. If the crosswalk is not found the function will not be executed and ignored.

There are some built-in crosswalk functions that can be used out of the box with util.crosswalk:

  • iso3166.country.alpha3ToAlpha2 : Converts an ISO 3166-1 Country Code from Alpha-3 to Alpha-2.
  • iso3166.country.alpha2ToAlpha3 : Converts an ISO 3166-1 Country Code from Alpha-2 to Alpha-3.

XML template

The XML template configuration allows you to define what the final XML should look like in the end. Along with special directives and interpolation placeholders data from messages and context can be integrated into the final outcome.

Well formed XML is required for the fitting to work as expected.

Declaration

An XML declaration (like the one below) is required only if the final XML needs it.

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>

A valid scenario where a declaration can be ignored is when the fitting is used to generate XML fragments.

<Foo>Hello World</Foo>
<Bar>Bar 1</Bar>
<Bar>Bar 2</Bar>

You can see from the sample above the template lacks a declaration, and a root element.

Directives and interpolation can be used on XML fragments.

Directives

There are three directives that can be used in the template configuration: *source, *scope, and *payloadLoop. All directives are optional but crucial when mapping data.

  • *source: JSON path string to refine an element's data scope. All root elements have a default source of $.payload, which points to the Message.payload field. A parent's *source scope is passed to all its children as their default *scope. When a non-root element *source is not set, it will be defaulted to its *scope. The only way a deeply nested element can use a different Message field, like the Message.header, is to reset the scope with the *scope directive. The dollar sign ($) in a source's JSON path value always points to the inherited or set *scope.
  • *scope: JSON path string to define an element's message data scope. All root elements have a default scope of $, which is the Message root. Non-root (or nested) elements get their scope from its parent's *scope and *source combination. The dollar sign ($) in a scope's JSON path value always points to the Message object.
  • *payloadLoop: Boolean flag that defines an element as an element that will repeat based on each message received. There can only be one *payloadLoop per template. If more than one element is marked as *payloadLoop only the first one found (while doing a top-down document traverse) will be taken into consideration for looping.

All directives are used as attributes and are required to have the asterisk prefix, otherwise they will be considered a plain element attribute.

*source mappings that reference an array will cause an element to be automatically repeated.

Interpolation

Values from messages and context can be integrated into the final XML by using interpolation references. Interpolation references are dot-notation path strings wrapped with squiggly brackets and a starting dollar sign, that is ${source.name}. The references can be used within attributes, and element text (even within CDATA).

Interpolation paths can have two different root nodes: source and context.

  • source: References the inherited or defined element scope or source from processed Message object.
  • context: References the pipeline's Context object.

Interpolation paths should always point to primitive values such as string and numbers, but if an array is found values will be automatically joined with commas.

The interpolation reference ${source} can be used when the element source mapping produces an array of primitive values. The element will be repeated by each array item; the only way to reference each item's value is by using ${source}.

Sample interpolation paths:

  • ${source}
  • ${source.name}
  • ${source.address.city}
  • ${context.runId}

Static (or hard coded) content can be combined with interpolation to create richer XML content. For instance, and attribute or element content value of "RunId-${context.runId}" will render as "RunId-123456789", assuming the context's runId value is 123456789.

Example

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<Root>
  <Student *payloadLoop="true" *source="$.student" id="${source.id}">
    <Name>${source.name}</Name>
    <Course *source="$.courses">${source}</Course>
  </Student>
  <Transaction *scope="$.header">${source.transactionId}</Transaction>
</Root>

And the following message structure:

{
  header: { transactionId: 12345 },
  payload: {
    student: {
      name: 'John Smith',
      id: '100',
      courses: ['English', 'Spanish']
    }
  }
}

Based on template the following can be inferred for the <Root> element:

  • *scope is defaulted to $
  • *source is defaulted to $.payload
  • All of <Root> children's scope would point to $.payload
  • <Student> element:
    • *scope value is inherited from <Root>: $.payload
    • *source is explicitly set to $.student
    • *payloadLoop is set to true. Multiple instances of the element will be rendered if more than one message is processed by the fitting.
    • Attribute id has an interpolation reference: ${source.id}. This mapping is going to retrieve the id field from the element's source $.student.
    • All of <Student> children's scope would point to $.payload.student
    • <Name> element:

      *scope value is inherited from <Student>: $.payload.student

      • *source value is defaulted to element's scope: $.payload.student
      • Text has an interpolation reference: ${source.name}. This mapping is going to retrieve the name field from the element's source $.student.
      • All of <Name> children's scope would point to $.payload.student.
    • <Course> element:
      • *scope value is inherited from <Student>: $.payload.student
      • *source is explicitly set to: $.courses
      • Because <Course>'s source points to an array, the element will be repeated for all courses contained in the list.
      • Text has an interpolation reference: ${source}, which points to each $.courses element.
      • All of <Course> children's scope would point to $.payload.student.courses.
  • <Transaction> element:
    • Rendering of this element happens right after the last message is processed due to its preceding sibling's *payloadLoop directive.
    • *scope value is explicitly set to: $.header. This element's scope was supposed to inherit <Student>'s source, but it got overridden.
    • *source value is defaulted to element's scope: $.header
    • Text has an interpolation reference: ${source.transactionId}. This mapping is going to retrieve the transactionId field from the element's source $.header.
    • All of <Transaction> children's scope would point to $.header.

About XML Paths

This fitting utilizes XML paths for definitions and messageForEach configuration. Even though they may look like XPath, their only similarity is that forward slash (/) is used to separate nodes. Follow these rules to create a successful path:

  • Paths are case sensitive, element and attribute nodes need to match the case in which they are used within the XML.
  • Always use the full node name when building the path, even when it has a namespace prefix.
  • Attribute nodes need to be prefixed with the at (@) symbol.
  • Element content such as text or CDATA is matched by the pseudo node :text.
  • Path matching is always relative. To ensure the highest level of specificity a full path must be configured.

Example

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<Root xmlns="http://ellucian.com/some-ns" xmlns:t="http://tempuri.org/">
  <Student name="John Smith" age="33">
    <Course id="1">Spanish - 101</Course>
    <Course id="2">English - 101</Course>
  </Student>
  <Course name="English" code="101">
    <Session id="1" days="MWF" time="1:00PM" />
    <Session id="2" days="MWF" time="3:00PM" />
  </Course>
</Root>

The following paths are supported:

  • Root/Student/Course - Maps only Course element nodes in Root/Student elements.
  • Course - Maps Course element nodes in Root/Student and the ones inside the Root element as well.
  • Root/Student/Course/@id - Maps the id attribute node of Root/Student/Course elements.
  • Course/@id - Maps the id attribute node of all Course elements within the XML.
  • @id - Maps the id attribute node of any XML element that should contain it.
  • Root/Student/Course/:text - Maps the Root/Student/Course element's escaped/non-escaped content node.
  • Course/:text - Maps the escaped/non-escaped content of all Course element nodes within the XML.
  • :text - Maps the escaped/non-escaped content of any element node within the XML.

Common errors to avoid

Remember that the XML paths implemented in this fitting are not, and were not meant to mimic, XPath. Avoid the following:

  • Prefixing paths with /, //, ., or ... It is not supported. The fitting will automatically remove these prefixes from paths that have them.
  • Adding filtering predicates. Any paths containing predicates will be ignored. A predicate is the square bracket section on the following XPath: /Root/Student/Course[@id='1']
  • Adding asterisk (*) wildcard for flexible matching. It is not supported.

It is easier to set date values using JavaScript than using the date picker in the Pipeline Settings user interface, because the date picker sets the time zone to the local time zone, and most database column values do not have a timestamp.

Example of setting the date and time using the JavaScript Transform fitting:

function transform (message, context) {
  // datetime in ISO 8601 format without timezone
  message.header.date_param = new Date('2024-01-08T15:18:05.000Z');
  return message;
}

Passing null values to parameters

Database null values can be passed to parameters with some limitations.

Passing null values through the context is limited to string parameters:

  • To pass a null to a string parameter, enter the value "null" (without double quotes).
  • To pass an empty string, enter two single quotes ('').

Null values can be passed to parameters using the JavaScript Transform fitting to set values in the message header and payload. Null values must be passed as an object that has the data type as the key. For example: {'string':null}.

Examples of how to pass null values using the JavaScript Transform fitting:

function transform (message, context) {
