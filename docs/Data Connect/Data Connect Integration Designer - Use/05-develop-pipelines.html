Develop pipelines

Several concepts apply to both Integration Pipelines and Serverless APIs.

Packages

A package, also known as an integration package, logically groups one or more pipelines. The package can also include other artifacts, such as transform functions. The Designer provides a seamless workflow to create and maintain integration packages.

While only a name is required, having a brief package description helps identify its purpose. it is recommended that all pipelines contained in a package share a common use-case scenario, or purpose.

Pipelines

A pipeline is a collection of sequential steps called segments. By properly organizing and configuring each segment, a myriad of simple and complex tasks can be achieved. Each segment in a pipeline is an instance of a fitting precisely configured to perform a specific task.

Like packages, pipelines are internally managed as versioned JSON documents. The pipeline Designer provides simple drag-and-drop user interface to effectively build pipelines without any of the JSON configuration complexities.

Example of a pipeline created with the Designer and exported

{
  "name": "extractDataFromServerA",
  "pipeline": [
    "getApplicants",
    "forEachApplicant",
    "getApplicantChoices",
    "mergeChoicesWithApplicant"
  ],
  "segments": {
    "getApplicants": {
      "class": "ethosProxyGet",
      "config": { "resource": "applicants", "acceptVersions": ["1"] }
    },
    "forEachApplicant": {
      "class": "forEach"
    },
    "getApplicantChoices": {
      "class": "ethosProxyGetFilter",
      "config": {
        "resource": "applicant-choices",
        "acceptVersions": ["1"],
        "filter": "?applicant={{applicant.id}}"
      }
    },
    "mergeChoicesWithApplicant": {
      "class": "JavaScriptTransform",
      "config": { "artifactName": "mergeData" }
    }
  }
}

Fittings and segments

The relationship between fittings and segments is tightly coupled.

A pipeline contains a set of segments and each defines and configures fitting execution, thus one cannot execute without the other. It is important to know the differences between fittings and segments.

Fittings

Fittings are basic building blocks capable of performing functions. They are configured with segments.

Each fitting has a very specific purpose. Fittings are classified into three main types:

  • Sources - enable the pipeline to fetch data from internal and external resources.
  • Transformations - allow for data to be changed or acted upon.
  • Destinations - enable the pipeline to send data to internal and external resources.

Most fittings provide a configuration setting to fine-tune their execution logic, making them highly customizable and versatile. Their execution logic gets triggered as soon as a message is received. And while many fittings will produce another message in return, that is not the case with some Destination types.

Among many other things, fittings can be used to:

  • Consume Ethos resources
  • Parse and format JSON, XML, fixed-width, and delimited files
  • Request generic HTTP resources
  • Transform data

A list of currently supported fittings can be found in the Available fittings documentation.

Segments

Segments are instances of fittings configured to perform a specific task. Every segment has three base configuration settings: name, description, and execution condition.

Field Description Required
Name Segment name. The Designer will automatically set it to the fitting name, this can be changed to something more appropriate with no negative consequences. Yes
Description Self-documenting field that describes the purpose of the segment. No
Execution Condition Provides a way to conditionally execute the segment based on a defined reference from a context field, message header, or message payload. Evaluated at run-time, the resulting value must be of type boolean (true or false). When true the segment will be executed, otherwise it will be skipped. No

Some fittings will provide additional configuration fields, in addition to name, description, and execution condition. Additional configurations will be explained in the Available fittings documentation.

Messages

Data moves through a pipeline using messages. A message is an envelope composed of two main parts: a header and a payload.

The header is an object structure designed to contain metadata, and is mainly used for informational purposes. Some fittings will automatically add header fields to report certain execution aspects. These headers are useful when debugging a pipeline. The header can also be leveraged as a vehicle for auxiliary data storage by using the JavascriptTransform fitting. However, header persistence is not guaranteed. Some fittings will pluck the header out of the message, or even reset it, making it a volatile aspect of a message.

The payload, on the other hand, is the container that transports the data being processed and transformed by the pipeline. A payload can contain data of the following types:

Type Description Example
string Plain and simple text value. "Hello, my name is John."
array List of values. Each value in the list can be of type string, number, boolean (true or false flags), object, or another array. ["Foo", "Bar", "Baz"]
object Complex structure consisting of key and value pairs where key is the name of a property, and the value can be of type string, number, boolean (true or false flags), array, or another object. { first: "John", last: "Smith", age: 43, married: true }
buffer Used to represent a continuous sequence of text characters, mainly used when streaming data from one segment to another. N/A

The payload content can (and will) change as data moves from one segment to the other. It is also important to be aware of what type of payload a fitting expects, and what type of payload it will return. For instance, the DelimitedFormatter fitting accepts string payloads, and produces object payloads. This input or output criteria is very important when connecting one segment with another.

There are some exceptional fittings that don't use messages to transport data, learn about these in the Available fittings documentation.

Pipeline parameters and context

Even though messages are used to transport data from one segment to another, they are dynamic by nature — their values will inevitably change as the pipeline progresses. Use message data references on a segment configuration only when it is certain data will exist within the header or payload.

Pipeline parameters and the context can be used for a more consistent source of information across all segments.

Parameters

Parameters are values that can be defined by the user before pipeline execution.

For example, consider a pipeline built to extract and process data for students of a certain year. The year can be hard-coded right into the pipeline's configuration, but it would make for a very rigid one, limited to that very specific year. Instead, a parameter can be defined to hold the year and be used within the pipeline's logic. The pipeline is then flexible enough to be used for any year.

Parameters are optional, a pipeline can declare one or more, or no parameters at all.

The pipeline Designer provides an easy way to add new parameters. Clicking the drop-down menu aside the pipeline name and then selecting Edit Pipeline Settings opens the Pipeline Settings panel. With the Pipeline Parameters tab selected, existing parameters can be updated or deleted, and new parameters can be added by clicking the + PARAMETER button.

The only required field for a parameter declaration is its Name, but a wide array of options are available for a deeper parameter customization:

All pipeline execution forms present the operational user with a section where parameter values can be entered. After the pipeline is executed, all parameter values are transferred to the context.

Persistent parameters

To make a parameter available for all jobs after you create or edit it, click the This parameter will be persisted across all jobs. It can be assigned with the "Setup" permission check box.

After a job is created or edited with persistent parameters, you will need to save the pipeline and publish a new version. Because previously-created jobs will still have the sensitive values visible, Ellucian recommends that after you successfully create all the new jobs, you delete your previous jobs, so that users are not able to go in and view the sensitive values you want hidden, such as the API key. The final user requires Experience Setup permissions to set up the parameter.

The pipeline can then be published. When you publish, the system will force you to update to a new version.

After publishing, the values can be assigned on the Integration Packages card, by selecting the pipeline and navigating to the Pipeline parameters tab. To access this page, the user requires the Setup permissions, in addition to either View or Manage permissions for the parent package of the pipeline.

When parameters are also marked as sensitive, after they are saved and the user navigates back to the page, they can no longer see that value. Only String, Number or Array parameters can be marked as persistent and sensitive.

Sensitive parameters

When a value is flagged as Sensitive, it is masked in the user interface and in diagnostic logs.

Parameters marked as Sensitive cannot have default values.

The types of values that should be flagged as sensitive include API keys, SFTP passwords or private keys, OAuth Client ID, and Secret values for third party OAuth endpoints.

About reserved parameter names

Any parameter that starts with double underscore (__) is deemed reserved and may not be declared as a pipeline parameter.

The following parameters (entries in pipeline context) are automatically populated by the framework:

  • __runId - Unique identifier for the current pipeline execution. Always set.
  • __tenantId - GUID of the tenant for which the pipeline is executing. Always set.
  • __lastRunCreated - The date and time of the last run of the current pipeline was initialized. Not guaranteed to be set.
  • __lastSuccessfulRunCreated - The date and time of the last run of the current pipeline was successfully completed. Not guaranteed to be set.
  • __pipelineName - The name of the pipeline being executed. Always set.
  • __user - User object. Only set when at least one user field is included.
  • id - Set to the Ethos Person ID of the end user, if available.
  • __region - AWS region.
  • __stage - Indicates if is Dev, Test or Prod.
  • __regionTld - This changes depending on the region, Example: .com for usa or .au for Australia.

Legacy parameters names runId, tenantId, lastRunCreated, and lastSuccessfulRunCreated are still supported for backwards compatibility. Ellucian recommends use of the double underscore (__) convention to invoke reserved parameters.

Special reserved parameters

The following parameters can be set by the pipeline logic, allowing the modification of a pipeline result.

  • __httpStatusCode (number) - If set, when invoking an API Pipeline, the value will be used as the HTTP Status code response.
  • __httpStatusMessage (string|object|number) - If set, when invoking an API Pipeline, the value will be used as the HTTP Status code message.

See: Return custom HTTP status.

Context

The context is a centralized data repository accessible to all segments. As soon as a pipeline job is started, all parameter values are made available through the context. The context can also be leveraged by pipeline creators; the AddToContext and JavaScriptTransform fittings provide a convenient interface to create segments that extend the context with new fields. When a new field is added to the context, it is automatically accessible to all segments in the pipeline.

The only caveat when using the context is that, after a field is added, its value cannot be updated or deleted.

Note: Context fields are immutable. This feature is meant to maintain the integrity of input parameters (and other internal fields) across the pipeline execution lifetime.

Be aware that context might not be shared during distributed execution of pipelines. See Integration pipelines for more information.

Crosswalks

Crosswalks are powerful dictionaries you can tailor per tenant, allowing one pipeline to generate different outputs.

For example, "Client A wants to convert a code 'ABC' to 'BCD' and client B wants to convert the same code to 'XYZ'," is a perfect fit for crosswalks, as it allows different clients to specify different outputs.

JavaScript transform functions

JavaScript (JS) Transform Functions are a way to handle data in a custom manner, allowing you to interact with messages and the pipeline’s context to transform any data into a desired output.

A JS Transform Function is used by the JavaScriptTransform fitting with the option to write an inline function in the Designer, that is available only when that fitting is being executed, or referencing an Externalize JavaScript transform functions JS file which is available through the whole lifecycle of a pipeline. Externalized JS Transform Functions, can be referenced in any amount of pipelines within the same integration package.

The function must be named transform and it must accept at least one parameter, which is the message. It can also accept a second parameter that will hold the pipeline’s context. Values may be obtained from the pipeline context using context.get('key'). New values can also be added to the context from within a transform function by using the context.set function, which accepts a key and a value as parameters.

In addition, the JS Transform Function should always end with a return statement. The returned value will be pushed forward to the next pipeline segment. However, returning a message is not strictly required.

If the function throws an exception (or external conditions throw an exception, for example an execution timeout) and a stopOnError flag has been configured inside the JavaScriptTransform fitting to be true, any further messages will be dropped, effectively stopping the pipeline.

Here is an example of a JavaScript Transform Function:

function transform (message, context) {
  // Transform logic here
  return message;
}

It is important to note that a JS Transform Function is executed in a sandbox, and may not require or import any modules.

Pipeline execution lifecycle

Whether they are scheduled or ad-hoc, when a pipeline is executed its lifecycle depends entirely on messages flowing between segments. As soon as message emission stops, pipeline execution ends.

Starting

By default, an empty message is automatically fed into the first segment to jump-start the pipeline execution. It is good practice to retrieve (or generate) data at the beginning of the pipeline so that it is processed along the way.

Source fittings are particularly useful to retrieve data from Ethos, SFTP, or the built-in file repository among other sources. These fittings will accept an incoming message, and either extend or replace its data before forwarding a message to the next segment. Other source fittings will stream data through multiple messages, easing the transmission burden of big data loads. Refer to the Available fittings documentation for more details.

Message processing

When a pipeline is in progress, segments sequentially receive and emit messages until all messages have been processed. Even though the pipeline starts with just one message, some fittings are designed to emit one or more messages.

As long as there is a message in transit, each segment in the pipeline sequence gets an opportunity to execute its underlying logic.

Note: The only way to conditionally include (or exclude) a segment from the execution chain is by configuring its Execute Condition. Execute conditions are references that can point to context, message header, or message payload values. When specified, only if the reference evaluates to true the segment will be executed; otherwise, the segment will be skipped and the message forwarded to the next segment in line (if any).

Ending

A pipeline execution ends when one of the following events happen:

  • Last message reaches the end of the pipeline or endpoint segment.
  • Exceptions thrown by JavascriptTransform segments.

It is good practice to save transformed data on or before the end of the pipeline. Destination fittings are particularly useful to send data to Ethos, SFTP, or the built-in file repository among other destinations. Be aware that most destination fittings will produce endpoint segments. Refer to the Available fittings documentation for more details.

When the very last message is processed by the last pipeline segment, the execution job will naturally reach its end. Endpoint segments, on the other hand, can create a premature end even when located by mid-pipeline; effectively stopping a message transmission before reaching the last segment.

About endpoint segments

The word endpoint is used to describe a segment that receives and processes a message, but will not emit any. Consequently, any following segments are not executed. Most destination fittings will produce endpoint segments, while some can be configured to avoid this default behavior.

An exception, in most cases, is an unexpected situation found within a segment's logic for a given message. These exceptions get reported for future troubleshooting but the pipeline continues. There is also the possibility of using the JavascriptTransform fitting to configure a segment that can voluntarily raise an exception to completely halt the pipeline execution; any current or pending messages will not be processed.
