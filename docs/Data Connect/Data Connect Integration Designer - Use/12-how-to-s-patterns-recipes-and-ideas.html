How-to's, Patterns, Recipes, and Ideas

Provides information about pipeline errors.

Error handling on Pipelines

During the design phase, any errors that arise during pipeline execution are reported immediately as part of the test runner pop up. This contrasts with a published pipeline, where the error status is reported and then you can click on Errors to jump to the Errors tab.
  • An error during design phase: If a pipeline throws an error during testing in design phase, an Errors tab will appear next to Payloads tab in the Test Pipeline dialog.
  • An error during a job run phase:
    • The pipeline runs as scheduled, but fails. The error is reported in the job status page and in the details.
    • You can click on View Errors, for a specific job to display the Errors Report tab, already setup to filter by Job Run ID (also known as Correlation ID).
    • The more details button on the far right can be used to view more information about the error.

Error patterns

Some fittings have specific configuration for errors. For example, they can store the error from a request to be processed later or they can stop the pipeline execution altogether. Refer to each fitting documentation for further detail. Unless specified, an error will stop the pipeline for the given message, not the whole workflow.

The following are usage ideas.

Save error for later processing

This segment posts information to persons and stores data in errors:
"Ethos Proxy Post": {
  "class": "ethosProxyPost",
  "config": {
    "resource": "academic-levels",
    "contentVersion": "6",
    "acceptVersion": "6",
    "errorPath": "errors"
  }
}
This segment evaluates if the POST call returned errors and provides appropriate error messages by adding a new property to the original payload:
"JavaScript Transform": {
  "class": "JavaScriptTransform",
  "config": {
    "pushUndefined": true,
    "stopOnError": false,
    "code": "function transform (message, context) {\n  if(message.errors.code == \"key_already_exists\"){\n    message.payload.errorMessage =\"Key already exists\"\n  }\n  \n  if(message.errors.code == \"invalid_level\"){\n    message.payload.errorMessage =\"The level is invalid, check dependencies\"\n  }\n  \n  return message;\n}\n"
  }
}

Stop On Error condition with JavaScript transform

This segment evaluates a message and then stops pipeline execution altogether by throwing an exception. Any new messages are dropped, effectively stopping the pipeline. If the pipeline has been split into phases for parallel processing, this might not stop the pipeline, any such evaluation is done on the fan-in portion of the pipeline. Refer to the performance section for more information on parallel processing.

Access an error response HTTP status

Given a segment that performs an HTTP request (GET, POST, PUT, etc), any error that arises is saved to the defined Error Path field. for this example, we will use errors. An error will also report an "Error", which will mark the pipeline as "Failed". On error, the following payload is returned:

{
  "payload": {
    "errors": {
      "code": 404,
      "body": {
        "statusCode": 404,
        "description": "Not Found"
      }
    }
  }
}

Additional logic can check for the status using the payload.errors.code property.

Common patterns

The following are common patterns to address common problems.

Concurrency

  • Pipeline doesn't use forEach- how can I change it?:
    • Apply the reducer fitting, then add forEach. For example, if the pipeline is reading 1000 person IDs from a file, and then fetching a record from Ethos for each person.
    • Sample:
      File Reader → Line Parser → Ethos Proxy Get
      Can be changed to this to add parallelism:
      File Reader → Line Parser → Reducer → forEach → Ethos Proxy Get
  • For a phase to run in parallel, it can only use the following fittings:
    • Add to Context
    • Ethos Proxy fittings
    • Ethos GraphQL
    • JavaScript Transform
    • JSON Parser
    • Merge
    • Object Mapper
    • File Attributes
    • SFTP List
    • Stringify
  • Context vs. Message Header:
    • The Context use case is to store information used repeatedly and that cannot be overwritten, for example, school codes, general codes, etc.
    • The Message header is intended to store information pertaining to the message, for example, calculated student codes, person information, etc.
    • Here is an example workflow of "Add to context":
      EthosProxyGet.- Retrieve current Term → AddToContext.- Save Term to Context → EthosProxyGetArray.- Retrieve Persons → ObjectMapper.- Uses Term for all Persons → ...
    • An example of a workflow using header:
      EthosProxyGetArray.- Retrieve Persons → ForEach → EthosProxyGet.- Retrieve Persons address. Target: payload.header.zipCode = address.zipCode → ObjectMapper.- Uses Payload + header → ...
  • Consecutive loops using intermediate files:
    • The pipeline might need to loop through the same payload over and over. For example, a pipeline might need to create aggregate data from persons and addresses, update some data, write a report, create a CSV, followed by creating an XML, etc. One common problem is that writing to a file outputs data about the result file, and the original message data is lost. Instead of calling the API again (and any intermediate data to create the payload) the pattern is to write the payload to an intermediate file, then reading that file repeatedly, effectively caching the work done.
    • The following example shows how the data is created, stored in a file, and then read two times: one time to post data for update and a second time to create a report. More calls can be chained by using the same read-then-apply pattern.
      EthosProxyGetArray.- Retrieve Persons → ForEach → EthosProxyGet.- Retrieve Persons address. Target - payload.header.zipCode = address.zipCode → ObjectMapper.- Uses Payload + header → Stringify → s3Sink.- Creates an intermediate file that can be read multiple times. Will write a file to {job run id}/filename.json → s3Accessor.- "key": "{pipelineName}/{{context.runId}}/filename.json" → EthosProxyPost.- Update Persons → s3Accessor.- "key": "{pipelineName}/{{context.runId}}/filename.json" → s3Sink.- Updates Persons Report → ...

Externalize JavaScript transform functions

A JS Transform function can also be externalized so it can be referenced any time in a pipeline for any amount of times without having to rewrite the function every time you want to use it.

Even better, externalizing a function can make it available to use in any pipeline within a specific pipeline. See Develop pipelines.

Previously, Develop pipelines: JavaScript Transform Functions were shown for error handling at an inline level, meaning they are written in the fitting configuration and only available when that fitting is executed.

Additionally, externalized JS Transform Functions can be versioned, so bug fixes or additional logic can be introduced with ease.

Create a JavaScript transform function draft

In order to externalize a function, you must first create a draft. You can update and test the drafts within the Designer.

About this task

A pipeline draft will not be published if it references a function draft rather than a published function.

Procedure

  1. To create a transform function draft, click on an existing package inside the Integration Designer screen. Then click on the Transform Functions tab, and then the + TRANSFORM FUNCTION button on the right side of the screen.
  2. Enter a Transform Function to have a globally unique name and a valid syntax. After you complete these fields, click the SAVE button to create a draft.
  3. To test the Transform Function draft in the Designer, add a JavaScriptTransform fitting and select an Artifact Name in the configuration.
    This drop-down shows all available Transform Functions within the Integration Package; including drafts and published functions. In this example, the Draft tag is added. The fitting configuration also displays the function’s content but it will not allow edits.

Edit an existing JavaScript transform function draft

Transform function drafts can be edited before publishing and this can be done any amount of times.

Procedure

  1. To edit a draft, click on the ellipsis belonging to the draft you want to edit and then select the Edit option from the menu.
  2. This will prompt a dialog where you can update the Transform Function. To change the name, Ellucian recommends deleting the draft and creating a new one. After making the changes, click SAVE.

Delete a JavaScript transform function draft

A transform function can be deleted as long as it is not currently shared or is in draft state.

Procedure

  1. To delete a function, open the Actions menu button and select the Delete option.
  2. A confirmation dialog displays. Click the DELETE button.
  3. After the function is deleted, update all references to this function in the pipelines that currently use it. Otherwise, a pipeline test or run can result in unexpected behavior or error out.

Publish a JavaScript transform function

The publishing process of a transform function is similar to the one of a pipeline, with the only difference that publishing a transform function is done directly from the Integration Designer main screen.

Procedure

  1. Open the Actions menu button and select the Publish option.
  2. Optional: In the dialog, versioning is left to the user’s discretion. The next Patch and Minor versions options are displayed in addition to the next Major version. Versioning works the same as in pipelines. Patch and minor versions of a function are consolidated and only the latest is shown in the Integration Designer Transform Function table, while the major version will be treated as a completely different Transform Function, hence showing as another row in the Integration Designer Transform Function table.
  3. After you select a version, click the PUBLISH button.
  4. You can now test the transform function in a pipeline and it is available at an integration package level.
    There is a Published tag next to the function’s name and the option to select a fixed Artifact Version is enabled.

Considerations when using an externalized JavaScript transform function

Describes considerations when using an externalized JavaScript Transform Function.

Some considerations to take into account when using an externalized Transform Function are that externalized-based scripts are cached for faster repeated execution and the retrieval only happens one time per pipeline execution. Knowing that, when choosing to use the latest version of a Transform Function inside the JavaScriptTransform fitting configuration, it should be used carefully because updating a Transform Function and publishing a new version of it can result in undesirable behavior ad hoc for ongoing Pipeline Jobs executions that use the configuration.

In addition, publishing a pipeline that uses an external Transform Function does not automatically publish the function. The Transform Function needs to be published separately.
