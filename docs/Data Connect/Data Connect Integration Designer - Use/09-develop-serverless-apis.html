Develop serverless APIs

After you create a serverless API draft, you can optionally define input or output schemas.

Create a serverless API

The following documentation provides step-by-step instructions on how to create a serverless API.

Procedure

  1. Select the package you want to create the pipeline on, and click on the plus(+) button.
    A dialog box displays with several fields to configure the pipeline.
  2. By default, the Integration Pipeline Type is selected. In order to create a serverless API, select API from the Pipeline Type drop-down.
  3. Enter a unique name for your pipeline.
    Note: A warning displays if the same name already exists in the system. Because the pipeline will work as an API resource, it should not contain spaces.
  4. Choose the appropriate HTTP method (GET, POST, PUT, DELETE) based on the actions you plan to perform in your pipeline.
    Note: GET requests cannot receive a body.
  5. Select the desired authentication type (User token or Ethos token) based on your pipeline's authentication requirements.
    1. Select User token if the pipeline will be called from an Experience card.
    2. Select Ethos token if the pipeline will be called through the Ethos Integration proxy by an external application.
    3. See Authorization for more details on authorization requirements and setup.
  6. Optional: You can provide a description for the pipeline to clarify the purpose or functionality of the pipeline.
  7. Click Save to create a draft of the pipeline within the package.
    You can now proceed with further configurations, such as defining input and output schema and building the pipeline using the fittings and pipeline parameters.

Configure serverless API behavior

After creating the Serverless API draft, optional input or output schemas can be defined.

About this task

Defining schema can ensure an appropriate validation is executed against the received input or generated output. See the section Create schemas for a detailed guide on schemas.

Procedure

  1. Define Pipeline parameters.
    1. For example, parameters for an API key or an Id parameter can be defined.
    2. After it is published, the pipeline will be invocable with an HTTP request. The HTTP request parameters are bound to the pipeline parameters.
  2. Add appropriate fittings to fulfill your use case.
    1. For example, add an Ethos Proxy Get to retrieve information from an Ethos resource.
    2. You can use values from the parameters, payload, or context to refine the request.
    See Available fittings documentation for more information.
  3. Configure the output as expected. See About creating a response for details.
    1. The response must be a single message.
    2. A custom HTTP status can also be defined. See: Return custom HTTP status.

Import an existing pipeline

It is possible to import an existing pipeline JSON file into the Designer. However, the pipeline must match the API type. If an attempt is made to import an integration pipeline when working on a serverless API the import will fail.

Test the pipeline draft before publishing

The Test button can be used to test the pipeline logic. However, it will not fully simulate a HTTP API call.

About this task

These are the differences when testing with the Test dialog:
  • Input and output schema validation is not checked.
  • No value will be injected in context._user (See: Obtain the current user ID value)
  • A value should be hard set, as needed for testing.
  • If a custom HTTP code or message were used, the test response will include those overridden values in the result shown in the test window.

    After it is published, a Platform Component is created in Ethos Integration.
  2. To confirm a Platform Component was created, navigate to Ethos Integration and select the Platform Components tab
  3. Select the Data Connect card.
    The published serverless API name displays under the Owned Resources tab.
  4. Confirm the application for which the API key will be used is listed under the Platform Components- Data Connect- Application Access list.
    Before executing the serverless API, appropriate authorization needs to be set up:
    • If the pipeline was configured to require a 'User Token':
      • Permissions are automatically pushed to Experience Permissions.
      • The final user's role will need to be assigned the 'Execute' action for the specific pipeline.
      • See: Authorization for more details.
    • If the pipeline was configured to require an 'Ethos token': An appropriate tag must be added. See: Authorization

    Then, the pipeline can be executed.

Example

The following cUrl will execute a POST to the latest serverless API named 'exampleServerlessAPI':

curl --location 'https://integrate.elluciancloud.com/api/exampleServerlessAPI?year=2023' 
--header 'Content-Type: application/json' --header 'Accept: application/json' --header 'Authorization: Bearer {{validTokenValue}}' --data '{"id": "12345"}'

The following cUrl will execute a GET to the execute version 1.0.3 of a serverless API named 'anotherExample':

curl --location --request GET 'https://integrate.elluciancloud.com/api/anotherExample' --header 'Content-Type: application/json' --header 'Accept: application/vnd.hedtech.integration.v1.0.3+json' --header 'Authorization: Bearer {{validTokenValue}}'

Note that GET requests cannot receive a body.

The examples above can be used as a basis to execute serverless APIs from third party applications. The URL might change depending on the desired execution region.

See Execute serverless APIs from Experience extensions for a guide to executing the serverless API from Experience.

About pipeline versioning

Pipelines are published using semantic versioning.

See Pipeline versioning guidelines.

See API Behaviors.

When executing pipelines, the 'accept' header will indicate which version of the pipeline to execute, or the value 'application/json' can be used to retrieve the latest version of the pipeline.

Using the latest version is recommended during development trials, to ensure an up-to-date pipeline definition is used. For production usage, at least a major version should be specified, as pipeline definitions are cached to speed up the execution process.

At this time, it's not possible to publish 'beta' versions.

About the input message

The payload of the HTTP request, if any, will be passed in the 'payload' property of the initial message.

Examples

A payload in the following form will be wrapped into a Data Connect message:

{"id":12345}

will be wrapped in a Data Connect message and passed as:

{
   header:{}
   payload:{"id":12345}
}

Note: in the Test dialog, the first simple form can be used. If the payload is a valid Data Connect message, it will be passed as is:

{
   "header": { "initial": 1 },
   "payload": { "data": "example data"}
}

If no payload is received, an empty message will be pushed.

{
   header: { }
   payload: { }
}

If an Array of data is passed, it will be pushed as different messages.

About creating a response

When the pipeline ends, the message payload will be used as the Serverless API result.

If more than one message is emitted from the pipeline, only the payload from the first message is used. If needed, reduce all messages and save them into an array.

Example: The pipeline produces a single, single-object response

Pipeline result:

{ "data": "example data"}

Result when invoked:

{ "data": "example data"}

Example: The pipeline produces an array response

Pipeline result:

[{ "data": "1"}]

Result when invoked:

{
    "data": "1"
}

Incorrect Example: The pipeline produces several messages

In this scenario, only the first result will be returned. A reducer can be used to collect all messages into an array to return. Pipeline result:

[{ "data": "1"}, { "data": "2"}]

Result when invoked:

{
    "data": "1"
}

Validations

The execution endpoint throws exceptions if certain validations are not met.

The following table illustrates known errors and causes.

Error Cause
404 The pipeline does not exist.
406 The accept header was not defined or the format is not valid.
406 The specified pipeline version does not exist.
405 HTTP Verb does not match the defined verb in the pipeline
403 The provided token is not linked to the appropriate permissions. See Authorization for more details.
401 The token was not sent, the token is not authorized, or the token does not match the specified token type in the pipeline.
415 The input body does not match the defined input schema.
500 The output message does not match the defined input schema.
400 Pipeline configuration error. Parameters might be missing, or be in the wrong format.
500 Pipeline execution error. Usually, the resulting payload will contain a list of errors.

Obtain the current user ID value

A serverless API with an authentication type of 'User token' will inject a property __user.id in the context, with the value being the Ethos Person GUID for the current Experience user.

About this task

This property can be used for different uses cases, for example:

  • Used to fetch data for the current Experience user without requiring the ID to be sent separately.
  • Used for authorization confirmation, for example, that only the current user data is retrieved, or to validate that the current user can access certain data.
  • Call BPAPIs to retrieve a Banner ID as needed.

For example: The following fitting can be used to retrieve the Ethos person that is currently logged into Experience:

"Ethos Proxy Get": {
     "class": "ethosProxyGet",
     "config": {
       "resource": "persons",
       "acceptVersions": [
         "12"
       ],
       "idFromContext": "__user.id",
       "cache": false,
       "ignoreErrors": false,
       "apiKey": "ethosApiKey"
     }
   }

The value can be retrieved in a JST fitting by using

context.get('__user').id

Authorization

Grant the permission that allows users to invoke a serverless API that authorizes with a Ethos token or a user (OAuth) token.

Authentication type Ethos token configuration

The serverless API package should be added as an application tag.

Procedure

  1. Navigate to Ethos Integration, then click the Applications tab and select the application that will invoke the serverless API.
    For example, navigate to the Banner Integration application.
  2. Click the Tags sub-tab, then click the Add Tag button. Verify the tag does not already exist.
  3. Enter integration-package as a tag name. The name should match exactly.
  4. As a value, enter the camel-cased version of your displayed package name. This is the Package name and not the serverless API name.
    Examples:
    • A package named 'example' should be added as example (No change).
    • A package named 'Example' should be added as example (The first letter changed case).
    • A package named 'example one' would be added as exampleOne.
    • A package named 'example may 31' would be added as exampleMay31.
  5. If you need more than one integration package to be authorized, add them in the value field separated by a , (comma) with NO spaces between packages.
    Example value: 'example,otherExample,universityPackage'
  6. Click Save. The pipeline is ready to be invoked.
    When executing the serverless API, the presence of a tag with the serverless API's package name is validated. If not present, a 403 HTTP error is returned.
  7. Add the application configured with the integration-package tag to the Application Access list under Platform Components > Data Connect > Application Access.

Authentication type User token configuration

Grant the permission that allows users to invoke a Serverless API that authorizes with a User (OAuth) token.

Before you begin

Appropriate user roles should exist in Ellucian Experience.

About this task

Assign permissions to the specific serverless API.

Procedure

  1. Access Ellucian Experience Setup. In the Ellucian Customer Center, click Tools and then select the desired Experience Setup instance under the Experience category:
    1. Click Experience Setup (Test) to access the Test instance of Experience Setup.
    2. Click Experience Setup to access the Production instance of Experience Setup.
  2. In Experience Setup, in the Environments drop-down, select the desired Ethos environment (for example, Test or Production).
  3. In the Experience Setup header, click Permissions and then select DATA-CONNECT.
  4. In the left pane, click the APIs section. Expanding the section displays a list of packages that contain serverless APIs.
  5. Select the package and the exact serverless API under it. Assign execute permissions to the Role or Individual.
    1. For more information about Experience permissions, and the detailed procedure for granting permissions, see Experience application permissions.
    2. Permission needs to be assigned at the individual pipeline level and not at the package level. The UI allows assigning permissions at the package level, but permissions must be assigned per each individual serverless API.
  6. Click Save.
    The pipeline should be callable as an API with the user token that has the appropriate role.
  7. Instruct any user whose permissions have changed to log out of Experience and log back in. Experience permissions are cached. Logging out and back in refreshes the cache and ensures that the user has the granted permissions within Experience.

Create schemas

There are two types of schemas in a Serverless API: Input and Output schemas.

Both follow the same creation process so this guide can be used in either case. Input and output schemas are optional properties within the API Definition object of a pipeline so if not configured, they will not be included in the pipeline JSON object.

Define Input and Output Schemas

When a Serverless API is loaded into the Designer page, it shows the Input Schema and Output Schema tabs. Click on the desired schema to start working with it. The schema definitions can be created, edited, and deleted as long as the Serverless API is in a Draft state. When a schema has not yet been defined the UI will display only the HTTP method and the Authorization type of the pipeline in addition to an empty state message. Any errors detected while working on a schema will be added to the error collection panel located in the top right corner of the UI next to the Test button.

Important: Any changes to the schema's properties are not saved until the pipeline draft is saved. You can do this by clicking on the Save button.

Add a property

To add a new schema property, click the + button located on the left hand panel next to Properties.

Doing so will render a form on the main content of the page with the following fields:

Property Name Required This will be used as the property key in the schema object.
Label Optional This field gets parsed to the title schema property.
Property Type Required The simple schema editor allows for Boolean, Date Time,Integer, Number, and String. The Date Time type it will get parsed to a Stringtype and append a Format property with a value of date-time.
Required Optional Indicates whether the schema property will be mandatory or not.
Description Optional Used to describe the property.

Fill in the form fields as needed by the property.

Edit a property

To edit an existing property, click on the property name, under the property list, located in the left panel. Alternatively, to edit an existing property, click the ellipsis icon and then click the Edit option in the action menu displayed.

Delete a property

To delete a property, click on the ellipsis icon located next to the property name on the left panel and then click the Delete option. Alternatively, a property can be deleted from the Summary View. Deleting a property from a schema is an action that cannot be undone, however, it will not be completely lost until the pipeline draft is saved. Reloading the browser without saving would result in the property still being displayed.

Summary View

When a schema already has properties, clicking on Summary displays a table listing all the properties and their configuration. Properties can be modified by clicking on the corresponding action button on each row. A property's form can be also displayed by clicking on the property name in this table.

Return custom HTTP status

The HTTP code and return result can be overridden to enable specific use cases.

For example: A serverless API can return an http status of 404 to indicate a record was not found, or 202 to indicate a process has been started.

By default serverless APIs will return a 200 status and the contents of last message. In case of an error, the returned status code will be 500, with the payload being an array of errors encountered.

The pipeline logic can set the following values in the context to override the returning HTTP code and the resulting content. The values can be set with a JavaScript transform or with a setContext fitting.

  • __httpStatusCode (number) - If set, on invoking an API Pipeline this value will be used as the HTTP Status code response.
  • __httpStatusMessage (string|object|number) - If set on invoking an API Pipeline this value will be used as the HTTP message.
Note: The values can be set one time. Setting the values several times either causes an error or the values are ignored altogether.

Examples

The following JavaScript function injects values to override both the http status code and the result.

function transform (message, context) {
  context.set("__httpStatusCode", 202);
  context.set("__httpStatusMessage", "Your request has been received");
  message.payload={  message:'hello'}
  return message;
}

An error status code can be specified, as well. You can take advantage of JavaScript transform Stop On Error and throw an error to stop pipeline execution altogether.

function transform (message, context) {
  context.set("__httpStatusCode", 202);
  context.set("__httpStatusMessage", "Your request has been received");
  throw new Error('Error message'); //The pipeline will use the message specified above in the response, so the error message on this line is not actually returned.
}

You can also use a setContext fitting to set the status:

   "Add To Context": {
      "class": "addToContext",
      "config": {
        "source": "$.returnCode",
        "target": "__httpStatusCode"
      }
    },

Execute serverless APIs from Experience extensions

You must execute serverless APIs from Experience extensions.

Prerequisites

  • A serverless API, that specifies User Token as the Authorization Type, should have been published or received by the 'sharing' functionality.
  • Permissions to be enabling calling the Pipeline from an Experience Extension have been set up. Permissions for the API display under Data Connect on the Permissions tab within the Experience Setup page. The user's role needs to be assigned the 'Execute' action for the specific pipeline.
  • An Extension has been created. The extension card can be modified to be able to set a Server Configuration which can be fetched later during the Serverless API. See Define Basic Configuration Parameters documentation for more details.
  • The Extension has been published and enabled to the tenant to execute the Serverless API.

Call a serverless API from a card

To call a serverless API you should use the authenticatedEthosFetch method that is provided by the useData hook from the Experience SDK. This method already injects a valid User Token to the request and an Accept header with the value of 'application/json'. A specific version cannot be sent at this time. All that is needed to do is pass down the name of the serverless API as the first and only argument for said method i.e.:

import { useData } from '@ellucian/experience-extension-utils';
const SampleCard = (props) => {
    const { authenticatedEthosFetch } = useData();
	// Could also be: 
	// const { data: { authenticatedEthosFetch } } = props;
    const [mydata, setData] = useState();

    useEffect(() => {
        fetchData();
    }, []);

    const fetchData = () => {
        authenticatedEthosFetch("name-of-your-serverless-api")
            .then((response) => response.json())
            .then((data) => {
                setData(data);
            })
			.catch((error) => {
				// do something with the error
			});
    }

// ...

Use Server Configuration Card values when calling a Serverless API

You can use Experience's Server Configuration values to store sensitive values, for example, API keys. See Define Basic Configuration Parameters documentation for more details.

It is important to note that whatever you define as a server configuration parameter, the key must match whatever Pipeline Parameters you have defined when designing the serverless API. That is, if you have set a pipeline parameter name to be ethosApiKey, you need to make sure that the same name is set as key on the server configuration object in your extension. Failing to do so would result in that value being ignored by the API execution.

Another important point is that you must include cardId explicitly as a query parameter on the request URI, otherwise, the serverless API will not attempt to get the Server Configuration from your card and continue its execution without it. You can modify the server values when configuring your extension's card in Experience UI but you have to account for two scenarios: calling the API with card configuration, and calling the API with card configuration in preview mode.

Call the API with Card Configuration

Cards within Experience Extensions have a cardId prop set by default. Sending this value as a query parameter on the request made by authenticatedEthosFetch will enable the Serverless API to fetch a Card's Server Configuration value as long as these have been already saved during the Card Configuration process. You can access the cardId prop with the useCardInfo hook provided by the Experience SDK. Here's an example:

import { useData, useCardInfo } from '@ellucian/experience-extension-utils';
const SampleCard = (props) => {
    const { authenticatedEthosFetch } = useData();
 	const { cardId } = useCardInfo();
	const [mydata, setData] = useState();

    useEffect(() => {
        fetchData();
    }, []);

    const fetchData = () => {
        authenticatedEthosFetch(`name-of-your-pipeline-api?cardId=${cardId}`)
            .then((response) => response.json())
            .then((data) => {
                setData(data);
            })
			.catch((error) => {
				// do something with the error
			});
    }

// ...

The above will result in the Serverless API using the saved card configuration values when executing.

Call the API with Card Configuration in Preview Mode

Extensions should account for the scenario in which a Card is being used in a Preview mode. This is the result of actively updating the values of the server configuration on the card configuration screen without saving. When using authenticatedEthosFetch on the experience card, the call needs to indicate that its on preview mode, so the server configuration values are retrieved from a temporary storage (these values will not be used on the non-preview mode unless they are explicitly saved on the card configuration process). To enable this behavior, the cardPrefix value of the card needs to be sent as a query parameter, alongside the cardId value on a homonymous query parameter name. All these values are made available by the useCardInfo hook provided by the Experience SDK. Here's an example:

import { useData, useCardInfo } from '@ellucian/experience-extension-utils';
const SampleCard = (props) => {
    const { authenticatedEthosFetch } = useData();
 	const { serverConfigContext: { cardPrefix }, cardId } = useCardInfo();
	const [mydata, setData] = useState();

    useEffect(() => {
        fetchData();
    }, []);

    const fetchData = () => {
        authenticatedEthosFetch(`name-of-your-pipeline-api?cardId=${cardId}&cardPrefix=${cardPrefix}`)
            .then((response) => response.json())
            .then((data) => {
                setData(data);
            })
			.catch((error) => {
				// do something with the error
			});
    }

// ...

The above will result in the serverless API using whatever temporary values from the card configuration for its execution. Combining Server Configuration Card values and Query Params when calling a Serverless API It is possible to use both server configuration card values along with query parameters when executing a serverless API. The query parameter will take precedence over any values returned by the card's configuration. This functionality can be used for testing or for sending non-sensitive values such as dates or flags. Here's an example:

import { useData, useCardInfo } from '@ellucian/experience-extension-utils';
const SampleCard = (props) => {
    const { authenticatedEthosFetch } = useData();
 	const { cardId } = useCardInfo();
	const [mydata, setData] = useState();

    useEffect(() => {
        fetchData();
    }, []);

    const fetchData = () => {
        authenticatedEthosFetch(`name-of-your-pipeline-api?cardId=${cardId}&dateOfBirth=06-07-2023`)
            .then((response) => response.json())
            .then((data) => {
                setData(data);
            })
			.catch((error) => {
				// do something with the error
			});
    }

// ...
