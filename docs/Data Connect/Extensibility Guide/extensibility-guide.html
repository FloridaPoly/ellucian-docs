Summary

Overview

Extensibility provides enhanced capabilities for customizing and extending Pre-built integrations. It is essential for building scalable, maintainable integrations that support institutional or customer-specific extensions to base-delivered functionality as organizations adopt integration pipelines to achieve their desired outcomes.

A core element of this approach is the use of sub‑pipelines, which offer an effective and modular way to introduce new features, extend existing processes, and enhance functionality without creating a bespoke project. By decomposing a main pipeline into smaller, independent components, teams can more easily manage tasks such as data preprocessing, transformation, or validation.

Each sub‑pipeline operates autonomously, making it simpler to test, debug, and upgrade individual components without impacting the broader integration. Leveraging this architecture ensures a flexible and future‑proof foundation that adapts to evolving requirements with minimal effort.

Framework Versions

While both Version 2.0 and Version 3.0 support the same foundational model—Extract, Process, Transform, Audit, Error, and Post‑Processing, Version 3.0 significantly expands capabilities, introduces new lifecycle controls, and strengthens validation and parameter behavior.

Version 2.0 formalized baseline vs. custom vs. extend modes, added structured sub‑pipelines for each phase, and unified how report, audit, and error logs are processed.

Version 3.0 builds upon that foundation with more rigorous pre‑processing (Phase 0), default parameter behavior, dynamic file‑generation rules, expanded validation logic, additional conditions for Import/Export behaviors, and new operational parameters such as Processed File Option and extended parameter defaults. V3 also improves failure‑handling clarity and introduces more flexible output destinations, including support for sending files to API endpoints rather than only SFTP/S3.

Version 3.0 enhances the framework in several major ways:

  • Phase 0 – Parameter & Input Validation: V3 introduces a formal Phase 0, validating required parameters, SFTP/S3 credentials, and university details before any extraction occurs. This improves failure isolation and prevents unnecessary downstream execution.

  • Dynamic Output Structure: Report, audit, and error logs now support dynamic, schema‑less structures where keys become headers and values become row entries. This makes custom file‑building significantly more flexible.

  • Refined Error/Audit File Generation Rules: V3 clearly differentiates file behavior across phases—error files only generate on Phase 2 record‑level issues, audit files only generate when Phase 2 runs successfully, and both support override through extended parameters (sendAuditFile, sendErrorFile).

  • Extended Parameters With Defaults and Conditions: V3 introduces default values, conditional activation rules, and new variables such as noFile, overwriteInputFileHeaders, and enhanced handling for preview scenarios.

  • Expanded Import‑Process Enhancements: New parameters—such as Processed File Option (Move/Delete/None) and Processed File Path—support life‑cycle‑based cleanup operations, additional cross‑file validation, and deletion of temporary files created during inbound processing.

  • Flexible Output Destinations: Output files may be delivered to third‑party API endpoints instead of only SFTP/S3, providing infrastructure‑agnostic delivery options.

  • Standardized Context Initialization: Context variables governing which phases run (baseline/custom/extend) are now centrally defined in the baseline validation sub‑pipeline, reducing configuration inconsistencies.

Together, these improvements make V3.0 more reliable, configurable, and operationally robust than V2.0.

Note: The first fitting in the Pre-built integration is a JavaScript fitting that establishes the audit trail and extensibility versioning. This allows you to determine the version of the extensibility release when you run the pipeline with diagnostics mode enabled. Extensibility V3.0

Summary

Extensibility V3.0 Overview

The integration workflow is organized into a series of structured phases that guide data from initial validation through final delivery and post‑processing. It begins with validating parameters and inputs to ensure the integration is properly configured, followed by extracting the required data from source systems. The data is then processed and transformed as needed, then the output file and sent to its destination. Additional phases handle auditing and error reporting to support transparency and traceability. The workflow concludes with optional post‑processing operations, allowing institutions to introduce custom logic tailored to their specific requirements.

  • Phase 0: Parameter and input validation

  • Phase 1: Extract/retrieve data

  • Phase 2: Process Data

  • Phase 3: Transform data - write the output file and send to the destination

  • Phase 4: Prepare/send Audit data to its destination

  • Phase 5: Prepare/send the Error data to its destination

  • Phase 6: Post Processing - additional operations (Custom)

Extensibility

Each Pre-built integration enables institutions to override or extend the baseline phase by supplying their own sub‑pipeline, providing greater flexibility and customization. An optional post‑processing hook offers additional extensibility. The diagram below illustrates the overall process at a high level.

Overriding an integration phase replaces the baseline Pre-built phase with institution‑specific logic (labeled Custom in the diagram). Extending a phase runs the baseline step of the phase as delivered, but also provides a hook for the institution to insert additional operations.

Following two examples to help differentiate when to use a Custom override versus when to use an Extension of a Pre-built step
  • Override - Phase 1: Extract / retrieve Data:

    Baseline behavior: Extracts student data using standard field mappings and default attribute definitions.

    Your need: Your institution uses a custom residency classification system, for example, through SIS extensibility, that cannot be derived from the baseline extract fields or logic.

    Why override?

    Because the extraction logic must pull different source fields or apply institution‑specific derivations, the entire extract step needs to be replaced with your custom implementation.

  • Extend - Phase 1: Extract / retrieve Data:

    Your addition: After the baseline extract completes, you want to enrich the output by adding elements such as:

    • assignment to institution‑specific advising groups
    • custom tags used by downstream systems
    • campus‑specific default attribute values

    Why extend?

    The baseline extract already provides the necessary core data. You simply need to append additional institution‑specific fields or apply data enrichment, so extending the step rather than replacing it is appropriate.

  • Sample Decisions
    Scenario Use… Reason
    You need the step to behave completely differently Custom Baseline logic is insufficient or incompatible
    You need to enforce unique business rules Custom Institution rules supersede baseline
    You need small additions before/after baseline Extension Baseline logic is still useful
    You need notifications, logging, enrichment, or minor transformations Extension These complement baseline logic
    You need to transform data in a new way It depends Override if replacing; extend if adding

    The Extensibility Framework requires a standardized context setup, which will be established by the sub-pipeline Ellucian-Baseline-Validation-Sub. Although the fittings of a Pre-built integrations are not visible in Data Connect Designer, this sub-pipeline is configured and executes in the pipeline, and you will see evidence of this fitting when running the pipeline in diagnostics mode.

    Fitting: JS - Baseline validation setup (Baseline)

    Context: validationParameters, valueValidationParameters, parameterValidationExists, {projectValidation}

  5. Pipeline-Specific Parameters

    Parameters used across Phases 1 to 5 are marked as non-required to allow flexibility in Custom mode—where unused parameters may be skipped.

    Additionally, each phase includes validation logic to check the presence of applicable parameters.

    Fitting: JS - Validate Baseline parameter (Baseline)

  6. Pipeline-Specific Parameters Value Validation

    Parameter values will be validated using the sub-pipeline Ellucian-{Project}-Parameters-Validation. An error will be thrown if any parameter value is not valid.

    Fitting: Sub-pipeline - Baseline Parameter User Value Validation

  7. University Name Data Extraction

    Use the installation-controls API to extract the university name for the audit file. See Documentation for more details on the API: Link

  8. Error Handling/ No record scenario in Phase 1

    If an error occurs/ no records exists for inbound during Phase 1 execution, the pipeline must terminate and return a meaningful error/audit message. No further phases should execute.

  9. Reporting, Audit, and Error Files

    Outputs for reportLog, auditLog, and errorLog in Phase 2 support dynamic structures.

    • Keys in the output object will serve as headers.

    • Corresponding values will populate the rows in the output files generated during Phases 3, 4, and 5.

    • Note: If no specific format is provided by the project, standard formats for audit and error files will be applied.

  10. Flexible Output Destination

    The output file can be delivered to a third-party API endpoint instead of relying solely on an SFTP/S3 step.

  11. Custom Sub-Pipeline Fitting Placement

    • Phase 1: Custom sub-pipeline fittings are added after the last Baseline Phase 1 fitting.

    • Phase 2: Custom fittings are positioned just before the JS - Persist header for report file (Baseline) fitting.

    • Phases 3–5: Custom sub-pipeline fittings are placed at the start of each respective phase.

  12. Change Notification / Popsel / Save List Handling

    In the case of Change Notification or Population Selection / Save List, Phase 1 should only be used to extract the population only. The processing of each population record must be performed in Phase 2 to extract records details.

    If APIs or Insights are used to extract record details in Phase 2, then the Report File, Audit File, and Error File should all be generated.

  13. Error File Generation

    The error file will only be generated if any error occurs during Phase 2 while processing individual records. Errors encountered in Phase 0 or Phase 1 will not result in an error file being created.

    Note: The extended parameter variable sendErrorFile must be set to true for the Error File to be generated.

  14. Audit File Generation

    The audit file will only be generated during Phase 2 when records are processed. After the report file is created, the audit file will be created, capturing the count of records extracted. Additionally, the audit file will be generated if explicitly required by the project.

    No audit file will be created if no data is extracted in Phase 1.

    Note: The extended parameter variable sendAuditFile must be set to true for the Error File to be generated.

  15. Report File Generation

    A report file will not be generated if no data is fetched during extraction or if all data is filtered out during processing.

Extensibility V2.0

Summary

Extensibility V2.0 Overview

At a high level, each integration project follows a structured sequence of five core steps: extracting or retrieving the required data, processing or transforming it, delivering the processed data to its intended destination, and then generating and sending both audit data and error data for tracking and troubleshooting. Each Pre-built integration offers institutions the flexibility to override baseline behavior by supplying a custom sub‑pipeline, ensuring the process can be adapted to meet unique requirements.

  1. Extract/retrieve data
  2. Process or transform data
  3. Prepare/send data to its destination
  4. Prepare/send Audit data to its destination
  5. Prepare/send the Error date to its destination

Each Pre-built integration allows users to override or extend the baseline-delivered steps by using a sub-pipeline, enhancing flexibility and customization. This can be further enhanced by the provided post-processing hook. The diagram below provides a high-level individual process overview

Overview

This page applies to Pre-built integrations supporting extract processes, using V2.0 of the extensibility framework.

  2. Pipeline-specific parameters that are not required in Phases b1 to 5 need to be added in the pipeline phase, and additional checks for these parameters need to be added.
  3. Audit File and Error File will only be prepared if we are processing records to filter out, or based on requirements

Import

Overview

The content on this page applies to Pre-built integrations supporting import processes, using V2.0 of the extensibility framework.

In case of Import Process:

  1. The Error file will only be created when an error occurs.
  2. The audit file will not always be generated when there is an error in data extraction or before data processing for an individual record; in all other cases, the audit file will be generated. If no data is fetched, the audit file must be empty, with column headers, and show 0 as the record count.
  3. If no data is fetched or left after processing, no report file will be generated.
  4. Pipeline created to read input file ({ClientAlias}-Read-Input-File-Sub) generates a file with input file data and writes it to internal DC S3 with name processedFile.txt, therefore, it should be deleted at the end of the main pipeline.
  5. Pipeline‑specific parameters that are used in Phases 1 through 5 will be optional, and the pipeline must include additional phase‑appropriate checks to validate these parameters.
