About the Ellucian Ethos Data Model

The Ellucian Ethos Data Model is a single model of all of the concepts in the entire domain of higher education.

For Ellucian Ethos Data Model-based APIs, each concept is treated as a separate entity in the model, and the same name is used by both business and technical audiences. The model is expressed in the form of JSON Schema documents that are attached to API Documentation that can be access through the API Catalog.

All Ellucian applications and third-party certified partner applications that use the Ethos Data Model-based APIs are required to support the Ellucian Ethos Data Model for system integration purposes.

It is expected that legacy systems must adapt to the Ellucian Ethos Data Model definition and provide reasonable defaults to support existing business logic. Ellucian Ethos Integration will be used to facilitate system integration using the Ellucian Ethos Data Model.

The Ellucian Ethos Data Model identity is established by specifying an ID property following the GUID implementation. A global unique identifier (GUID) is a unique reference to an Ellucian Ethos Data Model object that allows us to uniquely identify that object across the entire Higher Education domain. Ellucian Ethos Data Model definitions are generic, designed to support global requirements, and not limited by an existing Ellucian application. All Ellucian application teams along with certified partners and customers collaborate to define and validate the definition that can be supported by each application.

Semantic versioning

Ellucian applies semantic versioning to Ellucian Ethos Data Models and APIs to help clients quickly identify if a newer version of the data model and API contains a breaking change.

What is semantic versioning?

The version format is major.minor.patch where:

  • The major number identifies a breaking change.
  • The minor version identifies a compatible change that will not break the calling application.
  • The patch number is a bug or security fix.
Refer to the Semantic Versioning Specification (SemVer) Web site that describes the standard.

Version numbering for new and upated models

Ellucian introduced semantic versioning with the Q3 2018 release of the Ellucian Ethos Data Models. As of that release:
  • All new data models and APIs start as version 1.0.0
  • All updated data models and APIs with a breaking change started as version 16.0.0
  • All updated data models and APIs without a breaking change kept their existing major number but started using the minor semantic version.

    For example, if Ellucian updates version 6 of a currently supported data model and API with a non-breaking change, we will release that data model and API as version 6.1.0

Previously released data models and APIs will retain their current non-semantic version.

Breaking changes

A breaking change occurs when Ellucian must change or modify an existing API or property to accommodate changed business processes or functionality that no longer behaves as it did in the past. As a result, you must also update applications that use an API with breaking changes.

Changes not categorized as breaking changes

Ellucian continues to evolve the Ellucian Ethos Data Models by creating new data models and adding properties to existing data models to augment the capabilities of the Ethos framework. Ellucian adds new functionality to data models in a backwards compatible way. That is, Ellucian APIs can add additional properties without breaking integrations that used older versions of that API. This type of change, adding new functionality, does not represent a breaking change. The majority of changes delivered to data models fit into this category, which means most APIs reach a stable state and you will seldom need to update integrations that use those APIs.

These are examples of data model changes that do not require consuming applications to make changes to their existing code:
  • Adding a new property or object.
  • Changing a property constraint from required to optional.
  • Adding a filter or namedQuery.
  • Delivering a brand new data model.

Changes categorized as a breaking change

There are times when it is necessary to introduce a breaking change to accommodate new patterns and functionality that is incompatible with previous capabilities. Ellucian is committed to avoiding breaking changes wherever possible in the Ethos ecosystem.

Examples of breaking changes to a data model that would require consumers to also update their code include:
  • changes to a property name or format
  • change a property constraint from optional to required
  • filter or namedQuery format change
  • removal of a property or portion of an object
  • retiring of a data model
  • renaming of a data model

How do I ensure minimal disruption?

Here are some important steps to follow to ensure minimum disruption due to breaking changes:
  • Update your custom integrations to accommodate version-specific requests.
  • Plan ahead to use the latest version of the data models and APIs before the two-year deprecation time frame expires older data model and API versions.
  • Catalog the data models and properties that are critical to your Ethos client applications. Verify updates against your own list of critical properties and data models.

Deprecation

Deprecation refers to functions or elements that are in the process of being replaced by newer ones. For data models and APIs, deprecation means the previously released version of the API will continue to work and is supported for prioritized defect fixes.

The new version will not necessarily be backward compatible. Until your integration can use the new version, you should remain on the older version. When Ellucian releases an updated data model and an updated API that contains a breaking change, Ellucian will support all previous versions of the data models and APIs for a period of two years. At the end of the two-year time period, Ellucian will no longer support the old data models and APIs but will support only the new data model and API.

How will I know when a Data Model or API is deprecated?

During the two-year time period, Ellucian will identify the older data models and APIs that have a breaking change as deprecated. Ellucian is working on a way to add information to older data models and APIs that indicates their two-year deprecation time period is underway and what the cessation date is for the data model and API.

Versioned API calls

Ellucian strongly recommends using versioned API calls for all CRUD (create, read, update, and delete) operations.

Ellucian will continue to support versionless GET operations. If a consumer makes a call without specifying the data model version, the application will return the latest version of the API. This could result in a break in the integration if the data model had a breaking change in a property that the application uses.

When a system publishes a change, they publish a payload for the latest version they support. If a consuming or subscribing system does not yet support that version, they must make an API request to the source application specifying the requested version.

Why do I need to use versioned API calls?

If you have developed your own API based on an data model Ellucian delivered, Ellucian recommends you do a versioned call so you get the proper data model version you have developed against. Because specific versions of a data model will eventually be no longer supported, Ellucian recommends keeping as current as possible with the latest data model versions.

If you have developed your own integrations based on Ellucian delivered data models and APIs, Ellucian recommends versioned calls so you get the proper version that the integration was developed against. Because specific versions of a data model and API will eventually be no longer supported, Ellucian recommends keeping as current as possible with the latest versions.
