Use Schema Designer

Schema Designer provides a secure, flexible, and SaaS-compliant way to extend the Banner data model.

Schema Designer features a no-code/low-code interface for functional and administrative users, and offers robust APIs for developers. Schema Designer ensures safe and compliant extensibility. It supports Multi-Entity Processing (MEP) and allows institutions to manage data across multiple entities with ease. The solution integrates with Ellucian Experience and surfaces extended data through components such as More Info cards.

Schema Designer User Interface

The Schema Designer User Interface provides an intuitive dashboard to build extended and custom tables.

Home page

You can see a grid of all tables, both custom and extended, with details such as Table Name, Description, Banner Table, API Name, and Security Object.

A Search field is available on the Home page, allowing you to quickly find tables by entering their name or description. The search results dynamically update as you type.

Table details page

Clicking any table name link from the Home page opens the detailed view of that table. This page provides additional information about the table, including specific field details, data types, and configurations. You can view and manage fields within the table to tailor it according to your business needs.

Schema Designer Home page

The Home page in Schema Designer serves as the central dashboard for managing both extended and custom tables. You can access, view, and manage table details.

A Search field is available on the Home page, allowing you to quickly find tables by entering their Name or Description. The search results dynamically update as you type. The Import icon imports a published table that you want to use.

Extended tables and custom tables creation

You can add new tables by selecting either Extended Table or Custom Table from the Create button. To perform this, you must have access to the Schema Designer Experience Extension, granted through role setup or individual permissions in Experience Setup.

Create a new extended table

You can create a new extended table.

Procedure

  1. Log in to Ellucian Experience as an administrator.
  2. Click the Application menu in the global navigation bar, at the top of the Experience dashboard.
  3. Click Schema Designer in the Applications menu.
    The Schema Designer Home page appears.
  4. Click Create and select Extended Table.
    The Create Extended Table page appears.
  5. In the Table Name field, enter the name of the new table.
    The API Name field is auto-populated by default based on the table name entered. You can change the name if required and the name must start with x-.

    The Security Object Name field is auto-populated by default based on the table name entered, You can change the name if required and the name must start with API_X.

    The Business Event Name field is auto-populated by default based on the table name entered, You can change the name or leave it empty. The name must start with EXTN.ExtendedAPI.

  6. In the Description field, enter a brief overview of the purpose of the table.
  7. Select the One-to-Many Relationship check box if you want to configure relationships to link the extended table with baseline table.
    This means the extended table can have multiple records for each key combination of the baseline table record.
  8. Click Next.
    The Select Banner Table page appears.
  9. Select a Banner table from the page to extend its functionality.
    The Extended Schema page appears.

    This page has a Summary section and a Fields section on the left pane and by default the Summary section is selected. The Fields section lists the existing key fields, with an Add (+) icon. The right pane displays the table with fields configured.

    If the baseline table has any primary keys, they key fields will be added to the Fields section.

  10. Add a key field.
    1. Click the icon.
    2. Ensure that the Key Field check box is selected.
      The Required Field, Display Field on UI, Unique Field, and Indexed Field check boxes will be selected and disabled.

      The Prompt Name and Field Name fields are auto-populated with New Field by default, and you can update it if required. The number of characters in the prompt name must not exceed 50 and the number of characters in the field name must not exceed 30.

      Note: Field Name which is named as pidm or <tableName>_pidm are mapped to xbannerId as the primary PIDM field, while all other _pidm columns are exposed by replacing _pidm with bannerId (for example, xcustom_pidm_other → xcustombannerIdother).
    3. From the Baseline Field list, select the appropriate column to associate to your key field.
    4. In the Field Data Type field, choose one of the three supported data types (String, Number, or Date), and configure additional properties based on the selected field data type.
      Field Scale is available only for the Number field type.
    5. In the Field Length fields, enter a numeric value.
    6. In the Attribute Order field, enter a sequence number to control the display order of the extended field in the More Info section of the specific Banner page.
      Fields display in the More Info section according to the assigned sequence number.
      Note: Attribute Order is an optional field. When provided, it must contain only unique positive integer values.
  11. Add a data field.
    1. Click the icon.
    2. Ensure that the Key Field check box is not selected.
      The following check boxes control field behavior:
      • Required Field: Indicates whether the extended field is required.
      • Display Field on UI: Indicates whether the extended field displays on the UI.
      • Unique Field: Indicates whether the extended non-key field must contain unique values. Before the Schema Designer 1.5 release, uniqueness was enforced only on key columns.
      • Indexed Field: Indicates whether the extended field is indexed. When selected, the system creates and manages an index on the field to improve query performance.
      Note:
      • Only one non-key column can be marked as Unique within the table.
      • When an extended field is set as Unique, it is automatically indexed.
    3. In the Prompt Name field, enter the name of the data field.
      The Prompt Name and Field Name fields are auto-populated with New Field by default, and you can update it if required. The number of characters in the prompt name must not exceed 50 and the number of characters in the field name must not exceed 30.
    4. In the Field Data Type field, choose one of the five supported data types (String, Date, Number, Date Time, or Large Object) and configure additional properties based on the selected field data type.
      Note: Large Object stores large amounts of text data, such as documents and lengthy descriptions and Date Time stores both date and time information, including the timezone.
    5. In the Field Length fields, enter a numeric value.
      Field Scale is only available for the Number field type.
  12. Select a table to validate the data field’s entries against the selected table.
    1. Click Select Source Table.
    2. Specify the column using the Source Column list.
    The entries must match the existing tables or columns for accuracy.
  13. Click Dropdown Configuration to set up the data field’s entry as a drop-down list on the More Info section of the specific Banner page.
    1. In the Source Column Description field, enter the description column of the selected source table.
      The column description publishes when the drop-down values are defined.
      Use this for rendering the table in the More Info section.
    2. In the LOV API Name field, enter the API that provides the values to display as the drop-down list for the entries in this data field.
    3. In the LOV API Code field, enter the property name representing the code of the resource record in the API configured in LOV API Name.
      This code will be saved as a data field in the extended data table.
    4. In the LOV API Description field, enter the property name that represents the description of the resource record in the API configured in LOV API Name. This displays as the description for each value in the drop-down list.
  14. Click the drop-down option next to the table name and click View Table Details to change the Banner table selected before publishing.
    The extended table details appear.
  15. Click the Banner Table button.
    The Select Banner Table page appears and the system automatically updates the key columns to match the new Banner while preserving any additional data fields that you previously added or associated with the original table.
  16. Click Publish.

Results

The Experience page triggers the extension-configurations API to create the new extended table.
Create a new custom table

You can create a new custom table.

Procedure

  1. Log in to Ellucian Experience as an administrator.
  2. Click the Application menu in the global navigation bar, at the top of the Experience dashboard.
  3. Click Schema Designer in the Applications menu.
    The Schema Designer Home page appears.
  4. Click Create and select Custom Table.
    The Create Custom Table page appears.
  5. In the Table Name field, enter the name of the new table.
    The API Name field is auto-populated by default based on the table name entered. You can change the name if required and the name must start with x-.

    The Security Object Name field is auto-populated by default based on the table name entered, You can change the name if required and the name must start with API_X.

    The Business Event Name field is auto-populated by default based on the table name entered, You can change the name or leave it empty. The name must start with CSTM.CustomAPI.

  6. In the Description field, enter a brief overview of the purpose of table.
  7. Select the Table Auto Increment check box if you want to set up auto-increment for primary keys.
    This ensures unique identifiers for each record.
  8. Select the MEP Enable check box if you want to enable MEP to support multiple entities within the same table.
    This facilitates data segregation and management.
  9. Click Next.
    The Custom Schema page appears.

    This page has a Summary section and a Fields section on the left pane and by default the Summary section is selected. The Fields section lists the existing key fields, with a + icon. The right pane displays the table with fields configured.

  10. Add a key field.
    1. Click the + icon.
    2. Ensure that the Key Field check box is selected.
      The Required Field, Display Field on UI, Unique Field, and Indexed Field check boxes will be selected and disabled.

      The Prompt Name and Field Name fields are auto-populated with New Field by default, and you can update it if required. The number of characters for both must not exceed 30.

      Note: Field Name which is named as pidm or <tableName>_pidm are mapped to xbannerId as the primary PIDM field, while all other _pidm columns are exposed by replacing _pidm with bannerId (for example, xcustom_pidm_other → xcustombannerIdother).
    3. In the Field Data Type field, choose one of the three supported data types (String, Number, or Date), and configure additional properties based on the selected field data type.
      Field Scale is available only for the Number field type.

      If you select Number as the Field Data Type, a new check box called Field Auto Increment becomes available.

    4. Select the Field Auto Increment check box if you want to set up auto-increment for the number data field.
      The Starting Value and Increment Step fields display, each preconfigured with a default value of 1. You can update these values to any positive, non-decimal integer.
      Note: Only one numeric field can be configured for auto-increment at a given time. When auto-increment is enabled for a numeric field, it cannot be assigned to any other numeric field unless it is first removed from the previous entry. Additionally, field-level auto-increment can be configured only when auto-increment is not already defined at the table level.
    5. In the Field Length field, enter a numeric value.
    6. In the Attribute Order field, enter a sequence number to control the display order of the custom field.
      If no value is provided, the Schema Designer assigns a default order.
      Note: Attribute Order is an optional field. When provided, it must contain only unique positive integer values.
  11. Add a data field.
    1. Click the + icon.
    2. Ensure that the Key Field check box is not selected.
      The following check boxes control field behavior:
      • Required Field: Indicates whether the custom field is required.
      • Display Field on UI: Indicates whether the custom field displays on the UI.
      • Unique Field: Indicates whether the custom non-key field must contain unique values. Previously, uniqueness was enforced only on key columns.
      • Indexed Field: Indicates whether the custom field is indexed. When selected, the system creates and manages an index on the field to improve query performance.
      Note:
      • Only one non-key column can be marked as Unique within the table.
      • When a custom field is set as Unique, it is automatically indexed.
    3. In the Prompt Name field, enter the name of the data field.
      The Prompt Name and Field Name fields are auto-populated with New Field by default, and you can update it if required. The number of characters in the prompt name must not exceed 50 and the number of characters in the field name must not exceed 30.
    4. In the Field Data Type field, choose one of the five supported data types (String, Date, Number, Date Time, or Large Object) and configure additional properties based on the selected field data type.
      Note: Large Object stores large amounts of text data, such as documents and lengthy descriptions and Date Time stores both date and time information, including the timezone.
    5. In the Field Length field, enter a numeric value.
      Field Scale is available only for the Number field type.
  12. Select a table to validate the entries of the fields against the selected table.
    1. Click Select Source Table.
    2. Specify the column using the Source Column list.
    The entries must match the existing tables or columns for accuracy.
  13. Click Publish.

Results

The system calls the custom-table-configurations API to create the new custom table.

Procedure

  2. Click the drop-down option next to the table name and click View Table Details.

    The Manage Extension Mapping page displays with detailed information about the linking of the extended table and Banner Admin pages. You can add or delete multiple mappings by selecting or deselecting the Banner pages in the Map to Banner Pages option.

Schema Designer APIs

Schema Designer offers robust, SaaS-safe APIs for creating, managing, and migrating extended and custom tables through RESTful endpoints, enabling secure integration and automation across environments.

Extended table and extended table API creation

If you have data requirements to meet your unique business needs to extend an existing Banner-delivered table, you can create an extended table in BAN_EXTENSIONS schema.

Extension of Banner schema with your own data and APIs

If you have data requirements that are not part of the delivered Banner schema and you need to extend an existing Banner table, you can create an extended table in BAN_EXTENSIONS schema.

You can create an extended table and extended table API and access them through the Banner Ethos API Integration application. You can define and configure an extended table without modifying the source code or bringing the system down for updates. The approach through a configuration API enables administrators to define the schema of the extended table and the system creates an extended table in the BAN_EXTENSIONS schema.

The new extended table definition resides in the GORRSDE Banner configuration table and the new extended table API definition resides in the GURASPC Banner configuration table. The system also creates a definition of the created extended table API into an API Specification. The table is read and interpreted at run time, executing the specification as defined based out of the schema of the table defined by the administrator, and returning the requested resource.

extension-configurations API

You can use the extension-configurations API to create, modify, or delete an extended table and extended table API.

You can also use the extension-configurations API to create and manage the extension configurations to create the extended table and a specification-driven API is generated for the extended table. The extension-configurations API is available in the Banner Ethos Integration API application.

For more information, see Extension Configurations: extension-configurations.

One-to-Many feature

The extension-configurations API includes a property named onetoMany, which indicates if an extended table can establish one-to-many relationships with the baseline table. This helps users define and manage table relationships effectively.
  • True: The extended table supports one-to-many relationships with the baseline table.
  • False: The extended table does not support one-to-many relationships with the baseline table.
Features of extended table API

Extended table APIs support all methods.

Extended table API functionality supports the following:
  • GET ALL, GET by ID, create (POST), update (PUT) and delete (DELETE) methods.
  • API paging parameters – limit and offset.
  • Semantic versioning standards with multiple major and minor version updates.
  • Filters on all data model schema properties.
  • Properties data types such as string, object, array, date, and date-time.
  • Change notifications in the form of Banner Event Publisher events.
  • Banner Data Privacy.
  • MEP-enabled institutions.
The functionality currently does not support the following:
  • Defining a named query for the extended table API.
  • Creating an alternative resource representation on an existing Ellucian delivered resource.
  • Defining an array within an array data type.
Naming conventions

Following a naming convention for your extended resources ensures that they do not conflict with Ellucian delivered resources in future releases.

Extended table names

Ellucian recommends using one of the following naming conventions when naming your extended table:
  • Prefix the name of the extended table with the letter x. For example, xnextofkin.
  • Using a prefix to name the extended table ensures that they are unique.
    Note: The table name can have up to 30 characters. The column names need not be prefixed with extended table name.

API names

Ellucian recommends using one of the following naming conventions when naming your extended table API:
  • Prefix the name of the API with the letter x- followed by the extended table name. For example, x-nextofkin.
  • If the name of the API is not provided in the configuration, the system generates the name prefixed with x-, followed by the name of the extended table.

Without a unique prefix, an API with an identical name could be delivered with a future Banner Ethos API release and could overwrite your extended resource.

Create an extended table and extended table API

If you have data requirements to meet your unique business needs to extend an existing Banner delivered table, you can create an extended table in BAN_EXTENSIONS schema.

Before you begin

The user who needs access to the extension-configurations API must be assigned with the security object delivered (API_EXT_CONFIGURATIONS).

Procedure

  1. Make a POST call to extension-configurations to create the extended table configurations.
    The API does the following:
    • Creates extension configurations to extend the Banner baseline tables that the administrator/student can create and deletes the extended data.
    • Creates the extended table (which holds the extended data) based on the configurations for the mapping between the baseline table and the custom table/delivered table.
    • Creates the spec-based API for the extended table which supports all the methods (GET/POST/PUT/DELETE) with standard validations and additional validations based on the configuration entries.
    • Creates the security object for the spec-based API for the extended table.
    • Creates a business event if the event name is included in the request.
  2. Use your preferred REST API client to send a POST request.
    Example:

        "columnName": "XMATERIL_TERM_CODE"

        "attributeDisplay": "true",

        "columnName": "XMATERIL_CRN"
      },
      {
        "attributeDataLength": "20",
        "attributeDataType": "VARCHAR2",
        "attributeDisplay": "true",
        "attributePrompt": "Name",
        "attributeRequired": "Y",
        "columnName": "XMATERIL_NAME"
      },
      {
        "attributeDataLength": "10",
        "attributeDataType": "VARCHAR2",
        "attributeDisplay": "true",
        "attributePrompt": "Type",
        "attributeRequired": "N",

Edit an extended table and extended table API

If you need to modify specific metadata attributes of an existing extended table, you can use the extension-configuration-revisions API. This API allows you to update specific properties of the extended table without deleting it or creating a new one.

Before you begin

The user who needs access to the extension-configuration-revisions API must be assigned with the security object delivered (API_EXT_CONFIG_REVISIONS).

Procedure

  1. Make a PUT call to extension-configuration-revisions API to update the extended table configurations.
    The API does the following:
    • Allows adding new non-key columns to an existing extended table.
    • Updates only the supported metadata attributes of the extended table.
      • attributeDataLength: You can increase the length, but cannot reduce it. For numeric datatype columns in Oracle, you can increase it up to 38.
      • attributeDataScale: You can increase the scale for numeric fields, but you cannot reduce it.
      • attributeDisplay: You can update this value only when the field is not required.
      • attributePrompt: You can update the prompt.
      • attributeRequired: You cannot change this value from false to true.
      • attributeDataType: You cannot change the data type.
      • columnName: You cannot change the column name.
      • columnBaseTable: You cannot change the base table column.
      • attributeOrder: You can change the integer value, provided it remains unique within the table.
      • attributeUniqueColumn: You can change this value from false to true or from true to false, provided that only one non-key column is marked as unique.
      • attributeIndex: You can change this value.
    • Regenerates the extended table API specification and the OpenAPI definition.
  2. Use your preferred REST API client to send a PUT request.

Extension of Banner schema with your own data and APIs

If you have data requirements that are not part of the delivered Banner schema and you need a custom table other than the existing Banner tables, you can create a custom table in BAN_EXTENSIONS schema.

You can create a custom table and the custom table API and access it through the Banner Ethos API Integration application. You can define and configure a custom table without modifying the source code or bringing the system down for updates. The approach through a configuration API enables administrators to define the schema of the custom table and the system creates a custom table in BAN_EXTENSIONS schema.

The new custom table definition resides in the GORCSTT Banner configuration table and the new custom table API definition resides in the GURASPC Banner configuration table. The system also creates a definition of the created custom table into an API specification. The table is read and interpreted at run time, executing the specification as defined based out of the schema of the table defined by the administrator and returning the requested resource.

custom-table-configurations API

You can use the custom-table-configurations API to create, modify, or delete a custom table and custom table API.

See the Open API documentation for the supported methods and schema properties of the custom-table- configurations.

You can also use the custom-table-configurations API to create and manage the custom table configurations to create the custom table and a specification-driven API is generated for the custom table. The custom-table-configurations API is available in the BannerEthos Integration API application.

Table-level Auto-Increment feature

The custom-table-configurations API provides an auto-increment feature for custom tables, which can be enabled by setting the requiresAutoIncrement property to true. This setting is applied during the configuration of the custom table using the custom-table-configurations API.

After enabling the auto-increment feature, the API automatically adds a new column to the custom table. This column name pattern is <TableName>_SEQUENCE_NUM, where <TableName> is the name of your custom table. The column is specifically designed to hold values in an incremental sequence for each new record inserted into the table, ensuring that each entry is uniquely identified.

Additionally, this auto-increment column becomes an integral part primary key configuration of the table. It is combined with any other key columns you have specified to form a composite primary key. This ensures data integrity and uniqueness across all records within the custom table.

You can use the auto-increment feature to streamline data management and enhance the reliability of your custom tables without manual intervention for sequence number generation.

Column-level Auto-Increment feature

In addition to table-level support, you can now configure auto-increment at the column level.

You can mark a specific custom column for auto-increment using the following properties:
  • attributeAutoIncrement
  • attributeStartingValue
  • attributeIncrementStep

This gives more flexibility to generate numbers on any column, making it easier to follow your business rules or match old numbering patterns. If a starting value or increment step is not provided, the system applies the defaults (start = 1, step = 1).

Features of custom table API

Custom APIs supports all methods.

Custom table API functionality supports the following:
  • GET ALL, GET by ID, create (POST), update (PUT) and delete (DELETE) methods.
  • API paging parameters – limit and offset.
  • Semantic versioning standards with multiple major and minor version updates.
  • Filters on all data model schema properties.
  • Properties data types such as string, object, array, date, and date-time.
  • Change notifications in the form of Banner Event Publisher events.

Naming conventions

Following a naming convention for your custom resources ensures that they do not conflict with Ellucian delivered resources in future releases.

Custom table names

Ellucian recommends using one of the following naming conventions when naming your custom table:
  • Prefix the name of the custom table with the letter x. For example, xmaterial.
  • The second letter of the custom table name must be one of the following characters: [f, g, n, p, r, s, t].
  • Using a prefix to name your custom table ensures that they are unique.
  • Note: The table name can have up to 30 characters. The column names need not be prefixed with custom table name.

API names

Ellucian recommends using one of the following naming conventions when naming your custom table API:
  • Prefix the name of the API with the letter x followed by the custom table name. For example, x-xmaterial.
  • If the name of the API is not provided in the configuration, the system generates the name prefixed with x-, followed by the name of the custom table.

Without a unique prefix, an API with an identical name could be delivered with a future Banner Ethos API release and could overwrite your extended resource.

Migrate artifacts between tenants: Export/Import process

Organizations often build and test Schema Designer configurations such as extended/custom tables, APIs, and extension mappings in a non-production tenant because manually recreating these configurations in production is time-consuming and error-prone.

The Export/Import workflows solve this by providing a streamlined, repeatable process.
  • One-click extraction - A single call to the schema-extensibility-artifacts endpoint gathers all selected artifact types—extension-configurations, custom-table-configurations, and extension-mappings—and returns them as ready-to-use request payloads
  • Portable payloads - The exported JSON strictly conforms to the create-batch schema of each target API. No manual transformation is required.
  • Batch creation in production - These payloads are posted to each artifact’s/batches endpoint, which automatically recreates:
    • All tables and columns
    • Security objects and business events
    • UI mappings
    • OpenAPI specification registration
  • End-to-end integrity - After import, each artifact behaves exactly as in the test tenant:
    • Extended/custom tables are fully created
    • APIs function as expected
    • Extended fields appear in the More Info section of Banner admin pages
    • Security objects are active
    • Business events are created (in disabled state by default)
    • OpenAPI specifications are registered in the API Registry

The Export/Import feature offers a repeatable, tenant-agnostic pipeline to migrate all Schema Designer configurations—including metadata, UI mappings, and security objects—from test to production with no manual edits and minimal downtime. Post-import, all components function exactly as they did in the test environment.

Run the migration of Supplemental Data Configurations (GURMSDC) process

Migration of Supplemental Data Configurations (GURMSDC) is a Banner batch process that migrates Supplemental Data Engine (SDE) configuration metadata to the schema extensibility framework.

Before you begin

Before you run GURMSDC:
  • Identify the tables to be migrated.
  • List all SDE baseline tables that you plan to migrate.
  • Confirm whether you will migrate all tables from GOBSDTB, or only specific tables.
  • Identify the attributes to be migrated.
  • Review the user-defined columns in each SDE table.

  • Check that attributes meet eligibility rules (data types, primary key constraints, mapping requirements).

About this task

The GURMSDC process creates the extensibility metadata (custom table definition, API mapping, and security objects) from SDE configuration records. You can run GURMSDC in AUDIT mode and UPDATE mode.

Procedure

  1. Log in to Banner as a Banner administrator.
  2. Access the Process Submission Controls (GJAPCTL) page.
  3. Enter GURMSDC in the Process field.
  4. Select Next Section.
  5. Enter DATABASE in the Printer field.
  6. Select Next Section.
  7. Enter the following information:
    Parameter Value
    Mode AUDIT (validate only) or UPDATE (perform migration).
    Tables Blank (all tables in GOBSDTB), or a specific table name (repeat Param 02 for each table).
  8. Select Next Section.
  9. Click Save to submit the job.
  10. Make a note of the files created that appear in the message area to review the results.
  11. Exit GJAPCTL.
Review the GURMSDC process

You must review the results of the GURMSDC migration process to verify if the migration was successful.

Procedure

  1. Access the Saved Output Review (GJIREVO) page.
  2. Enter GURMSDC in the Process field.
  3. Select a file in the File Name field.

Results

The log file contains statistics information and possible error messages from the migration process.

Run the Migration of Supplemental Data Values (GURMSDV) process

Migration of Supplemental Data Values (GURMSDV) is a Banner batch process that migrates Supplemental Data Engine (SDE) data values to the schema extensibility framework tables. This process ensures that existing user-defined data is preserved, accessible through extensible APIs, and available in configurable UI components within Banner administrative pages.

Before you begin

Before you run GURMSDV:
  • Ensure that all required configurations have been migrated using GURMSDC.
  • Identify the tables to be migrated.
  • List all the SDE baseline tables that you plan to migrate.
  • Confirm whether you will migrate all tables from GOBSDTB, or only specific tables.
  • Review the attributes and data integrity.
  • Check for nullability, data type, and length consistency between SDE and the extensibility tables.
  • Verify that primary key structures are intact and match the target tables.

Procedure

  1. Log in to Banner as a Banner administrator.
  2. Access the Process Submission Controls (GJAPCTL) page.
  3. Enter GURMSDV in the Process field.
  4. Select Next Section.
  5. Enter DATABASE in the Printer field.
  6. Select Next Section.
  7. Enter the following information:
    Parameter Value
    Mode AUDIT (validate only) or UPDATE (perform migration).
    Tables ALL, % (all tables in GOBSDTB), or a specific table name (repeat Param 02 for each table).
  8. Select Next Section.
  9. Click Save to submit the job.
  10. Make a note of the files created that appear in the message area to review the results.
  11. Exit GJAPCTL.
Review the GURMSDV process

You must review the results of the GURMSDV migration process to verify if the migration was successful.

Procedure

  1. Access the Saved Output Review (GJIREVO) page.
  2. Enter GURMSDV in the Process field.
  3. Select a file in the File Name field.

Results
