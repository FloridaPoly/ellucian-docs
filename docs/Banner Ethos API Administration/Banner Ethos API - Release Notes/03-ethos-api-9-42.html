Integration API Release 9.42

The Banner Integration API 9.42 release includes enhancements to bank-tapes API error handling, international tracking bulk import capabilities, person merge operations, Grails framework upgrade, custom configuration APIs, comprehensive filtering for generated APIs, API Designer, new ProCode APIs, and enhanced person APIs.

Banner Integration API 9.42 runs on Banner platform version 12.0 and Banner Common DB Upgrade 9.43.

Tip: For more information about the following APIs, see the Banner API Catalog.

Enhanced ucasxmlset Integration API

The ucasxmlset Integration API has been enhanced to include two new UCAS reference endpoints: getReferenceApplicationSections and getReferenceDocumentCategories.

This enhancement addresses PE0006670 in the Ellucian Customer Center.

Enhanced bank-tapes API with improved error messaging

The bank-tapes API has been enhanced to provide user-friendly error messages when not valid ID values are submitted in PUT or POST batch requests.

This enhancement includes updates to the PHRBKTP (Payroll Bank Tape) database table to properly configure the SURROGATE_ID, DATA_ORIGIN, USER_ID, and VERSION columns as non-nullable, and adds a GUID column to the table. These database improvements enable the API to perform proper validation and return clear, actionable error messages when the not valid ID values are detected in batch operations, improving the integration development experience and reducing troubleshooting time.

For complete API specifications and error response schemas, see the bank-tapes API in the Banner API Catalog.

This enhancement addresses PE0008185 in the Ellucian Customer Center.

Enhanced bulk import capabilities for international tracking agency recruit integration

A new Integration API, intt-agent-transactions, has been introduced to retrieve agency and agent-related data from Recruit into Banner. This API is utilized within the INTTRACK Data Collection pipelines, specifically the Agency GET Pipeline and Agent GET Pipeline

The Ellucian Ethos Data Access pipelines have been enhanced to support bulk data loading for international student recruitment tracking through agency partnerships. The enhancement implements Data Connect pipelines for the international tracking agency recruit integration, enabling institutions to efficiently process large volumes of recruitment data from international agencies.

These pipelines enable automated bulk import of agent and agency transaction data for UKVI (UK Visas and Immigration) compliance tracking and international student recruitment workflows. The enhancement includes integration API endpoints and ETL (Extract, Transform, Load) processes that support CSV file-based bulk loading of recruitment tracking data, significantly improving data processing efficiency for institutions managing high volumes of international recruitment activities.

For information about configuring and using bulk import processes for international tracking, see Configure Banner for file bulk loads.

This enhancement addresses PE0008175 in the Ellucian Customer Center.

Enhanced duplicate-person-data-cleanup-operations API

The duplicate-person-data-cleanup-operations API has been enhanced to automatically detect and resolve sequence number conflicts during person merge operations. Previously, when merging duplicate person records with identical sequence numbers in multi-row tables (such as spraddr for person addresses), the merge operation would fail due to uniqueness constraints, requiring manual database intervention to increment sequence numbers before completing the merge.

This enhancement implements intelligent backend logic that automatically detects sequence number conflicts between source ("bad ID") and target ("good ID") person records during merge processing. When conflicts are detected, the system automatically assigns the next available sequence number to the incoming data, ensuring a successful merge without manual SQL updates. The auto-resolution logic is designed as a reusable service component that supports multiple Banner tables using sequence numbers, improving data cleanup efficiency and reducing the risk of human error in manual interventions.

The enhancement includes comprehensive error handling, structured logging with correlation identifiers for troubleshooting, and performance optimizations to ensure merge operations complete within established service-level targets. These improvements streamline duplicate person remediation workflows and support institutional data quality initiatives.

For complete API specifications and merge operation schemas, see the duplicate-person-data-cleanup-operations API in the Banner API Catalog.

This enhancement addresses PE0008353 in the Ellucian Customer Center.

Grails 7 brings enhanced compatibility with current Java technologies, improved memory management, and optimized request processing capabilities that benefit all API operations.

This platform upgrade ensures Banner Integration API continues to leverage industry-standard security practices and performance optimizations. The upgrade includes enhanced dependency management, improved plugin architecture, and modernized runtime components that support future API enhancements. Integration partners can expect continued API compatibility while benefiting from the underlying performance and security improvements provided by the Grails 7 framework.

Enhanced extension-configurations and custom-table-configurations APIs

The extension-configurations and custom-table-configurations APIs have been enhanced to support Boolean data types for custom extension fields and custom table columns.

This enhancement introduces native Boolean data type support in extension definitions and custom table schemas, enabling institutions to define Boolean fields that accept standard true/false values in API requests and responses. The enhancement includes proper JSON schema validation, automatic type conversion, and improved error messaging when not valid Boolean values are submitted. Integration partners can now design cleaner data models with explicit Boolean semantics, simplifying conditional logic in external systems and improving data quality through stronger type enforcement.

For complete API specifications, extension configuration patterns, and custom table schema definitions, see the extension-configurations and custom-table-configurations APIs in the Banner API Catalog.

This enhancement addresses PE0008391 in the Ellucian Customer Center.

Enhanced comprehensive filtering for Schema Designer generated extension and custom table APIs

APIs generated through Schema Designer for custom table extensions and custom tables have been enhanced to support comprehensive filtering capabilities using criteria specifications.

This enhancement implements the SPEC (Specification) API filtering framework for all Schema Designer generated APIs, enabling institutions and integration partners to construct complex filter criteria using query parameters similar to standard Ethos APIs. The enhancement supports multiple filter operators (equals, contains, greater than, less than), compound conditions (AND/OR logic), and nested criteria expressions. Generated APIs now process filter criteria server-side using optimized SQL query generation, returning only matching records and significantly reducing data transfer volumes.

The comprehensive filtering support includes proper URL encoding handling, null value filtering, and integration with the existing Ethos filter compiler infrastructure. These improvements enable more efficient API consumption patterns for custom data extensions, supporting complex integration scenarios while maintaining consistent filtering semantics across all Banner Integration API endpoints.

For complete API specifications and filter syntax documentation, see the generated API definitions in the Banner API Catalog and Schema Designer documentation.

This enhancement addresses PE0008390 in the Ellucian Customer Center.

Support to allow integration with third party payment providers

The enhancements include:

  • FABCHKP – Check Print Process Enhancements

    When invoices originate exclusively from TPP, the Check Print process now performs the following updates:

    • Origin Code mapping: Copies the FABINVH_ORIGIN_CODE (values like TPP_) into the new column FABCHKS_ORIGIN_CODE.
    • Final Reconciliation status: Creates checks with reconciliation indicators

      (FABCHKS_RECON_IND = 'F', FABINCK_RECON_IND = 'Y').

    • Invoice Number population: For single‑invoice checks, populates the new column FABCHKS_INVOICE_NUM with the TPP invoice number.
    • Pending Pay Type: Sets FABCHKS_PAY_TYPE to “Pending” until settlement details are added through the check‑payment‑type‑details API. Additional fields supported:
      • FABCHKS_TPP_PAYMENT_NUM
      • FABCHKS_TPP_PAYMENT_DATE
      • FABCHKS_TPP_RECON_INFO
  • Accounts Payable Invoices API (v16.2.0)

    Enhancements include:

    • POST API originCode: New property originCode to represent TPP invoices (FABINVH_ORIGIN_CODE like TPP_)
    • Grouping Indicator: New property groupingIndicator (combine or isolate) to control Banner Check Number assignment.
    • GET API properties: Includes originCode and groupingIndicator.
    • GET API queries: Adds filters such as originCode, type, referenceNumber, paymentStatus, processState, and payment:source.
  • Check Payment Type Details API

    Updates across versions:

    • POST Batch API v1.1.0 & v2.0.0: Accepts new properties:
      • tppPaymentNumber (FABCHKS_TPP_PAYMENT_NUM)
      • tppPaymentDate (FABCHKS_TPP_PAYMENT_DATE)
      • tppSettlementDate (FABCHKS_TPP_SETTLE_DATE)
      • tppReconciliationInformation (FABCHKS_TPP_RECON_INFO)
    • Payment Type values: Expanded to include debitCard, vCard, ACH, and Check.
    • GET API v1.1.0 & v2.0.0: Returns additional values such as originCode, invoiceNumber, and TPP payment details.
    • POST Batch API v2.0.0 only:
      • Pay Type Check no longer removes Final Reconciliation status.
      • Pay Type None removes Final Reconciliation status (for non‑TPP partners).
      • Pay Type Check is deprecated for non‑TPP integrations in v2.0.0, though v1.1.0 continues to support it.

Enhanced Structured Progression with automatic curriculum end date and catalogue term updates

Structured Progression has been enhanced to automatically update the Learner Curriculum End Date (SORLCUR_END_DATE) and increment the Catalogue Term when progression outcomes are locked or approved. This automation ensures alignment with UK and Ireland institutional data maintenance practices and compliance with HESA and ERM statutory reporting standards.

When progression outcomes from an exam committee determine that a student must repeat a year or extend their study period, the system now automatically extends the curriculum end date based on configurable rules mapped to the progression outcome. For example, a "Repeat Year" outcome automatically extends the end date by one academic year. The enhancement also automatically increments the Catalogue Term for rolled records, ensuring accurate term alignment for downstream reporting and compliance processes.

This automation eliminates the need for manual student-by-student record updates, reducing administrative workload and minimizing the risk of reporting inaccuracies. The enhancement integrates seamlessly with the existing roll-to-next-term process, ensuring data updates occur within the standard progression workflow while maintaining synchronization between progression outcomes, academic standing, and learner curriculum details.

This enhancement addresses PE0007399 in the Ellucian Customer Center.

Enhanced sections API for improved update semantics

The sections API has been enhanced to improve usability and align with standard REST API update semantics. The academicPeriod field behavior now differs between POST and PUT operations for more intuitive API usage.

For POST (create) operations, academicPeriod remains a required field, as a section cannot be created without an academic period. For PUT (update) operations, academicPeriod is now optional. When not provided in a PUT request, the API retains the existing academic period value. When provided, the value is validated and updated according to existing business rules.

This enhancement enables partial updates without redundant payload requirements, reduces the likelihood of integration errors, and simplifies client implementations while preserving correct creation rules and validation for academic period changes.

For complete API specifications and request examples, see the sections API in the Banner API Catalog.

The enhanced APIs now check for existing payment IDs in previously posted transactions and return an appropriate error response when a duplicate payment attempt is detected, preventing duplicate charges from being posted to student accounts.

Enhanced payment posting APIs with UTC timezone support

The proxy-student-charges-payments and proxy-charges-payments APIs have been enhanced to support ISO 8601 timestamp format with automatic UTC offset conversion. The APIs now convert the UTC offset provided in API requests to the receiving Banner server's UTC offset for both POST operations and response data.

This enhancement eliminates timezone discrepancies between client applications and Banner server instances. Integration partners no longer need to manually calculate and adjust for timezone differences, as the APIs automatically handle the conversion between the client's timezone and the server's configured timezone. Timestamps submitted in requests are converted to the server's local time for storage, and response timestamps are converted from server time to the client's requested timezone format.

For complete API specifications, timezone format requirements, and conversion behavior, see the proxy-student-charges-payments and proxy-charges-payments APIs in the Banner API Catalog.

Grails 7 Migration: Date-Time JSON Response Format Change

As part of the Student API App migration to Grails 7, the JSON rendering behavior for date/time fields has changed. This affects GET API responses that return date-time values, such as expectedGradDate property in one of the API.

In Grails 7, java.util.Date-style values are rendered in ISO-8601 format with a Z suffix and include millisecond precision. The Grails 7 upgrade guide documents that java.util.Date values now render with milliseconds, for example changing from 2025-10-07T21:14:31Z to 2025-10-07T21:14:31.407Z. The guide also notes that Date and Calendar values use millisecond precision with three decimal places, and that temporal values with timezone information render with the Z suffix for UTC.

Impacted API Behavior

In the Student API App, when a date-time field is assigned using Timestamp, the GET response now includes milliseconds in the serialized JSON output.

Code Example:

entity.studentObject.expectedGradDate =
        new Timestamp(entity.studentObject.expectedGradDate.getTime())

Previous Response Format:

{
  "expectedGradDate": "2026-09-30T04:00:00Z"
}

Grails 7 Response Format:

{
  "expectedGradDate": "2026-09-30T04:00:00.000Z"
}

The .000 portion represents milliseconds. In this example, the millisecond value is zero, so Grails renders it as .000.
