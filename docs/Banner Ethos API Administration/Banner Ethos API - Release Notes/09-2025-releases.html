Integration API Release 9.40

The Banner Integration API 9.40 release contains enhancements and defect resolutions.

Banner Integration API 9.40 runs on Banner platform version 11.4 and Banner Common DB Upgrade 9.41.

Tip: For more information about the following APIs, see the Banner API Catalog.

Preferred middle and last name display support

The following pages are updated for the preferred middle and last name display support:
  • firstName, middleName, lastName
  • Legal name

Preferred middle and last name display has more information in the Banner General Self-Service December 2025 release notes. For details, see Release 9.24.

New Receipt Required property for the accounts-payable-invoices API

The updated accounts-payable-invoices EEDM API (v16.1.0) has a new optional input value, Receipt Required. This input value designates the Receipt Required field for an invoice document. The values as Yes or No.

If the Receipt Required value is not present in the payload and the Integration Configuration Settings (GORICCR) page setting indicates that Banner Matching is active, then normal Banner Matching rules apply.

Tip: The submittedBy user must have Invoice Receipt Required Override authority on the User Profile Maintenance (FOMPROF) page to submit a value for the receiptRequired API property.

For details, see PE0005645 in Banner Integration API 9.40

This enhancement addresses PE0005645 in the Ellucian Customer Center.

New Receipt Required property for the requisitions API

The requisitions EEDM API (v11.20) has an optional new value, Receipt Required. This input value designates the Receipt Required field for an invoice document. The values as Yes or No.

If the Receipt Required value is not present in the payload and the Integration Configuration Settings (GORICCR) page setting indicates that Banner Matching is active and normal Banner Matching rules apply.

Tip: The submittedBy user must have Requisition Receipt Required Override authority on the User Profile Maintenance (FOMPROF) page to submit a value for the receiptRequired API property.

For details, see PE0005646 in Banner Integration API 9.40

This enhancement addresses PE0005646 in the Ellucian Customer Center.

Updated security-business-profile-user-assignments API

The updated security-business-profile-user-assignments ERP API (v1.0.0) now supports the POST request method and the DELETE request method. This allows for batch submissions of business profile user assignment details, which means that administrators can group users with similar responsibilities for fine-grained access control virtualization-based security processing in bulk. Updates are applied to the Banner GORFBPR table.

This enhancement addresses PE0006713 in the Ellucian Customer Center.

SDE Migration Framework updates

The Supplemental Data Engine (SDE) Migration Framework now supports Composite Primary Keys and One-to-Many Relationships, which helps support broader data migration use cases. This enhancement reduces manual effort, ensures data integrity, and accelerates migration for complex relational models.

The Migration of Supplemental Data Configurations (GURMSDC) process is extended to handle table migration for tables with composite primary keys and one-to-many relationships to ensure seamless schema migration across complex relational structures.

The Migration of Supplemental Data Values (GURMSDV) process is enhanced to support the migration of data values for tables with composite primary keys and one-to-many relationships to preserve referential integrity and ensure consistency during the migration process.

This enhancement addresses PE0006937 in the Ellucian Customer Center.

New Last Inventory Date property for the fixed-assets API

The updated fixed-assets Ellucian Customer Center API (v12.1.0) adds a new property lastInventoryOn to manage the last inventoried date for an asset tag. The last inventoried date corresponds to the FFBMAST_LAST_INVENTORY_DATE field in the Banner Fixed Assets (FFBMAST) table.

The fixed-assets API can now query and update fixed asset master records for the last inventoried date.

The GET and PUT request methods are supported.
  • The GET method includes the new property lastInventoryOn when a value is present for FFBMAST_LAST_INVENTORY_DATE.
  • The GET method is now available to use with one of the following new criteria:
    • tag, which accepts Ptag code or Otag code and returns the Ptag value if it exists
    • description, which is a case-insensitive query for the asset tag description, including queries for descriptions using wildcards
    • lastInventoryOn, with three options:
      • Equals last inventoried date
      • Greater than or equal to last inventoried date
      • Less than or equal to last inventoried date
  • The PUT method allows updates to lastInventoryOn for individual fixed asset records one at a time according to the ID (GUID).

This enhancement addresses PE0007121 in the Ellucian Customer Center.

Updated persons API

The updated persons ERP API (v1.0.0) adds support for the Preferred Last Name and preferred Preferred Middle Name Banner properties. These objects apply to the SPBPERS_PREF_MIDDLE_NAME and SPBPERS_PREF_LAST_NAME database columns.

For the General Person Identification (SPAIDEN) page:
  • For the Alternative Identification record where spriden_ntype_code maps to favored – if the record is present for the first name then the middle name and last name values are always retrieved from the Alternative Identification record.
  • For the Current Identification record Preferred First/Middle/Last Name – if no favored name type is present then the value from the SPBPERS table is selected to display.
This is a user-friendly approach that allows flexibility:
  • Faculty members who publish and conduct research under a different last name or middle name other than their legal one can now use their preferred last name in institutional records.
  • Employees, students, and staff who undergo name changes are can now use their preferred last names.

This enhancement addresses PE0007179 in the Ellucian Customer Center.

Extended and custom table configuration updates

This enhancement introduces versioning for extended and custom table configurations to allow users to safely update attribute properties by using new revision APIs. As a result, users no longer need to delete and recreate configurations to make changes, which is faster and preserves data integrity. Two new APIs support this enhancement:
  • The extension-configuration-revisions ERP API (v1.0.0) supports controlled updates by using the PUT request method.
  • The custom-table-configuration-revisions ERP API (v1.0.0) supports controlled updates by using the PUT request method.
Supported updates include the following:
  • Increased field length
  • Adjusted numeric scale
  • Updated display and prompt text

Each valid change triggers Schema Definition (SD) regeneration (and the schema version is upgraded to the next minor version). Additionally, strong validations prevent unsafe changes like data type or required flag modifications.This reduces effort, prevents data loss, and saves time during schema updates. Safe and validated changes ensure data consistency and improve the overall configuration experience when using in Schema Designer.

This enhancement addresses PE0007379 in the Ellucian Customer Center.

Specification-based API updates

Specification-based API GET methods now support filtering results by multiple values for specific fields – such as student IDs – in a single HTTP GET request. For example, the API requests can include multiple student IDs.

The specification-based APIs support filtering by using the $in operator. This allows clients to pass multiple values for a field in a single request, such as the following two examples:

{"xCustomLookupSet": {"$in": ["Test 1", "Test 2"]}}
{{iurl}}/x-xCustom?criteria={"xCustomLookupId":{"$in":[143,145]},"xCustomLookupDate":{"$in":["2025-07-20","2025-07-15"]}, "xCustomLookupSet":{"$in":["Test 3","Test 10"]}}

These examples return results that matches any of the specified values, which reduces the need for multiple API calls.

Banner Batch for Migration of SDE configurations and data

Two new batch jobs are available for the Supplemental Data Engine (SDE) to support the Schema Extensibility migration process:
  • GURMSDC (Migrate Table)
  • GURMSDV (Migrate Data)

Flexible options let you choose which tables to include during migration, improving clarity, reducing errors, and enabling more controlled migration processes.

The enhancement supports:
  • Migrating all eligible tables by default when no selection is made
  • Allowing users to explicitly specify that all tables toe include
  • Allowing users to specify a list of specific tables to migrate, which supports selective migration scenarios
  • Validating the user input to ensure no conflicting or incomplete selections
  • Logging the selected tables for audit and traceability

Administrators can easily migrate all or selected tables, improve auditability, and streamline migration processes – which is critical for institutions with selective migration needs or compliance requirements. When the table name parameter is left empty, all eligible tables are migrated by default. For selective migration, run the 02 parameter with specific table names.

Tip: This release supports migration of only 1:1 mapping tables with a single primary key.

Security object generation using application deployment

Before the release of Banner Integration API 9.38, security objects were delivered to Banner systems through database upgrades.

Starting with Banner Integration API 9.39, delivery of security objects is done by using application layer. If Banner Integration API 9.39 or later is deployed, it automatically loads the relevant security objects into Banner if Ellucian delivers them that way.

Enabling automatic security object loading at the application layer minimizes reliance on database upgrades, which simplifies the deployment of API applications. This process is controlled by the Banner Applications Configurations (GUACONF) setting, api.enableSecurityMetadataCreationJob, which is delivered as enabled (Y) by default with Banner Common DB Upgrade 9.40.

Warning: The api.enableSecurityMetadataCreationJob setting exists as a safeguard.While failures are uncommon, in rare instances this setting – because it operates during application deployment – might potentially interrupt the application startup process. To mitigate this risk, administrators can disable the (N) setting to allow the application to boot normally even if the automated security object generation fails. If the api.enableSecurityMetadataCreationJob setting is not enabled, any newly delivered security objects that need to be loaded using this setting must instead be manually created using the Security Maintenance (GSASECR) page.

Updated section-details API

The anonymous grading indicator, anonymousGradingInd, is added to the section-details ERP API (v1.1.0). The anonymousGradingInd indicator gets information from the SSRANGD table (Grading tab) on the Schedule Detail (SSADETL) page.

You can filter and group sections based on whether those sections are anonymously graded. Filtering helps Anonymous Grading platform users to group course sections based on whether they are configured for Anonymous Grading. Grouping course sections needs to be done before students are registered. This means that groupings cannot depend on whether anonymous grading IDs are generated for registered students.

If Anonymous Grading is set to Yes for the section, the anonymousGradingInd value is set to Y. If Anonymous Grading is set to No for the section, the anonymousGradingInd value is set to N. If the section has no record in the SSRANGD table, the anonymousGradingInd value is null.

Additionally, the Anonymous Grading Faculty Grading uses the section-details API and anonymousGradingInd to categorize sections as either Anonymous Grading or Non-Anonymous Grading. When anonymousGradingInd is set to Y, the section is categorized under Anonymous Grading. Otherwise, the section is categorized as Non-Anonymous Grading.

This enhancement addresses PE0005529 in the Ellucian Customer Center.

Updated grade-details API

New fields are added to support the grade-details ERP API (v1.1.0) for incomplete grading rules information that originates on the Incomplete Grade Rules (SHAINCG) page.

The grade-details API provides a list of valid grade codes for a student in a section, based on the student's level and grade mode for that section. The Anonymous Grading platform solution uses the grade-details API to control which grades are assigned to students, including applying incomplete grading rules correctly. The grade-details API also ensures that when a student is graded based on their anonymous ID, only the grades that are valid for that student's level and grading mode can be assigned. If one of those valid grades is an incomplete grade, the incomplete final grade and extension date fields are displayed as soon as the faculty member assigns the incomplete grade to the student.

Adding the incomplete grading rules information means that:
  • If the incomplete final grade cannot be overridden, it shows as display-only.
  • If the extension date cannot be overridden, it shows as display-only.
  • If the extension date can be overridden, the rules about overriding the date displays.
Tip: Anonymous Grading uses the rules that are created in the SHAINCG page.
The incompleteGradeOverIndicator data element value can be set to true or false, depending on whether the Override Grade indicator is selected on the SHAINCG page for the effective term and level.
  • If the incompleteGradeOverIndicator value is true, an instructor can change the Incomplete Final Grade value if that instructor assigns an incomplete grade to a student.
  • If incompleteGradeOverIndicator value is false, the Incomplete Final Grade value cannot be changed.
The incompleteDateOverType data element can have the following values, which control whether an instructor can change the Extension Date if that instructor assigns an incomplete grade to a student, and how the date can be changed when changes are allowed. For example:
  • A indicates that the Extension Date can be changed to any date.
  • L indicates that the Extension Time can be lengthened so that the instructor can change it to a later date only.
  • N indicates that the Extension Time can be shortened so that the instructor can change it to an earlier date only.
  • S indicates that the Extension Date cannot be changed at all.
