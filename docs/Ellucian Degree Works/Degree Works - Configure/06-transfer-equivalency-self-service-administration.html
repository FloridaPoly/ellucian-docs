Transfer Equivalency Self-Service Administration

Transfer Equivalency Self-Service is a tool used outside of the standard Degree Works interface to allow students who are considering transferring to your school to see how their transfer classes might articulate and apply to a degree at your institution.

To see how classes articulate, prospective students should:
  • Choose an intended degree and major, and enter a starting term.
  • Choose a transfer school, and enter the grade, credits, and term for each transfer class.
  • Enter placement exam scores.
  • Process to see the articulation and degree audit.

Initial Transfer Equivalency Self-Service setup and configuration

Before deploying Transfer Equivalency Self-Service, you must set up and configure the tool.

Transfer Equivalency Self-Service user access

Transfer Equivalency Self-Service is an anonymous application, meaning users do not need to have an access ID to use it. However, the application requires that the TREQER user exists. This user is typically delivered when Degree Works is initially installed. The TREQER user must have the DWTESELF, RSAUDIT, and SDWORKS Shepherd keys. Use the Users function of Controller to verify and add these keys if necessary.

When a user creates an account, they will be assigned the Shepherd keys defined in the core.security.newUser.roles setting and the user class defined in the core.security.newUser.userClass setting. These Shepherd settings are delivered with the standard default values. Note that the user class defined in core.security.newUser.userClass must be valid in AUD012.

The core.security.referenceUser.password must be the same as the TREQER user's password on the SHP_USER_MST.

Transfer Equivalency Self-Service allows only SHP authentication. If you are using an authentication method like SAML for other Degree Works applications, you will need to add a specification to the core.security.authenticationType Shepherd setting for Transfer Equivalency Self-Service:

  • core.security.authenticationType = SHP
  • specification = treqss

If your environment is configured to use SHP as your default authentication method, you should remove the treqss specification for the core.security.authenticationType Shepherd setting so Transfer Equivalency Self-Service will also use that default specification.

UCX tables

The values that display in the Goals, Classes, and Exams drop-down lists are defined in UCX tables. You should review them to ensure they contain the necessary entries and the descriptions are clear and accurate. After updating a UCX table, refresh the page in the browser to load the changes. It is not necessary to restart the application.

Review the following UCX tables to ensure that they are configured correctly for your Transfer Equivalency Self-Service environment:

  • Show in Transfer Equivalency Self-Service in AUD027, AUD029, STU016, STU035, STU307, STU316, STU346, STU350, STU398, STU560, STU563, STU576
  • Credit-By-Exam in STU314
  • Description in TRQ065

Transfer Equivalency Self-Service database table structure

Transfer Equivalency Self-Service uses several tables in its database table structure.

SHP_USER_MST

When a user creates an account, a SHP_USER_MST record is created for that user with the email stored as the SHP_ALT_ID, the password in the SHP_ACCESS_CODE, and the name in SHP_NAME. The value in core.security.newUser.roles is stored in SHP_KEY_LIST, and the value in core.security.newUser.userClass is stored in SHP_FILTER.

DAP_APPLICNT_MST

A DAP_APPLICNT_MST record is added when a user saves goal data. The selected school and degree goals are stored in the DAP_SCHOOL and DAP_DEGREE fields, while the selected term is converted to the correct catalog year using the STU016 Catalog Year and is stored in DAP_CATALOG_YR.

DAP_APPDATA_DTL

A DAP_APPDATA_DTL record is created for each goal item selected when a user saves goal data. The goal type is stored in DAP_GOAL_CODE. Valid values are CAMPUS, COLLEGE, CONC, MAJOR, MINOR, and PROGRAM. The selected goal value code is stored in DAP_GOAL_VALUE.

DAP_TRANSFER_DTL

A DAP_TRANSFER_DTL record should be created for each class or exam the user enters.

For classes, the DAP_SCHOOL_ID is the RAD_ETS_CODE for the selected school while the DAP_TR_DISC, DAP_TR_CRSE_NUM, DAP_TR_TITLE, DAP_TR_CREDITS, DAP_TR_CR_METHOD, and DAP_TR_GRADE should be the values provided for the selected class.

For exams, the DAP_SCHOOL_ID is TESTS, while the DAP_TR_DISC is the test code, the DAP_TR_TITLE is the test description from STU314, DAP_TR_START is the test date (if entered), and DAP_TR_GRADE is the score provided for the exam.

RAD_PRIMARY_MST

When a user creates an account, a RAD_PRIMARY_MST record is created for that user with the email stored in RAD_EMAIL and the name in RAD_NAME.

Transfer Equivalency Self-Service deployment

Transfer Equivalency Self-Service is designed to deploy equally well in on-premise and cloud-hosted scenarios on all supported platforms. It provides a mobile-ready, responsive user interface communicating with the servers using lightweight, stateless, restful API over HTTP SSL.

The TransferApplication deployment artifact is a JAR file that is executable using java and includes an embedded container.

Prerequisites

Transfer Equivalency Self-Service requires prerequisites in its setup.

  • Java:

    Java version 17 is the only third-party dependency required to run this application. Oracle Java and OpenJDK are supported.

  • SSL:

    Ellucian recommends SSL, because the security implementation uses stateless tokens. Using signed certificates is recommended for all deployment scenarios, including test or development environments. Self-signed certificates, even for internal test deployments, can be problematic because of browser requirements and warnings. The SSL certificate needs to be configured in a keystore, and that keystore needs to be accessible in the deployment environment. There are various options for how to do this, for example using Java's keytool command.

Deployment examples

When the prerequisites and configuration are in place, start the application using a java -jar command.

java $JAVA_OPTIONS -jar TransferApplication.jar

Transfer Equivalency Self-Service environment settings

Several environment variables are required to be configured before running the application. Several Shepherd settings are also required but they are only used at runtime so they can be configured or changed while the application is running without restarting.

Depending on the desired deployment platform there are many options for how these environment variables can be configured. The only requirement is that they are available in the environment where the product's JAR files will be executed. For example, it may be desirable to configure them in a shell script, in a specific user's profile, a startup instruction like init.d, or in a continuous deployment tool like Jenkins.

The minimum required variables are documented here. But many optional variables are provided in the Spring Boot platform, for example tuning the embedded container. Please refer to Spring documentation for those: http://docs.spring.io/spring-boot/appendix/application-properties/index.html.

Environment Variables are the recommended method to configure these properties. But there are various other ways these can be configured. Please refer to this documentation for more information: https://docs.spring.io/spring-boot/reference/features/external-config.html.

Required environment variables for TransferApplication

  • DW_DATASOURCE_URL: A JDBC connection string for the Degree Works database. For example jdbc:oracle:thin:@{SERVER}:{PORT}/{SERVICE_NAME} where {SERVER} is the address, {PORT} is the port of the listener, and {SERVICE_NAME} is the service name of the database.
  • DW_DATASOURCE_USERNAME: The database username.
  • DW_DATASOURCE_PASSWORD: The database password. If you want to hide this password using an encrypted string, see the Database credentials changes topic.
  • SERVER_PORT: The desired port for TransferApplication. This must be different from the ports used by other applications on this server.
  • SERVER_SERVLET_CONTEXT_PATH: An optional context path. If this is blank, the application will be deployed at the root URL like https://myserver.edu:NNNN (where NNNN is the SERVER_PORT). If a value is specified like /my-context-path, the application would be accessible at a URL like https://myserver.edu:NNNN/my-context-path (where NNNN is the SERVER_PORT).
  • SERVER_SSL_KEY_STORE: The path to a keystore file you created to contain your SSL certificate.
  • SERVER_SSL_KEY_STORE_PASSWORD: The password for your keystore file.
  • SERVER_SSL_KEYSTORETYPE: The type of your keystore. JKS is the default.
  • SERVER_SSL_KEY_ALIAS: The alias of the key you created.

Optional environment variables

  • JAVA_OPTIONS: The memory allocation for the application can be defined using this variable, and is recommended. The value defines the initial heap size and max heap size and is in the following format: -Xms1024m -Xmx1024m. The heap size values should be adjusted as appropriate for your server.
  • SERVER_MAX_HTTP_HEADER_SIZE: This setting allows you to set the maximum size of the HTTP message header. By default, this is 8KB, and for some users with a large number of Shepherd access keys, this can be too small. It’s recommended to use this variable and set it to at least 12KB. For example:
    export SERVER_MAX_HTTP_HEADER_SIZE=12288
  • SERVER_TOMCAT_REDIRECT_CONTEXT_ROOT: Embedded Tomcat for Spring Boot has a default behavior to redirect a request without a trailing slash to one with a trailing slash. However, that redirect happens without evaluating forward headers like X-Forwarded-Proto. So, when SSL offloading is in place, the redirect happens to http instead of https. This can be an issue especially for load balanced environments. To disable the default behavior, set this variable to false.
    Warning: You should do this only if the default behavior is not working. If you are offloading SSL at a proxy or load balancer, see the Load balancing and proxies topic. Then, if you have problems accessing the application in the browser when you do not include a trailing slash at the end of the request, try setting this variable to false.
  • DEBUG: A boolean true or false which will enable or disable debug logging. The log file is by default named treqss.log. But, the location and name of that file can be customized by setting an environment variable LOGGING_FILE. The log can also be accessible through an API with administrative authorization. Please refer to logfile in the Monitoring section of this documentation, below.
  • DEPLOY_LOCATION: the location of the TransferApplication.jar file. This location should be set then referenced in the java -jar command that starts the application.
  • LOGGING_FILE: the name of the file including the path location. If this is specified, the LOG_PATH should not be used.
  • LOG_PATH: the location of the log file. The default PATH location is the Java temporary java folder from the Java property java.io.tmpdir. This is usually /tmp. The file name will be treqss.log for TransferApplication.
  • LOG_DEFAULT_THRESHOLD: If set to DEBUG, the application will output more verbose logging. Debug output will be sent to the log during the startup process and for all requests thereafter. Warning: this will result in very large log files. If not set, the debug threshold is INFO.
  • DW_ENABLE_MONITOR - This environment variable can be set to enable /health, /metrics, /prometheus, and /status endpoints for health and monitoring metrics. By default, this monitoring functionality is not enabled. Adding this variable to an application's startup script and setting it to true would enable these endpoints for the application. See individual API documentation in the API Catalog for additional information.
  • DW_RABBITMQ_SSLALGORITHM: Specify the SSL algorithm to use when connecting to the RabbitMQ broker using SSL. If not specified, it uses the current RabbitMQ driver's default (at least TLSv1.2). This is only considered if the Shepherd setting core.amqp.useSsl is set to true.

Database pooling configuration

For production deployments, you can configure the size of the database connection pool through the following environment variables:

  • DW_DATASOURCE_INITIAL_SIZE: The initial number of connections that are created when the pool is started.
  • DW_DATASOURCE_MIN_IDLE: The minimum number of active connections that can remain idle in the pool, without extra ones being created.
  • DW_DATASOURCE_MAX_IDLE: The maximum number of connections that can remain idle in the pool, without extra ones being released.
  • DW_DATASOURCE_MAX_TOTAL: The maximum number of active connections that can be allocated from this pool at the same time.

For more information, see the Java database pooling configuration topic.

Transfer Equivalency Self-Service navigation

Users can navigate through Transfer Equivalency Self-Service using the application header bar and icons on each page.

Help

Users can access online help by clicking the help icon on the header bar.

Mega menu

Users on a mobile device can navigate through the application using the mega menu on the header bar.

Log out

The log out button displays on the header bar only if the user logs in to an existing account, or creates an account either from the landing page or while saving data from within the application. When the application is used anonymously, the log out button does not display.

Breadcrumbs

On the header of each page in Transfer Equivalency Self-Service, breadcrumbs indicate user progress and allow navigation between the steps.

A breadcrumb is bold for the current step, active but not bold for a previous stage, and greyed out for a future stage.

When a user is on the academic goals page, the Goals process waypoint is bold, while Classes, Exams, and Audit are greyed out and inactive. When a user selects all of the required goal data, the Classes, Exams, and Audit process waypoints become active and the user can click them to navigate to other steps in the process.

Start over

The start over button displays on the header of each page in Transfer Equivalency Self-Service and is enabled when unsaved edits exist. Selecting the start over button takes the user back to the academic goals page and resets input data. For a user who hasn't saved any data, all selected goals and entered classes/exams are cleared. For a user who has saved data and logged in, all selected goals and entered classes/exams are reset to the values from the last save, and any changes to selected goals and entered classes/exams are lost.

Save

The Save button displays on the header of each page in Transfer Equivalency Self-Service and will be inactive until the user makes a change to goals or classes/exams. If the user is logged in, clicking the button updates the saved goals, classes, and exams in the database. If the user is not logged in, a prompt appears to create a new account to save data. The user is not able to log in to an existing account from within the application, only from the landing page.

External links

You can configure an unlimited number of external links to display on the header of each page in Transfer Equivalency Self-Service, which show in the More menu.

To add an external link, you need to add the label for the button in TransferMessages.properties and add a Shepherd setting in Controller with the URL. The Shepherd setting and properties file label should be in the format treq.selfService.nextSteps.##, where # is a sequence number and must match. The sequence numbers do not need to be consecutive, but the links display in sequence order. A good practice is to use sequence numbers with a gap that leave some room to insert additional links at a future date, positioned as desired, without having to modify existing settings. For example, sequence numbers of 10, 20, 30 would be a good pattern because then you can decide later that you want to insert a new one at the second position by giving it a key of 15.

For an example, you could add the following settings in Controller:

Key Value
treq.selfService.nextSteps.10 https://www.yourschool.edu/application
treq.selfService.nextSteps.20 https://www.yourschool.edu/moreinformation

In TransferMessages.properties, you would add the following labels: 

treq.selfService.nextSteps.10=Apply for Admission
treq.selfService.nextSteps.20=More Information

Getting started with Transfer Equivalency Self-Service

On the landing page, prospective students can select how they want to use the application.

The user has the option to continue anonymously without signing in, logging in with a previously created account, or creating a new account.

If the treq.selfService.enableAnonymous Shepherd setting is false, the Continue without signing in button does not display.

If the treq.selfService.persistence.enableShpAccount Shepherd setting is false, the Have an account? Log in and Create an account buttons and the Save icon on other pages do not display.

Note: Both of these settings cannot be false, at least one should be true.

Account creation

When a user clicks the Create an account button, they are prompted to provide an email address, name, and password. These are required fields and cannot be left blank. A SHP_USR_MST record is created for the user and the data provided by the user is stored as the SHP_ALT_ID, SHP_NAME, and SHP_ACCESS_CODE, respectively. This user is able to save their work and log in again with these credentials. The values for core.security.newUser.roles and core.security.newUser.userClass are stored as SHP_KEY_LIST and SHP_FILTER, respectively.

You must review the following Shepherd settings to ensure they are configured correctly for your environment:
  • core.idFactory.idPrefix
  • core.security.newUser.roles
  • core.security.newUser.userClass
  • treq.selfService.enableAnonymous
  • treq.selfService.persistence.enableShpAccount

Existing account login

When a user clicks the Have an account? Log in button, they will be prompted for a previously saved email address and password. These are required fields and cannot be left blank.

Academic goals selection

To get started on the Select your academic goals page, users provide some information about their degree goals by answering questions about their intended enrollment term, degree, major, level, and other information, making selections from the drop-down lists.

Mandatory questions are designated with an *, and users will not be allowed to proceed until they select an answer from the drop-down list.

As selections are made, the response will show under the question.

Users can jump to different questions if they want to make a change to their responses. However, they will not be able to jump to optional questions until all required questions have been answered.

When they have completed their selections, the wizard moves to the Classes page. If any required fields have been skipped, users are not able to move forward until they are answered.

You can configure Transfer Equivalency Self-Service to use no filtering, curriculum rules, or a specific form of filtering to filter the goal data drop-down lists with the core.whatIf.filterMode Shepherd setting. Additionally, you can configure which goal data can be used for filtering, required goal data and other behavior.

Academic goals with no filtering

When Transfer Equivalency Self-Service is configured for no filtering rules (core.whatIf.filterMode = N), standard UCX filtering will be used in the academic goals drop-down lists.

Term, Level, Degree, and Major are required goal data items for a transfer audit. Additional academic goals can be configured to display.

Term will always display and is a required field. The term drop-down list will be populated with all STU016 values with Show in Transfer Equivalency Self-Service = Q or B. Note that the value in STU016 Catalog Year for each term configured to display in Transfer Equivalency Self-Service must be valid in STU035 and have STU035 Show in Transfer Equivalency Self-Service Picklist = Y.

Level will always display and is a required field. The level drop-down list will be populated with all STU350 values with Show in Transfer Equivalency Self-Service Picklist = Y.

Degree will always display and is a required field. The degree drop-down list will be populated with all STU307 values with Show in Transfer Equivalency Self-Service Picklist = Y.

Program can be configured to display and will be optional if displayed. The program drop-down list will be populated with all STU316 values with Show in Transfer Equivalency Self-Service = Y.

Major will always display and is a required field. The values in the major drop-down list will be all AUD027 values with Show in Transfer Equivalency Self-Service = Y.

Campus can be configured to display and will be optional if displayed. The campus drop-down list will be populated with all STU576 values with Show in Transfer Equivalency Self-Service Picklist = Y.

Minor can be configured to display and will be optional if displayed. The minor drop-down list will be populated with all AUD029 values with Show in Transfer Equivalency Self-Service = Y.

College can be configured to display and will be optional if displayed. The college drop-down list will be populated with all STU560 values with Show in Transfer Equivalency Self-Service Picklist = Y.

Concentration can be configured to display and will be optional if displayed. The concentration drop-down list will be populated with all STU563 values with Show in Transfer Equivalency Self-Service Picklist = Y.

Transfer classes entry

On the Classes page, users can enter transfer class information that could be articulated and applied to their intended goal.

Entering transfer classes is optional. Users can proceed to Exams or Audit without adding transfer classes by clicking Skip.

To add a transfer class, the user must first select a transfer school, then select the transfer class, and then enter in the class information.

The list of transfer schools is populated with the schools for which you have mappings in DAP_MAPPING_DTL. The city and state that displays comes from the RAD_ETS_MST for that school, if this record exists. Schools are listed in alphabetical order by school name.

The list of transfer courses is populated from the mappings for the selected school. Courses are listed in alphabetical order by transfer course discipline and number.

For the class details, the user selects the term in which they took the class, how many credits they received, the grade they earned, and if enabled, the credit type.

The options in the Term drop-down list are all terms in STU016 with the Show in Transfer Equivalency Self-Service flag = Y or B.

The Credits field allows numeric values only and follows the format defined in the core.credit.format Shepherd setting.

The options in the Grade drop-down are all grades in STU398 with the Show in Transfer Equivalency Self-Service flag = Y.

When treq.selfService.showCalendarType is true, the Credit Type drop-down displays. It contains all values in STU346 with the Show in Transfer Equivalency Self-Service flag = Y. If the RAD_CALENDAR field on the selected schools RAD_ETS_MST is a valid value in STU346, the value loads as the initial default. If it is not, the core.institution.calendarType Shepherd setting value loads as the default.

When treq.selfService.showCalendarType is false, the user does not have to select the credit type when adding a transfer class. The articulation engine uses the RAD_CALENDAR value from RAD_ETS_MST for the selected school if it matches a valid entry in STU346; otherwise, it uses the core.institution.calendarType Shepherd setting.

After entering the transfer class details, the user can select to add another class from the same school, a class at a different school, a placement exam, or run the transfer audit. After selecting one of the options, the class data the user entered is added to the My transfer work panel. Classes are not saved to the database until they have been added to My transfer work and the user clicks Save.

The My transfer work displays transfer classes and placement exams. Exams are ordered by the test name, and classes are ordered by school then by course discipline and number.

To edit a class, users click the Edit icon to the right of the class. The class loads in the Edit Transfer Class dialog window, and after editing the transfer class, users should click Done.

To edit an exam, users click the Edit icon next to the exam. The exam loads in the Edit Placement Exam dialog window, and after editing the placement exam, users should click Done.

Audit generation

On the Audit page, prospective students can view transfer audits showing how the classes and exams they added might articulate and apply to their selected program goal.

After the required goal questions have been answered, a prospective student can access the Audit page either by selecting the I'm all done and would like to run a transfer audit option on the Classes or Exams pages, or by clicking the Audit process waypoint in the navigation breadcrumb. You can define the report format to be used for the transfer audit in the core.treq.selfService.auditArticulate.report.default Shepherd setting. This must be a valid value in RPT036 and is typically TRQ31. The RPT036 flags for defined report format are used to configure the transfer audit.

Auto resolution

You can configure Transfer Equivalency Self-Service to resolve duplicate and undecided situations automatically based on a set of defined rules.

Rather than returning an unresolved articulation, if more than one matching mapping is found (an undecided scenario), or if the student has more than one transfer class that maps to the same course(s) at the transfer school (a duplicate scenario), you can define a hierarchy of resolution rules, and if a match still cannot be determined after working through the hierarchy, it will check the defined rule of last resort.

You can configure transfer classes for which no mapping is found to map to a generic course in the articulation.leftoverCourse.courseDiscipline and articulation.leftoverCourse.courseNumber Shepherd settings. These classes are then be counted in the overall degree credits and can apply to rules on the transfer audit.

There are several resolution options that you can use in the articulation.resolutionRules.duplicate and articulation.resolutionRules.undecided Shepherd settings. These options are applied in list order until a final mapping is found or until all resolution options have been tried.

CREDITMAX

For all the potential mappings, add up the total amount of credits that would be awarded in each. The mapping that would result in the most transfer credits wins.

For example, you can have the following Undecided situations:

a. MATH 101, MATH 102 -> MATH 200, MATH 300, MATH 400
b. MATH 101, MATH 103 ->MATH 51, MATH 22

or

c. ENG 35, ENG 36, ENG 37 -> HUMN 104
d. ENG 35, ENG 38 -> ENG 200

In case a, MATH 101 is part of a pair of transfer classes that maps to three local classes. In case b, the transfer class pair maps to a pair of local classes. Though all that matters is the total number of credits awarded by the local classes. If the total transfer credits in the case b is 10 and case a is 8, CREDITMAX says the articulation engine would choose case b.

Similarly, in Case c and d, even though ENG 35 is part of a transfer class pair in one mapping and a trio in another, all that matters is if HUMN 104 awards more or fewer credits than ENG 200.

LOCALHIGH

Use the mapping with the highest numbered local course (course at the target school). You can use it any time transfer classes can be mapped to more than local course.

a. MATH 101, MATH 102 -> MATH 200, MATH 300, MATH 400
b. MATH 101, MATH 103 ->MATH 51, MATH 22

or

c. ENG 101 ->ENG 200
d. ENG 101 -> ENG 500

or

e. ENG 101 -> ENG 200
f. ENG 102 -> ENG 200

In case a and case b, MATH 400 is the highest numbered local course in any of the resulting mapping options, so that is the option the articulation engine would choose.

Similarly, in case c and case d, ENG 500 is the highest numbered local course, so the articulation engine would choose it if using LOCALHIGH.

In case e and f, both local courses are the same, which is a duplicate situation. In this case, LOCALHIGH would have no effect in resolving the mapping and the auditor engine would move to the next resolution option, so it really should not be used at all. However, if it is used, it would not cause any errors.

Course numbers are compared numerically to determine which is highest (alpha characters are stripped out and the resulting integer is used). That means that MATH 30L, CALC 30, and STAT 3H0 are the same number.

TRANSFERHIGH

Use the mapping with the highest numbered source class (the classes taken by the student).

a. MATH 101, MATH 102 -> MATH 200, MATH 300, MATH 400
b. MATH 101, MATH 103 ->MATH 51, MATH 22

or

c. ENG 101 ->ENG 500
d. ENG 102 -> ENG 200

or

e. ENG 101 -> ENG 200
f. ENG 101 -> ENG 500

In case a and case b, MATH 103 is the highest numbered transfer class in any of the resulting mapping options, so that is the option the articulation engine would choose.

In case c and case d, ENG 102 is the highest numbered transfer class, so it is the option the articulation engine would choose.

In case e and case f, the same transfer class is used in both mapping pairs, so TRANSFERHIGH would not lead to a resolution, and the articulation engine would need to move to the next option.

As with LOCALHIGH, class numbers are compared numerically.

RECENT

Use the class that was taken most recently. This applies only to transfer classes. The term would determine which class was most recent (for example, Spring 2023 is more recent than Fall 2022).

RANDOM AND NONE

RANDOM allows the auditor to pick a mapping arbitrarily. This resolution option could lead to different results each time. NONE tells the auditor to not resolve this mapping.

a. MATH 101, MATH 102 -> MATH 200, MATH 300, MATH 400
b. MATH 101, MATH 103 ->MATH 51, MATH 22

In case a and case b, RANDOM means the auditor may choose a one time and b the next.

Ellucian recommends using RANDOM as the rule of last resort rather than NONE.

REPEAT POLICY AND RESOLUTION OPTIONS

The RAD_COURSE_MST.RAD_REPEAT_MAX for the target school class can affect the resolution option. That field can be set to a value between 1 and 99 or Y, which indicates that a class can be repeated an infinite number of times.

For duplicate situations, this means that multiple source school classes can articulate to the same target class. For example:

MATH 101 -> CALC 100
MATH 102 -> CALC 100

If CALC 100 has RAD_REPEAT_MAX set to 1-99 or Y, both classes articulate to CALC 100 in a transfer audit.

Transfer Equivalency Self-Service localization

You can localize the color scheme, logo, text, labels, and messages in Transfer Equivalency Self-Service for your institution.

Theme

Use Controller to define the color and logo to be used by Transfer Equivalency Self-Service in the theme.* Shepherd settings. If you have localized these settings for Responsive Dashboard with the default specification, Transfer Equivalency Self-Service automatically uses them as well. Optionally, you can define different values for Transfer Equivalency Self-Service by adding a treqss specification.

To change the color theme of your Transfer Equivalency Self-Service deployment, specify the Hex color code for the primary color in the theme.color.primary Shepherd setting and secondary color in the theme.color.secondary Shepherd setting. The call to action color has limited configurability and is defined in the theme.color.tertiaryName Shepherd setting. You must select an option from the drop-down of available colors.

To change the logo, specify the URL of the graphic to be used in the theme.url.logo Shepherd setting. This URL must be accessible to users of Transfer Equivalency Self-Service and so may need to reside outside your network and firewall. You must also add the host server to the Content Security Policy (CSP) by adding it to the core.security.contentSecurityPolicy.imgSrc Shepherd setting.

Language properties

You can localize the text, labels, and messages in Transfer Equivalency Self-Service for your institution using the Properties function of Controller. The properties used by Transfer Equivalency Self-Service are:

  • TransferMessages.properties
  • PDFAuditMessages.properties

You can add header text to each page using the *.headerText properties. By default, most of these properties have an empty value so that no text shows.

To add header text to any page, copy and paste the properties you want to localize from the Baseline Language Property editor pane to the Localized Language Property editor pane. For example, to add header text to the top of the Goals page, copy transfer.selfService.academicGoal.headerText from the baseline editor and paste into the localized editor and add whatever text you like.

The header text default color is black. To change the default color to be used in your header text, localize the *.headerText.fontColor properties. The color options are primary, secondary, and cta (call to action), each corresponding to the three colors defined in Transfer Equivalency Self-Service. For example, to set the Goals page header text to a different color, set its property like this:

 transfer.selfService.academicGoal.headerText.fontColor=secondary

You can do the same for the font weight, which is either bold or normal. The default weight is normal. To set the default weight for the Goals page header text to bold, set the fontWeight property like this:

transfer.selfService.academicGoal.headerText.fontWeight=bold

To add line breaks and tabs in your header text, use newline (\n) and tab (\t) characters. For example:

transfer.selfService.academicGoal.headerText=This is line 1 of the text.\nThis text is on line 2.\nThis text is on line 3.There is a tab \t here also.

The text would appear on the Goals page like this:

This is line 1 of the text.
This text is on line 2.
This text is on line 3. There is a tab     here also.

In the following example, you would also use the line-continuation backslash character to make it easier to read and edit in Controller. Any time you use newline (\n), it is good to also use the line-continuation character (\) and place the next set of text on the next line. The formatting of the text in Controller will then closely match what you see on the dashboard. Be sure there is not a space after the line-continuation backslash. A space after a backslash will prevent the header text from displaying.

transfer.selfService.academicGoal.headerText=After entering in your intended academic program goals you can: \n\
\t * Enter the classes you completed at other institutions \n\
\t * Provide the placement exam scores you have received \n\
\t * Generate a transfer audit to see how your coursework might apply \n\
Please contact an admissions counsellor if you need assistance.

For more information about how to localize application properties, see the Localize language properties in an application topic.

Transfer Equivalency Self-Service debugging

Transfer Equivalency Self-Service users can enable debugging from the application to troubleshoot session issues.

Users with access to this functionality can enable and disable debug from a page in Transfer Equivalency Self-Service. Most debugging output for the application is aggregated into one file, even if multiple applications or APIs are involved. Access to the application server is not needed, and the application does not need to be restarted. However, access to the server is required to access the generated log file, which will be in the logs directory of the application server.

To debug issues for anonymous users, the DEBUG Shepherd key should be assigned to the user defined in the core.security.referenceUser.username setting, which is typically TREQER, using the Users function of Controller. All anonymous users will then see the Debug link in the header bar. Note that if core.security.referenceUser.username has the DEBUG key and a user signs in with an existing account or creates an account, they may see the Debug link while on the landing page. However, it will no longer appear after they enter credentials, unless the DEBUG key has also been assigned to that user.

For users with an existing account to debug issues, you should assign the DEBUG Shepherd key to that user with the Users function of Controller. After logging in, they will then see the Debug link in the header bar.

For users creating an account to debug issues, you should assign the DEBUG Shepherd key in the core.security.newUser.roles Shepherd setting. After creating an account, they will then see the Debug link in the header bar.

Clicking the Debug link will take users to the Debug page. On that page, they should select the Enable Debug toggle to turn debugging on for the Transfer Equivalency Self-Service application.

A random Debug Tag will be generated, and users can copy this to their clipboard by clicking on the page icon. The debug tag is appended to each line of debug in the log file so that users can easily identify which lines are from their session, as opposed to other users using the application at the same time.

After enabling debug, users can resume using Transfer Equivalency Self-Service by clicking the Goals process waypoint and then executing the steps to duplicate the issue they are experiencing. Debug should be turned off by going back to the Debug page and selecting the Enable Debug toggle when the issue has been duplicated. Debug for this session is also turned off when they log out of the application.

Debug will appear in the Transfer Equivalency Self-Service log file on the application server. This is typically defined by the $LOGGING_FILE environment variable. Searching for a user's Debug Tag will isolate the lines of debug specific to their actions. For example:

2023-10-24 16:22:23,144 68b4e19d-3fb4-4975-9815-83eea01266ff DEBUG [41-exec-17] .h.d.s.s.StatelessPreAuthenticatedFilter : Checking secure context token: null

The packdebug script can be used to collect the log files generated for a user session Debug Tag. For more information, see the packdebug script topic.
