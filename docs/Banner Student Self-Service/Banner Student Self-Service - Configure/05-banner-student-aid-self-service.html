BSA Self-Service configuration

This section describes Self-Service related configuration elements.

Web access

To be able to access BSA Self-Service pages, the following must exist.

  • The individual must have a person Banner™ ID.
  • The Banner ID must have the BSA Web role, which occurs when either of the following occurs.
    • The STUDENT Web role is assigned automatically (GOVROLE_STUDENT_IND = Y) when a Student record is created for the person in the SGBSTDN table (Student record).
    • The BSA Web role is assigned automatically (GOVROLE_BSAC_IND = Y) when an Admissions record is created for the person in the SARADAP table (Student record).
  • The Banner ID must have a third-party access record in GOBTPAC table.

Web trees

The model for building your student aid web pages using the Tree Application Form Definition (KVATAFD) is called a "tree."

  • A tree is composed of a set of objects, and the attributes attached to them are called "properties".
  • An object is a node in the tree that, along with its properties, generates the set of web pages attached to an application form.
  • Properties are attributes that are assigned to an object for the purpose of defining the layout of the web page that is being built.

A tree does not need to have all object types, nor do the objects need to be displayed in any particular order. You can have many versions of web trees, including multiple trees with similar or very different designs for a given aid year and aid period, depending on the needs of your institution.

Web tree objects use parent/child relationships.

An application form can be configured to have multiple module objects in the tree. When the application form is displayed on the Web, each module in the tree along with its child objects (nodes) will constitute a web page. This means that the application form will be composed of as many web pages as you have modules assigned to the tree. The web page for a module is dynamically displayed at runtime by taking all objects and object properties that belong to the module and displaying them in the page. The object properties are used to determine the appearance of the objects in the web page. The module web page is dynamically displayed by the bwvkkapf.P_ShowModulePage procedure. Although the generated module web page has the "look and feel" of Web Tailor, the page cannot be customized in Web Tailor as all the page characteristics are taken from the objects, properties, and property values defined in the application form tree.

Note: When working with 9x Self-Service, Ellucian recommends creating at least one question along with declaration text, to ensure declaration statement display.

Web tree objects

This section describes web tree objects that can be displayed on your student aid web pages.

The following web tree objects are available:

  • Application form objects
  • Module objects
  • "Select a Specific Award" objects
  • Section objects
  • Question objects
  • Tracking requirement objects
  • Text objects

Not all objects must appear on an application form, nor must they appear in any particular order, other than observing proper parent/child relationships.

Application form objects

An application form object is the highest-level ("root") object in a web tree, and is the parent to all the objects that belong to the application form tree.

Properties that can be assigned to application form objects include the following:
  • Label
  • Information text
  • Footer information
Module objects

A module object has an application form object as its parent.

An application form can have one or more modules associated with it.

A module identifies the segment of student aid in which an applicant is interested when applying for awards through Self-Service.

The following are examples of modules:
  • Applying to Need based Awards
  • Applying to Merit based Awards
  • Applying for a Loan
A module can be classified as one of the following types:
  • Need Analysis (NA) module, in which the following apply:
    • Module to which an applicant applies for need
    • Composed of one or more "budget group section" objects under which there are one or more “budget group question” objects
    • Budget group calculation is automatically enforced when an applicant answers the budget questions
    • Composed of one or more “budget component section” objects (for each budget group) under which there are one or more “budget component question” objects and, optionally, “tracking requirements for a budget component” objects

      An example of a need analysis module is Applying for Need.

  • Generic (GE) module, which is composed of one or more “plain section” objects under which there are one or more “generic question” objects, or one or more “text” objects that, when concatenated, define the page where your institution requests consent from the applicant for a particular subject (such as disclosure of information).

    Examples of generic modules are Applying for Merit Awards, Declaration Page, and so on.

  • Awards (AW) module, in which the following apply:
    • Module to which an applicant applies for specific awards, such as scholarships, bursaries, loans, work study, and so on
    • Composed of one or more “select a specific award” objects, under which there can be one or more “specific award section” objects, which in turn can have one or more “award question” or “tracking requirement for a specific award” objects

Although an application form can have various modules associated with it, there are restrictions related to the type of module that the application form can have. These restrictions are as follows.

  • An application form can have only one module of type NA (Need Analysis).
  • An application form can have multiple modules of type GE (for example, one for Merit, one for Declaration, and so on).
  • An application form can have multiple modules of type AW (for example, Specific Awards, Loans, Work Study, and so on).
Properties that can be assigned to module objects include the following:
  • Header information
  • Label
  • Information text
  • Footer information
  • Declaration module (assigned to Generic module type only)
  • Required module
  • Process Type for an Award Module (assigned to Award module type only)

A module can be required or optional. This feature is controlled using the required property for the module.

  • It is not necessary for all questions to be answered for a module to be marked as complete.
  • When a module is not required, the applicant does not need to mark it as complete, as the system will do so automatically. When the application form is saved, the system verifies that modules that are required were completed, and for the ones that are not required and were not marked as complete, it marks them as complete automatically.
    Note: If the module is of the Award (AW) type, all answers are stored but the award will need to be removed from the KVRSAWA table if not all questions have an answer.
"Select a Specific Award" objects

The “select a specific award” object is described in this section.

A “select a specific award” object has an award module as its parent, and is composed of one or more “select a specific award” objects, under which there can be one or more “specific award section” objects, which in turn can have one or more “award question” or “tracking requirement for a specific award” objects.

Properties that can be assigned to “select a specific award” objects include the following:
  • Award code
  • Award label
  • Information text
  • Footer information
Section objects

A section object has either a module object or a "select a specific award" object as its parent. A specific award module can have one or more sections associated with it.

A section identifies a group of elements with common characteristics based on a given functionality. The following are examples of sections:
  • Parent 1 information
  • Parent 2 information
  • Existing debt information
  • Non-academic expense information
  • Academic information (about grades, and so on)
A section can be classified as one of the following types:
  • Budget group section, in which the following apply:
    • Has a need analysis (NA) module as its parent
    • Composed of one or more “budget group question” objects
  • Budget component section, in which the following apply:
    • Has a need analysis (NA) module as its parent
    • Composed of one or more “budget component question” or “tracking requirement for a budget component” objects
  • Plain section, in which the following apply:
    • Has a generic (GE) module as its parent
    • Composed of one or more “generic question” or text objects
  • Specific award section, in which the following apply:
    • Has an award module as its parent
    • Composed of one or more “award question” or “tracking requirement for a specific award” objects
Properties that can be assigned to section objects include the following:
  • Label
  • Information text
  • Question header
  • Question information text
  • Footer information
  • Budget component label (assigned to budget component section type only)
Question objects

A question object has a section object as its parent.

A section can have one or more questions associated with it, and a question can be associated with multiple sections, but the same question code cannot be used twice in the same section. After you have associated a question with a section, that question code will not be available to be used again in the same section.

The same question can be associated with different sections in the tree, as explained in Sharing questions between modules. This allows you to ask the same question in different sections of different modules and application forms.

A question can be anything that you want it to be. For example, beyond using them to obtain typical applicant information, you can also use them as "substitute" fields if you need to get some information from an applicant and there is not another place within the BSA module for storing it. For example, you might need to store values for “Authorize university to verify my information” and “Release Indicator.” This can be done creating the following questions:
  • QAUVI - Do you authorize this institution to verify the information you have provided in this application?
  • QREL - Can we release your information to internal departments at this institution?

Your institution can then review the responses provided by the applicant for these questions and proceed as required based on the answers.

The following are examples of questions:
  • What is your marital status?
  • Parent # 1 Annual Gross Income?
  • Parent # 2 Vehicle Value?
  • If you already have a loan, how much do you currently owe?
  • Do you have any type of loan from external sources?
A question can be classified as one of the following types, depending on the parent to which the applicant is related:
  • Budget group question, in which the following apply:
    • Has a budget group section as its parent
    • Exists in the common pool of questions defined per aid year on the Question for Web Maintenance (KVAQUES) and stored in the KVRQUES table
    • The question is one for which the unique answers provided help to categorize an applicant in a specific budget group
  • Budget component question, in which the following apply:
    • Has a budget component section as its parent
    • Exists in the common pool of questions defined per aid year on KVAQUES and stored in the KVRQUES table
  • Generic question, in which the following apply:
    • Has a plain section as its parent
    • Exists in the common pool of questions defined per aid year on KVAQUES and stored in the KVRQUES table
  • Award question, in which the following apply:
    • Has a “select as a specific award” object as its parent
    • Exists in the common pool of questions defined per aid year on KVAQUES and stored in the KVRQUES table
Properties that can be assigned to question objects include the following:
  • Question code
  • Label
  • Text orientation
  • Information text
  • Footer information
Sharing questions between modules

A question can be shared by all modules that have the same aid year and aid period, regardless the application form.

For example, the question QBG1 (What is your marital status?) can be associated with the module MOD-NA (Applying to Need-Based Awards) and to the module MOD-LO (Applying for a Loan). In this case, the Need Analysis module, the Merit module, the Specific Awards module, the Loan module, and any others can share the same question/answer for the same aid year and aid period whether they belong to the same application form or not.

For another example, the application form UNDERGRADUATE and the application form GRADUATE can share the same question/answer for the same aid year and aid period.

The only restriction is that a common question cannot be updated by an applicant while an application form to which the question has been assigned is locked. In this case applicants can work on their student aid application forms, but any questions shared by application forms of the same aid year and period that are locked at that point in time will not be able to be updated until they are unlocked.

As a general practice, it is not recommended that you lock any data before the deadline so that applicants can work on their applications and apply all the changes they want until the deadline date has arrived. Then, student aid users can start locking the applications.

Two questions with different codes (such as QBG1 and QLO5) but identical descriptions can be created; however, the system considers the questions to be unique because they have been defined with different codes. This is helpful if a user wants to assign questions to a particular object (such as a specific section, module, or application form in which they will be asked). The user can create new codes with question values that are used in existing codes. In other words, it is the question code that differentiates one question from the other and not the description associated to it. Based on this, the following questions are unique and considered two separate instances when they are related to a section of a module and application form:
  • QBG1 - What is your marital status?
  • QLO5 - What is your marital status?

Questions cannot be shared between sections of the same module when the module is Generic (GE) type.

For a Need Analysis (NA) type module, questions can be shared between sections of the same module. However, we recommend that the question is not repeated for the same budget components that are associated with the same budget group because it would appear to the applicant that the same question was being asked.

For an Awards (AW) type module, questions can be shared between sections that belong to different award codes, as long as the question is associated to the corresponding award in the KVRQUFN table.

For example, let’s say you have an award module MOD-LO (Applying for a Loan). The following sections are associated with that module.

Loan-1 SECTION-LO11 QBG1-What is your marital status?

QBG2-Do you have any dependent children?

QBG3-Where will you live while attending this institution?

QBG4-Have you graduated from a post secondary institution or lived away from home for more than 2 years?
SECTION-LO12 QBC50-Do you have any type of loan from external sources?

QBC51-If you already have a loan how much do you currently owe?
Loan-2 SECTION-LO23 QBC40-What is the average amount you expend in food monthly?

QBG2-Do you have any dependent children?
Based on the rules for sharing questions for an Awards (AW) type module the following principles for QBG2, shown in bold, are in effect:
  • Question QBG2 cannot be associated more than one time to the SECTION-LO11.
  • Question QBG2 cannot be associated to section SECTION-LO12 because that is associated to the same award (Loan-1).
  • Question QBG2 can be associated to SECTION-LO23 because that section belongs to a different award (Loan-2)
Furthermore, a question that is being shared by two modules of the same aid year and aid period can be updated in both modules if the following conditions exist:
  • Application form to which the question is associated has not been locked (this is when KVREMST_LOCK_IND is not Y).
  • Need analysis data that is using the answers from the questions has not been locked (this is when KVRNAAL_LOCK_IND is not Y),

If any application form to which a question is associated is locked, the question cannot be updated in the application form that is not locked.

Whenever the need analysis data has been locked, the following restrictions are in effect:
  • The applicant's budget group will not be calculated
  • The applicant's answers associated with the budget group questions cannot be changed
  • The applicant's answers associated with the budget component questions cannot be changed
Tracking requirement objects

A tracking requirement object has a section object as its parent.

A section can have one or more tracking requirements associated with it, and a tracking requirement can be associated with multiple sections, but the same tracking requirement cannot be used twice in the same section. When you have associated a tracking requirement with a section, that requirement will not appear with the listed values when you add further requirements in the same section.

A tracking requirement can be classified as one of the following types, depending on the parent to which is related:
  • Tracking requirement for a budget component, in which the following apply:
    • Has a budget component section as its parent
    • Exists in the Tracking Requirements Attached to Budget Component Table (KVRTRBC) (table to be delivered in a future release)
  • Tracking requirement for a specific award, in which the following apply:
    • Has a specific award section as parent
    • Exists in the Tracking Requirements Attached to Fund Code (KVATRFN) and stored in the KVRTRFN table
Properties that can be assigned to tracking requirement objects include the following:
  • Tracking requirement code
  • Tracking requirement label
  • Text orientation
  • Information text
  • Footer information
  • Document view text
  • Document upload link text

On a web page, a tracking requirement object is displayed as an item on the Additional Requirements page (bwvkkqry.P_DispTrackReq).

Text objects

A text object has a plain section as its parent as long as the plain section has a Generic (GE) module tagged with the property "declaration page."

This object is used to attach free text to a specific section that would behave, for example, like a declaration page or a page where an applicant is expected to answer some questions related to the release of information have provided as part of the student aid application.

The text orientation property can be assigned to text objects.

On a web page, a text object is displayed as text on the web page with which its parent is associated.

Style sheets

This section describes the classes’ sections used for each element in the BSA application.

The following classes' sections are used for each element:

  • BSA classes
  • NEED ANALYSIS classes

These are required for the system to properly display the BSA application form; otherwise, the application form does not show the proper fonts (hierarchically).

The names of the specific classes are as follows:
  • mod_ge_header - Used for the header of the Generic module
  • mod_ge_info_text - Used for the information text of the Generic module
  • sel_aw_info_text- Used for the Specific Award information text

The BSA and NEED ANALYSIS classes' sections are mandatory for BSA application form Self-Service pages. If your institution uses custom style sheets (CSS), you must copy these sections into you default style sheet file so that BSA can properly render the Self-Service pages.

Banner Document Management (BDM)

You can allow BSA Self-Service users to upload documents to BDM and to display and delete documents previously uploaded to BDM.

Only applicants can manage documents using BSA Self-Service; staff members manage documents using BSA pages.

To allow applicants to manage documents in BDM, you must define settings on the following pages:
  • Document Type Validation (ETVDTYP)
  • Banner Document Management - Student Aid Linking (KVALINK)

Refer to Link to Banner Document Management for details on how to set up the link between BSA and BDM, and to the Online Help for complete details about the pages.

In addition, the following fields on the Application Form Maintenance (KVAAPFR) control document uploading by an applicant on Self-Service when an application page is locked.

  • The Uploading Applicant Lock field in the Application Form Maintenance section allows you to specify whether applicants are allowed to upload, display, and delete documents for the specified application form, or whether the system is to use the settings on KVALINK when the application form is locked. If the Uploading Applicant Lock check box on the General Controls section of KVALINK is unchecked, that overrides the value set in this field.
  • The Uploading Applicant Lock field on the Applicant Expiry Date section work in a similar way to the Uploading Applicant Lock field in the Application Form Maintenance section. The field on the Applicant Expiry Date section allows you to specify whether a particular applicant is allowed to manage documents for the application form, or whether the system should use the value in the field on the Application Form Maintenance section of this page. After the application is expired for an applicant record on this section, the applicant cannot upload, display, or delete documents for tracking requirements associated with the application form regardless of if the application form is locked.
If desired, you can change the text for the links displayed on the Self-Service pages by changing the values associated with the following properties on KVATAFD:
  • Document view text
  • Document upload link text

Testing application forms

Testing application forms is described.

Using the testing mode, which can be set in the Tree Application Form Definition (KVATAFD), you can release an application form and let test users (that is, technical staff using test applicant IDs) apply and navigate a web application up to the point of entering data into the application form as real users would. Submitting an application is not allowed. If an application form needs to be changed, it can be returned to in-process mode using KVATAFD. This allows you to perform more complete "real life" testing before releasing a web application form to a production environment.

All BSA Self-Service pages can be tested by a test applicant (that is, an applicant who has a record set to Active in the Application Form Testing Table [KVRAPFT]) to use the pages when the application form has a status of Testing Mode (KVRAPFR_COMPLETION_IND = T).

Only tasks related to filling in an application form are allowed in testing mode. The test applicant is not allowed to submit the application form on the web but can perform other tasks. In addition, the test applicant can to go to the My Student Aid page (bwvkkqry.P_ShowAwards) to view awards but is not allowed to accept or decline any awards. Documents cannot be uploaded to, displayed in, or deleted from BDM when an application form is in testing mode. The test applicant can generate a PDF application at any time from the Application Summary page (bwvkkmen.P_AppForm). You can modify PDF headers in the Application Form PDF Header Field section of KVAAPFR while the application is in testing mode.

It is recommended that you use testing mode only in a test or pre-production environment and not in a production environment to avoid interfering with real production data.

The test applicant (even if an actual student) can view only the web applications that are in testing mode and for which the test applicant ID is set to Active on the Application Form Testing section on the Application Form Maintenance (KVAAPFR).

If an applicant ID is set to Active on KVAAPFR but the application is not in testing mode, the applicant will not see the application form. (If the applicant ID is active for more than one application form, any application forms that are in testing mode will be accessible.) The My Student Aid page will be accessible to the applicant, but the Accept and Decline buttons will not be displayed. For this reason, you should not leave test applicant IDs in active mode when testing is complete and the application form has been released.

Actual student users will not be able to access pages in testing mode.

Data that is created during testing of an application form is deleted from the relevant BSA tables when the application form is changed from Testing Mode to In-Process or Released (previously called Completed). This ensures that no test data is retained in tables used for live processing of applications.

Data stored in tables that are not used for live processing is not purged, and this data might appear in the following:
  • Applicant GPA (KVAAGPA)
  • Applicant Miscellaneous (KVAAMIS)
  • Applicant Tracking Requirements (KVAAREQ)
  • Applicant Institutional Award (KVAAWRD)
  • Aid Fund Code Donor Information (KVADONR)
  • Aid Fund Code Designator Information (KVADSGR)
  • Applicant Employment/Fellowship Award (KVAEMPL)
  • Government Aid Applicant (KVAGAID)
  • Identification Code Person (KVAIDCO)
  • Applicant Institutional Loan (KVALOAN)
  • Applicant Other Award (KVAOTHR)
  • Pre-Banner Award Data (KVAPBAW)
  • Disburse Institutional Awards Process (KVPDBIA)
  • Applicant Deferral Process (KVPFEDF)
  • Memo to Paid Process (KVPMOPD)
  • Mass Institutional Awarding Process (KVPMSIA)
When an application form’s status is changed from Testing Mode to In-Process, the following types of changes can be made:
  • Description of a question or answer (such as correcting a typo)
  • Properties of a question or answer (such as Info Text, label, header, footer, and so on)
  • Module adjustments (such as removing a module or rearranging modules)

In addition, when the application form is released to production and actual applicants have started to apply, you can change the description of a question or answer.

You also need to specify which applicant IDs can test an application form in the Application Form Testing section of the Application Form Maintenance (KVAAPFR). Only IDs specified in this section and assigned the status of Active can test the application form in BSA Self-Service.

If an applicant ID is set up in active status on the Application Form Testing section of KVAAPFR for any application form for which the value in the Completion Indicator field is Tree Under Construction, Tree Posted for Testing, or No tree exists, when that test applicant logs into BSA Self-Service, the applicant will not see anything other than test applications applicable to that ID.

An applicant ID can be set to active status on the Application Form Testing section of KVAAPFR only when the application form is in process or in testing mode. ID records are automatically set to inactive status when an application form is marked as in-process or released in KVATAFD and ID records cannot be removed if the application form is in testing mode.

Applicant ID records are automatically set to inactive status when an application form is marked as in-process or released in KVATAFD.

Applicant ID records cannot be deleted from this section if the application form is in testing mode.

Copy an application form

The following procedure explains how to copy the definition of one application form to another.

Procedure

  1. Access the Application Form Maintenance (KVAAPFR) page.
  2. Specify the record to be copied in the Key block.
  3. Go to the next block.
  4. Select Copy Application Form from the Options menu to open the Copy Application Form window.
  5. Specify the target application form, aid year, and aid period, then click OK.

    The details for the source record specified in the Key block continue to be displayed.

  6. Roll back and specify the new record in the Key block, then go to the next block to change details as desired.

Set up aid fund code aid year-period rules

Instructions on how to configure the aid fund code aid year-period rules.

Procedure

  1. Access the Aid Fund Code Aid Year-Period Maintenance (KVAFAYP) page.
  2. Enter the application form code, aid year, and aid period in the Key block, and go to the next section.
  3. If the application form is to be available for use on the Web, select the Open for applying via Web check box.
  4. Enter the start and end dates for the record specified in the Key block.
  5. Save your changes.

Set up questions and answers

Instructions on how to configure the questions and answers.

Procedure

Web application PDF output

You can allow applicants and staff members to generate web applications in PDF format.

Applicants can generate submitted web application PDFs using BSA Self-Service, while staff members can generate web applications at any time using the Application Form per Applicant for Web Tracking (KVAFAPP).

PDFs are generated in a "secured" format because they include confidential applicant information. Data in a secured PDF cannot be edited.

Depending on how you define the output for a particular web application, the following are included:
  • Optional institution-defined header section, which can contain multiple groups
  • Application data section, which contains the data provided by the applicant and the details pertaining to the application form as set up on the Tree Application Form Definition (KVATAFD)
  • Application summary section

The application data and application summary sections are always included in the PDF; a header is included only if one is defined for the web application on KVAAPFR.

You can define different PDF versions of the same application form/aid year/aid period combination for staff and applicants. For example, you might want to include header fields for staff members that you do not want to be included for applicants. In KVAFAPP, staff members can generate both versions of a PDF.

An applicant can generate a PDF only after the application form has been submitted in BSA Self-Service. When an application form has been submitted, a Generate PDF Application link is displayed on the following pages:
  • Application Summary page (bwvkkmen.P_AppForm)
  • Submit Application page (bwvkkmen.P_SubmitApplication)

Before the application form has been submitted, the Generate PDF Application link is not displayed on these pages.

If an applicant submits an application and subsequently makes more changes, the Generate PDF Application link will no longer displayed on the pages until the application is resubmitted.

An applicant can access the PDF of the submitted application form even if the application deadline has passed.

A staff member can generate a PDF regardless of whether the application form has been submitted.

When an application is marked as "Testing" on the Tree Application Form Definition (KVATAFD), a testing staff member can login to BSA Self-Service as an applicant and generate a PDF at any time while in testing mode. The Generate PDF Application link is displayed on the Application Summary web page.

Note: The link can become disabled if the user has already clicked the link or navigates away from the page. To make the link active again, the user must refresh the page.

Staff members cannot, however, use KVAFAPP to generate PDFs for an application form in "Testing" or "In-Process" status.

You can change PDF header settings while an application form is in "Testing" status.

When an application is marked as "Released", no further changes can be made to the PDF header settings. Applicants and staff member can then generate PDFs as normal (that is, using BSA Self-Service and KVAFAPP, respectively).

Header

The optional header is defined on the Application Form Maintenance (KVAAPFR), where you specify which fields you want to be included.

When defining header fields, you must specify an associated user-defined group PDF header. Group PDF headers allow you to include multiple "sections" within the header. You can define and include as many fields in a header or group as you want, and you can define as many groups as you want. If you plan to have header fields, you must have at least one group.

For the purpose of this functionality, a "field" that is included in a header means both the field label and the value in that field. For example, in the sample PDF application form, the Biographic group includes the ID field, and both the field label ("ID") and the applicant’s actual ID in Banner ("N0001223") are included. This is because the ID field was defined to be included in the header, in the Biographic group.

To allow you to arrange the fields as desired, there are three "columns" in a header group, and you can specify in which column each field is to appear. You can also specify the order in which the header groups and header fields are to be displayed.

With the exception of the institution name and logo (discussed in Institution name and logo), the system uses the value in the Customized Description field on the Application Form PDF Header Field section of KVAAPFR as the field label in the header.

There are two ways the system determines what value to display for each header field:
  • Rule code
  • Fixed calculation

Many of the most common fields that institutions use in PDF headers have been predefined and delivered as seed data for Application Form PDF Header Field Validation Table (KVVAPHD). You can use these predefined values or you can create your own. Refer to the System-Required Data for details about the delivered seed data.

Rule code

When a header field is controlled by a rule code, the system uses Banner Mass Data Update Utility processes and rules to determine the value for the field.

For example, in the sample PDF application form, the "Applicant’s name" field value is determined by a rule code. This particular header field definition is delivered as seed data for KVVAPHD, and it is defined to use the BSA_PDF_WEB_APP_BIO_DEMO process code and BSA_PDF_WEB_APP_NAME rule code. An SQL statement (delivered as seed data for the Business Rule Builder Table [GKRRSQL]) is defined for this process code/rule code combination. When a user creates a PDF, the system runs the process code/rule code and displays the applicant’s name in the "Applicant’s name" field.

If a process or rule code is not valid or inactive at the time a user generates a PDF whose header uses the code, "N/A" is displayed as the field value. This applies only to the header of the PDF.

When an application form tree is marked as "Testing" or "Released" on KVATAFD, validation is performed to check that any MDUU rules used for headers in the application form/aid year/aid period combination are valid and active. If a process or rule code is not valid or inactive, the system displays an error message and the application is not marked as "Testing" or "Released", respectively.

Fixed calculation

When a header field is controlled by a fixed calculation, the system uses the value specified for the given record from a column in the Banner database.

For example, in the sample PDF application form, the "ID" field value is determined by a fixed calculation. This particular header field is also delivered as seed data for KVVAPHD, and it is defined to use the value in the SPRIDEN_ID column for the PIDM. When a user creates a PDF, the system displays that value in the "ID" field.

Institution name and logo

Unlike the rest of the header fields for which seed data is delivered, the institution name and logo header fields never display a field label.

The institution name header field is controlled by a rule code, and the institution logo field is controlled by a fixed calculation.

Note: The delivered War file includes a generic GIF image. Your institution can replace the delivered image with your own logo, as described in Customize the PDF Java application. If you do not replace the image, an Ellucian logo displays.

Application form data

The application form data section displays the questions defined for the application form, the applicant's answers, and any tracking requirements specified.

An applicant's answers are underline. If no answer was entered for a question, nothing is displayed as the answer.

If you have defined a header for an application form, the application form data section is displayed after the header (where a header can consist of one or more groups). If no header has been defined, the application form data section is displayed first.

Application summary

The application summary section displays summary details of the application, similar to the Application Summary page in BSA Self-Service, This section is shown in the sample PDF application form shown in Figure 3 and is always the last section of the PDF.

Technical notes

PDF generation is enabled in both Tomcat and WebLogic environments.

There is a known limitation in Safari browsers on Mac environments. When a user tries to generate a PDF in this environment, Safari prompts for a password. To see the contents of the generated PDF, the user must right-click on the Generate PDF Application link and save the PDF file. The saved PDF can then be viewed in Adobe Reader.

Note: The generated PDF is secured, and secured PDFs can be reliably viewed only in Adobe Reader. Not all other PDF readers allow users to view secured PDFs.

Secured PDFs and BDM

PDF web applications are generated in a secured format, and secured PDFs cannot be viewed in Banner Document Management (BDM), although they can be uploaded and removed.

If a secured PDF is uploaded to BDM, the contents of the file cannot be viewed, although the BDM interface shows an icon for the file.

".N" constant value

To improve the handling of answers for free-form text questions, the system inserts the value ".N" for any answer the applicant leaves blank after previously answering the question.

This prevents processing errors if a valid value is changed to a null values in the KVAAPRE record. When determining whether a module can be marked as complete, the system treats a question with the ".N" constant as its value as if the question were not answered.

For example, if an applicant previously entered 1000 for the question "What is your monthly income?", and then returns and removes that value, leaving the answer blank, the system assigns ".N" as the answer value instead of replacing the previous value of 1000 with a null value.

Application Deadline

The Application Deadline field shows the date by which the application must be submitted.

If an active record exists for the applicant in the Applicant Expiry Date section of the Application Form Maintenance (KVAAPFR), that date is used to control the application form expiration. That date is interpreted as follows.

  • A date "beyond" the current application form expiry date means that the applicant will be able to continue applying to the corresponding application form even after the regular expiry date is in effect.
  • A date "in the past" (earlier than the current expiry date) means the applicant will be stopped from applying even before the regular application form expiry date is in effect.
  • A "null" date means the applicant will always be able to apply to the application form.

If no active record exists for the applicant, or no record at all exists in the Applicant Expiry Date section in KVAAPFR, the regular expiry date of the application form that is defined in the Application Form Maintenance section in KVAAPFR page is used.

Disbursement Schedule

This page is used to display details about the disbursement schedule for an institutional award.

To determine which disbursement schedule is to be displayed on this page, the system checks the value of Disbursement Schedule Indicator check box in the Wide Applicability Aid Year-Period Control (KVAWCTL).

If the Disbursement Schedule Indicator check box is unchecked, no schedule of any type is displayed.

If the Disbursement Schedule Indicator check box is checked, the system determines what, if any, disbursement schedule to display based on the following criteria.

  • If actual disbursement is available (KVRAWRD_FUND_DISB_IND is Y), the actual disbursement schedule is displayed.
  • If no actual disbursement is available, the disbursement schedule that is displayed depends on the value in the Projected Disbursement Schedule Indicator field in the Applicant Institutional Award (KVAAWRD), as follows.
    • If the KVAAWRD value is null, the system determines which projected schedule to use based on the value in the Projected Disbursement Schedule Indicator field of KVAWCTL as follows:

      If the KVAWCTL value is Projected with Edit Checks, the system displays the projected disbursement schedule, performing edit checks.

      If the KVAWCTL value is Projected with NO Edit Checks, the system displays the projected disbursement schedule without performing edit checks.

      If the KVAWCTL value is Do Not Display Projected, the system does not display a projected disbursement schedule.

    • If the KVAAWRD value is Projected with Edit Checks, the system displays the projected disbursement schedule, performing edit checks regardless of the value for KVAWCTL's Projected Disbursement Schedule Indicator field.
    • If the KVAAWRD value is Projected with NO Edit Checks, the system displays the projected disbursement schedule without performing edit checks.
    • If the KVAAWRD value is Do Not Display Projected, the system does not display a projected disbursement schedule.

Upload or View My Other Documents

This page is used to upload or display applicant documents (such as driver’s license or passport) that are not associated with web application tracking requirements to Banner Document Management (BDM).

This page provides drop down for applicants to choose document type and buttons to upload & view the document. Applicants can upload only one document per document type. On selection of Document Type, if the applicant has previously uploaded a document for this type, then Upload Document button will be disabled, and View Document button will be enabled. On click of View Document button, ApplicationXtender(AX) page opens in a new tab for displaying the file.

If there are no documents uploaded for the selected document type, File Browse and Upload Document buttons will be enabled. On click of Upload Document button, if document upload is successful, AX page opens in a new tab with preview of uploaded file.

If your institution is not using BDM, or if BSA and BDM have not been integrated or BDM configurations are not set in GUACONF, then this page displays an error message BDM integration is not available. Please contact your administrator. See the Banner Student Aid - Banner Document Management Integration and Link to Banner Document Management for more information.
