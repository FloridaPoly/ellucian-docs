Banner Student Self-Service installation

You can streamline the Student Self-Service installation by using Ellucian Solution Manager (ESM) to complete most of the installation tasks. You do need to manually customize the WAR file, set up the application-specific configurations, and configure the application server.

Supporting documentation

Refer to the following content for more information about the Ellucian Solution Manager and Banner Self-Service common components.
  • Ellucian Solution Manager overview
  • Banner Self-Service Common Features

Before you get started

Review these prerequisites for hardware, software, and the supporting documentation you can reference. Ellucian recommends that you use Ellucian Solution Manager to perform Banner product upgrades, rather than using a manual installation process.

Review Banner product release dependency information in Ellucian Solution Manager or the Banner Interdependency Matrix attached to Article KB000500135 - Banner Interdependency and Compatibility Matrix in the Ellucian Customer Center.

These are the hardware requirements Ellucian recommends.

The number of CPU cores, memory, and configuration for application servers running Banner 9 applications is dependent on the number of expected concurrent users working on the system. Optimal performance sizing and configuration vary per institution, but the following information provides a good starting point:

Recommended: Quad core CPU with 8 GB of memory for the application server.

Please refer to the Banner Sizing and Configuration Guide in the Supporting documentation section of the Banner Admin Common Install content on the Ellucian Documentation site for more information.

Single Sign-On (SSO) support

Ellucian recommends that you establish the single sign-on environment before implementing Student Self-Service.

Student Self-Service supports Central Authentication Service (CAS) and Security Assertion Markup Language (SAML) 2.0 as the Single Sign-On (SSO) protocols. Both are certified to run with Ellucian Ethos Identity. You can download Ellucian Ethos Identity from the Ellucian Customer Center.

For more information about how to establish a single sign-on environment, see the Banner Single Sign-On documentation or Setting Up Ellucian Identity, which you can download from the Ellucian Customer Center.

Warning: If you do not enable Single Sign-On (SSO), a user must authenticate before accessing each Banner 9.x application. If a user logs out of an application, the user is logged out of that current application, but is still logged in to all other applications that are currently open.
Java dependencies

Ellucian supports Banner 9 Self-Service applications on Java 17 and Java 21. You must install Java 17.0.x (64-bit version) or Java 21.0.x (64-bit version) on the web application server before you deploy the application.

You must use the same version of Java to customize and deploy the WAR file and you must define the JDK bin directory in the PATH system property.

If you want to implement an alternative to Oracle JDK, Ellucian recommends the following runtime Java virtual machines for running Banner 9 Self-Service applications.
  • Ellucian Cloud – Amazon Corretto OpenJDK for running Banner applications in the cloud (hosted or SaaS)
  • RedHat Enterprise Linux and Oracle Enterprise Linux – OpenJDK
  • Windows – Amazon Corretto OpenJDK
  • Solaris – Azul OpenJDK as an alternative
  • AIX – IBM distributes Java as part of AIX
  • HP-UX – HP distributes Java as part of HP-UX

Language settings

Banner Student Self-Service uses data from the GURINFO table.

This seed data is delivered with the DB Upgrade 9.14. As this seed data is multi-lingual, it is important that the Oracle NLS language setting must match the Banner database when the data is loaded. Specifically, the NLS_LANG key must be set to AMERICAN_AMERICA.AL32UTF8.

Configure shared settings

The shared_configuration home directory contains a cross-application configuration file called banner_configuration.groovy. You can change settings in this file. As part of improving the Banner security model, it is mandatory to externalize the cross-application configuration file banner_configuration.groovy by setting the system property -DBANNER_APP_CONFIG.

Shared configurations can also exist in database table (GUROCFG) under application ID GLOBAL. The configurations in database will always take precedence over the configurations in the file. The Banner Common DB Upgrade uploads some shared configurations by default to the database (GUROCFG table). You can edit these configurations using the GUACONF page.

Shared configurations in the groovy file

These configurations are in the banner_configuration.groovy file.

JNDI datasource

You can optionally change the datasource name in the configuration file to point to the JNDI datasource that is configured in your application server.

For example, jndiName = "jdbc/bannerSsbDataSource" is the default configuration. You can change this to match the JNDI datasource name in your environment. If you change the jndiName, you must regenerate the WAR file, even if you are using an external configuration.

Session timeouts

When you determine the timeout settings for CAS and Student Self-Service, consider the time limits imposed for each.

For example, if the Student Self-Service timeout setting is less than the CAS timeout setting, SSO authentication might still be valid even though the user is exited from Student Self-Service. As long as the CAS authentication remains valid, the user can re-enter Student Self-Service without re-authenticating.

The following timeouts are used in the Self-Service application.

banner.transactionTimeout

The banner.transactionTimeout setting is used to prevent excessive delays due to long database transactions. The setting is configured in the banner_configuration.groovy file. To use this timeout, set the banner.transactionTimeout setting to 300 seconds.

Ensure that either the configuration file is deployed with the application, or the application is using the configuration file where it is currently located.

If a database transaction takes longer than banner.transactionTimeout seconds, the transaction is aborted and any change is rolled back.

Note: In some cases, the web user interface might ignore the database timeout/error notification and not remove the loading spinner. If this occurs, refresh the page to continue using the application.
AJAX timeout

The AJAX timeout terminates HTTP requests that exceed the specified time limit. The Self-Service application sets the timeout value based on the banner.transactionTimeout setting plus an increment to allow for communication and processing of the request.

You do not need to override the AJAX timeout, but the timeout value can be overridden in JavaScript by calling $.ajaxSetup( { timeout: timeoutValue } );

Note: The timeoutValue must be in milliseconds.
Note: Although the web user interface continues after an AJAX timeout, the server might continue processing the request until it completes or reaches a database transactionTimeout.

Example 1: 
aboutInfoAccessRoles = [ROLE_SELFSERVICE-EMPLOYEE_BAN_DEFAULT_M]
Example 2: 
aboutInfoAccessRoles = [ROLE_SELFSERVICE-EMPLOYEE_BAN_DEFAULT_M,ROLE_SELFSERVICE-STUDENT_BAN_DEFAULT_M]
Note the following:
  1. Platform version is not available for other roles that are not configured under aboutInfoAccessRoles configuration.
  2. Platform version is not available in unsecured Self-Service pages.
  3. If there is no configuration for aboutInfoAccessRoles, then Platform version will not be seen in the About dialog.
Page Audit

Page Audit is a Banner Platform feature that enables page audit across Banner Self-Service applications.

Table Name: GURASSA

Information Description
Audit Time Application server time.
SSB Login ID The user id used to login to SSB. SPRIDEN ID is stored for Self-Service users/SSO users. Email address is stored for Guest users.
Application ID Application ID for the page the user is accessing.
Page URL Page the user is accessing.

Example: /StudentRegistrationSsb/ssb/registration
IP Address IP address of user.
Activity Date The date that information in this record was entered or last updated.
User ID The user ID of the person who inserted or last updated this record.
PIDM Self-Service users get the respective PIDM. Guest users are not handled for this information yet.

Enable Page Audit

The following table shows a few example values and results.

App ID GUACONF    
  Key Value Result
Global EnablePageAudit N or null No pages audited.
    % All pages across all the Self-Service applications are audited.
    Registration Those URLs of applications that contains the word registration is audited. This is not case sensitive search.
    Hr Those URLs of applications that contains the word hr is audited.
Note: If you have configured the same configuration in the above table at the application level, then audit is enabled only for the configured application and not across all Self-Service applications.
Login Audit

Login Audit is a Banner Platform feature that enables login and logout audit across Banner Self-Service applications.

Table Name: GURASSL

Information Comment
Audit Time Application server time.
SSB Login ID The user id used to log in to SSB. SPRIDEN ID is stored for Self-Service users/SSO users. Email address is stored for Guest users.
Application ID Application ID for the page the user is accessing.
IP Address IP address of the user.
User Agent User agent from the client browser.
Activity Date The date that information in this record was entered or last updated.
User ID The user ID of the person who inserted or last updated this record.
PIDM Self-Service users get the respective PIDM. Guest users are not handled for this information yet.
Logon Comment

A comment recorded at logon/logout time

Login Successful for successful login

Logout Successful for successful logout
Note: For a better understanding of the Login Audit, see the following notes:
  1. Only successful login/logouts are audited in the new table GURASSL; the error cases will continue to be audited in GURALOG table.
  2. Single Sign On login/logout is also audited, tested with CAS and SAML.
  3. Login ID is Spriden ID for Single Sign On.
  4. User agent is the complete string from the browser that is used.
  5. Guest users are audited for Login/Logouts with the email address.

Configure application-specific settings

Banner XE applications read configuration at startup from a shared configuration file (banner_configuration.groovy), from an application configuration file (StudentSelfService_configuration.groovy) and from the database table (GUROCFG).

The application configuration file setting can override the shared configuration file settings and the configurations in database can override any configurations set in the files.

Application configurations in the groovy file

The application configuration for Banner Student Self-Service is set in StudentSelfService_configuration.groovy file.

Config job and application page role job

The job configurations configJob and applicationPageRoleJob have been added to the StudentSelfService_configuration.groovy file. configJob is an improved job and applicationPageRoleJob is a new job.

The purpose of these job parameters is to set the configurations for a job to run periodically to pick up the new values set on the database configurations or application page role and become active in the Self-Service applications.

The following old configJob configuration is deprecated, so Ellucian recommends to remove it from your configuration file.

configJob {
    interval = 86400000
    actualCount = -1
}
If the old configurations exist, the system ignores them and uses the new jobs instead. The application that is still on the older configuration or not configured for newer jobs falls back to the default:
  • 30 minutes run for configJob
  • daily mid-night at 00:00 run for applicationPageRoleJob

You can configure the configJob and applicationPageRoleJob jobs using Spring Scheduler cron expressions. See Config job and application page role job configurations in the Banner Self-Service Common Features Use content for information on customizing the cron expression for the jobs configJob and applicationPageRoleJob.

Note: The application configurations loaded in the database take precedence over the configurations in the configuration file. If you have removed the configurations from the database table, or have not configured the configJob, the application continues to use the configurations in the configuration file, not the ones in the database.
System properties configured in the groovy file

The following properties in the StudentSelfService_configuration.groovy file are internal to the application and are required for carrying out its own lifecycle activities. Leave these properties undisturbed.


grails.plugin.xframeoptions.urlPattern = '/login/auth' 
grails.plugin.xframeoptions.deny = true 
bnrStudentSelfServShort="Student Self-Service" 
banner.applicationName="Banner StudentSelfService"
Institutional home page redirection support

The institutional home page redirection support configuration allows Student Self-Service to provide an institutional home page to which users can navigate back to if they have access issues.

Access issues are specific to insufficient privileges when accessing the Student Self-Service application.

/********************************************************************* 
* Home Page link when error happens during authentication. *

grails.plugin.springsecurity.homePageUrl='http://URL:PORT/ StudentSelfService/'
Proxied Oracle users

When connecting to self-service applications, the ssbOracleUsersProxied setting specifies whether the Oracle account is used for the database connections. The ssbOracleUsersProxied setting also controls whether Value Based Security (VBS) is enabled in the self-service application.

The following values can be used for the ssbOracleUsersProxied setting:
  • False - The Oracle account is not used for the connection and VBS is not enabled in the self-service application. If the Oracle account is locked, the user can still log in to the self-service application.
  • True - The Oracle account is used for the connection and VBS is enabled in the self-service application. If the Oracle account is locked, the user cannot log in to the self-service application.

You can configure Banner Student Self-Service to run in a single sign-on (SSO) environment using either Central Authentication Service (CAS) or Security Assertion Markup Language (SAML) SSO protocols. Ellucian certifies against and supports Ellucian Ethos Identity.

Redirect pages in a MEP environment

If your environment is enabled for Multi-Entity Processing (MEP), two settings (grails.plugin.springsecurity.logout) must be configured in the StudentSelfService_configuration.groovy configuration file for your environment. You do not need to configure these settings if your environment is not enabled for MEP.

If a user tries to access a Self-Service URL that does not include a valid MEP code, an error prompt is displayed on the Error page of the application and the user can use the Logout or Return Home button.

The following configuration settings determine where each button redirects the user:

  • grails.plugin.springsecurity.logout.afterLogoutUrl – This setting contains the URL of the institution-specific page where the user is redirected if the Logout button is clicked.
    For example, a portal page has the following settings:
    • https://cas-server/logout?url=http://myportal/ main_page.html (CAS environment)
    • http://myportal/main_page.html (non-CAS environment)
  • grails.plugin.springsecurity.logout.mepErrorLogoutUrl – This setting contains the URL of the institution-specific page where the user is redirected if the Return Home button is clicked.

Each URL can be any page that does not require a MEP-enabled database connection or any page outside the Self-Service application.

Self-service end point

The ssbEnabled setting is set to true for instances that expose self-service end points. Student Self-Service is a Self-Service application, so the default value is always true.

Application configurations in the database

Student Self-Service configurations in the GUROCFG database table are under application ID SSS. The configurations in the database will always take precedence over the configurations in the file.

The Banner Common DB Upgrade uploads some SSS configurations by default to the GUROCFG database table. You can edit these configurations using the Banner Applications Configurations (GUACONF) page.

defaultWebSessionTimeout

The defaultWebSessionTimeout property is used to terminate user sessions that are left idle or abandoned without logging out. This setting is used to set the overall session inactivity time.

Note: If defaultWebSessionTimeout is not specified, a default value of 1500 seconds is used.
Password reset

You can specify whether users have the ability to reset their passwords by updating the ssbPassword.reset.enabled setting.

If the value of the setting is true, users can reset their passwords. If the value of the setting is false, a disabled error message is displayed.
Location of images

The banner.picturesPath setting in the in the GUACONF page specifies the location of student and faculty photographs.

In banner { picturesPath = System.getProperty(‘base.dir’) + ‘/test/images’ }, banner.picturesPath setting is the application base directory appended with /test/images.

The base.dir is a system property that can be set through JAVA_OPTS.

The value of banner.picturesPath must be a fully qualified path to the directory that contains the image files. For example, banner { picturesPath = '/home/banner/test/images' }.

Logback logging

Logging configurations are available in logback.xml file. In a PRODUCTION environment, this file resides in the Banner application's classpath. You can externalize the logback configuration as specified in the Externalize logback configuration topic.

These are the default settings for Banner logging:
  • The default Root logger level is configured to ERROR.
  • Logging is turned to DEBUG for specific packages and is commented.
  • Use JMX to change logger levels for Root or specific packages/artifacts.
  • JMX MBean must be unique for each application that is deployed into the JVM. This configuration should be updated for each instance of each application to ensure uniqueness.
    jmxConfigurator("${loggingAppName}-logback")
  • Users can specify a different logging directory using the following system property:
    -Dbanner.logging.dir=<full directory path> (THIS MUST BE AN ABSOLUTE PATH WITH WRITE PERMISSION)

    For example:

    -Dbanner.logging.dir=/home/tomcat/target/logs
  • Users can enable hibernate loggers by configuring the following system property:
    -Dorg.jboss.logging.provider=slf4j

    For example:

    setEnv.sh(linux)/setEnv.bat(Windows)
  • If a different logging directory is not configured, then the log files will be generated in the build folder as provided default by Grails.

Logging level

The root logging level is pre-configured to the ERROR level. Multiple class or package level configurations, by default, are set to a status of DEBUG and is commented.

You can set a different logging level for any package or class. However, configuration changes for logging take effect when the application is restarted.

For example:

<root level="DEBUG">
        <appender-ref ref="APP_LOG"/>
    </root>

Uncomment the packages or classes in the logback as required.

For example:

//logger("net.hedtech.banner.security.SelfServiceBannerAuthenticationProvider", DEBUG)

If the package is not defined, then define in the above format.

Note: Changing the logging level to DEBUG produces very large log files.

Alternatively, you can use JMX to modify logging levels for any specified package or class, or even at the root level. When using JMX, the logging level changes only affect the running application. When you restart the application, changes that you made using JMX are lost.

Externalize logback configuration

The default logback setting can be overridden by an external logback configuration.

Procedure

  1. Take a copy of the example file from the release-StudentSelfService-9.35.zip/config location and rename it to StudentSelfService_logback.xml.
  2. Modify the file to enable the required logger level and if you need to change the logging directory, change it through -Dbanner.logging.dir.
    For example, if you need to change the new log directory to C:/Tomcat/logs, set the following as parameter:
    -Dbanner.logging.dir=C:/Tomcat/logs
  3. Place the updated logback configuration file in any location.
    For example, C:\yourlocation\custom_logback.xml.
  4. You can refer to the external logback config using the -D<APPNAME>_log.config parameter.
    To externalize the logback for Student Self-Service, the syntax will be -DStudentSelfService_log.config=C:\\yourlocation\\StudentSelfService_logback.xml.

Date format keys

The default.date.format and js.datepicker.dateFormat are date format keys that use different specifications to represent the date. The default.date.format is associated with the ICU format, which is dd/MM/yyyy. The js.datepicker.dateFormat is associated with the Java Script or Keith Wood format, which is dd/mm/yyyy.

For dates to be displayed properly, the two formats must match. For example, for 1 June, 2012, the calendar parses 01/06/2012 using js.datepicker.dateFormat, and when the dates are saved, the date value on the server side is parsed by groovy using default.date.format to display 01/06/2012 in the application.

default.date.format

This key determines the date format for display and data entry in the user interface. It must match the ICU specification and can be changed based on locale. For more information about the ICU specification, see https://unicode-org.github.io/icu/userguide/.

For the default.date.format for June 1, 2014, use one of the following variables for the year:

Year format Interpretation Comment
yy 14 Two digit year
yyyy 2014 Four digit year

For the default.date.format for June 1, 2014, use one of the following variables for the month:

Month format Interpretation Comment
M 6 Single digit month (no leading zero)
MM 06 Double digit month
MMM Jun Short month name
MMMM June Long month name

For the default.date.format for June 1, 2014, use one of the following variables for the day:

Day format Interpretation Comment
d 1 Single digit day in a month (no leading zero)
dd 01 Double digit day in a month

js.datepicker.dateFormat

This key determines the date format for the interactive date selection control. It must match the jQuery Keith Wood datepicker format specification. For more information on the Keith Wood datepicker format, see http://keith-wood.name/datepick.html.

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the year:

Year format Interpretation Comment
yy 14 Two digit year
yyyy 2014 Four digit year

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the month:

Month format Interpretation Comment
m 6 Single digit month (no leading zero)
mm 06 Double digit month
M Jun Short month name
MM June Long month name

For the js.datepicker.dateFormat for June 1, 2014, use one of the following variables for the day:

Day format Interpretation Comment
d 1 Single digit day in a month (no leading zero)
dd 01 Double digit day in a month
