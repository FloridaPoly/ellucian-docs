Use API Designer

Create and manage APIs with API Designer.

Table 1. Use API Designer
Topic Description
API draft overview Create a new API draft or create an API draft from a published API.

API draft overview

Create a new API draft or create an API draft from a published API.

You can create an API draft by using one of the following methods:
  • Create a new API and save it as a draft.

    The new API draft is always published as version v1.0.0. For details, see Create a new API draft.

  • Create a draft copy from a published API.

    You can republish this API with a different version from the original published API version. For details, see Create a draft copy of a published API.

In API Designer, the Draft APIs page lists all API drafts with the following information:
  • The API name
  • A description of the API
  • When the API was last updated
  • Who updated the API
  • The API domain
  • The API request method that is used

You can also use the Draft APIs page to delete or export an API draft.

Tip: For easy access to API drafts that are created as copies of published APIs, a link to access an API draft is also created on the Published APIs page next to the original API name in the Draft column.

Create a new API draft

You can create and save a new API draft.

Before you begin

Make sure that users have permissions assigned to access and use API Designer. For details, see Access Ellucian API Designer

About this task

Use the following steps to create a new API draft. When a new API draft is published for the first time, it is published as version v1.0.0.

Procedure

  1. Log in to Ellucian Experience, click the Applications icon in the Ellucian Experience bar.
  2. Select API Designer from the list.
  3. Click the NEW button and choose API.
    This opens the Create API window.
  4. Enter the API name in the API Name field.
    Make sure that this name is unique and easily-identifiable. For details, see API details component.
  5. Select the domain name from the list in the Domain field.
    Domain names are defined as Banner Baseline schemas but can be customized to meet organizational needs. For details, see API details component and Add customized domains.
  6. Enter an API description in the Description field.
  7. Click Next.
  8. Select Starting data source and choose Domain or Model.
    For details about data sources, see Data source.

    For details about models, see Create a model.

  9. Use the data joining, custom fields, filtering, summarize, and sorting data manipulation options to further define the criteria.
    For details, see Data definition.
  10. Optional: Select the page size. For details, see API pagination.
  11. Optional: Click PREVIEW DATA to preview the sample data.
    PREVIEW DATA allows you to see sample data of the API output and provides the following information:
    • Total Records is the number of records retrieved by an API.
    • Execution Time is the time it takes to run an API (measured using the database query).
    • Execution Plan is a downloadable JSON file with the query details.
    Note: ORDER BY is not supported in the Execution Plan in the Oracle database. Both PREVIEW DATA and the API remain executable despite this limitation.
  12. Optional: Define or edit the following components for an API draft:
    • API Details – such as the API name, API domain, API description, and ID Property.

      For details, see API details component.

    • Security – for details, see Security settings overview.
    • API Schema – for details, see API schema.
  13. Click SAVE to save the API draft.

Results

This draft API now appears on the Draft APIs page and can be edited or published as version 1.0.0.

What to do next

  • Apply operations. For details, see Data definition.
  • Create a model to simplify complex API structure. For details, see Create a model.
  • Publish an API. For details, see Publish an API.

Create a draft copy of a published API

You can create an API draft as a copy of a published API that can be republished as a different version.

Before you begin

Access Ellucian API Designer

About this task

Create a copy of a published API. This API draft can be published as a major, minor, or patch version. For details, see API Designer versioning.

Procedure

  1. Log in to Ellucian Experience, click the Applications icon in the Ellucian Experience bar.
  2. Select API Designer from the list.
  3. On the Published APIs page, open an existing published API.
  4. Click Create Draft.
    Note: An API draft can be created only for the last version of a published API. For example, if an API has versions v1.0.0, v2.1.0, and v3.0.4, you can only save v3.0.4 as a draft.
    A draft copy of published API is saved on the Draft APIs page. A corresponding link to the API draft is also created on the Published APIs page.
  5. In the created draft copy you can do the following actions:
    • Change the data source.
    • Add, edit, or remove operations. For more information, see Data definition.
    • Change the page size. For details, see API pagination.
    • Update API Details – including the API domain, API description, and ID property. For more information, see API details component.
    • In some cases, update Security. For more information, see Security settings overview.
    • Update API Schema. For more information, see API schema.
  6. Optional: Click PREVIEW DATA to preview the sample data.
    PREVIEW DATA allows you to see sample data of the API output and provides the following information:
    • Total Records is the number of records retrieved by an API.
    • Execution Time is the time it takes to run an API as measured using the database query.
    • Execution Plan is a downloadable JSON file with the query details.
    Note: ORDER BY is not supported in the Execution Plan in the Oracle database. Both PREVIEW DATA and the API remain executable despite this limitation.
  7. Click SAVE to save the API.

Results

This draft API is now listed on the Draft APIs page and can be edited or published as a major, minor, or patch version.

Create a model

Simplify complex API structure by creating models (data sets) to use as custom data sources when you create an API.

Before you begin

Access Ellucian API Designer

About this task

Models are reusable data sets that combine data from tables, views, or other models and can represent key concepts or processes in your organization. Models can be reused across multiple APIs and models.

Procedure

  1. Log in to Ellucian Experience, click the Applications icon in the Ellucian Experience bar.
  2. Select API Designer from the list.
  3. Select the NEW button and choose Model.
    The Create Model window opens.
  4. Enter the model name in the Model Name field.
  5. Select the domain name from the list in the Domain field.
  6. Enter a description in the Description field.
    Tip: You can Edit Model Details – such as the name, domain and description – before the model is used by another model or an API.
  7. Click Next.
  8. Select Starting data source and choose Domain or Model.
    Tip:

    API Designer supports up to two levels of nested models. A parent model can contain a nested model, and that nested model can include one additional nested model.

    For details, see Data definition.
  9. Use the data manipulation options to further define the criteria.
    For details, see Data definition.
  10. Optional: Click PREVIEW DATA to preview the sample data.
    PREVIEW DATA allows you to see sample data of the API output and provides the following information:
    • Total Records is the number of records retrieved by an API.
    • Execution Time is the time it takes to run an API (measured using the database query).
    • Execution Plan is a downloadable JSON file with the query details.
    Note: ORDER BY is not supported in the Execution Plan in the Oracle database. Both PREVIEW DATA and the API remain executable despite this limitation.
  11. Click SAVE to save the model.

Results

This model is now listed on the Models page and can be used as a data source.

Data definition

You can apply operations to structure and refine your API queries.

You can configure complex queries on the Data Definition page, which is accessible when you create a draft API or a model or when you select an existing one. You can perform the following actions:
  • Define an initial data source and join it with other data sources.
  • Sort data, summarize data, and filter data using functions, specific fields, parameters, or literal values.
  • Add custom fields.
  • Set or change the page size to control the data.
For details, see:
  • Data source
  • Join data
  • Filter data
  • Summarize data
  • Sort data
  • Custom fields
  • API pagination
  • Add additional fields to use in join, filter, and sort data operations

Data source

You can define a data source for an API.

A user is prompted to define a starting data source for each new API or model. A data source can be a table, a view from a specific domain, or a model. For details about domains, see API details component.

For each data source, you can choose which fields to publish in the API schema by selecting or deselecting them from the drop-down list for the data source.

Tip: All data source fields are selected by default. To select required fields only, clear the Select All check box and then make any selections.

Join data

You can join data to refine your API queries.

You can select the Join Data option to combine data from two or more tables or models based on a common key or related column. This enables more comprehensive and connected API responses by merging related data sources.

You can choose from the following Join Data types:
  • Inner Join
  • Left Outer Join
  • Right Outer Join
  • Full Outer Join

Each data source supports specific fields as join key fields. However, you can add additional fields to enable joining, filtering, and sorting of data as needed. For details, see Add additional fields to use in join, filter, and sort data operations.

For details about models, see Create a model.

Binary comparison operators for joins

When configuring join conditions, you can use binary comparison operators to define how fields from different data sources relate to each other. The following operators are available:

  • Equals (=)
  • Not Equal (!=)
  • Greater Than (>)
  • Greater Than or Equal To (>=)
  • Less Than (<)
  • Less Than or Equal To (<=)

These operators allow you to create more flexible join conditions beyond simple equality comparisons.

Filter data

You can filter data and refine your API queries.

API Designer includes a powerful data filtering feature that allows you to refine results by using a variety of filter operators. Available Filter options—such as Equals, Contains, Greater Than, and Between—depend on the data type of the field being filtered (for example – a string, a number, or a date).

These filter operators can be flexibly used to refine data as follows:
  • Use Fields values directly from the data source.
  • Use Literal values to apply static values like numbers, text, or dates.
  • Use ​​Parameters​ to apply dynamic values that can be passed at runtime, which enables flexible and reusable filtering logic. For details, see Parameters.
  • Use built-in Functions such as EffectiveTermCode, NVL, DateAdd, and others to transform or evaluate data dynamically during filtering.
    • If you choose a function with arguments, a new panel displays in the dialog that allows you to define the value for each argument. The argument can be a Literal or a Field.
    • Depending on the function, each argument can take a text, number, or date value. If the argument value is a literal argument, the input adapts to the respective type.
    • The data type of the field selected on the left side of the filter condition determines the type of literal argument that can be entered.
      • Select a string field to enter a text literal.
      • Select a date field to choose a date value using the calendar widget.
    • If the argument value is a field, you can choose any field, but the following warning is displayed if you choose a field that has a different data type: The field type does not match the argument type. Please make sure your data is compatible.
    • Some functions, such as COALESCE and NVL, can take any of argument types. In those cases, API Designer recommends the data type according to the field chosen for the left side of the filter condition.

Each data source supports only certain fields as filter fields. However, you can add additional fields to enable joining, filtering, and sorting of data as needed. For details, see Add additional fields to use in join, filter, and sort data operations.

BETWEEN operator

The BETWEEN operator allows you to filter data within a specified range. When you select this operator, you must provide three values to define the range:

  • The field to filter
  • A start value for the range
  • An end value for the range

Each value can be a Field, Literal, Parameter, or Function. The data structure uses rangeValues with startValue and endValue properties to define the range boundaries.

IN and NOT IN operators

The IN and NOT IN operators allow you to filter data based on a list of values. When you select either operator, a side section displays where you can enter multiple values as a comma-separated list.

These operators are useful for filtering data that matches (IN) or does not match (NOT IN) any value in the specified list. Each value in the list can be a Field, Literal, Parameter, or Function.

Summarize data

Use the Summarize option to apply aggregate functions and retrieve summarized data in your API queries.

Select one of the following functions from the list, then choose a data source and field to apply it to:
  • Sum Of
  • Count Of
  • Minimum Of
  • Maximum Of
  • Average Of
  • Count All
    Tip: The Count All option does not need a data source or a field value.

To group aggregated results by a specific field, use the optional Group By feature.

Tip:
  • When Summarize options are applied, you can no longer select Fields from the Data Source drop-down. All fields that are to display in the API Schema output must be added in the Group By clause of the Summarize options.
  • When ID Property is defined on the API Details page, it is automatically added to the Group By clause of the Summarize option and it is included in the API Schema output.
  • When the Sort option is used, only the fields included in the Group By clause of the Summarize section are available for sorting.

Sort data

You can apply the sort option to structure data in API queries.

Use the Sort option to organize any data in a specific order for clearer and more meaningful API responses. Choose a data source and field to sort by and then select the sort order, which is Ascending or Descending.

Tip: You can sort by up to a maximum of three fields.

Each data source supports only certain fields as sort fields. However, you can add additional fields to enable joining, filtering, and sorting of data as needed. For details, see Add additional fields to use in join, filter, and sort data operations.

Custom fields

Custom fields let you create calculated values derived from existing data, adding dynamic logic to API responses without modifying the underlying database.

Custom fields can be included in APIs and models to enrich returned information. Custom fields are generated at runtime when the API is called and are never stored in the database.

Tip: API Designer dynamically generates custom fields when the API is called.
Custom fields are especially useful for the following tasks:
  • Formatting data (such as converting text to lowercase)
  • Extracting substrings (such as first 10 characters of a description)
  • Calculating dates (such as adding days to a deadline)

Custom fields can also be used in filter, summarize and sort options. This allows calculated values to participate in query criteria and ordering, providing greater flexibility when refining and organizing API results.

You can add a custom field by selecting the Custom Fields option on the API Data Definitions page. First, provide a name for the new field – then choose a function from the available list. For each function, you need to define the arguments, which can be either a Literal, a Field, or a Parameter. After the custom field is created, it is included in both the API schema and the API response.

For example, you can add a custom field called LastNameUppercase that uses the UPPERCASE function to convert the value of the lastName field to uppercase. This field appears in the following places:
API schema
With the data source marked as Function, it indicates that the value is derived from a calculation rather than a direct database column.
API response
{
"firstName": "John",
"lastName": "Frink",
"LastNameUppercase": "FRINK"
}

API pagination

API Designer supports pagination to help you efficiently retrieve large data sets.

You control the amount of data returned per request by setting the Page Size in the API Data Definition section. Select the size from the drop-down list. The selected page size is passed in the request using the custom header x-max-page-size as demonstrated in the following example:

x-max-page-size: 500
Tip: API specifications support a maximum page size of 1000.

Pagination and sorting behavior

To ensure consistent and reliable pagination, always use a unique and stable sort field. This action of sorting by field prevents duplicate records from appearing across pages.

If you do not specify a sort order in your query, Banner-delivered APIs default to sorting by the surrogate_id field in ascending order. This field typically belongs to the primary table or view of the API and helps maintain stable pagination.

Tip: While this default behavior supports consistency, Ellucian strongly recommends explicitly defining a unique sort field to guarantee accurate and duplicate-free results.

Add additional fields to use in join, filter, and sort data operations

Add fields to use with Join Data, Filter, or Sort data operations.

About this task

In API Designer, not all table columns are available by default for join, filter, and sort operations. Only Banner Baseline columns that are indexed are initially displayed for these actions.

To include a column that is not indexed, you can add it through the Integration Configuration Settings (GORICCR) page.

Tip: When using columns that are not indexed in join or filter statements, at least one indexed column must be included in the join criteria—especially for larger tables. This is important to maintain API performance.

Procedure

  1. Access the Integration Configuration Settings (GORICCR) page in the Banner Admin pages.
  2. Use API_DESIGNER as the Process value.
  3. Use DISPLAY_COLUMNS as the Setting value.
  4. Click Go.
  5. Click Insert.
  6. Choose the DISPLAY_COLUMNS setting.
  7. Add the Value as the column name that is not indexed in the following format: 
    [table Name]_[Column Name]

    In this example, the table name is from a specific table and the column name is the specific name of the column.

    The end format appears as follows:

    GOREMAL_PREFERRED_IND

    There are no spaces in the table name or column name, and underscores separate each word.

  8. Fill in a Description for the column name.
  9. Save the information.

Results

After the table column is added to GORICCR, the table column is available as a data source field in API Designer for selection in join, filter, and sort operations.

About API details, security, and schema

You can define API details, security, and schema to ensure clear communication between systems and to prevent data exchange errors and inconsistencies.

Tip: Make sure you have access to API Designer to begin using the application. For more information, see Access Ellucian API Designer.

Security measures are essential for protecting sensitive information from unauthorized access. A well-structured schema enforces data integrity and simplifies integration to make APIs more reliable and scalable.

You can define the key components of an API during the drafting phase. You can also perform a final review and edit before publishing.

To access these key components, open an existing draft API and click the drop-down menu next to the API name:
  • API details component
  • Security settings overview
  • API schema

API details component

You can define API details such as name, domain, description, and ID property to ensure proper documentation and uniqueness.

The API Details component provides essential metadata for defining and managing an API within API Designer. It serves as the starting point for configuring a new API or editing an existing one, which ensures every API is clearly defined, categorized, and documented. This section includes the following fields:
  • API Name is the unique name used to identify the API. Create the name in an easy-to-understand and descriptive way to ensure clarity and usability. API Designer auto-validates the name to ensure it complies with API naming conventions.
    • You can change the name of a new API draft.
    • If an API draft is created from a published API, the name is locked and cannot be modified.
  • Domain specifies the business or technical domain the API relates to. This helps categorize the API for easier discovery and organization. Properly tagging the domain ensures that APIs are easier to locate, manage, and understand across large systems or teams.

    For domains, API Designer uses a predefined list of Banner Baseline schemes—such as STUDENT, GENERAL, CORE, and other schemas—as the default options. This list can be customized to meet specific organizational needs. For more information, see Add customized domains.

  • Description is a brief summary of the API purpose, functionality, and usage context. This helps you quickly understand the API’s value and use cases.
  • ID Property is an optional configuration that lets you specify a unique identifier for records retrieved through the API. This allows for more targeted and efficient API calls, which enables you to retrieve a specific record instead of the entire data set.

How does the ID Property work?

  1. You can define the ID Property by selecting a Data Source and a Field.
  2. The selected field must be unique—typically a primary key column from the data source table (such as SURROGATE_ID, GUID, and other options).

    For example, consider a user who has an API called x-team that gets team member information. Calling the x-team API displays the following results:

    Name SURROGATE_ID Task
    Mindy 1 Supervisor
    Lenny 2 Quality
    Karl 3 Analyst
    Homer 4 Safety

    If the ID Property unique identifier used as SURROGATE_ID and the following call is made – x-team/1 – the user whose SURROGATE_ID value is 1 displays in the results:

    {
"name": "Mindy",
"id": 1,
"task": "Supervisor"
}

Automatic Application of the ID Property in API Configuration

The ID Property is automatically applied in the following areas when configured:
  • For the API Data Definition, the selected field is automatically preselected on the field list of API data source field list and cannot be deselected.

    For example, if you set the ID Property to the SURROGATE_ID field from the Identification/Name Repeating Table (SPRIDEN) page, SURROGATE_ID is selected on the SPRIDEN data source.

  • For the API Schema, the ID Property appears in the schema with the reserved name (id).
    Note: This reserved name cannot be used for any other field. If another field has a conflicting name, it is automatically renamed – for example, to id1 – and this new name can be edited as needed.
    For example, if the ID Property is defined as the SURROGATE_ID field from the SPRIDEN data source and the SPRIDEN_ID field is also selected on the SPRIDEN data source, the following names appear in the schema output:
    • The SPRIDEN_SURROGATE_ID is listed on the schema as (id) and cannot be renamed.
    • The SPRIDEN_ID field is listed as (id1) and can be renamed.
  • For the Summarize operation, the ID Property is automatically included in the Group-By clause with a required status.
    Tip: If the Group-By clause that contains the ID Property is removed from the Summarize operation, the ID Property is also removed from the API details.
Add customized domains

About this task

Use the following steps to add a customized domain.

Procedure

  1. Identify the schema to add to API Designer.
  2. Access the Banner Applications Configurations (GUACONF) page in Banner Admin.
  3. Set the Application ID to BAN_GEN.
  4. On the Configurations tab, add a new row with the following details:
    • Set the Configuration Name to banner.api.designer.custom.domains.
    • Set the Configuration Type to string.

Example

The following example is a JSON object for a domain:

{

After the JSON object is added to the GUACONF page, it displays in the Domains list within the API Designer application.

Security settings overview

Security settings enable you to specify authentication methods for APIs.

API Designer offers two authentication methods. Each authentication method provides different levels of access privileges:

Table 1. Authentication method types
# Security method User requirements Returned data
1 Basic Authentication Security object on the Security Maintenance (GSASECR) page All data that is available is returned to the authenticated user.
2 User-Level Authentication Banner Self-Service roles All data that is available is returned to the authenticated user.

This user role authentication method is primarily designed for use with validation tables.
Principal ID (such as PIDM) This authentication method applies an additional user context filter to the API that returns data based on the filter.
Tip: Only PIDM is currently supported. Using this method is strongly recommended when the API returns data for multiple users.
Basic Authentication

Basic Authentication is the default security method that is applied to all of the APIs that are created by using API Designer.

Publishing an API automatically creates a corresponding security object on the Security Maintenance (GSASECR) page for the user who published it.

The security object follows this format: API_<API_NAME>

In the above example:
  • The API prefix is added.
  • The API name is converted to uppercase.
  • Any dashes (-) in the name are replaced with underscores ( _ ).

For example, an API named x-students generates the following security object: API_X_STUDENTS

The API_X_STUDENTS security object controls user access to the API. You can manually assign this object on the GSASECR page to any Principal User IDs that require access to the API. This is especially useful for supporting third-party integrations.

How does Basic Authentication work?

No additional security configuration is required to publish an API. Basic Authentication is automatically applied to all published APIs by default. No further action is needed.

APIs secured with Basic Authentication can be accessed by using one of the following methods:
Basic Authentication
For Basic Authentication, the necessary credentials (user name and password) are sent in the request header to access the API.

For example, a user with the Principal User ID that is defined in Banner Security can be used to call an API.

Open Authorization (OAuth)
OAuth is an open standard protocol that enables secure authorization for third-party applications without requiring users to share their passwords.
For example, an Ellucian Experience token can be used to call an API.
Tip:
  • When an API is run with Basic Authentication, the API returns all of the data that is available to the authenticated user without any restrictions.
  • After you publish an API with Basic Authentication, User Authentication Security settings cannot be modified.
User-Level Authentication

The User-Level Authentication method enables access control based on user roles and the Principal User ID.

You can configure User-Level Authentication to enhance security and personalization. User-Level Authentication is an optional security method that enables access control based on user roles and a Principal User ID.
Role-Based Authentication
Role-Based Authentication restricts API access according to Banner Self-Service roles such as student, faculty, employee, and other roles. Role-based Authentication ensures that only authenticated users with the appropriate role can access an API. Multiple roles are supported.
Tip:
  • When an API with Role-Based Authentication is used, the API returns all data available to the authenticated user’s role without applying additional filters.
  • After you publish an API with Role-Based Authentication, User Authentication security settings cannot be modified. Only Additional User Context Filter settings can be added or removed.

This type of authentication is especially useful for APIs that return data from validation tables. Use cases might include providing access to generic lists, such as available courses or terms.

User Context Filter Authentication
Refine Role-Based Authentication further by adding a user context filter. A user context filter restricts API access to the user's Banner Self-Service role and the user's Principal ID (currently, only PIDM is supported).
Tip: Using a User-Context Filter is highly recommended for APIs that return data for multiple users, but each authenticated user can see only their own record.

Using a User-Context Filter is particularly useful for building personalized content in Ellucian Experience cards or on Ellucian Experience pages.

How does User-Level Authentication work?

Before you publish an API, you can define User-Level Authentication in API Designer by navigating to the Security Settings.
  • To activate Role-Based Authentication, select the User Authentication check box and select one or more roles.
  • To activate User Context Filter Authentication, select both the User Authentication and the Additional User Context Filter check boxes. Then, select the data source, PIDM field, and Principal User ID.
An API secured by User-Level Authentication can only be accessed by using Open Authorization (OAuth).
  • When an API is run with Role-Based Authentication, it returns all of the available data to the authenticated user without additional restrictions.
  • When an API is run with Additional User Context Filter, it returns data specific to the authenticated user based on the applied filter.

In this example, the a-student-class API returns different results depending on the security method applied. The results are as follows:

Table 1. Authentication examples
Example Security method Number of returned roles
1 Basic Authentication 20 class records for all users
2 User-Level Authentication with Student role 20 class records for all users with the Student role
3 User-Level Authentication with Student role and additional user context filtering attributes 1 class record for that PIDM (user) with the Student role

API schema

You can define the API schema to determine how API output displays to users.

API Schema allows you to modify API properties and add parameters.

Parameters

API parameters let you define specific inputs so the system returns only the data or results relevant to business needs.

In API Designer, parameters can be used in Filters, in Filter functions, and in Custom Fields functions.

To define parameters, go to the Parameters tab in the API Schema section and provide the following details:

Parameter attribute Description
Parameter Name A unique name for the parameter
Data Type The type of data expected (for example, Integer, Number, String, Date, DateTime, or Char)
Default Value The value used as the default filter criteria
Description A brief explanation of the purpose of the parameter.

After the API is published, the response includes the default parameter value. However, you can change the criteria when calling the API.

Note: Parameters defined at the model level cannot be edited or deleted within the API schema. To modify or remove these parameters, you must modify or remove them at the model level.

For example, for the API x-email-types, the default parameter for the field emalCode is set as emailCodeParam = "HOME":

{
    "emailAddress": "test@net",
    "activityDate": "2005-09-26",
    "emalCode": "HOME"
 }

To retrieve data for a different value, such as PERS for emailCode, you can call the API by using criteria filtering. For example: x-email-types?criteria={"emailCodeParam":"PERS"}

{
    "emailAddress": "bobelliot@gmail.com",
    "activityDate": "2021-03-19",
    "emalCode": "PERS"
 }

To retrieve data for multiple values, such as PERS for emailCode and Y for preferredInd, you can call the API using multiple criteria filters. For example: x-email-types?criteria={"emailCodeParam": "PERS","preferredIndParam": "Y"}.

{ 
"emailAddress": "bobelliot@gmail.com", 
"activityDate": "2021-03-19", 
"emalCode": "PERS",
"preferredInd": "Y" 
}

You can test how the API responds to different parameter values by using the PREVIEW DATA feature before publishing the API.

When you click the PREVIEW DATA button, a dialog appears showing the list of parameters currently used by the API, each pre-filled with its default value. You can modify these values before running the preview to see how the data changes based on the updated parameter inputs, which helps to validate the API’s behavior before making it available for use.

Properties

API Designer supports a flexible set of schema properties and filters that can be used to control and refine API responses.

Schema provides a standardized framework to ensure consistency, validation, and interoperability across various systems. API Designer automatically populates all labels and descriptions for the API output based on information from the database to streamline the schema creation process.

You can view and edit certain schema components for API drafts. For published APIs, these components are read-only. Editable and viewable schema components include:
  • HTTP Method
  • Authentication Type
  • Property Names
  • Data Sources
  • Field Names
  • Labels
  • Data Types
  • Descriptions
You can view the API Schema in two formats:
  • The Summary list displays all properties at a glance.
  • The Individual Property View focuses on a single property with detailed information.
For each property in API drafts, you can modify the following fields:
  • Property Name is the key that appears in the JSON output for the API for the corresponding column.
  • Label is a user-friendly name that displays in the API Registry and API Selector.
  • Description contains additional information about the property that is also shown in the API Registry and API Selector.
Tip: The Data Source, Field Name, and Data Type schema elements depend on column data and cannot be modified.

API Designer versioning

You can publish new APIs as a "1.0.0 version" (v1.0.0) or republish APIs as different versions.

When you publish an API for the first time, it is always published as version 1.0.0 (v1.0.0). When you republish an API, you are prompted to increment the version. Version updates follow Semantic Versioning (SemVer) and can be one of the following types:
  • Major (from v1.0.0 to v2.0.0)
  • Minor (from v1.0.0 to v1.1.0)
  • Patch (from v1.0.0 to v1.0.1)
For example, if you want to republish the API, x-student v1.0.0 to a new version, you can update it as follows:
  • x-student v1.0.1 (patch)
  • x-student v1.1.0 (minor)
  • x-student v2.0.0 (major)

Published versions appear in the Version column of the published API list.

Tip: For the example above:
  • Republishing with a major version creates a separate, new API entry. For example, both x-student v1.0.0 and x-student v2.0.0 are listed as active APIs.
  • When a minor or patch version is published, it replaces the previously listed version in the Published APIs page list. For example, x-student v1.0.0 is replaced by x-student v1.1.0 (minor) or by x-student v1.0.1 (patch) in the API list.

Additional behavior during import

During the import (single or bulk) of an API that has multiple published versions, a draft link is created only for the highest version, even if that version has a Deprecated status.

API import behavior

Understand how single and bulk API imports work, including name conflict handling, dependent models, and how imported APIs are saved as drafts.

You can import APIs from a JSON file as either a single API or multiple APIs in bulk. All imported APIs are saved as draft APIs.

Name conflict behavior on import

The following name conflict behavior applies to each API.
  • You can optionally update the API Name, Domain, and Description before saving.
  • If a published API with the same name exists, keeping the same name creates a draft copy of the published API. Changing the name creates a new, independent draft API.
  • If a draft API with the same name exists, a warning indicates that saving will overwrite the existing draft.
  • If a model with the same name exists, a warning indicates that you can change or overwrite the model name.
Tip: Review API names carefully during import to avoid unintentionally overwriting an existing draft.

Bulk API import

If the uploaded file contains multiple APIs, a dialog window displays listing all APIs available for import including detail information.
  • By default, all eligible APIs are selected for import. You can manage selections using the Select All and Deselect All options or by manually selecting or clearing individual APIs.
  • You can edit individual APIs before import by clicking Edit for a specific API and modifying the API name, Domain, and Description.

Import dependent models

Imported APIs can include dependent models. During import, you can control how these models are created or updated in the target environment.

Model rename or override actions are available for both single API import and bulk API import.

If a model in the import file has the same name as an existing model, you must choose how to resolve the conflict:
  • Rename the model to create a new model.
  • Override the existing model.

If the existing model is used in a published API, the override option is not available. You must rename the model before importing the API.

Tip: Review model dependencies and naming conflicts before importing to avoid issues with published APIs and to maintain consistent model usage.

For published APIs, there are additional considerations to make sure that you can delete an API successfully:

      • If only one version of the API exists, the Keep security object check box displays during deletion.
